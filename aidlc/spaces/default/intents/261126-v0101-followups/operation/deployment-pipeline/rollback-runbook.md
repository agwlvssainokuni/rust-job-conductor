# 戻し方の手順: v0.10.1

出典: `deployment-pipeline-questions.md` の Q4(まとめの確かめ済み)、`cd-config.md`、`deployment-strategy.md`、team.md の Deployment、v0.10.0 の `rollback-runbook.md`、要件の NFR1。

## 公開の前(下書きのうち)

| 場面 | 手順 |
|---|---|
| `release.yml` のどれかのジョブが落ちた | 原因を `main` で直して CI を通す → `git push origin :refs/tags/v0.10.1` と `git tag -d v0.10.1` でタグを消す → 直したコミットの上にタグを付け直して push |
| 下書きを確かめて問題が見つかった | 下書きのリリースを消す(`gh release delete v0.10.1`)→ 上と同じくタグを消し、直してから付け直す |

- 公開前は利用者に届いていないため、利用者への影響は無い。
- `checks` の `coverage` で性能のテストが上限を超えたときは、上限を下げずに、`construction/build-and-test/build-and-test-summary.md` の「原因不明の失敗の記録の手順」で記録する。同じ CI を再び走らせて通ったときも、記録は残す。

## 公開の後

| 場面 | 手順 |
|---|---|
| 利用者が困る不具合 | 前の版 v0.10.0 のリリースは残るため、利用者はそのバイナリに戻せる。直したものを v0.10.2(3 桁目を上げる。team.md)として同じ流れで出す |
| 公開を取り下げる | リリースを下書きに戻すか消す。タグは残し、v0.10.2 で置き換える(公開した版の付け直しはしない) |

## 互換の注意(v0.10.1 と v0.10.0 の行き来)

- ステートの形、定義の書式は変えていない(要件の NFR1)。v0.10.1 と v0.10.0 の間で、ステートと定義ファイルはそのまま使える。
- ログの名前: 空白を除くと Windows の予約名になるジョブ ID だけ、v0.10.0 と v0.10.1 でログの名前が違う(例: `con ` は v0.10.0 で `con_…`、v0.10.1 で `_con_…`)。戻しても、すでにあるログのファイルは消えず、新しい試行のファイルが前の版の名前で作られるだけ。
