# 配り方: v0.10.1

出典: `deployment-pipeline-questions.md`(Q1〜Q5、まとめの確かめ済み)、`cd-config.md`、team.md の Deployment・Way of Working、project.md の Mandated、要件の FR2.2。

## やり方

- **一度に全部(下書きを経る)**: 単一バイナリの CLI で、利用者が自分で取ってくるため、段階的な切り替え(blue/green、canary)は当てはまらない。代わりに「下書きのリリース」が人の確かめの段になる(Q3)。
- 環境は 1 つ(利用者の手元)。ステージングは無い(Q1)。

## 手順

1. `main` が最新で、CI がすべて通っていることを確かめる(45912018052 で確認済み。記録のコミットの後の CI も確かめる)。
2. `main` の上にタグ `v0.10.1` を付けて push する(人が行うか、人の頼みで AI が行う)。
3. `release.yml` の 4 つのジョブが通るのを見る。
4. 下書きのリリースの成果物、`SHA256SUMS`、自動の注記を確かめ、v0.10.1 の変更を注記に足す(Q5)。
   - F1: README の `watch --follow` の注意の書き直し。
   - F2: ログの名前で、空白を除いて予約名と比べるようにした。**空白を除くと Windows の予約名になるジョブ ID(例: `con `、` con`、`con .x`)のログの名前が v0.10.0 と変わる(`con ` → `con_` だったものが `_con_`)**。読み取りの前にも「止める」印を見るようにした。
   - F3: 計画(`--dry-run`)の模擬を速くした(1,000 ジョブで約 7 分の 1)。出力は変わらない。
   - F5: デモの場面 4 で、`DEMO_PAUSE=1` のとき `watch --follow` の前で待つ。
   - 文書: 仕様書の誤りの種類の数(34 種)と、runtime の契約の表を直した。
5. 公開は人が確かめてから行う。

## smoke test

- `build` のジョブが、展開したバイナリの `--version` を 3 対象で確かめる(Intel macOS はクロスビルドのため除き、注記に書く)。
- 公開の後、利用者の手元では `conductor --version` が `conductor 0.10.1` を出すことで確かめられる。

## 中止の条件

- `verify-tag` か `checks` か `build` が落ちたら、下書きは作られない。原因を直してから、タグを消して付け直す(`rollback-runbook.md`)。
