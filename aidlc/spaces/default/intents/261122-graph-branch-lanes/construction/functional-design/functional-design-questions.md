# 機能の設計の質問(Functional Design Questions): graph の text 表示の改善 その 2

## 先に分かったこと(git の出力では、この形の図は取れない)

`git log --graph` は、起点のコミットから**たどれるコミットだけ**を描く。「`a` の成功が `c`、警告が `d`」の形では、`a` から `b` へたどれない(`b` は、`a` の次のジョブだが、`a` の親ではない)ので、git の出力に `b` が出ない。

```text
*   a
|\
* | c
|/
* d
* e
o @end
```

(`b` が無い。記述順に全ジョブを並べる `conductor graph` の図とは別物。)このため、前回の「同じ行き先」のように、git の出力をそのまま正解データにすることはできない。そこで、前回の「両方の飛び越し」と同じ流儀で、**規則から図を導いて、ユーザーが見て承認する**進め方になる。

## Q1. [プロダクト] この形の描き方

背景: 前回の「両方の飛び越し」では、飛び越される間の主線の `|` を省き、`\` と `/` だけを描きました(`a` から `b`、`b` から `c` への線は、実際にはないため)。この形も、`a` から出る 2 本の線(成功と警告)を、同じ流儀で描く案です。2 本の線は、1 つの分岐の行で同時に出し(` \ \`)、近い行き先(`c`)が内側、遠い行き先(`d`)が外側になります。

見本 B1(5 ジョブ、`a` の成功が `c`、警告が `d`):

```text
*     a
 \ \
* | | b
 / /
* | c
 /
* d
* e
o @end
```

見本 B2(4 ジョブ、`a` の成功が `c`、警告が終点):

```text
*     a
 \ \
* | | b
 / /
* | c
* | d
 /
o @end
```

見本 B3(7 ジョブ、外側に通常の飛び越し `a` が `g` へ、`b` の成功が `d`、警告が `e`):

```text
*   a
|\
* \     b
 \ \ \
* | | | c
 / / /
* | | d
 / /
* | e
* | f
|/
* g
o @end
```

- A. この描き方で進める(2 本の線を同時に出し、主線の `|` を省く)
- B. 別の描き方にしたい(Other に、イメージを書く)
- X. Other (please specify)

[Answer]: A

## Q2. [プロダクト] 範囲: どこまでを図にするか

背景: 2 本の線が、既存の線と、同じ行き先で合流する形や、交差する形まで含めると、形の数が大きく増えます。

- A. 2 本の線が、どちらも新しい線で、既存の線の内側に収まる形(入れ子か、並び)だけを図にする。同じ行き先への合流を含む形と、交差する形は、従来どおり辺の一覧(後回し)
- B. A に加えて、同じ行き先への合流(前回の `|\|` と同じ規則)を含む形も図にする
- X. Other (please specify)

[Answer]: A

## Q3. [開発者] 正解データの作り方

背景: git では取れないので、正解データは、規則から導いた図(試作のスクリプトで生成)になります。前回の「両方の飛び越し」は、通常の図と主線の `|` を除いて一致することで、間接的に確かめました。今回は、2 本の線の形が新しいため、間接的な確かめ方が使えません。

- A. 範囲(Q2)の全形(ジョブ 2〜8 個)の図を、規則から生成して、テスト用のファイルにする。「git では確かめられず、規則から導いた」と、ファイルの先頭に明記する。ユーザーは、設計の段階で、代表的な図を見て承認する
- B. 代表的な図(10 個ほど)だけを、手で書いて、テストにする
- X. Other (please specify)

[Answer]: A
