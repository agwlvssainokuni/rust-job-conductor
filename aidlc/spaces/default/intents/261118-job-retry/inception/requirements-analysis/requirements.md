# Requirements — 正常終了しなかったジョブの自動リトライ

## Sources

- 意図の整理: `ideation/intent-capture/intent-statement.md`(`intent-statement`)
- 範囲の定義: `ideation/scope-definition/scope-document.md`(`scope-document`)と `intent-backlog.md`(IB1〜IB5)
- 既存コードの調査: `aidlc/spaces/default/codekb/rust-job-conductor/` の `business-overview.md`、`architecture.md`、`code-structure.md`
- 確認事項の回答: `requirements-analysis-questions.md`(Q1〜Q11。Q10 と Q11 は、レビューの指摘への対応で追加)
- 依頼文: 「ジョブが所定の終了コードで終わったとき、最大 N 回、設定した間隔を空けて自動でリトライする機能を追加する」

## Intent analysis

- 目的: 一時的な失敗でジョブが止まるたびに手で再実行する手間をなくし、定期実行が人の手を借りずに終わる割合を上げる。(`intent-statement`)
- 現状: `conductor` は「自動の再試行はしない」と明記している(README、`core/src/flow/next_step.rs`、`runtime/src/lib.rs`、`cli/src/pipeline.rs`)。呼び出す側のスクリプトやスケジューラで再実行している。(`intent-statement`、`architecture.md`)
- 方針: ジョブごとの設定として、所定の終了コードのときに、間隔を空けて、最大 N 回、同じジョブを実行し直す。設定がなければ今までと同じ動作にする。(`scope-document`、Q1〜Q9)
- 位置づけ: リトライは、ジョブの終了コードが「エラー」と分類された直後に、同じジョブをもう一度実行する形で挟まる。(`architecture.md` のリトライの置き場所の節)

## Functional requirements

### FR1 設定(ジョブごと)

- FR1.1 ジョブの定義に、リトライする終了コードの一覧、最大回数 N、リトライの間隔を書ける。合格基準: 3 つを書いた定義が `validate` を通り、`run` が書いたとおりに動く。(Q1、`scope-document`)
- FR1.2 リトライの終了コードの一覧を書かないジョブは、リトライしない。合格基準: 一覧のないジョブがエラーで終わったとき、再実行されない。(Q1: A)
- FR1.3 リトライの終了コードの一覧が、そのジョブの成功や警告の終了コードと重なったら、定義の誤りにする(終了コード 64、`validate` も同じ)。合格基準: 重なる定義で `run` はジョブを実行せず 64 で終わり、`validate` が失敗する。(Q2: A)
- FR1.4 リトライの間隔は、整数と単位 `s`、`m`、`h` のいずれかからなる文字列で書く(例: `"30s"`、`"2m"`、`"1h"`)。合格基準: この書式の値が受け付けられ、ほかの書式(小数、ほかの単位、単位なし、空)は定義の誤りになる。(Q3: C、Q9: A)
- FR1.5 回ごとに間隔を伸ばす方式は、倍率(整数)と、間隔の上限の 2 つを指定する。合格基準: 2 つを書いた定義が受け付けられ、倍率が整数でない、または上限が間隔の書式でない定義は誤りになる。(Q4: A)
- FR1.6 リトライの項目を書かない定義ファイルは、これまでと完全に同じ動作のままにする。合格基準: リトライの項目を含まない既存の定義とテストが、変更なしで通る。(`scope-document`、IB3)
- FR1.7 リトライの終了コードの一覧を書いたジョブは、最大回数 N と間隔も必ず書く。どちらかを省略した定義は、定義の誤り(64、`validate` も同じ)にする。合格基準: 一覧だけを書いた定義と、一覧と N だけ(または間隔だけ)を書いた定義で、`run` はジョブを実行せず 64 で終わり、`validate` が失敗する。(Q10: A)
- FR1.8 リトライの値の範囲: 最大回数 N は 1 以上、間隔は 1 秒以上、倍率は 2 以上の整数とする。範囲を外れた定義(N=0、間隔 `"0s"`、倍率 1 以下、負の値)は定義の誤りにする。合格基準: 範囲の境界(N=1 と 0、間隔 `"1s"` と `"0s"`、倍率 2 と 1)で、内側は受け付けられ、外側は誤りになる。(Q11: A)
- FR1.9 倍率と上限は、両方を書くか、両方とも書かない(固定の間隔)かのどちらかにする。一方だけを書いた定義は、定義の誤りにする。合格基準: 倍率だけ、または上限だけを書いた定義で、`run` は 64 で終わり、`validate` が失敗する。([assumption]。Q4 は 2 つを指定すると決めており、一方だけの扱いは確認していない)

### FR2 間隔

- FR2.1 固定の間隔のとき、すべてのリトライの前に、書いた間隔だけ待つ。合格基準: 間隔 `"30s"` で、各リトライの前の待機が 30 秒である。(Q1、`scope-document`)
- FR2.2 伸ばす方式のとき、最初のリトライの前は書いた間隔だけ待ち、以降のリトライでは、直前の待機に倍率を掛けた間隔だけ待つ。ただし、上限を超えない。合格基準: 間隔 `"10s"`、倍率 2、上限 `"60s"` で、待機が 10 秒、20 秒、40 秒、60 秒、60 秒の順になる。(Q4: A。式は [assumption]。下の前提を参照)

### FR3 実行

- FR3.1 ジョブが、リトライの一覧にある終了コードで終わったとき、間隔を空けて、同じジョブを実行し直す。合格基準: 一覧にあるコードで終わるジョブが、設定した回数まで、実行し直される。(依頼文、Q1)
- FR3.2 最大回数 N は、最初の実行に加えて実行し直す回数である(合計で最大 N+1 回実行する)。合格基準: N=3 で、常に対象のコードで終わるジョブが、ちょうど 4 回実行される。(Q5: A)
- FR3.3 実行し直したジョブが、成功または警告の終了コードで終わったときは、通常と同じ遷移で先に進む。合格基準: 2 回目で成功したジョブの後続のジョブが実行され、記録される結果は成功である。(Q1、既存の遷移)
- FR3.4 最大回数まで実行し直しても、まだ対象のコードで終わるときは、通常のエラーと同じ扱いにする。最後の試行の終了コードで終わり、再開位置はそのジョブになる。合格基準: 使い切ったあとの終了コードと、ステートファイルが、リトライなしで同じコードでエラーになったときと同じである。(Q6: A)
- FR3.5 リトライは、`run`(ジョブ 1 つ)と `pipeline`(パイプライン全体)の両方で動く。合格基準: どちらのコマンドでも FR3.1〜FR3.4 が成り立つ。(`architecture.md`: 両方に同じ流れがある)
- FR3.6 リトライの対象は、ジョブ自身の終了コードがエラーと分類された場合だけにする。ジョブを起動できなかった場合(127)、シグナルで終了した場合、conductor が中断した場合は、対象にしない。合格基準: これらの場合に、リトライの一覧の内容にかかわらず、実行し直されない。([assumption]。下の前提を参照)

### FR4 中断(シグナル)

- FR4.1 間隔の待機中に中断のシグナルを受けたら、すぐに待機をやめ、いまの中断と同じ動きにする。128 + 番号で終わり、再開位置はそのジョブになる。エラーとしては記録しない。合格基準: 待機中にシグナルを送ると、128 + 番号で終わり、ステートファイルにそのジョブが再開位置として残り、エラーの記録はない。(Q7: A)
- FR4.2 ジョブの実行中のシグナルは、これまでと同じ(子に転送して終わる)にする。合格基準: 既存のシグナルのテストが変更なしで通る。(Q7、既存の動作)

### FR5 ステート(再開)

- FR5.1 リトライの回数は、ステートファイルに記録しない。ステートファイルの形式(`format_version = 1`)は変えない。合格基準: リトライを使った実行のステートファイルが、これまでの conductor で読め、キーが増えない。(Q8: A)
- FR5.2 リトライの途中で止まったあとの再開では、そのジョブを最初の実行から数え直す。合格基準: 途中で止めて再開すると、そのジョブの最初の試行として実行され、リトライの回数が N に戻る。(Q8: A。at-least-once の範囲内)

### FR6 表示

- FR6.1 リトライの前に、何回目のリトライか(最大回数 N のうち)と、次の実行までの待ち時間を表示する。合格基準: 各リトライの前に、これらを含む行が出る。(`scope-document`、IB4)
- FR6.2 表示の文言は、英語と日本語の両方に用意し、ロケールに従う。合格基準: 日本語と英語の環境で、それぞれの言語で表示される。(既存の表示の方針)

### FR7 検証と変換

- FR7.1 `validate` が、リトライの項目の誤り(FR1.3〜FR1.5 と FR1.7〜FR1.9 の誤り)を検出する。合格基準: 誤りのある定義で `validate` が失敗し、ジョブは実行されない。(`architecture.md`、既存の `validate`)
- FR7.2 `convert`(YAML と TOML の相互変換)が、リトライの項目を失わずに変換する。合格基準: リトライの項目を含む定義を往復変換して、同じ内容になる。(`architecture.md`: 変換は項目の中身に依存しない)

### FR8 文書

- FR8.1 README に、リトライの項目の書き方、動き、at-least-once との関係(リトライするジョブは、同じ処理が複数回走っても困らないことが必要)を書く。合格基準: README に説明があり、CI の `docs-check`(必須の語の検査)が通る。(意図の整理 Q7: A、`business-overview.md`)

## Non-functional requirements

- NFR1 互換性: リトライを設定しない定義の、動作、出力、終了コードを変えない。合格基準: 既存のテストが、アサーションの変更なしで通る。(FR1.6、`intent-statement`)
- NFR2 既存の検査の維持: `unsafe` の禁止(cli)、`platform/` の外での OS 別の `cfg` の禁止、ネットワークを使わないこと、を保つ。合格基準: 既存の `nfr_source` のテストが通る。(`code-structure.md`)
- NFR3 テストのしやすさ: 間隔の待機を、実際の時間を待たずにテストできる。合格基準: 間隔が 1 時間のリトライのテストが、実際に待たずに完了する。(`architecture.md`: 時間と待機の差し込み口がない)
- NFR4 カバレッジ: 行カバレッジ 80% の下限を維持する。合格基準: CI の `coverage` ジョブが通る。(`team.md`)
- NFR5 3 つの OS: Linux、macOS、Windows で同じ動作にする。合格基準: CI の 3 つの OS のテストが通る。(`business-overview.md`)
- NFR6 依存の維持: 新しい外部クレートを追加せず、`-sys` クレートと C のビルド依存を増やさない。合格基準: `Cargo.toml` の依存の一覧が増えず、CI の `build-check` の検査が通る。([assumption]。標準ライブラリだけで待機できる見込み)
- NFR7 待機の打ち切りの速さ: 間隔が長くても、待機中にシグナルを受けたら、1 秒以内に待機をやめる。合格基準: 間隔 1 時間のリトライの待機中にシグナルを送り、1 秒以内に終わる。([assumption]。1 秒は目安として置いた値)

## Constraints

- C1 リトライの項目の値は整数と文字列で表す(小数は使わない)。理由: ジョブの定義の型が `Eq` を導出している。(`code-structure.md`)
- C2 出力の内容でのリトライの判定と、リトライの結果の外部への通知は、この機能に含めない。(`intent-statement` の Initial Scope Signal)
- C3 ステートファイルの形式は変えない。(Q8: A)
- C4 利用者への周知は README の更新だけで行う。(意図の整理 Q7: A)
- C5 チームの方針に従う: test-after、`cargo fmt` と `cargo clippy -D warnings`、変更は小さな単位で、こまめにコミットする。(`team.md`)

## Assumptions

- A1 [assumption] 伸ばす方式の間隔は、「最初は書いた間隔、以降は直前の間隔 × 倍率、上限で頭打ち」とする(FR2.2)。Q4 は倍率と上限を指定するとだけ決めており、式は確認していない。
- A2 [assumption] ジョブを起動できなかった場合(127)、シグナルで終了した場合、conductor が中断した場合は、リトライしない(FR3.6)。リトライしても直らない失敗を繰り返さないための前提で、確認していない。
- A3 [assumption] 設定の項目名と形(平らなキーか、ジョブの下の表か)は、設計の段階で決める。
- A4 [assumption] リトライの途中の表示は、`-v` なしの通常の出力に出す(FR6.1)。表示のレベルは確認していない。
- A5 [assumption] NFR7 の 1 秒、NFR6 の標準ライブラリだけで待機できること、は目安の前提である。
- A6 [assumption] 倍率と上限は、両方を書くか、両方とも書かないかのどちらかにする(FR1.9)。Q4 は 2 つを指定すると決めており、一方だけを書いた定義の扱いは確認していない。

## Out of scope

- 出力の内容でのリトライの判定(意図の整理 Q6: B)
- リトライの回数や結果の、外部への通知(意図の整理 Q6: C)
- 全ジョブ共通の既定のリトライ設定、パイプライン全体だけの設定(Q2 範囲の定義で、ジョブごとだけが選ばれた)
- ステートファイルへの回数の記録(Q8: A)

## Open questions

- 項目名と形、最大回数・間隔・倍率・上限の「上側」の最大値(極端に大きい値と、倍率を掛けたときの桁あふれの扱い)(Functional Design で決める。下側の範囲と省略の扱いは FR1.7、FR1.8 で決めた)
- 起動できなかった場合(127)と、ジョブ自身が 127 で終わる場合の区別、リトライの表示の出力先(標準出力か標準エラーか)、NFR7 の合否の確かめ方(時間の差し込み口による擬似的な検証を含む)(Functional Design で決める)
- A1、A2、A4、A6 の確認(User Stories と Functional Design で、受け入れ基準に落とすときに確認する)
- 次の隅の扱い(Functional Design で決める): 終了コードの一覧がなく、最大回数や間隔だけがある定義(FR1.2 で黙って無視するか、定義の誤りにするか)、空の一覧(`[]`)、上限が間隔より小さい定義
