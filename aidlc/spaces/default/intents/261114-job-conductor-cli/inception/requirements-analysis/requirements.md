# Requirements

上流: intent-statement(課題・利用者・成功基準)、scope-document(初版の範囲と優先度)、team-practices(テスト・CI・コードの実践)。取り込み済みの要件定義書の記述を一次入力として分析し、確認済みの回答 Q1〜Q9(requirements-analysis-questions.md)と、ここまでのステージの成果物を根拠とする。優先度は MoSCoW。

## Intent Analysis

- 既存のジョブ実行環境は、ジョブを一列に順次実行するだけで、終了判定も限定的なため、警告時の分岐やスキップができない。ジョブ間で実行状態を引き継げないことも課題である。(intent-statement)
- 環境自体は変えず、各ジョブの呼び出しに `conductor` をラッパーとして挟み、分岐・スキップ・ステート管理を上位レイヤーで補う。個別のステップ実行と、パイプライン一括実行の両方を扱う。(intent-statement、要件定義書)
- 初版の成功基準は、「個別実行」と「一連の実行」の2モードで、警告時の分岐・スキップが定義どおりに動作すること。(intent-statement)

## Functional Requirements

### FR1 定義ファイル(`conductor.toml`)【Must】

複数のジョブ、コマンド、終了ステータスの対応、遷移ルールを1つのファイルに集約する。

- **FR1.1** 定義ファイルは、パイプラインの基本情報(名前、説明)を持てる。 要件定義書
- **FR1.2** 各ジョブは、ジョブID、実行コマンド、警告とみなす終了コード(`warning_exit_codes`)、成功とみなす終了コードを持てる。終了コード 0 は既定で成功である。 [Q1]
- **FR1.3** 各ジョブは、結果(成功・警告・エラー)ごとの遷移ルールとして、遷移先のジョブIDを指定できる。 要件定義書、[Q3]
- **FR1.4** 起動時に定義ファイルを検証し、誤り(記述ミス、存在しないジョブIDなど)があれば、ジョブを一切実行せず、ファイル名・行・原因を表示して異常終了する。 [Q5]、wireframes(Rough Mockups の Q5)

受け入れ基準:
- Given 正しい定義ファイルがある、When `conductor run <job-id>` を実行する、Then 定義に従ってジョブが実行される。
- Given 遷移先に存在しないジョブIDを書いた定義ファイルがある、When `conductor run <job-id>` を実行する、Then ジョブは実行されず、ファイル名・行・原因が表示され、非0で終了する。
- Given 定義ファイルが存在しない、When `conductor run <job-id>` を実行する、Then ジョブは実行されず、存在しないファイルのパスが表示され、非0で終了する。

### FR2 個別実行モード(`conductor run <job-id>`)【Must】

既存のスケジューラから、ジョブIDを指定して1ステップずつ呼び出される。

- **FR2.1** 指定されたジョブのコマンドを、シェルを介さず、コマンド名と引数に分けて直接起動する。 [Q6]
- **FR2.2** ジョブの終了コードを、成功・警告・エラーに分類する。0 または成功コードは成功、`warning_exit_codes` の値は警告、それ以外の非0はエラーとする。 [Q1]
- **FR2.3** 分類結果と遷移ルールに従い、後続ジョブのスキップ、または代替ジョブへのジャンプを、ステートに書き込む。遷移先を指定した場合、現在のジョブと遷移先のあいだのジョブはスキップ扱いとする。 要件定義書、[Q3]
- **FR2.4** 後続のジョブが呼び出されたとき、ステートを参照し、スキップ対象であれば実処理をせず、即座に終了コード 0 で終了する。 要件定義書、intent-statement
- **FR2.5** スケジューラへ返す終了コードは、警告のときは 0、エラーのときはジョブの終了コードをそのまま(非0)とする。 [Q2]
- **FR2.6** ジョブ本体の標準出力・標準エラーは、そのまま通す。`conductor` 自身の表示は、オプションで有効にしない限り出さない。ただし定義ファイルの誤りなど `conductor` 自身のエラーは、オプションの有無にかかわらず常に表示する。 wireframes(Rough Mockups の Q2、Q3、Q7)
- **FR2.7** ジョブの実行時間に上限は設けない。ジョブのタイムアウトは、ジョブ側またはスケジューラ側で管理する。 [Q7]
- **FR2.8** 同じ定義・ステートに対する同時実行の排他制御は行わない。同時実行は利用者側で避ける。 [Q5]

受け入れ基準:
- Given 警告の終了コードを返すジョブで、警告時の遷移先が定義されている、When そのジョブを `conductor run` で実行する、Then 終了コード 0 で終了し、ステートに遷移先までのスキップが記録される。
- Given 前のジョブの警告でスキップ対象になったジョブがある、When そのジョブを `conductor run` で呼び出す、Then コマンドは実行されず、終了コード 0 で終了する。
- Given エラーの終了コード(警告に指定していない非0)を返すジョブ、When `conductor run` で実行する、Then ジョブの終了コードがそのまま返る。
- Given 存在しないコマンドを指定したジョブ、When `conductor run` で実行する、Then エラーの原因が表示され、非0で終了する。

### FR3 一連の実行モード(`conductor pipeline <pipeline-name>`)【Must】

定義されたパイプライン全体を `conductor` 自身が駆動して実行する。

- **FR3.1** 定義されたジョブを順に実行し、各ジョブの結果と遷移ルールに従って、スキップ・ジャンプを行う。 要件定義書
- **FR3.2** ジョブがエラーで終わった場合、そこで停止し、ジョブの終了コード(非0)で終了する。自動での再試行はしない。 [Q9]

受け入れ基準:
- Given 3つのジョブを定義し、すべて成功する、When `conductor pipeline` を実行する、Then 3つが順に実行され、終了コード 0 で終了する。
- Given 2つ目のジョブが警告で、警告時の遷移先が4つ目のジョブである、When `conductor pipeline` を実行する、Then 3つ目のジョブはスキップされ、4つ目が実行される。
- Given 2つ目のジョブがエラーになる、When `conductor pipeline` を実行する、Then 3つ目以降は実行されず、非0で終了する。

### FR4 ステート管理【Must】

実行状態を、ローカルのステートファイルで保持する。

- **FR4.1** 遷移情報(スキップ・ジャンプ)と、各ジョブの実行結果を、ローカルのステートファイルに保持する。ステートファイルは、実行ディレクトリの近傍に保存する。 要件定義書、intent-statement
- **FR4.2** パイプラインが最後まで終わったとき、ステートは次回に備えて自動で初期化される。 [Q4]
- **FR4.3** ジョブがエラーで終わったとき、ステートは保持される。同じパイプラインを再び流すと、エラーになったジョブから再開し、前に成功したジョブはステートに従ってスキップ扱いとする。最初からやり直すときは、`conductor reset` で初期化してから流す。 [Q9]
- **FR4.4** ステートファイルへの書き込みは、途中で中断されても壊れた内容が残らないようにする(書き込み途中のファイルを完全なものとして読まない)。 [assumption](Assumptions を参照)
- **FR4.5** ステートファイルが読めない、または壊れている場合は、ジョブを実行せず、原因とファイルのパスを表示して、非0で終了する。 [assumption](Assumptions を参照)

受け入れ基準:
- Given 3つのジョブを個別実行で最後まで実行した、When 最後のジョブが終わる、Then ステートは初期化され、次に最初のジョブを実行できる。
- Given 2つ目のジョブがエラーで終わった、When 同じパイプラインを再度流す、Then 1つ目はスキップされ、2つ目から再開する。
- Given ステートファイルが壊れている、When `conductor run <job-id>` を実行する、Then ジョブは実行されず、ステートファイルのパスと原因が表示され、非0で終了する。

### FR5 状態の確認(`conductor watch`)【Should】

- **FR5.1** 現在の実行状態(ジョブごとの状態)を一覧で1回表示して終了する。変更を追って表示し続けることはしない。 wireframes(Rough Mockups の Q4)、scope-document

受け入れ基準:
- Given 一部のジョブが実行済みでステートがある、When `conductor watch` を実行する、Then ジョブごとの状態が一覧で表示され、コマンドが終了する。
- Given ステートが空(初期状態)である、When `conductor watch` を実行する、Then ステートが空であることが表示され、エラーにならない。

### FR6 状態の初期化(`conductor reset`)【Must】

- **FR6.1** 保持しているステートを初期化する。ステートがない場合も、エラーにならない。 要件定義書、scope-document

受け入れ基準:
- Given エラー終了で残ったステートがある、When `conductor reset` を実行する、Then ステートが初期化され、次の実行は先頭から始まる。
- Given ステートがない、When `conductor reset` を実行する、Then エラーにならず、終了コード 0 で終了する。

### FR7 定義ファイルの変換(`conductor convert <file> --to <format>`)【Should】

- **FR7.1** 定義ファイルを、YAML から TOML、または TOML から YAML へ変換する。 要件定義書、scope-document
- **FR7.2** 入力が読めない、または形式が誤っている場合は、変換せず、原因を表示して非0で終了する。 [assumption](Assumptions を参照)

受け入れ基準:
- Given 正しい TOML の定義ファイル、When `conductor convert <file> --to yaml` を実行する、Then 同じ内容の YAML が得られる。
- Given 文法が壊れた入力ファイル、When `conductor convert` を実行する、Then 変換は行われず、原因が表示され、非0で終了する。

## Non-Functional Requirements

- **NFR1 起動オーバーヘッド** `conductor` の起動から、ジョブの起動(またはスキップの判定)までを、100ms 以内とする。測定条件(使用する環境、定義ファイルの規模)は、後続のステージで定める。 [Q8]
- **NFR2 単一バイナリ** 外部ランタイム(JVM やインタプリタなど)に依存せず、OS ネイティブの単一バイナリとして動作する。 要件定義書、intent-statement
- **NFR3 対応OS** Linux・macOS・Windows のすべてで動作する。主な開発環境の OS 以外は、CI(GitHub Actions)で検証する。 constraint-register の C3、team-practices
- **NFR4 型安全と早期検知** 定義ファイルの読み込みとステートの読み書きで、型の誤りや設定ミスを、ジョブ実行の前に検知する。 要件定義書
- **NFR5 テスト** 行カバレッジ 80% を下限とし、`cargo test` による単体テストと、バイナリを実行する統合テストを含める。 team-practices
- **NFR6 表示の判別性** 状態の表示は、色だけに頼らず文字でも判別できる。端末以外への出力では、色を自動で無効にする。 wireframes(Rough Mockups の Q6)

受け入れ基準:
- NFR1: Given 通常規模の定義ファイル、When `conductor run <job-id>` を同じ環境で繰り返し測定する、Then `conductor` 自身のオーバーヘッドが 100ms 以内に収まる。
- NFR3: Given 3つの OS の CI、When テストを実行する、Then すべてで合格する。
- NFR6: Given 出力が端末ではなくファイルにリダイレクトされている、When `conductor watch` を実行する、Then 色の制御文字が含まれない。

## Constraints

- 既存のジョブ実行環境そのものは変更しない。 constraint-register の C1
- スケジューラが受け付ける終了コードは 0 / 非0 の2値のみである。 constraint-register の C2
- 実装言語は Rust で、開発者は Rust に不慣れである。 constraint-register の C4、C5
- 期限・予算の制約はなく、規制・機密データに関する要件もない。 constraint-register の C7、C8、C9
- 開発の進め方: `main` を統合先とし、squash せずに履歴を残す。ウォーキングスケルトンは作らず、機能を1つずつ順に作る。test-after で実装する。 team-practices

## Assumptions

- 本ステージのコーナー確認(ファイル・形式・状態・同時実行・設定)から、次を前提とする。いずれも、あなたが修正できる。 [assumption]
  - FR4.4(ステートの書き込みを中断に強くする)と FR4.5(壊れたステートでは実行せずエラーにする)は、質問せずに採用した既定である。理由: 壊れた内容を完全なものとして読むと、スキップや遷移を誤り、誤ったジョブを実行するため。 [assumption]
  - FR7.2(変換の失敗時は変換せずエラーにする)は、質問せずに採用した既定である。理由: 入力を壊したまま出力しないため。 [assumption]
  - 定義ファイルは `conductor.toml` を直接読み、YAML は `convert` で変換してから使う(YAML を直接読むことは初版の範囲外)。理由: 要件定義書が TOML を定義ファイルとし、YAML は変換機能としてのみ挙げているため。 [assumption]
  - ジョブのコマンドは、1つの文字列として書かれたものを、コマンド名と引数に分けて起動する(Q6 でシェルを介さないと確認)。引用符で囲んだ引数(例: `--msg='...'`)の分け方は、設計で定める。 [assumption]
  - 排他制御は行わないため(FR2.8)、同時実行したときのステートの整合は保証しない。利用者側で同時実行を避ける。 [assumption]

## Out of Scope

- 通知機能(Slack 通知など)そのものの組み込み。通知はジョブ側のスクリプトで行う。 intent-statement
- 複数ホストにまたがる分散実行・ステート共有。 intent-statement
- Web UI / GUI。 intent-statement
- エラー時の自動での再試行。 [Q9]
- ジョブの実行時間の上限(タイムアウト)を `conductor` が管理すること。 [Q7]
- 同じパイプラインの同時実行に対する排他制御。 [Q5]

## Open Questions

- 個別実行モードで、「パイプラインが最後まで終わった」ことを、どのジョブをもって判定するか(定義上の最後のジョブか、遷移の終点か)。ステートの自動初期化(FR4.2)に関わる。 要確認
- `conductor` 自身の表示を有効にするオプションの名称と粒度(ジョブの結果とスキップの表示を同じオプションで有効にするか)。 wireframes(Rough Mockups の Assumptions & Open Questions)
- ステートファイルの名前と保存場所の具体(「実行ディレクトリの近傍」の具体)。 要確認
- 遷移ルールを書いていない結果(例: 警告時の遷移先を省略した場合)のときの既定の動き(定義順の次のジョブに進むか、エラーにするか)。 要確認
- 「主な開発環境の OS」がどれか、完成バイナリの配布先と公開の承認の要否。 practices-discovery の evidence
- 一連の実行モード(`conductor pipeline`)の入出力イメージは、未作成である。 wireframes(Rough Mockups)
