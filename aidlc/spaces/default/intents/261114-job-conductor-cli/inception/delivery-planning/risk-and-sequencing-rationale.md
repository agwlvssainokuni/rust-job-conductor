# Risk and Sequencing Rationale(順序の理由とリスク)

上流: bolt-plan、unit-of-work-dependency、raid-log(feasibility)、team-practices。**Bolt** とは、Construction での作業の1回のまとまり(1つ以上の Unit を作り、動くものに到達するまで)である。

## 選んだ順序

B1(u1-core)→ B2(u4-converter)→ B3(u2-runtime)→ B4(u3-cli)。[Q1: B]

依存の許す範囲(トポロジー)は、次のとおり。u2 は u1 のあと、u3 は u1・u2・u4 のあとで、u1 と u4 は、順序を入れ替えられる。 unit-of-work-dependency

## なぜこの順序か(「小さく慣れてから、難しいものへ」)

- **学習の曲線を緩やかにする。** 開発者は Rust に不慣れである。(RAID の R2) 最初の Bolt(B1)は、入出力のない純粋なロジックと型の定義であり、Rust の基本とテストの書き方を身につけやすい。2つ目(B2)は、最も小さい Unit で、プロジェクトの作り方、テスト、CI の回し方を、軽く確かめられる。
- **難しい Unit を、慣れたあとに置く。** u2-runtime は、OS のプロセス・シグナルとファイルの扱いが集中し、最も難しい。(RAID の R1) 慣れる前に当たるより、B1・B2 で土台を固めてから、B3 に進む。
- **最後に全体を組み立てる。** u3-cli は、他のすべてに依存する調整役であり、最後が自然である。

## 心配(Q3)と、その対策

選ばれた心配は、複数の OS での、プロセス起動とシグナルの違い(A)と、ステートの書き込みの安全性(C)である。どちらも u2-runtime(B3)に集中する。この順序では、B3 は3番目になるため、次の対策を置く。

| 心配 | 対策 |
|------|------|
| OS ごとの違い(A) | B1・B2 の時点から、CI(GitHub Actions)で、3つの OS のテストを回し、CI の設定と、OS 差の影響の見え方を、軽い Unit で確かめておく。B3 では、プロセス・シグナルの動作を、3つの OS のテストで確かめる |
| ステートの書き込みの安全性(C) | B3 の Definition of Done に、原子的な書き込みと、破損・食い違い・版の不一致の検知を含める。中断(書き込み中にプロセスが止まる)の再現テストを設ける |
| 共有する型の変更が波及する | 共有する型は B1(u1-core)に置く。B1 で型を固めてから、B3 に進むため、B3 での型の変更は最小限で済む(contract-summary) |

順序を変えて、B3 を2番目にする案(リスク優先)もあるが、慣れる前に最も難しい Unit に当たることになり、選ばなかった。

## 評価の観点(参考: WSJF 風の見方)

**WSJF** とは、Weighted Shortest Job First の略で、(価値 + 緊急性 + リスクの低減)を、作業の大きさで割った点数で、順序を決める考え方である。ここでは、数値のスコアは付けず、観点だけを定性的に整理する。(厳密な数値化は、依頼者の価値判断を要し、要望もなかったため行わない)

| Bolt | 価値 | リスクの低減 | 大きさ |
|------|------|--------------|--------|
| B1 u1-core | 高(分岐・スキップの中核の判断) | 中(規則の誤りを早く見つける) | M |
| B2 u4-converter | 低(Should) | 低(慣れのための小さな Unit) | S |
| B3 u2-runtime | 高(実行とステートの土台) | 高(OS 差、安全性) | L |
| B4 u3-cli | 高(利用者が使う入口。すべてをつなぐ) | 中(起動オーバーヘッド、全体の結合) | L |

## この順序の弱点

- B1〜B2 の時点では、利用者が使える形(コマンドとして動くもの)はない。動く `conductor` が見えるのは B4 の完了時である。(チームの実践により、ウォーキングスケルトンは作らないと決めている)
- B3 を3番目に置くため、OS 差の問題が見つかるのが遅くなりうる。対策として、B1・B2 から CI で3つの OS のテストを回す。

## Assumptions & Open Questions

- 数値によるスコアリング(WSJF)は行っていない。順序は、学習の曲線とリスクの観点の定性的な判断である。 [assumption]
- CI(GitHub Actions)の設定の時期は、このあとの CI Pipeline のステージで決める。B1 から3つの OS で回すことを、対策として前提にした。 [assumption]
