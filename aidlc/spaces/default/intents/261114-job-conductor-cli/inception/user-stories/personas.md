# Personas

上流: requirements(FR1〜FR7、NFR1〜NFR6)、team-practices。ペルソナは、intent-statement の Target Customer に基づく2つ。定義ファイル(`conductor.toml`)を書く人は、運用担当者・開発者に含める。[Q1]

## 優先順位

1. 運用担当者・開発者(ジョブの運用者)【最優先】
2. ローカル開発者(デバッグ・テスト担当)

最優先の利用場面は、既存スケジューラから `conductor run <job-id>` が1ステップずつ呼ばれる場面である(個別実行)。 intent-statement、Rough Mockups の Q1

## P1 運用担当者・開発者(ジョブの運用者)

| 項目 | 内容 |
|------|------|
| 役割 | 既存の直列ジョブスケジューラ上でバッチジョブを運用し、`conductor.toml` を書く、組織内の運用担当者・開発者 |
| 目標 | 警告時に別の処理へ分岐する、特定のジョブをスキップする、ジョブ間で実行状態を引き継ぐ、といった制御を、既存環境を変えずに実現する |
| 課題 | 既存環境は直列実行で、終了判定が 0 / 非0 の2値のみ。警告時の分岐やスキップができない。ジョブ間で実行状態を引き継げない |
| 利用の文脈 | スケジューラが `conductor run <job-id>` を1ステップずつ呼び出す。失敗時は、スケジューラまたは本人が同じパイプラインを再び流す |
| 主な関心 | 結果の分類と終了コード、スキップの正確さ、エラー後の再開、定義の誤りを実行前に拒否すること |
| 根拠 | intent-statement(Problem Statement、Target Customer)、requirements(FR1〜FR4) |

## P2 ローカル開発者(デバッグ・テスト担当)

| 項目 | 内容 |
|------|------|
| 役割 | ローカルでパイプラインをデバッグ・テストする開発者 |
| 目標 | スケジューラなしで、パイプライン全体を一気に流し、分岐やスキップが定義どおりに動くか確かめる |
| 課題 | 本番のスケジューラがない環境で、定義の挙動を確認する手段が必要 |
| 利用の文脈 | `conductor pipeline <pipeline-name>` を実行する。状態の確認(`watch`)や初期化(`reset`)、定義ファイルの変換(`convert`)も使う |
| 主な関心 | 一括実行の結果が分かりやすいこと、状態を見られること、初期化で最初からやり直せること |
| 根拠 | intent-statement(Target Customer)、requirements(FR3、FR5〜FR7) |

## 2つのペルソナの関係

- P1 が書いた定義ファイルを、P2 がローカルで確かめる。同じ人が両方の役割を担うこともある。 intent-statement
- ペルソナどうしの意思決定の上下関係はない。意思決定者は依頼者本人である。 stakeholder-map
