# Interaction Specification(コマンドの対話仕様)

上流: wireframes と user-flow(Rough Mockups)、stories(US1.1〜US7.1)、requirements(FR1〜FR7、NFR1〜NFR6)、team-practices。画面を持たない CLI のため、コンポーネントではなく、コマンド・オプション・終了コード・状態遷移の仕様として書く。

## 1. コマンドとオプション

| コマンド | 概要 | 優先度 | ストーリー |
|----------|------|--------|------------|
| `conductor run <job-id>` | 指定したジョブを1つ実行する(個別実行) | Must | US2.1〜US2.5 |
| `conductor pipeline <pipeline-name>` | パイプライン全体を一括実行する | Must | US3.1、US3.2 |
| `conductor watch` | 現在の状態を一覧で1回表示する | Should | US5.1 |
| `conductor reset` | ステートを初期化する | Must | US6.1 |
| `conductor convert <file> --to <format>` | 定義ファイルを YAML と TOML のあいだで変換する | Should | US7.1 |

| オプション | 対象 | 意味 | 出典 |
|------------|------|------|------|
| `--config <パス>` | `run`、`pipeline`、`watch`、`reset` | 使う定義ファイルを指定する。既定は実行ディレクトリの `conductor.toml` | [Q2]、requirements の FR1.6 |
| `-v` / `--verbose` | `run`、`pipeline` | `conductor` 自身の表示(ジョブの結果、スキップ、遷移)を有効にする。1段階のみ。`watch` と `reset` は、`conductor` 自身の表示の対象がない(`watch` は一覧が本体、`reset` は何も表示しない)ため、このオプションを受け付けない | [Q1] |

## 2. 結果の分類

| 結果 | 条件 |
|------|------|
| 成功 | `success_exit_codes` を書かなければ、終了コード 0。書けば、書いた値だけ(0 を書かなければ 0 でも成功にならない) |
| 警告 | 終了コードが `warning_exit_codes` の値 |
| エラー | 上のどちらでもない終了コード(`success_exit_codes` に含まれない 0 を含む)、コマンドの起動失敗、シグナルによる終了 |

- `success_exit_codes` に含まれない 0 で終わったジョブは、`conductor` 自身のエラーとして原因を表示し、固定の終了コード 1 で終了し、ステートにエラーの位置を残す。ジョブ自身の終了コードが 0 のため、「そのまま返す」ことができないからである。 [承認時の依頼者の確認(固定の 1)]

- `success_exit_codes` と `warning_exit_codes` に同じ値を書くこと、0 を警告に指定することは、定義の誤りとして起動時に拒否する。 requirements の FR1.4、[Q4]

## 3. スケジューラに返す終了コード(個別実行)

| 状況 | `conductor` が返す終了コード | 出典 |
|------|------------------------------|------|
| 成功 | 0 | requirements の FR2.5 |
| 警告 | 0 | requirements の FR2.5 |
| スキップ対象のジョブ | 0 | requirements の FR2.4 |
| エラー(ジョブが非0で終了) | ジョブの終了コードをそのまま | requirements の FR2.5 |
| `success_exit_codes` に含まれない 0 でジョブが終了 | 1(固定) | 承認時の依頼者の確認 |
| コマンドを起動できない | 127 | [Q7] |
| シグナルでジョブが終了 | 128 + シグナル番号 | [Q7] |
| 定義ファイルの誤り、ステートの破損・食い違い | 非0(具体の値は設計で定める) | requirements の FR1.4、FR4.5、FR4.6 |

## 4. 遷移とスキップ

- 遷移先は、記述順で後ろのジョブID、または `@end` に限る。エラーには書けない。 [Q3]、requirements の FR1.3
- 遷移先を書かない成功・警告は、記述順で次のジョブへ進む。 requirements の FR1.3
- 遷移先を指定したとき、現在のジョブと遷移先のあいだのジョブは、スキップ扱いになる。 requirements の FR2.3
- `@end` が指定されたあとは、以降のジョブはすべてスキップ扱いになる。 [Q3]

## 5. ステートの更新

- ジョブの結果と遷移の情報を、ローカルのステートファイルに保持する。書き込みは、中断されても壊れた内容が残らないようにする。 requirements の FR4.1、FR4.4
- 記述順で最後のジョブが、実行またはスキップのどちらで終わっても、完了とみなし、ステートを初期化する。`@end` に到達した一連の実行も、完了とみなす。 requirements の FR4.2
- エラーで終わったときは、ステートを保持する。次に流すと、エラーになったジョブから再開する。自動での再試行はしない。 requirements の FR4.3、FR3.2
- ステートと定義のジョブ構成が食い違うときは、実行せずにエラーで終了し、`conductor reset` を促す。 requirements の FR4.6

## 6. シグナルの扱い [Q8]

| 状況 | 動き |
|------|------|
| `conductor` が、実行中のジョブがある間にシグナルを受け取る | 受け取ったシグナルを、起動したジョブにも転送し、ジョブの終了を待つ |
| ジョブが終了した | ジョブがシグナルで終わったものとして、エラー扱い(128 + シグナル番号)にし、ステートにエラーの位置を残して終了する |
| Windows | シグナルの仕組みが違うため、終了を要求する同等の動きに読み替える。具体は設計で定める |

- 転送はこの確認(Q8)で決まった方針であり、要件(requirements)には、まだ書かれていない。要件に足すかどうかは、このステージの承認時にご相談する。 [assumption]

## 7. エラー表示の方針

- `conductor` 自身のエラーは、オプションの有無にかかわらず、常に表示する。 requirements の FR2.6
- 定義ファイルの誤りには、ファイル名・行・原因を含める。 requirements の FR1.4
- ステートの誤りには、ステートファイルのパスと原因を含める。 requirements の FR4.5
- 表示の言語は、環境のロケールに従う。 [Q5]

## 8. 表示のタイミング(個別実行)

| 場面 | 既定 | `-v` を付けたとき |
|------|------|-------------------|
| 成功・警告 | `conductor` 自身の表示なし | 結果と遷移を表示 |
| スキップ | 何も表示しない | スキップした旨を表示 |
| エラー(ジョブ) | ジョブ本体の出力のみ | 結果を表示 |
| `conductor` 自身のエラー | 原因を表示 | 原因を表示 |

出典: [Q1]、Rough Mockups の Q2、Q3、Q7

## Assumptions & Open Questions

- 表示される文言そのもの、`convert` の出力先、定義の誤り・ステートの誤りで返す具体的な終了コードの値は、設計で定める。 [assumption]
- 個別実行で、順序外のジョブが呼ばれた場合と、実行済みのジョブが再び呼ばれた場合の動作は、設計で定める(requirements の未解決事項)。 [assumption]
- シグナルの転送(Q8)と、成功コードの意味(Q4)および固定の終了コード 1 は、承認時の依頼者の確認を受けて、要件 FR2.2・FR2.9 に反映した。
