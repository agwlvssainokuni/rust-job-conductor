# Feasibility Assessment

上流: intent-statement(課題・利用者・成功基準・初版の対象外)と、本ステージの回答(Q1〜Q7)に基づく。

## Summary

- 総合評価(アーキテクトの見立て・仮説): **実現可能**。技術的な障害は確認されていない。主な注意点は、Windows を含む複数OS対応(Q1)と、開発者が Rust に不慣れであること(Q3)の2点。
- 目的は、既存の直列ジョブ環境を変更せず、上位レイヤーで分岐・スキップ・ステート管理を補うこと(intent-statement の Initiative Trigger)。

## Technical Viability

| 観点 | 評価 | 根拠 |
|------|------|------|
| スケジューラ連携 | 実現可能(仮説) | コマンドは書き換えられるため、ラッパーとして挟める。終了コードは 0 / 非0 の2値のみ受け付けるため、警告などの細かい状態はラッパー自身が内部で保持し、スケジューラには 0 または非0 を返す設計が必要。 [Q2] |
| 対応OS | 実現可能だが工数に影響 | Linux・macOS・Windows のすべてで動作する必要がある。OS ごとの違い(プロセス起動、ファイルロック、パスの扱い)を吸収する必要がある。 [Q1] |
| 開発体制 | 注意が必要 | Rust で実装することは決まっているが、開発者は Rust に不慣れである。学習コストにより初期の進行が遅れうる。 [Q3] |
| 起動速度 | 数値基準なし | 数値の目安はなく、ジョブ本体に比べて無視できる程度であればよい。測定可能な合格基準は Inception で決める必要がある。 [Q6] |
| 規制・機密データ | 制約なし | 規制や機密データの取り扱いに関する要件はない。 [Q5] |

## Risk Analysis

- 複数OS対応により、特に Windows でのプロセス制御やファイル排他の挙動差が品質リスクになりうる。 [Q1]
- Rust への不慣れが、実装品質とスケジュールのばらつきの要因になりうる。ただし期限の制約はないため、影響は限定的と見込む。 [Q3, Q4]
- 終了コードが 0 / 非0 のみのため、スケジューラ側から見ると「スキップ」と「正常終了」を区別できない。運用上の見え方(どこで確認するか)は未検討である。 [Q2]

## Conclusion

- 初版(mvp)として進めることに、技術的・組織的な阻害要因は見つかっていない。 [Q4, Q7]
