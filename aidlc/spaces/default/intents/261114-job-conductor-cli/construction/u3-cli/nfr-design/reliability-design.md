# Reliability Design(u3-cli)

上流: reliability-requirements(NFR2.2〜NFR2.8)、security-design、functional-spec(W1〜W6)、rules(BR2.x〜BR5.x)、u1-core・u2-runtime の保証。`conductor` は、1回で終わるコマンドで、可用性の目標、フェイルオーバー、複製、バックアップ、サーキットブレーカー、バックオフ付きの再試行、ヘルスチェックの対象ではない。ここでは、**失敗の経路ごとの振る舞い**と、**保証の範囲**を設計する。

## 失敗の経路と振る舞い(NFR2.2、NFR2.6)

| 事象 | 振る舞い | 終了コード | ステート |
|------|----------|------------|----------|
| 使い方の誤り | 使い方を標準エラーへ。ジョブを実行しない | 68 | 変えない |
| 定義の誤り・command の誤り・定義ファイルがない | すべての誤りを標準エラーへ | 64 | 変えない |
| 知らないジョブID(run) | 使い方の誤りとして表示 | 68 | 変えない |
| ステートが読めない・壊れている・版の不一致・食い違い | path と原因、`reset` の案内 | 65 | 変えない |
| 判断が Reject(順序外) | 理由を表示 | 66 | 変えない |
| 判断が Skip | 起動せず記録(必要なら初期化) | 0 | 記録 |
| ジョブが成功・警告 | 記録、0 で終わる | 0 | 記録 |
| ジョブがエラー | 記録(再開位置)、ジョブの終了コード(BR5.2 で 0〜255) | ジョブの値 | 再開位置 |
| 成功コードに含まれない 0 | 原因を表示、エラーとして記録 | 1 | 再開位置 |
| ジョブを起動できない | `cannot start command` を表示、記録 | 127 | 再開位置 |
| ジョブがシグナルで終了 | エラーとして記録 | 128 + 番号 | 再開位置 |
| 中断(シグナル)を受け取った | ジョブへ転送し、終了を待って記録、または、起動前・ジョブのあいだなら、再開位置を記録 | 128 + 受け取った番号 | 再開位置 |
| ジョブのあとのステートの書き込みの失敗 | 原因を表示。ジョブは、実行済み | 65 | 直前の完全な内容(ジョブは、次の呼び出しで再実行されうる) |
| 完了のあとの初期化の失敗 | 原因を表示 | 65 | `completed` のまま残る(u2-runtime が、次の読み込みで空として扱う) |
| convert の失敗 | 種類と場所を標準エラーへ。標準出力は空 | 67 | 触れない |
| 内部の誤り(パニック) | 固定の文を標準エラーへ | 70 | 直前の完全な内容(ジョブの実行中なら、ジョブが孤児として残りうる) |
| 標準出力・標準エラーへの書き込みの失敗 | 標準エラーは無視。標準出力(watch は 65、convert は 67) | 本来の値、または 65/67 | 変えない |

## 設計の要点

1. **決定的:** 終了コードは、純粋な関数(`exit_code_for`)に集め、表(上)を、テストで全項目を確かめる(NFR2.2)。OS の違いを入れない(BR5.2 で範囲を揃える)。
2. **at-least-once(NFR2.4):** ジョブの終了と、結果の書き込みのあいだに落ちると、ジョブは、再実行されうる。流れの順序(判断 → 初期ステートの書き込み → ジョブ → 記録 → 書き込み → 初期化)を、固定する。利用者向けの文書に、保証の範囲を書く(Code Generation で作る)。
3. **自動の再試行をしない(NFR2.3):** エラーの後、何も起きない。再開は、利用者の再実行(エラーのジョブから)か、`reset`(先頭から)。
4. **中断の順序(NFR2.5):** 転送 → 待つ → 記録 → 終了(128 + 番号)。2回目以降のシグナルは、追加の動作をしない(強制終了しない)。ジョブが終わらないシグナルの無視をした場合、待ち続ける(時間の上限がないため。要件)。
5. **回復(NFR2.7):** `reset` は、読み込みも検査も迂回して、ステートを消す。壊れた、食い違う、完了のまま残った、どの状態でも動く。
6. **書式の版(NFR2.8):** 定義とステートは、版 1 だけを読む。将来の版は、定義: 64、ステート: 65、`reset` を促す(ステート)。
7. **失敗の順序での終了コードの優先:** 検査・判断の途中でシグナルが届いても、Reject・Skip・各種のエラーの終了コードが、中断の終了コードより優先する(BR4.2a)。

## 設計の判断(代替案との比較)

### D1 ジョブの結果の書き込みが失敗したら、65 で終わる(ジョブの終了コードを返さない)

- **Context:** ジョブは、すでに実行された。ステートの書き込みが失敗すると、記録が残らない。
- **Decision:** ステートの誤り(65)として終わり、原因を表示する。ジョブの終了コードは、返さない。
- **Consequences:** 良い点は、スケジューラが、失敗(非 0)を知り、記録の不整合に気づける。悪い点は、ジョブが成功しても、`conductor` が失敗を返す(誤って、後続を止める)。次の呼び出しで、ジョブは再実行されうる。
- **Alternatives Rejected:** ジョブの終了コードを返し、書き込みの失敗は、警告の表示だけにする案: スケジューラは進むが、記録が無いまま、次のジョブが、前のジョブの状態を知らず、順序外(66)になる。

### D2 完了後の初期化の失敗は、65 とし、`completed` のまま残す

- **Context:** パイプラインが完了したが、ステートを消せない。
- **Decision:** 65 で終わる。`completed` のステートは、u2-runtime が、次の読み込みで、空として扱う(再実行できる)。
- **Consequences:** 良い点は、次の実行が、先頭から始まる。悪い点は、完了したのに、失敗が返る。
- **Alternatives Rejected:** 初期化の失敗を、無視して 0 を返す案: スケジューラは成功と見るが、残ったステートを、利用者が知らない(表示があれば、知らせられるが、失敗の扱いが曖昧になる)。

## この Unit に該当しない信頼性の項目

- 可用性(SLA/SLO)、フェイルオーバー、複製、バックアップ、サーキットブレーカー、バックオフ、ヘルスチェック、縮退運転: 持たない。再試行は、しないことが要件(NFR2.3)。

## Assumptions & Open Questions

- ジョブのあとの書き込みの失敗(65)で、ジョブの終了コードを返さない判断(D1)は、スケジューラ側の運用に影響する。人の確認が、レビューのあとに要りうる。 [assumption]
