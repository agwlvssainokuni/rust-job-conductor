# Scalability Design(u3-cli)

上流: scalability-requirements(NFR1.5、NFR1.6)、performance-design、functional-spec。`conductor` は、1回で終わるコマンドで、常駐せず、サーバーではない。スケーリングのパターン(水平・垂直、負荷分散、データの分割、自動のスケーリング、キューによる分離)は、当てはまらない。ここでは、**扱える規模の上限と、同時に動く複数の `conductor`** の設計を示す。

## 設計

| 項目 | 設計 | 根拠 |
|------|------|------|
| 定義の大きさ | 1 MiB まで(u1-core が、読み取りを上限 + 1 バイトで打ち切る) | NFR1.5 |
| ジョブの数 | 1,000 個程度(仮)まで。起動のオーバーヘッドは、ジョブの数に、ほぼ線形(全ジョブの `check_command`、検証、ステートの照合が、1回ずつの走査) | NFR1.5 |
| ステートの大きさ | 1 MiB まで(u2-runtime)。ジョブ1つあたり数十バイトのため、1,000 個でも約数十 KiB | NFR1.5 |
| 流れの計算量 | ジョブごとの判断(`decide_before_run`)と記録(`apply_*`)は、ジョブの数に比例する走査。一括実行では、ジョブごとに、ステートの複製が起きるため、全体で、ジョブ数の2乗になりうる(1,000 個でも約 100 万回の小さなコピーで、許容) | NFR1.5 |
| 同時の実行 | 排他制御をしない。同じ定義に、複数の `conductor` が同時に動いてもよい。ステートは、原子的な置き換えで壊れた内容にならず、後に書いた方が勝つ。整合は、保証しない | NFR1.6、FR2.8 |
| 状態を持たない | `conductor` のプロセスは、ステートを、ファイルにしか持たない(プロセスの中には、実行のあいだだけの値)。水平のスケーリング(複数のホスト)は、対象外 | requirements の Out of Scope |
| 容量の測定 | ジョブ 1,000 個の定義で、`run` の起動から、ジョブの起動まで、1 秒以内(仮。警告として記録)。`pipeline` も、同じ定義で、全体の時間を測って記録する | NFR1.5 |

## 設計の判断(代替案との比較)

### D1 排他制御をしない

- **Context:** 既存のスケジューラが、同じ定義に対して、同時に `conductor` を呼ぶ可能性がある。要件 FR2.8 は、排他制御をしないと定めている。
- **Decision:** ファイルのロックを使わない。ステートの書き込みは、原子的な置き換え(u2-runtime)で、壊れた内容を残さない。
- **Consequences:** 良い点は、実装が単純で、ロックの取り残しによる停止が無い。悪い点は、同時の実行で、ステートの内容(どのジョブが記録済みか)が、後勝ちで失われ、ジョブが再実行されうる。利用者が、同時の実行を避ける。
- **Alternatives Rejected:** ファイルのロック(助言ロック)で、同じステートの実行を直列にする案: 整合は保てるが、要件 FR2.8(排他制御をしない)に反し、ロックの取り残しと、OS ごとの違い(ネットワークのファイルシステムなど)を、持ち込む。

### D2 一括実行のステートの複製を、許容する

- **Context:** `apply_*` が、新しい `PipelineState` を返す(複製)ため、一括実行では、ジョブごとに複製が起きる。
- **Decision:** 最適化せず、複製を許容する(ジョブ 1,000 個でも、約 100 万回の小さなコピーで、問題にならない見込み)。
- **Consequences:** 良い点は、純粋な関数のまま、単純。悪い点は、非常に大きな定義では、無駄になる(対象外の規模)。
- **Alternatives Rejected:** 可変の参照で、その場で更新する案: 速いが、u2-runtime の `apply_*` の純粋な設計と、テストのしやすさを損なう。

## この Unit に該当しないスケーラビリティの項目

- 水平・垂直のスケーリング、負荷分散、データの分割(シャーディング)、自動のスケーリングの規則、容量の閾値のアラート、キューによる分離: `conductor` は、1回で終わるコマンドで、持たない。

## Assumptions & Open Questions

- 1,000 個の規模での、ステートの複製の合計の費用は、Code Generation の測定で確かめる(超えるなら、設計を見直す)。 [assumption]
