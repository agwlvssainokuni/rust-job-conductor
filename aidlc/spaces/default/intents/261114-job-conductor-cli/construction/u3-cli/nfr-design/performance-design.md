# Performance Design(u3-cli)

上流: performance-requirements(NFR1.1〜NFR1.4)、scalability-requirements(NFR1.5、NFR1.6)、tech-stack-decisions(T4〜T6)、functional-spec(W1〜W6)。`conductor` は、1回で終わるコマンドである。性能の設計は、**起動から終了までのオーバーヘッドの配分と、その守り方**に限る。コードは、短い疑似コード(15行以下)に限る。

## 起動の経路(`run` と `pipeline`)と時間の配分(NFR1.1。仮)

| 段階 | 内容 | 担当 | 配分(仮) |
|------|------|------|-----------|
| 1 | プロセスの起動、引数の解釈(`lexopt`)、`-v` と `--config` の確認 | u3-cli | 合計 10ms 以内(この Unit の分) |
| 2 | シグナルの受け取りの準備(専用のスレッドを1つ起動する) | u3-cli | (同上) |
| 3 | 定義の読み込みと検証(`load_definition`) | u1-core | 20ms |
| 4 | 全ジョブの `check_command`、ステートの読み込み、照合、(空なら)初期ステートの書き込み(`Fast`)、起動前の判断 | u2-runtime、u1-core | 20ms |
| — | ジョブの起動 | u2-runtime | (ジョブ自身の時間は、含めない) |
| 5 | ジョブの終了の観測(最大 10ms の遅れ)、分類、記録、`Durable` の書き込み、完了時の初期化、終了 | u2-runtime、u1-core、u3-cli | ジョブのあと 50ms |

- 起動前 50ms + ジョブのあと 50ms = 100ms(AC2.5.3 の、`run` の合計)。配分は、仮で、Code Generation の実測で確定する。

## 設計の要点

1. **起動の経路に、不要な処理を入れない(NFR1.4):** ロケールの判定、文言の表の用意、色の判定(端末か、`NO_COLOR` か)は、最初の表示が必要になるまで、行わない(`OnceCell` 相当で、遅延する)。成功・スキップで、`-v` なしなら、表示は一度もなく、これらは、一度も実行されない。`convert` に関わる処理(u4-converter のライブラリの初期化)は、`convert` コマンドの経路でだけ行う(`run` と `pipeline` は、`convert` のコードを呼ばない)。静的な初期化(起動時に動く処理、`lazy` な大域の変数)は、この Unit に置かない。
2. **スレッドは、シグナル用の1つだけ:** 起動の段階 2 で、専用のスレッドを1つ起動する(約 100 マイクロ秒の見込み)。`watch`・`reset`・`convert` では起動しない。待ちは、u2-runtime の、同じスレッドの `try_wait` のくり返し(最初 1ms、最大 10ms)で、追加のスレッドは作らない。
3. **余分なコピーを避ける:** 定義(`PipelineDefinition`)とステート(`PipelineState`)は、流れの中で、参照で渡す。`apply_*` は、新しいステートを返す(複製)が、ジョブ 10 個程度では、無視できる大きさ。1,000 個程度でも、線形(NFR1.5)。
4. **ジョブの出力は、加工しない(NFR1.3):** ジョブの標準出力・標準エラーは、u2-runtime が、子プロセスに引き継ぐ(継承)ため、`conductor` は、バッファリングも、コピーもしない。`conductor` 自身の出力(表示)は、行ごとに、標準エラー・標準出力へ直接書く(ブロック単位のバッファは使わず、書いたらすぐに見える)。
5. **`pipeline` の、ジョブごとの費用(NFR1.1 の限定):** ジョブごとに、`Durable` の書き込み(約 10ms。macOS)と、最大 10ms の観測の遅れが、加わる。合計の 100ms は、`run` だけを約束し、`pipeline` は、ジョブ1つあたり 50ms 以内(警告)を目標にする。
6. **リリースのビルド(T4):** `opt-level = 3`、`lto = "thin"`、`codegen-units = 1`、`strip = true`。

## 測定の設計(NFR1.1、NFR1.2)

- 補助の実行ファイル(u2-runtime のものを拡張)が、起動時に、単調な時計の値を、標準出力に出し、すぐに終わる。測定のテストが、`conductor` を起動する直前と終了の直後の時刻(同じプロセスの時計)を測り、オーバーヘッド = 全体の時間 − 補助の実行ファイルが報告した、自身の実行時間 とする。起動前と、ジョブのあとの内訳は、補助の実行ファイルが報告した、起動時刻と、テストが測った起動の直前の時刻の差、で求める(同じ時計の種類で、差を取る)。20 回測り、p95(昇順の 19 番目)を出す。
- 100ms を超えても、配分の確定までは、警告(要約に出力)。確定のあと、CI を失敗にする。

## 判断(代替案との比較)

### D1 表示と locale の準備を、遅延させる

- **Context:** 成功・スキップの経路(最も多い)では、表示が1度もない。
- **Decision:** ロケールの判定と、文言の表の用意を、最初の表示のときまで、遅延する。
- **Consequences:** 良い点は、成功の経路の起動が、速い。悪い点は、最初のエラーの表示が、わずかに遅くなる(無視できる)。
- **Alternatives Rejected:** 起動時に、判定する案: 実装は単純だが、成功の経路で、無駄になる。

### D2 シグナルのスレッドは、run・pipeline のときだけ起動する

- **Context:** `watch`・`reset`・`convert` は、すぐに終わり、シグナルでの中断の後始末が要らない(既定の動作で終わる)。
- **Decision:** シグナルの準備と、スレッドの起動は、run・pipeline の起動の経路だけで行う。
- **Consequences:** 良い点は、不要なスレッドを作らない。悪い点は、`watch` 中の Ctrl+C は、既定の動作(プロセスの終了)になる(要件に反しない)。
- **Alternatives Rejected:** 全コマンドで、同じ準備をする案: 一貫するが、`watch`・`reset`・`convert` で無駄になり、`convert` の途中の中断を、2つ目の終了コードの規則で扱う必要が出るため退けた。

## Assumptions & Open Questions

- 100ms の配分は、仮である。実測で見直す。特に、Windows のプロセスの起動の費用(実行ファイルの読み込み)と、macOS の `Durable` の書き込みの費用が、配分に効く。 [assumption]
- `std::sync::OnceLock` による遅延は、最小の Rust のバージョン(1.85)で使える(安定化は 1.70)。 [assumption]
