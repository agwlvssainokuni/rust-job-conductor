# Scalability Requirements(u3-cli)

上流: requirements(NFR1〜NFR3)、functional-spec、rules、contract-summary(E1〜E3)。`conductor` は、1回で終わるコマンドで、常駐せず、サーバーではなく、水平・垂直のスケーリングも、自動のスケーリングも、キューも、負荷分散もない。ここでは、**扱える規模の上限(容量)**と、**同時に動く複数の `conductor` の扱い**を、要件として定める。各行は、inception の NFR の ID に枝番を付けた ID を持つ。

## 要件

| ID | 要件 | 判定の基準 | 出典 |
|----|------|------------|------|
| NFR1.5 | 扱える定義の規模の上限を、定義ファイル 1 MiB(u1-core)、ジョブの数 1,000 個程度(仮)、ステートファイル 1 MiB(u2-runtime)とする。上限の範囲では、起動のオーバーヘッドが、ジョブの数に対して、ほぼ線形で増え、NFR1.1 の測定条件(ジョブ10個)から、大きく外れない | ジョブ 1,000 個の定義で、`conductor run <job-id>` を実行し、起動から、ジョブの起動まで、1 秒以内(仮。警告として記録。基準は、実測で見直す)。ジョブ 10 個の NFR1.1 は、別に守る | NFR1 |
| NFR1.6 | 同じ定義に対して、複数の `conductor` が、同時に動いてもよい。排他制御はしない(要件 FR2.8)。ステートの整合は、同時の実行では保証せず(後に書いた方が勝つ)、利用者が、同時の実行を避ける | 同じ定義に、2つの `run` を同時に動かして、どちらも実行され(u2-runtime の AC2.5.2)、ステートファイルが、壊れた内容にならない(読み戻せる)こと | NFR1、FR2.8 |

## この Unit に該当しないスケーラビリティの項目

- 水平・垂直のスケーリング、負荷分散、データの分割、自動のスケーリングの規則、キューによる分離、ステートレスな設計の要件: `conductor` は、複数のホストにまたがる分散実行・ステート共有を、対象外とする(requirements の Out of Scope)。
- 成長の見込み: ジョブの数と定義の大きさは、利用者が手で書く規模(数個〜数十個)を想定し、増えても、1,000 個を超えない。

## Assumptions & Open Questions

- ジョブ 1,000 個(仮)は、定義ファイル 1 MiB の上限に、ジョブ 1 つあたり 1 KiB 程度の定義が収まる範囲として置いた値である。u1-core の検証と、u2-runtime の `check_command`、ステートの読み書きが、この規模で、問題ないかは、Code Generation の測定で確かめる。 [assumption]
