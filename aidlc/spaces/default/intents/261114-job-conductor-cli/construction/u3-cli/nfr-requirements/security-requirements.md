# Security Requirements(u3-cli)

上流: functional-spec(W1〜W6)、rules(BR1.1〜BR7.3)、requirements(NFR4)、contract-summary(E1)、質問への回答(Q1〜Q3)。u3-cli は、`conductor` の実行ファイルであり、認証・認可・暗号化・ネットワークはない。入力は、(1) コマンドラインの引数、(2) 環境変数(`LANG` など)、(3) 定義ファイル・ステートファイル・convert の入力(いずれも、他の Unit が読み、検査する)、(4) シグナルである。出力は、標準出力・標準エラー、終了コード、ジョブの起動(u2-runtime)である。各行は、inception の NFR の ID に枝番を付けた ID を持つ。

## 要件

| ID | 要件 | 判定の基準 | 出典 |
|----|------|------------|------|
| NFR4.1 | コマンドとオプションは、BR1.1〜BR1.3、BR1.6 の文法だけを受け付ける。知らないコマンド、必須の引数がない、余分な引数、許されない場所のオプションは、ジョブを一切実行せず、使い方の誤り(終了コード 68)にする。引数は、シェルを介して、解釈・展開しない | 規則の表(コマンドごとの、正しい引数と誤った引数)のテストで、期待どおりの終了コードと、ジョブが実行されないこと。`--` で始まる未知のオプションと、`-v` を `watch`・`reset`・`convert` に付けたとき、68 | NFR4、BR1.1〜BR1.3 |
| NFR4.2 | 端末に出す文字列のうち、入力に由来するもの(ジョブID、キー名、パス、command の最初の語、ステートの内容)は、制御文字・エスケープシーケンスの開始(ESC)・書式の制御文字・双方向の制御文字を、エスケープして出す。長いものは、64 文字で切る(パスは、切らず、エスケープだけ)。ジョブ本体の出力は、そのまま通し、加工しない | ESC(`\x1b[31m` など)、改行、`U+202E` を含むジョブID・パスを、定義に書いたとき、表示に、生の制御文字が現れない(テスト)。ジョブ本体の出力は、バイトのまま同じ | NFR4、BR6.4 |
| NFR4.3 | シグナルは、**専用のスレッドで受け取り**、受け取った番号のうち、最初の1つだけを、中断の合図(u2-runtime の `InterruptSignal`。立ったら下りず、最初の番号を保つ)に書く。UNIX 系: `signal-hook` の `Signals`(イテレータ)を、専用のスレッドで回す(SIGHUP、SIGINT、SIGQUIT、SIGTERM)。Windows: `ctrlc` のハンドラ(ライブラリが、専用のスレッドで呼ぶ)から、番号 2 を書く。OS が、直接ハンドラを呼ぶ部分(非同期シグナルに安全な操作だけ)は、ライブラリの内部にあり、この Unit は、その中身に触れない。この Unit(クレート)は、`unsafe` を使わず(`signal-hook` の `low_level` のような、`unsafe` を要る API は使わない)、シグナルの受け取りの準備は、定義の検査より前に行う。Windows の Ctrl+Break とコンソールの終了の通知は、この版では対象外とし、既定の動作に任せる(Q4 は、Ctrl+C だけを対象にする) | クレートに `#![forbid(unsafe_code)]` を置く。ソースの検索で、`unsafe` と `low_level` がない。シグナルを受け取るテスト(UNIX 系)で、2つ以上のシグナルを続けて送っても、最初の番号が合図に残り、終了の処理が、メインの流れで、1回だけ行われること | NFR4、BR4.1、Q2: A |
| NFR4.4 | convert は、変換が成功するまで、標準出力に何も書かない。失敗のとき、標準出力は、空のまま。ステートと定義ファイルは、convert で、読まず、書かない | convert の失敗(文法の誤り、読めない、表せない値)のテストで、標準出力が空、終了コード 67。成功のテストで、結果が、全部、1回で書かれる | NFR4、BR7.3 |
| NFR4.5 | `conductor` は、ネットワークに接続せず、利用状況の収集(テレメトリ)をしない。読み書きするファイルは、定義ファイル、ステートファイル(と、その一時ファイル)、convert の入力に限る | ソースの検索で、`std::net` と、ネットワークのライブラリの使用がない。依存の一覧(`cargo tree`)に、ネットワークのライブラリがない(テスト専用の依存を除く) | NFR4 |
| NFR4.6 | `--config` と convert の入力のパスは、そのまま使う(シェルの展開をしない)。パスの指す先が、通常のファイルでない、または読めないときの失敗は、固定の文とパスで、表示する(NFR4.2 のエスケープ)。パスの検査(シンボリックリンクの解決、ディレクトリの制限)は、しない | 存在しない・ディレクトリ・権限なしのパスで、期待どおりの kind と表示、パニックしない | NFR4、BR1.2、BR1.4 |
| NFR4.7 | 外部の入力に対する処理で、パニックしない。内部の誤り(パニック)が起きたときは、パニックのフックで、`conductor: error: internal error` を標準エラーに表示し、終了コード 70 で終わる(`conductor` 自身のエラーの1つとして、E1 に足す。64〜68 と同じく、0〜255 の範囲にあり、ジョブ自身の終了コードと重なりうる。区別は、標準エラーの固定の文で行う)。**ジョブの実行中にパニックした場合**: 子プロセスの終了を待たずに終わるため、ジョブは、孤児として残りうる。ステートは、直前の完全な内容のままで、次の実行は、そのジョブを、再実行しうる(NFR2.4 の保証の範囲に含める)。標準出力・標準エラーへの書き込みの失敗(閉じたパイプなど)で、パニックしない(BR7.1、BR7.3 の終了コード) | 閉じたパイプへの書き込み(`watch`、`convert`)で、パニックせず、決められた終了コードで終わる。パニックを起こす内部のテスト用の経路で、70 と固定の文が出る。ジョブの実行中のパニックのテスト(補助の実行ファイルを、眠らせて、パニックを起こす)で、終了コード 70、ステートが読み戻せること | NFR4、BR7.1、BR7.3 |
| NFR4.8 | リリースの実行ファイルは、タグを付けたとき、CI(GitHub Actions)が、Linux・macOS・Windows の3つ向けに、ロック済みの依存(`Cargo.lock`)でビルドし、実行ファイルごとに、SHA-256 のチェックサムを、同時に公開する。**このチェックサムが守るのは、転送の破損の検知までで、配布元の改ざん(署名がない)は防げない**(この版の範囲。署名は、将来の検討) | CI のリリースのワークフロー(CI Pipeline・Deployment Pipeline のステージで作成)に、3つの OS のビルドと、チェックサムの生成と公開が含まれること。ビルドは `--locked`。この要件は、このステージでは、**要件(上流の根拠は、team.md の「タグでリリース」)として記録するだけ**で、実装の確認は、後のステージで行う | NFR4、team.md(タグでリリース) |


## 上流に出典のない、このステージで足した要件

- NFR4.2 の双方向の制御文字のエスケープ、NFR4.8 のチェックサム、NFR4.7 の終了コード 70(内部の誤り)は、inception の要件(FR・NFR)に直接の出典がなく、`team.md`(タグでリリース)や、安全の方針(NFR4)から、このステージで足した要件である。人のレビューの対象として、ここに明記する。

## この Unit に該当しない NFR

- 認証・認可・暗号化・秘密情報の取り扱い: `conductor` は、秘密情報を扱わず、ネットワークにも触れない。ジョブの環境変数は、そのまま引き継ぐだけで、読み取って表示も保存もしない。

## Assumptions & Open Questions

- 終了コード 70(内部の誤り)は、E1 に足す新しい値である(契約の更新は、この Unit の Code Generation の `code-summary.md` に記録する)。 [assumption]
- 実行ファイルの署名(コードサイニング)は、この版では、行わない。チェックサムの公開だけとする。署名を求める要望が出たら、見直す。 [assumption]
- 依存のライセンスと脆弱性の確認(`cargo-deny`、`cargo-audit`)は、CI Pipeline のステージで決める(u1-core の依存の方針と同じ)。 [assumption]
