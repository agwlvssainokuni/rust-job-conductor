# CI/CD Pipeline(u2-runtime)

上流: nfr-design(security-design、logical-components)、nfr-requirements(security-requirements、tech-stack-decisions)、team.md の実践(GitHub Actions、3つの OS、rustfmt と clippy、行カバレッジ 80%、タグでリリース)、質問への回答(Q1、Q2)。u2-runtime は library であり、サーバー、コンテナ、クラウドの資源、監視、デプロイ先の環境を持たない。この Unit が負うのは `cicd-pipeline.md` だけである(infrastructure-specification と monitoring-design は、種類(kind)の対象外)。この文書は、CI で何を確かめるかの設計であり、ワークフローのファイルは、後の CI Pipeline のステージで、ワークスペースに1つだけ作る(u1-core・u4-converter と共有する)。

## 方針

- 実行の場所は GitHub Actions。ローカルでは主な開発環境の OS で確かめ、他の OS は CI で確かめる(team.md)。
- **ワークスペース全体で、1つのワークフロー**にする。この Unit 専用の段階は、プロセスを起動するテストの時間の上限、OS 固有のテスト、カバレッジの対象である。
- この Unit は、単独では配布しない。リリースのバイナリは、u3-cli を含むリリース用のワークフロー(タグで起動)が、`-p` で u3-cli のパッケージだけをビルドして作る。この Unit のテスト専用の補助の実行ファイル(bin)は、配布に含めない。したがって、この Unit に、デプロイ、環境の昇格、ブルー/グリーン、カナリアはない。

## 段階と確認の対応(stage → gate)

| 段階 | 内容 | 失敗時 | 関わる NFR |
|------|------|--------|------------|
| 1. 整形の確認 | `cargo fmt --all -- --check` | マージをブロック | team.md(Code Style) |
| 2. 静的解析 | `cargo clippy --workspace --all-targets --locked -- -D warnings` | マージをブロック | team.md(Code Style) |
| 3. ビルド | `cargo build --workspace --locked`。`cargo tree --package <この Unit のパッケージ> --edges normal --target all` で、**実行時の依存(開発用の依存を除く)**の一覧を出力し、C などのビルドを要する依存(`-sys` で終わるクレートや、C のビルドスクリプトを持つもの)が含まれないことを確かめる(開発用の `tempfile` が引き込む `linux-raw-sys`・`windows-sys` は、対象外。`libc` は、宣言だけで、C のコンパイルを要しない例外として、許可リストに書く)。`libc` は、宣言だけで、C のコンパイルを要しない。最小の Rust のバージョン(1.85)で、この Unit の本体(開発用の依存を除く)がビルドできることを、Linux と Windows で `cargo +1.85 build --package <この Unit のパッケージ> --locked` で確かめる。**検索の検査(`src/` だけを対象にし、`tests/` と補助の実行ファイルは、対象外)**: `unsafe` が、`platform` の UNIX 系のモジュールの1か所だけにあること(NFR4.8)。`cfg(unix)`・`cfg(windows)` が、`platform` の外にないこと(NFR3.1)。`"sh"`、`"cmd"`、`std::process::Command::new` の引数に、シェルを指定する箇所がないこと(NFR4.1)。最小の Rust のバージョンのビルドが、ロック済みの依存の `rust-version` が高くて失敗したときは、**その依存を、最小のバージョンで動く版へ下げる**(下げられなければ、人の承認で、最小のバージョンを上げる)。 | マージをブロック | NFR2.1、NFR3.1、NFR4.8 |
| 4. テスト | `cargo test --workspace --locked` を、Linux・macOS・Windows の3つで実行する。補助の実行ファイル(bin)は、`cargo test` が自動でビルドする。分け方の規則の表、起動(引数のメタ文字、環境変数・作業ディレクトリの引き継ぎ、存在しないコマンド、シグナル終了、終了コード)、ステートの読み込み・書き込み・照合・初期化、記録(`apply_*`)のテストを含む | マージをブロック | NFR3.1、NFR5.1、NFR4.1〜NFR4.7 |
| 5. OS 固有のテスト(Q2: A) | **UNIX 系(Linux・macOS)**: シグナルの転送のテスト(補助の実行ファイルが「眠り続ける」ところへ、合図を立て、SIGTERM が1回だけ届いて、`terminatedBySignal = 15` になること)、新しいプロセスグループでの起動、権限による書き込みの失敗(root でないときだけ)。**Windows**: `.cmd` に、引用符を壊す危険な引数を渡すと `startFailure` になること(NFR4.9)。Ctrl+C の経路は、OS が配るため、u3-cli のテストで確かめる。これらも、**マージを止める必須のチェック**にする。Windows の `.cmd` のテストの結果が、期待と異なったら、設計を見直す(危険な引数を、この Unit が先に拒否する) | マージをブロック | NFR4.8、NFR4.9 |
| 6. プロセスを起動するテストの時間の上限(Q1: A) | プロセスを起動するテストは、**各 30 秒**の時間の上限を、テストの中で持つ(別のスレッドで動かし、結果を待つ時間で測り、超えたら、そのテストを失敗にする。**上限を超えたときは、テストが持っている子プロセス(眠り続ける補助の実行ファイルなど)を、強制終了して回収してから失敗にする**(残ったプロセスが、Windows で実行ファイルをロックして、後続のビルドを妨げないように))。CI のジョブ全体は、15 分で打ち切る(`timeout-minutes: 15`。仮の値で、実測で見直す)。この上限が検知するのは、ハング(戻らない)だけで、メモリの枯渇などは、ランナーがジョブごと落とすことで、CI の失敗になる | マージをブロック | NFR4.7 |
| 7. 起動時間の確認 | この Unit の起動前の処理(全ジョブの `check_command`、ステートの読み込み、照合、初期ステートの書き込み(同期なし))を、ジョブ10個の定義で 100 回繰り返し、p95(昇順の 95 番目)を、標準のライブラリの時計で測る。3つの OS で行う | p95 が 20ms(仮)を超えたら、ジョブの要約欄に、測定値と基準を書き出して警告とし、失敗にはしない。Code Generation の実測で、失敗にするかを決める | NFR1.1 |
| 8. カバレッジ | Linux だけで `cargo llvm-cov` により、この Unit のクレート(`--package <この Unit のパッケージ>`。測る対象は `crates/u2-runtime/src/`)の行カバレッジを、Unit ごとに測り、80% 未満なら失敗にする。補助の実行ファイルのソースは、測定から除外する(`--ignore-filename-regex`)。`cfg(windows)` のコードは、Linux の測定に入らないため、その部分は、数値ではなく、Windows の CI のテストの成功で確かめる。ワークスペース全体の値も、あわせて記録する | マージをブロック | NFR5.1 |
| 9. 依存の確認(候補) | `cargo-deny`(ライセンス)と `cargo-audit`(脆弱性)。導入は CI Pipeline のステージで決める(u1-core・u4-converter と同じ) | — | NFR2.1 |

## ジョブの構成(必須のチェックにする単位)

| ジョブ名 | 実行の場所 | 内容 |
|----------|------------|------|
| `lint` | Linux | 段階 1(整形)、段階 2(静的解析) |
| `build-check` | Linux、Windows | 段階 3(ビルド、`cargo tree` の検査、最小の Rust のバージョンのビルド、検索の検査。検索の検査は Linux のみ) |
| `test` | Linux、macOS、Windows(OS のマトリクス) | 段階 4・5・6(`cargo test --workspace --locked` を、**1回の実行で**行う。OS 固有のテスト(段階 5)は、`cfg` で、その OS だけが実行する、同じ実行の中のテスト。時間の上限(段階 6)も、同じ実行の中)、`timeout-minutes: 15`。デバッグビルドで実行する |
| `startup-bench` | Linux、macOS、Windows | 段階 7(リリースビルドで測る。警告のみで、失敗にしない)。必須のチェックにしない |
| `coverage` | Linux | 段階 8 |
| `deps`(候補) | Linux | 段階 9 |

- **必須のチェックにするのは、`lint`、`build-check`、`test`(OS ごとの3つ)、`coverage`**。ワークフローの `timeout-minutes` は、`test` と `build-check` に 15、`coverage` に 20(仮)を設定する。
- **スキップを成功と数えない**: `root` の環境で、権限のテストを自分でスキップしたときは、テストの出力に「スキップ」と明記し、ジョブの要約欄に、スキップした件数を書き出す(見えなくならないように)。

## 起動の条件

- `main` への push と、`main` に向けたプルリクエスト。
- パスの絞り込みはしない。「マージ前に CI を通す」(team.md)ために、必須のチェックは、すべての変更で実行する。文書だけの変更でも起動する(パスの絞り込みで起動しないと、必須のチェックが保留のままになり、マージできなくなるため)。

## ツールチェインとキャッシュ

- Rust は、edition 2024 を使える最新の安定版。ワークフローで、バージョンを明示して固定する。
- 依存のビルド結果は、`Cargo.lock` のハッシュをキーにしてキャッシュする。キャッシュがなくても、結果は変わらない。

## 3つの OS 固有の注意

- `cargo test` は、各テストを新しいスレッドで動かす。そのスタックの大きさは、既定では、どの OS でもほぼ同じ(約 2 MiB)である。
- macOS では、ディスクへの同期(`sync_all`)が、Linux より遅い。起動時間の確認(段階 7)の初期ステートの書き込みは、同期を省く設計(NFR1.1)だが、結果の書き込みの同期の時間も、同じ段階で記録する(基準の対象にはしない)。
- Windows では、ステートの置き換え(`rename`)が、ほかのプロセスが開いているファイルに対して失敗しうる。テストは、置き換え先をディレクトリにする方法で、失敗を起こす(権限に頼らない)。
- 改行が CRLF の `command` を含む定義、パスの区切りの違いは、テストで固定の文字列にせず、標準のライブラリの組み立てを使う。
- GitHub Actions の Linux のランナーは、通常、root ではないが、コンテナで root の場合、権限による失敗のテストは、自分でスキップする(失敗にしない)。

## ロールバック

- 失敗した変更は、`main` で `git revert` して戻す。履歴をそのまま取り込んだ(squash しない)取り込みを戻すときは、取り込みの形で分ける: マージコミットがあれば、親を指定する(`git revert -m 1 <マージコミット>`)。マージコミットがなく(早送り、リベース)、複数のコミットが入っているときは、そのコミットの範囲を、新しい順に revert する(`git revert <最初のコミット>^..<最後のコミット>`)。取り込みの形は、CI Pipeline のステージで決める。
- この Unit は、状態を持たず(ステートファイルは、実行時のもの)、配布もしないため、データの巻き戻しや、環境の戻しは要らない。

## 秘密情報(secrets)

- この Unit の CI は、秘密情報を必要としない。読み取りだけの権限(`contents: read`)で動かす。依存の取得は、公開のレジストリだけを使う。

## 環境の昇格

- なし。環境は、開発(ローカル)と CI の2つだけで、ステージングや本番は持たない。リリースは、タグで区切る(team.md)。

## Assumptions & Open Questions

- ワークフローのファイル(`.github/workflows/`)の作成は、CI Pipeline のステージで、ワークスペースに1つだけ行う。この文書は、u1-core・u4-converter の cicd-pipeline.md とあわせて、その入力となる設計である。 [assumption]
- プロセスを起動するテストの 30 秒、ジョブ全体の 15 分(`coverage` は 20 分)は、仮の値である。Code Generation で実測してから、見直す。 [assumption]
- Windows の `.cmd` のテスト(NFR4.9)の期待は、CI で確かめるまで、未確認である。期待と異なれば、設計を見直す(Q2: A)。 [assumption]
- 行カバレッジの測定に使う `cargo-llvm-cov` が、CI の Linux で動くことは、CI Pipeline のステージで確かめる。 [assumption]
