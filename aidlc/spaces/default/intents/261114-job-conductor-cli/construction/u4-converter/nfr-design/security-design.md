# Security Design(u4-converter)

上流: security-requirements(NFR4.1〜NFR4.7)、tech-stack-decisions(T1、T2、NFR1.1、NFR2.1、NFR3.1、NFR5.1)、functional-spec(W1)、rules(BR1.1〜BR1.12)、contract-summary(C4)。u4-converter は library であり、認証・認可・暗号化・ネットワークはない。入力は、利用者が指定する変換元のファイル1つである。コードは、短い疑似コード(15行以下)に限る。

**この設計は、nfr-requirements の関連する記述より優先する**(下の「既存の成果物との差分」を参照)。

## 設計の要点

### 1. 変換の流れ(イベントで読み、自分で展開して数える)

functional-spec の W1 と、rules の BR1.12 の失敗の順序に、1対1で対応させる。どの段階でも、失敗は、種類と場所を持つ ConversionError として返し、出力は作らない。YAML の読み取りは、**ライブラリが返す展開済みの木には頼らず**、パーサーの**イベントの列**(ノードの出現、アンカー、エイリアスの参照、位置)を、**再帰を使わずに**(明示のスタックで)読み、この Unit が、展開と数えを行う。(これにより、展開の大きさと深さの強制を、ライブラリの内部の挙動に頼らずに、確かめられる。)

1. **取り込み(Intake):** ファイルを開き、通常のファイルか確かめる。読み取りは「上限(1 MiB)+ 1 バイト」までに制限し、超えたら `tooLarge`。UTF-8 でなければ `unreadable`。(NFR4.2、BR1.5。BR1.12 の 1〜4)
2. **読み取り(Read)— 展開前の構造:**
   - **YAML:** イベントの列を、最後まで、明示のスタックで読み、展開しない構造(アンカーとエイリアスの参照を、そのまま持つ木。「素の木」)を作る。この段階で、文法の誤り、重複するキー、再帰するアンカー(アンカーが閉じる前に、そのアンカーを参照するエイリアス)、展開前の構造の深さ 32 の超過を、`syntax`(行つき)として返す。深さは、スタックに積むときに数え、33 段目で打ち切る(再帰がないため、異常終了しない)。素の木の大きさは、入力(1 MiB)で抑えられる。文書の数も数える。
   - **TOML:** `toml` のライブラリで読む。再帰の制限により、深い入力は、異常終了せず失敗で返ることを、Code Generation で確かめる(T2)。読み取り後に、深さを数え、32 を超えたら `syntax`。TOML には、エイリアスがないため、深さの確認は、この1回だけ。
   (BR1.12 の 5。NFR4.4、NFR4.7)
3. **文書の数と最上位の確認(RootCheck):** YAML に複数の文書があれば `unrepresentable`。最上位(最初の文書)がマップでなければ `rootNotMap`(空の YAML も)。空の TOML は空のマップ。(BR1.8。BR1.12 の 6、7)
4. **展開と途中の表現への写し取り(Resolve):** 素の木を、深さ優先・入力に現れる順で、明示のスタックを使い、途中の表現(Q1: A。下の `Value`)へ写す。この段階で、(i) アンカー・エイリアス・マージキーの展開(BR1.7)、(ii) 展開後の要素数と深さの数え(NFR4.3、NFR4.4)、(iii) 表せない値(null、文字列でないキー、タグつきの値、TOML の日時、i64 を超える整数)の、最初の1つの記録(BR1.6)を行う。要素数が 100,000 を超えたら `tooLarge`、展開後の深さが 32 を超えたら `syntax` で、その時点で打ち切る(先に達した方)。打ち切りがなければ、記録した表せない値があれば `unrepresentable`(keyPath つき)を返す。展開の上限の超過が、表せない値より優先される。TOML は、エイリアスがないため、展開は何もせず、表せない値(日時)の記録だけを行う。(BR1.12 の 8、9)
5. **書き出し(Write):** 途中の表現を、相手の形式の文字列にする。(BR1.2、BR1.3)
6. 文字列を返す。書き出し先への出力は、Cli の責務。(BR1.9)

### 2. 途中の表現(`Value`)と書き出しの規則

- **型:** 文字列、整数(`i64`)、浮動小数(`f64`)、真偽値、配列(順序つき)、マップ(キーは文字列。入力に現れる順を保つ並び)。
- **整数:** `i64` の範囲だけを持つ。YAML の整数が、`i64` を超えたら、`unrepresentable`(TOML が `i64` までのため。TOML から YAML の向きは、常に範囲内)。
- **浮動小数:** `-0.0` の符号、`nan`、`inf`、`-inf` を保つ。書き出しでは、整数と区別できる形で出力する(`1.0` を `1` にしない)。往復の等しさ(BR1.11)は、NaN どうしを等しく、`0.0` と `-0.0` を区別して比べる。
- **マップの順序:** 読み取りの順(入力に現れる順)を保った並びで持つ。書き出しの順序は、読み取りの順とする(BR1.3 は、順序の保持を求めないが、この実装は、決まった順序を出力する。これにより、出力が確定する)。TOML の書き出しで、ライブラリが、テーブルを整列する場合は、その順序でよい(BR1.3 の範囲)。この場合も、テストは、順序を問わない比較(BR1.11)を使う。
- **文字列の引用符:** 値もキーも、読み戻したときに文字列のままになるように、必要なら引用符で囲む。キー `<<` は、YAML へ出力するとき、必ず引用符で囲む。(BR1.2)

### 3. 副作用を持たない

入力のファイルを読む以外の入出力を、この Unit に置かない。環境変数の参照、プロセスの起動、ネットワーク、ファイルの書き込みは、しない。YAML のタグで、型の構築やコードの実行をしない(タグつきの値は BR1.6 に従って拒否または同じ扱い)。ソースに `std::process`、`std::net` を使わないことを、検索で確かめる。(NFR4.5)

### 4. エラーの表示(NFR4.6)

- 表示は、kind ごとの固定の文と、ファイル名、行、キーの経路から組み立てる。ライブラリのエラー文、ソースの抜粋、誤った値は含めない。
- キー名など、入力に由来する文字列は、制御文字と、書式・双方向の制御文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)をエスケープし、64 文字までに切る。
- u1-core にも同じ処理がある。u4-converter は、Unit の独立を保つため、この小さな関数を、この Unit にも持つ(D4)。

### 5. パニックしない(NFR4.7)

外部の入力に対する処理は、すべて、戻り値のエラーで失敗を返す。YAML の読み取りと展開は、再帰を使わず、明示のスタックで行う(深さは 32 で打ち切るため、スタックも小さい)。素の木と途中の表現を捨てるときの再帰も、深さが 32 までに抑えられている。配列やマップの添字を、入力の長さを確かめずに使わない。

## 既存の成果物との差分(この設計を優先する)

| 対象 | 変更の内容 |
|------|------------|
| tech-stack-decisions の T1(YAML のライブラリの条件) | 条件に、「パーサーのイベントの列(ノード、アンカー、エイリアス、位置)を、展開せずに提供し、呼び出し側が、再帰を使わずに読めること」を足す。`serde` ベースで、展開済みの木だけを返すライブラリは、候補から外す。条件を満たすものがなければ、T1 の止めて人に確認する手順に従う |
| security-requirements の NFR4.3 の (a)/(b) | この設計は、(a)(展開しながら数える。自分で展開する)を採る。(b)(展開前の見積もり)と、NFR4.4 の事前の走査は、使わない(イベントの列を、自分で読むため、不要) |
| security-requirements の NFR4.4 | YAML は、スタックで読むため、再帰の制限に頼らない(深さは、明示のスタックに積むときに数える)。TOML は、`toml` のライブラリの再帰の制限に頼り、Code Generation で確かめる |

## 他の NFR の設計(NFR1.1、NFR2.1、NFR3.1、NFR5.1)

- **NFR1.1:** この Unit は、静的な初期化(起動時に動く処理、`lazy` な大域の変数)を持たない。ライブラリの初期化は、`convert` の呼び出しの中でだけ行う。`run` と `pipeline` の起動経路から、この Unit の関数を呼ばない(u3-cli の設計で確かめる)。
- **NFR2.1:** 依存は、Rust だけのライブラリに限る(`cargo tree` に `-sys` がない。CI で確かめる)。
- **NFR3.1:** OS 固有の分岐を置かない。3つの OS で、同じテストが通る(CI)。
- **NFR5.1:** 往復のテスト(BR1.11)と、各 kind のテスト、上限と深さの境界のテストで、行カバレッジ 80% 以上(CI の Linux で `cargo llvm-cov`)。

## 設計の判断(代替案との比較)

### D1 途中の表現を、自前の小さな型にする [Q1: A]

- **Context:** YAML と TOML は、型の体系が違う(null、日時など)。検査(表せない値、大きさ、深さ)と書き出しの規則(引用符)を、1か所に集めたい。
- **Decision:** 文字列・整数・浮動小数・真偽・配列・マップだけを持つ、この Unit の中の小さな型(`Value`)を、途中の表現にする。ライブラリの型は、読み書きの端だけで使う。
- **Consequences:** 良い点は、検査と書き出しの規則が1か所に集まり、往復のテスト(BR1.11)を、型の上で書ける。悪い点は、写し取りのコードが増える。
- **Alternatives Rejected:** (B) 片方のライブラリの値の型を、そのまま途中の表現にする案: 写し取りは減るが、もう片方に無い型(null、日時)の扱いが、ライブラリの型に引きずられ、検査と引用符の規則が散らばるため退けた。

### D2 YAML は、イベントの列を自分で読み、展開と数えを自分で行う [Q2: A の見直し(下の注)]

- **Context:** Rust では、スタックの枯渇は、プロセスの異常終了(abort)になり、戻り値のエラーにならない。また、ライブラリが、展開済みの木を返す場合、展開の大きさ(いわゆる「billion laughs」)を、呼び出し側で抑えられない。
- **Decision:** YAML のパーサーのイベントの列を、再帰を使わずに読み、展開前の構造(素の木)を作り、そこから、自分で展開して数える(上の流れの 2、4)。深さは、スタックに積むときに数える。
- **Consequences:** 良い点は、展開の大きさと深さを、ライブラリの内部に頼らず、確かめられる。事前の走査も、不要になる。悪い点は、展開(アンカー、エイリアス、マージキー)を自分で実装する(コードが増える。往復のテストで守る)。また、イベントの列を提供するライブラリに、候補が限られる(T1 の条件)。
- **Alternatives Rejected:** (1) ライブラリが展開した木を返し、その後で数える案: 展開の大きさが、数える前に、メモリを使い切りうるため退けた。(2) ライブラリの再帰の制限に任せ、ライブラリが展開を段階的に行えるか確かめる案(元の Q2: A の主案): ライブラリの制限値が 32 とは限らず、展開の段階的な制御も、ライブラリによるため、確かめられる範囲が狭い。確かめて使える場合は、実装の簡素化として残してよい(その場合も、深さ 32 と要素数の数えは、この設計の上限を守る)。(3) 別のスレッドで、大きなスタックで読む案: 異常終了の危険を下げるだけで、防げないため退けた。
- **注(Q2 との関係):** Q2 の選択 A(ライブラリの制限を確かめて任せる、だめなら事前の走査)は、この設計では、「ライブラリの制限に任せる」の前に、イベントの列を自分で読む方法を主案にする、という見直しになる。これは、Q2 の趣旨(異常終了させない、展開の爆発を防ぐ)を、より確かな方法で満たす。選択の変更になるため、レビューのあとに、人に確認する。

### D3 失敗の判定の順序を、段階で固定する

- **Context:** 同じ入力で、実装者の選び方しだいで kind が変わると、テストが確定しない(BR1.12)。
- **Decision:** 上の「変換の流れ」の段階と、BR1.12 の順序を、1対1にする。YAML の場合、文法の誤り・重複するキー・再帰するアンカー・展開前の深さ(段階 2)、文書の数と最上位(段階 3)、展開の上限(段階 4 の途中)、表せない値(段階 4 の最後)の順。
- **Consequences:** 良い点は、テストが確定する。悪い点は、表せない値を、展開の最後まで記録して、あとで返すため、先に見つけても、すぐには返せない。
- **Alternatives Rejected:** 最初に見つかった失敗を、すぐに返す案: 実装は単純だが、展開と走査の順で kind が変わり、テストが確定しないため退けた。

### D4 エラー表示の補助を、u1-core と共有せず、持つ

- **Context:** キー名のエスケープと切り詰めは、u1-core にも同じものがある。
- **Decision:** u4-converter は、Unit の独立を保つため、小さな関数を、この Unit にも持つ。内容は、同じ規則(security-requirements の NFR4.6)に従い、揃っていることは、同じ入力と期待値の表を、両方のテストに置いて確かめる(表の内容は、レビューで見比べる)。
- **Consequences:** 良い点は、Unit が独立し、それぞれのビルドとテストが、他に依存しない。悪い点は、同じ規則を2か所に持つ(規則を変えるときは、両方を直す)。
- **Alternatives Rejected:** 共通の(他に依存しない)クレートを作って、両方から使う案: 重複は無くなり、依存の DAG も壊れないが、この規模(数十行)に対して、クレートが増え、リリースとバージョンの管理が増えるため、いまは退けた。重複が育つなら、見直す。

## Assumptions & Open Questions

- イベントの列を、展開せずに提供する YAML のライブラリが、T1 の条件(YAML 1.2、位置、重複するキーの扱い、MSRV 1.85)を満たすかは、Code Generation の最初に確かめる。満たすものがなければ、止めて人に確認する(T1)。 [assumption]
- 重複するキーの検知は、素の木を作るときに、この Unit が行う(ライブラリが検知しない場合も含む)。 [assumption]
- 表せない値の記録は、最初の1つだけで十分とする(BR1.6)。複数を報告する要望が出たら、見直す。 [assumption]
- D2 は、Q2 の選択 A から、方法を見直した。人に、この見直しを、レビューのあとで確認する。 [assumption]
- 認証・認可・暗号化は、この Unit に該当しない。 [assumption]
