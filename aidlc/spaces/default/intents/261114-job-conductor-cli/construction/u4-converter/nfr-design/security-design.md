# Security Design(u4-converter)

上流: security-requirements(NFR4.1〜NFR4.7)、tech-stack-decisions(T1、T2、NFR1.1、NFR2.1、NFR3.1、NFR5.1)、functional-spec(W1)、rules(BR1.1〜BR1.12)、contract-summary(C4)。u4-converter は library であり、認証・認可・暗号化・ネットワークはない。入力は、利用者が指定する変換元のファイル1つである。コードは、短い疑似コード(15行以下)に限る。

## 設計の要点

### 1. 変換の流れ(段階を分け、順序を固定する)

functional-spec の W1 と、rules の BR1.12 の失敗の順序に、1対1で対応させる。どの段階でも、失敗は、種類と場所を持つ ConversionError として返し、出力は作らない。

1. **取り込み(Intake):** ファイルを開き、通常のファイルか確かめる。読み取りは「上限(1 MiB)+ 1 バイト」までに制限し、超えたら `tooLarge`。UTF-8 でなければ `unreadable`。(NFR4.2、BR1.5。段階 1〜4)
2. **読み取り(Read):** 入力の形式(`--to` と反対。BR1.1)として、文書の終わりまで読む。文法の誤り、重複するキー、再帰するアンカー、展開前の構造の深さの超過は `syntax`。深さの超過は、T1・Q2 の方針に従い、(a) ライブラリの再帰の制限、または (b) 読み取りの前の、再帰を使わない深さの走査で、異常終了せずに拒否する。(NFR4.4。段階 5)
3. **文書の数と最上位の確認:** YAML に複数の文書があれば `unrepresentable`。最上位(最初の文書)がマップでなければ `rootNotMap`(空の YAML も)。空の TOML は空のマップ。(BR1.8。段階 6、7)
4. **途中の表現への写し取り(Normalize):** ライブラリの木を、この Unit の途中の表現(Q1: A。文字列・整数・浮動小数・真偽・配列・マップだけを持つ小さな型)へ、深さ優先・入力に現れる順で写す。この段階で、(i) アンカー・エイリアス・マージキーの展開(BR1.7)、(ii) 展開後の要素数と深さの数え(NFR4.3、NFR4.4。超えた時点で打ち切る)、(iii) 表せない値(null、文字列でないキー、タグつきの値、TOML の日時、範囲を超える整数)の最初の1つの記録(BR1.6)を行う。展開の上限の超過(`tooLarge`、深さは `syntax`)は、表せない値より優先して返す(BR1.12 の 8 は 9 より先)。(段階 8、9)
5. **書き出し(Write):** 途中の表現を、相手の形式の文字列にする。文字列は、値もキーも、読み戻したときに文字列のままになるように、必要なら引用符で囲む。キー `<<` は、YAML へ出力するとき、必ず引用符で囲む。(BR1.2、BR1.3)
6. 文字列を返す。書き出し先への出力は、Cli の責務。(BR1.9)

### 2. 副作用を持たない

入力のファイルを読む以外の入出力を、この Unit に置かない。環境変数の参照、プロセスの起動、ネットワーク、ファイルの書き込みは、しない。YAML のタグで、型の構築やコードの実行をしない(タグつきの値は BR1.6 に従って拒否または同じ扱い)。ソースに `std::process`、`std::net` を使わないことを、検索で確かめる。(NFR4.5)

### 3. 展開の大きさと深さの強制(NFR4.3、NFR4.4)

- **(a) 展開しながら数える:** ライブラリが、展開を段階的に行える(イベントの列、または、展開を呼び出し側が進める作り)場合は、写し取りの段階で、要素数と深さを数え、上限(100,000、32)に達した時点で打ち切る。先に達した方の kind を返す。
- **(b) 展開前に見積もる:** ライブラリが、展開した木を、一度に返す場合は、読み取りの前に、イベントの列から、アンカーごとの大きさと参照の回数で、展開後の要素数を、木を作らずに見積もり、上限を超える見込みなら拒否する。
- **どちらも使えない:** そのライブラリを選ばない。T1 の「止めて人に確認する」手順に従う(Code Generation の Step 1)。
- 深さは、最上位のマップを 1 として数える。読み取り時(展開前)と展開後の2回数える。(NFR4.4)

### 4. エラーの表示(NFR4.6)

- 表示は、kind ごとの固定の文と、ファイル名、行、キーの経路から組み立てる。ライブラリのエラー文、ソースの抜粋、誤った値は含めない。
- キー名など、入力に由来する文字列は、制御文字と、書式・双方向の制御文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)をエスケープし、64 文字までに切る。
- この処理は、u1-core にも同じものがある。u4-converter は、u1-core に依存しない(依存の DAG のため)ので、小さな関数を、この Unit にも持つ(D4)。

### 5. パニックしない(NFR4.7)

外部の入力に対する処理は、すべて、戻り値のエラーで失敗を返す。整数は、相手の形式で表せる範囲を、変換の前に確かめ、桁あふれで黙って値が変わらないようにする。配列やマップの添字を、入力の長さを確かめずに使わない。

## 設計の判断(代替案との比較)

### D1 途中の表現を、自前の小さな型にする [Q1: A]

- **Context:** YAML と TOML は、型の体系が違う(null、日時など)。検査(表せない値、大きさ、深さ)と書き出しの規則(引用符)を、1か所に集めたい。
- **Decision:** 文字列・整数・浮動小数・真偽・配列・マップだけを持つ、この Unit の中の小さな型を、途中の表現にする。ライブラリの型は、読み書きの端だけで使う。
- **Consequences:** 良い点は、検査と書き出しの規則が1か所に集まり、往復のテスト(BR1.11)を、型の上で書ける。悪い点は、写し取りのコードが増える。
- **Alternatives Rejected:** (B) 片方のライブラリの値の型を、そのまま途中の表現にする案: 写し取りは減るが、もう片方に無い型(null、日時)の扱いが、ライブラリの型に引きずられ、検査と引用符の規則が散らばるため退けた。

### D2 深さの防ぎ方は、ライブラリの制限を確かめてから任せる [Q2: A]

- **Context:** Rust では、スタックの枯渇は、プロセスの異常終了(abort)になり、戻り値のエラーにならない。
- **Decision:** ライブラリの再帰の制限が、深さ 100,000 の入力でも、失敗で返ることを、Code Generation の最初に確かめ、確かめられたものに任せる。確かめられないときだけ、読み取りの前の、再帰を使わない深さの走査を足す。
- **Consequences:** 良い点は、確かめられれば、二重の処理(速度と実装)を避けられる。悪い点は、ライブラリの更新で、制限の挙動が変わりうる(テストで守る)。
- **Alternatives Rejected:** (B) 常に事前の走査を行う案: 確実だが、ライブラリの制限があっても、入力を2回走査する費用と実装が要るため退けた(必要なときだけ足す)。(C) 別のスレッドで、大きなスタックで読む案: 異常終了の危険を下げるだけで、防げないため退けた(NFR4.4)。

### D3 失敗の判定の順序を、段階で固定する

- **Context:** 同じ入力で、実装者の選び方しだいで kind が変わると、テストが確定しない(BR1.12)。
- **Decision:** 上の「変換の流れ」の段階と、BR1.12 の順序を、1対1にし、展開の上限の超過を、表せない値より先に返す。
- **Consequences:** 良い点は、テストが確定する。悪い点は、表せない値を、展開の最後まで記録して、あとで返すため、先に見つけても、すぐには返せない。
- **Alternatives Rejected:** 最初に見つかった失敗を、すぐに返す案: 実装は単純だが、展開と走査の順で kind が変わり、テストが確定しないため退けた。

### D4 エラー表示の補助を、u1-core と共有せず、持つ

- **Context:** キー名のエスケープと切り詰めは、u1-core にも同じものがある。
- **Decision:** u4-converter は、他の Unit に依存しない(依存の DAG)ため、小さな関数を、この Unit にも持つ。内容は、同じ規則(security-requirements の NFR4.6)に従い、テストで揃える。
- **Consequences:** 良い点は、Unit の独立を保てる。悪い点は、同じ規則を2か所に持つ(規則を変えるときは、両方を直す)。
- **Alternatives Rejected:** 共通のクレートを作って、両方から使う案: 重複は無くなるが、この規模(数十行)に対して、クレートが増え、依存の DAG が複雑になるため、いまは退けた。重複が育つなら、見直す。

## Assumptions & Open Questions

- YAML のライブラリが、(a)(b)のどちらかで、展開の大きさを抑えられるか、再帰の制限を持つかは、Code Generation の最初に確かめる(T1 の止める手順)。 [assumption]
- 表せない値の記録(段階 4 の (iii))は、最初の1つだけで十分とする(BR1.6)。複数を報告する要望が出たら、見直す。 [assumption]
- 認証・認可・暗号化は、この Unit に該当しない。 [assumption]
