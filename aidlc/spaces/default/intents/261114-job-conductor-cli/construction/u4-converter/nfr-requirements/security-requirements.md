# Security Requirements(u4-converter)

上流: functional-spec(W1)、rules(BR1.1〜BR1.12)、requirements(NFR4)、contract-summary(C4)、質問への回答(Q1〜Q3)。u4-converter は library であり、認証・認可・暗号化・ネットワークはない。入力は、利用者が指定する変換元のファイル1つで、基本的に信頼できるが、誤り(巨大なファイル、展開で膨らむ YAML、深すぎる入れ子)は、事故として起こりうる。各行は、inception の NFR の ID に枝番を付けた ID を持つ。

## 要件

| ID | 要件 | 判定の基準 | 出典 |
|----|------|------------|------|
| NFR4.1 | 入力が誤っているときは、変換を行わず、出力を作らない。誤りは、種類(`fileMissing`、`unreadable`、`tooLarge`、`syntax`、`unrepresentable`、`rootNotMap`)と場所で返す | 誤った入力のテストで、成功の結果(ConvertedText)が返らず、種類と場所が期待どおり | NFR4、FR7.2、AC7.1.3、BR1.4〜BR1.6、BR1.8 |
| NFR4.2 | 入力の大きさに上限(1 MiB)を置く。読み取りは「上限 + 1 バイト」までに制限し、超えたら `tooLarge` | 1 MiB ちょうどは受理、1 MiB + 1 バイトは `tooLarge`。上限を超えて読まないこと(終わりのない入力でも、上限 + 1 バイトで止まる) | NFR4、BR1.5、Q2: A |
| NFR4.3 | YAML の展開(アンカー、エイリアス、マージキー)で、メモリを使い切らない。展開後の要素数に上限(100,000)を置く。強制の手段は、次の2つのどちらか(Code Generation の最初に、選んだライブラリで確かめて決める): (a) 展開しながら数え、超えた時点で打ち切る、(b) 展開する前に、イベント(ノードの出現)の列から、アンカーごとの大きさと参照の回数で、展開後の要素数を見積もり(実際の木は作らない)、上限を超える見込みなら拒否する。どちらも使えない(ライブラリが、展開した木を、上限なしで返すだけ)場合は、そのライブラリを選ばない。超えたときの kind は `tooLarge` | エイリアスを入れ子にして膨らませる入力(いわゆる「billion laughs」型)で、メモリを使い切らず、`tooLarge` が返る(テスト入力は、上限を超えるが、1 MiB 以内のもの)。展開後の要素数ちょうど 100,000 は受理、100,001 は `tooLarge` | NFR4、BR1.7、Q2: A |
| NFR4.4 | 入れ子の深さに上限(32)を置く。深さは、最上位のマップを 1 として数え、マップ・配列・インラインのテーブルが 1 段ずつ。読み取り時(展開前)と、YAML の展開後の2回数える。超えたら `syntax`。展開しながら数えるときは、深さの超過と要素数の超過のうち、先に達した方を返す(深さ優先の順)。読み取りの再帰による異常終了(スタックの枯渇。Rust では、スタックの枯渇は、プロセスの異常終了(abort)になり、戻り値のエラーにならない)を防ぐ。強制の手段は、次の順に選ぶ: (a) ライブラリが、再帰の深さの制限を持ち、超えたらエラーを返す、(b) 読み取りの前に、構造の深さ(括弧・インデント・イベントの入れ子)を、再帰を使わずに数える事前の走査を行い、32 を超える入力を、読み取りの前に拒否する。別のスレッドで大きなスタックを使う方法は、異常終了の危険を下げるだけで、防ぐ手段にしない | 深さ 32 は受理、33 は `syntax`。深さ 1000 と 100,000 の入力(YAML と TOML。配列、インラインのテーブル、インデントの入れ子)で、異常終了せず `syntax` が返る。エイリアスを通して深くなる入力も同じ | NFR4、BR1.7、BR1.12 |
| NFR4.5 | 変換は、副作用を持たない。入力のファイルを読むだけで、書き込み、環境変数の参照、プロセスの起動、ネットワークへのアクセスをしない。YAML のタグで、コードを実行したり、型を構築したりしない。タグつきの値は、BR1.6 に従う(`!!binary`、独自のタグは `unrepresentable`。`!!str` など、標準のスカラーのタグで、結果の型が変わらないものは、タグなしと同じに扱う) | (a) 変換の入口の関数が、入力のパスのファイルを読む以外の入出力をしないこと: テストで、一時ディレクトリの外にファイルが作られないこと、環境変数を変えても結果が変わらないこと(`temp_env` などの道具は使わず、標準のライブラリで、環境変数を変えて比べる)。(b) `!!binary`、独自のタグ(`!mytag`)は `unrepresentable`、`!!str "1"` は文字列 `1` として受理。この Unit のソースに、`std::process`、`std::net` の使用がない(検索で確かめる) | NFR4、BR1.6、BR1.9 |
| NFR4.6 | エラーの表示は、固定の文と場所(ファイル名、行、キーの経路)だけで組み立てる。入力の値と、ライブラリのエラー文を含めない。キーの名前は、制御文字と書式・双方向の制御文字をエスケープし、64 文字までに切る | すべての `kind` で、表示の文に入力の値が現れない。キー名のエスケープと切り詰めのテスト | NFR4、BR1.10 |
| NFR4.7 | 外部の入力に対する処理で、パニックしない。失敗は、戻り値のエラーで返す。数値の範囲(整数の桁あふれ)の扱いで、パニックや、黙った値の変化をしない | 範囲を超える整数、深い入れ子、壊れた UTF-8、空の入力で、パニックせず、期待する `kind` が返る | NFR4、BR1.6、BR1.12 |

## この Unit に該当しない NFR

- 認証・認可・暗号化・秘密情報の取り扱い: この Unit は、秘密情報を扱わず、ネットワークにも触れない。

## Assumptions & Open Questions

- 展開後の要素数 100,000 の上限は、確定した値だが、実際の定義ファイルに対して十分に大きいかは、Code Generation の実測で見直す。 [assumption]
- 読み取りの再帰による異常終了を防ぐ手段(ライブラリの深さの制限)は、選んだ YAML・TOML のライブラリに依存する。Code Generation の最初に、深さ 1000 の入力で確かめる(u1-core と同じ手順)。足りなければ、NFR4.4 の (b)(読み取りの前の、再帰を使わない深さの走査)を使う。別スレッドで読む方法は、防ぐ手段にしない。TOML の側も、選んだライブラリで、深さ 1000 と 100,000 の入力が、異常終了せず失敗で返ることを確かめる(確かめられなければ、同じ (b) を使う)。 [assumption]
