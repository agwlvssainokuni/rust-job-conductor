# Security Requirements(u1-core)

上流: functional-spec(この Unit の functional-spec.md)、rules(この Unit の rules.md)、requirements(NFR4)、contract-summary(E2 定義ファイルの約束事)。u1-core は、定義ファイル(利用者が書く入力)の読み込みと検証、および入出力のない判断ロジックを受け持つ library である。認証・認可・暗号化・個人情報の保持はなく、規制・機密データに関する要件もない(constraint-register の C9)。ここでは、入力の安全な扱いに絞って要件を定める。各行は、inception の NFR の ID に枝番を付けた ID を持つ。

## 要件

| ID | 要件 | 判定の基準 | 出典 |
|----|------|------------|------|
| NFR4.1 | 型の誤り(例: 終了コードを文字列で書く、必須の値の欠落)を、ジョブの実行より前に検知し、ファイル名・行・原因を返す | 型の誤りを含む定義ファイルを渡すと、`typeMismatch` の `DefinitionError` が返り、ジョブは実行されない | NFR4、rules の BR1.5 |
| NFR4.2 | 定義にないキーは、受け付けず、エラーにする。キーの綴りの誤りを、実行前に見つける | 知らないキーを含む定義ファイルを渡すと、`unknownKey` が返り、キーと行が示される | NFR4、rules の BR1.6 |
| NFR4.3 | 書式の版を、他の検査より先に確認する。版が無い、または対応しない定義は、受け付けない | 版が無い定義は `versionMissing`、対応しない版は `versionUnsupported` が返る。版のエラーがあるときは、他の検査の結果は返さない | NFR4、rules の BR1.7 |
| NFR4.4 | 定義ファイルの大きさに上限(1 MiB)を置き、超えたときは、読み取りに進まず、定義の誤りとして拒否する | 上限を超える定義ファイルを渡すと、読み取りの前に拒否され、`unreadable`(上限超過)が返る | NFR4 |
| NFR4.5 | 定義の内容を、実行や評価はしない。定義に書かれたコマンドの文字列は、データとして扱い、検証の段階では、起動も展開もしない | 検証の処理が、ファイルシステムへの書き込み、プロセスの起動、環境変数の展開を行わない(単体テストで確かめる) | NFR4、components の DefinitionLoader |
| NFR4.6 | エラーの表示に含める情報は、原因の把握に必要な範囲に限る(ファイル名、行、キー、理由)。定義の内容の全文や、環境変数の値は含めない | `DefinitionError` の内容が、ファイル名・行・種類・理由に限られる | NFR4、decisions の ADR-003 |
| NFR4.7 | 読み取りは、不正な形式の入力に対して、異常終了(パニック)しない。常に、`DefinitionError` として報告する | 壊れた TOML、巨大な入れ子、不正な文字列を渡しても、パニックせず、`DefinitionError` が返る(単体テストで確かめる) | NFR4 |

## 脅威の考察(簡易)

- **誤った・壊れた定義ファイル:** 利用者の記述ミスや、壊れたファイルは、起こりうる主な脅威であり、NFR4.1〜NFR4.4、NFR4.7 で、実行前に検知する。
- **悪意のある定義ファイル:** 定義ファイルを書く人は、ジョブのコマンドを書ける人であり、定義ファイルを書ける人は、そもそもコマンドを実行できる立場にある。ここでは、権限の昇格は、脅威としない。ただし、巨大なファイルで資源を使い切ること(NFR4.4)と、検証の処理が副作用を持つこと(NFR4.5)は、防ぐ。
- **機密情報:** 定義ファイルのコマンドの文字列に、認証情報が含まれうるが、この Unit は、それを保存・送信しない。表示にも、全文を含めない(NFR4.6)。

## Assumptions & Open Questions

- 「巨大な入れ子」などへの具体的な上限(読み取りの深さなど)は、Code Generation で、使うライブラリの機能に合わせて決める。 [assumption]
- 認証・認可・暗号化は、この Unit に該当しない。 [assumption]
