# Security Design(u1-core)

上流: security-requirements(NFR4.1〜NFR4.7)、tech-stack-decisions(NFR1.1、NFR2.1、NFR3.1、NFR5.1)、functional-spec(W1 定義の読み込みと検証、W3 判断)、contract-summary(C2、E2)。u1-core は library であり、認証・認可・暗号化・ネットワークはない。入力は、利用者が書く定義ファイル1つである。この文書は、前のステージ(NFR Requirements)のレビューで引き継いだ指摘(7点)への対応も含む。コードは、短い疑似コード(15行以下)に限る。

## 設計の要点

1. **定義ファイルの読み取りは、段階を分ける(二段階の読み取り)。** 版の検査を先に行う(NFR4.3、BR1.7)ため、次の順にする。
   1. ファイルの大きさを確認し、上限(1 MiB)を超えるなら拒否する。読み取りそのものを「上限 + 1 バイト」までに制限し、確認と読み取りのあいだにファイルが変わっても、上限を超えて読まない。(NFR4.4)
   2. 内容を、型を決めない汎用の木(キーと値の入れ子)として読み取る。文法の誤りは、この段階で、`syntax` の誤りとして返す。(NFR4.7)
   3. 木の中の版のキーを確認する。版が無ければ `versionMissing`、対応しなければ `versionUnsupported` を返し、ここで終える。(NFR4.3)
   4. 版が通れば、同じ木から、型付きの構造に変換する。知らないキーと型の誤りは、この段階で、`unknownKey` と `typeMismatch` として返す。(NFR4.1、NFR4.2)
   5. 構造の検査(ジョブIDの重複・空、遷移の向き、終了コードの重複など。BR1.1〜BR1.4、BR1.13)を行い、すべての誤りをまとめて返す。
2. **検証は副作用を持たない。** 検証の処理は、ファイルの書き込み、プロセスの起動、環境変数の展開をしない。コマンドの文字列は、データとして保持するだけで、解釈しない。(NFR4.5)
3. **エラーの表示は、範囲と種類から組み立てる。** ライブラリの標準のエラー文は、ソースの行の抜粋や、誤った値を含みうるため、そのまま使わない。ファイル名、行番号、種類、理由(固定の文)から、表示の内容を組み立てる。行番号は、エラーが指す位置(バイトの位置)から、ファイルの先頭からの改行を数えて求める。(NFR4.6)
4. **パニックしない。** 外部の入力に対する処理は、すべて、戻り値のエラーで失敗を返し、パニックに頼らない。入れ子の深さには、数値の上限(32 段)を置く。深すぎる入力は、読み取る前の簡易な走査、または読み取りの設定で拒否し、`syntax` として返す。再帰による異常終了(スタックの枯渇)は、パニックでは捕まえられないため、上限で未然に防ぐ。(NFR4.7)

## 追加する種類

DefinitionError に、次の種類を足す(functional-design の entities.md の `kind` の拡張。Code Generation で反映する)。

| 種類 | 意味 |
|------|------|
| `syntax` | TOML の文法の誤り、入れ子が深すぎる入力 |
| `tooLarge` | ファイルの大きさが上限(1 MiB)を超えた(BR1.9 の `unreadable` とは分ける) |

「上限超過」を `unreadable` に含めず、`tooLarge` として分けることで、BR1.9 の意味を広げずに済む。

## 設計の判断(代替案との比較)

### D1 TOML の読み取りに serde と toml を使う [Q1: A]

- **Context:** 型の誤りと知らないキーを、実行前に検知したい(NFR4)。Rust に不慣れな開発者が、誤りにくい方法を選びたい。
- **Decision:** `serde` と `toml` を使い、型付きの構造への変換で、型の誤りと知らないキーを検知する。二段階の読み取り(汎用の木 → 型付きの構造)にする。
- **Consequences:** 良い点は、型に載せて検証でき、実績がある。悪い点は、依存が増える。標準のエラー文は、そのまま使えない(上の3)。
- **Alternatives Rejected:**
  - TOML の読み取りを手書きする案: 依存は無いが、実装と検証の手間が大きく、誤りやすい。読み取りの誤りが、そのまま、誤った定義の実行につながるため退けた。
  - 設定用の別のライブラリ(複数形式を扱う設定ライブラリ)を使う案: 形式の幅は広いが、型の厳密な検証、知らないキーの拒否、行番号の報告に、余計な仕組みが入り、依存も大きくなるため退けた。

### D2 エラーの型に thiserror を使う [Q3: A]

- **Context:** DefinitionError など、種類の多いエラーに、表示の文を付ける必要がある。
- **Decision:** `thiserror` を使い、種類ごとに表示の文を型に付ける。ただし、外部のエラー文は、そのまま取り込まず(上の3)、固定の文から組み立てる。
- **Consequences:** 記述が短い。依存が1つ増える。
- **Alternatives Rejected:**
  - 標準のライブラリだけで手書きする案: 依存は増えないが、種類が多いため、記述が長く、書き間違いやすい。
  - エラーを文字列で持つ案: 簡単だが、種類で処理を分けられず、終了コード(64〜67)や表示の出し分けに使えないため退けた。

### D3 定義ファイルの大きさに上限(1 MiB)を置く [Q4: A]

- **Context:** 誤って巨大なファイルが渡される事故を防ぎたい。定義ファイルは、利用者が書く、基本的に信頼できる入力である。
- **Decision:** 上限は 1 MiB。読み取りを「上限 + 1 バイト」までに制限し、超えたら `tooLarge` で拒否する。
- **Consequences:** 良い点は、資源の浪費を防げる。悪い点は、正当な巨大な定義も拒否される(実際の定義は、数 KiB を想定)。
- **Alternatives Rejected:**
  - 上限を置かない案: 実装は単純だが、誤った入力で、メモリを使い切る恐れがある。
  - 上限を大きく(例: 64 MiB)置く案: 事故は防げるが、定義ファイルとして不自然に大きく、上限の意味が薄いため退けた。

### D4 edition 2024 と最新の安定版を使う [Q2: A]

- **Context:** 新規のプロジェクトであり、古いコンパイラへの対応の要請はない。
- **Decision:** edition 2024、最新の安定版。最小のバージョンは、その edition を使える最低のものとし、CI で固定する。
- **Consequences:** 新しい機能を使える。古いコンパイラでは、ビルドできない。
- **Alternatives Rejected:**
  - edition 2021 と、古めのコンパイラへの対応: 互換の幅は広がるが、新規のプロジェクトでは、その利点が薄いため退けた。

## 依存の方針(NFR4.5、NFR2.1、NFR1.1 に関わる)

- **バージョンの固定:** `Cargo.lock` をコミットし、依存のバージョンを固定する。更新は、意図して行う。
- **ライセンスと脆弱性の確認:** `cargo-deny`(ライセンスと禁止リスト)と `cargo-audit`(既知の脆弱性)を、CI の確認項目の候補とする。導入は、CI Pipeline のステージで決める。
- **起動への影響:** 依存の追加は、起動オーバーヘッド(NFR1)と、単一バイナリ(NFR2)への影響を確認してから行う。

## Assumptions & Open Questions

- `toml` の標準の機能で、「上限 + 1 バイト」までの制限、知らないキーの拒否、エラー位置の取得が可能かは、Code Generation の最初に確かめる。足りない部分は、補う(D1 の選択は変えない)。 [assumption]
- 入れ子の上限 32 段は、定義ファイルの実際の使い方(ジョブとその遷移の、浅い構造)に対して、十分に大きい値として置いた。実測で調整する。 [assumption]
- `cargo-deny` と `cargo-audit` を CI に入れるかは、CI Pipeline のステージで決める。 [assumption]
