# Security Design(u1-core)

上流: security-requirements(NFR4.1〜NFR4.7)、tech-stack-decisions(NFR1.1、NFR2.1、NFR3.1、NFR5.1)、functional-spec(W1 定義の読み込みと検証、W3 判断)、rules(BR1.1〜BR1.13)、contract-summary(C2、E2)。u1-core は library であり、認証・認可・暗号化・ネットワークはない。入力は、利用者が書く定義ファイル1つである。この文書は、前のステージ(NFR Requirements)のレビューで引き継いだ指摘(7点)と、このステージの1回目のレビューの指摘(4点の Major を含む)への対応も含む。コードは、短い疑似コード(15行以下)に限る。

**この設計は、functional-design と nfr-requirements の関連する記述より優先する**(下の「既存の成果物との差分」を参照)。

## 設計の要点

### 1. 定義ファイルの読み取りの流れ(位置の情報を持つ形で読み、検査は自分で行う)

次の順に行う。どの段階でも、誤りは、ここで決まる「種類」と「位置(行)」を持つ DefinitionError として返す。

1. **取り込み(Intake):** ファイルの大きさを確認し、上限(1 MiB)を超えるなら拒否する(`tooLarge`)。読み取りそのものを「上限 + 1 バイト」までに制限し、確認と読み取りのあいだにファイルが変わっても、上限を超えて読まない。通常のファイルでないもの(名前付きパイプなど)や、大きさが 0 のファイルも、読み取りの結果で扱う(読めなければ `unreadable`)。UTF-8 でない内容は、`unreadable`(理由「文字コード」)として返す。(NFR4.4)
2. **読み取り(Parse):** 内容を、位置の情報(バイトの範囲)を保ったまま、型を決めない文書の木として読み取る。TOML の文法の誤りは、この段階で `syntax` として返し、以降の段階には進まない。(NFR4.7)
3. **入れ子の深さの検査:** 読み取りのあと、木を走査して、入れ子の深さを数える。深さには、テーブル、テーブルの配列、インラインのテーブル、配列を、それぞれ1段として数える。32段を超えたら、`syntax`(理由「深すぎる入れ子」)で拒否する。(Q1: A)
4. **版の確認(VersionCheck):** 木の版のキーを確認する。版が無ければ `versionMissing`、対応しなければ `versionUnsupported` を返し、ここで終える(他の検査はしない)。(NFR4.3、BR1.7)
5. **構造の検査(Walk):** 木を、**自分で**走査して、次の検査を、すべて行い、誤りを**すべて集める**。
   - キーが、定義で許されたキーの集合に含まれるか(`unknownKey`)。(BR1.6)
   - 値の型が、期待する型か、必須の値があるか(`typeMismatch`)。期待する型は、この走査の中で、検査のたびに決まっているため、誤りに含められる。(BR1.5)
   - ジョブIDの重複・空・`@` の接頭(`duplicateJobId`、`invalidJobId`)、ジョブが0(`noJobs`)、空の名前・コマンド(`emptyField`)、同じ `on` の遷移の重複(`duplicateTransition`)。(BR1.13)
   - 遷移先の存在・エラーへの遷移・後ろ向きの遷移(`unknownTarget`、`errorTransition`、`backwardOrSelfTarget`)。(BR1.1〜BR1.3)
   - 終了コードの重複・0 の警告指定(`overlappingExitCodes`、`zeroAsWarning`)。(BR1.4)
   - パイプライン名の一致(`pipelineNameMismatch`)。(BR1.8)
6. 誤りが1つでもあれば、集めた誤りをすべて返す。なければ、検査の済んだ値から、PipelineDefinition を作って返す。(W1 の最後の手順)

### 2. この読み取りの設計の理由(自分で走査する)

- **行番号:** 木の各要素は、元のファイルでのバイトの範囲を持つ。誤りの位置は、その要素の範囲の先頭から、ファイルの先頭からの改行の数で、行番号を求める。構文の誤りも、読み取りの結果が持つ範囲から、同じ方法で行を求める。
- **誤りの分類と、すべての誤りを返すこと:** 検査を自分で行うため、誤りの種類は、どの検査で見つかったかで決まり、ライブラリのエラー文を読み取って分類する必要がない。1回の走査で、複数の誤りを集められる(W1 の「すべての誤りを返す」と一致する)。
- **ライブラリのエラー文を使わない:** 構文の誤りも含め、表示する理由は、固定の文から組み立てる。(NFR4.6)

### 3. エラーの表示の組み立て(Describe)

- 表示は、ファイル名、行、種類、理由(固定の文)から組み立てる。ライブラリのエラー文、ソースの行の抜粋、誤った値は、含めない。(NFR4.6)
- キーの名前(`unknownKey` などで必要。NFR4.2)は、入力に由来するため、表示するときに、次の処理をする: 制御文字は、エスケープして表示する。長さは、64 文字までとし、超えた分は省略の印にする。
- 型の誤りの「期待する型」は、走査の検査が持つ固定の文字列(例: 「整数のリスト」)で示す。

### 4. パニックしない

外部の入力に対する処理は、すべて、戻り値のエラーで失敗を返す。入れ子の深さの上限(32段)は、読み取りのあとの走査で数えるが、読み取り(Parse)自体の再帰による異常終了を防ぐため、次の2つを前提にする。

- 読み取りのライブラリが、入れ子に対する再帰の深さの制限を持つこと。Code Generation の最初に、これを**確かめる**(深さ 1000 の入れ子の入力で、異常終了せず `syntax` が返ること)。
- 確かめられなければ、読み取りを、十分に大きいスタックを持つ別のスレッドで行い、深さ超過で失敗を返す(代替の方式)。

(この確認は、Code Generation のテストの最初の項目とする。判定の基準は、「深さ 33 の入力は `syntax`」と「深さ 1000 の入力でも異常終了しない」の2つである)

## 追加・変更する種類(DefinitionError の `kind`)

| 種類 | 意味 | 備考 |
|------|------|------|
| `syntax`(追加) | TOML の文法の誤り、深すぎる入れ子 | 読み取りの結果が持つ範囲から行を求める |
| `tooLarge`(追加) | ファイルの大きさが上限(1 MiB)を超えた | BR1.9 の `unreadable` とは分ける |
| `unreadable`(既存) | 読めない(権限、名前付きパイプなど)、UTF-8 でない内容 | 理由で区別する |

終了コードの対応(BR5.1)は、`kind` ではなく、エラーの「分類」(定義の誤り・ステートの誤り・拒否・変換の誤り)で行う。定義の誤りの `kind` は、すべて 64 に対応する。そのため、`kind` の追加は、他の Unit の終了コードの対応に影響しない。

## 設計の判断(代替案との比較)

### D0 読み取りの方式: 位置を持つ文書の木を、自分で走査して検査する(最も影響の大きい判断)

- **Context:** 型の誤りと知らないキーを、**行番号つき**で、**すべて**集めて、実行前に返したい。ライブラリのエラー文は、使えない(NFR4.6)。
- **Decision:** 位置の情報(バイトの範囲)を保つ文書の木として読み取り、検査を自分で行う(上の1の流れ)。TOML の読み取りには、`toml` の仲間のライブラリ(位置を保つ文書の木を提供するもの)を使う。
- **Consequences:** 良い点は、行番号、誤りの分類、複数の誤りの収集を、自分で制御できる。悪い点は、許されたキーの集合と、期待する型を、検査のコードに書く必要がある(型の定義と、二重に持つことになる)。
- **Alternatives Rejected:**
  - 型付きの構造への自動変換(serde の `deny_unknown_fields`)に任せる案: 記述は短いが、最初の誤りで止まり、複数の誤りを集められない。誤りの種類は、ライブラリのエラー文を読んで分類する必要があり、行番号も、エラーが持つ範囲に限られる。要件(W1 の「すべての誤りを返す」)を満たせないため退けた。
  - 汎用の木(位置なし)を読み取ってから、型付きに変換する案: 版の確認を先にできるが、木に位置がなく、`unknownKey` と `typeMismatch` の行番号を出せないため退けた。
  - 型付きの構造に、位置を持つ値(位置つきの型)を使う案: 位置は取れるが、複数の誤りを集める難しさは残り、検査の制御も弱くなるため、D0 の方式を選んだ。

### D1 TOML の読み取りに serde と toml の仲間のライブラリを使う [Q1: A]

- **Context:** 型の誤りと知らないキーを、実行前に検知したい(NFR4)。Rust に不慣れな開発者が、誤りにくい方法を選びたい。
- **Decision:** `toml` の仲間のライブラリ(位置を保つ文書の木。D0)を使い、検査は自分で行う。Q1 の「serde と toml」の選択は、`toml` の仲間を使うこと(読み取りの実績のあるライブラリを使い、手書きしない)で満たされる。シリアライズ用の `serde` は、`convert`(u4-converter)や、ステートの読み書き(u2-runtime)で使い、この Unit の読み取りには、必須としない。
- **Consequences:** 良い点は、実績のある読み取りを使え、位置の情報も使える。悪い点は、`serde` の自動変換の手軽さは、この Unit では使わない。
- **Alternatives Rejected:**
  - TOML の読み取りを手書きする案: 依存は無いが、実装と検証の手間が大きく、誤りやすい。読み取りの誤りが、そのまま、誤った定義の実行につながるため退けた。
  - 複数形式を扱う設定用のライブラリを使う案: 形式の幅は広いが、厳密な検証、位置の報告に、余計な仕組みが入り、依存も大きくなるため退けた。

### D2 エラーの型に thiserror を使う [Q3: A]

- **Context:** DefinitionError など、種類の多いエラーに、表示の文を付ける必要がある。
- **Decision:** `thiserror` を使い、種類ごとに表示の文を型に付ける。ただし、外部のエラー文は、そのまま取り込まず、固定の文から組み立てる(上の3)。
- **Consequences:** 記述が短い。依存が1つ増える。
- **Alternatives Rejected:**
  - 標準のライブラリだけで手書きする案: 依存は増えないが、種類が多いため、記述が長く、書き間違いやすい。
  - エラーを文字列で持つ案: 簡単だが、種類で処理を分けられず、終了コードの対応や表示の出し分けに使えないため退けた。

### D3 定義ファイルの大きさに上限(1 MiB)を置く [Q4: A]

- **Context:** 誤って巨大なファイルが渡される事故を防ぎたい。定義ファイルは、利用者が書く、基本的に信頼できる入力である。
- **Decision:** 上限は 1 MiB。読み取りを「上限 + 1 バイト」までに制限し、超えたら `tooLarge` で拒否する。
- **Consequences:** 良い点は、資源の浪費を防げる。悪い点は、正当な巨大な定義も拒否される(実際の定義は、数 KiB を想定)。
- **Alternatives Rejected:**
  - 上限を置かない案: 実装は単純だが、誤った入力で、メモリを使い切る恐れがある。
  - 上限を大きく(例: 64 MiB)置く案: 事故は防げるが、定義ファイルとして不自然に大きく、上限の意味が薄いため退けた。

### D4 入れ子の深さの上限は 32 段で、読み取りのあとの走査で数える [Q1(NFR Design): A]

- **Context:** 深すぎる入れ子は、読み取りのときに、プログラムを異常終了させうる。実際の定義は、ジョブとその遷移の、浅い構造である。
- **Decision:** 32 段を上限とし、読み取りのあとの走査で数える(テーブル、テーブルの配列、インラインのテーブル、配列を、それぞれ1段)。読み取り自体の再帰による異常終了は、ライブラリの制限に頼り、Code Generation で確かめる(上の4)。
- **Consequences:** 良い点は、判定が測定でき、テストできる(深さ 33 の入力、深さ 1000 の入力)。悪い点は、ライブラリの再帰の制限に頼る部分があり、確かめる手間が要る。
- **Alternatives Rejected:**
  - 上限を置かず、ライブラリの既定に任せる案(Q1: B): 実装は単純だが、巨大な入れ子による異常終了を、こちらで防げない。
  - 読み取り前に、生の文字列を走査して深さを数える案: 文字列の中のかっこや、コメントを誤って数える恐れがあり、不正確である。
  - 読み取りを、別のスレッドで、大きなスタックで行う案: 確実だが、起動オーバーヘッド(NFR1)への影響を測る必要がある。ライブラリの制限が使えない場合の、代替の方式として残す。

### D5 edition 2024 と最新の安定版を使う [Q2: A]

- **Context:** 新規のプロジェクトであり、古いコンパイラへの対応の要請はない。
- **Decision:** edition 2024、最新の安定版。最小のバージョンは、その edition を使える最低のものとし、CI で固定する。
- **Consequences:** 新しい機能を使える。古いコンパイラでは、ビルドできない。
- **Alternatives Rejected:**
  - edition 2021 と、古めのコンパイラへの対応: 互換の幅は広がるが、新規のプロジェクトでは、その利点が薄いため退けた。
  - 特定のバージョンに固定して、更新しない案: 再現性は高いが、安全性の修正や、新しい機能を取り込めないため退けた。

## 依存の方針

- **バージョンの固定:** `Cargo.lock` をコミットし、依存のバージョンを固定する。更新は、意図して行う。
- **ライセンスと脆弱性の確認:** `cargo-deny`(ライセンスと禁止リスト)と `cargo-audit`(既知の脆弱性)は、CI の確認項目の候補として記録する。導入は、CI Pipeline のステージで決める。(Q3: A)
- **起動への影響:** 依存の追加は、起動オーバーヘッド(NFR1)と、単一バイナリ(NFR2)への影響を確認してから行う。

| ID | 基準 | 確認の方法 |

| NFR1.1 | 定義の読み取りと検証は、起動のたびに1回だけ行い、起動時に、ネットワークへのアクセスや、不要な初期化をしない。ジョブ10個程度の定義で、この Unit の処理(取り込みから結果まで)が、1回の実行で 20ms 以内(p95)に収まる(起動経路全体の 100ms の予算の一部) | u3-cli の起動経路の測定の一部として、ベンチマークで確かめる(3つの OS) |

## Assumptions & Open Questions

- 位置を保つ文書の木を提供する `toml` の仲間のライブラリの具体名とバージョン、およびその読み取りが、入れ子に対する再帰の制限を持つかは、Code Generation の最初に確かめる。足りない場合は、D4 の代替(別スレッド)で補う。 [assumption]
- 許されたキーの集合と、期待する型を、検査のコードと、型の定義で二重に持つ点は、テスト(定義の例の網羅)で、食い違いを防ぐ。 [assumption]
- NFR1.1 の 20ms(p95)は、起動経路の 100ms の予算の、この Unit への配分の仮の値であり、Code Generation で、実測して見直す。 [assumption]
- 認証・認可・暗号化は、この Unit に該当しない。 [assumption]
