# 要件: v0.10.3 の仕様書の粗の直しと数の検査

出典: 依頼の文(`project-description.json`)、要件の質問(`requirements-analysis-questions.md` の Q1〜Q7、まとめの確かめ済み)、コードの知識(`business-overview.md`、`architecture.md`、`code-structure.md`、`code-quality-assessment.md`)、引き渡し(`inception/reverse-engineering/developer-scan.md` の 1〜4)、チームの実践(`team.md`)、project.md。

## 1. 意図の分析

- 目的: v0.10.2 のレビューで残った仕様書の小さな粗(A-1)と、`team.md` の古い記述(A-2)を直し、仕様書の数が再び実装とずれないように、突き合わせるテストを足す(A-3)。最後に版を 0.10.3 にする(依頼の文)。
- 種類: 整理の intent。`conductor` の動きは変えない。テストを 1 つ(またはまとまり)足す。
- 背景: v0.10.2 の前は、仕様書が 1 版分まるごと実装とずれていた。`docs/spec/` を読むテストも CI も無い(developer-scan の 1)。
- 成功の基準: A-1 の 3 点と A-2 の古い記述が直り、数の検査のテストが今の仕様書で通り、数をずらすと落ちる。既存のテストと CI がすべて通る。

## 2. 機能の要件

### FR1. 仕様書の小さな粗(A-1)

- **FR1.1** `docs/spec/language-agnostic/11-quality-and-build.md` の根拠の列で、テスト名の `_` のままの 14 個(AC-097a と、4.7 の AC-206〜234 の 13 個)を、ほかの 588 個と同じ空白の書き方に直す(Q1 A)。合否: 根拠の列に `_` を含むテスト名が残らない(識別子として `_` を含むもの、たとえば型名や環境変数名は対象外)。
- **FR1.2** `crates/core/tests/env_types.rs` のテスト名の「33 種」を「34 種」に直す(テスト名だけ。中身は変えない)。
- **FR1.3** AC-430 の前提を、実際のテスト(`crates/cli/tests/unix_demo.rs:243-244`)に合わせて `LC_ALL=C` にし、「この前提では、デモが `LC_ALL` を消したかは表示からは見分けられない」と注記する(Q2 A)。rust 版 11 章に同じ記述があれば同じに直す。
- **FR1.4** language-agnostic の 11 章の 2.1 の性能の表で、AC-573 と「参照実装の基準」の 6 行は「目安」のまま残し、各行に「参照実装は強制として検査する」と書き添える(Q3 B)。

### FR2. team.md の古い記述(A-2)

- **FR2.1** 11 行目の「867 コミットすべてが非マージ」と、14 行目の「タグは v0.1.0 から v0.9.9 まで」を、数と範囲を書かない、古くならない書き方にする(例:「履歴は線形で、マージコミットは無い(作者は 1 人)」「タグは v0.1.0 から付いている」)(Q6 A)。
- **FR2.2** v0.10.0 の intent だけの言い方(15 行目の後ろの文、24・25・39・40・55・68 行目)を、どの版にも当てはまる言い方に直して残す(例:「機能を足す intent は、機能を 1 つずつ作り、各機能の最後に README とデモを直し、作り終えてから版を上げる」「署名・公証、Intel macOS の動作確認、audit と startup-bench の強制は見送る(2026-11-28 にも署名の見送りを確かめた)」)(Q7 A)。決まりの中身は変えない。
- **FR2.3** 書き換えはコード生成の計画の承認(人の確かめ)を経て行う。計画に、行ごとの今の文と書き換えた後の文を載せる。上の行の外は変えない。

### FR3. 仕様書の数の検査(A-3)

- **FR3.1** 仕様書(`docs/spec/rust/`、`docs/spec/language-agnostic/`)の数を、実装と突き合わせるテストを足す。本番のコードは変えず、テストが仕様書とソースのファイルを文字列として読んで数を取り出す(`crates/runtime/tests/nfr_source.rs` と同じ前例)(Q4 A)。
- **FR3.2** 対象の数(Q5 A): 定義の誤りの種類(34)、`.env` の誤りの種類(14)、`[pipeline]` のキー(9)、`[[job]]` のキー(9)、ステートの最上位・ジョブ・試行のキー(10・5・2)、試行の誤りの理由(3)、`watch` の列(4)、`--interval` の範囲と既定(1〜3600、2 秒)、`--format` の値(3)、デモの場面(0〜15)。実装の側の数は、ソースから取り出す(developer-scan の 2.1 の場所)。仕様書の側は、数の語(「34 種」など)と表の行の数のどちらか(または両方)で取り出す。
- **FR3.3** 版の注記つきの履歴の数(R12:105・L12:129 の 33 種、R08:425 の 3 列、R04:107・L04:125 の 6 コマンド、R11:533・L11:1226 の 14 まで、R12:60 の 22 種など)は、誤りとして拾わない。
- **FR3.4** 合否: (1) 今の仕様書と実装でテストが通る。(2) 実装か仕様書の数を 1 つずらすと、どの数がどのファイルでずれたかが分かる失敗の文でテストが落ちる(コード生成の中で、一時的にずらして確かめる)。(3) 3 つの OS の CI で通る。

### FR4. 版

- **FR4.1** すべてを片づけてから、版を 0.10.3 にする(v0.10.2 の 10ce84e と同じ 22 ファイルの範囲)。件名は「版を 0.10.3 にする」の 1 コミット。

## 3. 非機能の要件

- **NFR1 動きを変えない**: `crates/` の本番のコード(`src/`)は、版の外を変えない。テスト(`tests/`、`src/tests/`)の追加と、テスト名の直し(FR1.2)だけ。
- **NFR2 テストの都合で本番を曲げない**: 数を取り出すために、本番に公開の口・`pub`・関数を足さない(project.md の NEVER)。
- **NFR3 品質**: `cargo fmt`、`cargo clippy -D warnings`、`cargo test --workspace` が通る。行カバレッジ 80% 以上。CI(3 つの OS、MSRV、coverage、docs-check)が通る。
- **NFR4 依存**: 新しい依存を足さない(テストでも)。
- **NFR5 OS に依らない**: 数の検査のテストは、改行(CRLF)や区切り文字の違いで Windows でも通る形にする。

## 4. 制約

- 変更は小さな単位でコミットし、直接 `main` に入れる(team.md)。
- `team.md` の書き換えは FR2 の行だけ。

## 5. 前提

- 仕様書の数の書き方は、v0.10.2 で直した今の形(developer-scan の 2.1)を出発点にする。検査は、今の書き方を壊さない範囲で、決まった語や表を読む。理由: 仕様書の書き方を検査に合わせて大きく変えるのは、この整理の範囲を越えるため。
- テストを置くクレートは設計で決める(`docs.rs` のある cli、または `nfr_source.rs` のある runtime の近く)。

## 6. 範囲の外

- 凍結している 5 つの言語版の仕様書。
- 仕様書の書き方そのものを、検査のために作り直すこと。
- 数の検査を、ここに挙げた数の外(使い方の誤り 8 種、ステートの誤り 6 種など)へ広げること(後の intent の候補)。

## 7. 未決の事項(設計で決める)

- テストの置き場所と名前、仕様書とソースから数を取り出す方法(決まった語の正規表現か、表の行の数か)と、履歴の数の除き方。
- `team.md` の各行の書き換えた後の文。
