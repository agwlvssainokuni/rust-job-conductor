# 要件: v0.10.0 の小さな機能のまとまり

出典: 意図の表明(`intent-statement.md`)、スコープ文書(`scope-document.md`)、チームの実践(`team-practices.md`)、コードの知識(`business-overview.md`、`architecture.md`、`code-structure.md`、`api-documentation.md`)、要件の質問(`requirements-analysis-questions.md` の Q1〜Q18)。

## 1. 意図の分析

- 目的: 定義の書き方の不便(同じ設定の繰り返し、環境ごとの `.env` の有無、要らない環境変数)を減らし、実行の様子と結果を後から確かめやすくする(intent-statement.md の Problem Statement)。
- 利用者: 開発者ご自身と、社内や身近な運用の担当者(intent-statement.md の Target Customer)。
- 種類: 既存の単体の CLI(`conductor`)への機能追加。core・runtime・cli の 3 クレートにまたがる(code-structure.md)。
- 成功の基準: 7 つの機能(B1〜B7)をすべて v0.10.0 として公開する。今ある定義ファイルは書き換えずに同じに動く。チームの基準(test-after、行カバレッジ 80% 以上、3 つの OS の CI)を満たす(intent-statement.md の Success Metrics、scope-document.md の 4)。

## 2. 機能の要件

### FR1. パイプライン共通のリトライの既定(B1)

- **FR1.1** `[pipeline.retry]` を書ける。項目と検査は `[job.retry]` と同じ(`exit_codes`、`max`、`interval`、`multiplier`、`max_interval`)(scope-document.md の 2)。
  - 合否: 正しい `[pipeline.retry]` を持つ定義が検査を通る。`[job.retry]` で誤りになる値は、`[pipeline.retry]` でも同じ誤り(64)になる。
- **FR1.2** `[pipeline.retry]` は、`retry` を持たないすべてのジョブに既定として当てはまる(Q1)。
  - 合否: `retry` を書いていないジョブが、既定の `exit_codes` で終わったとき、既定の `max`・`interval` に従ってリトライされる。
- **FR1.3** ジョブに `retry` があれば、ジョブのものを丸ごと使い、既定と項目ごとには混ぜない(Q1)。
  - 合否: 既定に `multiplier` があり、ジョブの `retry` に無いとき、そのジョブの待ち時間は伸びない。
- **FR1.4** ジョブ側で既定を打ち消す書き方を用意する。打ち消したジョブはリトライしない。名前と形は設計で決める(Q2)。
  - 合否: 打ち消したジョブは、既定の `exit_codes` で終わってもリトライされない。
- **FR1.5** 既定の `exit_codes` が、既定を当てはめるジョブの成功・警告の終了コードと重なると、定義の誤り(64)にする(Q3)。打ち消したジョブと、自分の `retry` を持つジョブは、この検査の対象にしない。
  - 合否: 重なる定義は 64 で止まり、どのジョブも動かない。誤りの表示に入力の値を含めない(project.md の Forbidden)。
- **FR1.6** `[pipeline.retry]` を書かない定義の動きは変えない(intent-statement.md の Success Metrics)。

### FR2. 無くてもよい `.env`(B2)

- **FR2.1** `env_file` の項目に、今の文字列に加えて表の形 `{ path = "<パス>", required = <真偽> }` を書ける。`[pipeline]` と `[job]` の両方で書ける。文字列と表は 1 つの配列に混ぜて書ける(Q4)。
  - 合否: 文字列だけの今の定義は、同じに動く。表の `path` が無い・空・型が違う、知らないキーがある、`required` が真偽でないときは定義の誤り(64)。
- **FR2.2** `required = false` のファイルが無ければ、読まずに進む。何も表示しない(Q5)。
  - 合否: ファイルが無くても終了コードは変わらず、標準出力・標準エラーに何も足されない。そのファイルの変数はジョブに渡らない。
- **FR2.3** `required = false` でも、ファイルがあって読めない、大きすぎる、UTF-8 でない、書式が誤っているときは、今までどおり定義の誤り(64)にする(Q5 の質問文)。
- **FR2.4** `required` を省いた表と、文字列は、必ず要るファイル(今と同じ)として扱う。
- **FR2.5** `--dry-run` と `graph` は、無くてもよいファイルが無くても誤りにしない(FR2.2 と同じ扱い)。

### FR3. `unset_env`(B3)

- **FR3.1** `[pipeline]` と `[job]` に、`unset_env` を環境変数の名前の配列で書ける(Q6)。
  - 合否: 名前の規則(`env` と同じ)に反する名前、空の名前、予約名 `CONDUCTOR_*` は定義の誤り(64)。
- **FR3.2** `unset_env` に書いた名前の変数は、親から引き継いだ環境から消してジョブに渡す。名前は完全一致で比べる(Q6)。パイプラインの `unset_env` とジョブの `unset_env` は合わせて使う。
  - 合否: 親の環境に `FOO` があり、`unset_env = ["FOO"]` のとき、ジョブの環境に `FOO` が無い。
- **FR3.3** `unset_env` の名前が、同じジョブに当てはまる `env` か `env_file` の変数と同じなら、定義の誤り(64)にする(Q7)。`env_file` の中身との重なりは、`.env` を読んだときに見つけ、`.env` の誤りと同じく 64 で止める。
  - 合否: どちらの重なりも 64 で止まり、ジョブは動かない。表示に変数の値を含めない。
- **FR3.4** 自動の変数(`CONDUCTOR_*`)は `unset_env` の対象にならない(予約名は書けないため)。
- **FR3.5** `unset_env` を書かない定義の動きは変えない。

### FR4. `graph --format dot`(B4)

- **FR4.1** `graph --format` に `dot` を足す。出力は Graphviz の DOT 言語(scope-document.md の 2)。
  - 合否: 出力が DOT の文法で書かれ、ジョブの数と流れの辺の数が text・mermaid と一致する。
- **FR4.2** `-v` と `--state`(`--run-id` を含む)に、text・mermaid と同じく対応する(Q8)。
  - 合否: `--state` のとき、各ジョブの状態が DOT の出力で見分けられる。`-v` のとき、text・mermaid の `-v` と同じ情報が出る。
- **FR4.3** ジョブの名前などの値は、DOT の文字列として正しく escape する。
- **FR4.4** `--format` の値が `text`・`mermaid`・`dot` 以外なら、今と同じ使い方の誤り。

### FR5. ジョブの出力をファイルにも残す(B5)

- **FR5.1** `[pipeline]` に `log_dir` を書ける。相対パスは定義ファイルのディレクトリが基準(`env_file` と同じ)(scope-document.md の 2)。
- **FR5.2** `log_dir` があるとき、ジョブの標準出力と標準エラーを、今までどおり端末にも出したうえで、ジョブの試行ごとに 1 つのファイルにまとめて残す(Q9)。
  - 合否: ファイルに、その試行の標準出力と標準エラーの両方の内容がある。端末にも同じ内容が出る。
- **FR5.3** ファイルは実行ごと・試行ごとに別にし、前のファイルを上書きも追記もしない。名前にジョブ、試行の番号、時刻を含める(Q10)。形は設計で決める。
  - 合否: 同じジョブを 2 回動かす(再実行やリトライを含む)と、ファイルが 2 つになる。
- **FR5.4** `log_dir` のディレクトリが無ければ作る(Q11)。作れない・書けないときの扱い(終了コード、ジョブを動かすかどうか)は設計で決める。
- **FR5.5** `log_dir` を書かない定義では、今と同じく出力を親から引き継ぐだけにする。

### FR6. 時刻と所要時間の記録(B6)

- **FR6.1** ステートの各ジョブに、試行ごとの開始と終了の時刻を書く(Q13)。
  - 合否: 2 回リトライして成功したジョブのステートに、3 つの試行の開始と終了がある。
- **FR6.2** 時刻は UTC の RFC 3339(例: `2026-11-25T09:12:48Z`)で書く(Q12、Q17)。
- **FR6.3** ステートに書いてよいのは開始と終了の時刻だけを足す。コマンド・環境変数・ジョブの出力は書かない(team-practices.md の Code Style、project.md の Forbidden)。
- **FR6.4** `format_version` は 1 のままにする。動いたジョブに試行の記録が 1 つも無いステートは、壊れたステートの誤り(65)にする(Q14、スコープ Q5)。
  - 合否: v0.9.9 で書いたステート(動いたジョブを含む)を読むと 65 で止まる。
- **FR6.7** FR6.4 の誤りは、ステートを読むすべてのコマンドに当てはまる。`run`・`pipeline`(`--dry-run` を含む)、`watch`、`graph --state` の 4 つ(要件のレビューの指摘 R-01)。
  - 合否: 4 つのコマンドのそれぞれで、v0.9.9 で書いたステートを読むと 65 で止まる。`reset` は、そのステートを消せる(今と同じく中身を読まずに消す)。
- **FR6.8** FR6.4 の誤りのとき、標準エラーに「ステートが古い形式か壊れていること」と「`conductor reset` でステートを消せば作り直せること」を知らせる。ステートの値やパスの中身は表示しない(要件のレビューの指摘 R-01、project.md の Forbidden)。
  - 合否: 65 のときの標準エラーに、`reset` で直せる旨の 1 文がある。ステートの中の値が含まれない。
- **FR6.9** 終了の時刻が無い試行(動いている最中のもの、または中断で止まったもの)は、正しいステートとして許す。終了の時刻が無くてよいのは、各ジョブの最後の試行だけ(要件のレビューの指摘 R-02)。
  - 合否: 中断で止まったジョブを含むステートは、65 にならずに読める。最後でない試行に終了の時刻が無ければ 65。
- **FR6.5** `watch` の表に、各ジョブの所要時間を出す。所要時間は、最初の試行の開始から最後の試行の終了まで(scope-document.md の 2)。動いていない・飛ばしたジョブは空にする。最後の試行に終了の時刻が無いとき、パイプラインが動いている最中なら開始からの経過時間を出し、中断で止まっているなら空にする(要件のレビューの指摘 R-02)。動いている最中かどうかの見分け方は設計で決める。
- **FR6.6** 時刻の書式と読み取りは、新しい依存を使わずに自前で書く(team-practices.md の Code Style)。

### FR7. `watch` の継続表示(B7)

- **FR7.1** オプションを付けたときだけ、`watch` が一定の間隔で表示し直す。オプションが無ければ今と同じく 1 回表示して終わる(Q15)。オプションの名前は設計で決める。
- **FR7.2** 間隔の既定は 2 秒。オプションで変えられる。範囲は設計で決める(Q15)。
- **FR7.3** Ctrl-C(中断のシグナル)で終わる。パイプラインが終わった(完了、または中断で止まった)ときも、最後の表示をしてから自動で終わる(Q15)。終了コードは設計で決める。
- **FR7.4** UNIX 系の端末なら、画面を消して描き直す。Windows、パイプ、ファイルへの出力では、追記していく(Q16、Q18)。
  - 合否: 端末でない出力に、制御の文字(ANSI)が含まれない。
- **FR7.5** ステートがまだ無い、または読めないときの扱い(待つか、誤りで終わるか)は設計で決める。

### FR8. 文書と版

- **FR8.1** 各機能の最後に、README とデモを更新する(scope-definition-questions.md Q6、team-practices.md の Walking Skeleton)。使い方の表は `args.rs`、`report/messages.rs`、README の 3 か所を揃える。
- **FR8.2** 7 つを作り終えてから、`crates/cli/Cargo.toml` の版を 0.10.0 にする(intent-statement.md の Success Metrics)。

## 3. 非機能の要件

- **NFR1 後方互換**: `[pipeline.retry]`、表の `env_file`、`unset_env`、`log_dir` を書かない今の定義ファイルは、v0.9.9 と同じに動く。既存のテストはすべて通る(intent-statement.md の Success Metrics)。
- **NFR2 テスト**: test-after で、各機能に単体テストと、実バイナリを動かす統合テストを書く。行カバレッジ 80% 以上を保つ(team-practices.md の Testing Posture、project.md の Mandated)。
- **NFR3 3 つの OS**: ubuntu・macos・windows の CI と、最小の Rust(1.100)の CI が通る(project.md の Mandated)。
- **NFR4 依存**: 新しい外部ライブラリを加えない(project.md の Forbidden)。
- **NFR5 `unsafe` と `cfg`**: `unsafe` は runtime の `platform/unix.rs` の外に書かない。`cfg(unix)`/`cfg(windows)` は `platform` の外に置かない(project.md の Forbidden、Q17・Q18 の判断)。
- **NFR6 秘密の保護**: エラーの表示に入力の値を含めない。ステートに環境変数を書かない。`log_dir` のファイルには、ジョブ自身の出力だけを残し、`conductor` は環境変数の値を書き足さない(project.md の Forbidden)。
- **NFR7 品質の検査**: `cargo fmt` と `cargo clippy -D warnings` が通る(project.md の Mandated)。

## 4. 制約

- 変更は小さな単位でコミットし、直接 `main` に入れる(team-practices.md の Way of Working)。
- 機能は B1 → B2 → B3 → B4 → B5 → B6 → B7 の順に 1 つずつ作る。B7 は B6 の後(scope-document.md の 5)。
- 期限は無い(scope-document.md の 7)。

## 5. 前提

- `watch` の所要時間の表示の形(例: `1m23s`)は、既存の表の形に合わせて設計で決める。理由: 利用者の世界の事実に依らず、表示の統一で決まるため。
- `log_dir` は `[pipeline]` にだけ書く。理由: 意図とスコープの記述が `[pipeline]` の設定として挙げており、ジョブごとの指定の要望は無いため。
- 継続表示の中で、ステートの書き込みの途中を読んでも誤りにしない(ステートの書き込みは原子的なため。architecture.md)。

## 6. 範囲の外

- ジョブのタイムアウト、エラーのときの遷移、排他制御、並列実行、値の展開(`${X}`)、新しい依存の追加(scope-document.md の 3)。
- 時刻を持たない v0.9.9 までのステートの読み込み(scope-document.md の 3、Q14)。
- `unset_env` の接頭辞のパターン(Q6)。
- その場所の時刻と時差での記録(Q17)。
- Windows の端末での描き直し(Q18)。

## 7. 未決の事項(設計で決める)

要件のレビューの指摘 R-03・R-04 は、ここに挙げた項目と合わせて設計で扱い、決めたものから合否の基準に落とす。

- `log_dir` のファイルの権限、同じ時刻の名前の衝突の避け方、ログの整理を範囲に入れるかどうか(R-03)。
- DOT で状態をどの属性で見分けるか(R-04)。
- ステートが「実行中」のまま残ったときの継続表示の扱い。終わらないときは Ctrl-C で抜けられる(FR7.3)(R-04)。
- `watch` で、パイプラインが動いている最中かどうかの見分け方(FR6.5)。

- 打ち消しの書き方の名前と形(FR1.4)。
- ログのファイルの名前の形と、作れない・書けないときの扱い(FR5.3、FR5.4)。
- 継続表示のオプションの名前、間隔の範囲、終了コード、ステートが無いときの扱い(FR7.1〜FR7.5)。
- DOT での状態と `-v` の表し方(FR4.2)。
