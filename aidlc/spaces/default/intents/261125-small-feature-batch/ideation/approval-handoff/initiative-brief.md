# 取り組みの概要: v0.10.0 の小さな機能のまとまり

出典: 意図の表明(`intent-statement.md`)、関係者の地図(`stakeholder-map.md`)、スコープ文書(`scope-document.md`)、意図のバックログ(`intent-backlog.md`)、承認の質問(`approval-handoff-questions.md`)。

## 1. 意図と問題

- 機能の候補 4〜10 の 7 つを v0.10.0 として出す(intent-statement.md の Problem Statement)。
- 狙いは 2 つ。定義の書き方の不便(同じ設定の繰り返し、環境ごとの `.env` の有無、要らない環境変数の除去)を減らすこと、実行の様子と結果を後から確かめやすくすること(intent-statement.md の Problem Statement)。
- 使う人は、開発者ご自身と、社内や身近な運用の担当者(intent-statement.md の Target Customer)。
- 成功の基準: v0.10.0 として公開する。今ある定義ファイルが書き換えずにそのまま同じに動く。チームの基準(test-after、行カバレッジ 80% 以上、3 つの OS の CI)を満たす(intent-statement.md の Success Metrics)。

## 2. 市場の裏づけ

該当なし。内部で使うツールで、外部の市場での位置づけは無いため、市場調査は省いた。新しい依存を加えない決まり(project.md の Forbidden)により、作るか買うかも決まっている。

## 3. 実現可能性とリスク

実現可能性の調査は省いた。既存の単体の CLI への小さな機能追加で、外部の連携先も規制も無いため。

| リスク | 扱い | 出典 |
|--------|------|------|
| 時刻を持たない v0.9.9 までのステートファイルは、v0.10.0 で読めなくなる | 受け入れる。知らせ方は要件の段階で決める | scope-document.md の 6、承認 Q2 |
| 7 つとも必須で、1 つが手間取ると公開全体が遅れる | 受け入れる。期限は無い | intent-backlog.md、scope-document.md の 7、承認 Q2 |
| 各機能の合否の基準と境界がまだ決まっていない | 受け入れる。要件の段階で決める | scope-document.md の Assumptions & Open Questions、承認 Q2 |

## 4. 範囲の境界

- 範囲の内側: 4 `[pipeline.retry]` の共通の既定、5 `graph --format dot`、6 無くてもよい `.env`、7 `unset_env`、8 `log_dir`、9 時刻と所要時間、10 `watch` の継続表示。機能ごとの README とデモの更新、最後に版を 0.10.0 にすること(scope-document.md の 2)。
- 範囲の外側: タイムアウト、エラーのときの遷移、排他制御、並列実行、値の展開(`${X}`)、新しい依存の追加、時刻を持たない古いステートの読み込み(scope-document.md の 3)。

## 5. 見た目の案

該当なし。コマンドラインツールで画面が無いため、ラフな画面案は省いた。出力の形は後の設計の段階で決める。

## 6. チームの計画

- 決める人とレビューする人は開発者ご自身 1 人。決まった報告は無い(stakeholder-map.md)。
- 追加の予算や人員は要らない。開発者ご自身が AI の支援で進める(承認 Q3)。
- 進める順序: B1 リトライの既定 → B2 無くてもよい `.env` → B3 `unset_env` → B4 `graph --format dot` → B5 `log_dir` → B6 時刻と所要時間 → B7 `watch` の継続表示(intent-backlog.md)。

## 7. 進めるかどうかの判断

**Go**。開発者ご自身が意図と範囲に同意し(承認 Q1)、リスクを理解したうえで進める(承認 Q2、Q4)。

## 8. 引き継ぎで残る事項

- 各機能の合否の基準と境界(リトライの既定とジョブ側の設定の優先関係、`watch` の継続表示の終わり方、`.env` が無いときの扱いなど)を、要件の段階で決める。
- 時刻を持たない古いステートファイルを読んだときの知らせ方(エラーの文言、終了コード)を、要件の段階で決める。
