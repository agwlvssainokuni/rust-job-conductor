# 機能の設計の質問: u5-log-dir(ジョブの出力をファイルにも残す)

出典: ユニットの定義(`unit-of-work.md` の U5)、要件(`requirements.md` の FR5.1〜FR5.5、FR6.6、7 章の未決の事項、要件のレビューの指摘 R-03)、契約(`contract-summary.md` の C2、C6 と Open questions)、設計の決定(ADR-002、ADR-005)、今のコード(`crates/runtime/src/runner.rs`、`crates/cli/src/deps.rs`)。

すでに決まっていること(質問しない): `[pipeline] log_dir` は相対なら定義ファイルのディレクトリが基準(FR5.1)。`log_dir` があるときは出力を端末にも出しつつ、試行ごとに 1 つのファイルに標準出力と標準エラーをまとめて残す(FR5.2)。名前は `<log_dir>/<ジョブの ID>.<開始の時刻>.<試行の番号>.log`、時刻は `20261125T091248Z` の形で、ステートの `started_at` と同じ値(C2、C6)。前のファイルを上書きも追記もしない(FR5.3)。ディレクトリが無ければ作る(FR5.4)。`conductor` はジョブの出力のほかに何も書き足さない(NFR6)。`log_dir` を書かなければ今と同じ(FR5.5)。時刻の整形(CoreTime)と現在の時刻(RuntimeClock)はこのユニットで作る(Q3)。

## Q1. [利用者] ログのディレクトリやファイルを作れない・書けないとき

ディレクトリを作る権限が無い、ディスクがいっぱい、などの場合です(FR5.4)。今の終了コードで「ジョブを起動できなかった」は 127 です。

A. ジョブを起動する前にファイルを作れなければ、そのジョブを起動せず、起動できなかったとして 127 で止める(理由を標準エラーに 1 行)。起動した後の書き込みの失敗は、警告を 1 回出してファイルへの書き込みだけをやめ、ジョブは端末への出力を続けたまま最後まで動かす
B. 作れなくても書けなくても、警告を出して、ログなしでジョブを動かす(終了コードは変えない)
C. 起動前でも実行中でも、作れない・書けないときはジョブを止めてエラーにする
X. Other (please specify)

[Answer]: A

## Q2. [利用者] 同じ名前のファイルがすでにあるとき

名前は秒までの時刻と試行の番号を含むので、ふつうは重なりません。重なるのは、別の run ID で同じジョブを同じ秒に動かしたときなどです(C6)。

A. 名前の末尾に番号を足して、新しいファイルを作る(例 `build.20261125T091248Z.1-2.log`)。今のファイルには触れない
B. 誤りにして、そのジョブを起動しない(Q1 の起動前の失敗と同じ扱い)
X. Other (please specify)

[Answer]: A

## Q3. [開発者] ジョブの ID がファイル名に使えない文字を含むとき

今のジョブの ID は「空でなく `@` で始まらない文字列」で、`/`、`\`、`:`、`..`、空白、制御文字なども書けます(C6 の Open question)。

A. ファイル名に使えない・危ない文字(`/` `\` `:` `*` `?` `"` `<` `>` `|`、制御文字、先頭の `.`)を `_` に置き換えて名前にする。置き換えで重なれば Q2 の扱い
B. `log_dir` を書いた定義で、そういう ID のジョブがあれば定義の誤り(64)にする
C. ジョブの ID を名前に使わず、記述順の番号にする(例 `job-03.20261125T091248Z.1.log`)
X. Other (please specify)

[Answer]: A

## Q4. [利用者] ログのファイルの権限

ジョブの出力には、秘密(トークンなど)が混じることがあります。

A. UNIX 系では本人だけが読み書きできる権限(0600)で作る。Windows は既定のまま
B. OS の既定(umask に従う。ふつうは 0644)
X. Other (please specify)

[Answer]: A

要件のレビューで「ログの整理を範囲に入れるか」が未決です(R-03)。ログは実行のたびに増えます。

A. 範囲に入れない。`conductor` は消さず、利用者が消す(README に書く)
B. 範囲に入れる。保存する数か日数の上限を設定で書けるようにする
