# 性能の設計: u1-pipeline-retry

出典: 性能の要件(`performance-requirements.md` の NFR1.3)、技術の選択(`tech-stack-decisions.md`)、機能の仕様(`functional-spec.md` の 2)、契約(`contract-summary.md` の C3)。

## 設計

- 既定の読み取りは、パイプラインを読むときに 1 度だけ行う。
- 既定との重なりの検査は、今のジョブごとの関係の検査(`cross_check`)の中で、ジョブ 1 つにつき 1 回行う。既定の `exit_codes` は昇順で重複が無く、最大 255 個。比べる相手(成功・警告の終了コード)は今の `[job.retry]` の検査と同じ並びなので、手間はジョブの数に比例する。
- 既定の `RetryPolicy` は、組み立てのときに、既定を当てはめるジョブの数だけ複製する。複製は小さく(終了コードの並びと数個の整数)、組み立ては 1 度だけ。リトライの判断の側では、今と同じく各ジョブの値を読むだけで、既定を探す手間は無い(ADR-003)。

## 確かめ方

- 起動の測定(`startup-bench`、`nfr_perf.rs`)は警告のみで強制されないため、強制される確認として、`crates/core/tests/definition_perf.rs` に時間の上限つきのテストを 1 つ足す。既定を持ち、既定を当てはめるジョブが多数(例 1 万)ある定義の読み込みが、同じ数のジョブで既定を持たない定義と同じ程度の上限(今のテストの上限の決め方に合わせる)に収まることを確かめる。上限の値は、今のテストと同じく、実測に余裕を持たせて Code Generation で決める。
