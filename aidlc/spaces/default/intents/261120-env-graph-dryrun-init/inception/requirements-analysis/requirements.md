# 要件: v0.9.0 の機能拡張

出典: 意図の記述(`ideation/intent-capture/intent-statement.md`)、スコープ文書(`ideation/scope-definition/scope-document.md`)、コード知識ベース(`aidlc/spaces/default/codekb/rust-job-conductor/` の `business-overview.md`、`architecture.md`、`code-structure.md`)、チームの実践(`inception/practices-discovery/team-practices.md`)、要件分析の質問(`requirements-analysis-questions.md`。以下 Q1〜Q8)。

## 1. 意図の分析

- 目的: ジョブに値(環境変数)を渡す手段が定義の中にない、という運用の手間を減らす(intent-statement.md の Problem Statement)。あわせて、実行前の確認、定義の作成、フローの見える化の手段を足す(スコープ文書の「範囲の内側」)。
- 種類: 既存のコマンドラインツール(`conductor` v0.8.0。コアの crate が定義と判断、runtime が実行と状態、cli が引数と表示)への、機能の追加(code-structure.md、architecture.md)。
- 利用者: 自分たちのチーム(内部の開発者と運用担当)(intent-statement.md の Target Customer)。
- 成功の基準: 4 つの機能が、この文書の要件どおりに動き、3 つの OS の CI で成功して、リリースできる(intent-statement.md の Success Metrics)。
- 優先順位(スコープ文書の優先順位): 必須は、環境変数の注入と `.env`、`graph`。後回しにしてよいのは、`--dry-run`、`init`。

## 2. 機能要件

### FR1 環境変数の注入と `.env`

- FR1.1 定義に、`[pipeline.env]`(全ジョブ共通)と `[job.env]`(そのジョブだけ)を書ける。値は文字列だけである。文字列でない値は、型の誤り(`typeMismatch`)として拒否する。値の中の `${X}` などは展開せず、そのまま渡す。(Q1)
- FR1.2 `env` の名前は、`run_id_env` と同じ規則とする: 1 文字以上、先頭は ASCII の英字か `_`、2 文字目以降は ASCII の英数字か `_`。規則に合わない名前は、拒否する。(Q1)
- FR1.3 ジョブの環境変数の優先順位は、後ろが勝つ順で、「引き継いだ環境 < `[pipeline].env_file` < `[pipeline.env]` < `[job].env_file` < `[job.env]`」とする。(Q1)
- FR1.4 `env_file` は、`[pipeline]` と `[job]` に書ける。値は、文字列、または文字列の配列とする。配列は書いた順に読み、後ろのファイルが勝つ。(Q1)
- FR1.5 `env_file` の相対パスは、定義ファイルのあるディレクトリを基準にする。(Q1)
- FR1.6 `.env` ファイルは、自前の厳格な書式で読む。受け付ける書き方は、次のとおり。(Q1)
  - 空行と、`#` で始まる行(コメント)。
  - `KEY=VALUE`。先頭の `export ` は許す。`KEY` は FR1.2 の名前の規則に従う。
  - 値は、引用符なし(行末まで。前後の空白は除く。空白に続く `#` から先はコメント)、単一引用符(そのまま。エスケープなし)、二重引用符(エスケープは `\n`、`\r`、`\t`、`\"`、`\\` だけ。ほかの `\` は誤り)のいずれか。
  - 変数の展開、複数行の値は、受け付けない(閉じていない引用符は誤り)。`KEY=` は空文字列。
  - 誤りは、行番号つきで報告する。
- FR1.7 同じ `.env` ファイルの中で、同じキーが 2 回以上出たときは、後ろが勝つ。`validate` は、警告のメッセージを出す(誤りにはしない)。複数のファイルをまたぐ上書きは、警告しない。(Q1)
- FR1.8 `.env` は、呼び出しごとに、最初のジョブを起動する前に、すべて読む。ファイルが無い、読めない、書式の誤り、のどれかのときは、ジョブを 1 つも実行せずに止まる(終了コードは非 0。具体の値は、機能の設計で決める)。再開のときも、再び読む。(Q1)
- FR1.9 `.env` の大きさの上限は 1 MiB、項目の数の上限は 10,000 とする。NUL を含む値は、誤りとする。(Q7)
- FR1.10 ジョブに、`conductor` が自動で渡す変数は、`CONDUCTOR_PIPELINE`、`CONDUCTOR_JOB_ID`、`CONDUCTOR_RUN_ID`、`CONDUCTOR_ATTEMPT` の 4 つとする。(Q3)
  - `CONDUCTOR_ATTEMPT` は 1 から始まり、リトライのたびに 1 増える。
  - run ID が無いときは、`CONDUCTOR_RUN_ID` を渡さない。
- FR1.11 `CONDUCTOR_` で始まる名前を、利用者が `env` や `.env` に書いたときは、予約名として拒否する。(Q1)
- FR1.12 環境変数の値は、`-v`、`--dry-run`、`graph`、ステート、エラーの表示に出さない。出してよいのは、名前だけである。(Q1)
- FR1.13 `format_version` は 1 のままとする。新しいキー(`env`、`env_file`)を足すだけで、既存のキーの意味は変えない。旧版の `conductor` は、新しいキーを「未知のキー」として拒否する。(Q2)

### FR2 `conductor graph`

- FR2.1 `conductor graph` は、定義を読んで、フローの図を標準出力に出す。ジョブを実行せず、ステートを読み書きしない(`--state` を除く)。(Q1)
- FR2.2 既定の出力(text)は、`git log --graph` 風にする。(Q1)
  - ジョブは `*`、終点(`@end`)は `o` で表す。上から下が、実行の順(定義の記述順)。
  - 遷移で飛び越すジョブは、`|\` と `|/` による分岐と合流で表す。
  - 成功と警告の行き先が同じなら、1 つの辺にまとめて表す。
- FR2.3 `-v` を付けると、ジョブごとに、コマンド、リトライの設定、遷移による飛び越しの注記を出す。(Q1)
- FR2.4 辺は、実行のときに次のジョブを決める判断と、同じ関数から作る。実行の動きと、図の動きが食い違わないようにする。(Q1)
- FR2.5 `--format mermaid` を付けると、Mermaid の `flowchart` を出す。(Q1)
- FR2.6 定義が検証で誤りになるときは、`validate` と同じ誤り(終了コードも同じ)を出し、図は出さない。(Q5)
- FR2.7 `--state`(と `--run-id`)を付けると、ステートを読んで、ジョブの状態を図に重ねる: 成功 `[OK]`、スキップ `[--]`、エラー `[NG]`、未実行 `[  ]`。エラーで止まっているときは、再開位置を示す。(Q1)

### FR3 `--dry-run`

- FR3.1 `pipeline` と `run` で、`--dry-run` を使える。ジョブを実行せず、ステートを作成も更新も削除もしない。計画を出せたときの終了コードは 0。(Q1、Q4)
- FR3.2 `--dry-run` は、ステートを読んで、再開位置と、ジョブごとの扱い(実行する、スキップする)を示す。あわせて、分割後のコマンド、渡される環境変数の名前、リトライの設定を示す。(Q1)
- FR3.3 コマンドの誤り(引用符の閉じ忘れなど)は、`--dry-run` で見つかり、本実行と同じ誤りと終了コードにする。ステートの誤りも、同じにする。(Q1)
- FR3.4 `--assume <ジョブID>=<終了コード>` を付けると(複数回指定できる)、そのジョブがその終了コードで終わったと仮定した流れ(どのジョブが実行され、スキップされるか)を示す。実際には何も実行しない。(Q1、スコープ定義の Q6)

### FR4 `conductor init`

- FR4.1 `conductor init [--config <パス>] [--force] [<パイプライン名>]` は、定義のひな形を作る。パスの既定は `conductor.toml`。(Q1)
- FR4.2 作る先にファイルが既にあるときは、何も変更せず、終了コード 69 で終わる。`--force` を付けると、上書きする。(Q1)
- FR4.3 ファイルの作成は、排他的に行う(同時に作られても、既存のファイルを壊さない)。(Q1)
- FR4.4 パスに `-` を指定すると、ファイルを作らずに、標準出力にひな形を出す。(Q1)
- FR4.5 ひな形は 1 種類で、コメントはロケール(日本語/英語)に従う。`[pipeline.env]` と `[job.retry]` の例を含む。作ったものは、必ず `validate` に通る。(Q6)

### FR5 共通

- FR5.1 新しいメッセージ(誤り、警告、使い方、図の注記)は、日本語と英語の両方で用意する。(team-practices.md の Code Style、既存のメッセージの方針)
- FR5.2 README に、新しい機能(キー、コマンド、オプション、終了コード 69)を、版(v0.9.0 以降)つきで書く。デモに、新しい機能の場面を足す。(intent-statement.md の周知の方針)

## 3. 非機能要件

- NFR1 性能: ジョブが 1,000 個ある定義で、`graph` と `--dry-run` は、1 秒以内に終わる。テストで確かめる。(Q8)
- NFR2 秘密情報: 環境変数の値は、出力とステートに出さない(FR1.12)。エラーの表示に入力の値を含めない(project.md の NEVER)。
- NFR3 互換と移植性: Linux、macOS、Windows で、同じ挙動にする。Windows では環境変数の名前が大文字小文字を区別しないため、同じ表の中で、大文字小文字だけが違う名前を、誤りとして拒否する。(team-practices.md の CI の方針)
- NFR4 品質: 新しい機能のコードは、行カバレッジ 80% 以上、`cargo fmt` と `cargo clippy -D warnings`、MSRV 1.100 を満たす。(project.md の ALWAYS)
- NFR5 依存: 新しい外部ライブラリを追加しない。`.env` の読み取りと、図の描画は、自前で書く。(project.md の NEVER、team-practices.md)
- NFR6 構造の制約: `unsafe` は runtime の `platform/unix.rs` の外に書かない。`cfg(unix)`/`cfg(windows)` は `platform` の外に置かない。(project.md の NEVER)
- NFR7 保守: 定義の仕様書(rust 版と language-agnostic 版)を、実装に合わせて更新する。(スコープの Q と、決定の記録)

## 4. 制約

- 技術: Rust(edition 2024、MSRV 1.100)。コアの crate は、定義の読み込みのほかにファイルに触れない(architecture.md の既存の性質)。
- 組織: `main` に直接コミットし、変更は小さな単位に保つ(team-practices.md)。
- 互換: v0.8.0 の定義とステートが変更なしで動く必要は、必須ではない(スコープ文書の Q7)。ただし FR1.13 により、新しいキーを使わない既存の定義は、読める。

## 5. 前提

- 利用者は、自分たちのチーム(内部)である(intent-statement.md)。
- 環境変数の注入は、`unset_env` と、optional な `env_file` を含めない(Q1)。
- 守る期限はない(スコープ文書)。

## 6. 範囲の外側

- 並列実行、ジョブのタイムアウト、排他制御、`error` への遷移(intent-statement.md、scope-document.md)。
- `.env` の変数の展開、複数行の値(FR1.6)。
- 定義の書式の版の引き上げ(FR1.13)。
