# 機能の設計: 質問(U1 u1-env-injection: 環境変数の注入と `.env`)

この文書は、U1 の振る舞い(`.env` の読み取り、層の統合、起動への反映、`validate` の警告)のうち、要件(FR1.1〜FR1.13)と契約(C1、C3、C4)がまだ決めていない点を、決めるための質問です。要件で決まっている点(優先順位、`.env` の書式、上限、予約名など)は、質問にしません。

既存のコードの前提(読んだもの):

- 定義の誤りの終了コードは 64、ステートの誤りは 65、使い方の誤りは 68。新しい値は、`init` の 69 だけ(契約 C5)。
- ジョブは `run_job(job, signal)` で起動され、環境は引き継ぐ。リトライは `run_job_with_retry` が、同じ関数を繰り返し呼ぶ。
- 定義の検証の誤りは、種類つきで、複数を集めて返す(`DefinitionError`)。理由の文に、入力の値は含めない。

各質問の「推奨」は、アーキテクトの案です。

## Q1. [アーキテクト] `.env` の誤りの終了コード

`.env` のファイルが無い、読めない、書式の誤り、上限の超過、のとき、ジョブを 1 つも実行せずに止まります(FR1.8)。そのときの終了コードは、どれにしますか。

- A. 64(定義の誤りと同じ)。`env_file` は定義の一部で、「定義が実行できる状態にない」という点で、定義ファイルが無い、読めないのと同じ。新しい終了コードを増やさない(推奨)
- B. 65(ステートの誤りと同じ)。ファイルの読み取りの失敗という点で近いが、ステートの意味(再開のための記録)と混ざる
- C. 新しい終了コード(71 など)。`.env` の誤りを、定義の誤りと区別できるが、契約の変更(C5)になり、README とテストが増える
- X. Other (please specify)

[Answer]: A

## Q2. [アーキテクト] 実行の前に読む `.env` の範囲

`pipeline` は、最初のジョブを起動する前に、`.env` を読みます(FR1.8)。どのファイルまで読みますか。

- A. 定義にある、すべてのジョブの `env_file` と、`[pipeline].env_file` を、すべて読む。すでに成功した(再開で飛ばす)ジョブと、遷移でスキップされるジョブの分も読む。理由: 実行の途中で誤りが出て止まる(例: 3 つ目のジョブの `.env` が壊れている)ことを避け、再開のたびに同じ結果になる(推奨)
- B. これから実行するジョブだけの分を読む。再開のときは、実行済みのジョブの `.env` が、もう無くても動く。ただし、遷移で飛ぶかどうかは、実行してみないと分からないため、読む範囲が実行ごとに変わる
- X. Other (please specify)

`run`(1 ジョブだけを実行する)は、どちらの案でも、`[pipeline].env_file` と、そのジョブの `env_file` だけを読みます。

[Answer]: A

## Q3. [アーキテクト] `validate` が `.env` を読むか

重複キーの警告(FR1.7)は、`.env` の中身を読まないと出せません。`validate` は、`.env` を読みますか。

- A. 読む。`.env` が無い、読めない、書式の誤り、のときは、定義の誤りと同じ扱い(Q1 の終了コード)にする。重複キーの警告も出す。`validate` が通れば、`pipeline` の `.env` の読み取りでは、誤りが出ない(推奨)
- B. 読むが、ファイルが無いときは、警告にとどめる(本番の環境にだけ `.env` がある、という使い方を許す)。ただし、`pipeline` では、誤りで止まるため、`validate` が通っても、実行できないことがある
- C. 読まない。重複キーの警告は、実行(`pipeline`、`run`)のときに出す
- X. Other (please specify)

[Answer]: A

## Q4. [アーキテクト] 誤りの報告のしかた

`.env` に、複数の誤り(書式の誤りの行が 2 つ以上、または複数のファイルの誤り)があるとき、どう報告しますか。

- A. すべて集めて、全部報告する。ただし、出力が長くなりすぎないよう、20 件で打ち切り、残りは件数だけを示す。定義の検証が「複数の誤りを集めて返す」のと同じ流儀(推奨)
- B. 最初の 1 件で止めて、報告する。実装は簡単だが、直しては実行し直す、の繰り返しになる
- X. Other (please specify)

[Answer]: A

## Q5. [アーキテクト] 先頭の BOM(UTF-8 の目印)

Windows の一部のエディタは、UTF-8 のファイルの先頭に BOM(`EF BB BF`)を付けます。`.env` の先頭に BOM があったとき、どうしますか。

- A. 先頭の BOM だけを無視して、読む。BOM が付いたファイルを、1 行目の誤り(名前が正しくない)にしない(推奨)
- B. 誤りにする。BOM を許さないことで、書式を単純に保つ
- X. Other (please specify)

(CRLF の改行は、どちらの案でも受け付けます。行末の CR を取り除きます。)

[Answer]: A

## Q6. [アーキテクト] `env_file` のパスの範囲

`env_file` に、絶対パスと、`..` を含む相対パスを許しますか(FR1.5 は、相対パスの基準だけを決めています)。

- A. どちらも許す。シンボリックリンクも、OS の規則のまま。エラーの表示に出すパスは、制御文字のエスケープと切り詰めをして、値としては扱わない(定義ファイルのパスと同じ扱い)(推奨)
- B. 定義ファイルのあるディレクトリの中(`..` と絶対パスを禁止)に限る。誤用は防げるが、共有の `.env` を、リポジトリの外に置けない
- X. Other (please specify)

[Answer]: A

## Q7. [アーキテクト] 大文字小文字だけが違う名前

Windows の環境変数は、大文字小文字を区別しません(NFR3)。`env` の表の中では、すでに誤りにすると決めています。`.env` の中と、層(`.env`、`env` の表、`pipeline` と `job`)をまたぐ場合は、どうしますか。

- A. `.env` の中も、`env` の表の中と同じく、大文字小文字だけが違う名前は、誤りにする。層をまたぐときは、完全に同じ名前で統合し(後ろの層が勝つ)、大文字小文字だけが違う名前は、別の名前として、層の順に環境へ足す(Windows では、OS が、後ろに足した名前で、前の名前を置き換える。結果は、どの OS でも、後ろの層が勝つ)(推奨)
- B. 層をまたぐときも、大文字小文字を同じ名前として統合する(後ろの層が、綴りも含めて勝つ)。OS による違いはなくなるが、Linux と macOS の利用者が、`path` と `PATH` を別の変数として使えなくなる
- X. Other (please specify)

[Answer]: A

## Q8. [アーキテクト] run ID が無いときの、引き継いだ `CONDUCTOR_RUN_ID`

run ID が無いとき、`CONDUCTOR_RUN_ID` は渡しません(FR1.10)。ところが、外側の `conductor`(入れ子の呼び出し)が渡した `CONDUCTOR_RUN_ID` が、引き継いだ環境に残っていることがあります。

- A. 渡さないだけ。引き継いだ環境は、そのまま子に渡る(要件の文面どおり。実装が単純。入れ子の呼び出しで、外側の run ID が見えることがある)(推奨)
- B. 子の環境から、引き継いだ `CONDUCTOR_RUN_ID` を取り除く。入れ子の呼び出しで、外側の run ID が見えなくなるが、起動の口(`run_job`)に、取り除く名前の指定が増える
- X. Other (please specify)

(同じ考え方が `CONDUCTOR_PIPELINE`、`CONDUCTOR_JOB_ID`、`CONDUCTOR_ATTEMPT` には、当てはまりません。この 3 つは、常に渡し、引き継いだ値を上書きします。)

[Answer]: A
