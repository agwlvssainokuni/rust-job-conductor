# 機能の設計: 質問(U3 u3-dry-run: `--dry-run` と `--assume`)

この文書は、U3 の振る舞い(実行計画の生成、`--assume` の模擬、出力の形、誤りの扱い)のうち、要件(FR3.1〜FR3.4)と契約(C1、C2、C5、C7)が決めていない点を、決めるための質問です。要件と契約で決まっている点(何も実行しない、ステートを作成も更新も削除もしない、計画を出せたときは終了コード 0、再開位置とジョブごとの扱い、分割後のコマンドと渡される環境変数の名前とリトライの設定を示す、値は出さない)は、質問にしません。

## 質問せずに決めたこと(既存のコードを読んで、決まったこと。異議があれば、教えてください)

- **コマンドの分割の置き場所**(契約の未解決事項。ドメイン設計のレビューの指摘): `core` は `runtime` を呼べないので、`CliFlows` が、`runtime` の `check_command` で各ジョブのコマンドを分け、分けた結果を、計画の作成(`core`)へ渡す。分割の誤り(引用符の閉じ忘れなど)は、`pipeline` と `run` の準備と同じ検査(`check_definition`。誤りは 64)で、すでに見つかる。`--dry-run` も、同じ検査を通すので、FR3.3(本番と同じ誤りと終了コード)は、そのまま満たされる。
- **実行の流れの模擬**: 計画は、`pipeline` の流れと同じ判断(`decide_before_run`、`classify_and_decide`)を、実行の代わりに、仮定の終了コードで進める。ステートは、読むだけで、模擬の途中の状態は、`core` の中だけで持ち、保存しない。
- **`.env` と `env`**: `--dry-run` も、`pipeline` と同じ範囲の `.env` を、同じ読み取りで読み(U1 の設計の BR6.1)、誤りのときは、本番と同じに、終了コード 64 で止まる。計画に出すのは、渡される環境変数の「名前」だけ(契約 C1。引き継いだ環境の名前は含まない)。値は、どこにも出さない。
- **リトライ**: 計画には、リトライの設定を示す。模擬では、リトライを繰り返さず、仮定の終了コードを、「リトライを終えた最後の結果」として扱う(リトライの対象の終了コードを仮定したときは、その旨を注記する)。
- **`--remove-on-complete`、`--run-id`**: `--dry-run` と併用できる。`--run-id` は、読むステートの場所を決める(本番と同じ)。`--remove-on-complete` は、何も削除しないので、効果がない(受け付けて、無視する)。
- **`--assume` を `--dry-run` なしで付けたとき**: 使い方の誤り(終了コード 68。契約 C5)。

## Q1. [アーキテクト] `--assume` の不正な入力と、使われない仮定

`--assume <ジョブID>=<終了コード>` の、不正な入力(契約の未解決事項)と、実行されないジョブへの仮定の扱いを決めます。

- A. (1) 書式の誤り(`=` がない、終了コードが整数でない)、存在しないジョブ ID、同じジョブ ID の重複、終了コードが 0〜255 の範囲外は、使い方の誤り(終了コード 68)で、何も表示せず止まる。メッセージには、入力の値を含めない(ジョブ ID と終了コードの値は、出さない。誤りの種類だけ)。(2) 仮定したジョブが、模擬の流れで実行されない(遷移でスキップされる、実行済み、停止のあと)ときは、誤りにせず、計画の中に、「使われなかった仮定」として、ジョブ ID を注記する(推奨)
- B. (1) は A と同じ。(2) 仮定が使われなかったときは、誤り(68)にする。意図しない仮定に、気づきやすいが、「この遷移なら、ここは通らない」という確認に使いにくい

[Answer]: A

## Q2. [アーキテクト] 仮定の指定がないジョブの、模擬での終了コード

`--assume` で指定しなかったジョブは、模擬で、どう終わるものとしますか。

- A. 成功(終了コード 0)で終わるものとする。何も指定しなければ、「すべて成功したときの流れ」が出る。指定したジョブだけが、別の結果になる(推奨)
- B. 指定しなかったジョブは、模擬の対象にせず、最初の指定のないジョブで、計画を打ち切る(「ここから先は、実行してみないと分からない」とする)。仮定のない計画は、最初のジョブまでになる
- X. Other (please specify)

[Answer]: A

## Q3. [アーキテクト] `--dry-run` の出力の形

出力の項目と順序は、契約 C7 で決まっています(ヘッダー、再開位置、仮定、ジョブごとの項目)。表示の形(文言と並べ方)を決めます。

- A. ジョブごとに、見出しの行と、字下げした詳細の行(複数行)。例:

  ```text
  計画(--dry-run): パイプライン demo(run ID: r1)
  再開位置: b(前回のエラーで停止)
  仮定: c=75
  1. [実行済み] a
  2. [実行する] b  <- 再開位置
       コマンド: ["echo", "b"]
       環境変数: CONDUCTOR_PIPELINE, CONDUCTOR_JOB_ID, CONDUCTOR_RUN_ID, CONDUCTOR_ATTEMPT, API_URL
       リトライ: 終了コード 75、76 を最大 3 回、間隔 5 秒
  3. [実行する(仮定: 終了コード 75 → エラー)] c
       ...
  4. [実行されない(停止のあと)] d
  ```

  読みやすく、長いコマンドでも崩れない(推奨)
- B. 1 行 1 ジョブの、表の形(ジョブ、扱い、コマンド、環境変数の名前)。一覧しやすいが、環境変数の名前とコマンドが長いと、行が長くなる

[Answer]: A

## Q4. [アーキテクト] 本番なら「拒否される」ときの `run --dry-run`

`run <ジョブID> --dry-run` で、本番なら順序外(前のジョブが済んでいない)として拒否される(終了コード 66)ときの扱いです。

- A. 本番と同じに、拒否の理由を表示し、終了コード 66 で止まる。`--dry-run` が「本番と同じ判断を、実行せずに行う」ことを、終了コードでも守る。スクリプトが、`--dry-run` の終了コードで、本番が拒否されるかを調べられる(推奨)
- B. 計画の中に「拒否される」と示し、終了コードは 0 にする(計画を出せたので)。計画は常に出るが、終了コードは、本番と食い違う
- X. Other (please specify)

[Answer]: A
