# 機能の設計: 質問(U2 u2-graph: `conductor graph`)

この文書は、U2 の振る舞い(辺の取り出し、レーンの配置、text と Mermaid の整形、`--state` の重ね合わせ)のうち、要件(FR2.1〜FR2.7)と契約(C2、C5、C6)が決めていない点を、決めるための質問です。要件と契約で決まっている点(`*` と `o`、`|\` と `|/`、`@end`、成功と警告が同じ行き先なら 1 つの辺、`-v`、`[OK]` などの記号、`validate` と同じ誤りと終了コード 64)は、質問にしません。

## 前提(既存のコードを読んで分かったこと)

- ジョブから出る辺は、結果が「成功」のときの遷移先と、「警告」のときの遷移先です。遷移を書かなければ、記述順で次のジョブ(最後のジョブなら、終点 `@end`)です。「エラー」には遷移がなく、そこで止まるので、辺はありません。
- 例(ジョブ a、b、c、d、e。`a` が成功で `d` へ飛ぶ):

  ```text
  * a
  |\
  | * b
  | * c
  |/
  * d
  * e
  o @end
  ```

  左のレーンは「成功で d へ飛ぶ辺」、右のレーンは「警告で次のジョブ(b)へ進む辺」です。成功と警告の行き先が同じなら、分岐しません。

- この例のように、遷移が後ろ向きでないこと(定義の検査で保証)から、レーンは、必ず有限で、交差しません(入れ子か、並びのどちらか)。

## Q1. [アーキテクト] 分岐のレーンに、辺の種類(成功、警告)を書くか

上の例の `|\` の左右のレーンが、成功と警告のどちらの辺かは、記号だけでは分かりません。

- A. 既定では書かない(記号だけ。`git log --graph` と同じ)。`-v` のときだけ、分岐の行の直後に、注記の行を添える(例: `|   成功 → d、警告 → b` のように、辺の種類と行き先)。要件 FR2.3(`-v` で飛び越しの注記)に合う(推奨)
- B. 常に、分岐のレーンに、短いラベル(`ok`、`warn`)を書く。読みやすいが、`git log --graph` から離れ、行が長くなる
- X. Other (please specify)

[Answer]: A

## Q2. [アーキテクト] `--state` の記号と、再開位置の示し方

`--state` では、ジョブの状態を重ねます(成功 `[OK]`、スキップ `[--]`、エラー `[NG]`、未実行 `[  ]`。FR2.7)。記号を置く場所と、再開位置の示し方を決めます。

- A. 記号は、ノードの記号のあと、ジョブ ID の前に置く(例: `* [OK] a`)。レーンの位置が、状態の有無で変わらない。再開位置は、そのジョブの行の末尾に、`  <- 再開位置`(英語は `  <- resume here`)を添える(推奨)
- B. 記号は、行頭に置く(例: `[OK] * a`)。状態が縦にそろって見えるが、レーンの前に、固定の幅の列が入る。再開位置は、A と同じ
- X. Other (please specify)

[Answer]: A

## Q3. [アーキテクト] `--state` まわりの扱い(ステートが無いとき、食い違うとき、`--run-id` だけのとき)

- A. (1) ステートが無いときは、エラーにせず、すべてのジョブを未実行 `[  ]` で表示する。(2) ステートが定義と食い違うとき(ジョブの並びが違う、など)は、既存の照合と同じ誤り(ステートの誤り。終了コード 65)で止まる。(3) `--run-id` を `--state` なしで付けたときは、使い方の誤り(終了コード 68)にする。契約 C5 の未解決事項はこれで決まる(推奨)
- B. (1) ステートが無いときは、誤り(65)にする。(2) と (3) は A と同じ。ステートが無いこと自体を、利用者に気づかせるが、「まだ実行していない定義の図」に `--state` を付けられない
- X. Other (please specify)

[Answer]: A

## Q4. [アーキテクト] Mermaid の節の ID

ジョブ ID には、Mermaid の節の ID として使えない文字(ハイフン、ドット、日本語、`end` などの予約語)が入りうります。

- A. 節の ID は、連番(`n0`、`n1`、…。終点は `nend`)にし、ジョブ ID は、ラベル(`n0["job-id"]`)として、引用符つきで書く。ラベルの中の `"` と制御文字は、エスケープする(`#quot;` など)。どのジョブ ID でも壊れない(推奨)
- B. ジョブ ID をそのまま節の ID にする。読みやすいが、使えない文字を含む ID で、図が壊れる(その場合は、別の規則が要る)
- X. Other (please specify)

[Answer]: A

## Q5. [アーキテクト] 飛び越しが交差するときの text の図

飛び越しの区間が、入れ子でも並びでもなく、交差することがあります(例: `a` が成功で `d` へ、`b` が成功で `e` へ飛ぶ。a < b < d < e)。この形は、定義の検査を通ります。入れ子と並びは、レーンで描けます(`|\` と `|/`)。交差する飛び越しは、レーンが交差するため、決まった描き方が、複雑になります。

- A. 交差する飛び越しがあるときは、text では、レーンの図の代わりに、辺の一覧(`a -> d`(成功)のような、1 行 1 辺の形)を出し、先頭に「飛び越しが交差するため、レーンの図にできません」という注記を付ける。入れ子と並びの図は、単純な規則で、確実に描ける。Mermaid は、交差に関係なく、常に描ける(推奨)
- B. 交差する飛び越しも、レーンで描く。合流の行を、複数に分け、レーンを左へ詰める規則を足す。見た目は統一されるが、規則と、期待出力のテストが、大きく増える
- X. Other (please specify)

[Answer]: X. git log --graph と同じ方式で、交差も描く(ユーザーの言葉: 「git logみたいに交差できない？」)。実際の `git log --graph` の出力を確かめた結果、交差も描ける。この方式(ジョブは左の列に並び、飛び越しの辺は右のレーン)に倣い、機能の設計に、git の出力から取った期待出力の例を載せる。

注記: この文書の「前提」の例(飛び越されるジョブを右のレーンに描いた図)は、説明用の略図で、`git log --graph` の方式ではない。採用するのは、上のとおり、ジョブが左の列に並ぶ方式。
