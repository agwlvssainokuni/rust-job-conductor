## Intent analysis

ジョブの `command` は、いまは 1 つの文字列で、独自の規則(`'...'`、`"..."`、空白区切り)で分割される。空白や引用符を含む引数を渡すには、この規則を覚えて書く必要がある。**文字列の配列**でも書けるようにして、1 要素を 1 引数として、分割も展開もせずに渡せるようにする。既存の文字列の書き方は、そのまま使える(追加の変更。公開済みの v0.1.0 の定義は、壊れない)。

## Functional requirements

- **FR1 `command` の書き方** `command` は、文字列、または文字列の配列で書ける。
  - **FR1.1** 文字列は、従来どおり。分割の規則、起動の仕方、結果は、変わらない。
    - 受け入れ基準: 既存のテスト(文字列の `command`)が、変更なしで、すべて成功する。
  - **FR1.2** 配列は、1 要素が 1 引数。先頭の要素が実行するプログラムで、残りが引数。空白、引用符、`$`、`*`、`|` などは、そのまま 1 つの引数の文字として渡し、分割も展開もしない。
    - 受け入れ基準: `command = ["sh", "-c", "echo \"$1\"", "x", "a b"]` を実行すると、プログラム `sh` に、引数 `-c`、`echo "$1"`、`x`、`a b` の 4 つが、この順で渡る。
  - **FR1.3** 型の誤りは、定義の誤り(終了コード 64)になる。`command` が、文字列でも配列でもない、または、配列の要素に文字列でないものがある。
    - 受け入れ基準: `command = 5`、`command = ["a", 5]`、`command = {}` は、いずれも定義の誤りで、誤りの場所(キーと行)を示す。
  - **FR1.4** 配列の検証 [Q1: A]。空の配列は、定義の誤り。先頭の要素が、空、または空白だけの文字列なら、定義の誤り。2 番目以降の要素は、空の文字列でも、有効な引数として渡す。
    - 受け入れ基準: `command = []` と `command = [""]` と `command = ["  ", "x"]` は、定義の誤り。`command = ["echo", ""]` は有効で、空の引数が 1 つ渡る。
  - **FR1.5** 文字列の `command` が、空、または空白だけなら、従来どおり、定義の誤りになる(変更なし)。
- **FR2 実行** 配列の `command` のジョブも、文字列と同じに実行する。
  - **FR2.1** 配列は、シェルを介さず、先頭の要素をプログラム、残りを引数として、直接起動する。作業ディレクトリ、環境変数、シグナル、終了コードの扱いは、文字列と同じ。
    - 受け入れ基準: 同じプログラムと引数を、文字列と配列で書いたジョブは、同じ終了コード、同じステート、同じ表示になる。
  - **FR2.2** 起動に失敗した(127)ときの表示に出すプログラム名は、配列では先頭の要素、文字列では従来どおり先頭の語。長さと制御文字の扱いは、従来どおり(64 文字で切り、エスケープする)。
    - 受け入れ基準: 存在しないプログラムを配列で書くと、終了コード 127 で、その名前(先頭の要素)が表示される。
  - **FR2.3** Windows で、`.cmd` と `.bat` に渡す引数は、従来どおり、標準のライブラリの安全なエスケープに従う(配列の要素に、メタ文字があっても、続くコマンドは実行されない)。
- **FR3 変換(`convert`)** TOML と YAML の変換で、`command` の形を保つ。文字列は文字列のまま、配列は配列のまま。
  - 受け入れ基準: 配列の `command` を含む定義を、TOML → YAML → TOML と変換すると、元と同じ木になる(YAML → TOML → YAML も同じ)。
- **FR4 書式の版** `format_version` は 1 のまま。配列は、追加の書き方 [Q2: A]。v0.1.x の `conductor` は、配列を使った定義を、定義の誤り(文字列でない)として拒否する。この互換の注意を、README に書く。
  - 受け入れ基準: `format_version = 1` で配列の `command` を書いた定義が、受け入れられる。README に、v0.1.x が配列を拒否することが書かれている。
- **FR5 文書とデモ** README の「command の書き方」に、配列の書き方(1 要素 1 引数、分割も展開もしない、先頭の要素の検査、空の引数)を、例とともに書く。デモの定義に、配列の `command` を使うジョブを入れる。
  - 受け入れ基準: README に配列の節がある。`demo/run-demo.sh` が、配列の `command` を含む定義で、最後まで成功する。

## Non-functional requirements

- **NFR1 後方互換** 文字列の `command` を使う既存の定義は、動作、終了コード、メッセージ、ステートの形が、変わらない。ステートファイルの形式は変えない(ステートは `command` を保存しない)。
- **NFR2 安全** 配列の要素の値(入力の値)は、エラーメッセージに出さない(誤りの種類と場所だけ)。表示するプログラム名は、制御文字と双方向制御文字をエスケープし、64 文字で切る。`unsafe` を増やさない。
- **NFR3 品質** 行カバレッジ 80% 以上を保つ。既存の 564 件のテストは、成功する(型の変更に伴う修正を除く)。`cargo fmt --check`、`cargo clippy -D warnings`、Rust 1.85 でのビルドとテスト、Linux・macOS・Windows の CI が成功する。
- **NFR4 配布** 公開は新しい版(v0.2.0。`Cargo.toml` の `version` を上げる)で行う。

## Constraints

- Rust 1.85 で、ビルドできること(let チェーンなど、1.88 以降の構文は使わない)。
- ライブラリの追加はしない(TOML は `toml`、YAML は `saphyr-parser` を、そのまま使う)。
- チームの実践(test-after、`rustfmt`、`clippy`、`main` への取り込みで履歴を残す)に従う。

## Assumptions

- ステートファイルは `command` を保存していない(調査で確認。コードの検索による)。変更が要る場合は、Functional Design で、見直す。[memory:M1]
- `convert` は、YAML の配列を、TOML の配列(インライン形式)に、TOML の配列を、YAML のブロックの列に書く(形式の細部は、Code Generation で決める。意味が同じであればよい)。[assumption]
- 配列の `command` を使うジョブの `-v` と `watch` の表示は、従来と同じ(いまの表示に、`command` の文字列は出ない)。[assumption]

## Out of scope

- 配列でのシェルの利用(`["sh", "-c", ...]` は、普通のプログラムとして起動するだけ)。環境変数の展開、`~` の展開、グロブ。
- `command` と別の `args` キーを設ける形。ジョブごとの環境変数・作業ディレクトリの指定。
- ステートファイルの形式の変更。`format_version` の引き上げ。
