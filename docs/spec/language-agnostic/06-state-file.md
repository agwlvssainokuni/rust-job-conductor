# 06. ステートファイル(論理項目・保存の性質・読み書き・整合性・reset)

対象: `conductor` v0.10.1 までと同じ挙動の実行ツール。ステートファイルは、あるパイプライン定義の実行の途中経過(どのジョブがどう終わったか、どこから再開するか)を保存するファイル。実行の意味論(いつ何を記録するか)は [05-execution-flow.md](05-execution-flow.md) にある。この文書は、ステートが持つ**論理的な項目**、保存の**必須の性質**、**参照用の書式**、読み書きの手順、異常系の挙動を定める。

## 0. この文書の読み方(必須と任意の区別)

| 区分 | 内容 |
|---|---|
| 必須(どの実装も同じ) | §2 の論理項目・値の規則・矛盾の条件、§3 の保存の性質、§6 の読み込みの検査(順序・種類・理由文・案内文)、§7 の整合性検査、§8 の reset の挙動、ファイルの場所と名前(§1) |
| 参照(現行の書式) | §4 の TOML 書式(実ファイル例つき)。実装は、言語に応じて別の書式(JSON、独自のテキスト等)を選んでよい。ただし、論理項目・検査の挙動・異常系の種類と理由文は、書式に依らず同じにする |
| 実装に任せてよい点 | 書式のエスケープの細部、一時ファイルの名前の付け方、権限の設定、読み込みの内部の構造 |

注意: 他の実装と**ステートファイルを共有する**(ある実装が書いたファイルを別の実装が読む)ことが要件なら、参照の書式(§4)をそのまま採ること。共有しないなら別の書式でよいが、その場合、§6 の検査の「書式の検査」(UTF-8・構文・未知の項目)に相当する検査を、その書式で行うこと。

## 1. 場所と名前

ステートファイルは、**定義ファイルと同じディレクトリ**に置く。

| run ID | ファイル名 |
|---|---|
| なし | `<定義ファイル名>.state` |
| あり | `<定義ファイル名>.<run-id>.state` |

- `<定義ファイル名>` は、定義ファイルのパスの最後の要素(拡張子を含む)。例: `conductor.toml` → `conductor.toml.state`、`--config ci/nightly.toml --run-id 12345` → `ci/nightly.toml.12345.state`。
- 定義ファイルのパスは、`--config` で与えられた文字列のまま(正規化・絶対化しない)。ディレクトリ部分が空(`conductor.toml` のように親が無い)なら、実行ディレクトリ。
- run ID は検査済み(`A-Za-z0-9._-`、1〜64 文字、先頭が `.` でない。05 §6)なので、パス区切りや `..` は入らない。
- 一時ファイルの名前: `.<ステートファイル名>.tmp.<プロセス番号>.<時刻(ナノ秒)>.<連番>`(同じディレクトリ。§5)。名前の付け方は実装に任せてよいが、**ドットで始まり、`.tmp.` を含み、後始末(§5 の 9)で識別できる**こと。
- 大文字小文字を区別しないファイルシステム(macOS の既定、Windows)では、`A` と `a` の run ID は同じファイルになる。食い違いは、中身の `run_id` との照合で壊れたステート(65)として検出される(§6 の 9)。

## 2. ステートの論理項目

### 2.1 ステート全体の項目

| 項目 | 型 | 必須 | 意味・値 |
|---|---|---|---|
| `format_version` | 整数 | 必須 | 常に `1`。読み込みでは最初に検査される(§6) |
| `definition_key` | 文字列 | 必須 | 定義ファイルのパス(`definition_path` と**同じ文字列**を書く。読んだ値を保持するかは実装による。どちらも照合に使わない) |
| `definition_path` | 文字列 | 必須 | 定義ファイルのパス(`--config` の文字列。文字列として表せない部分は代替文字に置換される)。空でもよい |
| `pipeline_name` | 文字列 | 必須 | 記録時の `[pipeline].name`。照合に使う(§7) |
| `job_order` | 文字列の列 | 必須 | 記録時のジョブIDを、定義の記述順に並べたもの |
| `job` | ジョブ状態の列 | 必須 | ジョブごとの状態(§2.2)。`job_order` と同じ順・同じ数 |
| `resume_job_id` | 文字列 | 任意 | 次に実行する、または再開するジョブのID。無いときは項目自体を保存しない。`job_order` に含まれる値 |
| `end_reached` | 真偽 | 必須 | `@end` に到達したか。一度 true になったら、その run のあいだ false に戻らない |
| `completed` | 真偽 | 必須 | 完了したか(§9) |
| `run_id` | 文字列 | 任意 | run ID。run ID ありのステートだけが保存する。無いステートには項目を保存しない |

上の表にない項目は、ステート全体にも、ジョブ状態の中にも許さない(§6 の `corrupt`)。旧形式の項目(`jobs` など)も未知の項目として拒否される。

### 2.2 ジョブ状態の項目

| 項目 | 型 | 必須 | 意味・値 |
|---|---|---|---|
| `id` | 文字列 | 必須 | ジョブID |
| `status` | 文字列 | 必須 | `"pending"` / `"success"` / `"warning"` / `"error"` / `"skipped"`(これ以外は `corrupt`) |
| `exit_code` | 整数(32 ビット符号付き整数の範囲: -2147483648〜2147483647) | 任意 | ジョブの終了コード。`status` が success / warning / error のときだけ持てる。終了コードが無い結果(起動失敗・シグナル終了)の error には保存しない。負数も許す(例 `-1`)。範囲外の整数は `corrupt` |
| `skip_reason` | 文字列 | 条件付き | `"byTransition"`(遷移によるスキップ)/ `"byEnd"`(`@end` によるスキップ)。**`status = "skipped"` のときだけ必須、そのほかの `status` では保存してはならない** |
| `attempt`(v0.10.0 以降) | 試行の列 | 条件付き | 試行(ジョブの 1 回の起動)の時刻の並び。古い順。**`status` が success / warning / error のときは 1 つ以上が必須**(§2.3)。試行が無ければ項目自体を保存しない(§2.2a) |

ジョブ状態の項目は、上の 5 つだけ。

### 2.2a 試行の項目(v0.10.0 以降)

| 項目 | 型 | 必須 | 意味・値 |
|---|---|---|---|
| `started_at` | 文字列(時刻) | 必須 | 試行を始めた時刻。起動の前に取る |
| `ended_at` | 文字列(時刻) | 任意 | 試行が終わった時刻。**無くてよいのは最後の試行だけ**(動いている最中か、`conductor` が強制終了された後) |

- 項目は上の 2 つだけ。ほかの項目は `corrupt`(知らない項目)。コマンド・環境変数・ジョブの出力は保存しない。【必須】
- 時刻の書式は UTC の RFC 3339 の `YYYY-MM-DDTHH:MM:SSZ` だけ(例 `2026-11-25T09:12:48Z`)。読むときも、この形だけを受け付ける(長さ 20、区切りの位置、数字、`Z`。小数の秒・時差・小文字は不可)。年は 1970〜9999、月は 1〜12、日はその月の日数まで(うるう年を含む。うるう秒は扱わない)、時は 0〜23、分と秒は 0〜59。形に合わなければ `corrupt`(時刻の書式の誤り)。文字列でなければ `corrupt`(値の型の誤り)。【必須】
- 終わりが始まりより前でも、誤りにしない(時計が戻った場合)。
- 時刻は、UTC の UNIX 時刻の秒(範囲は 1970-01-01T00:00:00Z〜9999-12-31T23:59:59Z)として持てば足りる。現在の時刻は、実行の部品の時計から取る(差し替えられるようにする。11 章の注入のテスト)。
- 受け入れテストは 11 章 4.26 節(AC-553〜AC-561)。

### 2.3 内容の矛盾(読み込み時に `corrupt` になる条件)

- ジョブ状態のジョブID に重複がある。
- ジョブ状態の並び(`id` の列)が `job_order` と、数も順序も完全には一致しない。
- `resume_job_id` が `job_order` にない。
- `resume_job_id` があるのに `completed = true`(完了と再開位置は両立しない)。
- `status` が `skipped` なのに `skip_reason` が無い、または `skipped` 以外なのに `skip_reason` がある。
- `status` が pending / skipped なのに `exit_code` がある。
- (v0.10.0 以降)`status` が success / warning / error(動いたジョブ)なのに、試行が 1 つも無い。理由 `動いたジョブに試行の記録がありません(古い形式の可能性があります)`。
- (v0.10.0 以降)最後でない試行に `ended_at` が無い。理由 `終わりの時刻の無い試行が、最後の試行ではありません`。
- (v0.10.0 以降)試行の時刻の書式が誤っている(§2.2a)。理由 `時刻の書式が誤っています`。

pending と skipped のジョブは、試行を持っても持たなくてもよい(中断で終わった試行が残る pending など)。

**v0.9.9 までに書いたステート**: 書式の版は `1` のままだが、v0.9.9 までは試行を書かなかったため、動いたジョブ(success / warning / error)を含むステートは、上の「試行が無い」で `corrupt`(65)になる。`run`・`pipeline`・`--dry-run`・`watch`・`graph --state` のどれでも同じで、`conductor reset`(run ID つきは `reset --run-id <ID>`)の案内を出す(§6.2)。pending と skipped だけのステートは、そのまま読める。

### 2.4 初期ステート(`initial_state`)

定義から作る、記録前のステート: 全ジョブ `pending`(`exit_code`・`skip_reason` なし)、`resume_job_id` 無し、`end_reached = false`、`completed = false`、`definition_key` = `definition_path` = 定義ファイルのパス文字列、`pipeline_name` = 定義の名前、`job_order` = 定義のジョブIDの記述順、`run_id` = 決定した run ID(あれば)。どのジョブも試行を持たない(v0.10.0 以降)。

### 2.5 不変条件(実装が保つもの)

05 §3 の記録関数が作るステートは、次を満たす(読み込みの検査と対応する)。

- ジョブ状態と `job_order` は同じ順・同じID。
- `skipped` のジョブにだけ `skip_reason` がある。`exit_code` は結果のある状態(success / warning / error)にだけある。
- `end_reached` は単調(true になったら戻らない)。
- `completed = true` のとき `resume_job_id` は無い。
- ただし、エラーのジョブを再実行して「起動前の中断」(05 §12 の 2)になったときは、`status = error` のまま `exit_code` が消える。
- (v0.9.0 以降)ステートに、環境変数(名前も値も)、`.env` の内容、`env` の設定を**書かない**。環境変数の項目はない(v0.10.0 以降も同じ。`unset_env` の名前も書かない)。再開のときも、`.env` は、呼び出しごとに読み直す(05 §14.5)。
- (v0.9.0 以降)`graph --state` は、ステートを、完了したものも含めて**読むだけ**で、書かず・消さない。`--dry-run` は、ステートを(完了したものは「空」として)読むだけで、書かず・消さない。どちらも、定義との照合(§7)を行い、食い違いは 65。

## 3. 保存の必須の性質

書式に依らず、実装が満たすこと。

| # | 性質 | 内容 |
|---|---|---|
| 1 | 原子的な置換 | 読み手は、直前の完全な内容か、新しい完全な内容のどちらかだけを見る。途中の内容は決して見えない。どの段階で失敗しても、ステートファイルは直前の完全な内容のまま(§5) |
| 2 | 再開に必要な情報 | 全ジョブの `id`・`status`・`exit_code`・`skip_reason`、`resume_job_id`、`end_reached`、`completed`、定義との照合用の `pipeline_name`・`job_order`、run ID を保存する。リトライの待ち時間は保存しない(再開は最初の実行から数え直す)。(v0.10.0 以降)試行ごとの開始と終了の時刻を保存する(§2.2a)。試行の数は時刻の並びから分かるが、`CONDUCTOR_ATTEMPT` とリトライの回数は、再開のたびに 1 から数え直す(05 §14) |
| 3 | 壊れたときの検出 | 読み込みで、構文・型・値・矛盾・版・run ID・大きさを検査し(§6)、壊れていれば**黙って続行せず**、種類と理由を表示して 65 で止まる。読み込みは、ファイルを消さず、書き換えない |
| 4 | 完了のステートの扱い | 完了のステートは書式を変えず残し、読み込み(`run`・`pipeline`)では「空」とみなす(§9) |
| 5 | 耐久性の 2 段階 | 結果・スキップ・中断の記録は、内容の同期まで行う(Durable)。試行の開始の記録(v0.10.0 以降。v0.9.x までは最初の初期ステートだけ)は、同期を省いてよい(Fast)(§5) |
| 6 | 排他制御はしない | ファイルロック・PID ファイルを使わない(§11) |

## 4. 参照用の書式(現行どおりの TOML、`format_version = 1`)

この節は「参照」。論理項目(§2)は書式に依らず同じで、実装は言語に応じて別の書式を選んでよい(その場合も §6 の検査の挙動は同じ)。以下は現行の書式。

### 4.1 エンコード

- UTF-8 の TOML(TOML 1.0)。
- 書き出し: キーは、各テーブル内で**アルファベット順**(辞書順)。最上位のスカラーと配列を先に、続いて `[[job]]`(テーブルの配列)を、`job_order` と同じ順で書く。各 `[[job]]` の前に空行。配列はインライン(`["a", "b", "c"]`)。文字列は `"` で囲む。エスケープの細部(基本文字列かリテラル文字列か)は、TOML として正しければよい(読み込みは、TOML として正しければ、どの文字列表記でも受け付ける)。
- 読み込みはキーの順序に依存しない。
- 論理項目とのキーの対応は同名: §2.1 の項目は最上位のキー、§2.2 は `[[job]]` の中のキー、§2.2a は `[[job.attempt]]`(v0.10.0 以降。ジョブの中のテーブルの配列)の中のキー。`job` が `[[job]]`、`job_order` が文字列の配列。任意の項目(`resume_job_id`、`run_id`、`exit_code`、`skip_reason`、`attempt`、`ended_at`)は、無いときキー自体を書かない。
- (v0.10.0 以降)各 `[[job]]` の中では、スカラーのキーをアルファベット順に書き、続けて `[[job.attempt]]` を古い順に書く(`[[job.attempt]]` の中も `ended_at`、`started_at` のアルファベット順)。読み込みは順序に依存しないので、キーの順は実装に任せてよい。

### 4.2 実ファイルの例(実装の出力。全項目)

v0.10.0 以降、動いたジョブ(success / warning / error)は `[[job.attempt]]` を持つ。下の例の時刻は、形を示すための値である。

(3)全種類の状態を含む例(4 ジョブ。run ID なし、`end_reached = true`、エラーで停止)。


(4)`skip_reason = "byTransition"` の例(遷移 `a --success--> c` で b を飛ばした直後。a 成功、b は byTransition でスキップ、c が次):

(5)(v0.10.0 以降)リトライを 2 回行い、3 回目の試行が動いている最中のジョブ(`pending`、最後の試行に `ended_at` が無い。ジョブの部分だけ)。前の 2 回の試行の終わりの時刻は、次の試行を始めるときに書かれる(§5.1)。

```toml

[[job.attempt]]

started_at = "2026-11-25T09:12:48Z"

[[job.attempt]]

```

## 5. 書き込み(`write_state`)の手順と原子性

入力: 定義ファイルのパス、run ID、ステート、耐久性(Durable / Fast)。

```text
1. text = serialize(state)            # 書式への変換。失敗(通常は起きない)なら WriteFailed(理由=「内容を TOML にできません」)
2. path = ステートファイルの場所(§1)
3. 一時ファイルを、同じディレクトリに、「既存なら失敗する」新規作成で作る
     名前 = ".<ステートファイル名>.tmp.<プロセス番号>.<ナノ秒>.<連番>"
     名前が既存なら、連番を進めて作り直す。最大 16 回。それでも作れなければ WriteFailed
     連番 = プロセス内の通し番号(原子的に増やす) + 試行回数(桁あふれは折り返してよい)
4. 全内容を書き、フラッシュする
5. Durable のときだけ、ファイルの内容を記憶装置まで同期する
6. 一時ファイルを閉じる(Windows は、開いたままだと移せない・消せない)
7. 一時ファイルをステートファイルへ、名前の付け替え(rename)で置き換える
8. 3〜7 のどこかで失敗したら: 自分が作った一時ファイルを消し、WriteFailed(理由=「書き込みに失敗しました」)
9. 成功し、かつ Durable のとき:
     UNIX 系では、ディレクトリを同期(失敗は無視。Windows では何もしない)
     同じ名前の型の一時ファイルのうち、更新から 24 時間以上たった通常のファイルを消す(失敗は無視)
```

性質:

- **原子的**: 読み手は、直前の完全な内容か、新しい完全な内容のどちらかだけを見る。途中の内容は見えない。どの段階で失敗しても、ステートファイルは直前の完全な内容のまま。
- 置き換え先がディレクトリなど、名前の付け替えが失敗するときは `WriteFailed`。ステートは変わらず、一時ファイルも残らない。書けないディレクトリも `WriteFailed`。
- 残った一時ファイル(プロセスが落ちたとき)は、読み込みに影響しない。`Durable` の書き込みの成功後に、24 時間以上古いものだけ消える。`Fast` では消さない。
- 「同じ名前の型」= 名前が `.<ステートファイル名>.tmp.` で始まるもの。
- ファイルの権限(パーミッション): 明示的には設定しない。一時ファイルは OS 標準の新規作成の権限(UNIX 系では 0666 から umask を引いた値。実測は `-rw-r--r--`)で作られ、置き換えでそのままステートファイルになる。既存のステートファイルを置き換えるときも、権限は引き継がず、新しい一時ファイルの権限になる。所有者の変更・ACL の操作はしない。
- 排他制御(ファイルロック)はしない(§11)。

### 5.1 いつ書くか(書き込みの契機)

| 契機 | 内容 | 耐久性 |
|---|---|---|
| (v0.10.0 以降)試行を始めるとき(ジョブを起動する前。リトライの各試行と再開を含め、試行ごとに 1 回) | 時計から取った時刻で試行を足したステート(05 §18。最後の試行に終わりが無ければ、その試行を自身の `started_at` で閉じてから、終わりの無い試行を足す)。リトライの 2 回目以降は、前の試行を、覚えていた終わりの時刻で閉じてから足す。ステートが空なら、初期ステート(§2.4)に試行を足したものを書き、これが初期化の書き込みを兼ねる。完了のまま残ったステートがあっても、同じ名前のファイルを**上書きする**。書き込みに失敗したら、ジョブを起動しない(v0.9.x までは、ステートが空で最初のジョブが `Run` と決まった直後に、初期ステートだけを書いた) | `Fast`(同期を省く) |
| ジョブの最終の結果が出た後(リトライを含めて 1 回だけ) | 05 §3.3 の結果の記録(試行を閉じたものに)。起動前の中断・待機中の中断も、この契機で書く(ジョブの状態は変わらず、`resume_job_id` が付く) | `Durable` |
| スキップが決まったとき(05 §3.4 の記録が元と異なるときだけ) | スキップの記録 | `Durable` |
| `pipeline` のジョブのあいだの中断 | 05 §3.5 の中断の記録 | `Durable` |
| 完了(`completed = true`)になったとき | 上の契機の書き込みに含まれる(完了のステートも同じ手順) | `Durable` |

- (v0.10.0 以降)試行の終わり: 起動して終わった・起動に失敗した・ログのファイルを作れずに起動しなかった試行は、試行の後に時計から時刻を取って閉じる。起動の前に中断の合図が立っていて起動しなかった試行は、取り除く。リトライするときは、終わりの時刻を覚えておき、試行を**開いたまま書かずに**待つ(待ちのあいだ、`watch --follow` には動いている最中に見える)。待ちが中断されたら、覚えていた時刻で閉じて、上の `Durable` の書き込みに入る(05 §18)。
- 結果・スキップの記録は、試行を変えない。
- `Reject`(66)では何も書かない(初期ステートも)。
- 書き込みの失敗(65)の表示の末尾に、ジョブの起動前なら `(ジョブは起動していません / the job was not started)`、起動後なら `(ジョブは実行されました / the job has already been executed)` が付く(ロケールに従う。英語/日本語の選択は 05 §5.5)。
- 結果を書けなかったときは、以降のジョブを起動せず、65 で終わる。

## 6. 読み込み(`read_state` / `read_state_raw`)の手順と異常系

### 6.1 手順

入力: 定義ファイルのパス、run ID(ファイル名側の期待値)。上から順に、最初に当てはまる結果で終わる。

| 順 | 処理 | 結果 |
|---|---|---|
| 1 | パスの種別(シンボリックリンクは辿る)を確認 | 存在しない → **空**(ステート無し)。取得失敗 → `unreadable`。通常のファイルでない(ディレクトリ、名前付きパイプ、デバイスへのリンクなど)→ `unreadable`(**開かない**) |
| 2 | ファイルを開く | 存在しない(1 のあとに消えた)→ **空**。その他の開く失敗(権限など)→ `unreadable` |
| 3 | 開いたハンドルの種別と大きさ(メタデータ)を確認 | 取得失敗・通常のファイルでない → `unreadable`。1 MiB(1,048,576 バイト)**超** → `tooLarge` |
| 4 | 上限 + 1 バイトまで読む(終わりのない入力でも止まる) | 読み取り失敗 → `unreadable`。読めたバイト数が上限超 → `tooLarge`(ちょうど上限は受理) |
| 5 | 長さ 0 | **空** |
| 6 | UTF-8 として解釈 | 失敗 → `corrupt`(理由 `UTF-8 の文字列ではありません`) |
| 7 | 書式として解析(最上位は項目の集合) | 失敗 → `corrupt`(`TOML として読めません`)。別の書式を採る実装も、構文の誤りの理由文はこの固定文を使う |
| 8 | `format_version` の確認(**ほかの検査より先**。将来の版が、未知の項目で corrupt にならないように) | 項目無し → `corrupt`(`format_version がありません`)。整数以外 → `corrupt`(`format_version が整数ではありません`)。整数で 1 以外(0 や 2 を含む)→ `versionMismatch`(`対応していない版です(reset が必要です)`) |
| 9 | 最上位に未知の項目がある | `corrupt`(`知らないキーがあります`) |
| 10 | `run_id` の取り出しと照合 | 型が文字列でない → `corrupt`(`値の型が誤っています`)。中身の `run_id`(無ければ「なし」)がファイル名の run ID(無ければ「なし」)と一致しない → `corrupt`(`run_id がファイル名の run ID と一致しません`) |
| 11 | 必須項目の取り出し: `definition_key`、`definition_path`、`pipeline_name`、`end_reached`、`completed`、`job_order`、`job`(この順) | 無い → `corrupt`(`必須のキーがありません`)。型が違う → `corrupt`(`値の型が誤っています`) |
| 12 | `job` の各要素を順に検査(§2.2、§2.2a、§2.3 のジョブごとの項) | 未知の項目、`id`/`status` 欠落、`status`/`skip_reason` の不正値、`exit_code` の型・範囲、`skip_reason` と `status` の不整合、`exit_code` と `status` の不整合、(v0.10.0 以降)試行の検査、動いたジョブに試行が無い → `corrupt` |
| 13 | `resume_job_id` の型 | 文字列でない → `corrupt` |
| 14 | 内容の矛盾(この順): ジョブIDの重複 → `job` の並びと `job_order` の不一致 → `resume_job_id` が `job_order` に無い → `completed` かつ `resume_job_id` あり | いずれも `corrupt`(それぞれ `ジョブIDが重複しています`、`job の並びが job_order と一致しません`、`resume_job_id が job_order にありません`、`completed と resume_job_id が両立しません`) |
| 15 | `read_state` のみ: `completed = true` | **空**(完了のまま残ったステート。ファイルは消さない) |

- 順 12 の `corrupt` の理由文(個別。いずれも種類は `corrupt`):

| 違反 | 理由 |
|---|---|
| `job` の要素がテーブルでない、`id`・`status` が文字列でない、`exit_code` が整数でない・32 ビット符号付き整数の範囲外、`skip_reason` が文字列でない | `値の型が誤っています` |
| `id` または `status` が無い | `必須のキーがありません` |
| 未知のキー | `知らないキーがあります` |
| `status` が 5 つの値以外 | `status の値が誤っています` |
| `skip_reason` が 2 つの値以外 | `skip_reason の値が誤っています` |
| `status = skipped` と `skip_reason` の有無の不整合 | `skip_reason が status と合いません` |
| `status` が pending / skipped なのに `exit_code` あり | `exit_code が status と合いません` |
| (v0.10.0 以降)試行の列が配列でない・要素が表でない、時刻が文字列でない | `値の型が誤っています` |
| (v0.10.0 以降)試行に未知のキー | `知らないキーがあります` |
| (v0.10.0 以降)試行に `started_at` が無い | `必須のキーがありません` |
| (v0.10.0 以降)時刻の形の誤り(§2.2a) | `時刻の書式が誤っています` |
| (v0.10.0 以降)最後でない試行に `ended_at` が無い | `終わりの時刻の無い試行が、最後の試行ではありません` |
| (v0.10.0 以降)動いたジョブ(success / warning / error)に試行が無い | `動いたジョブに試行の記録がありません(古い形式の可能性があります)` |

- `read_state_raw`(`watch` と `graph --state` が使う)は、15 を行わない(完了のステートもそのまま返す)。1〜14 は同じ。
- 検査の `run_id` 照合(10)は、`completed` の判定(15)より前なので、完了のステートでも run ID の食い違いは `corrupt`。
- ステートのパスが通常のファイルでない(書き手のいない名前付きパイプ、ディレクトリ、デバイスへのシンボリックリンクなど)とき、開かずに `unreadable`(理由は `開く、または読み取ることができません`)。名前付きパイプでも止まらない。v0.9.7 までは、先に開いたため、書き手のいない名前付きパイプのステートで止まり、終わりのないデバイスへのリンクは上限 + 1 バイトで止めて `tooLarge` だった。
- 読む権限のないステートは、1 MiB を超えていても `unreadable`(開く操作が大きさの確認より先に失敗する)。
- 読み取りでは、ファイルを**消さない・書き換えない**。
- 「空」= ステートが無いのと同じ扱い。呼び出し側は、すべて pending のステートとして扱い、最初の `Run` の試行を始めるときに、初期ステートに試行を足したものを書く(§5.1)。
- 順 8 の「整数以外」には、文字列・真偽・浮動小数点・配列などすべてを含む。

### 6.2 失敗の表示と終了コード

すべて終了コード 65。標準エラーの 1 行(固定の文 + パス + 固定の理由。入力の値・部品のエラー文は含めない):

```text
conductor: error: <ステートファイルのパス>: <kind の文>: <理由>[; <案内>]
```

| kind | 英語の文 | 日本語の文 | 理由の例(常に日本語) | 案内を付けるか |
|---|---|---|---|---|
| `unreadable` | `cannot read state file` | `ステートファイルを読めません` | `開く、または読み取ることができません` | 付ける |
| `tooLarge` | `state file is too large` | `ステートファイルが大きすぎます` | `大きさが上限(1 MiB)を超えています` | 付ける |
| `corrupt` | `state file is corrupt` | `ステートファイルが壊れています` | §6.1 の各理由 | 付ける |
| `versionMismatch` | `state file version is not supported` | `ステートファイルの版が合いません` | `対応していない版です(reset が必要です)` | 付ける |
| `writeFailed` | `cannot write state file` | `ステートファイルを書き込めません` | `書き込みに失敗しました` / `内容を TOML にできません` | 付けない(§5.1 の `(ジョブは…)` が付く) |
| `removeFailed` | `cannot remove state file` | `ステートファイルを削除できません` | `削除に失敗しました` | 付けない |

案内(読み込みのときだけ): run ID なし → `; run \`conductor reset\` to discard the state`(日本語 `; \`conductor reset\` でステートを初期化できます`)、run ID あり → `; run \`conductor reset --run-id <ID>\` to discard the state`(`<ID>` は文字どおりの `<ID>`。日本語は `; \`conductor reset --run-id <ID>\` でステートを初期化できます`)。

実例(英語ロケール):

```text
conductor: error: c2.toml.state: state file is corrupt: TOML として読めません; run `conductor reset` to discard the state
conductor: error: c2.toml.state: state file version is not supported: 対応していない版です(reset が必要です); run `conductor reset` to discard the state
conductor: error: c2.toml.r3.state: state file is corrupt: run_id がファイル名の run ID と一致しません; run `conductor reset --run-id <ID>` to discard the state
```

### 6.3 異常系の挙動の一覧(`run` / `pipeline`)

| 状況 | 結果 | ジョブの起動 | ステート |
|---|---|---|---|
| ファイルが無い | 空として続行 | する | 最初の `Run` の試行の前に、初期ステートに試行を足して書く(§5.1) |
| 長さ 0 | 空として続行 | する | 同上(上書き) |
| `completed = true` | 空として続行(定義との照合もしない) | する | 初期ステートで上書き |
| 読めない(権限等) | 65 | しない | 変更なし |
| 1 MiB 超 | 65 | しない | 変更なし |
| UTF-8 でない・構文の誤り・未知の項目・必須項目欠落・型の誤り・内容の矛盾(v0.10.0 以降は試行の誤りと、v0.9.9 までの試行の無いステートを含む) | 65(`corrupt`) | しない | 変更なし |
| `format_version` が 1 以外の整数 | 65(`versionMismatch`) | しない | 変更なし |
| 中身の `run_id` とファイル名の run ID が不一致、または片方だけ有る | 65(`corrupt`) | しない | 変更なし |
| 定義と食い違い(§7) | 65 | しない | 変更なし |
| 書き込み・削除の失敗 | 65 | §5.1 の表のとおり | 直前の内容のまま(書き込み)/ 残る(削除) |

どの異常でも、回復は `conductor reset`(または `--run-id`、`--all`)。`reset` は読まず検査もしないため、どんなファイルでも消せる(§8)。

## 7. 定義との整合性検査(`check_consistency`)

空でない(完了していない)ステートを読んだ後、`run`・`pipeline` の前処理(05 §5.1 の 7)で、定義と照合する。純粋な関数。

```text
if state.pipeline_name != definition.name:              Mismatch(PipelineName)
defined  = 定義のジョブIDの記述順の列
recorded = state.job_order
if defined == recorded:                                  Ok
if sorted(defined) == sorted(recorded):                  Mismatch(JobOrder)    # 並びだけが違う
else:                                                    Mismatch(JobIds)      # 追加・削除・改名
```

比較は文字列の完全一致(バイト列として。大文字小文字・正規化を区別する)。`sorted` は文字列の全順序(バイト列の辞書順など、一貫した順序)で、重複は取り除かず、並べ替えた列同士の一致を見る。

| 状況 | 結果 |
|---|---|
| パイプライン名が違う | `PipelineName` |
| ジョブID の集合が違う(追加・削除・改名。重複の有無も含め、並べ替えた列が違う) | `JobIds` |
| 集合は同じで記述順だけが違う | `JobOrder` |
| すべて同じ | `Ok` |

- `definition_key` と `definition_path` は照合に使わない(定義ファイルの置き場所を動かしても食い違いにしないため)。
- ジョブのコマンド、遷移、成功コード、リトライ設定などの違いは検知しない(IDと並びだけを見る)。
- `completed = true` のステートは「空」なので、照合しない。
- 食い違いのとき、ジョブは起動せず、ステートも変えず、65。標準エラー:

```text
conductor: error: <ステートファイルのパス>: state does not match the definition: <種類>; <案内>
```

  種類: `pipeline name` / `job ids` / `job order`(日本語: `パイプライン名` / `ジョブID` / `ジョブの並び`)。日本語の文は `ステートが定義と食い違っています`。案内は §6.2 と同じ(run ID あり/なしで切り替わる)。

## 8. 初期化(`reset`)

### 8.1 `conductor reset [--config <パス>] [--run-id <ID>]`

- 読まず、検査せず(破損・食い違い・版違い・大きさに関係なく)ステートファイルを削除する。定義ファイルは検証しない。
- 対象のファイル: run ID の決定(05 §6.2。`--run-id` があれば定義を読まない。なければ定義の `run_id_env` だけをゆるく読み、その環境変数を見る)で決まった 1 つ。
- 結果: ファイルが無ければ**成功**(0、何も表示しない)。削除が成功 → 0。失敗(ディレクトリ・権限等。「存在しない」以外)→ `removeFailed`、65。
- 完了のステートも消す。標準出力・標準エラーには何も出さない。
- パスがシンボリックリンクなら、リンク自体を削除する(OS の通常の削除の挙動。リンク先は消さない)。
- run ID の値が規則に合わなければ 68。

### 8.2 `conductor reset --all [--config <パス>]`

定義の全ステートを、run ID の有無によらず消す。環境変数は見ない(値の誤りも 68 にならない)。`--run-id` との併用は 68。

対象の判定(厳密):

1. 一覧にするのは、定義ファイルと同じディレクトリだけ(再帰しない)。
2. `<定義ファイル名>.state`(run ID なし): **通常のファイルのときだけ**(シンボリックリンクを辿らずに種別を判定する。シンボリックリンクは辿らず、消さない)、中身を読まずに削除。
3. `<定義ファイル名>.<run-id>.state`: 名前の `<run-id>` が有効な run ID(§1・05 §6.1)であるものだけが候補。名前は、定義ファイル名で始まり、続けて `.`、run ID、`.state`。候補をファイル名の昇順に処理する。
   - 通常のファイルでない(ディレクトリ、シンボリックリンク)→ 黙って除外。取得中に消えた → 除外。メタデータの取得が失敗 → `kept` に入れる。
   - 中身を見分ける(`inspect_run_state`):

| 中身 | 結果 |
|---|---|
| 開けない、1 MiB 超、読み取り失敗、UTF-8・構文・形式の誤り(`run_id` の不一致以外の `corrupt`)、`versionMismatch` | **残して**、名前を `kept` に入れる |
| 長さ 0 | 残す。`kept` に**入れない**(誰のものか分からない) |
| 読めて、中身の `run_id` が名前の run ID と一致(完了のままのものを含む) | **削除** |
| 読めるが、中身の `run_id` が無い、または値が違う(別の定義のステートでありうる) | 残す。`kept` に入れない(黙って残す) |

4. 一時ファイル(`.<ステート名>.tmp.*`)、ほかの名前のファイル、ほかのディレクトリは対象外。
5. 削除の失敗(「存在しない」以外)→ `removeFailed`、65(処理は途中で打ち切る)。ディレクトリ一覧の取得に失敗(ディレクトリが無い場合を除く)→ `unreadable`、65。ディレクトリが無ければ成功。

結果の出力: `kept` が空でなければ、標準エラーに警告(終了コードは 0)。消すものがなければ何も出さず 0。

```text
conductor: warning: kept state files that could not be read (remove one with `conductor reset --run-id <ID>`):
  c2.toml.r2.state
```

日本語: `conductor: warning: 読めなかったため、次のステートファイルは残しました(`conductor reset --run-id <ID>` で個別に消せます):`、続けて 2 スペースで字下げしたファイル名を 1 行ずつ。

実測(`c2.toml` に対して `reset --all`): run ID なしの `c2.toml.state` は削除、順序が壊れた `c2.toml.r2.state` は `kept`(警告)、`run_id = "r2"` を持つが名前が `r3` の `c2.toml.r3.state` は黙って残る、ほかの定義のステート `conductor.toml.r1.state` は対象外で残る。

## 9. 完了と `--remove-on-complete`

### 9.1 完了のステートの扱い

- 完了(`completed = true`)の条件は 05 §10。完了のステートは、`completed = true` のまま**残る**(自動では消えない)。書式は変わらない(`format_version = 1`)。
- 読み込み(`read_state`)は、完了のステートを「空」として返す(§6.1 の 15)。したがって次の `pipeline` は先頭から始まり、`run` は最初のジョブ以外が順序外(66)になる。
- `watch` は `read_state_raw` で完了のステートを読み、表の下に完了を示す行(英語 `completed`、日本語 `完了`)を足す。`no state (nothing has run yet)` を出すのは、ファイルが無いか長さ 0 のときだけ。壊れた完了のステートは 65。(v0.10.0 以降)`watch --follow` は、完了したステートを 1 回描いて 0 で終わる(04 §7.3)。
- `reset`・`reset --all` は完了のステートも消す。

### 9.2 削除の指定

| 項目 | 値 |
|---|---|
| オプション | `--remove-on-complete`(`run`・`pipeline` だけ。値を取らない。ほかのコマンドに付けると 68) |
| 定義 | `[pipeline]` の `remove_on_complete`(真偽値。省略時 false。真偽値でなければ定義の誤り 64) |
| 実効値 | `--remove-on-complete` があれば true、なければ定義の値。環境変数では切り替えない。オプションで false にする手段はない |

完了時の手順: 完了のステートを `Durable` で書く → 実効値が真なら `reset_state`(run ID に応じたファイルを削除。存在しなくても成功)→ 成功なら 0(`run` ではジョブの終了コード)。削除に失敗したら 65(完了のステートは `completed = true` のまま残る。`watch` は完了として表示する)。

`run` では、完了の契機が「スキップの記録」のときも同様に、書き込みの後に削除する。

## 11. 並行実行・排他・持続性

- **排他制御はしない**(ファイルロック、PID ファイルなし)。同じ定義(同じ run ID)で複数の conductor を同時に動かすと、それぞれが読んで書き、後に書いた方が勝つ。書き込み自体は原子的なので、ファイルが壊れることはないが、記録は失われうる。同時の実行は避けること。
- 別の実行単位(run)で同じ定義を並行して使うときは、run ID でステートを分ける(§1)。run ID ごとに独立したファイルと再開位置を持つ。
- **at-least-once**: ジョブの終了と、結果の書き込みのあいだに conductor が落ちると、ジョブは未実行として扱われ、再実行されうる。
- **リトライの回数はステートに書かない**(書式に項目がない)。再開は、そのジョブを最初の実行から数え直す。(v0.10.0 以降)試行ごとの開始と終了の時刻は書く(§2.2a)ので、試行の数は時刻の並びから分かるが、回数を数える値としては使わない。再開で足す試行は、前の試行を消さずに後ろに足す。
- (v0.10.0 以降)試行の開始の書き込み(`Fast`)は、試行ごとに 1 回ある。`watch` はこの書き込みにより、動いているジョブの開始の時刻を読める。
- ステートは、定義ファイルのあるディレクトリに作られる。書き込めないディレクトリでは、最初のジョブの前に 65 で止まる(初期ステートが書けない)。
- 古い run のステートは自動では消えない。`reset --all` か、`--remove-on-complete` で片づける。

## 13. 実装に任せてよい点と未確認

実装に任せてよい点:

- 保存の書式(§4 は参照。共有しないなら別の書式でよい)。項目の並び順、空白、文字列のエスケープの方式(書式として正しければよい)。

- 特殊な文字(バックスラッシュ、引用符、制御文字)を含む文字列を、現行の実装が、どの表記(基本文字列 / リテラル文字列)で書き出すか。読み込みは書式として正しければ受け付けるので、再実装は、書式として正しい出力ならよい。

## 14. ファイルの排他的な作成(`init` が使う。v0.9.0 以降)

ステートの書き込みとは別の部品だが、同じ「一時ファイルから置き換える」作り方(§5 の一時ファイル、書き込み、閉じる、名前の付け替え)を共有するので、ここに置く。

ファイルの作成の入力: パス、内容(バイト列)、`force`(真偽)。出力: 成功(`created`: 新規に作った、`replaced`: `--force` で、既にあったファイルを置き換えた)、または誤り(下の 5 種)。

| 誤り | 内容 |
|------|------|
| `alreadyExists` | 既にある(`force` なし)。終了コード 69 |
| `parentMissing` | 親のディレクトリが無い(作らない) |
| `isDirectory` | 作る先が、ディレクトリ |
| `permissionDenied` | 書く権限がない |
| `otherIo` | そのほかの入出力の誤り |

**`force = false`(新規)**:

1. 「ファイルがなければ作る」を **1 回の操作**で行う呼び出し(排他的な作成。既にあれば失敗)で、パスを開く。失敗したら、パスの今の姿(シンボリックリンクをたどらないメタデータ)で分類する: ディレクトリなら `isDirectory`、ファイル、またはシンボリックリンク(宙に浮いたものを含む)なら `alreadyExists`、メタデータも取れなければ、元の誤りの種類(「存在しない」→ `parentMissing`、「権限がない」→ `permissionDenied`、そのほか → `otherIo`)。OS によって、ディレクトリへの排他的な作成の誤りの種類が違うため、この分類にする。
2. 全内容を書き、flush する。閉じてから(Windows は、開いたままのファイルを消せない)、書き込みに失敗していれば、作ったファイルを消して `otherIo`。成功は `created`。

**`force = true`(置き換え)**:

1. 親のディレクトリ(パスの親。空なら `.`)のメタデータを取る。取れなければ種類で分類(「存在しない」→ `parentMissing`、「権限がない」→ `permissionDenied`、そのほか → `otherIo`)。ディレクトリでなければ `otherIo`。
2. パスの、シンボリックリンクをたどらないメタデータ: ディレクトリなら `isDirectory`。ファイルまたはシンボリックリンクなら `existed = true`(シンボリックリンクは、リンクそのものを置き換える)。無ければ `existed = false`。
3. 同じディレクトリに、一時ファイルを新規作成で作る(名前 = `.<ファイル名>.tmp.<プロセス識別子>.<ナノ秒>.<連番>`。§5 と同じ作り方。名前が重なったら連番を進めて、最大 16 回)。作れなければ、種類で分類する。
4. 全内容を書き、flush し、閉じて、名前の付け替えで置き換える。書き込みか付け替えに失敗したら、一時ファイルを消す(権限がなければ `permissionDenied`、そのほかは `otherIo`)。成功は、`existed` なら `replaced`、でなければ `created`。

- **親のディレクトリは作らない**。内容は、そのまま書く(改行を変換しない)。同期はしない。
- 表示は、誤りの種類ごとの固定の文とパスだけで、OS のエラーの文を含めない(08 の 4.13)。
- 置き換えたファイルは、新しい権限と所有者になる(§5 の権限の項と同じ)。Windows では、読み取り専用のファイルは置き換えられず、UNIX 系では置き換えられる。
- **既知の限界**: 新規の作成は、ファイルを作ってから書くので、その短い間と、強制終了のあとには、空のファイルが見えることがある(その場合、2 回目の `init` は `alreadyExists` になる。`--force` で直せる)。
