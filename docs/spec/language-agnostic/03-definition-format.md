# 03. 定義ファイルの書式と検証

この文書は、`conductor` の定義ファイル(既定の名前は `conductor.toml`)の書式と、読み込み時の検証を、実装言語に依存しない形で定める。この文書だけで、任意の言語・任意のライブラリ(または自前の構文解析)により、同じ受理・拒否・エラー(種類、文言、行番号)を返す読み込み処理を実装できることを目標とする。

- 定義ファイルの形式は **TOML だけ**である。YAML の定義は読めない(YAML で書きたいときは、[09. 変換器](09-converter.md)で TOML にしてから使う)。
- 検証は、見つけた誤りを**まとめて**返す。ただし、早い段階の誤り(取り込み、文法、深さ、版)は 1 件だけで打ち切る(第 2 節)。
- 定義の内容は、読み込みでは実行も評価もしない。`command` の文字列は、そのまま保持する。
- 確認できなかった点は「未確認」と書く。
- 「必須」と書いた挙動は、利用者から見える結果(受理/拒否、エラーの種類・文言・行番号、取り込み後の値)であり、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、利用者から見える結果が変わらない範囲で、実装が選んでよい。
- このツールの終了コード、エラー行の標準エラーへの出し方は [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方は [08. 出力と多言語対応](08-output-and-i18n.md) に従う。この文書は、エラーの内容(種類・位置・理由)までを定める。

## 1. 記法と用語

| 語 | 意味 |
|----|------|
| 文字 | Unicode のスカラー値(コードポイント。サロゲートを除く)。「N 文字」は、この単位で数える(UTF-8 のバイト数でも、書記素でもない)。 |
| 空白を取り除く(trim) | 文字列の先頭と末尾から、Unicode の White_Space 属性を持つ文字(U+0009〜U+000D、U+0020、U+0085、U+00A0、U+1680、U+2000〜U+200A、U+2028、U+2029、U+202F、U+205F、U+3000)を取り除く。「空白だけ」は、取り除いた結果が空文字列になること。 |
| 位置 | 入力の先頭からのバイト位置(0 始まり、UTF-8 のバイト列で数える。BOM があれば、BOM も数える)。 |
| 行 | 行番号。1 始まり。第 10 節の規則で、位置から求める。 |
| 値の型 | 文字列(string)、整数(integer)、浮動小数(float)、真偽値(boolean)、日時(datetime)、配列(array)、テーブル(table。キーと値の対応)。TOML の値は、この 7 種のいずれか。 |
| テーブルの配列 | 要素がすべてテーブルである配列(`[[job]]` の繰り返しで書くもの、または `[{...}, {...}]` と書くもの)。 |
| 誤り | エラーの 1 件。種類(`kind`)、行(なしもある)、理由(`reason`)をもつ(第 9 節)。 |
| 受理 | その値や書き方を誤りなく読み込むこと。拒否はその逆。 |

## 2. 処理の段階と打ち切り

`load(path, expected_pipeline_name)` は次の順に処理する。前の段階で失敗したら、そこで打ち切り、**その 1 件だけ**を返す(後ろの段階は実行しない)。最後の Walk だけが、複数の誤りを返す。

| 段階 | 失敗の種類(`kind` の識別子) | 返る誤りの数 |
|------|------------------------------|--------------|
| 1. Intake(場所の決定、ファイルの読み取り) | `fileMissing` / `unreadable` / `tooLarge` | 1 |
| 2. Parse(TOML の文法) | `syntax` | 1 |
| 3. Depth(入れ子の深さ) | `syntax` | 1 |
| 4. VersionCheck(`format_version`) | `versionMissing` / `versionUnsupported` | 1 |
| 5. Walk(構造、型、遷移、終了コード、名前) | 第 9.3 節の種類のうち該当するもの | 1 件以上(位置の順) |

`parse(text, file_label, expected_pipeline_name)` は、段階 2〜5 を文字列に対して行う(ファイルに触れない)。`file_label` は、エラーの表示に使うファイル名である。

- `expected_pipeline_name`(`pipeline` コマンドで渡されたパイプライン名)が無いときは、名前の照合をしない。
- 検証に成功したときだけ、定義(第 11 節)を返す。誤りが 1 件でもあれば、定義は返さない。
- 版の確認(段階 4)に通らないと、構造の検査(段階 5)は一切行わない。たとえば `format_version` が無い定義に、未知のキーや型の誤りがあっても、返るのは `versionMissing` の 1 件だけである。
- 文法の誤り(段階 2)は版の確認より先である。`format_version = = 1` は `syntax` である。

## 3. 取り込み(Intake)

### 3.1 場所

- 定義ファイルのパスの指定(`--config`)があれば、それを使う。なければ、カレントディレクトリの `conductor.toml`。
- 表示用のファイル名は、パスを文字列にしたもの(与えられた表記のまま。正規化しない)である。

### 3.2 読み取りの手順と失敗

次の順に調べる。最初に当てはまったもので失敗する。

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルの情報(種別・大きさ)の取得で「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | 同、権限がない | `unreadable` | `読み取りの権限がありません` |
| 3 | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 4 | 通常のファイルでない(ディレクトリなど) | `unreadable` | `通常のファイルではありません` |
| 5 | 取得した大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `ファイルの大きさが上限(1 MiB)を超えています` |
| 6 | ファイルを開けない(権限) | `unreadable` | `読み取りの権限がありません` |
| 6' | ファイルを開けない(その他) | `unreadable` | `読み取りに失敗しました` |
| 7 | 読み取りの途中の失敗 | `unreadable` | 権限の問題なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 8 | 読み取った結果が上限を超える(順 5 のあとに大きくなった場合) | `tooLarge` | 順 5 と同じ |
| 9 | UTF-8 として解釈できない | `unreadable` | `文字コードが UTF-8 ではありません` |

- 上限は **1 MiB = 1,048,576 バイトちょうどまで受理**し、1 バイトでも超えると `tooLarge`。読み取りは「上限 + 1 バイト」までしか行わない(巨大なファイルを全部は読まない)。
- 空のファイル(0 バイト)は、空の文字列として読めて、次の段階へ進む(結果は、`format_version` が無いので `versionMissing`)。
- 順 5 の大きさの確認は UTF-8 の確認(順 9)より先なので、1 MiB を超えて UTF-8 でないファイルは `tooLarge` である。
- いずれも、行番号は付かない。
- シンボリックリンクは、リンク先の情報で判定する(リンクを辿る)。
- OS による権限・種別の判定の細部(Windows など)は、実装に任せてよい。必須なのは、上の表の条件の順序と、各理由の文言である。

## 4. 受理する文法(Parse)

定義ファイルは、TOML の**部分集合**で書く。この節は、受理しなければならない文法(4.2〜4.6)、拒否しなければならない書き方(4.7)、受理してもしなくてもよい拡張(4.8)を定める。TOML の読み取りライブラリを使ってよいが、ライブラリが 4.2〜4.7 と違う結果を返すときは、この文書の規定が優先する(4.8 の任意の拡張は、ライブラリの挙動のままでよい)。

文法の根拠となる外部の規格は TOML v1.0.0 である。この節で明示していない細部(エスケープの正確な意味、日時の細かい書式など)は、TOML v1.0.0 の規定に従う。

### 4.1 入力の全体

- 入力は UTF-8 のテキスト。先頭の U+FEFF(BOM)があれば、無視する(位置には数える)。
- 改行は LF(U+000A)または CRLF(U+000D U+000A)。**CR だけの改行は拒否**する(`syntax`)。1 つのファイルに LF と CRLF が混在してもよい。
- 空白は、半角スペース(U+0020)とタブ(U+0009)だけ。それ以外(垂直タブ U+000B、全角スペース U+3000 など)を、トークンの間に置くことは拒否(`syntax`)。
- 制御文字の禁止: コメントの中、および文字列の中では、タブ以外の制御文字(U+0000〜U+0008、U+000A〜U+001F、U+007F)を直接書くことはできない(`syntax`)。ただし、複数行の文字列の中の改行(LF、CRLF)は許す。
- 空の入力、コメントと空行だけの入力は、空のテーブルとして受理する。

### 4.2 コメントと文

- `#` から行末までがコメント(値・見出しの後ろにも書ける)。コメントの中身は、4.1 の制御文字の禁止を除き、制限しない。
- 1 行に 1 つの「文」を書く。文は、キー/値の組(4.3)、テーブルの見出し(4.5)、テーブルの配列の見出し(4.5)のいずれか。文の後ろには、空白とコメントだけを置ける。同じ行に 2 つの文を置く(`x = 1 y = 2`)ことは拒否(`syntax`)。
- 行頭・行末の空白(スペース、タブ)は無視する。インデントに意味はない。

### 4.3 キーと、キー/値の組

```
キー/値の組  = キー  空白*  "="  空白*  値
キー         = 単純キー ( 空白* "." 空白* 単純キー )*       ← ドットキー
単純キー     = ベアキー | 基本文字列 | リテラル文字列
ベアキー     = [A-Za-z0-9_-]+
```

- ベアキーは、ASCII の英数字、`_`、`-` の 1 文字以上。それ以外の文字(`.`、空白、非 ASCII など)を含むキーは、引用符で囲む(`"a b"`、`'a.b'`、`"é"`)。空のキー(`"" = 1`)は受理する。
- 引用符つきのキーの中身は、基本文字列(4.4.1)・リテラル文字列(4.4.2)と同じ規則(エスケープ、禁止文字)で読む。**複数行文字列はキーにできない**(拒否、`syntax`)。
- ドットキー(`a.b.c = 1`)は、`a` のテーブルの中の `b` のテーブルの中の `c` に値を置くことと同じ。`.` の前後には空白を置いてよい(`a . b = 1`)。
- キーの無い組(`= 1`)、値の無い組(`x =` で行が終わる)、`=` の後ろから値までの改行(値は `=` と同じ行から始まる)は拒否(`syntax`)。
- **値は `=` と同じ行で始まる**。ただし、配列(4.4.6)とインラインテーブル(4.4.7)は、複数行にまたがってよい(インラインテーブルの複数行は 4.8 の任意の拡張)。

### 4.4 値

#### 4.4.1 基本文字列(`"..."`)

- 1 行に収まる。中に、禁止文字(4.1)と、エスケープされていない `"`、`\` を直接書けない。
- 受理するエスケープ(必須): `\b`(U+0008)、`\t`、`\n`、`\f`(U+000C)、`\r`、`\"`、`\\`、`\uXXXX`(16 進 4 桁)、`\UXXXXXXXX`(16 進 8 桁)。`\u` と `\U` の値は Unicode のスカラー値でなければならない(サロゲート U+D800〜U+DFFF と、U+10FFFF を超える値は拒否。`syntax`)。16 進の桁は大文字・小文字のどちらでもよい。
- 上のほかのエスケープ(`\q`、`\0`、`\ ` など)は拒否(`syntax`)。ただし `\e`(U+001B)と `\xHH`(U+00HH)は、4.8 の任意の拡張。
- 閉じていない文字列は拒否(`syntax`)。

#### 4.4.2 リテラル文字列(`'...'`)

- 1 行に収まる。エスケープは無い(`\` はそのままの文字)。`'` と禁止文字(4.1)は直接書けない。

#### 4.4.3 複数行の基本文字列(`"""..."""`)

- 開く `"""` の直後がすぐに改行(LF または CRLF)なら、その 1 つの改行は値に含めない。
- 中に、改行(値には**書かれたとおりの改行を保持する**。CRLF は CRLF のまま、LF は LF のまま。変換しない)、エスケープ(4.4.1 と同じ)、1 個または 2 個の連続した `"` を書ける。3 個以上の連続した `"` は、文字列の終わりになる。閉じる `"""` の直前に、`"` を 1 個または 2 個付けて書ける(`""""` で 1 個の `"` + 終わり、`"""""` で 2 個の `"` + 終わり)。それ以上は拒否。
- 行末の `\`(その後に空白と改行だけが続く)は「行の継続」で、その `\`、後続の空白、改行、次の行以降の空白・改行(次の空白でない文字まで)を、値から取り除く。
- 禁止文字(4.1)は、改行以外は直接書けない。閉じていないときは拒否(`syntax`、行は入力の末尾の行。第 4.9 節)。

#### 4.4.4 複数行のリテラル文字列(`'''...'''`)

- 開く `'''` の直後の 1 つの改行は値に含めない。中身は、書かれたとおり(エスケープなし。改行は保持する)。1 個または 2 個の連続した `'` を書ける。閉じる `'''` の直前に `'` を 1 個または 2 個付けてよい。3 個以上の連続した `'` は終わりになる。

#### 4.4.5 数値・真偽値・日時

| 型 | 受理する書式(必須) | 拒否する書式の例 |
|----|--------------------|------------------|
| 真偽値 | `true`、`false`(小文字だけ) | `True`、`TRUE`、`yes` |
| 整数(10 進) | `[+-]?` に続けて、`0`、または `[1-9]` から始まる数字の列。数字の間に 1 個の `_` を置ける(`1_000`)。`+0`、`-0` は受理(値 0) | `01`、`00`、`1__0`、`1_`、`_1`、`+`、`-` |
| 整数(16・8・2 進) | `0x` + 16 進数字(`0-9a-fA-F`)、`0o` + 8 進数字、`0b` + 2 進数字。数字の間に `_` を置ける。接頭辞は小文字だけ。**符号は付けない**。先頭に 0 を並べてよい(`0x00ff`) | `+0x1`、`0XFF`、`0o8`、`0b102`、`0x`、`0x_1` |
| 浮動小数 | 整数部(10 進の整数の書式、符号つき可)に、小数部(`.` + 1 桁以上の数字)と/または指数部(`e` または `E` + 符号つき可の数字の列)を続けたもの。数字の間に `_`。特別な値 `inf`、`+inf`、`-inf`、`nan`、`+nan`、`-nan`(小文字だけ) | `.5`、`5.`、`1.e3`、`1e`、`1e_3`、`Inf`、`NaN` |
| 日時 | RFC 3339 の、オフセットつき日時(`1979-05-27T07:32:00Z`、`1979-05-27T00:32:00.999999-07:00`)、ローカル日時(`1979-05-27T07:32:00`)、ローカル日付(`1979-05-27`)、ローカル時刻(`07:32:00`、`07:32:00.999`)。日時の区切りは `T`、`t`、または半角スペース 1 個を受理。`Z` は `z` でもよい。月日・時分秒の範囲を外れるもの(`2024-02-30`、`T25:00:00Z`)は拒否(`syntax`) | `2024-02-30`、`1979-05-27T25:00:00Z` |

- 整数は**任意の桁数の書式**として受理する(読み取りの段階では、範囲を判定しない)。64 ビット符号つき整数の範囲(-9,223,372,036,854,775,808〜9,223,372,036,854,775,807)に収まらない整数は、「範囲外の整数」という印をつけて、整数の型のまま扱う。定義の検査(第 5〜8 節)が、値を使う箇所で範囲外として拒否する(例: `format_version = 99999999999999999999` は `syntax` ではなく `versionUnsupported`、`success_exit_codes = [99999999999999999999]` は要素の `typeMismatch`)。定義のどのキーでも使われない場所にある範囲外の整数(例: 未知のキーの値)は、そのキーが `unknownKey` になるだけで、`syntax` にはならない。**変換器の TOML 読み取りは、これと異なり、範囲外の整数を `syntax` にする**([09. 変換器](09-converter.md)第 4 節)。
- 浮動小数は、値の範囲を判定しない(`1e400` は、読み取りでは拒否されない。型は浮動小数)。定義のどのキーも浮動小数を受け付けないので、置いた場所に応じて、型の誤り(`typeMismatch`)や未知のキー(`unknownKey`)になる。
- 日時の値は、読み取りは通る。定義のどのキーも日時を受け付けないので、同様に、型の誤りや未知のキーになる。

#### 4.4.6 配列(`[...]`)

- 要素を `,` で区切る。末尾に `,` を 1 個置いてよい(`[1, 2,]`)。`[,]`、`[1,,2]` は拒否(`syntax`)。
- 要素の型は混在してよい(`[1, "a", [2]]`)。入れ子の配列を書ける。
- 配列は複数行にまたがってよい。要素の前後・`,` の前後・`]` の前に、空白、改行、コメントを置ける。
- 閉じていない `[` は拒否(`syntax`)。

#### 4.4.7 インラインテーブル(`{...}`)

- `{ キー/値の組, キー/値の組, ... }`。キーにドットキーを使える(`{ a.b = 1 }`)。空のテーブル `{}` を受理する。
- 必須の書式は **1 行の中に収まるもの**で、末尾にカンマを置かない形(`{ x = 1, y = 2 }`)。インラインテーブルの中の改行・末尾のカンマは、4.8 の任意の拡張。
- 同じキーを 2 回書くこと(`{ x = 1, x = 2 }`)は拒否(`syntax`)。
- インラインテーブルは**閉じた値**である。定義した後で、`[a.y]` の見出しや `a.y = ...` のドットキーで、中身を増やすことは拒否(`syntax`)。

### 4.5 テーブルの見出しと意味規則

```
テーブルの見出し           = "["  空白* キー 空白* "]"     ← 行頭(前に空白だけ)から始まる
テーブルの配列の見出し     = "[[" 空白* キー 空白* "]]"
```

- 見出しの中のキーは、ドットキー(4.3)と同じ書式(`[a.b]`、`[ "a b" . c ]`)。`[` と `]` の内側に空白を置ける(`[ pipeline ]`)。`[[` と `]]` は、それぞれ 2 文字を連続して書く(`[ [a] ]` は拒否)。
- 見出しは、以降のキー/値の組を、次の見出しまで、そのテーブルの中に置く。見出しより前の組は、根のテーブルに置く。
- テーブルの配列の見出し `[[x]]` は、`x` の配列に新しい要素(空のテーブル)を 1 つ加え、以降の組と、`[x.y]` のようなサブテーブルの見出しを、その最後の要素に属させる。したがって、`[job.retry]` は、直前の `[[job]]` の要素に属する。`[[job.transitions]]` も同様。
- 途中の名前(`[a.b.c]` の `a` と `b`)が未定義のときは、暗黙のテーブルとして作る。

**意味規則(次を破る入力は、すべて `syntax`)**。以下は TOML v1.0.0 の規定の要約で、同じ結果になるように実装する。

| 規則 | 例(拒否) |
|------|-----------|
| 同じキーを同じテーブルに 2 回定義しない(値の型・書式によらない) | `a = 1` と `a = 2` / `a = 1` と `a = 1` |
| 同じテーブルの見出しを 2 回書かない | `[a]` を 2 回 |
| 値(スカラー、配列、インラインテーブル)として定義されたキーを、テーブルの見出しやドットキーのテーブルとして使わない | `a = 1` のあと `[a]` / `a = 1` のあと `[a.b]` |
| 静的な配列(`a = [1]`)を、`[[a]]` で伸ばさない | `a = [1]` のあと `[[a]]` |
| `[[a]]` で作られた配列を、`[a]` のテーブルとして再定義しない(逆も) | `[[a]]` のあと `[a]` |
| ドットキー・インラインテーブルで定義されたテーブルを、後から `[見出し]` で再定義・追加しない | `a.b = 1` のあと `[a]` / `a = {x = 1}` のあと `[a.y]` |
| 見出しで暗黙に作られたテーブルを、**あとから明示的に 1 回だけ**定義することは受理 | `[a.b]` のあと `[a]`(受理)、さらに `[a]`(拒否) |

- 受理する例: `[a.b]` `x=1` のあと `[a]` `y=1`(`a` は暗黙のテーブルだったので、明示してよい)。

### 4.6 受理する文法の一覧(早見)

必須で受理するもの: コメント、基本/リテラル/複数行の基本/複数行のリテラルの文字列、10・16・8・2 進の整数(`_` 区切り)、浮動小数、真偽値、日時 4 種、配列(複数行・コメント・末尾カンマ)、1 行のインラインテーブル、ベアキー・引用符つきのキー・ドットキー、テーブル `[a.b]`、テーブルの配列 `[[a.b]]`、BOM、LF と CRLF の改行。

### 4.7 拒否する文法の一覧

次は、すべて `syntax` で拒否する(必須)。

- 4.1 の禁止(CR だけの改行、タブ以外の制御文字、垂直タブなどの空白)。
- キーの重複、見出しの重複、4.5 の意味規則の違反。
- 文法に合わない記述: 値のないキー、`=` が 2 つ(`b = = 2`)、閉じていない文字列・配列・見出し(`[pipeline`)・インラインテーブル、未知のエスケープ、不正な数値(`0b102`、`01`、`1_`、`1__0`、`0x`、`+0x1`、`.5`、`5.`、`1e`)、不正な日時、`True` など大文字の真偽値、1 行に 2 つの文。
- 日時で、`1979-05-27 07:32:00Z`(スペース区切り)は**受理**であること(拒否と混同しない)。

### 4.8 受理してよい拡張(任意)

次は、仕様として必須にしない。受理しても、拒否(`syntax`)してもよい。一貫していれば、どちらでもよい(テストは、これらを使う定義を含まない)。

| 拡張 | 例 |
|------|----|
| インラインテーブルの中の改行と末尾のカンマ | `x = {a = 1,\n b = 2,}` |
| エスケープ `\e`(U+001B)、`\xHH`(U+00HH) | `"\e[0m"`、`"\x41"` |
| 秒を省略した時刻・日時 | `07:32`、`1979-05-27T07:32Z` |

参考: このツールの元の実装は、上の 3 つをすべて受理する。

### 4.9 文法の誤りの表示

文法の誤りの表示は固定で、読み取りライブラリのエラー文は使わない。

| 項目 | 値 |
|------|----|
| `kind` | `syntax` |
| 理由 | `TOML の文法に誤りがあります` |
| 行 | 次の規則(必須の部分と、ベストエフォートの部分) |

誤りの文には、入力の値(キー名や値)を含めない。

**行の規則**。誤りの位置を、「入力の先頭からのバイト位置」で決め、第 10 節の規則で行にする。位置の決め方(必須。次の表の例で確認済み):

| 誤り | 位置 | 例 |
|------|------|----|
| キー/値の組の中の文法の誤り(`=` の重複、値の書式など) | 受理できなくなった最初の文字 | `b = = 2` は、その行 |
| キーの重複 | 2 つ目のキー(ドットキーなら、その組の先頭) | `a = 1` を 2 回書くと、2 回目の行 |
| 見出しの重複 | 2 回目の見出し | `[a]` を 2 回書くと、2 回目の `[a]` の行 |
| 閉じていない見出し | 見出しを書いた行(`[pipeline` + 改行) | `format_version = 1\n[pipeline\n` は 2 行目 |
| 閉じていない 1 行の文字列 | その文字列の行 | `x = "abc` + 改行は、その行 |
| 閉じていない配列 | 配列の中で受理できなくなった最初の文字(次の文として現れた `y = 1` の `y` など) | `x = [1,` / `2` / `y = 1` と続く入力は、`y` の行(`x` の 2 行後) |
| 閉じていない複数行の文字列 | 入力の末尾の位置(末尾の改行の後ろの空の行も 1 行と数える) | 5 行 + 末尾の改行の入力で 6 行目 |
| 値がない(`x =` の後が改行) | `x =` を書いた行 | `format_version = 1` / `x =` / `y = 1` は 2 行目 |
| 4.5 の意味規則の違反 | 違反した定義の先頭(見出しやキー)の行 | `a = 1` のあと `[a]` の `[a]` の行 |

上の表のとおりに行が決まらない細かい場合(エスケープの途中、日時の途中など)は、**誤りの種類・理由は必須、行は「その誤りが書かれた行」に一致させる**。同じ誤りの位置が行をまたぐ書き方(複数行の文字列の途中)では、行は実装に任せてよい(未確認)。

例(必須): `"a = 1\nb = = 2\n"` は 2 行目。`"format_version = 1\n[pipeline\n"` は 2 行目。`a = 1` を 2 回書いた場合は、2 回目の行。`[a]` を 2 回書くと、2 回目の `[a]` の行。CRLF の入力でも、LF の数で数えた行になる。

## 5. 入れ子の深さの制限(Depth)

Parse に成功した値の木を走査し、入れ子の深さを数える。

- テーブル(見出し・ドットキー・インラインテーブルによるもの。暗黙に作られるテーブルも)、配列は、それぞれ**1 段**と数える。**テーブルの配列は、配列が 1 段、その要素のテーブルが 1 段で、合計 2 段**である(`[[a]]` だけで 2 段)。スカラーは数えない。**根のテーブルそのものは数えない**。
- 根の直下のコンテナ(テーブルまたは配列)の深さを 1 とし、その子のコンテナは 2、…と数える。**32 段まで受理**し、**33 段目を拒否**する。
- 拒否の誤り: `kind` は `syntax`、理由は `入れ子が深すぎます(上限は 32 段)`、行は、33 段目になったコンテナの先頭の位置の行。走査は、深さ優先で、テーブルでは各エントリを、そのテーブルが現れた順に調べる。上限を超えた最初のコンテナで打ち切る。
- 数え方の例:

| 書き方 | 段数 | 受理/拒否 |
|--------|------|-----------|
| `a = [[[...]]]`(`[` を n 個) | n | 32 個は受理、33 個は拒否 |
| `a = {b = {b = ... 1}}`(`{` を n 個) | n | 32 個は受理、33 個は拒否 |
| `[a.a.a....a]`(キーが n 個の見出し) | n | 32 個は受理、33 個は拒否 |
| `[[a.a.....a]]`(キーが n 個の見出し) | n + 1(途中のテーブル n - 1 段、配列 1 段、要素 1 段) | 31 個は受理(32 段)、32 個は拒否(33 段。行は見出しの行) |
| `[[a]]` / `[[a.b]]` / `[[a.b.c]]` の連続 | 2 / 4 / 6 | 受理 |

- 位置の取り方: 暗黙に作られたテーブルの位置は、その最初の見出し・最初のドットキーの先頭(見出しの行、ドットキーの行)とする。ただし、33 段目が暗黙のテーブルになる細かい場合の行は、**未確認**。33 段目が見出しの行なら、その行になる(上の表の例で確認済み)。
- 数千〜数十万段の入れ子の入力でも、異常終了(スタックあふれなど)せず、`syntax` の 1 件で返らなければならない(必須)。ただし、この段階の拒否になるか、4.9 の文法の誤り(理由が `TOML の文法に誤りがあります`)になるかは、実装に任せてよい(種類はどちらも `syntax`)。入れ子の数え方は、読み取りの再帰を使わず、明示のスタックなどで行うとよい(実装に任せてよい点)。
- 深さが 32 以内でも、根に未知のキーがあれば、後続の段階で別の誤りになる(例: `a = [[...32 段...]]` だけの定義は、版の確認で `versionMissing` になる)。

## 6. 書式の版(VersionCheck)

根の `format_version` を確認する。

| 状況 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `versionMissing` | なし | ``` `format_version` が必要です(対応する版は 1 です) ``` |
| 整数でない(文字列、浮動小数、真偽値、配列など) | `versionUnsupported` | 値の行 | ``` `format_version` は整数で書きます(対応する版は 1 です) ``` |
| 整数だが 1 でない(0、-1、2、9、範囲外の整数) | `versionUnsupported` | 値の行 | `この版には対応していません(対応する版は 1 です)` |

- 対応する版は **1 だけ**。`format_version = 1` を受理する。16 進などの書き方(`0x1`)でも、値が 1 なら受理する。
- 版が 1 のとき、取り込み後の定義の `format_version` は 1 になる。
- 位置(行)は、値の先頭(第 10 節)。

## 7. 定義の構造(Walk)

根のテーブルは、次のキーだけを持てる。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `format_version` | 整数 | 必須 | 第 6 節 |
| `pipeline` | テーブル | 必須 | 第 7.1 節 |
| `job` | テーブルの配列 | 必須(1 つ以上) | 第 7.2 節 |

許されていないキー(上の 3 つ以外)は、`unknownKey` である。以前の版の `[[jobs]]` も未知のキーとして拒否される(``キー `jobs` は定義にありません``)。`unknownKey` の理由は、`` キー `<キー名>` は定義にありません `` の形(`<キー名>` は整形したキー名)で、キー名の整形は第 9.2 節。位置はそのキーの先頭。

### 7.1 `[pipeline]`

| キー | 型 | 必須 | 既定値 | 検査 |
|------|----|------|--------|------|
| `name` | 文字列 | 必須 | なし | 空白だけ(trim して空)なら `emptyField` |
| `description` | 文字列 | 任意 | なし | 型だけ |
| `run_id_env` | 文字列 | 任意 | なし(実行時の既定は環境変数 `CONDUCTOR_RUN_ID`) | 名前の形(下記) |
| `remove_on_complete` | 真偽値 | 任意 | `false` | 型だけ |

- 許されたキー以外は `unknownKey`(例: `owner`、`remove_on_complet`)。
- `name` が無い: `typeMismatch`、行は `[pipeline]` のテーブルの先頭、理由 ``必須の値 `name` がありません``。文字列でない: `typeMismatch`、値の行、理由 ``` `name` は文字列で書きます ```。`description` が文字列でない: `typeMismatch`、値の行、理由 ``` `description` は文字列で書きます ```。`run_id_env` が文字列でない: `typeMismatch`、値の行、理由 ``` `run_id_env` は文字列で書きます ```。`remove_on_complete` が真偽値でない: `typeMismatch`、値の行、理由 ``` `remove_on_complete` は真偽値(`true` または `false`)で書きます ```。
- `run_id_env` の名前の形: 1 文字以上で、先頭が ASCII の英字(`A-Za-z`)または `_`、2 文字目以降が ASCII の英数字(`A-Za-z0-9`)または `_`。受理: `A`、`_`、`_a1`、`GITHUB_RUN_ID`。拒否(`invalidEnvName`): `""`、`1A`、`A-B`、`A B`、`A=B`、`é`、`A.B`、NUL を含む文字列。文字列でない値(整数など)は `typeMismatch`。誤りの文に、値は含めない。
- `remove_on_complete` は真偽値だけ(`true` / `false`)。文字列 `"true"`、整数 `1`、配列 `[true]` は `typeMismatch`。型が違うときの値は、`false` として扱って続行する(誤りは報告済み)。
- `pipeline` の形:
  - 無い: `typeMismatch`、行は **1 行目**(位置 0)、理由 ``必須の値 `pipeline` がありません``。
  - テーブルの配列(`[[pipeline]]`): `typeMismatch`、`pipeline` の行(配列の先頭)、理由 ``` `pipeline` は 1 つだけで、テーブルで書きます(1 ファイルに 1 パイプライン) ```。
  - その他(整数など): `typeMismatch`、値の行、理由 ``` `pipeline` はテーブルで書きます ```。
  - 上の誤りのとき、`[pipeline]` の中身の検査は行わない。
- 名前の照合: `expected_pipeline_name` が与えられ、定義の `name` と**完全に同じでない**(大文字小文字・空白も区別。バイト列の比較)と、`pipelineNameMismatch`、行は `name` の値の行、理由 ``指定されたパイプライン名が、定義の `name` と一致しません``。理由に両方の名前は含めない。`name` が空白だけのときは、`emptyField` だけを返し、照合はしない。`name` が文字列でない・無いときも、照合はしない。

### 7.2 `[[job]]`

`job` は、テーブルの配列でなければならない。

- 無い: `noJobs`、行は 1 行目(位置 0)、理由 ``ジョブ(`job`)が 1 つもありません``。
- 空の配列(`job = []`): `noJobs`、行は `job` の値の行。
- 配列でない(テーブルや整数など): `typeMismatch`、値の行、理由 ``` `job` はテーブルの配列で書きます ```。
- 配列の要素がテーブルでない: `typeMismatch`、その要素の行、理由 ``` `job` の要素はテーブルで書きます ```(その要素の検査は行わない)。

各ジョブ(テーブル)のキー:

| キー | 型 | 必須 | 既定値 | 説明 |
|------|----|------|--------|------|
| `id` | 文字列 | 必須 | なし | ジョブID。第 8.1 節の検査 |
| `command` | 文字列、または文字列の配列 | 必須 | なし | 第 7.3 節 |
| `warning_exit_codes` | 整数の配列 | 任意 | 空(`[]`) | 警告にする終了コード |
| `success_exit_codes` | 整数の配列 | 任意 | 省略(意味は `[0]`) | 成功にする終了コード |
| `transitions` | テーブルの配列 | 任意 | 空 | 第 7.4 節 |
| `retry` | テーブル | 任意 | なし | 第 7.5 節 |

許されたキー以外は `unknownKey`(例: `warn_exit_codes`)。

- `id` が無い: `typeMismatch`、行はジョブのテーブルの先頭、理由 ``必須の値 `id` がありません``。文字列でない: `typeMismatch`、値の行、理由 ``` `id` は文字列で書きます ```。
- 終了コードの配列(`warning_exit_codes` と `success_exit_codes`):
  - 配列でない: `typeMismatch`、値の行、理由 ``` `<キー名>` は整数のリストで書きます ```(`<キー名>` は実際のキー名)。
  - 要素が整数でない、または 32 ビット符号つき整数の範囲(-2,147,483,648〜2,147,483,647)に収まらない: 要素ごとに `typeMismatch`、その要素の行、理由 ``` `<キー名>` の要素は、整数(32 ビットの範囲)で書きます ```。1 つでも誤りがあれば、そのキー全体を「無効」として扱い、後続の重なりの検査では使わない。
  - 負の値(例: `-1`)は、その範囲なので**受理**する。重複した値も受理し、除かない(書いた順のまま保持する)。空の配列も受理する(`success_exit_codes = []` は、成功にする終了コードが無い、の意味になる)。
  - 整数は 16 進・8 進・2 進のリテラルでもよい(値で判定する)。
- `success_exit_codes` を省略すると、成功の終了コードは `[0]`。書いたら、**書いた値だけ**が成功(`0` を書かなければ 0 でも成功にならない)。
- 要素が浮動小数(`[1.0]`)や、範囲外の整数(`[99999999999999999999]`、`[0xFFFFFFFFFFFFFFFFFF]`)のときも、要素の型の誤り(`typeMismatch`)になる。

### 7.3 `command`

| 書き方 | 受理の条件 | 保持される値 |
|--------|-----------|---------------|
| 文字列 | trim して空でない | 1 本の文字列(そのまま。trim した値ではない) |
| 文字列の配列 | 空でない配列で、全要素が文字列で、**先頭の要素が trim して空でない**。2 番目以降の要素は空文字列でもよい | 要素の並び(そのまま) |

どちらの書き方かは、取り込み後も区別して保持する(実行側の解釈が異なる。[05. 実行フロー](05-execution-flow.md)・[07. プロセスとシグナル](07-process-and-signals.md))。

誤り:

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `typeMismatch` | ジョブの先頭 | ``必須の値 `command` がありません`` |
| 文字列が空または空白だけ | `emptyField` | 値の行 | ``` `command` が空です ``` |
| 配列が空 | `emptyField` | 値の行 | ``` `command` の配列が空です ``` |
| 配列に文字列でない要素がある | `typeMismatch`(要素ごと) | その要素の行 | ``` `command` の配列の要素は、文字列で書きます ``` |
| 配列の先頭の要素が空または空白だけ(全要素が文字列のとき) | `emptyField` | 先頭の要素の行 | ``` `command` の配列の先頭の要素が空です ``` |
| 文字列でも配列でもない(整数・真偽値・テーブル) | `typeMismatch` | 値の行 | ``` `command` は文字列、または文字列の配列で書きます ``` |

- 配列に型の誤りの要素があるときは、先頭要素の空の検査はしない。
- 受理の例: `command = "echo x"`、`command = ["my prog", "a b", "$HOME", ""]`、`["echo", ""]`。拒否の例: `5`、`true`、`{ a = 1 }`、`["a", 5]`、`[["a"]]`(`typeMismatch`)、`""`、`"   "`、`[]`、`[""]`、`["  ", "x"]`(`emptyField`)。
- 文字列の `command` の中の引用符・`$` などは、この段階では解釈しない(実行時の解釈は実行側の仕様)。
- 誤りの文に、入力の値は含めない。

### 7.4 `[[job.transitions]]`

`transitions` は、テーブルの配列(`[[job.transitions]]` の繰り返し、または `transitions = [{ on = "...", next = "..." }, ...]`)。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `on` | 文字列 | 必須 | `success` または `warning` |
| `next` | 文字列 | 必須 | 遷移先のジョブID、または `@end` |

- 許されたキー以外(`when` など)は `unknownKey`。
- `transitions` が配列でない: `typeMismatch`、値の行、理由 ``` `transitions` はテーブルの配列で書きます ```(遷移は空として扱う)。要素がテーブルでない: `typeMismatch`、その要素の行、理由 ``` `transitions` の要素はテーブルで書きます ```。
- `on` が無い: `typeMismatch`、遷移のテーブルの先頭の行、理由 ``必須の値 `on` がありません``。文字列でない: `typeMismatch`、値の行、``` `on` は文字列で書きます ```。
- `on` の値: `"success"`、`"warning"` を受理。`"error"` は `errorTransition`、値の行、理由 ``エラー結果(`error`)には遷移先を書けません``。それ以外の文字列(`"later"`、大文字の `"Success"` など)は `typeMismatch`、値の行、理由 ``` `on` は `success` または `warning` で書きます ```。
- `next` が無い: `typeMismatch`、遷移のテーブルの先頭の行、理由 ``必須の値 `next` がありません``。文字列でない: `typeMismatch`、値の行、``` `next` は文字列で書きます ```。
- 同じ `on`(`success` どうし、`warning` どうし)の遷移が 2 つ以上: 2 つ目以降の遷移に `duplicateTransition`、行は**その遷移(テーブルの先頭)の行**、理由 ``同じ結果(`on`)の遷移が 2 つ以上あります``。`success` と `warning` を 1 つずつは受理。`on` が不正(`error` や未知の値、型の誤り)の遷移は、重複判定に入れない。
- 遷移先の存在・順序の検査は、第 8 節。

### 7.5 `[job.retry]`(v0.8.0 以降)

ジョブが決めた終了コードで終わったときに、待って実行し直す設定。書き方は、`[job.retry]` の見出しでも、`retry = { ... }` のインラインテーブルでも、ドットキー(`retry.max = 3`)でもよい。**`[job.retry]` の位置は、ジョブのテーブルの中なら、`[[job.transitions]]` の前でも後でもよい**(TOML の意味どおり、直前の `[[job]]` に属する)。

許されたキーは次の 5 つだけ。それ以外は `unknownKey`(例: `retries`)。

| キー | 型 | 必須 | 範囲・書式 | 取り込み後 |
|------|----|------|-----------|-------------|
| `exit_codes` | 整数の配列 | 必須 | 空でない。各要素は 1 以上 255 以下の整数 | 昇順に並べ、重複をまとめる(`[75, 3, 75, 3, 12]` → `[3, 12, 75]`) |
| `max` | 整数 | 必須 | 1 以上 100 以下 | 整数(32 ビット符号なしに収まる) |
| `interval` | 文字列 | 必須 | `<整数><s\|m\|h>`、1 秒以上 24 時間以下 | 秒(64 ビット符号なし整数) |
| `multiplier` | 整数 | 任意 | 2 以上 10 以下 | 整数、または無し |
| `max_interval` | 文字列 | 任意 | `interval` と同じ書式、`interval` 以上 | 秒、または無し |

- 127 などの値も受理する(`[127, 1]` → `[1, 127]`)。
- `multiplier` と `max_interval` は、**両方を書くか、両方とも書かない**か。片方だけなら `retryBackoffIncomplete`。両方なしなら、待ち時間は毎回 `interval`。

#### 間隔の文字列の書式

- 文字列の最後の 1 文字が単位(`s`=秒、`m`=分=60 秒、`h`=時間=3600 秒。小文字だけ)。その前が、**ASCII の数字(0〜9)だけ**の 1 文字以上の列(符号・空白・小数点・`_`・全角数字・16 進(`0x`)は不可)。
- 数値は 1 以上。秒に換算した値が 1 以上 86,400(24 時間)以下。桁あふれ(64 ビット符号なし整数に収まらない、または換算の乗算があふれる)は拒否。先頭の 0 は何個並べてもよい(`0000000000000000000000000001s` は値 1 で受理)。値が 86,400 秒を超えるものは、桁数にかかわらず拒否する(巨大整数の型を使うか、あふれを検知すればよい。結果は同じ)。
- 受理: `1s`、`30s`、`5m`、`2h`、`24h`、`1440m`、`86400s`、`01s`(値 1)。拒否: `""`、`s`、`10`、`1.5s`、`-1s`、`+1s`、` 1s`、`1s `、`1 s`、`1d`、`1S`、`１s`、`1ms`、`0x10s`、`1_0s`、`0s`、`0h`、`86401s`、`25h`、`99999999999999999999999s`、`18446744073709551615h`。文字列でない値(整数・真偽値)も拒否。

#### 誤りと検査

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| `retry` がテーブルでない(整数、文字列、`[[job.retry]]` の配列) | `retryNotTable` | `retry` の値の行(配列のときは、その配列の先頭) | ``` `retry` はテーブルで書きます ``` |
| 必須のキー(`exit_codes`、`max`、`interval`)が無い | `retryMissingKey`(欠けたキーごとに 1 件) | `retry` のテーブルの先頭の行 | ``必須の値 `<キー名>` がありません`` |
| `exit_codes` が配列でない | `retryExitCodeInvalid` | 値の行 | ``` `exit_codes` は整数の一覧で書きます ``` |
| `exit_codes` が空の配列 | `retryExitCodesEmpty` | 値の行 | ``` `exit_codes` が空です ``` |
| `exit_codes` の要素が整数でない、32 ビットの範囲外、1〜255 の範囲外(0、256、-1、1.5、`"75"`、`true` など) | `retryExitCodeInvalid`(要素ごと) | その要素の行 | ``` `exit_codes` の要素は、1 以上 255 以下の整数で書きます ``` |
| `max` が整数でない、または 1〜100 の範囲外(0、101、-1、1.5、`"3"`、`true`) | `retryMaxInvalid` | 値の行 | ``` `max` は、1 以上 100 以下の整数で書きます ``` |
| `interval` / `max_interval` が書式・範囲に合わない | `retryDurationInvalid` | 値の行 | ``` `<キー名>` は、整数と単位(`s`、`m`、`h`)で、1 秒以上 24 時間以下に書きます(例: `30s`) ```(`<キー名>` は `interval` か `max_interval`) |
| `multiplier` が整数でない、または 2〜10 の範囲外(1、11、0、-2、`2.0`、`"2"`、`true`) | `retryMultiplierInvalid` | 値の行 | ``` `multiplier` は、2 以上 10 以下の整数で書きます ``` |
| `multiplier` と `max_interval` の片方だけがある | `retryBackoffIncomplete` | `retry` のテーブルの先頭の行 | ``` `multiplier` と `max_interval` は、両方を書くか、両方とも書きません ``` |
| `exit_codes` に、そのジョブの成功または警告の終了コードと同じ値がある | `retryExitCodesOverlap` | `exit_codes` の**キー**の行 | ``` `exit_codes` に、成功または警告の終了コードと同じ値があります ``` |
| `max_interval` が `interval` より小さい(秒で比べる。等しければ受理) | `retryMaxIntervalTooSmall` | `max_interval` の値の行 | ``` `max_interval` は、`interval` 以上で書きます ``` |

- 整数の読み取りは、64 ビット符号つき整数の範囲で判定する(その範囲に収まらない整数は、範囲外の誤りと同じ扱い)。16 進・`_` 区切りのリテラル(`max = 1_0`、`exit_codes = [0x4B, 1_0]`)も、値で判定して受理する。
- 空のテーブル `[job.retry]`(キーなし)は、`retryMissingKey` が 3 件(`exit_codes`、`max`、`interval` の順)返る(行はすべて同じ)。
- `exit_codes` の複数の要素が不正なら、不正な要素ごとに 1 件(例: `[0, 75, 256]` は 2 件)。
- **テーブルの位置が決まらない書き方**: `retry` を、見出しでなく、ドットキー(`retry.max = 3`)で作ったときは、必須キーの欠落の行は、その `retry` を最初に作ったキー(`retry.` で始まる最初の組)の行。インラインテーブル(`retry = { max = 1 }`)のときは、`retry` を書いた行(同じ行に `{` がある。ある行の途中で `{` が始まる場合でも行は同じ)。どちらも観測済み。位置のバイト順(複数の誤りの並び。第 8 節)で、キー名の先頭と `{` のどちらを使うかは未確認。
- **重なりの検査**(`retryExitCodesOverlap`)は、定義の他の値と照合する。`exit_codes` が有効(エラーなし)のときだけ行う。
  - 成功の終了コード: `success_exit_codes` を**書かなければ `[0]`**。書いて有効なら、その値。書いたが誤り(無効)のときは、成功との重なりを調べない(警告との重なりは調べる)。
  - 警告の終了コード: `warning_exit_codes` が有効なら、その値(無効なら調べない)。
  - どちらかと 1 つでも共通する値があれば、1 件(重なりの値の数にかかわらず 1 件)。
  - 例: `success_exit_codes = [0, 5]` と `exit_codes = [5, 75]` は誤り。`success_exit_codes = [3]` と `exit_codes = [3]` も誤り。`success_exit_codes = [0, 5]`、`warning_exit_codes = [4]`、`exit_codes = [75]` は受理。
- `retry` の有無は、ほかのキーの読み取りの結果に影響しない。
- 誤りの文に、入力の値は含めない。

## 8. 検査の順序とエラーの集約・並び

Walk の中の処理順(誤りは、見つかった順に集める):

1. 根のキー検査(`unknownKey`)。
2. `[pipeline]`: キー検査 → `name` → `description` → `run_id_env`(型の誤り、続けて名前の形の誤り) → `remove_on_complete` → `name` の空の検査 → 名前の照合。
3. `job`: 無い/空/型の誤りの処理。配列なら、各ジョブを順に、次の順で検査する: キー検査 → `id` → `command` → `warning_exit_codes` → `success_exit_codes` → `transitions`(各遷移について、キー検査 → `on` → `next` → 重複) → `retry`(キー検査 → `exit_codes` → `max` → `interval` → `multiplier` → `max_interval` → 倍率と上限の片方だけの検査)。
4. 全ジョブにまたがる検査(第 8.1〜8.4 節): ジョブIDの検査 → 各ジョブについて、遷移先 → 終了コード(`zeroAsWarning`、`overlappingExitCodes`) → `retry` の重なり・上限と間隔の大小。
5. 誤りが 1 件もなく、`[pipeline]` とすべてのジョブが組み立てられるときだけ、定義を返す。

返す誤りの順序: すべての誤りを、**誤りの位置(ファイル先頭からのバイト位置)の昇順**に並べて返す。同じ位置のものは、上の検査の順(集めた順)を保つ(安定な並べ替え)。行番号の昇順になるが、行番号が同じでもバイト位置が違えば、バイト位置の順である。

- 型の誤りなどで検査できなくなった値は、その値に依存する後続の検査だけを省略する(他の検査は続ける)。
- 位置がファイルの先頭(位置 0)の誤りは、行 1 として扱われる(`pipeline` が無い、`job` が無い)。

複数の誤りの例:

```toml
format_version = 1
unknown_top = true          # 2 行目: unknownKey

[pipeline]
name = "p"

[[job]]
id = "a"
command = "x"
success_exit_codes = ["zero"]   # 10 行目: typeMismatch

[[job]]
id = "b"
command = "y"
colour = "red"              # 15 行目: unknownKey

[[job.transitions]]
on = "success"
next = "nowhere"            # 19 行目: unknownTarget
```

返る誤り: `unknownKey`(2)、`typeMismatch`(10)、`unknownKey`(15)、`unknownTarget`(19)。

### 8.1 ジョブ間の検査: ジョブID

`id` が文字列であるジョブごとに、記述順に検査する。

- trim して空、または先頭が `@` → `invalidJobId`、`id` の値の行、理由 ``ジョブID(`id`)は、空でなく、`@` で始まらない文字列で書きます``。この ID は、遷移先の索引に入らない(後続のジョブから、遷移先として参照できない)。
- 既出の ID と完全に同じ(大文字小文字・前後の空白も区別。`" a "` と `"a"` は別) → `duplicateJobId`、2 つ目以降の `id` の値の行、理由 ``同じジョブID(`id`)が、すでに定義されています``。
- 長さの上限、使える文字(空白・記号)の制限は、これ以外にない(定義の検査では。実行時の状態ファイル名などへの影響は、[06. ステートファイル](06-state-file.md)による)。

### 8.2 遷移先

`on` と `next` がともに有効な遷移について、`next` を検査する(`on` が不正な遷移は、検査しない)。

- `next == "@end"`: 受理(以降のジョブをスキップして終える)。
- ID の索引に無い(存在しない、または無効な ID): `unknownTarget`、`next` の値の行、理由 ``遷移先(`next`)のジョブが、定義にありません``。
- 記述順で、自分自身または前のジョブ(位置 ≦ 自分の位置): `backwardOrSelfTarget`、`next` の値の行、理由 ``遷移先(`next`)は、記述順で後ろのジョブまたは `@end` で書きます``。
- 後ろのジョブの ID は受理する。

### 8.3 終了コード

各ジョブについて(`warning_exit_codes` と `success_exit_codes` が有効なとき):

- `warning_exit_codes` に 0 を含む → `zeroAsWarning`、`warning_exit_codes` の**キー**の行、理由 ``0 は警告の終了コード(`warning_exit_codes`)にできません``。(`success_exit_codes` の誤りの有無に関わらず検査する。)
- 両方を書き、有効で、共通する値がある → `overlappingExitCodes`、`warning_exit_codes` の**キー**の行、理由 ``` `warning_exit_codes` と `success_exit_codes` に、同じ値があります ```。ただし、共通の値が 0 だけで、すでに `zeroAsWarning` を報告した場合は、重ねて報告しない(例: `warning_exit_codes = [0]` と `success_exit_codes = [0]` は `zeroAsWarning` の 1 件だけ)。
- `success_exit_codes` を書かないとき、成功は `[0]` だが、`warning_exit_codes` との重なりは(書かれていない側は)調べない。警告に 0 を入れた場合は、`zeroAsWarning` で拒否される。

### 8.4 `retry` との関係

第 7.5 節(重なり、上限と間隔の大小)。

## 9. エラーの種類と表示

### 9.1 エラーの構造

| フィールド | 内容 |
|------------|------|
| `file` | 表示用のファイル名(第 3.1 節) |
| `line` | 行番号(1 始まり)。位置が決まらないときは無し |
| `kind` | 種類(第 9.3 節) |
| `reason` | 固定の文から組み立てた理由。入力の値は含めない。入力由来はキー名だけ(`unknownKey`) |

ライブラリ(読み込み処理の呼び出し側)に返す表示の書式:

```
<file>:<line>: <種類の文>: <reason>      行があるとき
<file>: <種類の文>: <reason>             行が無いとき
```

例: ``conductor.toml:7: 定義にないキーです: キー `x` は定義にありません``。ここで `<file>` は、制御文字・書式文字(第 9.2 節と同じ対象)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは、256 文字までで切って末尾に `…` を付ける)。

`conductor` コマンドの標準エラーへの表示は、`conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason>` の 1 行(誤りごとに 1 行、位置の順)で、`reason` は日本語のまま(言語によらない)。種類の文は、メッセージの言語([08](08-output-and-i18n.md))が日本語のとき日本語(第 9.3 節の「日本語」)、それ以外は英語(「英語」)。`<file>` と `reason` は、改行・制御文字・書式文字をエスケープして表示する(`\n`、`\r`、`\t`、その他は `\u{16進小文字}`)。**ここでは文字数で切らない**。例:

```
conductor: error: bad.toml:7: unknown key: キー `typo` は定義にありません
conductor: error: conductor.toml: definition file does not exist: 指定の場所にファイルがありません
```

定義の誤りがあるときの終了コード(64)と、その標準出力・標準エラーの扱いは、[10. エラーと終了コード](10-errors-and-exit-codes.md)に従う。

### 9.2 キー名の表示

`unknownKey` の理由に入るキー名は、`` ` `` で囲み、次の整形をする。

- 改行を `\n`、復帰を `\r`、タブを `\t` に、その他の制御文字(U+0000〜U+001F、U+007F〜U+009F)と書式文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)を `\u{16進小文字}` にエスケープする(例: U+0001 は `\u{1}`)。
- エスケープ後の文字数が **64 文字**を超えるときは、64 文字までで切って末尾に `…` を付ける(エスケープの途中では切らない。たとえば、残りが 2 文字でエスケープが 6 文字なら、そのエスケープは入れず、そこで切る)。ちょうど 64 文字は切らない。
- この整形は、`file`(256 文字)の整形と同じ手順で、上限だけが違う。

### 9.3 種類の一覧(30 種)

「識別子」は機械が読む名前、「日本語」は日本語の種類の文、「英語」は英語の種類の文。

| 識別子 | 日本語 | 英語 |
|--------|--------|------|
| `fileMissing` | 定義ファイルが存在しません | definition file does not exist |
| `unreadable` | 定義ファイルを読めません | cannot read definition file |
| `tooLarge` | 定義ファイルが大きすぎます | definition file is too large |
| `syntax` | 文法の誤りです | syntax error |
| `typeMismatch` | 値の型が正しくありません | wrong value type |
| `unknownKey` | 定義にないキーです | unknown key |
| `versionMissing` | 書式の版がありません | format_version is missing |
| `versionUnsupported` | 対応していない書式の版です | unsupported format_version |
| `unknownTarget` | 遷移先のジョブが定義にありません | transition target job is not defined |
| `errorTransition` | エラー結果には遷移先を書けません | no transition can be written for the error result |
| `backwardOrSelfTarget` | 遷移先は、記述順で後ろのジョブまたは @end のみです | transition target must be a later job or @end |
| `overlappingExitCodes` | 成功と警告の終了コードが重なっています | success and warning exit codes overlap |
| `zeroAsWarning` | 0 は警告の終了コードにできません | 0 cannot be a warning exit code |
| `pipelineNameMismatch` | パイプライン名が定義と一致しません | pipeline name does not match the definition |
| `duplicateJobId` | ジョブIDが重複しています | duplicate job id |
| `invalidJobId` | ジョブIDが正しくありません | invalid job id |
| `noJobs` | ジョブが 1 つもありません | no jobs are defined |
| `emptyField` | 必須の値が空です | required value is empty |
| `duplicateTransition` | 同じ結果の遷移が重複しています | duplicate transition for the same result |
| `invalidEnvName` | 環境変数の名前が正しくありません | invalid environment variable name |
| `retryNotTable` | retry は表で書きます | retry must be a table |
| `retryMissingKey` | retry の必須のキーがありません | a required key of retry is missing |
| `retryExitCodesEmpty` | retry の終了コードの一覧が空です | retry exit_codes is empty |
| `retryExitCodeInvalid` | retry の終了コードが正しくありません | retry exit_codes has an invalid exit code |
| `retryExitCodesOverlap` | retry の終了コードが、成功または警告の終了コードと重なっています | retry exit_codes overlap the success or warning exit codes |
| `retryMaxInvalid` | retry の最大回数が正しくありません | retry max is invalid |
| `retryDurationInvalid` | retry の間隔が正しくありません | retry interval is invalid |
| `retryBackoffIncomplete` | retry の倍率と間隔の上限は、両方を書くか、両方とも書きません | retry multiplier and max_interval must be given together or not at all |
| `retryMultiplierInvalid` | retry の倍率が正しくありません | retry multiplier is invalid |
| `retryMaxIntervalTooSmall` | retry の間隔の上限が、間隔より小さくなっています | retry max_interval is smaller than interval |

(`retryDurationInvalid` の英語は、`max_interval` の誤りにも同じ文が使われる。)

理由(`reason`)は、第 3〜8 節の各表の日本語の原文のとおり。英語の理由文は存在しない(理由は常に日本語)。理由の文中の `` ` `` は、文の一部としてそのまま出力する。

## 10. 行番号の出し方

- 行番号は 1 始まり。入力の先頭からのバイト位置を、「各行の先頭のバイト位置の表(先頭 0、および各 LF の次の位置)」で求める。位置がちょうど行頭ならその行、そうでなければ、その位置以下で最大の行頭を持つ行。範囲外の位置は、最後の行。
- 改行は LF の数で数える。CRLF でも、CR は直前の行に属し、LF のあとが次の行(CRLF の定義で、LF と同じ行番号になる)。BOM は、1 行目の先頭に含まれる(位置には数えるが、行は 1 のまま)。
- 位置の取り方:
  - 型の誤りや範囲の誤りは、**誤った値の先頭**(値のトークンの最初の文字。引用符を含む)。
  - 未知のキーは、**キーの先頭**(ドットキーなら、その組の先頭)。
  - 必須のキーの欠落は、**それを含むテーブルの先頭**(見出し `[pipeline]`、`[[job]]`、`[job.retry]`、`[[job.transitions]]` の行。インラインテーブルは、7.5 節に述べたとおり。ドットキーなどで暗黙に作られたテーブルは、7.5 節に述べたとおり、最初のドットキーの行)。
  - `pipeline` や `job` 自体が無いときは、位置 0(1 行目)。
  - 終了コードの重なり(`overlappingExitCodes`、`zeroAsWarning`、`retryExitCodesOverlap`)は、対象のキーの行(値ではなく**キー**の先頭)。
  - 配列の誤りは、要素ごとに、その要素の先頭の行(複数行の配列なら、要素の書かれた行)。
- Parse の文法の誤りは、第 4.9 節。深さの誤りは、第 5 節(33 段目のコンテナの先頭の行)。
- 取り込みの誤りと `versionMissing` は、行なし。
- 複数行の文字列の値の先頭は、開く引用符(`"""` または `'''`)の位置。

## 11. 取り込み後のデータモデル

検証に成功すると、次のデータを返す(言語中立の記法。型の表記は、string=文字列、int=整数、bool=真偽値、`T?`=無いことがある、`list<T>`=順序つきの並び)。

```
Definition {
    name: string                    // 空白だけでない(trim していない元の値)
    description: string?
    run_id_env: string?             // 名前の形は検査済み。無いなら実行時に CONDUCTOR_RUN_ID
    remove_on_complete: bool        // 省略時 false
    format_version: int             // 1
    jobs: list<Job>                 // 記述順を保つ。1 つ以上
}
Job {
    id: string                      // 空白だけでなく、@ で始まらず、定義内で一意
    command: Line(string) | Argv(list<string>)   // 文字列で書いたか、配列で書いたか
    warning_exit_codes: list<int>   // 省略時 []。0 を含まない。書いた順のまま。32 ビット符号つき
    success_exit_codes: list<int>?  // 省略時 無し(意味は [0])
    transitions: list<Transition>   // 書いた順。on ごとに高々 1 つ
    retry: RetryPolicy?             // 書かなければ無し
}
Transition { on: success | warning,  next: Job(string) | End }   // next が "@end" のとき End
RetryPolicy {
    exit_codes: list<int>           // 昇順・重複なし・各 1〜255・空でない
    max: int                        // 1〜100
    interval_secs: int              // 1〜86400
    multiplier: int?                // 2〜10。max_interval_secs と同時に有り
    max_interval_secs: int?         // interval_secs 以上。multiplier と同時に有り
}
```

- 成功として扱う終了コード = `success_exit_codes` があればそれ、なければ `[0]`。
- ジョブIDから記述順の位置(0 始まり)を引く操作がある(遷移先の検査と、実行時の遷移の解決に使う)。

## 12. `run_id_env` のゆるい読み取り

`watch` と `reset` は、`--run-id` が無いとき、定義全体を検証せず、`[pipeline].run_id_env` だけを取り出す。

- ファイルを読めない、TOML として読めない(深さ・大きさの上限を含む)、`pipeline` がテーブルでない、キーが無い、文字列でない、名前の形(第 7.1 節)に合わない、のどれでも「無し」(実行時は `CONDUCTOR_RUN_ID`)。
- ほかの誤り(`format_version` の誤り、未知のキーなど)は無視する。壊れた入力でも異常終了しない。
- 例: `[pipeline]\nname = "p"\nrun_id_env = "X_ID"\n` → `X_ID`。`run_id_env = 5`、`"1A"`、`""` → 無し。`pipeline = 3` → 無し。空の入力 → 無し。
- ファイルの大きさの上限(第 3.2 節)をこの読み取りに適用するかは、**未確認**(適用する実装でも、結果は「無し」になるので、利用者から見える差は、上限を超える巨大ファイルの `run_id_env` を読むかどうかだけである)。

## 13. 受理・拒否の例

最小の定義(受理):

```toml
format_version = 1

[pipeline]
name = "p"

[[job]]
id = "a"
command = "c"
```

全キーを使った定義(受理):

```toml
format_version = 1

[pipeline]
name = "nightly"
description = "夜間バッチ"
run_id_env = "GITHUB_RUN_ID"
remove_on_complete = true

[[job]]
id = "extract"
command = ["python", "scripts/extract.py", ""]
warning_exit_codes = [4]
success_exit_codes = [0, 5]

[job.retry]
exit_codes = [75, 111]
max = 5
interval = "10s"
multiplier = 2
max_interval = "60s"

[[job.transitions]]
on = "warning"
next = "notify"

[[job]]
id = "load"
command = "load"

[[job.transitions]]
on = "success"
next = "@end"

[[job]]
id = "notify"
command = "notify --channel ops"
```

別の書き方でも同じ定義になる例(受理。ドットキー、引用符つきのキー、インラインテーブル、見出しの空白):

```toml
"format_version" = 1
pipeline.name = "p"
job = [{ id = "a", command = "c", retry = { exit_codes = [75], max = 3, interval = "5s" } }]
```

拒否の例(各行の行番号は、ヘッダ `format_version = 1`(1 行目)/ `[pipeline]`(2 行目)/ `name = "p"`(3 行目)の続きとしての値。ジョブは 4 行目の `[[job]]` から):

| 入力(ヘッダの次から) | 結果 |
|------|------|
| `[[job]]` `id = "a"` `command = "c"` `[[job.transitions]]` `on = "success"` `next = "zzz"` | `unknownTarget` 9 行目 |
| 同、`on = "error"` `next = "@end"` | `errorTransition` 8 行目 |
| ジョブ a の `next = "a"`(自分自身) | `backwardOrSelfTarget` 9 行目 |
| `warning_exit_codes = [2, 3]` と `success_exit_codes = [0, 3]` | `overlappingExitCodes` 7 行目 |
| `warning_exit_codes = [0]` | `zeroAsWarning` 7 行目 |
| `warning_exit_codes = ["x"]` | `typeMismatch` 7 行目 |
| `id = 1` | `typeMismatch` 5 行目 |
| `command` が無い(`[[job]]` と `id` だけ) | `typeMismatch` 4 行目 |
| `warn_exit_codes = [1]` | `unknownKey` 7 行目 |
| `id = ""` / `id = "@end"` | `invalidJobId` 5 行目 |
| 同じ `id` の 2 つ目 | `duplicateJobId`(2 つ目の `id` の行) |
| `command = "  "` | `emptyField` 6 行目 |
| ヘッダのみ(ジョブなし) | `noJobs` 1 行目 |
| `[job.retry]` に `exit_codes = [0]`、`max = 0`、`interval = "0s"`、`multiplier = 1`、`max_interval = "0s"`、`unknown = 1`(7 行目が `[job.retry]`) | 8〜13 行目に、`retryExitCodeInvalid`、`retryMaxInvalid`、`retryDurationInvalid`、`retryMultiplierInvalid`、`retryDurationInvalid`、`unknownKey`(この順) |

そのほかの確認済みの例: 行番号は CRLF の改行でも同じ。複数のジョブにまたがる誤り(`command = ""`、`max = 0`、同じ `id`、`retry` の必須キー欠落)は、位置の順に `emptyField`(6)、`retryMaxInvalid`(9)、`duplicateJobId`(12)、`retryMissingKey`(14)で返る。`format_version = 1` だけのファイル、`format_version = 1.0`、`format_version = 2`、`format_version = 0x01`(+ 有効な定義)は、順に `noJobs` と `typeMismatch`(`pipeline` が無い)、`versionUnsupported`(整数でない)、`versionUnsupported`(対応していない版)、受理。

## 14. 未確認事項

- 4.9: 閉じていない複数行の文字列、エスケープの途中の誤り、日時の途中の誤りなど、表に載せていない文法の誤りの、行の厳密な規則(上の表と同じ書き方の範囲は確認済み)。
- 第 5 節: 33 段目が暗黙のテーブル(ドットキーで作られるテーブルなど)のときの、深さの誤りの行。また、数千段以上の入れ子で、理由文が `入れ子が深すぎます(上限は 32 段)` か `TOML の文法に誤りがあります` のどちらになるか(種類は常に `syntax`)。
- 第 7.5 節: インラインテーブルの欠落キーの誤りの位置が、`retry` のキーの先頭か `{` かの、バイト位置の違い(行は同じ)。
- 第 3.2 節: Windows など他の OS での、ファイルの権限・シンボリックリンクに関わる `unreadable` の判定の細部。
- 第 12 節: `run_id_env` のゆるい読み取りでの、ファイルの大きさの上限の適用。
