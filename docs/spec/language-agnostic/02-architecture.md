# 02. アーキテクチャ(論理コンポーネント・依存方向・データの流れ・分離点)

対象: `conductor` v0.9.4 までの挙動を実現する実装の、論理的な構成。用語は [00-README.md](00-README.md) の用語集に従う。

この章は、**実装の言語・部品の分け方を規定しない**。外から見える挙動(03〜11 章)を、無理なく、テストしやすく実現するための、論理的な責務の分け方を示す。実装は、モジュール・パッケージ・クラス・ファイルのどの単位に分けてもよい(1 つにまとめてもよい)。ただし、「入出力に触れない判断」と「入出力」を分け、環境・時刻・プロセス・シグナル・出力を差し替えられるようにすること(4 章)は、受け入れテスト(11 章)の一部(区分「単体」「注入」)を成り立たせるために必要である。

## 1. 論理コンポーネントと責務

| # | コンポーネント | 責務 | 入出力 | 詳細 |
|---|----------------|------|--------|------|
| A | 定義の読み込みと検査 | 定義ファイルの場所の決定と読み取り(Intake)、TOML の文法(Parse)、入れ子の深さ(Depth)、`format_version`(VersionCheck)、構造・型・遷移・終了コード・名前の検査(Walk)。誤りを位置(行)つきで返す。取り込み後のデータ(パイプラインとジョブ)を作る。`run_id_env` だけのゆるい読み取りも持つ。v0.9.0 以降は、`env`・`env_file` のキーの検査も持つ | ファイルを読む(Intake だけ)。ほかは文字列に対する純粋な処理 | 03 章 |
| B | 変換 | TOML と YAML の相互変換(入力の読み取り、アンカーとマージキーの展開、書き出し)。定義の検証はしない | 入力ファイル 1 つを読む。`convert_text` は文字列に対して純粋 | 09 章 |
| C | フロー決定(純粋な判断) | 実行結果の分類(成功・警告・エラー・分類なし)と報告する終了コード、遷移と次の動き、起動前の判断(実行・スキップ・拒否)、中断時の再開位置、リトライの判断と待ち時間、終了コードの範囲合わせ、run ID の値の検査。v0.9.0 以降: `.env` の解析、環境変数の層の統合(名前と値、名前だけの要約)、遷移の行き先の解決(実行と図で共有)、図の構造・配置・状態の重ね合わせ、実行計画の模擬 | なし(引数だけから結果を決める。ファイル・プロセス・環境変数・時刻に触れない) | 05(14〜16 章)、10 章 |
| D | 状態の読み書き | ステートの論理項目、記録関数(結果・スキップ・中断を、ステートの新しい値として作る純粋な関数)、読み込み(検査と異常系)、書き込み(原子的な置換と耐久性)、定義との整合性の検査、`reset` と `reset --all`、ステートファイルの場所と名前 | ステートのファイル(と、そのディレクトリ)。記録関数と整合性の検査は純粋 | 06 章 |
| E | プロセス実行 | `command` の分割と検査、ジョブの起動と待ち(待機ループ)、シグナルの転送、リトライの待機、中断の合図(共有される値)、プラットフォーム層(プロセスグループ、シグナル送信、シグナル終了の読み取り、ディレクトリの同期)。失敗は値で返す | 子プロセス、時刻(待ち)、OS。分割と検査は純粋 | 07 章 |
| F | シグナル監視 | OS のシグナル(UNIX 系: 4 種、Windows: Ctrl+C)を受け取り、中断の合図を立てる(最初の番号を保持する)。登録は `run`・`pipeline` だけ | OS のシグナル | 07 の 7 章 |
| G | 出力とロケール | 標準出力・標準エラーへの書き込み(書くたびに flush)、メッセージカタログ(英語・日本語)、`-v` の行、誤りの行、`watch` の表(色を含む)、使い方(`--help`)、入力由来の文字列のエスケープと切り詰め、ロケールと色の判定(最初に必要になったとき 1 回) | 標準出力・標準エラー、環境変数、端末かどうか | 08 章 |
| H | CLI の引数解析と配線 | 引数の字句の解析と検査(誤りの優先順位)、run ID の決定、`run`・`pipeline`・`watch`・`reset`・`validate`・`convert`(v0.9.0 以降は `graph`・`init`・`--dry-run`)の組み立て(前処理の順序、判断 → 実行 → 分類 → 記録の繰り返し)、終了コードの決定。プロセスを終了させるのは最上位の 1 か所だけ。想定外の内部失敗を捕捉して 70 で終わる | A〜G、I を呼ぶ | 04、05、10 章 |
| I | `.env` の読み取りとファイルの作成(v0.9.0 以降) | `.env` ファイルの読み取り(パスの解決、大きさの検査、上限 + 1 バイトまでの読み取り、UTF-8 の確認、C の解析の呼び出し、同じパスの 1 回だけの読み取り、すべてのファイル分の誤りの集約)。ファイルの排他的な作成(`init`。`--force` の置き換え)。ジョブの起動(E)は、足す環境変数を受け取って、引き継いだ環境に足す | `.env` ファイル、`init` が作るファイル | 03 の 7.7、06 の 14 章 |

補足:

- **C(純粋な判断)は、独立した単位として持つ**。ファイルにもプロセスにも環境変数にも時刻にも触れないので、表の例だけで検査できる(11 章の「単体」区分)。
- **記録関数(D の中)も純粋**にする。元のステートを変更せず、新しいステートを返す形にすると、「更新が元と等しいとき書かない」判断(06 の 5.1 節)が容易になる。
- **終了コードの定数と範囲合わせ**(10 章 1・4 章)は、C に置く(CLI の定数として持ってもよい)。
- **コンポーネント A・B の文法の部品**(TOML、YAML)は、自前の構文解析でも既存の部品でもよい。ただし、受理・拒否・エラーの種類・行番号が、03・09 章と同じになること(12 章 5 章)。
- 1 つの実行ファイルに、A〜I がすべて入る。コンポーネントの分け方は、OS ごとの分岐(プラットフォーム層)を 1 か所に集めること(11 の AC-420)と矛盾しない範囲で自由である。

## 2. 依存方向

```text
            ┌───────────────────────────┐
            │ H  CLI の引数解析と配線     │  最上位(終了コードを 1 回だけ返す)
            └──┬──────┬──────┬──────┬────┘
               │      │      │      │
               ▼      ▼      ▼      ▼
         ┌────────┐ ┌────┐ ┌────┐ ┌────┐
         │ G 出力  │ │ E  │ │ D  │ │ B  │
         │ ロケール│ │プロセス│ │ 状態│ │変換 │
         └────────┘ └─┬──┘ └─┬──┘ └────┘
                      │      │
                      ▼      ▼
                   ┌──────────────┐
                   │ C フロー決定   │  純粋
                   └──────┬───────┘
                          ▼
                   ┌──────────────┐
                   │ A 定義の読込と検査│  共有する型(ジョブ、遷移、実行結果、ステートの形)を持つ
                   └──────────────┘
         F シグナル監視 ── 中断の合図(共有される値)を介して E と H につながる
```

規則:

1. **H は、他のすべてを呼ぶ**。他のコンポーネントは、H を知らない(逆向きの依存を作らない)。
2. **A と C は、入出力から独立**(A の Intake を除く)。プロセス・状態・出力・シグナルの部品に依存しない。共有する型(パイプライン、ジョブ、遷移、実行結果、分類、ステートの形、run ID)は、A と C が持つ、依存の最下層に置く。
3. **D(状態)と E(プロセス)は、A と C の型を使う**が、互いに依存しない。D は「ステートを読み書きする」だけで、ジョブを起動しない。E は「ジョブを起動して待つ」だけで、ステートに触れない。両者をつなぐのは H。
4. **B(変換)は、他に依存しない**。定義の検証(A)を呼ばない。独立して検査できる。
5. **G(出力)は、実行結果・ステート・誤りの種類(データ)を受け取って文を作る**。判断をしない(何を表示するかは、H が決めた内容を表現する)。ロケールと色の判定は、最初に表示が必要になるまで行わない(成功・スキップで `-v` なしなら、判定しない)。
6. **F(シグナル監視)は、中断の合図を立てるだけ**。ジョブの扱いは、E の待機ループと H の流れが、合図を見て決める。
7. **OS ごとの分岐は、プラットフォーム層(E の一部)と、シグナル監視(F)の OS 別の登録だけに置く**。ほかの部品に `if (OS)` の分岐を持ち込まない。
8. (v0.9.0 以降)**I(`.env` の読み取り・ファイルの作成)は、A と C の型を使い、D・E に依存しない**。`.env` の解析と環境変数の統合は C(純粋)に置き、I は入出力だけを持つ。`graph` と `--dry-run` は、C の純粋な関数(図、計画)に、定義とステートと(名前の要約のための)`.env` の内容を渡し、H が整形(G)して、標準出力に 1 回で書く。図と計画は、**環境変数の値を持たない**(名前と出どころだけ)。

## 3. データの流れ

### 3.1 入口

```text
main():
    想定外の内部失敗を捕捉する仕組みを、最初に設定する     # 固定の英語 1 行 + 終了コード 70(10 の 6 章)
    code = run_cli(引数(プログラム名を除く), 本番の環境, 本番の出力)
    プロセスを code で終了する                              # 終了は、ここで 1 回だけ

run_cli(引数, 環境, 出力, ...):
    parsed = 引数を解析する(04 の 4 章)
      誤り           → 使い方の誤りを標準エラーに表示、return 68
      help           → 使い方全文を標準出力へ、return 0
      version        → `conductor <版>` を標準出力へ、return 0
      コマンド       → run / pipeline / watch / reset / validate / convert / graph / init のどれかへ
```

### 3.2 `pipeline` 実行のシーケンス

`prepare`(前処理)の順序と、そこでの失敗の終了コードは、05 の 5.1 節と 10 の 2 章に固定されている。

```text
H: pipeline
 ├─ prepare
 │    ├─ F: シグナルの監視を開始(定義の検査より前)         → 失敗 70(登録済みは続行)
 │    ├─ A: 定義の読み込みと検証(パイプライン名の照合を含む) → 失敗 64
 │    ├─ E: 全ジョブの command の検査                       → 失敗 64
 │    ├─ H: run ID の決定(--run-id | 環境変数)              → 失敗 68
 │    ├─ I: `.env` の読み取り(v0.9.0 以降。ステートの前)    → 失敗 64
 │    ├─ D: ステートの読み込み(完了のものは「空」)           → 失敗 65
 │    └─ D: 定義との整合性の検査                             → 食い違い 65
 └─ for job in 定義のジョブ(記述順):
      ├─ C: 起動前の判断 → 実行 / スキップ / 拒否
      │    ├─ 拒否     → G: 表示、return 66
      │    ├─ スキップ → D: 記録関数 → 変化があれば D: 書き込み(Durable)、続行(完了なら finish)
      │    └─ 実行:
      │         ├─ ステートが空なら D: 初期ステート → 書き込み(Fast)
      │         ├─ リトライ込みの実行
      │         │    loop { C: 環境の統合(試行ごと。v0.9.0 以降) → E: ジョブの起動と待ち(足す環境変数つき) → 実行結果
      │         │           C: リトライの判断
      │         │           リトライなら G: 知らせ(常に標準エラー) → E: 待機(秒) → 中断なら「起動しなかった中断」の結果 }
      │         ├─ C: 分類と次の動き(RunMode = Pipeline)
      │         ├─ G: 表示(-v のときの結果行・遷移行。常時のエラー行)
      │         ├─ D: 記録関数 → 書き込み(Durable)
      │         ├─ エラーまたは分類なし → return exitCodeFor(...)
      │         ├─ 完了 → finish(削除指定ならステートを消す)、return 0
      │         └─ 中断の合図が立っている → C: 再開位置 → D: 記録関数 → 書き込み(Durable)、return 128 + 番号
 └─ ループを抜けても完了していない → "cannot determine whether the pipeline is complete"、return 65
```

- `run` は、`prepare`(ジョブIDの存在の検査を含む)のあと、指定した 1 ジョブについて同じ「判断 → 実行 → 分類 → 記録」を行う。分類と次の動きは、RunMode = Individual で求める(05 の 5.2 節)。
- `watch`・`reset`・`validate`・`convert` は、シグナルを準備しない。それぞれ、ステートの読み込み(中身の検査を除く。D)・ステートの削除(D)・定義の検査(A と E の `command` の検査。v0.9.0 以降は、続けて I の `.env` の読み取り)・変換(B)を呼ぶ(04 の 7 章)。
- v0.9.0 以降の `graph`・`--dry-run`・`init` も、シグナルを準備しない。`graph`: 定義と `command` と `.env` の検査(`validate` と同じ)→(`--state`)run ID の決定、ステートの読み取り(完了したものも)と照合 → C: 図の構造と配置 → G: 整形 → 標準出力に 1 回で書く。`--dry-run`: `prepare` の、シグナルを除く部分(定義、`--assume` のジョブID、run ID、`.env`、ステート、照合)→ `command` の分割 → C: 計画の模擬(拒否は 66)→ G: 整形 → 標準出力に 1 回で書く(ジョブを起動せず、ステートに書かない)。`init`: G: ひな形の生成 → I: ファイルの排他的な作成、または標準出力(定義・`.env`・ステートを読まない)。
- `pipeline` は、次のジョブを「次の動き」の戻り値で決めない。記述順に全ジョブを見て、起動前の判断で決める(スキップ・再開は、ステートが運ぶ)。

### 3.3 責務の流れ(データ)

```text
定義ファイル ──A: 読み込みと検証──▶ パイプライン定義 ─┐
ステートファイル ──D: 読み込み──▶ ステート ───────────┤
                                                      ▼
                       C: 起動前の判断 ──▶ 実行 / スキップ / 拒否
E: ジョブの起動と待ち ──▶ 実行結果 ──C: 分類と次の動き──▶ (結果, 次の動き)
                                         │
        D: 記録関数(結果・スキップ・中断) ──▶ ステート(新) ──D: 書き込み──▶ ステートファイル
結果の「報告する終了コード」 ──C: 範囲合わせ──▶ conductor の終了コード
```

### 3.4 中断の伝わり方

- 中断の合図は、「立った/立っていない」と「最初のシグナル番号」を持つ、並行の実行単位の間で共有される値である。シグナル監視(F)が立て、待機ループ(E)と流れ(H)が読む。
- 立てる側と読む側は、別の実行単位(スレッド、シグナルハンドラ、非同期のタスクなど)かもしれない。読み書きが、見えない順序の乱れを起こさない形(原子的な値など)で行うこと(実装に任せてよい点。07 の 6 章)。

## 4. テスト容易性のための分離点

受け入れテスト(11 章)のうち、外から再現しにくいもの(区分「単体」「注入」)は、次の分離点で成り立つ。実装は、**次のものを、本番の実体と偽の実体で差し替えられる形で受け取る**。

| 分離点 | 本番の実体 | 差し替える目的(偽の実体の例) | 主な AC |
|--------|-----------|------------------------------|---------|
| 環境(環境変数、標準出力が端末か) | プロセスの環境変数、端末の判定 | ロケール・`NO_COLOR`・run ID の環境変数を、表で与える。ロケールを読んだ回数を記録する(遅延評価の確認) | 4.8、4.13 節 |
| 時刻・待ち | 実時間の待ち、現在時刻 | 待ち時間(リトライ)を記録だけして実際には待たない。一時ファイル名の時刻を固定する。待機ループの間隔を検査する | 4.9、4.10 節 |
| プロセス(ジョブの起動と待ち) | 子プロセスの起動と待機 | ジョブごとの実行結果を台本で返す(終了コード・シグナル終了・起動失敗・中断)。呼び出しを記録する(何が実行されたか)。ステートをメモリに持つ版(ファイルなし。大きなジョブ数の流れの測定にも使う) | 4.3、4.4、4.9、4.16 節 |
| シグナル(登録) | OS のシグナルの登録 | 登録の成功・失敗・登録済み・開始時にすでに合図が立っている、を再現する | 4.10 節 |
| 出力(標準出力・標準エラー) | 標準出力・標準エラー(書くたびに flush) | 文字列に溜める。書き込みの失敗を起こす(`cannot write to standard output`) | 4.5、4.7、4.13 節(注入) |
| ファイルシステム | 実ファイル | 一時ディレクトリ(実ファイル)で、定義の書き換え・実行・ステートの読み取りをする補助。v0.9.0 以降は、`.env` の読み取りとファイルの作成(`init`)も、差し替えられる口にして、誤り(`.env` の誤り、作れない誤り)を、注入で起こす | 全般、4.17、4.20 節 |

構成の指針:

1. **H の流れは、プロセス・ステート・変換・環境・シグナル・出力を、まとめて 1 つの依存の束として受け取る**(引数に束を渡す、コンストラクタで渡す、インターフェースを使うなど、言語に合う方法)。本番の入口は本番の実体の束を渡し、テストは偽の実体の束を渡す。
2. **待機ループは、「待つ対象」「転送の関数」「sleep の関数」を引数に取る**と、偽の子プロセスで、待ちの間隔(1・2・4・8・10 ms)、転送が 1 回だけであること、待ちの失敗(起動失敗として扱う)を、単体で検査できる(07 の 5 章)。
3. **C の純粋な判断は差し替え不要**(引数だけで決まる)。表の例を、そのままテストにできる。
4. **出力の書き込みは、1 か所を通す**(書くたびに flush する。順序を保つ)。標準出力と標準エラーを混ぜない(08 の 1 章)。
5. 外から作れない失敗(出力の書き込みの失敗、シグナル登録の失敗)は、差し替えでしか起こせない。それらを差し替えられる口がないと、AC の「注入」の区分が検査できない。
6. **製品の実行ファイルに、テスト専用の経路(わざと異常終了するコマンドなど)を持たない**(11 の AC-422)。内部失敗の検査は、入口の差し替え、または別のテスト用の実行ファイルで行う(10 の 6 章)。
7. ジョブの標準入出力・環境変数・作業ディレクトリは、子プロセスにそのまま引き継ぐ(07 の 4.2 節)。受け入れテストは、テスト用ジョブ(11 の 3.2 節)で確かめる。

## 5. 設計判断のチェックリスト
