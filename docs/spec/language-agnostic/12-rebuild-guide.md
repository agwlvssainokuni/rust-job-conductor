## 2. 実装時の落とし穴

03〜11 章の「実装に任せてよい点」「実装の特記事項」「未確認」「注意」から、実装を間違えやすい点を集約する。

### 2.1 定義の読み込み(03)

- 段階 1〜4 の誤りは 1 件で打ち切る。Walk だけが複数返す。`format_version` が無いと、未知のキーや型の誤りが隠れる(`versionMissing` の 1 件だけ)。文法の誤りは版の確認より先(`format_version = = 1` は `syntax`)。
- 誤りは**位置の昇順**に並べて返す(安定な並べ替え)。検査の順に返さない。
- 必須のキーの欠落の行は、「それを含むテーブルの先頭」。`pipeline`・`job` 自体が無いときは 1 行目(位置 0)。
- 終了コードの重なり(`overlappingExitCodes`、`zeroAsWarning`、`retryExitCodesOverlap`)の行は、**キー**の行(値ではない)。0 が成功と警告の両方に書かれたら `zeroAsWarning` の 1 件だけ。
- `success_exit_codes` を省略すると `[0]`。書いたら**書いた値だけ**が成功(0 を書かなければ 0 は成功でない)。空配列も受理する。
- `1979-05-27 07:32:00Z`(スペース区切りの日時)は**受理**する(拒否と混同しない)。インラインテーブルの改行・末尾のカンマ、`\e`、`\xHH`、秒を省いた時刻は、受理しても拒否しても挙動は変わらない(03 の 4.8 節。テストは使わない)。
- 理由の文に入力の値を入れない。キー名だけを `` `キー名` `` の形で、エスケープして 64 文字で切って入れる。
- `[job.retry]` は `[[job.transitions]]` の前後どちらでもよい。数値の範囲: `retry.exit_codes` は 1〜255(127 も可)、`max` は 1〜100、`multiplier` は 2〜10、間隔は 1 秒〜24 時間。`multiplier` と `max_interval` は両方書くか両方書かない。
- 文法の誤りの表示は固定の文で、読み取りの部品のエラー文を使わない。
- 数千段以上の入れ子でも異常終了しない。ただし、理由が `入れ子が深すぎます(上限は 32 段)` か `TOML の文法に誤りがあります` かは、実装に任せてよい(種類は `syntax`)。

### 2.2 CLI(04)

- オプションはコマンド名の前にも置ける。値を取るオプションは、次の引数を `-` 始まりでも、`--help` でも、そのまま値にする。このとき、値として取られた `--help`・`-h`・`--version` は、help・version にならない(`--config --help run a` は、`--help` というパスの定義を読む)。
- `-h`/`-V` は、`--` より前にオプションとして解釈されたものが 1 つでもあれば、ほかの誤りより先(`bogus --help` は help)。`--help=x`・`-h=x`・`-V=1` のように `=値` が付いても、help・version が勝つ。`-v=1` は `invalid value`。
- 単独の `-` は位置引数(`run -` はジョブID `-`)。`-- run` は、`run` がコマンド名で、ジョブIDが無いので `missing argument`(68)。
- 重複指定の誤りは、すべて `invalid value`(対象はオプション名)。`-v` の重複は、`-v` と `--verbose` の合計で数える。
- `watch` と `reset` は定義を検証しない。`--run-id` があれば定義を読まず、なければ `run_id_env` だけをゆるく読む(壊れた定義でも動く)。
- `reset --all` は環境変数も `--run-id` も見ない(値の誤りも 68 にならない)。
- `NO_COLOR` は、**空でない値が設定されていれば**色なし(空は未設定と同じ)。
- 非 UTF-8 の引数を表せない言語は、その引数を `invalid value` 扱いにしてよい(04 の 4.3 節)。`--config` と `convert` の入力のパスは、表せる限り無加工で通す。

### 2.3 実行の意味論(05)

- 分類なし(起動前・待機中の中断)は、ジョブの状態を変えない。`error` のジョブの再実行が起動前に中断されたときは、`status` は `error` のまま `exit_code` が消える。
- `pipeline` は、次のジョブを「次の動き」で決めず、記述順に全ジョブを見る。
- 完了の判定は、ジョブ実行後の中断の合図の判定より**先**。
- 全ジョブを通過しても完了にならないと、65(`cannot determine whether the pipeline is complete`)。
- 起動前の中断の終了コードは、`isError = false` で範囲合わせされる(`128 + n` の下位 8 ビットが 0 なら 0 になりうる。実在のシグナル番号では起きない)。
- リトライの知らせは「待機の前」に、常に標準エラーへ。`in 1 seconds`(単数形の処理なし)。リトライの回数はステートに書かず、再開では最初から数え直す。
- 遷移でスキップしたあとのステートには、成功直後でも `resume_job_id` が入りうる(05 の 12 章の 3)。

### 2.4 ステート(06)

- `definition_key` は書くが、読んでも照合に使わない(`definition_path` と同じ値)。
- 完了のステートは、読み込みでは「空」。次の `pipeline` は先頭から始まり、初期ステートで**上書き**する。先頭以外の `run` は順序外(66)。
- 大文字小文字を区別しないファイルシステムでは、run ID `A` と `a` が同じファイルになる(中身の `run_id` との照合で 65)。
- `reset --all` は、長さ 0 のファイルを消さず、警告にも出さない。別の `run_id` を持つファイルは黙って残す。
- 理由文(`TOML として読めません` など)は、ロケールによらず日本語。種類の文と案内だけがロケールに従う。
- 排他制御はしない。書き込みは原子的だが、同時実行では後の書き込みが勝つ。
- ステートの書式を TOML 以外にしてもよいが、書式の検査(UTF-8・構文・未知の項目)に当たる検査と、06 の 6 章の検査の順序・理由文は同じにする。

### 2.5 プロセスとシグナル(07)

- 区切りの文字はスペース・タブ・LF・CR の 4 つだけ(U+00A0 などは普通の文字)。二重引用符の中の `\\` は 1 つに縮まらない。
- シグナルの転送先は、ジョブの子プロセスの pid だけ(許可は 4 つ、1 回だけ)。孫には送らない。終了済みのジョブには送らない。
- 終了の観測の直後に合図が立っていたら、ジョブの終了コードが 0 でも、エラー(`128 + 番号`)。
- 登録はプロセスで 1 回だけ。2 回目は「すでに登録済み」(成功と同じ扱い)。
- ほぼ同時に複数のシグナルが届いたとき、どれが「最初」かは規定しない(最初に観測した 1 つを保持すれば足りる)。
- 終了の状態を取得できないときは、起動失敗(127)として扱う。

### 2.6 出力(08)

- 日本語の補足の区切りは ASCII の `, `。`Run ID` 見出しは日本語でも `Run ID`。`reset --all` の警告は `conductor: warning:`(終了コード 0)。
- 定義・ステート・変換の誤りの原因は、英語ロケールでも日本語の固定文。
- `--version`、内部の誤りの文、シグナルの準備の失敗の文は、ロケールを判定しない(英語のみ)。
- ロケールは `LC_ALL`、`LC_MESSAGES`、`LANG` の最初の空でない値だけで決める(大文字小文字を区別する。OS のロケール API は使わない)。
- 表示するファイル名は切り詰めない(パス用エスケープだけ)。定義・変換の部品が内部で 256 文字に切る実装でも、`conductor` の表示では切らない(08 の 9 章)。

### 2.7 変換(09)

- 出力のキーは**辞書順**(記述順は保持されない)。コメントも保持されない。
- 入力の形式は `--to` の反対。拡張子は見ない。
- `null`・日時・タグつきの値・文字列でないキー・複数の文書・範囲外の数値・マージキーの値がマップでない、はすべて失敗(67)。
- 非 ASCII のキー・値の YAML 出力は、常に二重引用符で囲む(plain で書ける範囲を広げる変更は、この仕様の変更になる)。

### 2.8 品質・ビルド(11)

- 性能の基準は、「強制」と書いたもの以外は目安(超えても不合格にせず警告として記録する)。測定は、最適化した版で行う。
- カバレッジは、1 つの OS(Linux)で測る。OS 専用のコードは計測の対象に入らない。テスト用ジョブは除外する。
- 最小の対応版の記載(設定、文書、CI の道具の版)は、すべて同時に更新して、一致させる(11 の 7 章)。
- 受け入れテストの多くは、テスト用ジョブ(11 の 3.2 節)で外から確かめる。製品の実行ファイルにテスト専用の経路を持たない(AC-422)。

## 3. 受け入れの観点(まとめ)

1. **単体**: 純粋な判断(05 の各表)、`command` の分割(07 の 3 章)、記録関数(05 の 3 章)、待機ループ(間隔と転送)、エスケープ(08 の 9 章)、終了コードの範囲合わせ(10 の 4 章)が、表の例のとおり。

## 5. 言語選定時に決めること

言語・ライブラリを選ぶ前に、次の項目が満たせるか、満たすために何を自前で書くかを決める。02 の 5 章の判断表を、言語の観点から整理したものである。

### 5.1 書式の扱い(定義・ステート・変換)

| 決めること | 観点 |
|------------|------|
| 定義(TOML)の読み取り | TOML の標準の部品を使うか、03 の 4 章の文法を自前で解析するか。必要なのは、(1) 受理・拒否が 03 の 4 章と同じ、(2) 値の位置(行)が分かる、(3) キーの重複を拒否する、(4) 数値・日時の細かい文法を拒否する、(5) 深さが 1,000 の入力で異常終了しない、の 5 つ。標準の部品がこれを満たさなければ、自前で書くか、前処理を足す。誤りの表示に、部品のエラー文を使わない(固定の文だけ) |
| ステートの書式 | 参照の TOML をそのまま使うか、言語に合う別の書式(JSON など)にするか。他の実装とステートファイルを共有するなら、参照の TOML を採る。別の書式なら、書式の検査と、06 の 6 章の検査の順序・理由文を、その書式で再現する |
| 変換の YAML | YAML の部品を使うか、09 の 5.0 の部分集合を自前で解析するか。必要なのは、アンカー・エイリアス・マージキーの扱いと、YAML 1.2 コアスキーマの解決、行つきの誤り、展開の上限(要素数 100,000、文字 16 MiB、深さ 32)。YAML の書き出しは、09 の 8.3 節の規則(辞書順、plain と引用符の使い分け)を自前で書く必要があることが多い |
| TOML の書き出し | ステートと変換の出力で使う。キーは辞書順。必須とした整形の規則は、09 の 8.2 の 1〜8 のみ。部品の標準の整形が、これを満たすか確かめる |
| 日本語の固定文 | 定義・ステート・変換の誤りの原因は、ロケールによらず日本語の固定文。文字コードは UTF-8 で、ソース・出力とも崩れないこと |
| 整数の幅 | `exit_code` は 32 ビット符号つき整数の範囲。待ち時間の計算は、あふれない(上限に止める)。言語の整数が任意精度でも、範囲の検査を行う |
| 文字数・位置 | 文字数はコードポイント単位、位置と大きさはバイト単位。文字列がバイト列でない言語(UTF-16 など)は、行番号・バイト位置・切り詰めの計算に注意する |

### 5.2 プロセス・シグナル・OS

| 決めること | 観点 |
|------------|------|
| 子プロセス API | シェルを介さず、`program` と引数の配列で起動できること。標準入出力・環境変数・作業ディレクトリを継承できること。終了コードと「シグナルで終了した」ことを区別して読めること。起動失敗(実行ファイルがない・実行権限がない)と、起動後の失敗を区別できること |
| 新しいプロセスグループ | UNIX 系で、ジョブを新しいプロセスグループで起動できること。標準 API にない言語は、OS の呼び出しを使う(1 か所にまとめる) |
| シグナルの受け取り | UNIX 系で SIGHUP・SIGINT・SIGQUIT・SIGTERM、Windows で Ctrl+C を、安全に受け取れること(シグナルハンドラの制約、専用のスレッド、セルフパイプなど)。受け取りが「中断の合図」を立てるだけの作りにできること。言語の実行環境が、既定でこれらのシグナルを横取りしないか(横取りするなら、登録で上書きする) |
| pid へのシグナル送信 | UNIX 系で、ジョブの子プロセスの pid に、許可した 4 つのシグナルを送れること(安全でない呼び出しになりうる。1 か所に隔離する)。Windows は転送しない(OS が Ctrl+C を配る) |
| 待機 | ジョブの終了の確認(ポーリング)か、終了の通知か。終了を観測した直後に合図を確認できること。リトライの待機が、合図から 1 秒以内に返ること |
| ファイルの置き換えと同期 | 一時ファイルへの書き込み、内容の同期(fsync)、名前の付け替えによる原子的な置き換え、ディレクトリの同期(UNIX 系)が、対象 OS で使えること。Windows で、既存ファイルへの名前の付け替えが成功する方法 |
| 端末の判定 | 標準出力が端末かどうか(色の判定)を、UNIX 系で正しく判定できること |
| 内部失敗の捕捉 | プログラムの最初に、想定外の失敗を捕捉して、固定の英語 1 行と終了コード 70 で終わる仕組みを置けること。標準エラーが閉じていても 70 で終わること |
| 単体の実行ファイル | 外部のランタイムを要さない形で配れること(静的リンク、ランタイムの同梱など)。要さない形にできない言語は、配布の形(11 の 6 章)を、代替の方法で満たす |
| 非 UTF-8 の引数 | UNIX 系で、不正なバイト列の引数を受け取れるか。受け取れなければ、`invalid value` 扱い(04 の 4.3 節) |
| 異常終了しない書き方 | 外部の入力の経路で、未検査の取り出し・強制的な中断を使わない(11 の AC-421)。例外を使う言語は、境界で捕捉して終了コードに変える |
