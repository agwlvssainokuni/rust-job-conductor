# 01. 概要(目的・設計方針・制約)

対象: `conductor` v0.9.3 までの挙動。用語は [00-README.md](00-README.md) の用語集に従う。

## 1. 目的

`conductor` は、既存のジョブスケジューラ(cron など)から呼び出される、**ジョブの流れの制御ツール**である。定義ファイル(`conductor.toml`)に、ジョブと、結果(成功・警告・エラー)ごとの次の動きを書いておくと、`conductor` が、

1. ジョブを記述順に実行し、
2. 結果に応じた遷移の規則に従って、後ろのジョブをスキップしたり、`@end` で終えたりし、
3. 実行の状態(ステート)をファイルに覚え、
4. エラーで止まったあとは、同じコマンドをもう一度呼ぶだけで、エラーのジョブから再開する。

スケジューラから見える結果は、`conductor` の**終了コード**だけである(成功・警告・スキップは 0、エラーはジョブの終了コード、そのほかは [10-errors-and-exit-codes.md](10-errors-and-exit-codes.md) の表)。

## 2. ユースケース

| # | 使い方 | 使うコマンド |
|---|--------|--------------|
| 1 | 複数のジョブを、1 回の呼び出しで、順に実行する(夜間バッチなど)。エラーで止まる。次の呼び出しで、止まったジョブから再開する | `conductor pipeline <名前>` |
| 2 | スケジューラが、ジョブを 1 つずつ別々に呼ぶ(ジョブごとに別の起動時刻・別のスケジュール)。`conductor` が、前のジョブの結果に応じて、実行・スキップ・拒否を決める | `conductor run <ジョブID>` |
| 3 | 警告(一部失敗)のとき、通常と別のジョブへ分岐する、または後ろのジョブを全部飛ばして終える | 遷移(`on = "warning"`、`next = "<ジョブID>"` または `"@end"`) |
| 4 | 一時的な失敗(特定の終了コード)を、待ってから実行し直す(最大 100 回、固定または倍率つきの間隔) | `[job.retry]`(v0.8.0 以降) |
| 5 | 同じ定義を、複数の実行単位(日付、CI の実行番号など)で並行して使う | `--run-id` または環境変数(run ID) |
| 6 | 実行の途中経過を見る、初期化する | `conductor watch`、`conductor reset [--all]` |
| 7 | 定義ファイルの書き間違いを、実行前に見つける | `conductor validate [<名前>]` |
| 8 | 定義ファイルを、TOML と YAML のあいだで変換する | `conductor convert <ファイル> --to <yaml\|toml>` |
| 9 | 完了したあとのステートファイルを、自動で片づける | `--remove-on-complete`、または `[pipeline].remove_on_complete = true` |
| 10 | ジョブに環境変数を渡す(定義に書く、`.env` ファイルから読む。パイプライン全体、またはジョブごと)。ジョブが、自分のジョブID・試行の番号などを知る | `[pipeline.env]`、`[job.env]`、`env_file`、自動の変数 `CONDUCTOR_*`(v0.9.0 以降) |
| 11 | 定義の遷移を図で見る(`git log --graph` 風の text、または Mermaid)。実行済みの状態と再開位置も重ねる | `conductor graph [--format text\|mermaid] [-v] [--state]`(v0.9.0 以降) |
| 12 | ジョブを実行せずに、実行したら何が起こるか(実行計画)を見る。終了コードを仮定して、流れを確かめる | `conductor pipeline <名前> --dry-run`、`conductor run <ジョブID> --dry-run`、`--assume <ジョブID>=<終了コード>`(v0.9.0 以降) |
| 13 | 定義ファイルのひな形を作る | `conductor init [--force] [<名前>]`(v0.9.0 以降) |

## 3. 利用者像

- **運用担当者・開発者**: 既存の cron・CI のジョブに、順序・分岐・再開の制御を足したい人。シェルスクリプトで書いていた制御を、宣言的な定義に置き換える。
- **スケジューラ**: `conductor` を子プロセスとして呼び、終了コードで結果を受け取る。
- 利用者は、`conductor` の実装言語の知識を要しない(単一の実行ファイルを置くだけで動く)。表示は、環境のロケールに従って、英語と日本語を切り替える。
- この仕様書の読み手(実装者)は、ここに書いた挙動を、任意の言語で再現する人である。

## 4. 設計方針

実装の言語によらず守る方針。各方針の詳細は、右の章にある。

| 方針 | 内容 | 主な根拠 |
|------|------|----------|
| 単一の実行ファイル | 外部のランタイムを要さない形で配れる(リリース物の要件は 11 章 6 章) | 11 章 |
| シェルを介さない | `command` は、シェルを呼ばずに直接起動する。`$`・`*`・`\|`・`;`・`>` は解釈せず、普通の文字として引数に渡す(注入を起こさない) | 07 章 |
| 定義は宣言的で、実行しない | 定義の検証は、コマンドを解釈・展開・起動しない。誤りは、位置(行)つきで、まとめて報告する | 03 章 |
| 純粋な判断と、入出力の分離 | 分類・遷移・起動前の判断・リトライの判断は、ファイルにもプロセスにも触れない純粋な関数として分ける。入出力は別の部品に置く | 02 章 |
| 再開できる | 状態は、ジョブの結果が出るたびに、原子的にファイルへ書く。エラーのジョブが再開位置になる | 05、06 章 |
| 外部の入力で異常終了しない | 引数・環境変数・ファイル・シグナルに対して、失敗は値(終了コードとメッセージ)で返す。想定外の内部失敗は、固定の 1 行と終了コード 70 | 10、11 章 |
| 入力の値を表示に出さない | エラーの文は固定の文で組み立てる。入力由来はキー名・ジョブID・パスだけで、エスケープと長さの制限をして出す。環境変数の値(`env`、`.env`)は、標準出力・標準エラー・ステートのどこにも出さない(名前だけ。v0.9.0 以降) | 08 章 |
| 3 OS で同じ挙動 | `command` の分割、判断、ステートの内容は、OS によらず同じ。OS 固有の処理は、プラットフォーム層の中だけに置く | 07 章 |
| 依存は最小 | C のコンパイルを要する依存やネットワークの部品を、実装に含めない。安全でない呼び出しは、あっても 1 か所 | 11 章 |
| 既定は静か | `conductor` 自身は、既定では何も出力しない(ジョブ本体の出力がそのまま流れる)。エラーのとき、または `-v` のときだけ標準エラーに書く | 08 章 |
| テストできる構造 | 環境・時刻・プロセス・シグナル・出力を、差し替えられる形で受け取る(02 章 4 章) | 02、11 章 |

## 5. 非目標

次のことは、**しない**(挙動にない)。

- スケジュール機能(時刻や周期での起動)。呼び出しは、外部のスケジューラの役目。
- ジョブの並列実行。1 回の呼び出しの中では、ジョブは 1 つずつ、記述順に実行する。
- ジョブの時間の上限(タイムアウト)。ジョブが終わらなければ待ち続ける。
- ステートファイルの排他制御(ファイルロック、PID ファイル)。同じ定義・同じ run ID の同時実行は避ける。
- ジョブの出力の加工・保存。ジョブの標準入出力・作業ディレクトリは、そのまま引き継ぐ。環境変数は、引き継いだものを残し、v0.9.0 以降は、定義(`env`、`env_file`)と自動の変数を「足す」だけである(取り除く書き方 `unset` はない)。
- 環境変数の値の展開(`${X}` など)、`.env` の複数行の値、省略できる `env_file`。値は、書いたとおりに渡す(v0.9.0 以降)。
- ネットワークへの接続、利用状況の収集。
- シェルの機能(変数の展開、パイプ、リダイレクト、ワイルドカード)。必要なら、`command` で明示的にシェルを呼ぶ(例: `["sh", "-c", "..."]`)。
- `error` 結果に対する遷移。エラーは、そこで止まり、再開で扱う。
- 後ろ向き・自分自身への遷移(ループ)。遷移は、記述順で後ろのジョブまたは `@end` だけ。
- YAML の定義の直接の読み込み。YAML は `convert` で TOML にしてから使う。
- 実行ファイルへの署名・公証(`SHA256SUMS` は転送の破損の検知まで)。
- ジョブの孫(ジョブが起こしたプロセス)へのシグナルの転送。転送先は、ジョブの子プロセスの pid だけ。

## 6. 制約

| 項目 | 内容 |
|------|------|
| 実装の言語 | 規定しない。ただし、TOML の読み取り(03 章の文法)、シグナルの受け取り、プロセスの起動と待ち(プロセスグループの指定、pid へのシグナル送信を含む、07 章)ができること。言語選定の観点は 12 章 5 章 |
| 対応 OS | Linux、macOS、Windows の 3 つ。配布物の対象の一覧は 11 章 6.1 |
| UNIX 系と Windows の差 | 色は UNIX 系だけ(標準出力が端末のとき)。シグナルは UNIX 系が 4 種、Windows は Ctrl+C のみ。ジョブは UNIX 系で新しいプロセスグループで動く。ディレクトリの同期は UNIX 系だけ(07 の 8 章、08 の 6.3) |
| 依存の方針(言語・ライブラリ非依存の考え方) | ネットワークの部品(HTTP・TLS など)を含めない。実行ファイルを作るのに C のコンパイルを要する依存を持ち込まない(持てない言語は、同等の「利用者にビルド環境を要求しない」方針に読み替える)。依存は最小にし、既知の脆弱性を定期的に検査する(11 の 2.3、7 章)。部品を自前で書くか既存のものを使うかは、挙動が同じなら任意 |
| 安全でない呼び出し | 型・境界の検査を外す呼び出しは、シグナル送信の 1 か所だけ(それがある言語では)。入口の部品には 0 か所(11 の AC-420) |
| ファイルの大きさ | 定義ファイル・ステートファイル・変換の入力・`.env` ファイル(v0.9.0 以降)は、各 1 MiB(1,048,576 バイト)まで |
| 文字コード | 定義・ステート・変換の入力は UTF-8 |
| 入れ子の深さ | 定義の入力は 32 段まで(03 の 5 章)。変換は、展開後も 32 段まで(09 の 6.3)。深さ 1,000 の入力(定義・ステート・変換)でも異常終了せず、失敗を返す(11 の AC-412)。再帰に依存しない作りにするとよい |
| 品質ゲート | 整形の差分なし、静的検査の警告なし、3 OS でのテスト通過、行カバレッジ 80% 以上(11 の 7 章。具体の道具は言語ごとに選ぶ) |

## 7. 主要な概念の概観

```text
   スケジューラ(cron など)
        │  conductor run <ジョブID>   /   conductor pipeline <名前>
        ▼
  ┌─────────────┐   読む   ┌──────────────────┐
  │ conductor   │────────▶│ 定義ファイル      │  conductor.toml
  │             │          │ (TOML・検証済み)   │  [pipeline] と [[job]]
  │             │   読む/書く┌──────────────────┐
  │             │◀───────▶│ ステートファイル   │  <定義名>[.<run-id>].state
  │             │          └──────────────────┘
  │             │  起動(シェルなし)  ┌──────────┐
  │             │────────────────▶│ ジョブ    │ 子プロセス
  └─────────────┘◀───────────────│ (command)│ 終了コード
        │ 終了コード            └──────────┘
        ▼
   スケジューラ
```

1 回の呼び出しの流れ(`run` の場合。詳細は 05 章):

1. 定義を読んで検証し(失敗は 64)、run ID を決め、(v0.9.0 以降)`env_file` の `.env` をすべて読み(失敗は 64)、ステートを読んで定義と照合する(失敗は 65)。
2. ステートから「実行・スキップ・拒否(66)」を決める。
3. 実行なら、ジョブを起動して終了を待つ(必要ならリトライ)。終了コードを、成功・警告・エラーに分類する。
4. 分類と遷移から、次の動き(後ろのジョブのスキップ、`@end`、完了、再開位置)を決め、ステートを書く。
5. 終了コードを返す(成功・警告は 0、エラーはジョブの終了コード、シグナルによる中断は `128 + 番号`)。

ジョブの状態は、`pending` から始まり、`success`・`warning`・`error`・`skipped` のいずれかになる。`error` のジョブが再開位置になり、同じコマンドの再呼び出しで再実行される。全ジョブが済むと `completed = true` になる(`--remove-on-complete` なら、ステートファイルを消す)。
