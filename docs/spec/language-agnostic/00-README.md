# 00. README(言語非依存版 conductor 仕様書の案内)

この仕様書は、コマンドラインツール `conductor` の **v0.9.2 までの挙動**(v0.9.0 で、環境変数の注入と `.env`、`graph`、`--dry-run`、`init` が加わった) を、実装の言語・ライブラリ・ビルドの仕組みに依存しない形で規定したものである。「この仕様書だけを渡された実装者(人または AI)が、任意の言語で、ゼロから、利用者から見て同じ挙動のツールを実装できる」ことを目標とする。

## 1. 範囲と版

| 項目 | 内容 |
|------|------|
| 対象 | 実行ファイル `conductor` の、利用者から見える挙動。コマンドライン、定義ファイル、ステートファイル、終了コード、標準出力・標準エラーの内容、ジョブの起動とシグナルの扱い、変換 |
| 版 | v0.9.0 の機能を含む。版の表示は、配布の版(`conductor <版>`)で、参照実装の部品の版も `0.9.2` である(表示は `conductor 0.9.2`)。v0.9.0 で加わった機能には、各章で「v0.9.0 以降」と書く |
| 対応 OS | Linux、macOS、Windows。3 OS で同じ定義に同じ結果を返す。OS ごとの差は 07 の 8 章に集めた |
| 根拠 | 現行の参照実装のソースとテスト、および実機での実行結果。参照実装は、この仕様の実現の一例にすぎない |
| 方針 | 参照実装の挙動が正である。推測で書かない。確認できなかった点は「未確認」と書き、全件を [12-rebuild-guide.md](12-rebuild-guide.md) の 4 章に集めた |
| 対象外 | 実行ファイルの配布先の運用、リポジトリの設定(ブランチ保護など)。ファイルから確認できないため未確認 |
| 言語非依存の範囲 | 実装の言語、部品(ライブラリ)の選び方、内部の型・モジュールの分け方は規定しない。規定するのは、外から見える結果(終了コード、出力、作られるファイル、エラーの種類と文言)である。ただし、書式(定義・ステート・変換)は、03・06・09 章が書式の規則そのものを定める |

## 3. 読む順序

- **全体をつかむ**: 01 → 02 → 04(コマンドの形)→ 05(実行の意味)の順。
- **ゼロから実装する**: 01 → 02 → 12(順序と完了条件)を先に読み、12 の各段で指示される章(03〜11)を、段ごとに読む。受け入れは 11 章の AC で確かめる。
- **特定の挙動を確かめる**: 終了コードは 10、定義の書式と検証は 03、ステートは 06、出力の文言は 08、変換は 09、プロセスとシグナルは 07。v0.9.0 の機能は、環境変数と `.env` が 03 の 7.6・7.7 と 05 の 14 章、`graph` が 04 の 7.7 と 05 の 15 章と 08 の 11 章、`--dry-run` が 04 の 7.9 と 05 の 16 章と 08 の 11 章、`init` が 04 の 7.8 と 05 の 17 章と 06 の 14 章と 08 の 12 章。
- 05(意味論)は 03(定義)・06(ステート)の用語を前提にする。06 は 05 の「いつ何を記録するか」を前提にする。両方を行き来してよい。

## 4. 規定の強さの語

この仕様書の記述は、次の 3 段階のどれかに当たる。章ごとに、【規定】【目安】【任意】、または「必須」「実装に任せてよい点」の見出しで区別している。

| 語 | 同じ意味で使われる表記 | 意味 | 確かめ方 |
|----|------------------------|------|----------|
| 必須 | 【規定】、「強制」、「必須の挙動」、「必須(どの実装も同じ)」 | どの実装も満たす。利用者から見える結果(終了コード、出力、ファイル、エラーの種類・文言・行番号)は、同じにしなければならない | 11 章の受け入れテスト(AC)。不合格なら、仕様に合わない |
| 目安 | 【目安】、「仮」、「参照」(06 章の書式) | 参照実装の値、または現行の書式。他の実装は、異なる値・書式にしてよい。ただし、利用者から見える挙動は変えない。性能の基準値は、超えても不合格にせず警告として記録する(11 の 2 章に「強制」と書いたものを除く) | 計測、または比較 |
| 任意 | 【任意】、「実装に任せてよい点」 | 実装が選んでよい。利用者から見える結果に影響しない(内部の型、部品の分け方、待機の方式、ライブラリの選択など) | 確かめない |

- 「必須」と「目安」が表の同じ行に並ぶときは、行ごとの表記に従う。
- 参照用の書式(06 の 4 章のステートの TOML)を共有する必要がある場合(別の実装が書いたステートを読む場合など)は、参照用の書式をそのまま採る。共有しなければ別の書式でよい(06 の 0 章)。
- 「未確認」は、確認できなかった点を指す。断定ではなく、必要なら実機で確かめる。

## 5. 用語集

用語は 03〜11 で、次の意味で統一して使う。

| 用語 | 意味 |
|------|------|
| ジョブ(job) | 定義の `[[job]]` 1 つ。ID(`id`)、実行するコマンド(`command`)、結果の扱い(終了コードの集合、遷移、リトライ)を持つ。`conductor` が子プロセスとして起動する単位 |
| ジョブID | ジョブの識別子(`id`)。定義の中で一意。空でなく、`@` で始まらない文字列 |
| パイプライン(pipeline) | 1 つの定義ファイルが表すジョブの並び全体。名前(`[pipeline].name`)を持つ。1 ファイルに 1 パイプライン。`conductor pipeline <名前>` は、その全ジョブを記述順に処理する |
| 定義ファイル(definition file) | パイプラインを書く TOML ファイル(既定の名前は `conductor.toml`)。書式の版は `format_version = 1` |
| 記述順 | 定義ファイルの中での `[[job]]` の並び。ジョブの実行順と、遷移の方向(前から後ろ)を決める |
| `command` | ジョブが実行するコマンド。文字列(空白で分割し引用符を解く)または文字列の配列(分割しない)。シェルを介さず、直接起動する |
| 終了コード(exit code) | ジョブ(子プロセス)の終了コード。または `conductor` 自身の終了コード(文脈で区別する。後者は「`conductor` の終了コード」と書く) |
| 成功コード | ジョブを成功とみなす終了コードの集合。`success_exit_codes` があればその値、なければ `[0]` |
| 警告コード | ジョブを警告とみなす終了コードの集合(`warning_exit_codes`。0 を含まず、成功コードと重ならない) |
| 実行結果(execution) | 1 回のジョブの起動と終了の観測の結果(起動したか、終了コード、シグナルによる終了、起動失敗、中断)。07 の 4.3 |
| 分類(classification) | 実行結果の区分。`success`(成功)、`warning`(警告)、`error`(エラー)、および「分類なし」(起動する前に中断された場合) |
| 警告(warning) | ジョブの分類の 1 つ。`conductor` の終了コードは 0 で、流れは成功と同様に進む(遷移は `on = "warning"` で別に書ける)。別に、`reset --all` の「警告(`conductor: warning:`)」の表示がある(終了コード 0)。文脈で区別する |
| 遷移(transition) | ジョブの結果(`success` または `warning`)ごとに書く、次の動き。行き先は、記述順で後ろのジョブのID、または `@end`。`error` には書けない |
| `@end` | 遷移先の特別な値。以降のジョブをスキップして終える |
| スキップ(skip) | ジョブを実行せずに済ませること。理由は `byTransition`(遷移で飛ばされた)、`byEnd`(`@end` より後ろ)、実行済み(`AlreadyExecuted`。ステートには記録しない) |
| 起動前の判断 | ジョブを起動する前に、ステートから決める「実行(Run)・スキップ(Skip)・拒否(Reject)」 |
| 拒否(reject) | 順序外の呼び出し(前のジョブが終わっていない)など。ジョブを実行せず、ステートも変えず、終了コード 66 |
| ステート(state) | 実行の途中経過(各ジョブの状態、再開位置、`@end` に到達したか、完了したか)。06 章の論理項目 |
| ステートファイル | ステートを保存するファイル。定義ファイルと同じディレクトリの `<定義ファイル名>.state`(run ID があれば `<定義ファイル名>.<run-id>.state`) |
| ジョブの状態(`status`) | ステートの中の、ジョブごとの値。`pending`、`success`、`warning`、`error`、`skipped` |
| run ID | 同じ定義を、別々の実行単位で並行して使うときに、ステートファイルを分ける識別子。`A-Za-z0-9._-` の 1〜64 文字で、先頭は `.` でない。`--run-id` または環境変数で与える |
| 再開位置(`resume_job_id`) | 次に実行する、または再開するジョブのID。エラーで止まったとき、そのジョブになる |
| 再開(resume) | エラーなどで止まった実行を、同じコマンドをもう一度呼ぶことで、止まったジョブから続けること。成功・警告のジョブは実行済みとしてスキップされる |
| 完了(completed) | パイプラインのすべてのジョブが済んだ(最後のジョブの終了、`@end` への到達、スキップによる終了)状態。ステートの `completed = true` |
| リトライ(retry) | `[job.retry]` を書いたジョブが、指定の終了コードで終わったとき、待ってから同じジョブを実行し直すこと。ステートには回数を書かない。`conductor` が落ちたあとの再開は、最初の実行から数え直す |
| 中断(interrupt) | `conductor` がシグナル(UNIX 系: SIGHUP・SIGINT・SIGQUIT・SIGTERM、Windows: Ctrl+C)を受け取ること。「中断の合図」が立つ(合図は、立ったことと最初のシグナル番号を保持する)。終了コードは `128 + 番号` |
| 一括実行 / 個別実行 | `pipeline`(全ジョブを記述順に処理。内部の `RunMode` の Pipeline)/ `run`(ジョブ 1 つ。スケジューラが 1 つずつ呼ぶ。Individual) |
| スケジューラ | `conductor` を呼び出す外部のもの(cron など)。`conductor` 自身はスケジュール機能を持たない |
| 変換(convert) | 定義ファイルを TOML と YAML のあいだで変換する `convert` コマンド。定義の検証はしない |
| 環境変数の層(v0.9.0 以降) | ジョブに足す環境変数の出どころ。後ろが勝つ順に、`[pipeline].env_file`、`[pipeline.env]`、`[job].env_file`、`[job.env]`、自動の変数(`CONDUCTOR_*`)。引き継いだ環境(`conductor` が親から受け取ったもの)は、これらの手前の土台で、`conductor` は足すだけ(取り除かない) |
| `.env`(v0.9.0 以降) | `env_file` で指す、`KEY=VALUE` の行からなるファイル。書式は 03 の 7.7。実行の前にすべて読む。誤りは終了コード 64 |
| 予約名(v0.9.0 以降) | `CONDUCTOR_` で始まる環境変数の名前(ASCII の大文字小文字を区別しない)。利用者は、`env` にも `.env` にも書けない。自動の変数が使う |
| 自動の変数(v0.9.0 以降) | ジョブに常に足される `CONDUCTOR_PIPELINE`、`CONDUCTOR_JOB_ID`、`CONDUCTOR_RUN_ID`(run ID があるときだけ)、`CONDUCTOR_ATTEMPT`(1 から。リトライごとに増える) |
| 辺(`graph`、v0.9.0 以降) | 図の中の、ジョブから行き先(後ろのジョブまたは終点 `@end`)への矢印。成功と警告のそれぞれの行き先から作る。エラーに辺はない |
| 計画(`--dry-run`、v0.9.0 以降) | ジョブを実行せず、仮定した終了コード(既定は 0)で、実行と同じ判断を進めて得る「実行したら何が起こるか」の表示 |
| 仮定(assume、v0.9.0 以降) | `--assume <ジョブID>=<終了コード>` で与える、計画の中のジョブの終了コード(0〜255) |
| ひな形(`init`、v0.9.0 以降) | `conductor init` が作る、有効な定義の例(日本語と英語の 2 つの文面。パイプライン名だけが入れ替わる) |
| Intake / Parse / Depth / VersionCheck / Walk | 定義の読み込みの 5 段階(03 の 2 章)。Intake=場所の決定と読み取り、Parse=TOML の文法、Depth=入れ子の深さ、VersionCheck=`format_version`、Walk=構造・型・遷移などの検査。変換の入口の Intake、Resolve、Write は 09 章 |
| 耐久性(`Durable` / `Fast`) | ステートの書き込みで、ファイルの内容の同期を行う(Durable)か省く(Fast)か |
| at-least-once | ジョブの終了とステートへの記録のあいだで `conductor` が落ちると、ジョブが再実行されうる、という保証の範囲(少なくとも 1 回) |
| プラットフォーム層 | OS ごとに実装が違う処理(プロセスグループの指定、シグナルの送信、シグナル終了の読み取り、ディレクトリの同期)をまとめた 1 か所。OS の分岐は、ここの外に置かない |
| 参照実装 | この仕様の根拠にした、現行の実装。他の実装は、この仕様どおりに作る |
| 被試験体 | 受け入れテスト(11 章)にかける実行ファイル |
| AC | 受け入れテスト(`AC-<通し番号>`)。11 の 4〜6 章に全件 |
| NFR | 非機能要件(性能、堅牢性、セキュリティ、保守性)。11 の 2 章 |

## 6. 表記の規約

- 本文は日本語。識別子、コード、エラーの文は原文のまま(`コード` 書式)で書く。
- 終了コード、キー名、既定値、メッセージの文言は、挙動の値をそのまま書く。メッセージは、英語と日本語の両方がある場合に、両方を示す(08 章が全件)。
- 「章」「節」は、同じ文書の見出しの番号を指す(`§` や `5.2` の形でも書く)。他の文書への参照は、文書の番号を付ける(例: 「06 の 5 章」)。
- 擬似コードと関数の名前(`classify`、`decide_before_run` など)は、挙動を説明するための仮の名前で、実装がその名前や形で持つことは求めない。
- 型は言語に依らない言い方で書く(「整数」「文字列」「列」「真偽」。32 ビット符号つき整数など、範囲が重要な場合は範囲を書く)。擬似コードは `text` のコードブロックで示す。
- 文字数は Unicode のコードポイント単位で数える(バイトでも書記素でもない)。ただし、ファイルの大きさと位置はバイトで数える。
- 表の「行」は 1 始まりの行番号。「位置」はファイル先頭からのバイト位置(0 始まり)。
- 数値の範囲は、閉区間で「1〜255」のように書く(両端を含む)。
- 実行例は、特に記さない限り `LANG=C`(英語の表示)で、標準エラーと終了コードを示す。
- 「未確認」は、確認できなかった点を指す。断定しない。
- 受け入れテストの「根拠」の欄(11 章)に、参照実装のテストの名前を併記している。名前は出所の記録であり、規定の本体ではない。
