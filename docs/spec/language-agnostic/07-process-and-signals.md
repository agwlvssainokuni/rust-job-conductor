## 1. 構成要素と責務

言語・部品の分け方は実装に任せる。次の責務が、別々に(単独で検査できる形で)あることを想定する。構成の全体は [02-architecture.md](02-architecture.md) にある。

| 構成要素 | 責務 |
|----------|------|
| 分割器 | `command` の文字列を、コマンド名と引数に分ける。文字を 1 つずつ左から読む状態機械で、再帰を使わない。3 OS で同じ規則 |
| `command` の検査 | `command` を起動せずに検査する。成功なら分けた結果(コマンド名と引数の並び)を返す |
| ジョブの起動と待ち | 1 つのジョブを、シェルを介さずに起動し、終了を待ち、「実行結果」(4.3 節)を返す。失敗は値で返し、異常終了しない |
| 待機ループ | ジョブの終了を確かめ続ける。中断の合図の転送の判断もここで行う(5 章) |
| リトライの待機 | リトライの前に待つ。待機中に中断の合図を確かめる(7.5 節) |
| 中断の合図 | 「中断が要求された」ことと、最初に受け取ったシグナルの番号を、スレッド(並行の実行単位)の間で共有する値(6 章) |
| プラットフォーム層 | プロセスグループの指定、シグナルの送信、シグナル終了の読み取り、ディレクトリの同期。OS ごとに実装が違う |
| シグナル監視 | OS のシグナル(UNIX 系)/ Ctrl+C(Windows)を受け取り、中断の合図を立てる |
| 流れの制御 | 合図の準備、ジョブの起動の呼び出し、中断時のステートの記録、終了コード(128 + 番号) |
| 分類 | 実行結果を、成功・警告・エラー・分類なしと、報告する終了コードに変える(4.4 節) |

OS ごとの分岐と OS 固有の呼び出しは、プラットフォーム層の外に置かない(保守性の要件。[11 章](11-quality-and-build.md)の「非機能要件」)。

## 2. `command` の形式(定義の側の受理条件)

定義ファイルの `[[job]]` の `command` は、次の 2 つの形式のどちらか。

| 形式 | TOML での書き方 | 起動のときの扱い |
|------|-----------------|------------------|
| 文字列形式 | `command = "sh scripts/x.sh"` | 3 章の規則で、コマンド名と引数に分ける |
| 配列形式(v0.2.0 以降) | `command = ["sh", "-c", "echo hi"]` | 要素をそのまま使う(分割・引用符の処理・展開をしない) |

定義の読み込み時の検査(誤りは定義の誤り、終了コード 64):

| 入力 | 判定 |
|------|------|
| `command` キーがない | 誤り(必須の値がない) |
| 文字列で、前後の空白(Unicode の空白)を除くと空 | 誤り(`command` が空) |
| 配列が空(`[]`) | 誤り(配列が空) |
| 配列に文字列でない要素がある | 誤り(要素は文字列で書く)。要素ごとに報告する |
| 配列の先頭の要素が、前後の空白を除くと空 | 誤り(先頭の要素が空) |
| 配列の 2 番目以降が空文字列 `""` | 有効(空の引数として渡す) |
| 文字列でも配列でもない(数値・表など) | 誤り(型) |

定義の検査とは別に、実行の前にもう一度、全ジョブの `command` を 3.6 節のとおり検査する。

## 3. `command` の分割規則

### 3.1 入力と出力

- 入力: `command` の文字列(UTF-8)。
- 出力: コマンド名(`program`。空でない)と、引数の並び(`args`)。`args` の各要素が、そのまま 1 つの引数になる。
- シェルは使わない。変数展開(`$HOME`)、グロブ(`*`)、パイプ(`|`)、`;`、`&&`、リダイレクト(`>`)、バッククォート、`~`、
  括弧は **解釈しない**。普通の文字として引数に入る。パイプなどが要るときは、利用者が `sh -c '...'` を `command` に書く。

### 3.2 文法

文字は Unicode のコードポイント単位(UTF-16 の符号単位でも、書記素でもない)で、左から右へ 1 回だけ読む。区切り文字は次の 4 つだけ。

```text
separator := ' ' (U+0020) | '\t' (U+0009) | '\n' (U+000A) | '\r' (U+000D)
```

(U+000B、U+000C、U+00A0 などのほかの空白は区切りではなく、普通の文字。)

状態は 4 つ。これに加えて、`in_word`(語の途中か)と `current`(組み立て中の語)を持つ。

| 状態 | 入力の文字 | 動作 | 次の状態 |
|------|-----------|------|----------|
| Plain(引用符の外) | separator | `in_word` なら `current` を語として確定し、空にする。`in_word = false` | Plain |
| Plain | `'` | `in_word = true`(語を開始。まだ何も足さない) | Single |
| Plain | `"` | `in_word = true` | Double |
| Plain | 上記以外(`\` を含む) | `in_word = true`。その文字を `current` に足す | Plain |
| Single(`'...'` の中) | `'` | 何も足さない | Plain |
| Single | 上記以外(`\`、`"`、改行を含む) | その文字を足す | Single |
| Double(`"..."` の中) | `"` | 何も足さない | Plain |
| Double | `\` | 何も足さない(バックスラッシュを保留する) | DoubleBackslash |
| Double | 上記以外 | その文字を足す | Double |
| DoubleBackslash(`"..."` の中で `\` を 1 つ保留中) | `"` | `"` を 1 つ足す(保留の `\` は消える) | Double |
| DoubleBackslash | `\` | 保留していた `\` を 1 つ足す。今読んだ `\` が新しい保留になる | DoubleBackslash |
| DoubleBackslash | 上記以外の文字 c | `\` と c を足す | Double |

入力の終わりでの確定:

1. 状態が Plain でなければ(Single / Double / DoubleBackslash)、**閉じていない引用符**(誤りの種類 `UnclosedQuote`)。
2. `in_word` なら `current` を最後の語として確定する。
3. 語の列の先頭がなければ、または先頭の語が空文字列なら、**コマンド名がない**(誤りの種類 `Empty`)。それ以外は、先頭の語が `program`、
   残りが `args`。

要点:

- 引用符で囲んだ部分と囲まない部分は、隣り合っていればつなげて 1 つの語になる(`a"b c"'d e'f` は 1 語 `ab cd ef`)。
- `''` と `""` は、空の語(空の引数)になる(`in_word` が立つため)。ただし先頭の語が空なら `Empty`。
- 二重引用符の中で解釈するバックスラッシュは、「直後が `"`」のときだけ(`\"` → `"`)。`\n`、`\t`、`\\` なども、
  **解釈せずそのまま**(`\n` は 2 文字のまま)。ただし `\\` は、1 つ目のバックスラッシュを出力し、2 つ目を新しい保留にする。
  したがって `\\"` は「`\` と、エスケープされた `"`」になる(引用符は閉じない)。`\` の個数の偶奇で数える規則ではなく、
  直前に保留している `\` が 1 つあるかどうかだけで決まるので、上の表を左から機械的に適用すること
  (`"` の直前に `\` が 1 つ以上並んでいれば、`"` は常にエスケープされ、引用符は閉じない)。
- 引用符の外のバックスラッシュは普通の文字(Windows のパス `C:\dir\x.exe` がそのまま書ける)。一重引用符の中も同じ。
- 末尾がバックスラッシュのパスを二重引用符で囲むと `\"` が引用符のエスケープになり、閉じない(誤り)。一重引用符で書く。
- 文字列の長さに上限はなく、入れ子もないため、再帰やスタックの深さに依存しない(約 30 万引数の入力でも分割できる)。【規定】

擬似コード(同じ結果になる実装であれば、書き方は自由):

```text
words = []; current = ""; in_word = false; state = Plain
for c in コードポイント列:
  switch state:
    Plain:  if c in separator: if in_word: words.push(current); current = ""; in_word = false
            elif c == "'": in_word = true; state = Single
            elif c == '"': in_word = true; state = Double
            else: in_word = true; current += c
    Single: if c == "'": state = Plain else current += c
    Double: if c == '"': state = Plain
            elif c == '\\': state = DoubleBackslash
            else: current += c
    DoubleBackslash:
            if c == '"': current += '"'; state = Double
            elif c == '\\': current += '\\'            # state は DoubleBackslash のまま
            else: current += '\\' + c; state = Double
if state != Plain: return 誤り(UnclosedQuote)
if in_word: words.push(current)
if words が空 or words[0] == "": return 誤り(Empty)
return (words[0], words[1:])
```

### 3.3 受理の例

| 入力(command の文字列) | program | args |
|--------------------------|---------|------|
| `echo a b` | `echo` | `a`, `b` |
| `␣␣echo ⇥ a ⏎ b␣␣`(空白・タブ・改行の混在) | `echo` | `a`, `b` |
| `echo\r\na`(CR LF) | `echo` | `a` |
| `echo 'a b' 'c\d' '"x"'` | `echo` | `a b`, `c\d`, `"x"` |
| `echo "a \" b"` | `echo` | `a " b` |
| `echo "a\nb" "c\\d"` | `echo` | `a\nb`, `c\\d`(バックスラッシュは、そのまま 2 つ) |
| `echo "\\"x"`(`"` `\` `\` `"` `x` `"`) | `echo` | `\"x` |
| `C:\dir\x.exe a\ b` | `C:\dir\x.exe` | `a\`, `b` |
| `\\server\share` | `\\server\share` | (なし) |
| `prog 'C:\dir\'` | `prog` | `C:\dir\` |
| `echo --msg='a b'` | `echo` | `--msg=a b` |
| `echo a"b c"'d e'f` | `echo` | `ab cd ef` |
| `echo '' "" x` | `echo` | (空), (空), `x` |
| `echo ''` | `echo` | (空) |
| `echo a;b && c \| d > e $HOME * `` `x` `` (y)` | `echo` | `a;b`, `&&`, `c`, `\|`, `d`, `>`, `e`, `$HOME`, `*`, `` `x` ``, `(y)` |
| `echo 'あ い' う` | `echo` | `あ い`, `う` |
| `a 'b c'` | `a` | `b c` |

### 3.4 拒否の例

| 入力 | 誤りの種類 |
|------|-----------|
| `echo 'a` | `UnclosedQuote` |
| `echo "a` | `UnclosedQuote` |
| `echo "a\`(末尾が二重引用符の中のバックスラッシュ) | `UnclosedQuote` |
| `echo "a\\" b`(`\\` + `"` は、引用符のエスケープ) | `UnclosedQuote` |
| `prog "C:\dir\"` | `UnclosedQuote` |
| (空文字列) | `Empty` |
| `␣⇥⏎`(区切りだけ) | `Empty` |
| `''` | `Empty`(先頭の語が空) |
| `'' x` | `Empty`(先頭の語が空) |

### 3.5 配列形式の扱い

- 要素を一切加工せずに使う。先頭が `program`、残りが `args`。分割、引用符の解釈、展開、前後の空白の除去をしない
  (`"  lead and trail  "` も、そのまま 1 つの引数)。
- 先頭の要素が、前後の空白を除いて空(空文字列・空白だけ)、または要素が 0 個のときは `Empty`(定義の検査の二重の備え)。
  先頭の要素が空白を含むが空でないとき(`"my prog"`)は、そのまま `program`(`my prog` というファイル名を起動する)。
- 2 番目以降は空文字列でもよい(空の引数)。

### 3.6 誤りの表示と検査のタイミング

| 項目 | 内容 |
|------|------|
| 誤りの内容 | 種類(`UnclosedQuote` か `Empty`)と、固定の文 |
| 固定の文 | `UnclosedQuote` は `引用符が閉じていません`、`Empty` は `コマンド名がありません`。**入力の値を含めない**(秘密の値が `command` に入っていても表示に出ない)【規定】 |
| 利用者への表示(標準エラー) | `conductor: error: <定義ファイルのパス>: job '<ジョブID>': <文>`。文は表示言語に従う。英語は `command has an unclosed quote` / `command is empty`、日本語は `command の引用符が閉じていません` / `command が空です` |
| 検査の時点 | `run` / `pipeline` / `validate` は、定義の読み込みと検証のあと、**全ジョブ**の `command` を検査し、誤りのあるジョブをすべて報告して(1 ジョブ 1 行)、終了コード 64 で終わる。ジョブは 1 つも起動せず、ステートにも触れない |
| 順序 | シグナルの準備(`run`/`pipeline` のみ)→ 定義の読み込み(64)→ `command` の検査(64)→ ジョブID(68)→ run ID(68)→ ステートの読み込み(65)→ 照合(65) |
| 防御 | ジョブの起動の内側でも分割し直す。万一失敗したら、起動失敗の実行結果を返す(通常は到達しない) |

## 4. プロセスの起動

### 4.1 手順(時系列)

「ジョブの起動と待ち」(ジョブ、足す環境変数の並び → 実行結果。v0.9.0 以降。足す環境変数の並びは、名前と値の対の並びで、v0.8.0 以前は無い)。失敗はすべて戻り値で返し、異常終了しない。

1. 実行結果を初期化する: `started = true`、`exit_code = なし`、`terminated_by_signal = なし`、`start_failure = false`、
   `interrupted = false`、`signal_number = なし`。
2. `command` を分割する(文字列は 3 章、配列は 3.5 節)。失敗なら `start_failure = true` で返す。
3. **起動の前**に合図が立っていれば、起動せずに返す: `started = false`、`interrupted = true`、`signal_number = 番号`。
   (ジョブは実行されない。)
4. `program` に `args` を渡して起動の準備をし、足す環境変数の各 `(name, value)` を**並びの順に**、引き継いだ環境に足し
   (v0.9.0 以降。引き継いだ環境は残り、同じ名前は上書きされる。同じ名前が並びに 2 回あれば、後ろが勝つ)、プラットフォーム層の設定を適用する
   (UNIX 系: 新しいプロセスグループで起動する。Windows: 何もしない)。
5. 起動する。失敗なら `start_failure = true` で返す(`started` は `true` のまま)。
6. 5 章の待機ループで終了を待つ。時間切れ(タイムアウト)はない。自動のリトライもしない(リトライは流れの制御の層で行う。7.5 節)。
7. 終了を観測したら:
   - `exit_code` = OS が報告する終了コード(取れなければ なし)。
   - `terminated_by_signal` = シグナルで終了したときのシグナル番号(UNIX 系のみ。Windows は常に なし)。
   - **この時点で** 合図が立っていれば `interrupted = true`、`signal_number = 番号`。
8. 終了の状態を取得できないときは、`start_failure = true` で返す(分類で 127)。

### 4.2 起動の条件

| 項目 | 規定 |
|------|------|
| シェル | 使わない。`sh -c` や `cmd /C` を挟まない【規定】。起動するのは、分割(または配列)で得た `program` だけ |
| プログラムの探索 | 実行環境の標準の規則に従う(`program` に区切り文字がなければ、OS の標準の探索。`PATH` など)。`conductor` 独自の探索はしない |
| 作業ディレクトリ | 引き継ぐ(`conductor` を起動したときのカレントディレクトリ。定義ファイルの場所に移らない)。変更しない【規定】 |
| 環境変数 | すべて引き継ぐ。**v0.8.0 以前**は、追加・削除・上書きをせず、run ID も渡さなかった。**v0.9.0 以降**は、引き継いだ環境を残したまま、起動に渡された足す環境変数(定義の `env`・`.env` と自動の変数 `CONDUCTOR_PIPELINE`・`CONDUCTOR_JOB_ID`・`CONDUCTOR_RUN_ID`(run ID があるとき)・`CONDUCTOR_ATTEMPT`。05 の 14 章)を**足す**(同じ名前は上書き。取り除くことはしない)。値は、書いたとおりに渡す【規定】 |
| 標準入力・標準出力・標準エラー | すべて引き継ぐ(リダイレクトしない)。ジョブの出力は、`conductor` を介さず、そのまま流れる。`conductor` は、ジョブの出力を読まない・保存しない・ステートに書かない【規定】 |
| 引数の渡し方 | 分割した各引数を、そのまま OS に渡す(メタ文字は注入にならない)【規定】。Windows で `.cmd` / `.bat` を起動するときは、引数の引用を OS の起動の規則に合わせて安全に行う(または起動を拒否する)。どちらでも、引数の中のコマンドは実行されない【規定】 |
| 起動できなかった場合 | 起動の失敗は、原因(見つからない・実行権限がない・実行できない形式・ディレクトリを指定した、など)を区別せず `start_failure = true`。終了コードは 127(分類)。表示は `conductor: error: job '<ID>': cannot start command '<プログラム名>'`(英語)。ジョブの終了コード・シグナルは なし |
| 時間の上限 | ない。ジョブが終わらなければ、`conductor` は待ち続ける |
| ジョブの強制終了 | しない(強制終了のシグナルを送る機能はない) |

### 4.3 実行結果の各項目

| 項目 | 意味 |
|------|------|
| `job_id`, `command` | 定義のジョブIDと `command` |
| `started` | 起動を試みたか。`false` は、起動の前に合図が立っていたときだけ |
| `exit_code` | OS が報告する終了コード。UNIX 系でシグナルによって終了したときは なし。Windows は常に値がある。UNIX 系の終了コードは下位 8 ビット(300 を返すと 44)、Windows は 32 ビット符号つきのまま(300 のまま) |
| `terminated_by_signal` | UNIX 系のシグナル終了の番号。Windows は常に なし |
| `start_failure` | 分割の失敗、起動の失敗、終了の状態の取得の失敗のいずれか |
| `interrupted` | 起動前、または、終了の観測の直後に、合図が立っていた |
| `signal_number` | `interrupted` のとき、**最初に受け取った**シグナルの番号 |

### 4.4 分類(終了コードの決定)

実行結果は、次の優先順位で、最初に当てはまるものを採る。

| 順 | 条件 | 分類 | 報告する終了コード |
|----|------|------|--------------------|
| 1 | `started = false` かつ `interrupted` | 分類なし(エラーとして記録しない) | `128 + signal_number` |
| 2 | `started = false` で中断でもない(起こらない) | エラー | 127 |
| 3 | `interrupted`(起動済み) | エラー | `128 + signal_number`(ジョブ自身の終了コードは見ない。ジョブが 0 で終わっていてもエラー) |
| 4 | `start_failure` | エラー | 127 |
| 5 | `terminated_by_signal = n` | エラー | `128 + n` |
| 6 | `exit_code = なし`(起動して終わったのに値がない) | エラー(`conductor` 自身のエラー) | 1 |
| 7 | `exit_code` が成功コード(既定は `[0]`、`success_exit_codes` で指定) | 成功 | 0 |
| 8 | `exit_code` が `warning_exit_codes` | 警告 | 0 |
| 9 | `exit_code = 0` で成功コードに含まれない | エラー(`conductor` 自身のエラー) | 1 |
| 10 | 上記以外 | エラー | `exit_code` のまま |

`conductor` の終了コードは、報告する終了コードを 0〜255 に合わせたもの(範囲内はそのまま。範囲外は下位 8 ビット。エラーで
下位 8 ビットが 0 になるときは 1)。詳細は [10-errors-and-exit-codes.md](10-errors-and-exit-codes.md)。

## 5. 待ち(待機ループ)

ジョブの終了を待つ方法は、実装に任せる(ポーリング、OS の終了通知、専用スレッドなど)。次を守る。

| 項目 | 内容 | 強さ |
|------|------|------|
| 回収 | ジョブを回収する(終了の状態を読む)のは、待機ループだけ | 【規定】 |
| 転送の判断 | 「ジョブがまだ終わっていない」と観測した時点で、**まだ転送していない**かつ合図が立っていれば、シグナルをジョブに **1 回だけ** 転送する(7.2 節) | 【規定】 |
| 終了済みへの送信の禁止 | 終了済み・回収済みのジョブには送らない。ジョブが先に終わっていれば、合図が立っていても転送しない | 【規定】 |
| 転送は 1 回 | 2 回目以降の合図(同じシグナルでも別のシグナルでも)で、再度の転送や強制終了はしない | 【規定】 |
| 転送のあと | ジョブの終了を待ち続ける(ジョブがシグナルを無視すれば、`conductor` はそのまま待ち続ける) | 【規定】 |
| 確認の間隔 | 参照実装は、終了の確認をくり返し、確認と確認のあいだに 1、2、4、8、10、10、…(ミリ秒。前回の 2 倍、上限 10 ms)眠る | 【目安】(間隔が長すぎて、合図からの転送が目に見えて遅れないこと。10 ms 以下を推奨) |
| 待機の専用スレッド | 参照実装は使わない(呼び出したスレッドで待つ) | 【任意】 |

## 6. 中断の合図

「中断の合図」は、`conductor` がシグナルを受け取ったことを、ジョブを待つ側へ伝える値。

| 項目 | 規定 |
|------|------|
| 内容 | 「立っているか」と、立っているなら「最初のシグナルの番号」 |
| 初期 | 立っていない |
| 立てる(番号 n) | 立っていなければ n を保存する。**すでに立っていれば何もしない**(最初の番号が残る)。番号は任意の整数でよく、負数や非常に大きい値でも、「立った」ことは記録される |
| 性質 | 立ったら下りない。シグナル監視(別の実行単位)と待つ側のあいだで、安全に共有できる(競合しない)。待つ側は読むだけ |
| 等価性 | 番号が等しければ等しい |

実装の仕方(1 つの原子的な整数にする、など)は【任意】。

## 7. シグナル処理

### 7.1 準備(両 OS 共通)

- `run` と `pipeline` だけが、**定義の検査より前**に、シグナルの監視を始める【規定】。
  `watch`・`reset`・`validate`・`convert` は監視せず、OS の既定の動作で終わる。v0.9.0 以降の `graph`・`init` も監視しない。
  `run`・`pipeline` の `--dry-run` も、監視を始めない(ジョブを起動しないので、中断の合図を待つものがない。通常の準備の、シグナルを除く部分だけを行う)。
- 中断の合図を 1 つ作り、シグナル監視に渡す。
- 監視の登録は **プロセスで 1 回だけ**。2 回目の呼び出しは「すでに登録済み」として、流れを成功と同様に続ける
  (2 回目に渡した合図には配線されない)。登録に失敗したときは、標準エラーに
  `conductor: error: failed to set up signal handling` を書き、終了コード **70** で終わる(定義の検査もジョブの起動もしない)。
  登録に失敗した場合は、次の登録を許す(登録済みの印を戻す)。
- 「最初の番号」は、合図を立てる操作が呼ばれた順の最初。

### 7.2 UNIX 系(Linux、macOS)

受け取るシグナルは **SIGHUP(1)、SIGINT(2)、SIGQUIT(3)、SIGTERM(15)** の 4 つ【規定】。受け取るたびに、合図を立てる操作(6 章)を、そのシグナルの番号で呼ぶ。
登録後、これらのシグナルでは、OS の既定の動作(終了)をしなくなる。監視は専用の実行単位で行ってよい(【任意】)。

時系列(ジョブの実行中に、利用者が `kill -TERM <conductor の pid>` したとき):

1. `conductor` が SIGTERM を受け取る。監視が合図を立てる(番号 15)。
2. 待機ループは、次の確認(参照実装は最大 10 ms 後)で「まだ終わっていない」を観測し、合図が立っているのを見る。
3. ジョブの pid に、**同じシグナルを 1 回**送る。送る前に次を検査する。
   - pid が 0 より大きく、OS のプロセス識別子の範囲に収まる(0 や負にならない。プロセスグループへの送信にならない)。
   - シグナルが `{SIGHUP, SIGINT, SIGQUIT, SIGTERM}` のどれか(SIGKILL、SIGSTOP、SIGCONT、SIGUSR1、0、負、9999 は送らない)。
   - 送信先は、**ジョブの子プロセスの pid だけ**。ジョブの子孫(`sh -c` が起こした孫など)には、`conductor` は送らない。
   - 送信の失敗は無視する。
4. ジョブは、受け取ったシグナルの既定の動作で終了するか、自分で処理する。`conductor` は待ち続ける。2 回目以降のシグナルでは、何も追加しない。
5. ジョブの終了を観測する(回収する)。`exit_code`(シグナル終了なら なし)と `terminated_by_signal` を読み、直後に合図が立っているので
   `interrupted = true`、`signal_number = 15` を足す。
6. 分類で「エラー、`128 + 15 = 143`」となり、流れの制御はこの結果をステートに**エラーとして**記録する(再開位置はそのジョブ)。
7. `conductor` は **143** で終わる(`pipeline` は次のジョブを起動しない)。

その他:

- ジョブは、`conductor` が起動時に作る **新しいプロセスグループ**(グループ ID は子の pid)で動く【規定】。端末の
  Ctrl+C(SIGINT)は、フォアグラウンドのプロセスグループに配られるため、ジョブには直接届かず、`conductor` が受けて 1 回転送する
  (SIGINT のとき、ジョブは `terminated_by_signal = 2` で終わるのが典型)。
- 転送の許可集合にない番号で合図が立った場合(`conductor` 本体の監視は 4 つだけを受けるため、通常は起こらない。起動の部品を単独で使う場合のみ)は、
  送信せず、ジョブが自分で終わるのを待ち、終わりを観測した後に `interrupted = true`、`signal_number = その番号` を足す
  (ジョブの終了コードは `exit_code` に残るが、分類では見ない)。
- 時間を空けて複数のシグナルが届いたときは、到着順の最初の番号が残る(INT のあとの HUP でも 2)。
  ほぼ同時に届いたときに、どれが「最初」になるかは**規定しない**。参照実装では、番号の小さい順に処理されるため、小さい番号が残りうる
  (例: INT(2)と HUP(1)がほぼ同時なら HUP の 1)。
- 終了コードの例: SIGHUP は 129、SIGINT は 130、SIGQUIT は 131、SIGTERM は 143。

### 7.3 Windows

受け取るのは **Ctrl+C(番号 2)だけ**【規定】。OS のコンソールのイベントとして受け取り、合図を立てる(番号 2)。
登録の失敗の原因が「すでに別のハンドラが登録されている」場合は「すでに登録済み」、それ以外は登録の失敗として扱う(7.1 節)。

時系列(ジョブの実行中に、利用者が Ctrl+C を押したとき):

1. ジョブは `conductor` と **同じコンソール**で起動されている(新しいプロセスグループを作らない)。
   Ctrl+C は、OS が、同じコンソールを共有するプロセス(`conductor` とジョブ)の両方に配る。
2. `conductor` のハンドラが合図を立てる(番号 2)。
3. 待機ループは転送を試みるが、Windows の転送は **何もしない**(追加の送信をしない)【規定】。
4. ジョブは、OS から受け取った Ctrl+C で(既定の動作で)終了する。
5. 終了を観測する。シグナル終了の番号は常に なし、`exit_code` は OS の終了コード(Ctrl+C による終了コード)。直後に合図が立っているので
   `interrupted = true`、`signal_number = 2`。
6. 分類で「エラー、`128 + 2 = 130`」。ステートに**エラーとして**記録し、**130** で終わる。

その他:

- Ctrl+Break とコンソールを閉じたときの通知は、この版の対象外(OS の既定の動作)。受信するかは未確認。
- 自動の試験環境(CI の Windows ランナー)には、対話的なコンソールがなく、Ctrl+C を安定して送る方法がないため、この経路は自動テストにしない。
  リリース前に実機で手動確認する(確認項目: 終了コード 130、ジョブの子プロセスが残らない、
  `watch` で中断したジョブが `error` で次が `pending`、`run -v` の表示に `interrupted by signal 2`)。手順は 11 章の手動の受け入れテストにある。

### 7.4 合図が立つ時点ごとの動作(流れの制御)

| 合図が立った時点 | 動作 | ステートの記録 | 終了コード |
|------------------|------|----------------|------------|
| ジョブの起動の呼び出しの前(`started = false`) | ジョブを起動しない | 分類なし。エラーとしては記録しない。再開位置はそのジョブ | `128 + 番号` |
| ジョブの実行中 | 1 回転送(UNIX 系)。ジョブの終了を待つ | そのジョブを**エラー**として記録(ジョブが 0 で終わっても) | `128 + 番号` |
| ジョブの終了の観測の直後(転送が間に合わなかった場合を含む) | 起動済みで `interrupted = true`(上の行と同じ扱い) | エラー | `128 + 番号` |
| `pipeline` のジョブとジョブのあいだ(ジョブの結果は成功か警告で、完了ではない) | 次のジョブを起動しない | 記述順で、まだ起動していない最初のジョブ(エラーのジョブが先にあればそれ)を再開位置にして、中断を記録。エラーとは記録しない。`-v` で `interrupted by signal N` | `128 + 番号` |
| `pipeline` の最後のジョブが完了した直後 | 完了の処理(`--remove-on-complete` ならステートを削除)をして終わる | 完了 | 0(合図は無視される) |
| リトライの待機中(v0.8.0 以降) | 待機を打ち切る。`started = false`、`interrupted = true`、`signal_number = 番号` の実行結果を作る。次の実行はしない | 分類なし、再開位置はそのジョブ。エラーとしては記録しない | `128 + 番号` |
| 定義の検査・ステートの読み込み・照合の途中 | 検査は最後まで進める | (定義の誤り 64、ステートの誤り 65、拒否 66、スキップ 0 の終了コードが、中断の終了コードより優先する) | 各検査の値 |

### 7.5 リトライの待機

「待機(秒数, 合図)」→ 「経過」または「中断(最初の番号)」。OS 固有のコードを持たない。

- 手順: ループで ① 合図が立っていれば、すぐ「中断(最初の番号)」。② 開始からの経過が秒数以上なら「経過」。③ 短い時間(残り時間と、次に述べる上限の小さい方)だけ眠る。
- 合図は、待機の開始時と、**50 ms 以下の間隔**で確かめる【目安】。長い待ちでも、合図から **1 秒以内**に返る【規定】
  (例: 3600 秒の待機に、200 ms 後に合図を立てて、全体が 1.2 秒未満)。
- 秒数が 0 のときは、合図が立っていなければ、すぐ「経過」。合図が立っていれば「中断」。
- 複数の合図は、最初の番号を返す。

## 8. プラットフォーム差と OS 分岐の規則

### 8.1 差の一覧

| 項目 | UNIX 系(Linux、macOS) | Windows |
|------|------------------------|---------|
| ジョブのプロセスグループ | 新しいグループ | 指定しない(同じコンソール) |
| 監視するシグナル | SIGHUP・SIGINT・SIGQUIT・SIGTERM | Ctrl+C のみ(番号 2) |
| ジョブへの転送 | 子の pid に、シグナルを 1 回(許可集合のみ) | しない(OS が Ctrl+C を配る) |
| シグナル終了の読み取り | 終了の状態からシグナル番号を得る | なし(終了はすべて終了コード) |
| 終了コードの範囲 | 下位 8 ビット | 32 ビット符号つきのまま(`conductor` が報告する値は、0〜255 に合わせる) |
| ステート書き込み後のディレクトリの同期 | ディレクトリを開いて同期する。失敗は無視。親が空なら `.` | しない |
| 端末の色 | 使える(標準出力が端末で `NO_COLOR` が未設定か空のとき) | 使わない(色なし) |
| 自動の受け入れテスト | 11 章の「シグナルと中断」(UNIX 系) | Windows 専用の項目と、手動の確認 |

### 8.2 分岐を置く場所の規則

OS ごとの分岐と OS 固有の呼び出しは、プラットフォーム層(OS 固有の処理をまとめた 1 か所)の外にない【規定】。
言語の仕組みで強制できるなら強制し、できなければ、ソースの検索による検査で確かめる(11 章の保守性)。

- ジョブの起動の部品と、`conductor` の入口の部品のそれぞれに、プラットフォーム層を持つ。
- 安全でない(型や境界の検査を外す)呼び出しは、シグナル送信の 1 か所だけ(それがある言語では)。ほかでは使わない。
- ネットワークに接続しない(実装がネットワークの機能を持たない)。
- 製品のコードは、外部の入力(引数・環境・ファイル・OS の結果)に対して、異常終了する書き方をしない(失敗は値で返す)。

## 9. 想定外の内部の誤り

- 実行の入口で、想定外の内部の誤り(実装の不具合による異常終了)を捕まえる仕組みを最初に入れる。内部の誤りが起きると、
  標準エラーに固定の英語の 1 行 `conductor: error: internal error`(ロケールを判定しない)を書き、終了コード **70** で終わる。
  標準エラーへの書き込みが失敗しても 70 で終わる。【規定】
- 入口は、流れの結果の終了コードで、プロセスを 1 回だけ終了させる。入口に、わざと異常終了を起こすコマンドを持たない。
- ジョブの実行中に内部の誤りが起きると、子プロセスの終了を待たずに終わり、ジョブが孤児として残りうる。ステートは直前の完全な内容のままで、
  次の実行はそのジョブを再実行しうる(at-least-once の範囲)。
- `conductor` が SIGKILL などで強制終了されたときも、ジョブは残って動き続けうる(検知も停止もしない)。
