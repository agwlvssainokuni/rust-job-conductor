# 03. 定義ファイルの書式と検証

この文書は、`conductor` の定義ファイルの書式と、読み込み時の検証を定める。この文書だけで、TypeScript(Node.js)でゼロから、同じ受理・拒否・エラー(種類、文言、行番号)を返す読み込み処理を実装できることを目標とする。

- 定義ファイルの書式は **YAML(主)** と **JSON** の 2 つ。書式は**拡張子**で決める(第 2 節)。既定のファイル名は `conductor.yaml`。
- 検証は、見つけた誤りを**まとめて**返す。ただし、早い段階の誤り(取り込み、文法、展開と上限、版)は 1 件だけで打ち切る(第 2 節)。
- 定義の内容は、読み込みでは実行も評価もしない。`command` の文字列は、そのまま保持する。
- 確認できなかった点は「未確認」と書く。この文書の作成時に実際に動かして確かめた点は「確認」と書き、確かめた環境(Node.js v26.13.0、YAML ライブラリ `yaml` 2.9.1)を第 7 節に記す。実装時には、実際に採用する版で、第 7.5 節の試験を再度行う。
- 「必須」と書いた挙動は、利用者から見える結果(受理/拒否、エラーの種類・文言・行番号、取り込み後の値)であり、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、利用者から見える結果が変わらない範囲で、実装が選んでよい。
- このツールの終了コード、エラー行の標準エラーへの出し方は [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方は [08. 出力と多言語対応](08-output-and-i18n.md) に従う。この文書は、エラーの内容(種類・位置・理由)までを定める。
- YAML と JSON の読み取り(第 4〜7 節)は、[09. 変換器](09-converter.md)と共有する。実装は、`src/definition/` の中に「木の読み取り」の部分(`tree.ts`、`read-yaml.ts`、`read-json.ts`、`limits.ts` など。ファイル名は任意)を置き、`src/convert/` はその公開関数を使う。
- 実装は TypeScript の `strict`、ESM、Node.js 上の実行である(共通の前提は [02. アーキテクチャ](02-architecture.md))。読み込み処理は、利用者の入力の誤りを**例外ではなく戻り値**(結果の型)で返す。例外(`throw`)は、実装の不具合(想定外の内部失敗)にだけ使う。

## 1. 記法と用語

| 語 | 意味 |
|----|------|
| 文字 | Unicode のスカラー値(コードポイント。サロゲートを除く)。「N 文字」は、この単位で数える(UTF-8 のバイト数でも、書記素でも、JavaScript の文字列の `length`(UTF-16 コード単位)でもない)。TypeScript では、文字列を `for...of` で回すか `Array.from(s).length` で数える。文字列のバイト数は `Buffer.byteLength(s, 'utf8')` で数える。 |
| 空白を取り除く(trim) | 文字列の先頭と末尾から、Unicode の White_Space 属性を持つ文字(U+0009〜U+000D、U+0020、U+0085、U+00A0、U+1680、U+2000〜U+200A、U+2028、U+2029、U+202F、U+205F、U+3000)を取り除く。「空白だけ」は、取り除いた結果が空文字列になること。**`String.prototype.trim()` は使えない**(確認: `trim()` は U+FEFF を取り除き、U+0085 を取り除かない。この列挙と異なる)。正規表現 `/^\p{White_Space}+\|\p{White_Space}+$/gu` で置き換える方法が使える(確認: 上の列挙の全文字が `\p{White_Space}` に一致し、U+FEFF は一致しない)。実装時に、この列挙を使う単体テストで確かめる。 |
| 位置 | 値や構文要素の、入力中の場所。行(1 始まり)と列(1 始まり)の組。取り方は第 13 節。 |
| 行 | 行番号。1 始まり。LF の数で数える(CRLF でも同じ)。 |
| 値の型 | 木の値は、null、真偽値(boolean)、整数(integer)、範囲外の整数(hugeInt)、浮動小数(float)、文字列(string)、リスト(sequence)、マップ(mapping。キーと値の対応)の 8 種のいずれか(第 6 節)。 |
| 範囲外の整数 | 64 ビット符号つき整数の範囲(-9,223,372,036,854,775,808〜9,223,372,036,854,775,807)に収まらない整数の書き方。木では種別 `hugeInt` で表し、値は持たない。エラーにはしない(使う側の検査が拒否する)。 |
| マップのリスト | 要素がすべてマップであるリスト(`job` や `transitions`)。 |
| 誤り | エラーの 1 件。種類(`kind`)、行(なしもある)、理由(`reason`)をもつ(第 12 節)。 |
| 受理 | その値や書き方を誤りなく読み込むこと。拒否はその逆。 |

## 2. 書式の決定と処理の段階

### 2.1 書式の決定(拡張子)

- 定義ファイルのパスの指定(`--config`)があれば、それを使う。なければ、カレントディレクトリの `conductor.yaml`。
- 書式は、パスの**拡張子**で決める。拡張子は、パスの最後の要素(最後のパス区切りより後ろ。区切りは `/`、`process.platform` が `win32` のときは `\` も)の、最後の `.` から末尾まで。ASCII の大文字小文字を区別しない(`.YAML` は `.yaml`)。
- **`node:path` の `extname` は使わない**(確認: `path.extname('.yaml')` は空文字列を返す。この仕様では、`.yaml` という名前のファイルの拡張子は `.yaml` であり、YAML として読む)。上の規則を自前で実装する。

| 拡張子 | 書式 |
|--------|------|
| `.yaml`、`.yml` | YAML |
| `.json` | JSON |
| それ以外(拡張子なしを含む。`.txt`、`.xml`、末尾が `.` のものなど) | 拒否: `unsupportedFormat`、行なし、理由 ``拡張子は .yaml、.yml、.json のいずれかで書きます`` |

- この判定は、ファイルに触れる前に行う(ファイルが存在しなくても、拡張子が合わなければ `unsupportedFormat` になる)。
- 表示用のファイル名は、パスを文字列にしたもの(与えられた表記のまま。正規化しない)である。

### 2.2 処理の段階と打ち切り

`loadDefinition(path, expectedPipelineName)` は次の順に処理する。前の段階で失敗したら、そこで打ち切り、**その 1 件だけ**を返す(後ろの段階は実行しない)。最後の Walk だけが、複数の誤りを返す。

| 段階 | 内容 | 失敗の種類(`kind`) | 返る誤りの数 |
|------|------|----------------------|--------------|
| 1. Intake | 書式の決定、ファイルの読み取り | `unsupportedFormat` / `fileMissing` / `unreadable` / `tooLarge` | 1 |
| 2. Parse | 文法の検査(YAML はライブラリ、JSON は自前の読み取り)と、木の組み立て | `syntax` | 1 |
| 3. Resolve | 文書の数、タグ、キー、アンカーとエイリアスの展開、マージキー、重複キー、上限(要素数・文字の大きさ・入れ子の深さ) | `syntax` / `tooLarge` / `typeMismatch`(最上位がマップでない) | 1 |
| 4. VersionCheck | `format_version` | `versionMissing` / `versionUnsupported` | 1 |
| 5. Walk | 構造、型、遷移、終了コード、名前 | 第 12.3 節の種類のうち該当するもの | 1 件以上(位置の順) |

`parseDefinition(text, format, fileLabel, expectedPipelineName)` は、段階 2〜5 を文字列に対して行う(ファイルに触れない。同期関数)。`fileLabel` は、エラーの表示に使うファイル名である。

- `expectedPipelineName`(`pipeline` コマンドで渡されたパイプライン名)が無い(`undefined`)ときは、名前の照合をしない。
- 検証に成功したときだけ、定義(第 14 節)を返す。誤りが 1 件でもあれば、定義は返さない。
- 版の確認(段階 4)に通らないと、構造の検査(段階 5)は一切行わない。たとえば `format_version` が無い定義に、未知のキーや型の誤りがあっても、返るのは `versionMissing` の 1 件だけである。
- 文法の誤り(段階 2)は版の確認より先である。
- **JSON の段階 2 は、入力を 1 回、先頭から読み、最初に見つかった問題(文法の誤り、重複キー)で打ち切る。** 入れ子の深さ・要素数・文字の大きさの上限は、段階 2 では確認しない(段階 3 で確認する。第 5.3 節)。
- **YAML の段階 2 は、ライブラリで入力の全体(全文書)を読み終えてから、段階 3 に進む。** したがって、YAML では、入力の後ろにある文法の誤りが、前にある段階 3 の誤り(タグ、重複キー)より先に返る。
- 段階 3 は、木を、深さ優先・入力に現れる順に走査し、最初に見つかった問題で打ち切る。

## 3. 取り込み(Intake)

書式の決定(第 2.1 節)のあと、次の順に調べる。最初に当てはまったもので失敗する。

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルの情報(種別・大きさ)の取得で「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | 同、権限がない | `unreadable` | `読み取りの権限がありません` |
| 3 | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 4 | 通常のファイルでない(ディレクトリなど) | `unreadable` | `通常のファイルではありません` |
| 5 | 取得した大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `ファイルの大きさが上限(1 MiB)を超えています` |
| 6 | ファイルを開けない(権限) | `unreadable` | `読み取りの権限がありません` |
| 6' | ファイルを開けない(その他) | `unreadable` | `読み取りに失敗しました` |
| 7 | 読み取りの途中の失敗 | `unreadable` | 権限の問題なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 8 | 読み取った結果が上限を超える(順 5 のあとに大きくなった場合) | `tooLarge` | 順 5 と同じ |
| 9 | UTF-8 として解釈できない | `unreadable` | `文字コードが UTF-8 ではありません` |

実装(Node.js)の対応:

- 順 1〜5: `fs.promises.stat(path)`(シンボリックリンクはリンク先の情報で判定する。リンクを辿る)。失敗したとき、エラーの `code` が `ENOENT` なら順 1、`EACCES` か `EPERM` なら順 2、それ以外(`ENOTDIR`、`ELOOP`、`ENAMETOOLONG` を含む)は順 3。成功したら、`isFile()` が偽なら順 4、`size` が 1,048,576 を超えれば順 5。
- 順 6・7: `fs.promises.open(path, 'r')` で開き(失敗のときの `code` の分類は順 1〜3 と同じ。`ENOENT` はここでは順 6' になる)、`FileHandle.read` で、**上限 + 1 バイトまで**を、バッファに読む(読み取りが 0 バイトを返すか、上限 + 1 バイトに達するまで繰り返す)。読み取りの失敗の `code` が `EACCES`・`EPERM` なら権限、他は失敗。`FileHandle` は、`finally` で閉じる。**ファイル全体を一度に読む `readFile` は使わない**(上限を超える巨大なファイルを、メモリに読み込まないため)。
- 順 8: 読み取ったバイト数が 1,048,576 を超えていれば。
- 順 9: `new TextDecoder('utf-8', { fatal: true, ignoreBOM: true })` で復号する。不正なバイト列で `TypeError` を投げたら順 9。**`ignoreBOM: true` が必須**(既定では先頭の BOM が黙って取り除かれる。確認: `ignoreBOM: true` なら、先頭の BOM は U+FEFF の文字として残る)。確認: 過長な符号化(`C0 80`)、サロゲートの符号化(`ED A0 80`)、範囲外(`F4 90 80 80`)、単独の `FF` は、いずれも `fatal` で例外になる。

- 上限は **1 MiB = 1,048,576 バイトちょうどまで受理**し、1 バイトでも超えると `tooLarge`。
- 空のファイル(0 バイト)は、空の文字列として読めて、次の段階へ進む。YAML では文書が 0 個の入力として扱われ、`versionMissing` になる(第 6.7 節)。JSON では文法の誤り(`syntax`)になる(第 5 節)。
- 順 5 の大きさの確認は UTF-8 の確認(順 9)より先なので、1 MiB を超えて UTF-8 でないファイルは `tooLarge` である。
- 先頭の BOM(バイト列 EF BB BF)は不正ではない(順 9 を通る)。この後の段階が、BOM を取り除く(第 4.1・5 節)。
- いずれも、行番号は付かない。
- OS による権限・種別の判定の細部(Windows でのエラーの `code` など)は、実装に任せてよい(Windows での `code` の値は未確認)。必須なのは、上の表の条件の順序と、各理由の文言である。

## 4. YAML の受理する部分集合

YAML は、YAML 1.2(改訂 1.2.2)の文法で読み、スカラーの型は **コアスキーマ**(第 4.2 節)で決める。YAML 1.1 の型(`yes`/`no`/`on`/`off` の真偽値、`0777` の 8 進、日付、`<<` 以外の拡張など)は扱わない。

文法の細部(エスケープ、折りたたみ、インデントの規則など)は YAML 1.2.2 の規格に従い、読み取りライブラリがそれを実装する。**この文書が規格と別に決めること**は、次の 4.1 の表の「受理」「拒否」の列と、第 4.2〜4.6 節である。ライブラリがこれと違う結果を返すときは、この文書の規定が優先し、実装が補う(第 7 節)。

### 4.1 受理する部分集合と拒否するもの(一覧)

「確認」の列は、`yaml` 2.9.1(第 7 節の設定)で、ライブラリがその入力をどう扱ったかである。

| 項目 | 扱い | 備考(確認) |
|------|------|------|
| 入力の先頭の BOM(U+FEFF) | 受理(無視) | 実装が、ライブラリに渡す前に取り除く(位置にも数えない。第 13.1 節) |
| 改行 | LF、CRLF(混在可)を受理 | CRLF の行番号が LF の数と一致することを確認。**CR だけの改行は、この仕様では扱わない**(確認: ライブラリが改行と扱わず、文法の誤りになる場合がある。結果は `syntax`) |
| インデント | 半角スペースだけ。タブをインデントに使うことは拒否(`syntax`) | ライブラリが拒否する(エラー `TAB_AS_INDENT`)。`a:` + タブ + `1`、`-` + タブ + `b`、フロー形式の中のタブ、引用符なしのスカラーの途中のタブは、インデントではないので受理される |
| コメント(`#`) | 受理し、**捨てる**(値に影響しない)。`foo#bar` の `#` は、スカラーの一部 | 確認 |
| ブロックのマップ(`key: value`)、ブロックのリスト(`- item`) | 受理 | 親のキーと同じ桁の `- `(インデントなしのリスト)も受理(確認) |
| フローのマップ(`{a: 1}`)、フローのリスト(`[a, b]`) | 受理。入れ子、複数行、末尾のカンマ、`{}`、`[]` も受理 | 確認 |
| 引用符なしのスカラー(1 行、複数行) | 受理。型は第 4.2 節で決める | 先頭が `@` または `` ` `` のものは拒否(`syntax`)。確認: ライブラリが `BAD_SCALAR_START` で拒否する |
| `'...'`、`"..."` のスカラー | 受理。常に文字列 | 未知のエスケープ(`"\q"`、`"\xZZ"`、範囲外の `"\U00110000"`)は拒否(`syntax`)。確認: ライブラリが `BAD_DQ_ESCAPE` で拒否する。**サロゲートのエスケープは第 7.4 節 #12 を参照** |
| ブロックスカラー(`\|`、`>`)、インデント・チョンプの指示子 | 受理。常に文字列 | 確認(`\|2`、`>`、`\|-` の値) |
| 単純キー(1 行の `key:`) | 受理 | **確認: ブロックのマップの引用符なし・引用符つきの単純キーが 1,024 文字を超えると、ライブラリが拒否する**(エラー `KEY_OVER_1024_CHARS`。1,024 文字ちょうどは受理)。結果は `syntax`。フロー形式の `{...}` の中のキーには、この制限は無い(確認) |
| 明示のキー(`? key` + `: value`) | キーがスカラーで、第 4.2 節の解決の結果が**文字列**なら受理。それ以外は拒否(第 4.4 節) | 確認(ライブラリはリストのキー `? [a]` も構文としては受理する。拒否は実装の仕事) |
| アンカー(`&name`)とエイリアス(`*name`) | **受理**。展開して扱う(第 4.3 節) | |
| マージキー(`<<`) | **受理**(第 4.5 節) | |
| タグ(`!!str`、`!!int`、`!foo` など、すべて) | **拒否**(`syntax`、理由 ``タグは使えません``、そのノードの位置の行) | 標準のタグも拒否する。確認: 検出方法は第 7.4 節 #3 |
| 複数の文書(`---` で区切る) | **拒否**(`syntax`、第 4.6 節) | 末尾の `---` も(空の文書がもう 1 つあるものとして)拒否 |
| 文書の開始(`---`)と終了(`...`) | 1 つの文書の前後に置くのは受理 | 確認 |
| ディレクティブ | `%YAML 1.2`、`%YAML 1.1`、`%TAG`、未知の `%FOO` を、いずれも**ライブラリが受理する**(確認)。実装は、ディレクティブに独自の検査を足さない | `%TAG` で定義した名前のタグは、タグとして拒否される |
| 文字列でないキー(`1:`、`true:`、`~:`、キーが空、`? [a]` など) | **拒否**(`syntax`、第 4.4 節) | |
| 重複したキー | **拒否**(`syntax`、第 4.4 節) | |
| 閉じていないフロー・引用符、不正なインデント、`a: b: c`(1 行に複数のブロックのマップ)、値の位置にある `-` だけ(`a: -`)、複数行にまたがる単純キー(`"a` 改行 ` b": 1`、`a` だけの行の次にキーの行が続くもの) | 拒否(`syntax`、理由 ``YAML の文法に誤りがあります``) | 確認: ライブラリがそれぞれエラー(`MISSING_CHAR`、`BAD_INDENT`、`BLOCK_AS_IMPLICIT_KEY`、`UNEXPECTED_TOKEN`、`MULTILINE_IMPLICIT_KEY`)を返す |
| 定義されていないアンカーの参照(`a: *x`、後ろで定義されるアンカーの参照を含む) | 拒否(`syntax`、理由 ``YAML の文法に誤りがあります``、そのエイリアスの行) | **確認: ライブラリは、パースの時点ではエラーにしない**。実装が、展開のときに検出する(第 4.3 節、第 7.4 節 #6) |
| 引用符なしのスカラーの中の制御文字(例: U+0007、NUL) | ライブラリの挙動に従う(確認: `yaml` 2.9.1 は受理する。この文書の例には使わない) | |

「受理」と書いた構文を、ライブラリの都合で拒否してはならない。表にない構文は、YAML 1.2.2 の規格どおりに、ライブラリの結果に従ってよい(未確認の部分は、この文書の例に使っていない)。

### 4.2 スカラーの解決(コアスキーマ)

**引用符なしのスカラー**(引用符も `|`・`>` もない書き方)の型は、スカラーの文字列**全体**に対して、次の順に判定する。ライブラリが返す型情報は使わず、実装が自前で判定する(ライブラリのスキーマは `failsafe` に設定し、すべての引用符なしのスカラーを文字列として受け取る。第 7.3 節)。

| 順 | 条件 | 結果の型 |
|----|------|----------|
| 1 | 空文字列、`~`、`null`、`Null`、`NULL` | null |
| 2 | `true`、`True`、`TRUE` / `false`、`False`、`FALSE` | 真偽値 |
| 3 | `.inf`、`.Inf`、`.INF`、`+.inf`、`+.Inf`、`+.INF` / `-.inf`、`-.Inf`、`-.INF` / `.nan`、`.NaN`、`.NAN` | 浮動小数(+∞、-∞、NaN) |
| 4 | `0x` + 1 桁以上の 16 進数字(`0-9a-fA-F`) | 整数(16 進。符号なし) |
| 5 | `0o` + 1 桁以上の 8 進数字(0〜7) | 整数(8 進。符号なし) |
| 6 | `[-+]?[0-9]+`(`007` は 7、`-0` は 0、`+7` は 7) | 整数(10 進) |
| 7 | `[-+]? ( \.[0-9]+ \| [0-9]+ (\.[0-9]*)? ) ([eE] [-+]? [0-9]+)?`(整数の書式は順 6 が先) | 浮動小数 |
| 8 | 上のどれでもない | 文字列 |

- **整数は `bigint` で値にする**。数字の列から、`BigInt(...)` で得る(16 進は `BigInt('0x' + 数字)`、8 進は `BigInt('0o' + 数字)`、10 進は符号を除いて 0 の並びを取り除いた数字から。符号は別に扱う)。**`Number` や `parseInt` を経由しない**(JavaScript の `number` は 2^53 を超える整数を正確に表せないため。例: `9007199254740993` は `Number` では 9007199254740992 になる)。
  - 値が 64 ビット符号つき整数の範囲(-9,223,372,036,854,775,808〜9,223,372,036,854,775,807)に収まれば、種別 `int`(値は `bigint`)。範囲を超える整数の書式(`9223372036854775808`、`0xFFFFFFFFFFFFFFFFFF`、`-9223372036854775809`)は、種別 `hugeInt`(値は持たない)にする(エラーにはしない。第 6 節)。使う側の検査(第 9 節)が、範囲外として拒否する(例: `format_version: 99999999999999999999` は `versionUnsupported`)。
  - **巨大な数字の列で、時間とメモリを使わない**ために、先頭の 0 を除いた数字の桁数が 24 を超えるものは、`BigInt` を呼ばずに `hugeInt` とする(10 進 19 桁、16 進 16 桁、8 進 22 桁を超えれば、必ず範囲外なので、結果は同じ)。24 桁以下なら `BigInt` で値を得て、範囲を比べる。
  - `-0` は整数 0(`0n`)。
- 浮動小数は、スカラーの文字列を **`Number(文字列)`** で値にする(確認: `Number('1.')`=1、`Number('.5')`=0.5、`Number('+.5')`=0.5、`Number('-.5e3')`=-500、`Number('1.e3')`=1000、`Number('1.5E-2')`=0.015)。順 7 の書式に一致した文字列だけを渡すこと(`Number` は `0x10` や空文字列、前後の空白も受け付けるため)。結果が `Infinity` / `-Infinity` になる(`1e999`)ときは、値は ±∞ のまま、「範囲を超えた」という印(`overflow: true`)を付ける(エラーにはしない。変換器だけが、これを拒否する)。極小の値(`1e-400`)は、確認: `Number('1e-400')` は 0 になる。この仕様では、0 の浮動小数として受理する(エラーにしない)。
- 浮動小数の例: `1.5`、`-0.0`、`.5`、`1.`、`1e3`、`1.5E-2`。文字列になるもの: `.`、`e3`、`1e`、`1.2.3`、`-`、`+`、`.e1`、`inf`、`nan`、`NaN`、`0b11`、`1_000`、`0x`(桁なし)、`0o8`、`+0x1`、`0X1F`。
- **`yes`・`no`・`on`・`off`・`y`・`n`(大文字小文字を問わず)は文字列**。日付・時刻らしい書式(`2001-01-01`、`12:30:00`)も**文字列**。
- 引用符つき(`'...'`、`"..."`)のスカラーと、`|`・`>` のブロックスカラーは、常に文字列(`'1'` は文字列 `1`、`"null"` は文字列 `null`)。
- 空の値(`key:` の後ろに何もない、`- ` の後ろに何もない)は、引用符なしの空文字列と同じ扱いで、**null**。アンカーだけで中身がない(`a: &x`)も null。フローのマップでキーだけを書いた `{a, b: 1}` と、明示のキーだけの `? a` の「値」は、ライブラリが値を `null`(JavaScript の `null`)で返す(確認)。**これも YAML の null として扱い、位置はそのキーの位置とする**。
- 定義ファイルの検査で、null は「どの型でもない値」である。`description:`(値なし)は `description` の型の誤り、`retry:`(値なし)は `retryNotTable`、`job:`(値なし)は `job` の型の誤り、未知のキーの値が null なら `unknownKey` になる(第 9 節)。

#### 書き方による型の違い(YAML で起きやすい誤り)

| 書き方 | 型 | 定義での結果の例 |
|--------|----|------------------|
| `format_version: 1` | 整数 | 受理 |
| `format_version: "1"` | 文字列 | `versionUnsupported`(整数でない) |
| `format_version: 1.0` | 浮動小数 | `versionUnsupported`(整数でない) |
| `format_version: 0x1`、`0o1`、`01`、`+1` | 整数(値 1) | 受理 |
| `format_version: 1_0` | 文字列 | `versionUnsupported`(整数でない) |
| `id: 1` | 整数 | `typeMismatch`(文字列で書く) |
| `id: yes`、`id: on` | 文字列 | 受理(YAML 1.1 の真偽値ではない) |
| `id: true` | 真偽値 | `typeMismatch` |
| `id: null`、`id: ~`、`id:` | null | `typeMismatch` |
| `interval: 30` | 整数 | `retryDurationInvalid`(文字列で書く) |
| `interval: 30s`、`interval: "30s"` | 文字列 | 受理 |
| `max: "3"`、`max: 3.0` | 文字列、浮動小数 | `retryMaxInvalid` |
| `remove_on_complete: yes` | 文字列 | `typeMismatch`(真偽値で書く) |

### 4.3 アンカーとエイリアス

- `&name` で付けたアンカーを、`*name` で参照できる。`name` は、空白と `,[]{}` を含まない 1 文字以上(ライブラリの規則)。
- エイリアスは、参照先のノードの内容に置き換わる(コレクションは複製して展開する)。展開後の木には、アンカーもエイリアスも残らない。
- 同じ名前のアンカーを再定義してよい。エイリアスは、それより前の**最後の**定義を指す(確認: `a: &x 1`、`b: &x 2`、`c: *x` で、`Alias.resolve(doc)` は 2 を返す)。
- アンカーより前にあるエイリアス(`a: *x` + `b: &x 1`)、定義のないエイリアスは、拒否: `syntax`、理由 ``YAML の文法に誤りがあります``、行はそのエイリアスの行(確認: `Alias.resolve(doc)` が `undefined` を返す)。
- 閉じたアンカーへの参照は再帰ではない(`a: &r [1]` + `b: *r` は受理)。**自分自身を含むエイリアス**(`a: &r [*r]`)は拒否: `syntax`、理由 ``アンカーが自分自身を含んでいます``、行はそのエイリアスの行。判定は、**走査中に開いているコレクションのノードの集合**(通常の走査で入っているものも、エイリアスを通って入っているものも含む)を持ち、展開しようとしたエイリアスの対象がその集合に含まれるかで行う(確認: `a: &r [*r]` で `Alias.resolve(doc)` は、それを含む配列自身を返す)。
- エイリアスをキーにしてよい(`*k : 1`)。参照先が、文字列に解決されるスカラーのときに限る(第 4.4 節)。
- **展開の上限**: 第 6.3 節(要素数 100,000、文字の大きさ 16 MiB、深さ 32)。アンカーの入れ子による爆発的な増加(`l0: &l0 [x, x]`、`l1: &l1 [*l0, *l0]`、…)は、この上限で止まらなければならない(必須)。上限を超えたら、複製・確保の**前**に打ち切る。ライブラリの `toJS()` / `toJSON()` は、**呼ばない**(展開を自前で数えるため)。
- 定義の中でアンカーを置ける場所は、定義に存在するノードの中だけである(根のキーは 3 つだけなので、例えば根に `defaults:` を足すと `unknownKey` になる)。典型的な使い方は、ジョブの中のキーの値(`success_exit_codes: &ok [0, 2]` を別のジョブで `*ok`)や、ジョブのマップ全体(`- &base` を、別のジョブが `<<: *base` で取り込む)である(第 16 節の例)。

### 4.4 キー

- マップのキーは、**文字列に解決されるスカラー**でなければならない。次は `syntax`、理由 ``キーは文字列で書きます``、行はそのキーの位置: 整数・真偽値・浮動小数・null に解決されるスカラー(`1: x`、`true: x`、`1.5: x`、`~: x`、キーが空の `: x`)、範囲外の整数、リストやマップのキー(`? [1, 2]`、`[a]: 1`、`{a: 1}: x`)。引用符つきは常に文字列なので受理(`"1": x`)。
- **重複したキー**は拒否: `syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置。判定は、解決した後の文字列の同一性(文字列の `===`。UTF-8 の符号化で完全一致するかと同じ)で行う。引用符の有無が違っても重複(`a: 1` と `"a": 2`)。入れ子のマップごとに別。エイリアスをキーにしたときは、参照先の文字列で判定する。マージキー `<<`(第 4.5 節)を同じマップに 2 回書くことも重複。
  - **ライブラリの重複キー検査は使わない**(`uniqueKeys: false` を指定する)。確認: 既定の検査は、キーの数の 2 乗に比例して遅く、10 万個のキーを持つ 1 MiB の入力で約 78 秒かかった(`false` なら約 0.4 秒)。実装は、マップごとに `Set<string>` を持って判定する。
- キーの空文字列(`"": x`)は受理する。キーの大文字小文字・前後の空白は区別する。
- この検査は、入力に現れる順(深さ優先)に、段階 3 で行う。重複と非文字列のキーが同じ位置にあれば、どちらでも同じ `syntax` だが、理由は非文字列が先(キーの解決が先)。

### 4.5 マージキー(`<<`)

- マージキーとして扱うのは、**引用符なし・タグなし**のキー `<<` だけ(ライブラリの `Scalar` の `type` が `PLAIN` で、値が `<<`。タグは元々拒否される)。`"<<"`(引用符つき)は、文字列のキー `<<` として、通常のキーと同じに扱う。エイリアスを通して得たキー `<<` も、通常の文字列のキーとして扱う(この仕様の決定)。ライブラリのマージの機能は使わない(`merge: false`)。
- 値は、マップ、またはマップだけのリスト(`<<: [*a, *b]`)。それ以外(整数・文字列・null(`<<: ~` を含む)、マップでない要素を含むリスト)は拒否: `syntax`、理由 ``マージキーの値がマップではありません``、行はマージキーの位置。
- 優先順位: マップ自身の(`<<` でない)キーが、マージの内容より優先する(自身のキーが `<<` の前にあっても後にあっても同じ)。値がリストのときは、**先頭のマップが優先**。マージされるマップが `<<` を含むとき(入れ子のマージ)は、そのマージも同じ規則で先に展開した結果を使う。優先されずに捨てられたキーは、エラーにしない。
- **キーの順**: マージで加わるエントリは、そのマップの `<<` のエントリがあった位置に、取り込み元の順(リストなら先頭のマップから)で並ぶ。捨てられたものは並ばない。その後ろに、`<<` の後ろにある自身のエントリが続く。
- **位置**: マージで取り込まれたエントリ(キーと値と、その中のすべての子)の位置は、そのマージキー `<<` 自身の位置に置き換える(元の位置は使わない)。これは、エラーの行を決めるための規則である(第 13 節)。
- 実装の指針(任意): `<<` のエントリは、走査で、取り込み元の内容を評価しながら、エントリの並びに「場所取り」を入れる。そのマップの全エントリの走査が終わってから(自身のキーの集合が決まってから)、場所取りを、捨てられないエントリで置き換える。

### 4.6 複数の文書と最上位

- 文書の数を数える(`---` で区切る。末尾の `---` の後ろが空でも、空の文書が 1 つあるものとして数える。`a: 1\n---\n` は 2 文書。確認: `parseAllDocuments` が 2 個の文書を返す)。文書が 2 つ以上ある入力は、ライブラリによる全体の読み取り(段階 2)が成功し、かつ最初の文書の走査(段階 3)で他の失敗が無かったときに限り、拒否: `syntax`、理由 ``複数の文書は書けません(1 ファイルに書ける文書は 1 つです)``、行は 2 つ目の文書の内容の位置の行(ライブラリの `contents.range[0]` を行に変換する。確認: `a: 1\n---\n\n\nb: 2\n` で 5 行目、`a: 1\n---\n` で 3 行目)。2 つ目の文書の `contents` が無い(`null`)ときは行なし(未確認: そのような入力を作れるかは確かめていない)。
  - 最初の文書の失敗(タグなど)は、2 つ目の文書の拒否より先に返る(入力に現れる順)。2 つ目以降の文書は、走査しない(要素数・大きさの加算に含めない)。
- 文書が 0 個(空の入力、コメントと空行だけ)は、**空のマップ**として扱う(結果は `versionMissing`。確認: `parseAllDocuments('')` と、コメントだけの入力は、長さ 0 の配列を返す)。
- 最初の文書の最上位が **null**(`---` だけの文書など、中身が空)も、空のマップとして扱う(確認: `---\n` の文書は、空の引用符なしスカラーを内容として持つ)。
- 最上位が、マップでもなく null でもない(リスト、文字列、数など)なら、拒否: `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置。

## 5. JSON の受理する形式

JSON は、RFC 8259 の厳格な形式で読む。読み取りは**自前の小さな字句・構文解析**で行う(第 5.3 節)。**`JSON.parse` は使わない**。理由(確認):

- 重複キーを黙って後勝ちにする(`JSON.parse('{"a":1,"a":2}')` は `{ a: 2 }`)。この仕様は、重複キーを拒否する。
- 位置(行・列)を返さない。
- 数をすべて `number` にする(`9223372036854775808` は 9223372036854776000 に、`1e400` は `Infinity` になる)。この仕様は、整数を `bigint` で厳密に扱い、範囲外の整数と浮動小数の溢れを区別する。
- `__proto__` などのキーを、オブジェクトの性質として扱いうる。この仕様の木は、キーを文字列として持つ配列で表す(第 6.1 節)。

| 項目 | 規定 |
|------|------|
| 入力 | UTF-8 で復号済みの文字列(第 3 節)。先頭の BOM(U+FEFF)は無視する(位置には数えない。第 13.1 節)。 |
| 空白 | 半角スペース、タブ、LF、CR だけ。それ以外(垂直タブ、全角スペースなど)を、トークンの間に置くことは拒否。 |
| コメント(`//`、`/* */`、`#`) | **拒否**(`syntax`)。 |
| 末尾のカンマ(`[1,]`、`{"a":1,}`)、連続したカンマ、先頭のカンマ | **拒否**(`syntax`)。 |
| リテラル | `true`、`false`、`null`(小文字だけ)。`True`、`NaN`、`Infinity`、`undefined` は拒否。 |
| 文字列 | `"..."` だけ(単一引用符は拒否)。中にタブを含め、U+0000〜U+001F を直接書くことは拒否(`\t` などで書く)。U+007F 以上は直接書いてよい。エスケープは `\"`、`\\`、`\/`、`\b`、`\f`、`\n`、`\r`、`\t`、`\uXXXX`(16 進 4 桁。大文字小文字どちらでも)。それ以外のエスケープは拒否。`\u` でサロゲートの前半(U+D800〜U+DBFF)に、後半(U+DC00〜U+DFFF)の `\u` が続く対は 1 つの文字にする。**対にならないサロゲート**(単独の前半、単独の後半)は拒否(`syntax`)。 |
| 数 | `-?(0\|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` だけ。`+1`、`01`、`.5`、`5.`、`1e`、`0x10`、`1_000` は拒否。 |
| キー | 文字列だけ。 |
| 重複したキー | **拒否**(`syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置)。判定は、エスケープを解いた後の文字列の完全一致(`"a"` と `"a"` は重複)。 |
| 最上位 | 任意の JSON の値を、文法としては受理する。最上位がオブジェクト(マップ)でなければ、第 6.7 節のとおり `typeMismatch`。JSON の `null` も(YAML と違い)マップではないので `typeMismatch`。 |
| 空の入力、空白だけの入力 | 拒否(`syntax`)。 |
| 最上位の値の後ろ | 空白以外が続くことは拒否(`syntax`。複数の値、`{}{}`、後ろのゴミ)。 |

### 5.1 数の型

- 整数: `-?(0|[1-9][0-9]*)` だけ(小数部も指数部もない書き方)。`-0` は整数 0。値は**数字の列から `bigint` で**得る(`Number` を経由しない)。64 ビット符号つき整数の範囲を超えるものは `hugeInt`(YAML と同じ。エラーにはしない)。桁数が 19 を超える(符号と先頭の 0 を除く。JSON は先頭の 0 を持たないので、`0` 以外の先頭は 1〜9)ものは、`BigInt` を呼ばずに `hugeInt`、19 桁以下は `BigInt` で得て範囲を比べる。
- 浮動小数: 小数部または指数部を持つもの(`1.0`、`1e3`、`1E3`、`1e0`、`-0.0`)。値は `Number(字句)` で得る。結果が ±`Infinity`(`1e400`)のものは、`overflow: true` の印を付ける(エラーにはしない)。極小(`1e-400`)は 0(エラーにしない)。
- **整数だけの項目**(`format_version`、`max`、`multiplier`、各種の終了コード)に、浮動小数が来たら、型の誤りとして拒否する。**`1.0`、`1e0`、`10e-1` のように値が整数になる書き方でも拒否**(YAML の `1.0` も同じ)。
- JSON の数のうち、値を使う検査の対象外の場所にある浮動小数や範囲外の整数は、エラーにならない(そのキーが `unknownKey` になるだけ)。

### 5.2 JSON の誤りの位置

文法の誤りの位置は、**入力の先頭から読んでいって、読み進められなくなった最初の文字**(その前までが、有効な JSON の先頭部分になっているもの)の位置。入力が途中で終わったとき(閉じていない配列・文字列など)は、入力の末尾の位置(末尾が改行なら、その次の空の行を 1 行と数える)。例:

| 入力(`\n` は改行) | 誤りの位置 |
|------|------------|
| `{"a": 1,}` | `}` の位置(1 行目) |
| `{"a" 1}` | `1` の位置 |
| `{\n  "a": 1\n  "b": 2\n}` | `"b"` の位置(3 行目) |
| `[1, 2` + 末尾の改行 | 末尾(2 行目) |
| `{"a": "x` + 改行 + `"}` | 改行の位置(1 行目。文字列の中に改行を直接書いたため) |
| `{"a":1}{"b":2}` | 2 つ目の `{` の位置 |
| `{"a":1,"a":2}`(重複) | 2 つ目の `"a"` の位置(1 行目) |

文字列の中の誤り(不正なエスケープ、対にならないサロゲート、直接書いた制御文字)の行は、その文字列の行(文字列は改行を含められないので、どの文字でも同じ行)。

### 5.3 JSON の読み取りの規定(自前の字句・構文解析)

読み取りの関数の骨格: `readJson(text: string): ReadResult`(成功なら木、失敗なら 1 件の誤り)。実装の詳細は任せるが、次は**必須**である。

1. **入力を、先頭から 1 回だけ読む**。文字(UTF-16 コード単位)の添字を進め、位置(行、列)を、改行(LF)の数と、行の先頭の添字から求める。列は、行の先頭からのコード単位の数 + 1(列は順序づけにだけ使い、表示しない。第 13.1 節)。
2. **入れ子は、明示のスタックで読む**(関数の再帰で読まない)。この段階では、入れ子の深さの上限を**適用しない**(段階 3 が適用する)。これは、深い入れ子の後ろに文法の誤りがあるとき、文法の誤りが先に返る(段階 2 が先)ことを守るためである。スタックの大きさは、入力の大きさ(1 MiB)で抑えられる。
3. **整数の字句**: 第 5 節の「数」の文法に従って、字句を先頭から読む。読んだ字句に、小数部・指数部が無ければ整数、有れば浮動小数とする(第 5.1 節)。字句の直後の文字が、区切り(空白、`,`、`]`、`}`、入力の末尾)でなければ、その文字の位置で文法の誤り(`01` は 2 文字目の `1`、`1.` は `.` の次、`1e` は `e` の次、`+1` は `+`、`.5` は `.`、`0x10` は `x`)。
4. **リテラル**: `true`、`false`、`null` は、文字ごとに照合し、最初に合わない文字(または入力の末尾)の位置で文法の誤り。リテラルの直後が区切りでなければ、その文字の位置で文法の誤り。
5. **文字列**: 開きの `"` から読む。U+0000〜U+001F の文字、改行、入力の末尾は、その位置で文法の誤り。エスケープは第 5 節の表のとおり。`\u` の 4 桁が 16 進でなければ文法の誤り。サロゲートの前半の `\uD800`〜`\uDBFF` の直後が、`\uDC00`〜`\uDFFF` の `\u` でなければ、文法の誤り(位置はそのエスケープの `\` の位置)。後半が単独で現れたときも同じ。読んだ文字列は、エスケープを解いた JavaScript の文字列(対のサロゲートは 1 つの文字)として得る。
6. **オブジェクト**: `{` の後ろは、空白を飛ばして `}`(空のオブジェクト)か文字列(キー)。キーの文字列を読み終えた**時点で**、重複を調べる(そのオブジェクトの `Set<string>` に、エスケープを解いたキーが既にあれば、**そのキーの開きの `"` の位置で**重複のエラー。`:` 以降は読まない。この仕様の決定)。次に `:`、値、そして `,`(次のキー)か `}`。
7. **配列**: `[` の後ろは、空白を飛ばして `]`(空の配列)か値。値の後ろは `,`(次の値)か `]`。`,` の直後に `]` が来ること(末尾のカンマ)は、`]` の位置で文法の誤り。
8. **最上位**: 空白を飛ばして値を 1 つ読み、空白を飛ばして入力の末尾に達しなければ、その位置で文法の誤り。入力が空(空白だけを含む)なら、入力の末尾の位置で文法の誤り。
9. 木のノードの位置は、第 13.2 節(オブジェクトは `{`、配列は `[`、スカラーは字句の先頭、キーの位置は開きの `"`)。
10. 木は、**キーを文字列で持つ配列**(第 6.1 節の `entries`)として作る。JavaScript のオブジェクトにキーを書き込まない(`__proto__`、`constructor` などのキーが、特別な意味を持たないようにするため)。

文法の誤りの理由は `JSON の文法に誤りがあります`、重複は `キーが重複しています`(いずれも `syntax`)。

## 6. 木への展開(Resolve)と上限

### 6.1 木の型

段階 3 の結果と、段階 4・5 の入力は、YAML と JSON に共通の木である。型の骨格(例。名前は実装が決めてよい。判別共用体で、種別 `kind` を判別に使う):

```ts
/** 入力中の位置(1 始まり)。順序づけと行の表示に使う。 */
export interface Pos {
  readonly line: number;
  readonly column: number;
}

interface NodeBase {
  readonly pos: Pos; // 第 13 節
}

export interface NullNode extends NodeBase {
  readonly kind: 'null';
}
export interface BoolNode extends NodeBase {
  readonly kind: 'bool';
  readonly value: boolean;
}
/** 64 ビット符号つき整数に収まる整数。値は bigint(number にしない)。 */
export interface IntNode extends NodeBase {
  readonly kind: 'int';
  readonly value: bigint;
}
/** 64 ビット符号つき整数の範囲を超える整数。値は持たない。 */
export interface HugeIntNode extends NodeBase {
  readonly kind: 'hugeInt';
}
export interface FloatNode extends NodeBase {
  readonly kind: 'float';
  readonly value: number; // NaN、±Infinity を含みうる
  readonly overflow: boolean; // 範囲を超えた書き方(1e999 など)のとき true
}
export interface StringNode extends NodeBase {
  readonly kind: 'string';
  readonly value: string;
}
export interface SeqNode extends NodeBase {
  readonly kind: 'seq';
  readonly items: readonly TreeNode[];
}
export interface MapEntry {
  readonly key: string;
  readonly keyPos: Pos;
  readonly value: TreeNode;
}
export interface MapNode extends NodeBase {
  readonly kind: 'map';
  readonly entries: readonly MapEntry[]; // 順序つき。キーは重複しない
}

export type TreeNode =
  | NullNode
  | BoolNode
  | IntNode
  | HugeIntNode
  | FloatNode
  | StringNode
  | SeqNode
  | MapNode;
```

- 木は、エイリアスもアンカーもマージキーも含まない(展開済み)。マップのキーは文字列で重複せず、**記述順**を保つ(第 4.5 節のマージの順を含む)。
- マップを JavaScript のオブジェクト(`{}`)や `Record` で持たない(キー `__proto__` の扱いと、キーの順序の保証のため)。`entries` の配列で持つ。キーの検索が要る検査では、`Map<string, MapEntry>` を一時的に作る。「許されたキーか」の判定には、`Set<string>` を使う(**オブジェクトに対する `in` 演算子や `hasOwnProperty` を使わない**。`'toString' in {}` は真になる)。
- 木を走査する処理(段階 3 の走査、深さの数え、検査 Walk、変換器の書き出し)は、**関数の再帰を使わず、明示のスタック**で行うことが望ましい。必須なのは、深い入力でも、`RangeError: Maximum call stack size exceeded` などで異常終了せず、定められた誤りで返ること(第 6.4 節)。

### 6.2 YAML の展開の手順(段階 3)

ライブラリが返した、最初の文書の木(エイリアスを参照として持つ)を、深さ優先・入力に現れる順に走査し、上の木に写す。各ノードについて、次を行う(ここで「ノードの位置」は、第 13.2 節の位置)。

1. エイリアスなら、参照先を(第 4.3 節の、定義の有無と再帰の確認のうえで)展開する。展開したノードとその子の位置は、**エイリアスのトークン `*name` の位置**に置き換える(第 13 節)。
2. 明示のタグがあれば、`syntax`(タグ)で打ち切る。
3. スカラーなら、第 4.2 節で型を決める(キーの位置のスカラーは、文字列でなければ `syntax`(第 4.4 節))。
4. マップなら、第 4.4・4.5 節のとおり、キーの確認、重複の確認、マージの展開を行う。
5. 第 6.3 節の上限を、ノードを訪れるごとに加算して確認する。確認の順は、深さ、要素数、文字の大きさ(同じノードで複数が超えるとき、先のものを返す。この仕様の決定)。

複数の文書のときは、最初の文書だけを走査し、走査で失敗が無かったとき、第 4.6 節の失敗を返す。

### 6.3 上限

| 上限 | 値 | 超過したときの失敗 |
|------|----|--------------------|
| 要素数 | 100,000 | `tooLarge`、理由 ``要素数が上限(100000)を超えています`` |
| 文字の大きさ | 16 MiB(16,777,216 バイト) | `tooLarge`、理由 ``文字の大きさが上限(16 MiB)を超えています`` |
| 入れ子の深さ | 32 | `syntax`、理由 ``入れ子が深すぎます(上限は 32 段)`` |

- **要素数の数え方**: 展開で訪れたノードを 1 つずつ数える。**キーのスカラーも数える**。マップ・リストも 1。根のマップも 1。エイリアスは、エイリアス自身ではなく、**展開した参照先のノード(コレクションなら、その全部)を数える**(同じアンカーを n 回参照すれば、n 回数える)。マージキー `<<` のキー自身も 1 と数え、マージで取り込まれるマップの中身も、捨てられるものを含めて数える。**100,000 ちょうどまで受理**し、100,001 個目で失敗する。JSON にも同じ上限がある(展開はないが、数え方は同じ)。例: `a: [0, 0, ...]`(0 を n 個)は、根のマップ 1 + キー 1 + リスト 1 + 要素 n で、n = 99,997 まで受理、99,998 で失敗(JSON の `{"a":[0,0,...]}` も同じ境界)。
- **文字の大きさの数え方**: 訪れたスカラーの文字のバイト数(UTF-8)を足す。キーと値の両方。文字列(引用符つき、ブロックスカラーを含む)は、**値(エスケープを解いたもの)のバイト数**(`Buffer.byteLength(値, 'utf8')`)。引用符なしのスカラー(数、真偽値、null を含む)と、JSON の数・真偽値・null は、**書かれた文字のバイト数**(`123` は 3、`0x1F` は 4、`null` は 4、`true` は 4。値が空の null は 0。YAML の引用符なしのスカラーは、入力の文字列の、スカラーの `range` の先頭から値の終わりまでの部分文字列のバイト数。複数行にまたがるときは、途中の改行とインデントを含む。この点の境界は、実用上差が出る入力が 16 MiB 付近の複数行スカラーに限られる)。エイリアスの参照のたびに、参照先のスカラーの大きさを足す。マージキー `<<` は 2 バイト。**16 MiB ちょうどは受理**し、1 バイト超えると失敗する。複製・確保の**前**に確認すること(巨大な展開でメモリを使い果たさないために必要)。なお、ファイルの大きさの上限(1 MiB)により、展開のない入力が 16 MiB に達することはない。この上限が働くのは、アンカーとエイリアスで展開が増える場合だけである。
- **入れ子の深さの数え方**: テーブルに当たるもの、つまりマップとリストは、それぞれ**1 段**と数える。スカラーは数えない。**根のマップそのものは数えない**。根の直下のコレクションの深さを 1 とし、その子のコレクションは 2、…と数える。**32 段まで受理**し、**33 段目を拒否する**。数えるのは、**展開後の木**(アンカーの入れ子による深さを含む)に対して。失敗の行は、33 段目になったコレクションの位置(第 13 節)。YAML のフロー形式でもブロック形式でも同じに数える。
  - 例: `a: [[[...]]]`(`[` が n 個)は n 段。32 個は受理、33 個は拒否。JSON の `{"a": [[[...]]]}` も同じ。`a: {b: {b: ... 1}}` も、`{` の数が 32 まで受理、33 で拒否。
  - 例: ブロックのリスト `- - - ... x`(`- ` が n 個)は、根がリストでなくマップの値として置くなら n 段(`a:` の次の行から置く)。
  - 例: アンカーの入れ子 `l0: &l0 [x]`、`l1: &l1 [*l0]`、… の `l(k)` は、展開後に k + 1 段になる。`l31` まで(32 段)は受理、`l32`(33 段)は拒否(これらのキーが、`unknownKey` でない場所に置かれているときの話。深さの検査は Walk より先に行うので、根のキーの種類は関係ない)。
- 上限超過の失敗は、いずれも段階 3 の 1 件の打ち切り(`tooLarge`/`syntax`)で、複数は返さない。同じ入力に複数の上限の超過があれば、入力に現れる順で最初のもの。
- どの上限にも、**30 秒以内に**(巨大な展開でも)到達して終わること(必須)。第 7.4 節の対策(重複キーの検査、前処理)を含めて、実装時に、第 7.5 節の敵対的な入力で測る。

### 6.4 深い入力と異常終了の禁止

- 数千〜数十万段の入れ子の入力(フロー形式の `[[[[...`、ブロックのリストの `- - - ...`、深いインデントの入れ子)でも、プロセスが異常終了せず、`syntax` の 1 件で返らなければならない(必須)。理由が ``入れ子が深すぎます(上限は 32 段)`` か ``YAML の文法に誤りがあります`` かは、実装に任せてよい。
- JSON は自前の読み取りなので、明示のスタックで読む(第 5.3 節)。
- YAML は、確認: `yaml` 2.9.1 は、入れ子が約 1,700 段(フローのマップ、ブロックのマップ)〜約 1,900 段(リスト)を超えると、例外を投げず、文書の `errors` に `RESOURCE_EXHAUSTION` のエラーを入れる。1 MiB の `[` の連続、`- ` の連続、`{a: ` の連続、深いインデントの入れ子が、いずれも約 1 秒以内に `errors` を返した(スタックの使い果たしによる異常終了は起きなかった)。実装は、ライブラリの呼び出しを `try`/`catch` で囲み、投げられた例外(`RangeError` を含む)も、`syntax`(`YAML の文法に誤りがあります`)にする(防御。確認では発生しなかった)。実装時の版で、第 7.5 節の試験を再度行う。

### 6.5 変換器との違い

[09. 変換器](09-converter.md)は、この節の上限と数え方をそのまま使う。変換器だけが、範囲外の数(`hugeInt`、`overflow` の浮動小数)と NaN・∞ を、拒否する。定義の読み込みは、拒否しない。

### 6.6 JSON の段階 3

JSON には、タグ、アンカー、マージキーがないので、段階 3 は、第 6.3 節の上限の確認(木を深さ優先・入力に現れる順に走査して、第 6.2 節の 5 と同じ順で確認する)と、最上位の確認(次の 6.7)だけである。重複キーと文法の誤りは段階 2 で済んでいる。

### 6.7 最上位の確認

| 入力 | 結果 |
|------|------|
| 最上位がマップ | 次へ |
| YAML で、文書が 0 個、または最上位が null | 空のマップとして次へ(段階 4 で `versionMissing`) |
| それ以外(リスト、スカラー。JSON の `null` を含む) | `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置 |

## 7. YAML ライブラリの選定と、追加で実装すること

### 7.1 方針

YAML は Node.js の標準モジュールにないので、外部ライブラリを使う(実行時の依存は、この YAML ライブラリ 1 つだけ。JSON は第 5.3 節の自前の読み取りで、標準モジュールだけで済む)。**選定の基準**は次のとおり。

| 基準 | 内容 |
|------|------|
| 位置 | エラーの行と、各ノードの行・列を取れる(ノードの木が、位置つきで得られる) |
| 木の API | ノードの種別、スタイル(引用符・ブロック・フロー)、アンカー、エイリアス、明示のタグの有無を、型に落とさずに取れる(重複キー、非文字列キー、タグ、複数文書を、自前で拒否するため) |
| 複数の文書 | 入力に文書がいくつあるかを、数えられる |
| 重複キー・非文字列キー | ライブラリが拒否しなくてよい(自前で検出できる)。ライブラリの検査を止められる |
| アンカーの展開 | 展開をライブラリに任せず、自前で上限を数えながら展開できる(アンカーを参照のまま取れる) |
| 保守 | 保守が続いている(実装時に、直近の更新と、報告された不具合の状況を確認する) |
| 依存 | 依存が少ない |
| 型定義 | TypeScript の型定義が同梱されている(`@types` を別に要しない) |

### 7.3 ライブラリの呼び出しと設定

読み取りは、BOM を取り除いた文字列に対して、次のように呼ぶ。

| オプション | 値 | 理由 |
|-----------|----|------|
| 関数 | `parseAllDocuments(text, options)` | 全文書を読み、数える(第 4.6 節)。空の入力、コメントだけの入力では、長さ 0 の配列を返す(確認) |
| `version` | `'1.2'` | YAML 1.2 の文法 |
| `schema` | `'failsafe'` | 引用符なしのスカラーを、すべて文字列(元の文字)として受け取る。型は、実装が第 4.2 節で決める(確認: `a: yes`、`0777`、`0o17`、`~`、空の値のいずれも、値は元の文字のまま、空の値は空文字列) |
| `uniqueKeys` | `false` | 第 4.4 節。ライブラリの検査は遅く、自前で検査する |
| `merge` | `false` | `<<` を自前で展開する(第 4.5 節) |
| `lineCounter` | `new LineCounter()` | オフセットを行・列にする |
| `logLevel` | `'silent'` | 標準エラーなどに、ライブラリが出力しないため |
| `keepSourceTokens` | 既定(`false`) | |
| `strict`、`prettyErrors` | 既定 | |

- `toJS()`、`toJSON()`、`String(doc)` は呼ばない。ライブラリの `maxAliasCount` は、この呼び出しにだけ働くので、使わない。
- 各文書の `errors`(配列)が 1 つでもあれば、第 4.1 節の拒否(`syntax`、理由 ``YAML の文法に誤りがあります``)。行は、最初のエラーの `linePos[0].line`(`LineCounter` を渡したときに入る。確認。無ければ `LineCounter.linePos(pos[0]).line`)。`warnings`(例: 未知のタグの `TAG_RESOLVE_FAILED`)は無視する(タグは、第 7.4 節 #3 で別に拒否する)。複数の文書のうち、どれに `errors` があっても、段階 2 の失敗になる(文書の順に、最初のエラー)。

### 7.4 ライブラリだけでは足りないので、追加で実装すること

## 8. 書式の版(VersionCheck)

根の `format_version` を確認する。

| 状況 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `versionMissing` | なし | `` `format_version` が必要です(対応する版は 1 です) `` |
| 整数でない(文字列、浮動小数、真偽値、null、リスト、マップ。`1.0`、`1e0` を含む) | `versionUnsupported` | 値の位置の行 | `` `format_version` は整数で書きます(対応する版は 1 です) `` |
| 整数だが 1 でない(0、-1、2、9、範囲外の整数) | `versionUnsupported` | 値の位置の行 | `この版には対応していません(対応する版は 1 です)` |

- 対応する版は **1 だけ**。`format_version: 1` を受理する。YAML の `0x1`、`01`、`+1` でも、値が 1 なら受理する(JSON では `1` だけ)。値の比較は `bigint` で(`value === 1n`)。
- 版が 1 のとき、取り込み後の定義の `formatVersion` は 1 になる。

## 9. 定義の構造(Walk)

以降の「マップ」「リスト」は、木の型(第 6.1 節)である。**キーの型**は、すべて文字列(第 4.4 節で保証)。位置の取り方は第 13 節。

根のマップは、次のキーだけを持てる。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `format_version` | 整数 | 必須 | 第 8 節 |
| `pipeline` | マップ | 必須 | 第 9.1 節 |
| `job` | マップのリスト | 必須(1 つ以上) | 第 9.2 節 |

許されていないキー(上の 3 つ以外)は、`unknownKey` である。`jobs`(複数形)も未知のキーとして拒否される(``キー `jobs` は定義にありません``)。`unknownKey` の理由は、`` キー `<キー名>` は定義にありません `` の形(`<キー名>` は整形したキー名)で、キー名の整形は第 12.2 節。位置はそのキーの位置。値の型は問わない(null でも、アンカーの参照でも同じ)。

### 9.1 `pipeline`

| キー | 型 | 必須 | 既定値 | 検査 |
|------|----|------|--------|------|
| `name` | 文字列 | 必須 | なし | 空白だけ(trim して空)なら `emptyField` |
| `description` | 文字列 | 任意 | なし | 型だけ |
| `run_id_env` | 文字列 | 任意 | なし(実行時の既定は環境変数 `CONDUCTOR_RUN_ID`) | 名前の形(下記) |
| `remove_on_complete` | 真偽値 | 任意 | `false` | 型だけ |

- 許されたキー以外は `unknownKey`(例: `owner`、`remove_on_complet`)。
- `name` が無い: `typeMismatch`、行は `pipeline` のマップの位置、理由 ``必須の値 `name` がありません``。文字列でない(null を含む): `typeMismatch`、値の位置、理由 `` `name` は文字列で書きます ``。`description` が文字列でない: `typeMismatch`、値の位置、理由 `` `description` は文字列で書きます ``。`run_id_env` が文字列でない: `typeMismatch`、値の位置、理由 `` `run_id_env` は文字列で書きます ``。`remove_on_complete` が真偽値でない: `typeMismatch`、値の位置、理由 `` `remove_on_complete` は真偽値(`true` または `false`)で書きます ``。
- `name` が空白だけ: `emptyField`、`name` の値の位置、理由 `` `name` が空です ``(名前の照合はしない)。
- `run_id_env` の名前の形の誤り: `invalidEnvName`、値の位置、理由 `` `run_id_env` は、英字または `_` で始まり、英数字と `_` だけの名前で書きます ``。
- `run_id_env` の名前の形: 1 文字以上で、先頭が ASCII の英字(`A-Za-z`)または `_`、2 文字目以降が ASCII の英数字(`A-Za-z0-9`)または `_`。正規表現で書くなら `/^[A-Za-z_][A-Za-z0-9_]*$/`(**`$` は入力の末尾だけに一致するので、末尾に改行を持つ文字列は一致しない**。JavaScript の `$` は、`m` フラグが無ければ、文字列の末尾だけに一致する。`m` フラグを付けない)。受理: `A`、`_`、`_a1`、`GITHUB_RUN_ID`。拒否(`invalidEnvName`): `""`、`1A`、`A-B`、`A B`、`A=B`、`é`、`A.B`、NUL を含む文字列、`A` + 改行。文字列でない値(整数など)は `typeMismatch`。誤りの文に、値は含めない。
- `remove_on_complete` は真偽値だけ(`true` / `false`、YAML では `True`、`TRUE` なども)。文字列 `"true"`、`yes`(文字列)、整数 `1`、リスト `[true]` は `typeMismatch`。型が違うときの値は、`false` として扱って続行する(誤りは報告済み)。
- `pipeline` の形:
  - 無い: `typeMismatch`、行は **1 行目**(位置 (1, 1))、理由 ``必須の値 `pipeline` がありません``。
  - リスト: `typeMismatch`、リストの位置、理由 `` `pipeline` は 1 つだけで、マップで書きます(1 ファイルに 1 パイプライン) ``。
  - その他(整数、文字列、null など): `typeMismatch`、値の位置、理由 `` `pipeline` はマップで書きます ``。
  - 上の誤りのとき、`pipeline` の中身の検査は行わない。
- 名前の照合: `expectedPipelineName` が与えられ、定義の `name` と**完全に同じでない**(大文字小文字・空白も区別。文字列の `!==`)と、`pipelineNameMismatch`、行は `name` の値の位置、理由 ``指定されたパイプライン名が、定義の `name` と一致しません``。理由に両方の名前は含めない。`name` が空白だけのときは、`emptyField` だけを返し、照合はしない。`name` が文字列でない・無いときも、照合はしない。

### 9.2 `job`

`job` は、マップのリストでなければならない。

- 無い: `noJobs`、行は 1 行目(位置 (1, 1))、理由 ``ジョブ(`job`)が 1 つもありません``。
- 空のリスト(`job: []`): `noJobs`、行は `job` の値の位置。
- リストでない(マップ、整数、null など): `typeMismatch`、値の位置、理由 `` `job` はマップのリストで書きます ``。
- リストの要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `job` の要素はマップで書きます ``(その要素の検査は行わない)。

各ジョブ(マップ)のキー:

| キー | 型 | 必須 | 既定値 | 説明 |
|------|----|------|--------|------|
| `id` | 文字列 | 必須 | なし | ジョブID。第 11.1 節の検査 |
| `command` | 文字列、または文字列のリスト | 必須 | なし | 第 9.3 節 |
| `warning_exit_codes` | 整数のリスト | 任意 | 空(`[]`) | 警告にする終了コード |
| `success_exit_codes` | 整数のリスト | 任意 | 省略(意味は `[0]`) | 成功にする終了コード |
| `transitions` | マップのリスト | 任意 | 空 | 第 9.4 節 |
| `retry` | マップ | 任意 | なし | 第 9.5 節 |

許されたキー以外は `unknownKey`(例: `warn_exit_codes`)。

- `id` が無い: `typeMismatch`、行はジョブのマップの位置、理由 ``必須の値 `id` がありません``。文字列でない: `typeMismatch`、値の位置、理由 `` `id` は文字列で書きます ``。
- 終了コードのリスト(`warning_exit_codes` と `success_exit_codes`):
  - リストでない(null を含む): `typeMismatch`、値の位置、理由 `` `<キー名>` は整数のリストで書きます ``(`<キー名>` は実際のキー名)。
  - 要素が整数でない、または 32 ビット符号つき整数の範囲(-2,147,483,648〜2,147,483,647)に収まらない: 要素ごとに `typeMismatch`、その要素の位置、理由 `` `<キー名>` の要素は、整数(32 ビットの範囲)で書きます ``。1 つでも誤りがあれば、そのキー全体を「無効」として扱い、後続の重なりの検査では使わない。**範囲の判定は、木の `bigint` の値で行い(`-2147483648n <= v && v <= 2147483647n`)、範囲に収まったものだけを `number` に変換する**(`number` に落としてから判定しない)。
  - 負の値(例: `-1`)は、その範囲なので**受理**する。重複した値も受理し、除かない(書いた順のまま保持する)。空のリストも受理する(`success_exit_codes: []` は、成功にする終了コードが無い、の意味になる)。
  - 整数は、YAML の `0x1F`、`0o17`、`+3`、`007` でもよい(値で判定する)。JSON は 10 進の整数だけ。
- `success_exit_codes` を省略すると、成功の終了コードは `[0]`。書いたら、**書いた値だけ**が成功(`0` を書かなければ 0 でも成功にならない)。
- 要素が浮動小数(`1.0`、`1e0`)や、範囲外の整数(`99999999999999999999`、種別 `hugeInt`)のときも、要素の型の誤り(`typeMismatch`)になる。

### 9.3 `command`

| 書き方 | 受理の条件 | 保持される値 |
|--------|-----------|---------------|
| 文字列 | trim して空でない | 1 本の文字列(そのまま。trim した値ではない) |
| 文字列のリスト | 空でないリストで、全要素が文字列で、**先頭の要素が trim して空でない**。2 番目以降の要素は空文字列でもよい | 要素の並び(そのまま) |

どちらの書き方かは、取り込み後も区別して保持する(実行側の解釈が異なる。[05. 実行フロー](05-execution-flow.md)・[07. プロセスとシグナル](07-process-and-signals.md))。

誤り:

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `typeMismatch` | ジョブのマップの位置 | ``必須の値 `command` がありません`` |
| 文字列が空または空白だけ | `emptyField` | 値の位置 | `` `command` が空です `` |
| リストが空 | `emptyField` | 値の位置 | `` `command` の配列が空です `` |
| リストに文字列でない要素がある | `typeMismatch`(要素ごと) | その要素の位置 | `` `command` の配列の要素は、文字列で書きます `` |
| リストの先頭の要素が空または空白だけ(全要素が文字列のとき) | `emptyField` | 先頭の要素の位置 | `` `command` の配列の先頭の要素が空です `` |
| 文字列でもリストでもない(整数・真偽値・マップ・null) | `typeMismatch` | 値の位置 | `` `command` は文字列、または文字列の配列で書きます `` |

- リストに型の誤りの要素があるときは、先頭要素の空の検査はしない。
- 受理の例(YAML): `command: echo x`、`command: ["my prog", "a b", "$HOME", ""]`、`command: [echo, ""]`。拒否の例: `command: 5`、`command: true`、`command: {a: 1}`、`command: ["a", 5]`、`command: [[a]]`(`typeMismatch`)、`command: ""`、`command: "   "`、`command: []`、`command: [""]`、`command: ["  ", x]`(`emptyField`)、`command:`(値なしは null。`typeMismatch`)。
- 文字列の `command` の中の引用符・`$` などは、この段階では解釈しない(実行時の解釈は実行側の仕様)。YAML の引用符なしの複数行のスカラーは、折りたたまれた 1 つの文字列(改行が空白 1 個になる)になるが、書き方による値の違いは、そのまま保持する。
- 理由の文言(`の配列` という語)は、リストを指す(日本語の原文として固定する。`リスト` に言い換えない)。
- 誤りの文に、入力の値は含めない。

### 9.4 `transitions`

`transitions` は、マップのリスト(YAML のブロックの `- on: success` の繰り返し、またはフロー形式 `[{on: success, next: b}]`、JSON の配列)。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `on` | 文字列 | 必須 | `success` または `warning` |
| `next` | 文字列 | 必須 | 遷移先のジョブID、または `@end` |

- 許されたキー以外(`when` など)は `unknownKey`。
- `transitions` がリストでない(null を含む): `typeMismatch`、値の位置、理由 `` `transitions` はマップのリストで書きます ``(遷移は空として扱う)。要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `transitions` の要素はマップで書きます ``。
- `on` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `on` がありません``。文字列でない: `typeMismatch`、値の位置、`` `on` は文字列で書きます ``。
- `on` の値: `success`、`warning` を受理。`error` は `errorTransition`、値の位置、理由 ``エラー結果(`error`)には遷移先を書けません``。それ以外の文字列(`later`、大文字の `Success` など)は `typeMismatch`、値の位置、理由 `` `on` は `success` または `warning` で書きます ``。YAML のキー `on` は、YAML 1.1 の真偽値ではなく、文字列のキー(`on`)として読まれる(第 4.2 節)。
- `next` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `next` がありません``。文字列でない: `typeMismatch`、値の位置、`` `next` は文字列で書きます ``。
- 同じ `on`(`success` どうし、`warning` どうし)の遷移が 2 つ以上: 2 つ目以降の遷移に `duplicateTransition`、行は**その遷移(マップ)の位置**、理由 ``同じ結果(`on`)の遷移が 2 つ以上あります``。`success` と `warning` を 1 つずつは受理。`on` が不正(`error` や未知の値、型の誤り)の遷移は、重複判定に入れない。
- 遷移先の存在・順序の検査は、第 11 節。

### 9.5 `retry`

ジョブが決めた終了コードで終わったときに、待って実行し直す設定。書き方は、ブロックのマップでもフローのマップでも、JSON のオブジェクトでもよい。

許されたキーは次の 5 つだけ。それ以外は `unknownKey`(例: `retries`)。

| キー | 型 | 必須 | 範囲・書式 | 取り込み後 |
|------|----|------|-----------|-------------|
| `exit_codes` | 整数のリスト | 必須 | 空でない。各要素は 1 以上 255 以下の整数 | 昇順に並べ、重複をまとめる(`[75, 3, 75, 3, 12]` → `[3, 12, 75]`) |
| `max` | 整数 | 必須 | 1 以上 100 以下 | `number`(整数) |
| `interval` | 文字列 | 必須 | `<整数><s\|m\|h>`、1 秒以上 24 時間以下 | 秒(`number`。1〜86,400) |
| `multiplier` | 整数 | 任意 | 2 以上 10 以下 | `number`(整数)、または無し |
| `max_interval` | 文字列 | 任意 | `interval` と同じ書式、`interval` 以上 | 秒(`number`)、または無し |

- 127 などの値も受理する(`[127, 1]` → `[1, 127]`)。並べ替えは、数値の昇順(`Array.prototype.sort` の既定は文字列順なので、**比較関数 `(a, b) => a - b` を渡す**)。
- `multiplier` と `max_interval` は、**両方を書くか、両方とも書かない**か。片方だけなら `retryBackoffIncomplete`。両方なしなら、待ち時間は毎回 `interval`。
- 取り込み後の値は、いずれも 2^53 に収まる(最大でも 86,400)ので `number` でよい。**待ち時間の計算(倍率の累乗、上限、64 ビット符号なし整数の飽和)は、[05. 実行フロー](05-execution-flow.md)の規定に従い、`bigint` で行う**(この定義の値を `BigInt(...)` に変換して使う)。

#### 間隔の文字列の書式

- 文字列の最後の 1 文字が単位(`s`=秒、`m`=分=60 秒、`h`=時間=3600 秒。小文字だけ)。その前が、**ASCII の数字(0〜9)だけ**の 1 文字以上の列(符号・空白・小数点・`_`・全角数字・16 進(`0x`)は不可)。正規表現で書くなら `/^[0-9]+[smh]$/`(`\d` は ASCII の数字だけだが、書式を明示するため `[0-9]` を使う。`$` の注意は第 9.1 節と同じ)。
- 数値は 1 以上。秒に換算した値が 1 以上 86,400(24 時間)以下。桁あふれ(64 ビット符号なし整数に収まらない、または換算の乗算があふれる)は拒否。先頭の 0 は何個並べてもよい(`0000000000000000000000000001s` は値 1 で受理)。値が 86,400 秒を超えるものは、桁数にかかわらず拒否する。**判定は `bigint` で行う**(数字の列を `BigInt` にして、単位の倍率を掛けて、1n 以上 86400n 以下かを調べる。`Number`・`parseInt` を使うと、2^53 を超える桁で誤る)。巨大な桁数の字句で時間を使わないために、先頭の 0 を除いた数字の桁数が 5 を超えるものは、`BigInt` を呼ばずに範囲外とする(6 桁以上の数は 100,000 以上で、単位が `s` でも 86,400 を超えるので、結果は同じ)。5 桁以下だけ `BigInt` で調べればよい。
- 受理: `1s`、`30s`、`5m`、`2h`、`24h`、`1440m`、`86400s`、`01s`(値 1)。拒否: `""`、`s`、`10`、`1.5s`、`-1s`、`+1s`、` 1s`、`1s `、`1 s`、`1d`、`1S`、`１s`、`1ms`、`0x10s`、`1_0s`、`0s`、`0h`、`86401s`、`25h`、`99999999999999999999999s`、`18446744073709551615h`。文字列でない値(整数・真偽値・null)も拒否。
- YAML では、`interval: 30s` のように引用符なしで書いた `30s` は文字列、`interval: 30` は整数なので拒否。`interval: 0x10s` は文字列だが、書式に合わないので拒否(`retryDurationInvalid`)。

#### 誤りと検査

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| `retry` がマップでない(整数、文字列、リスト、null) | `retryNotTable` | `retry` の値の位置(リストのときは、リストの位置) | `` `retry` はマップで書きます `` |
| 必須のキー(`exit_codes`、`max`、`interval`)が無い | `retryMissingKey`(欠けたキーごとに 1 件) | `retry` のマップの位置 | ``必須の値 `<キー名>` がありません`` |
| `exit_codes` がリストでない | `retryExitCodeInvalid` | 値の位置 | `` `exit_codes` は整数の一覧で書きます `` |
| `exit_codes` が空のリスト | `retryExitCodesEmpty` | 値の位置 | `` `exit_codes` が空です `` |
| `exit_codes` の要素が整数でない、32 ビットの範囲外、1〜255 の範囲外(0、256、-1、1.5、`"75"`、`true` など) | `retryExitCodeInvalid`(要素ごと) | その要素の位置 | `` `exit_codes` の要素は、1 以上 255 以下の整数で書きます `` |
| `max` が整数でない、または 1〜100 の範囲外(0、101、-1、1.5、`"3"`、`true`) | `retryMaxInvalid` | 値の位置 | `` `max` は、1 以上 100 以下の整数で書きます `` |
| `interval` / `max_interval` が書式・範囲に合わない | `retryDurationInvalid` | 値の位置 | `` `<キー名>` は、整数と単位(`s`、`m`、`h`)で、1 秒以上 24 時間以下に書きます(例: `30s`) ``(`<キー名>` は `interval` か `max_interval`) |
| `multiplier` が整数でない、または 2〜10 の範囲外(1、11、0、-2、`2.0`、`"2"`、`true`) | `retryMultiplierInvalid` | 値の位置 | `` `multiplier` は、2 以上 10 以下の整数で書きます `` |
| `multiplier` と `max_interval` の片方だけがある | `retryBackoffIncomplete` | `retry` のマップの位置 | `` `multiplier` と `max_interval` は、両方を書くか、両方とも書きません `` |
| `exit_codes` に、そのジョブの成功または警告の終了コードと同じ値がある | `retryExitCodesOverlap` | `exit_codes` の**キー**の位置 | `` `exit_codes` に、成功または警告の終了コードと同じ値があります `` |
| `max_interval` が `interval` より小さい(秒で比べる。等しければ受理) | `retryMaxIntervalTooSmall` | `max_interval` の値の位置 | `` `max_interval` は、`interval` 以上で書きます `` |

- 整数の判定は、木の `int`(`bigint` の値)で行う。範囲外の整数(`hugeInt`)は、範囲外の誤りと同じ扱い。
- 空のマップ(`retry: {}`)は、`retryMissingKey` が 3 件(`exit_codes`、`max`、`interval` の順)返る(行はすべて同じ。マップの位置は、フロー形式では `{` の位置)。
- `exit_codes` の複数の要素が不正なら、不正な要素ごとに 1 件(例: `[0, 75, 256]` は 2 件)。
- **重なりの検査**(`retryExitCodesOverlap`)は、定義の他の値と照合する。`exit_codes` が有効(エラーなし)のときだけ行う。
  - 成功の終了コード: `success_exit_codes` を**書かなければ `[0]`**。書いて有効なら、その値。書いたが誤り(無効)のときは、成功との重なりを調べない(警告との重なりは調べる)。
  - 警告の終了コード: `warning_exit_codes` が有効なら、その値(無効なら調べない)。
  - どちらかと 1 つでも共通する値があれば、1 件(重なりの値の数にかかわらず 1 件)。
  - 例: `success_exit_codes: [0, 5]` と `exit_codes: [5, 75]` は誤り。`success_exit_codes: [3]` と `exit_codes: [3]` も誤り。`success_exit_codes: [0, 5]`、`warning_exit_codes: [4]`、`exit_codes: [75]` は受理。
- `retry` の有無は、ほかのキーの読み取りの結果に影響しない。
- 誤りの文に、入力の値は含めない。

## 10. 検査の順序とエラーの集約・並び

Walk の中の処理順(誤りは、見つかった順に集める):

1. 根のキー検査(`unknownKey`)。
2. `pipeline`: キー検査 → `name` → `description` → `run_id_env`(型の誤り、続けて名前の形の誤り) → `remove_on_complete` → `name` の空の検査 → 名前の照合。
3. `job`: 無い/空/型の誤りの処理。リストなら、各ジョブを順に、次の順で検査する: キー検査 → `id` → `command` → `warning_exit_codes` → `success_exit_codes` → `transitions`(各遷移について、キー検査 → `on` → `next` → 重複) → `retry`(キー検査 → `exit_codes` → `max` → `interval` → `multiplier` → `max_interval` → 倍率と上限の片方だけの検査)。
4. 全ジョブにまたがる検査(第 11 節): ジョブIDの検査 → 各ジョブについて、遷移先 → 終了コード(`zeroAsWarning`、`overlappingExitCodes`) → `retry` の重なり・上限と間隔の大小。
5. 誤りが 1 件もなく、`pipeline` とすべてのジョブが組み立てられるときだけ、定義を返す。

返す誤りの順序: すべての誤りを、**位置(行、同じ行なら列)の昇順**に並べて返す。同じ位置のものは、上の検査の順(集めた順)を保つ(**安定な並べ替え**。Node.js の `Array.prototype.sort` は安定である。ECMAScript 2019 以降の規定)。位置の取り方は第 13 節。

- 型の誤りなどで検査できなくなった値は、その値に依存する後続の検査だけを省略する(他の検査は続ける)。
- 位置が (1, 1) の誤りは、行 1 として扱われる(`pipeline` が無い、`job` が無い)。

複数の誤りの例:

```yaml
format_version: 1
unknown_top: true          # 2 行目: unknownKey

pipeline:
  name: p

job:
  - id: a
    command: x
    success_exit_codes: [zero]   # 10 行目: typeMismatch

  - id: b
    command: y
    colour: red              # 14 行目: unknownKey
    transitions:
      - on: success
        next: nowhere        # 17 行目: unknownTarget
```

返る誤り: `unknownKey`(2)、`typeMismatch`(10)、`unknownKey`(14)、`unknownTarget`(17)。

## 11. ジョブ間の検査

### 11.1 ジョブID

`id` が文字列であるジョブごとに、記述順に検査する。

- trim して空、または先頭が `@` → `invalidJobId`、`id` の値の位置、理由 ``ジョブID(`id`)は、空でなく、`@` で始まらない文字列で書きます``。この ID は、遷移先の索引に入らない(後続のジョブから、遷移先として参照できない)。
- 既出の ID と完全に同じ(大文字小文字・前後の空白も区別。`" a "` と `"a"` は別) → `duplicateJobId`、2 つ目以降の `id` の値の位置、理由 ``同じジョブID(`id`)が、すでに定義されています``。(既出の ID は `Set<string>` で調べる。`__proto__` や `constructor` という ID も、通常の文字列として扱う。)
- 長さの上限、使える文字(空白・記号)の制限は、これ以外にない(定義の検査では。実行時の状態ファイル名などへの影響は、[06. ステートファイル](06-state-file.md)による)。

### 11.2 遷移先

`on` と `next` がともに有効な遷移について、`next` を検査する(`on` が不正な遷移は、検査しない)。

- `next === "@end"`: 受理(以降のジョブをスキップして終える)。
- ID の索引に無い(存在しない、または無効な ID): `unknownTarget`、`next` の値の位置、理由 ``遷移先(`next`)のジョブが、定義にありません``。
- 記述順で、自分自身または前のジョブ(位置 ≦ 自分の位置): `backwardOrSelfTarget`、`next` の値の位置、理由 ``遷移先(`next`)は、記述順で後ろのジョブまたは `@end` で書きます``。
- 後ろのジョブの ID は受理する。

### 11.3 終了コード

各ジョブについて(`warning_exit_codes` と `success_exit_codes` が有効なとき):

- `warning_exit_codes` に 0 を含む → `zeroAsWarning`、`warning_exit_codes` の**キー**の位置、理由 ``0 は警告の終了コード(`warning_exit_codes`)にできません``。(`success_exit_codes` の誤りの有無に関わらず検査する。)
- 両方を書き、有効で、共通する値がある → `overlappingExitCodes`、`warning_exit_codes` の**キー**の位置、理由 `` `warning_exit_codes` と `success_exit_codes` に、同じ値があります ``。ただし、共通の値が 0 だけで、すでに `zeroAsWarning` を報告した場合は、重ねて報告しない(例: `warning_exit_codes: [0]` と `success_exit_codes: [0]` は `zeroAsWarning` の 1 件だけ)。
- `success_exit_codes` を書かないとき、成功は `[0]` だが、`warning_exit_codes` との重なりは(書かれていない側は)調べない。警告に 0 を入れた場合は、`zeroAsWarning` で拒否される。

### 11.4 `retry` との関係

第 9.5 節(重なり、上限と間隔の大小)。

## 12. エラーの種類と表示

### 12.1 エラーの構造

型の骨格(例。種類 `kind` を判別に使う判別共用体):

```ts
export const ERROR_KINDS = [
  'unsupportedFormat', 'fileMissing', 'unreadable', 'tooLarge', 'syntax',
  'typeMismatch', 'unknownKey', 'versionMissing', 'versionUnsupported',
  'unknownTarget', 'errorTransition', 'backwardOrSelfTarget',
  'overlappingExitCodes', 'zeroAsWarning', 'pipelineNameMismatch',
  'duplicateJobId', 'invalidJobId', 'noJobs', 'emptyField',
  'duplicateTransition', 'invalidEnvName', 'retryNotTable',
  'retryMissingKey', 'retryExitCodesEmpty', 'retryExitCodeInvalid',
  'retryExitCodesOverlap', 'retryMaxInvalid', 'retryDurationInvalid',
  'retryBackoffIncomplete', 'retryMultiplierInvalid',
  'retryMaxIntervalTooSmall',
] as const; // 31 種(第 12.3 節の表と同じ順)

export type ErrorKind = (typeof ERROR_KINDS)[number];

interface ErrorFields {
  /** 表示用のファイル名(第 2.1 節) */
  readonly file: string;
  /** 1 始まり。undefined は「行なし」 */
  readonly line: number | undefined;
  /** 1 始まり。undefined は「列なし」。順序づけにだけ使い、表示には出さない */
  readonly column: number | undefined;
  /** 固定の文から組み立てた理由(日本語)。入力の値は含めない */
  readonly reason: string;
}

/** 種類ごとの誤り。`kind` で絞り込める(判別共用体) */
type ErrorOf<K extends ErrorKind> = ErrorFields & { readonly kind: K };

export type DefinitionError = { [K in ErrorKind]: ErrorOf<K> }[ErrorKind];

/** 読み込みの結果。成功か、1 件以上の誤り */
export type LoadResult =
  | { readonly ok: true; readonly definition: Definition }
  | { readonly ok: false; readonly errors: readonly [DefinitionError, ...DefinitionError[]] };
```

| フィールド | 内容 |
|------------|------|
| `file` | 表示用のファイル名 |
| `line` | 行番号(1 始まり)。位置が決まらないときは無し |
| `column` | 列番号(1 始まり)。同じ行の中での順序づけのために保持する。**表示には出さない** |
| `kind` | 種類(第 12.3 節) |
| `reason` | 固定の文から組み立てた理由。入力の値は含めない。入力由来はキー名だけ(`unknownKey`) |

ライブラリ(読み込み処理の呼び出し側)に返す表示の書式:

```
<file>:<line>: <種類の文>: <reason>      行があるとき
<file>: <種類の文>: <reason>             行が無いとき
```

例: ``conductor.yaml:7: 定義にないキーです: キー `x` は定義にありません``。ここで `<file>` は、制御文字・書式文字(第 12.2 節と同じ対象)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは、256 文字までで切って末尾に `…` を付ける)。

`conductor` コマンドの標準エラーへの表示は、`conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason>` の 1 行(誤りごとに 1 行、位置の順)で、`reason` は日本語のまま(言語によらない)。種類の文は、メッセージの言語([08](08-output-and-i18n.md))が日本語のとき日本語(第 12.3 節の「日本語」)、それ以外は英語(「英語」)。`<file>` と `reason` は、改行・制御文字・書式文字をエスケープして表示する(`\n`、`\r`、`\t`、その他は `\u{16進小文字}`)。**ここでは文字数で切らない**。例:

```
conductor: error: bad.yaml:7: unknown key: キー `typo` は定義にありません
conductor: error: conductor.yaml: definition file does not exist: 指定の場所にファイルがありません
```

定義の誤りがあるときの終了コード(64)と、その標準出力・標準エラーの扱いは、[10. エラーと終了コード](10-errors-and-exit-codes.md)に従う。

### 12.2 キー名の表示

`unknownKey` の理由に入るキー名は、`` ` `` で囲み、次の整形をする。

- 改行を `\n`、復帰を `\r`、タブを `\t` に、その他の制御文字(U+0000〜U+001F、U+007F〜U+009F)と書式文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)を `\u{16進小文字}` にエスケープする(例: U+0001 は `\u{1}`)。
- エスケープ後の文字数(コードポイントの数)が **64 文字**を超えるときは、64 文字までで切って末尾に `…` を付ける(エスケープの途中では切らない。たとえば、残りが 2 文字でエスケープが 6 文字なら、そのエスケープは入れず、そこで切る)。ちょうど 64 文字は切らない。
- この整形は、`file`(256 文字)の整形と同じ手順で、上限だけが違う。
- 文字列は、コードポイントごとに走査する(`for...of`。UTF-16 のコード単位で走査すると、サロゲートの対を壊す)。

## 13. 位置(行番号と列番号)の出し方

### 13.1 位置の単位

- 位置は、行と列の組(`Pos`)。**行は 1 始まりで、LF の数で数える**(CRLF でも、CR は直前の行に属し、LF のあとが次の行)。**列は 1 始まりで、その行の先頭からの文字の数 + 1**。ただし、YAML では、ライブラリの `LineCounter` が返す列(JavaScript の文字列の添字、つまり UTF-16 コード単位の数 + 1。確認: サロゲートの対は 2 と数える)をそのまま使ってよい。**列は、同じ行の中の誤りの並びを決めるためだけに使い、行が違えば比べない**。同じ行の中で、前にあるものほど小さい列を返す限り、単位はどちらでもよい。JSON の自前の読み取りも、同じ単位(コード単位)にそろえる。
- 先頭の BOM は、位置には数えない(1 行目の 1 列目は、BOM の次の文字)。実装は、BOM を取り除いた文字列を、ライブラリと自前の読み取りに渡す。
- 位置が決まらない誤りは、行なし(取り込み、`versionMissing`、一部の `syntax`)。
- 位置が (1, 1)(入力の先頭)の誤りは、`pipeline` が無い、`job` が無い。

### 13.2 ノードの位置

YAML のノードの位置は、ライブラリのノードの `range[0]`(入力の文字列の中のオフセット)を、`LineCounter.linePos(offset)` で行・列にしたもの。

| ノード | 位置 |
|--------|------|
| スカラー | 値の先頭の文字(引用符つきなら、開く引用符。ブロックスカラーなら、`\|` または `>` の位置)。アンカー `&name` やタグが前置されていても、**内容の位置**(アンカーやタグの位置ではない。確認: `a: &s` + 改行 + `  x` で `x` の位置、`a: !!str 1` で `1` の位置) |
| ブロックのマップ | **最初のキーの先頭**(最初の対の `key.range[0]`)。そのキー自身が引用符つきなら、開く引用符。明示のキー `? a` のときは、`?` の位置ではなくキー `a` の位置(確認: ライブラリのマップの `range[0]` は `?` の位置を返すので、補正が要る)。アンカーやタグが前置されていても同じ(確認) |
| フローのマップ | `{` の位置(確認: タグが前置されていても、`{` の位置) |
| ブロックのリスト | **最初の `-` の位置**(確認: アンカーが前置されていても、`-` の位置) |
| フローのリスト | `[` の位置(確認) |
| JSON のオブジェクト・配列 | `{` / `[` の位置 |
| マップのキー(`keyPos`) | キーのスカラーの先頭 |
| 値が `null`(JavaScript の `null`)の対の値(`{a, b: 1}` の `a`、`? a`) | その対のキーの位置 |
| 展開されたノード(エイリアスから) | **エイリアスのトークン `*name` の位置**(複製した子のすべても同じ位置。確認: `c: *x` で `*` の位置) |
| マージで取り込まれたエントリ | そのマージキー `<<` の位置(キー、値、値の中のすべて) |

- 空の値(`a:`、`- ` の後ろに何もない)の位置は、ライブラリが返すオフセット(コロンやダッシュの直後)で、行は、そのキーやダッシュの行と同じである(確認: `a:` の値は 1 行目)。
- 「値の位置」とは、そのキーの値のノードの位置。「キーの位置」とは、`keyPos`。「マップの位置」とは、上の表のマップのノードの位置(必須キーの欠落、`retryMissingKey`、`retryBackoffIncomplete` で使う)。

### 13.3 誤りの位置の取り方(まとめ)

- 型の誤りや範囲の誤りは、**誤った値のノードの位置**。
- 未知のキーは、**キーの位置**。
- 必須のキーの欠落は、**それを含むマップの位置**。
- `pipeline` や `job` 自体が無いときは、(1, 1)。
- 終了コードの重なり(`overlappingExitCodes`、`zeroAsWarning`、`retryExitCodesOverlap`)は、対象の**キー**の位置(値ではない)。
- リストの誤りは、要素ごとに、その要素の位置。
- 取り込みの誤り、`unsupportedFormat`、`versionMissing` は、行なし。
- 段階 3 の誤りは、そのノードの位置(キーの誤り(重複、非文字列)はキーの位置、マージキーの誤りは `<<` の位置、深さの誤りは 33 段目のコレクションの位置、上限(要素数、大きさ)の誤りは、超えたノードの位置)。

### 13.4 文法の誤りの行

- **JSON**: 第 5.2 節のとおり、必須。
- **YAML**: 文法の誤りは、ライブラリが検出した位置の行(最初のエラーの `linePos[0].line`)。検出位置は、ライブラリの作りで変わる(原因の行より後ろになることも、前になることもある)。**必須なのは、種類(`syntax`)と理由(`YAML の文法に誤りがあります`)であり、行は、ライブラリが返すものでよい**。`yaml` 2.9.1 での確認結果(この表の行が、実装時の版で変わったときは、その版の結果に合わせて、この表を更新する):

| 入力(`\n` は改行) | ライブラリのエラー | 行 |
|------|------|----|
| `format_version: 1\npipeline: [1, 2\n` | `BAD_INDENT`(閉じていないフロー) | 3(入力の末尾の空の行) |
| `a: [1, 2\n` | `BAD_INDENT` | 2 |
| `a: [1, 2\nb: 3\n` | `BAD_INDENT` | 2(`b` の行) |
| `a: [1, 2`(末尾の改行なし) | `BAD_INDENT` | 1 |
| `a: "x\n` | `MISSING_CHAR`(閉じていない引用符) | 2 |
| `a: 1\nb: "\q"\n` | `BAD_DQ_ESCAPE` | 2 |
| `x: 1\na: b: c\n` | `BLOCK_AS_IMPLICIT_KEY` | 2 |
| `a: 1\nb:\n\t- x\n` | `TAB_AS_INDENT` | 3 |
| `a:\n  b: 1\n c: 2\n` | `BAD_INDENT` | 3 |
| `a: @x\n` | `BAD_SCALAR_START` | 1 |
| `a: 1\r\nb: [1,\r\n c: 2\r\n`(CRLF) | `BAD_INDENT` | 4(CRLF でも、LF の数で数えた行) |

## 14. 取り込み後のデータモデルと検査の関数

### 14.1 データモデル

検証に成功すると、次のデータを返す(型の骨格。`readonly` で、変更できない値として返す)。

```ts
export interface Definition {
  /** 空白だけでない(trim していない元の値) */
  readonly name: string;
  /** 無ければ undefined */
  readonly description: string | undefined;
  /** 名前の形は検査済み。undefined なら実行時に CONDUCTOR_RUN_ID */
  readonly runIdEnv: string | undefined;
  /** 省略時 false */
  readonly removeOnComplete: boolean;
  readonly formatVersion: 1;
  /** 記述順を保つ。1 つ以上 */
  readonly jobs: readonly [Job, ...Job[]];
}

export interface Job {
  /** 空白だけでなく、@ で始まらず、定義内で一意 */
  readonly id: string;
  /** 文字列で書いたか、リストで書いたか(判別共用体) */
  readonly command: Command;
  /** 省略時は空。0 を含まない。書いた順のまま。各値は 32 ビット符号つき整数の範囲 */
  readonly warningExitCodes: readonly number[];
  /** 省略時 undefined(意味は [0])。書いた順のまま */
  readonly successExitCodes: readonly number[] | undefined;
  /** 書いた順。on ごとに高々 1 つ */
  readonly transitions: readonly Transition[];
  /** 書かなければ undefined */
  readonly retry: RetryPolicy | undefined;
}

export type Command =
  | { readonly form: 'line'; readonly line: string }
  | { readonly form: 'argv'; readonly argv: readonly [string, ...string[]] };

export type Transition =
  | { readonly on: 'success' | 'warning'; readonly next: 'job'; readonly jobId: string }
  | { readonly on: 'success' | 'warning'; readonly next: 'end' };

export interface RetryPolicy {
  /** 昇順・重複なし・各 1〜255・空でない */
  readonly exitCodes: readonly [number, ...number[]];
  /** 1〜100 */
  readonly max: number;
  /** 1〜86400 */
  readonly intervalSecs: number;
  /** undefined なら固定間隔。multiplier と max_interval は必ず同時に有る/無い */
  readonly backoff: Backoff | undefined;
}

export interface Backoff {
  /** 2〜10 */
  readonly multiplier: number;
  /** intervalSecs 以上、86400 以下 */
  readonly maxIntervalSecs: number;
}
```

- 成功として扱う終了コード = `successExitCodes` があればそれ、なければ `[0]`。
- ジョブIDから記述順の位置(0 始まり)を引く操作がある(遷移先の検査と、実行時の遷移の解決に使う)。`Map<string, number>` で持つ。
- `Definition` を作るときに、`Object.freeze` を使うかは任意(型の `readonly` で十分)。作成後に配列を変更しない。

### 14.2 公開する関数の署名(例)

```ts
export type Format = 'yaml' | 'json';

/** 拡張子から書式を決める。決められなければ undefined(unsupportedFormat) */
export function formatFromPath(path: string): Format | undefined;

/** 段階 1〜5。ファイルに触れる(非同期) */
export function loadDefinition(
  path: string,
  expectedPipelineName?: string,
): Promise<LoadResult>;

/** 段階 2〜5。ファイルに触れない(同期) */
export function parseDefinition(
  text: string,
  format: Format,

/** watch・reset 用のゆるい読み取り(第 15 節)。誤りは undefined */

```

内部の検査の関数(名前は任意。木と、誤りを集める入れ物を受け取り、定義の部品を返す。誤りは `errors` に足す。例外を投げない):

```ts
interface WalkContext {
  readonly file: string;
  readonly errors: DefinitionError[]; // 集めた順
  add(kind: ErrorKind, pos: Pos | undefined, reason: string): void;
}

function walkRoot(root: MapNode, ctx: WalkContext, expectedName: string | undefined): Definition | undefined;
function walkPipeline(node: TreeNode, rootPos: Pos, ctx: WalkContext, expectedName: string | undefined): PipelineParts | undefined;

```

- `PipelineParts`、`JobParts` は、検査の途中の部品の型(誤りがあるときは組み立てを諦めて `undefined`)で、実装が決める。

## 15. `run_id_env` のゆるい読み取り

`watch` と `reset` は、`--run-id` が無いとき、定義全体を検証せず、`pipeline.run_id_env` だけを取り出す。

- 書式の決定(第 2.1 節)から段階 3(第 6 節の上限を含む)までは、定義の読み込みと同じに行う。段階 4・5 は行わない。
- 拡張子が対応していない、ファイルを読めない、大きさの上限を超える、YAML・JSON として読めない(上限を含む)、最上位がマップでない、`pipeline` がマップでない、キーが無い、文字列でない、名前の形(第 9.1 節)に合わない、のどれでも「無し」(`undefined`。実行時は `CONDUCTOR_RUN_ID`)。
- ほかの誤り(`format_version` の誤り、未知のキーなど)は無視する。壊れた入力でも異常終了しない(例外を投げず、`undefined` を返す)。
- ファイルの大きさの上限(第 3 節)は、この読み取りにも適用する(超えれば「無し」)。
- 例(YAML): `pipeline:\n  name: p\n  run_id_env: X_ID\n` → `X_ID`。`run_id_env: 5`、`"1A"`、`""` → 無し。`pipeline: 3` → 無し。空の入力 → 無し。

## 16. 受理・拒否の例

### 16.1 受理

最小の定義(YAML):

```yaml
format_version: 1

pipeline:
  name: p

job:
  - id: a
    command: c
```

同じ定義(JSON):

```json
{
  "format_version": 1,
  "pipeline": { "name": "p" },
  "job": [
    { "id": "a", "command": "c" }
  ]
}
```

全キーを使った定義(YAML):

```yaml
format_version: 1

pipeline:
  name: nightly
  description: 夜間バッチ
  run_id_env: GITHUB_RUN_ID
  remove_on_complete: true

job:
  - id: extract
    command: ["python", "scripts/extract.py", ""]
    warning_exit_codes: [4]
    success_exit_codes: [0, 5]
    retry:
      exit_codes: [75, 111]
      max: 5
      interval: 10s
      multiplier: 2
      max_interval: 60s
    transitions:
      - on: warning
        next: notify

  - id: load
    command: load
    transitions:
      - on: success
        next: "@end"

  - id: notify
    command: notify --channel ops
```

別の書き方でも同じ定義になる例(フロー形式、引用符つきのキー、コメント):

```yaml
"format_version": 1   # コメントは捨てられる
pipeline: { name: p }
job: [{ id: a, command: c, retry: { exit_codes: [75], max: 3, interval: 5s } }]
```

アンカーとエイリアス、マージキーを使った定義(受理。`b` は、`a` の `command` を取り込み、`id` は自分の値):

```yaml
format_version: 1
pipeline:
  name: p
job:
  - &base
    id: a
    command: c
    success_exit_codes: &ok [0, 2]
  - <<: *base
    id: b
    warning_exit_codes: [3]
  - id: c
    command: d
    success_exit_codes: *ok
```

(`b` は `command: c`、`success_exit_codes: [0, 2]`、`warning_exit_codes: [3]`、`id: b`。)

### 16.2 拒否(Walk の誤り)

行番号は、次の共通のヘッダの続きとしての値。ジョブは 5 行目の `- id: a`、6 行目の `command: c` から。

```yaml
format_version: 1
pipeline:
  name: p
job:
  - id: a
    command: c
```

| 入力(ヘッダの続き) | 結果 |
|------|------|
| 7 行目 `    transitions:`、8 行目 `      - on: success`、9 行目 `        next: zzz` | `unknownTarget` 9 行目 |
| 同、`on: error`、`next: "@end"` | `errorTransition` 8 行目 |
| 同、`on: success`、`next: a`(自分自身) | `backwardOrSelfTarget` 9 行目 |
| 7 行目 `    warning_exit_codes: [2, 3]`、8 行目 `    success_exit_codes: [0, 3]` | `overlappingExitCodes` 7 行目 |
| 7 行目 `    warning_exit_codes: [0]` | `zeroAsWarning` 7 行目 |
| 7 行目 `    warning_exit_codes: [x]` | `typeMismatch` 7 行目 |

## 17. 未確認事項
