# 01. 概要

この文書は、`conductor`(TypeScript 版。挙動の版は 0.8.0)が何のためのツールか、どのような方針で作るか、何を作らないか、どのような制約の下で作るか、を述べる。詳細な規定は、02 章以降にある。

## 1. 目的

複数のコマンド(シェルスクリプトや実行ファイル)を決まった順に実行する一連の作業(バッチ処理、定期ジョブ、データの取り込みの手順など)を、次の 3 点で支える。

| 目的 | 内容 |
|------|------|
| 宣言的に書く | 実行するコマンドの並びと、終了コードごとの扱い(成功・警告・エラー、次に進むジョブ、リトライ)を、1 つの定義ファイル(YAML か JSON)に書く |
| 途中経過を残す | どのジョブがどう終わったか、次にどこから再開するかを、ステートファイル(JSON)に保存する |
| 失敗から再開する | 失敗したジョブで止まり、原因を直したあとの再実行で、終わったジョブは飛ばして、失敗したところから続ける |

`conductor` は、Node.js 上で動く TypeScript 製のコマンドラインツールである。npm のパッケージ(tarball)として配り、利用者は Node.js を用意して入れる。OS ごとの実行ファイルは作らない(Node.js が動けば、3 OS で同じ成果物が動く)。

## 2. ユースケース

| ユースケース | コマンド | 内容 |
|--------------|----------|------|
| パイプラインを順に実行する | `conductor pipeline <名前>` | 定義の全ジョブを記述順に実行する。失敗したジョブで止まり、再度実行すると、そのジョブから再開する |
| 1 つのジョブだけ実行する | `conductor run <ジョブID>` | 外部のスケジューラが、ジョブを 1 つずつ呼ぶ。順序が守られているかをステートで確かめ、順序外なら拒否する |
| 状態を確かめる | `conductor watch` | ステートを表にして標準出力に出す(定義は検証しない) |
| ステートを捨てる | `conductor reset [--all]` | ステートを初期化する。壊れたステートからの回復にも使う |
| 定義を検査する | `conductor validate [<名前>]` | 定義とコマンドの書き方を、ジョブを起動せずに検査する(CI で定義の誤りを早く見つける) |
| 書式を変換する | `conductor convert <ファイル> --to yaml\|json` | 定義(など)を YAML と JSON のあいだで変換する |
| 同じ定義を並行して使う | `--run-id <ID>` | run ID でステートを分け、別の実行単位として扱う(CI の実行番号など) |
| 警告を許す | `warning_exit_codes`、`transitions` | 一部の終了コードを「警告」として扱い、続行したり、別のジョブへ飛んだりする |
| 一時的な失敗を再試行する | `retry` | 決めた終了コードで終わったときに、待ってから実行し直す(間隔の倍率と上限を指定できる) |

## 3. 設計方針

| 方針 | 内容 |
|------|------|
| 同じ挙動 | 版 0.8.0 と、利用者から見て同じ挙動にする。サブコマンド、オプション、終了コード、メッセージの文言、`watch` の表、実行の意味論は同じ |
| 失敗を値で返す | 外部の入力(引数、環境、ファイル、シグナル、ジョブの出力)に対して異常終了しない。誤りは、種類・位置・固定の理由・終了コードで返す。想定外の内部失敗だけが 70 |
| 少なくとも 1 回 | ジョブは、少なくとも 1 回は実行される。結果の記録を書けなければ、ジョブの終了コードより 65 を優先する。記録の前に落ちると、再実行されうる |
| シェルを介さない | `command` は、決まった規則で分割した引数を、`node:child_process` の `spawn`(`shell: false`)に直接渡す。展開・パイプ・リダイレクトは解釈しない。メタ文字は、そのまま引数になる(Windows の `.cmd` / `.bat` だけは、07 章 4.7 節の安全策を通す) |
| 入力の値を表示に出さない | エラーの文に、入力の値やライブラリのエラー文を含めない(入力に由来するのは、キー名だけ。制御文字をエスケープして切り詰める) |
| 純粋な判断とふるまいの分離 | 分類・遷移・再開・リトライの判断は、入出力に触れない純粋な関数(`src/flow/`)にして、表駆動のテストで確かめる。ファイル・プロセス・シグナル・時刻・標準出力は、`Deps` の interface の向こうに置く |
| 原子的なステート | ステートは、一時ファイルに書いてから置き換える。読み手は、直前の完全な内容か、新しい完全な内容のどちらかだけを見る |
| 非同期は直列 | `async`/`await` を使う。イベントループは 1 つなので、データ競合はない。ジョブ、出力、ステートの書き込みは、すべて直列に `await` する。待たない Promise を作らない |
| 出力を待ってから終わる | 標準出力・標準エラーの書き込みの完了を待ってから終わる(`process.exit()` を書き込みの完了前に呼ばない)。終了を決める箇所は、入口の 1 か所 |
| 依存は最小 | 実行時の外部ライブラリは、YAML の読み取りの 1 つだけ。ほかは `node:` の標準モジュール(引数の解析は自前、シグナルは `process.on`、プロセスは `node:child_process`、ファイルは `node:fs/promises`)。JSON の読み取りは自前(`JSON.parse` を製品のコードで使わない) |
| 確かめられる仕様 | すべての規定は、ビルドした `dist/bin/conductor.js` を外から実行する受け入れテスト(11 章。AC-001〜515)で確かめられる形で書く |

## 4. 非目標

次のことは、この版では行わない。

| 非目標 | 補足 |
|--------|------|
| ジョブの並列実行 | ジョブは、記述順に 1 つずつ実行する。分岐は、遷移による前方へのスキップだけ(後戻り・ループはない) |
| 常駐とスケジューリング | デーモンも、時刻による起動もない。起動は、利用者か外部のスケジューラが行う |
| 排他制御 | ファイルロックや PID ファイルを使わない。同じ定義(同じ run ID)の同時実行は、避けること(run ID で分ければ並行できる) |
| ジョブの出力の加工 | ジョブの標準入出力・標準エラーは、そのまま流れる(`stdio: 'inherit'`)。ログの収集・保存はしない |
| シェルの機能 | 変数の展開、パイプ、リダイレクト、ワイルドカードの展開は、`conductor` は解釈しない(必要なら、ジョブがシェルを起動する) |
| 環境変数の展開 | 定義の値に環境変数を埋め込む機能はない。環境変数を読むのは、run ID、ロケール、色の判定だけ |
| 定義の再利用や継承 | YAML のアンカー・マージキーによる、書式の内側での再利用だけ(展開して読む) |
| ネットワーク | 外向きの通信をしない(`node:net`・`node:http`・`node:dns` を使わない)。リモートの実行や、状態の共有もない |
| ほかの書式 | 定義は YAML と JSON だけ(拡張子が `.yaml`・`.yml`・`.json` 以外は拒否する) |
| リトライの回数の保存 | リトライの回数と待ち時間は、ステートに保存しない(再開は、最初の実行から数え直す) |
| 画面の対話 | 対話的な入力も、進捗の動的な表示もない(標準入力を読まない。ジョブに引き継ぐ) |
| ジョブの強制終了 | 中断のとき、子プロセスにシグナルを 1 回転送するだけ。止まらないジョブを強制終了しない |
| ライブラリとしての公開 | 公開するのは `bin` の `conductor` だけ。`package.json` の `exports` は `package.json` だけで、ほかのパッケージから import できない |
| 単一の実行ファイルの配布 | 任意(Node.js の単一実行可能アプリケーションの機能などの利用。11 章 6.4 節。確かめていない) |

## 5. 制約

| 項目 | 内容 |
|------|------|
| Node.js の版 | 実装時点の最新の LTS 系列と、その 1 つ前の LTS 系列をサポートする。`package.json` の `engines.node` に、最小の LTS 系列の最小の版を書く(具体的な版は、実装時に確認して決める。11 章の例は `>=22`)。CI では、最小の版と最新の版の両方でテストし、`engines` と CI の Node の版の一致を検査する |
| TypeScript | `strict`(`noUncheckedIndexedAccess` ほか)、ESM(`"type": "module"`、`module`/`moduleResolution` は `NodeNext`)。`tsc` で `dist/` に出力し、`bin` の `conductor` は先頭が `#!/usr/bin/env node` |
| 対象 OS | Linux、macOS、Windows の 3 つ。OS 差は `src/runner/platform.ts` の 1 か所に隔離する(`process.platform` を読むのはそこだけ)。ステートのディレクトリの同期の有無、端末の色、受け取るシグナルの一覧は、そこが出す値を使う |
| 配布 | npm のパッケージ(`conductor-<版>.tgz`)と `SHA256SUMS`。タグ `v*` で、ドラフトのリリースに添付する(npm への公開は人が手で行う)。パッケージ名 `conductor` は置き換えてよい |
| 依存の方針 | 実行時の依存は、YAML のライブラリ 1 つだけ(採用案は `yaml`。版は固定する。03 章 7 章、11 章 8 章)。選定は、行・列の位置、構文木(アンカー・エイリアス・タグ・スタイル)、複数文書の数え方、保守の継続、依存の少なさを基準にする。採否は、実装時の小さな試験で決める(12 章 4 章) |
| 開発時の依存 | TypeScript、ESLint(`typescript-eslint`)、Prettier、Vitest(`@vitest/coverage-v8`)、`@types/node` だけ。選定と版は、実装時に確認する |
| ほかの依存 | ネイティブのアドオン、ネットワークのライブラリ、`eval`・`node:vm`・`node:worker_threads` を使わない。テストも、Vitest だけ(疑似端末の試験を除く。11 章 10.1 節) |
| 入力の大きさ | 定義・ステート・変換の入力は 1 MiB まで。YAML・JSON の展開後の要素数は 100,000、文字の大きさは 16 MiB、入れ子の深さは 32 段まで |
| 文字コード | 定義・ステート・変換の入力は UTF-8(先頭の BOM は、定義と変換では受理し、ステートでは拒否する)。引数と環境変数は、Node.js が UTF-8 として復号した文字列(不正なバイトは U+FFFD に置き換わる。04 章 4.4 節) |
| 言語 | メッセージは、日本語と英語(環境変数 `LC_ALL`、`LC_MESSAGES`、`LANG` で決める)。理由の文(定義・ステート・変換)は、常に日本語 |
| ライセンス | Apache License 2.0。ソースの先頭に著作権表示を置く(11 章 2.4 節) |

## 6. 利用者像

| 利用者 | 求めるもの |
|--------|------------|
| 運用担当(バッチや定期ジョブの運用者) | 失敗したところから再開できること。状態を `watch` で確かめられること。壊れたステートを `reset` で回復できること |
| 開発者(ジョブと定義を書く人) | 定義の誤りが、種類と行番号つきで分かること。`validate` を CI に入れられること。リトライと警告の扱いを宣言で書けること |
| CI の管理者 | 実行番号などで run ID を分けて並行して使えること。終了コードで結果を判断できること。3 OS で動くこと |
| この仕様書の読者(再実装する人) | 02〜11 章を読んで、同じ挙動の実装を作り、受け入れテストで確かめられること。Node.js の非同期・標準出力・子プロセスの落とし穴、YAML ライブラリの扱いに不慣れでも、落とし穴と最初の試験が分かること(12 章) |

## 7. 概念の概観

### 7.1 定義ファイル

1 つのパイプラインと、ジョブの並びを書く。

```yaml
format_version: 1

pipeline:
  name: nightly
  description: 夜間バッチ

job:
  - id: extract
    command: extract --all --since yesterday
    warning_exit_codes: [3, 4]
    transitions:
      - on: warning
        next: notify
  - id: load
    command: load
    retry:
      exit_codes: [75]
      max: 3
      interval: 30s
  - id: notify
    command: notify --channel ops
```

- 書式は拡張子で決まる(`.yaml`・`.yml`・`.json`。ASCII の大文字小文字を区別しない)。JSON でも同じ構造を書く。
- ジョブは記述順に実行する。`transitions` で、成功・警告のときの次のジョブ(後ろのジョブか `@end`)を指定できる。飛ばされたジョブはスキップになる。
- 読み込みは、見つけた誤りをまとめて返す(種類、行、理由)。詳細は 03 章。

### 7.2 実行と分類

ジョブを起動し、終了コードで分類する。

| 結果 | 分類 | 終了コード |
|------|------|------------|
| 成功コード(省略時は 0)で終了 | 成功 | 0 |
| 警告コードで終了 | 警告 | 0 |
| それ以外の終了コード | エラー | ジョブの終了コード(0〜255 に合わせる) |
| シグナルで終了 | エラー | 128 + 番号 |
| 起動できない | エラー | 127 |
| 起動前に中断された | 分類なし | 128 + 番号 |

`pipeline` は、エラーで止まり、そのジョブの終了コードで終わる。リトライの対象なら、待って実行し直す。詳細は 05 章。

### 7.3 ステートと再開

実行の途中経過を、定義ファイルと同じ場所の `<定義ファイル名>.state` に JSON で保存する(run ID があれば `<定義ファイル名>.<run ID>.state`)。再実行では、終わったジョブ(`AlreadyExecuted`)を飛ばし、再開位置から続ける。`run` は、順序外・スキップ対象・`@end` より後ろ・実行済みのジョブを拒否する(66)。全ジョブが終わると完了になり、完了のステートは、次の実行では空とみなす。詳細は 05・06 章。

### 7.4 中断

UNIX 系では SIGHUP・SIGINT・SIGQUIT・SIGTERM、Windows では Ctrl+C(SIGINT)を `process.on` で受けると、実行中のジョブにシグナルを 1 回転送し(UNIX 系のみ。`child.kill`)、再開位置を記録して、128 + 番号で終わる。リトライの待機は、合図から 1 秒以内に切り上げる。詳細は 07 章。

### 7.5 出力

- `conductor` 自身は、既定では何も出力しない(ジョブの出力がそのまま流れる)。エラーのとき、または `-v` のときだけ、標準エラーに書く。
- `watch`、`--help`、`--version`、`convert` は、結果を標準出力に書く。標準出力に書けないとき(`EPIPE`、`ENOSPC` など)は、`watch` が 65、`convert` が 67 で終わる。
- メッセージは、環境変数で日本語か英語を選ぶ。`watch` の表は、端末なら状態語に色が付く。詳細は 08 章。

### 7.6 内部の構成

```text
src/bin ─▶ src/cli ─▶ definition / convert / runid / flow / state / runner / report
```

`cli` が引数を解き、各部を組み立てて終了コードを決める。`flow` は純粋な判断、`state` はステートの入出力、`runner` は子プロセスとシグナル(OS 差は `platform.ts` に隔離)、`report` は文の組み立て、`definition` は定義の読み込みと検査(YAML・JSON の読み取りを含む)、`convert` は書式の変換である。`src/bin/conductor.ts` は薄い入口で、内部の誤りの捕捉と、出力の完了待ちと、終了を受け持つ。依存の向きと型の骨格は 02 章。
