# 00. README(Go 版 仕様書の案内)

> この仕様書は v0.8.0 時点の挙動で凍結されている(v0.9.0 以降の環境変数の注入と `.env`、`graph`、`--dry-run`、`init` を含まない)。最新は [rust](../rust/00-README.md) と [language-agnostic](../language-agnostic/00-README.md)。

この仕様書は、コマンドラインツール `conductor` を、Go でゼロから実装し直すための仕様である。`conductor` は、1 つの定義ファイルに書かれたジョブ(外部コマンド)の並びを、終了コードで分類しながら順に実行し、途中経過をステートファイルに残して、失敗したところから再開できるようにする、単一の実行ファイルである。

この文書は、仕様書全体の入口である。範囲と版、目次、読む順序、規定の強さの語、用語集、この版が採った書式の選択をまとめる。

## 1. 仕様書の範囲と版

| 項目 | 内容 |
|------|------|
| 対象 | `conductor` の利用者から見える挙動を、Go で再実装するための仕様 |
| 版 | `conductor 0.8.0` と同じ利用者向けの挙動。`conductor --version` は `conductor 0.8.0` を出す(版の文字列は `internal/version` の定数 `Version` が唯一の定義) |
| 実装言語 | Go(`go.mod` の `go` 行は、実装時点の最新の安定版の 1 つ前以降。例: Go 1.25 以降。実装時に、最新の 2 つの安定版を確認して決める) |
| 外部ライブラリ | YAML の読み取りだけ(選定の基準と候補は [03](03-definition-format.md) 7 章と [11](11-quality-and-build.md) 8 章)。ほかは標準ライブラリ |
| 対象 OS | Linux、macOS、Windows の 3 つ。配布物は 4 つの対象(`linux/amd64`、`linux/arm64`、`darwin/arm64`、`windows/amd64`) |
| 同じにするもの | サブコマンド、オプション、終了コード、実行の意味論(分類・分岐・再開・リトライ・run ID)、メッセージの文言(日本語・英語)、`watch` の表 |
| 含まないもの | 実装そのもの(コードは規定しない。骨格のコードは、型とシグネチャの例である)。各章が「実装に任せてよい」と書いた点 |

この仕様書だけで、同じ受理・拒否・出力・終了コードを返す実装を作れることを目標とする。確認できなかった点は「未確認」と明記し、[12](12-rebuild-guide.md) 4 章にまとめた。Go の標準ライブラリや外部ライブラリの挙動で、作成時に実際に動かして確かめていないものは、「実装時に確認する」と書いてある。

## 3. 読む順序

| 目的 | 読む順序 |

各章の終わりに、その章の「実装に任せてよい点」と「未確認」がある。受け入れテスト(11 章)の期待は、定義・ステート・変換・終了コードの各章(03、06、09、10)の字句と食い違うときは、それらの章を正とする。

## 4. 規定の強さの語

章によって、記号や語が少し違うが、意味は次の 3 段階に対応する。

| 強さ | 意味 | 章での表記 |
|------|------|------------|
| 必須 | 利用者から見える結果(受理・拒否、出力の文字列、終了コード、作られるファイルの内容)であり、同じにしなければならない。受け入れテストで確かめる | 「必須」「【規定】」「強制」「〜しなければならない」 |
| 目安 | 推奨する値や分け方。利用者から見える挙動を損なわない範囲で、別の値や分け方を採ってよい。基準を超えたときは警告として記録する | 「目安」「【目安】」「推奨」「仮」(暫定として置いた値) |
| 任意 | 利用者から見える結果が変わらない範囲で、実装が自由に選んでよい | 「任意」「実装に任せてよい」「裁量」 |

- 【Go の設計】(07 章)は、Go の都合で選んだ設計で、利用者から見える結果が同じなら変えてよい(目安と同じ扱い)。
- 骨格のコード(型・シグネチャ)は、名前や細部が他の章の定めと食い違うときは、03・06・09 の定めを正とし、骨格を読み替える。
- 「未確認」は、作成時に確かめられなかった点で、断定していない。実装時に確かめる。

## 5. 用語集

02〜11 章で使っている語を、次のように統一する。

| 語 | 意味 |
|----|------|
| 定義ファイル | パイプラインを書いたファイル。YAML(`.yaml`、`.yml`)か JSON(`.json`)。既定の名前は `conductor.yaml` |
| 定義 | 定義ファイルを検証して読み込んだ結果(`format_version`、`pipeline`、`job`) |
| パイプライン | 名前をもち、ジョブの並びからなる 1 つの流れ。1 つの定義ファイルに 1 つ |
| ジョブ | 実行する外部コマンド 1 つと、その終了コードの扱い(成功・警告のコード、遷移、リトライ)。ID をもつ |
| ジョブID | ジョブの識別子(`id`)。定義の中で一意。空でなく、`@` で始まらない |
| `command` | ジョブが実行するコマンド。文字列(分割して実行する)か、文字列のリスト(そのまま渡す)。シェルは介さない |
| 成功コード・警告コード | ジョブの終了コードのうち、成功(`success_exit_codes`。省略時は `[0]`)・警告(`warning_exit_codes`)として扱う値 |
| 分類 | ジョブの結果を、成功・警告・エラー・分類なし(起動前の中断)に分けること |
| 遷移(`transitions`) | 成功・警告のとき、次に実行するジョブを指定すること。`@end` は、残りをスキップして終える |
| スキップ | 遷移などで、実行されないジョブ。理由は「遷移による」「`@end` による」 |
| 拒否 | 順序外などで、`run` が実行を断ること(終了コード 66) |
| リトライ(`retry`) | 決めた終了コードで終わったジョブを、待ってから実行し直すこと。最大回数・間隔・倍率・上限を指定できる |
| run ID | 実行単位を区別する文字列(`A-Za-z0-9._-`、1〜64 文字、先頭は `.` でない)。ステートファイルを分ける |
| ステートファイル | 実行の途中経過を JSON で保存するファイル。名前は `<定義ファイル名>.state`(run ID があれば `<定義ファイル名>.<run ID>.state`) |
| 再開位置(`resume_job_id`) | 次に実行する、または再開するジョブのID |
| 完了 | 全ジョブが終わった状態(`completed = true`)。完了のステートは、読み込みでは「空」とみなす |
| 空のステート | ステートが無いのと同じ扱い(ファイルがない、長さ 0、完了) |
| 耐久性(Durable / Fast) | ステートの書き込みで、内容の同期まで行うか(Durable)、省くか(Fast) |
| 実行方式 | `run`(1 ジョブ。Individual)と `pipeline`(全ジョブ。Pipeline) |
| at-least-once | ジョブは、少なくとも 1 回は実行される。結果の記録の前に落ちると、再実行されうる |
| 中断の合図(`Interrupt`) | シグナルを受けたことと、最初の番号を、goroutine の間で共有する値 |
| 起動失敗 | 子プロセスを作れなかったこと(終了コード 127) |
| 木(`Node`) | YAML・JSON の読み取り結果の共通の木。null、真偽値、整数、範囲外の整数、浮動小数、文字列、リスト、マップの 8 種 |
| マップ・リスト | キーと値の対応・値の並び(YAML のブロック/フロー、JSON のオブジェクト/配列) |
| 段階(Intake、Parse、Resolve、VersionCheck、Walk) | 定義の読み込みの処理の段階。前の段階で失敗したら、そこで打ち切る(03 章 2.2 節) |
| 種類(`kind`)・理由(`reason`) | エラーの識別子(`syntax`、`typeMismatch` など)と、固定の日本語の原因の文 |
| 案内 | ステートの誤りに付ける、`conductor reset` で回復できるという文 |
| `Deps` | `internal/cli` の差し替え口。環境、時刻、ファイル、プロセス、シグナル、標準出力・標準エラーの interface の束 |
| TJ(テストジョブ) | 受け入れテスト用の実行ファイル `cmd/conductor-testjob`。配布しない |
| AC | 受け入れテストの項目(`AC-xxx`)。11 章 4 章 |

## 6. この版が採った書式の選択

この版が採った、書式・名前・文言の選択を、一覧にする。

| 項目 | 内容 | 章 |
|------|------|----|
| 定義ファイルの書式 | YAML(YAML 1.2 のコアスキーマ)と JSON(RFC 8259)。書式は拡張子で決める(`.yaml`・`.yml` は YAML、`.json` は JSON。ASCII の大文字小文字を区別しない)。それ以外は `unsupportedFormat`(64) | 03 |
| 既定のファイル名 | `conductor.yaml`(`--config` で指す) | 03、04 |
| 定義のキー名 | `format_version`、`pipeline`(`name`、`description`、`run_id_env`、`remove_on_complete`)、`job`(`id`、`command`、`warning_exit_codes`、`success_exit_codes`、`transitions`、`retry`) | 03 |
| YAML の部分集合 | アンカー・エイリアス・マージキーは展開して受理。タグ、複数の文書、文字列でないキー、重複したキーは拒否。`yes`・`no`・`on`・`off` は文字列 | 03 |
| 読み込みの上限 | ファイル 1 MiB、要素数 100,000、文字の大きさ 16 MiB、入れ子の深さ 32 段(根のマップを数えず、33 段目を拒否) | 03 |
| 定義のエラーの種類 | 31 種(`unsupportedFormat` を含む)。位置は行(と順序づけのための列)で出し、誤りは位置の順に 1 行ずつ。理由は常に日本語の固定文で、入力の値を含めない | 03、08、10 |
| ステートファイル | JSON(`encoding/json`、UTF-8、BOM なし)。名前は `<定義ファイル名>.state`。キーは固定の順序で書き、インデントは空白 2 つ。読み込みは 14 段階の検査で、キーの重複・BOM・最上位がオブジェクトでない値を拒否する | 06 |
| ステートの理由文 | 全 23 件。`JSON として読めません`、`キーが重複しています`、`内容を JSON にできません` を含む | 06、10 |
| `convert` | YAML と JSON の相互変換(`--to yaml\|json`)。入力の形式は `--to` の反対とみなし、拡張子は見ない。出力のキーの順は入力の記述順。`null` は表せる。表せない値は、範囲外の数、YAML の NaN・無限大(JSON へ)、1,024 文字を超えるキー(JSON から YAML へ)の 3 つ | 09 |
| 変換のエラー | 6 種(`fileMissing`、`unreadable`、`tooLarge`、`syntax`、`unrepresentable`、`rootNotMap`)。終了コード 67 | 09、10 |
| `retryNotTable` の文言 | `retry must be a map` / `retry はマップで書きます` | 08 |
| 使い方(`--help`) | `convert <file> --to <yaml\|json>`、`--config` の既定は `conductor.yaml` | 08 |
| 引数の解析 | `flag` を使わず、自前の字句・検査の 2 段階(短縮形の連結、`--opt=value`、`--` などを仕様どおりに扱うため) | 04 |
| 終了コード | 0、1〜255(ジョブの値)、64(定義)、65(ステート)、66(拒否)、67(変換)、68(使い方)、70(内部)、127(起動失敗)、128+番号(シグナル) | 10 |
| 想定外の内部失敗 | `defer` + `recover`(メインと、すべての goroutine)で、`conductor: error: internal error` を 1 行出して 70 | 10 |
| シグナル | UNIX 系は SIGHUP・SIGINT・SIGQUIT・SIGTERM を `os/signal` で受け、子プロセスの pid にだけ 1 回転送。Windows は Ctrl+C(`os.Interrupt`)。終了コードは 128+番号 | 07 |
| パッケージ構成 | `cmd/conductor`、`internal/{definition,convert,runid,flow,state,runner,report,cli,testsupport,version}`、`cmd/conductor-testjob` | 02 |
| 品質ゲート | `gofmt -s`、`go vet`、`golangci-lint`、`go test -race`(カバレッジ 80% 以上は Linux のみ)、`govulncheck`、3 OS・最小版と最新版の Go でのテスト | 11 |
| リリース | `v*` のタグ(`main` 上で、`internal/version` と一致)で、4 つの対象をクロスビルドし、`SHA256SUMS` を付けて、下書きのリリースを作る | 11 |
