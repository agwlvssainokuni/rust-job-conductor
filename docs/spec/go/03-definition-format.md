# 03. 定義ファイルの書式と検証

この文書は、`conductor` の定義ファイルの書式と、読み込み時の検証を定める。この文書だけで、Go でゼロから、同じ受理・拒否・エラー(種類、文言、行番号)を返す読み込み処理を実装できることを目標とする。

- 定義ファイルの書式は **YAML(主)** と **JSON** の 2 つ。書式は**拡張子**で決める(第 2 節)。既定のファイル名は `conductor.yaml`。
- 検証は、見つけた誤りを**まとめて**返す。ただし、早い段階の誤り(取り込み、文法、展開と上限、版)は 1 件だけで打ち切る(第 2 節)。
- 定義の内容は、読み込みでは実行も評価もしない。`command` の文字列は、そのまま保持する。
- 確認できなかった点は「未確認」と書く。ライブラリや Go の API の挙動で、この文書の作成時点で確認できていないものは、実装時に確かめるべき点として明記してある。
- 「必須」と書いた挙動は、利用者から見える結果(受理/拒否、エラーの種類・文言・行番号、取り込み後の値)であり、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、利用者から見える結果が変わらない範囲で、実装が選んでよい。
- このツールの終了コード、エラー行の標準エラーへの出し方は [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方は [08. 出力と多言語対応](08-output-and-i18n.md) に従う。この文書は、エラーの内容(種類・位置・理由)までを定める。
- YAML と JSON の読み取り(第 4〜7 節)は、[09. 変換器](09-converter.md)と共有する。実装は、`internal/definition` の中に「木の読み取り」の部分(`tree.go`、`read_yaml.go`、`read_json.go` など)を置き、`internal/convert` はその公開関数を使う。

## 1. 記法と用語

| 語 | 意味 |
|----|------|
| 文字 | Unicode のスカラー値(コードポイント。サロゲートを除く)。「N 文字」は、この単位で数える(UTF-8 のバイト数でも、書記素でもない)。Go では `utf8.RuneCountInString` で数える。 |
| 空白を取り除く(trim) | 文字列の先頭と末尾から、Unicode の White_Space 属性を持つ文字(U+0009〜U+000D、U+0020、U+0085、U+00A0、U+1680、U+2000〜U+200A、U+2028、U+2029、U+202F、U+205F、U+3000)を取り除く。「空白だけ」は、取り除いた結果が空文字列になること。Go の `strings.TrimSpace` が同じ集合かは、実装時に、この列挙を使う単体テストで確かめる(未確認)。 |
| 位置 | 値や構文要素の、入力中の場所。行(1 始まり)と列(1 始まり)の組。取り方は第 13 節。 |
| 行 | 行番号。1 始まり。LF の数で数える(CRLF でも同じ)。 |
| 値の型 | 木の値は、null、真偽値(boolean)、整数(integer)、浮動小数(float)、文字列(string)、リスト(sequence)、マップ(mapping。キーと値の対応)の 7 種のいずれか(第 6 節)。 |
| マップのリスト | 要素がすべてマップであるリスト(`job` や `transitions`)。 |
| 誤り | エラーの 1 件。種類(`kind`)、行(なしもある)、理由(`reason`)をもつ(第 12 節)。 |
| 受理 | その値や書き方を誤りなく読み込むこと。拒否はその逆。 |

## 2. 書式の決定と処理の段階

### 2.1 書式の決定(拡張子)

- 定義ファイルのパスの指定(`--config`)があれば、それを使う。なければ、カレントディレクトリの `conductor.yaml`。
- 書式は、パスの**拡張子**で決める。拡張子は、パスの最後の要素(最後のパス区切りより後ろ)の、最後の `.` から末尾まで(Go の `filepath.Ext` と同じ)。ASCII の大文字小文字を区別しない(`.YAML` は `.yaml`)。

| 拡張子 | 書式 |
|--------|------|
| `.yaml`、`.yml` | YAML |
| `.json` | JSON |
| それ以外(拡張子なしを含む。`.txt`、`.xml` など) | 拒否: `unsupportedFormat`、行なし、理由 ``拡張子は .yaml、.yml、.json のいずれかで書きます`` |

- この判定は、ファイルに触れる前に行う(ファイルが存在しなくても、拡張子が合わなければ `unsupportedFormat` になる)。
- 表示用のファイル名は、パスを文字列にしたもの(与えられた表記のまま。正規化しない)である。

### 2.2 処理の段階と打ち切り

`Load(path, expectedPipelineName)` は次の順に処理する。前の段階で失敗したら、そこで打ち切り、**その 1 件だけ**を返す(後ろの段階は実行しない)。最後の Walk だけが、複数の誤りを返す。

| 段階 | 内容 | 失敗の種類(`kind`) | 返る誤りの数 |
|------|------|----------------------|--------------|
| 1. Intake | 書式の決定、ファイルの読み取り | `unsupportedFormat` / `fileMissing` / `unreadable` / `tooLarge` | 1 |
| 2. Parse | 文法の検査(YAML はライブラリ、JSON は自前の読み取り)と、木の組み立て | `syntax` | 1 |
| 3. Resolve | 文書の数、タグ、キー、アンカーとエイリアスの展開、マージキー、重複キー、上限(要素数・文字の大きさ・入れ子の深さ) | `syntax` / `tooLarge` / `typeMismatch`(最上位がマップでない) | 1 |
| 4. VersionCheck | `format_version` | `versionMissing` / `versionUnsupported` | 1 |
| 5. Walk | 構造、型、遷移、終了コード、名前 | 第 12.3 節の種類のうち該当するもの | 1 件以上(位置の順) |

`Parse(text, format, fileLabel, expectedPipelineName)` は、段階 2〜5 を文字列に対して行う(ファイルに触れない)。`fileLabel` は、エラーの表示に使うファイル名である。

- `expectedPipelineName`(`pipeline` コマンドで渡されたパイプライン名)が無いときは、名前の照合をしない。
- 検証に成功したときだけ、定義(第 14 節)を返す。誤りが 1 件でもあれば、定義は返さない。
- 版の確認(段階 4)に通らないと、構造の検査(段階 5)は一切行わない。たとえば `format_version` が無い定義に、未知のキーや型の誤りがあっても、返るのは `versionMissing` の 1 件だけである。
- 文法の誤り(段階 2)は版の確認より先である。
- **JSON の段階 2 は、入力を 1 回、先頭から読み、最初に見つかった問題(文法の誤り、重複キー)で打ち切る。**
- **YAML の段階 2 は、ライブラリで入力の全体(全文書)を読み終えてから、段階 3 に進む。** したがって、YAML では、入力の後ろにある文法の誤りが、前にある段階 3 の誤り(タグ、重複キー)より先に返る。
- 段階 3 は、木を、深さ優先・入力に現れる順に走査し、最初に見つかった問題で打ち切る。

## 3. 取り込み(Intake)

書式の決定(第 2.1 節)のあと、次の順に調べる。最初に当てはまったもので失敗する。

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルの情報(種別・大きさ)の取得で「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | 同、権限がない | `unreadable` | `読み取りの権限がありません` |
| 3 | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 4 | 通常のファイルでない(ディレクトリなど) | `unreadable` | `通常のファイルではありません` |
| 5 | 取得した大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `ファイルの大きさが上限(1 MiB)を超えています` |
| 6 | ファイルを開けない(権限) | `unreadable` | `読み取りの権限がありません` |
| 6' | ファイルを開けない(その他) | `unreadable` | `読み取りに失敗しました` |
| 7 | 読み取りの途中の失敗 | `unreadable` | 権限の問題なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 8 | 読み取った結果が上限を超える(順 5 のあとに大きくなった場合) | `tooLarge` | 順 5 と同じ |
| 9 | UTF-8 として解釈できない | `unreadable` | `文字コードが UTF-8 ではありません` |

- 上限は **1 MiB = 1,048,576 バイトちょうどまで受理**し、1 バイトでも超えると `tooLarge`。読み取りは「上限 + 1 バイト」までしか行わない(Go では `io.LimitReader` で上限 + 1 バイトに制限して読む)。
- 空のファイル(0 バイト)は、空の文字列として読めて、次の段階へ進む。YAML では文書が 0 個の入力として扱われ、`versionMissing` になる(第 6.7 節)。JSON では文法の誤り(`syntax`)になる(第 5 節)。
- 順 5 の大きさの確認は UTF-8 の確認(順 9)より先なので、1 MiB を超えて UTF-8 でないファイルは `tooLarge` である。
- UTF-8 の確認は、不正なバイト列を含むかどうかを調べる(Go では `utf8.Valid`)。先頭の BOM(U+EF BB BF)は不正ではない。
- いずれも、行番号は付かない。
- シンボリックリンクは、リンク先の情報で判定する(リンクを辿る)。
- OS による権限・種別の判定の細部(Windows など)は、実装に任せてよい。必須なのは、上の表の条件の順序と、各理由の文言である。

## 4. YAML の受理する部分集合

YAML は、YAML 1.2(改訂 1.2.2)の文法で読み、スカラーの型は **コアスキーマ**(第 4.2 節)で決める。YAML 1.1 の型(`yes`/`no`/`on`/`off` の真偽値、`0777` の 8 進、日付、`<<` 以外の拡張など)は扱わない。

文法の細部(エスケープ、折りたたみ、インデントの規則など)は YAML 1.2.2 の規格に従い、読み取りライブラリがそれを実装する。**この文書が規格と別に決めること**は、次の 4.1 の表の「受理」「拒否」の列と、第 4.2〜4.6 節である。ライブラリがこれと違う結果を返すときは、この文書の規定が優先し、実装が補う(第 7 節)。

### 4.1 受理する部分集合と拒否するもの(一覧)

| 項目 | 扱い | 備考 |
|------|------|------|
| 入力の先頭の BOM(U+FEFF) | 受理(無視) | |
| 改行 | LF、CRLF(混在可)を受理 | |
| インデント | 半角スペースだけ。タブをインデントに使うことは拒否(`syntax`) | |
| コメント(`#`) | 受理し、**捨てる**(値に影響しない)。`foo#bar` の `#` は、スカラーの一部 | |
| ブロックのマップ(`key: value`)、ブロックのリスト(`- item`) | 受理 | 親のキーと同じ桁の `- `(インデントなしのリスト)も受理 |
| フローのマップ(`{a: 1}`)、フローのリスト(`[a, b]`) | 受理。入れ子、複数行、末尾のカンマ、`{}`、`[]` も受理 | |
| 引用符なしのスカラー(1 行、複数行) | 受理。型は第 4.2 節で決める | 先頭が `@` または `` ` `` のものは拒否(`syntax`) |
| `'...'`、`"..."` のスカラー | 受理。常に文字列 | 未知のエスケープ(`"\q"`)は拒否(`syntax`) |
| ブロックスカラー(`\|`、`>`)、インデント・チョンプの指示子 | 受理。常に文字列 | |
| 単純キー(1 行の `key:`) | 受理 | 1024 文字を超えるキーは、ライブラリの挙動に任せる(未確認。この文書の例には使わない) |
| 明示のキー(`? key` + `: value`) | キーがスカラーで、第 4.2 節の解決の結果が**文字列**なら受理。それ以外は拒否(第 4.4 節) | |
| アンカー(`&name`)とエイリアス(`*name`) | **受理**。展開して扱う(第 4.3 節) | |
| マージキー(`<<`) | **受理**(第 4.5 節) | |
| タグ(`!!str`、`!!int`、`!foo` など、すべて) | **拒否**(`syntax`、理由 ``タグは使えません``、そのノードの位置の行) | 標準のタグも拒否する |
| 複数の文書(`---` で区切る) | **拒否**(`syntax`、第 4.6 節) | 末尾の `---` も(空の文書がもう 1 つあるものとして)拒否 |
| 文書の開始(`---`)と終了(`...`) | 1 つの文書の前後に置くのは受理 | |
| ディレクティブ | `%YAML 1.2` は受理。ほかのディレクティブ(`%TAG` など)は、ライブラリの挙動に任せる(未確認。この文書の例には使わない) | |
| 文字列でないキー(`1:`、`true:`、`~:`、キーが空、`? [a]` など) | **拒否**(`syntax`、第 4.4 節) | |
| 重複したキー | **拒否**(`syntax`、第 4.4 節) | |
| 閉じていないフロー・引用符、不正なインデント、`a: b: c`(1 行に複数のブロックのマップ)、値の位置にある `-` だけ(`a: -`)、定義されていないアンカーの参照 | 拒否(`syntax`、理由 ``YAML の文法に誤りがあります``) | 定義されていないアンカーの参照は、ライブラリが拒否する(第 7 節) |

「受理」と書いた構文を、ライブラリの都合で拒否してはならない。表にない構文は、YAML 1.2.2 の規格どおりに、ライブラリの結果に従ってよい(未確認の部分は、この文書の例に使っていない)。

### 4.2 スカラーの解決(コアスキーマ)

**引用符なしのスカラー**(引用符も `|`・`>` もない書き方)の型は、スカラーの文字列**全体**に対して、次の順に判定する。ライブラリが返す型情報は使わず、実装が自前で判定する(ライブラリは YAML 1.1 の型を混ぜることがあるため。第 7 節)。

| 順 | 条件 | 結果の型 |
|----|------|----------|
| 1 | 空文字列、`~`、`null`、`Null`、`NULL` | null |
| 2 | `true`、`True`、`TRUE` / `false`、`False`、`FALSE` | 真偽値 |
| 3 | `.inf`、`.Inf`、`.INF`、`+.inf`、`+.Inf`、`+.INF` / `-.inf`、`-.Inf`、`-.INF` / `.nan`、`.NaN`、`.NAN` | 浮動小数(+∞、-∞、NaN) |
| 4 | `0x` + 1 桁以上の 16 進数字(`0-9a-fA-F`) | 整数(16 進。符号なし) |
| 5 | `0o` + 1 桁以上の 8 進数字(0〜7) | 整数(8 進。符号なし) |
| 6 | `[-+]?[0-9]+`(`007` は 7、`-0` は 0、`+7` は 7) | 整数(10 進) |
| 7 | `[-+]? ( \.[0-9]+ \| [0-9]+ (\.[0-9]*)? ) ([eE] [-+]? [0-9]+)?`(整数の書式は順 6 が先) | 浮動小数 |
| 8 | 上のどれでもない | 文字列 |

- 整数は 64 ビット符号つき整数の範囲(-9,223,372,036,854,775,808〜9,223,372,036,854,775,807)で値にする。範囲を超える整数の書式(`9223372036854775808`、`0xFFFFFFFFFFFFFFFFFF`)は、**「範囲外の整数」(`bigint`)**という型の値にする(エラーにはしない。第 6 節)。値を使う検査(第 9 節)が、範囲外として拒否する(例: `format_version: 99999999999999999999` は `versionUnsupported`)。Go では `strconv.ParseInt` の範囲の誤りで判定する。
- 浮動小数は `strconv.ParseFloat` で値にする。範囲を超える大きさ(`1e999`)は、±∞ の値にして「範囲を超えた」という印(`overflow`)を付ける(エラーにはしない。変換器だけが、これを拒否する)。極小の値(`1e-400`)の結果は未確認(`ParseFloat` の結果のまま、エラーにしない)。
- 浮動小数の例: `1.5`、`-0.0`、`.5`、`1.`、`1e3`、`1.5E-2`。文字列になるもの: `.`、`e3`、`1e`、`1.2.3`、`-`、`+`、`.e1`、`inf`、`nan`、`NaN`、`0b11`、`1_000`、`0x`(桁なし)、`0o8`、`+0x1`、`0X1F`。
- **`yes`・`no`・`on`・`off`・`y`・`n`(大文字小文字を問わず)は文字列**。日付・時刻らしい書式(`2001-01-01`、`12:30:00`)も**文字列**。
- 引用符つき(`'...'`、`"..."`)のスカラーと、`|`・`>` のブロックスカラーは、常に文字列(`'1'` は文字列 `1`、`"null"` は文字列 `null`)。
- 空の値(`key:` の後ろに何もない、`- ` の後ろに何もない)は、引用符なしの空文字列と同じ扱いで、**null**。アンカーだけで中身がない(`a: &x`)も null。
- 定義ファイルの検査で、null は「どの型でもない値」である。`description:`(値なし)は `description` の型の誤り、`retry:`(値なし)は `retryNotTable`、`job:`(値なし)は `job` の型の誤り、未知のキーの値が null なら `unknownKey` になる(第 9 節)。

#### 書き方による型の違い(YAML で起きやすい誤り)

| 書き方 | 型 | 定義での結果の例 |
|--------|----|------------------|
| `format_version: 1` | 整数 | 受理 |
| `format_version: "1"` | 文字列 | `versionUnsupported`(整数でない) |
| `format_version: 1.0` | 浮動小数 | `versionUnsupported`(整数でない) |
| `format_version: 0x1`、`0o1`、`01`、`+1` | 整数(値 1) | 受理 |
| `format_version: 1_0` | 文字列 | `versionUnsupported`(整数でない) |
| `id: 1` | 整数 | `typeMismatch`(文字列で書く) |
| `id: yes`、`id: on` | 文字列 | 受理(YAML 1.1 の真偽値ではない) |
| `id: true` | 真偽値 | `typeMismatch` |
| `id: null`、`id: ~`、`id:` | null | `typeMismatch` |
| `interval: 30` | 整数 | `retryDurationInvalid`(文字列で書く) |
| `interval: 30s`、`interval: "30s"` | 文字列 | 受理 |
| `max: "3"`、`max: 3.0` | 文字列、浮動小数 | `retryMaxInvalid` |
| `remove_on_complete: yes` | 文字列 | `typeMismatch`(真偽値で書く) |

### 4.3 アンカーとエイリアス

- `&name` で付けたアンカーを、`*name` で参照できる。`name` は、空白と `,[]{}` を含まない 1 文字以上(ライブラリの規則)。
- エイリアスは、参照先のノードの内容に置き換わる(コレクションは複製して展開する)。展開後の木には、アンカーもエイリアスも残らない。
- 同じ名前のアンカーを再定義してよい。エイリアスは、それより前の**最後の**定義を指す(ライブラリがこう解決することを、実装時に確かめる。未確認)。
- 閉じたアンカーへの参照は再帰ではない(`a: &r [1]` + `b: *r` は受理)。**自分自身を含むエイリアス**(`a: &r [*r]`)は拒否: `syntax`、理由 ``アンカーが自分自身を含んでいます``、行はそのエイリアスの行。判定は、展開中のアンカーの対象ノードの集合を持ち、展開しようとしたエイリアスの対象がその集合に含まれるかで行う。
- エイリアスをキーにしてよい(`*k : 1`)。参照先が、文字列に解決されるスカラーのときに限る(第 4.4 節)。
- **展開の上限**: 第 6.3 節(要素数 100,000、文字の大きさ 16 MiB、深さ 32)。アンカーの入れ子による爆発的な増加(`l0: &l0 [x, x]`、`l1: &l1 [*l0, *l0]`、…)は、この上限で止まらなければならない(必須)。上限を超えたら、複製・確保の**前**に打ち切る。
- 定義の中でアンカーを置ける場所は、定義に存在するノードの中だけである(根のキーは 3 つだけなので、例えば根に `defaults:` を足すと `unknownKey` になる)。典型的な使い方は、ジョブの中のキーの値(`success_exit_codes: &ok [0, 2]` を別のジョブで `*ok`)や、ジョブのマップ全体(`- &base` を、別のジョブが `<<: *base` で取り込む)である(第 11 節の例)。

### 4.4 キー

- マップのキーは、**文字列に解決されるスカラー**でなければならない。次は `syntax`、理由 ``キーは文字列で書きます``、行はそのキーの位置: 整数・真偽値・浮動小数・null に解決されるスカラー(`1: x`、`true: x`、`1.5: x`、`~: x`、キーが空の `: x`)、範囲外の整数、リストやマップのキー(`? [1, 2]`、`[a]: 1`)。引用符つきは常に文字列なので受理(`"1": x`)。
- **重複したキー**は拒否: `syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置。判定は、解決した後の文字列の同一性(UTF-8 のバイト列の完全一致)で行う。引用符の有無が違っても重複(`a: 1` と `"a": 2`)。入れ子のマップごとに別。エイリアスをキーにしたときは、参照先の文字列で判定する。マージキー `<<`(第 4.5 節)を同じマップに 2 回書くことも重複。
- キーの空文字列(`"": x`)は受理する。キーの大文字小文字・前後の空白は区別する。
- この検査は、入力に現れる順(深さ優先)に、段階 3 で行う。重複と非文字列のキーが同じ位置にあれば、どちらでも同じ `syntax` だが、理由は非文字列が先(キーの解決が先)。

### 4.5 マージキー(`<<`)

- マージキーとして扱うのは、**引用符なし・タグなし**のキー `<<` だけ(タグは元々拒否される)。`"<<"`(引用符つき)は、文字列のキー `<<` として、通常のキーと同じに扱う。
- 値は、マップ、またはマップだけのリスト(`<<: [*a, *b]`)。それ以外(整数・文字列・null(`<<: ~` を含む)、マップでない要素を含むリスト)は拒否: `syntax`、理由 ``マージキーの値がマップではありません``、行はマージキーの位置。
- 優先順位: マップ自身の(`<<` でない)キーが、マージの内容より優先する(自身のキーが `<<` の前にあっても後にあっても同じ)。値がリストのときは、**先頭のマップが優先**。マージされるマップが `<<` を含むとき(入れ子のマージ)は、そのマージも同じ規則で先に展開した結果を使う。優先されずに捨てられたキーは、エラーにしない。
- **キーの順**: マージで加わるエントリは、そのマップの `<<` のエントリがあった位置に、取り込み元の順(リストなら先頭のマップから)で並ぶ。捨てられたものは並ばない。その後ろに、`<<` の後ろにある自身のエントリが続く。
- **位置**: マージで取り込まれたエントリ(キーと値と、その中のすべての子)の位置は、そのマージキー `<<` 自身の位置に置き換える(元の位置は使わない)。これは、エラーの行を決めるための規則である(第 13 節)。

### 4.6 複数の文書と最上位

- 文書の数を数える(`---` で区切る。末尾の `---` の後ろが空でも、空の文書が 1 つあるものとして数える。`a: 1\n---\n` は 2 文書)。文書が 2 つ以上ある入力は、ライブラリによる全体の読み取り(段階 2)が成功したときに限り、拒否: `syntax`、理由 ``複数の文書は書けません(1 ファイルに書ける文書は 1 つです)``、行は 2 つ目の文書の位置(空の文書のときの行は未確認。この文書の例では行を示さない)。
- 文書が 0 個(空の入力、コメントと空行だけ)は、**空のマップ**として扱う(結果は `versionMissing`)。
- 最初の文書の最上位が **null**(`---` だけの文書など、中身が空)も、空のマップとして扱う。
- 最上位が、マップでもなく null でもない(リスト、文字列、数など)なら、拒否: `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置。

## 5. JSON の受理する形式

JSON は、RFC 8259 の厳格な形式で読む。読み取りは**自前の小さな字句・構文解析**で行う(第 7.3 節)。

| 項目 | 規定 |
|------|------|
| 入力 | UTF-8。先頭の BOM は無視する(位置には数える)。 |
| 空白 | 半角スペース、タブ、LF、CR だけ。それ以外(垂直タブ、全角スペースなど)を、トークンの間に置くことは拒否。 |
| コメント(`//`、`/* */`、`#`) | **拒否**(`syntax`)。 |
| 末尾のカンマ(`[1,]`、`{"a":1,}`)、連続したカンマ、先頭のカンマ | **拒否**(`syntax`)。 |
| リテラル | `true`、`false`、`null`(小文字だけ)。`True`、`NaN`、`Infinity`、`undefined` は拒否。 |
| 文字列 | `"..."` だけ(単一引用符は拒否)。中にタブを含め、U+0000〜U+001F を直接書くことは拒否(`\t` などで書く)。U+007F 以上は直接書いてよい。エスケープは `\"`、`\\`、`\/`、`\b`、`\f`、`\n`、`\r`、`\t`、`\uXXXX`(16 進 4 桁。大文字小文字どちらでも)。それ以外のエスケープは拒否。`\u` でサロゲートの前半(U+D800〜U+DBFF)に、後半(U+DC00〜U+DFFF)の `\u` が続く対は 1 つの文字にする。**対にならないサロゲート**(単独の前半、単独の後半)は拒否(`syntax`)。 |
| 数 | `-?(0\|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` だけ。`+1`、`01`、`.5`、`5.`、`1e`、`0x10`、`1_000` は拒否。 |
| キー | 文字列だけ。 |
| 重複したキー | **拒否**(`syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置)。判定は、エスケープを解いた後の文字列の完全一致(`"a"` と `"a"` は重複)。 |
| 最上位 | 任意の JSON の値を、文法としては受理する。最上位がオブジェクト(マップ)でなければ、第 6.7 節のとおり `typeMismatch`。JSON の `null` も(YAML と違い)マップではないので `typeMismatch`。 |
| 空の入力、空白だけの入力 | 拒否(`syntax`)。 |
| 最上位の値の後ろ | 空白以外が続くことは拒否(`syntax`。複数の値、`{}{}`、後ろのゴミ)。 |

### 5.1 数の型

- 整数: `-?(0|[1-9][0-9]*)` だけ(小数部も指数部もない書き方)。`-0` は整数 0。64 ビット符号つき整数の範囲を超えるものは `bigint`(YAML と同じ。エラーにはしない)。
- 浮動小数: 小数部または指数部を持つもの(`1.0`、`1e3`、`1E3`、`1e0`、`-0.0`)。値が 64 ビット浮動小数の範囲を超える(`1e400`)ものは、±∞ に `overflow` の印を付ける(エラーにはしない)。
- **整数だけの項目**(`format_version`、`max`、`multiplier`、各種の終了コード)に、浮動小数が来たら、型の誤りとして拒否する。**`1.0`、`1e0`、`10e-1` のように値が整数になる書き方でも拒否**(YAML の `1.0` も同じ)。
- JSON の数のうち、値を使う検査の対象外の場所にある浮動小数や範囲外の整数は、エラーにならない(そのキーが `unknownKey` になるだけ)。

### 5.2 JSON の誤りの位置

文法の誤りの位置は、**入力の先頭から読んでいって、読み進められなくなった最初のバイト**(その前までが、有効な JSON の先頭部分になっているもの)の位置。入力が途中で終わったとき(閉じていない配列・文字列など)は、入力の末尾の位置(末尾が改行なら、その次の空の行を 1 行と数える)。例:

| 入力(`\n` は改行) | 誤りの位置 |
|------|------------|
| `{"a": 1,}` | `}` の位置(1 行目) |
| `{"a" 1}` | `1` の位置 |
| `{\n  "a": 1\n  "b": 2\n}` | `"b"` の位置(3 行目) |
| `[1, 2` + 末尾の改行 | 末尾(2 行目) |
| `{"a": "x` + 改行 + `"}` | 改行の位置(1 行目。文字列の中に改行を直接書いたため) |
| `{"a":1}{"b":2}` | 2 つ目の `{` の位置 |
| `{"a":1,"a":2}`(重複) | 2 つ目の `"a"` の位置(1 行目) |

## 6. 木への展開(Resolve)と上限

### 6.1 木の型

段階 3 の結果と、段階 4・5 の入力は、YAML と JSON に共通の木である。型の骨格(例。名前は実装が決めてよい):

```go
// Pos は入力中の位置(1 始まり)。順序づけと行の表示に使う。
type Pos struct{ Line, Col int }

type Kind int

const (
    KNull Kind = iota
    KBool
    KInt     // 64 ビット符号つきに収まる整数
    KBigInt  // 範囲外の整数(値は持たない)
    KFloat   // 浮動小数(Overflow が真なら、範囲を超えた書き方)
    KString
    KSeq
    KMap
)

type Node struct {
    Kind     Kind
    Pos      Pos       // 第 13 節
    Bool     bool
    Int      int64
    Float    float64
    Overflow bool      // KFloat で、範囲を超えた書き方(1e999 など)
    Str      string    // KString の値
    Src      string    // スカラーの書かれたままの文字列(第 6.3 節の数え方に使う)
    Items    []*Node   // KSeq
    Entries  []Entry   // KMap。順序つき。キーは重複しない
}

type Entry struct {
    Key    string
    KeyPos Pos
    Value  *Node
}
```

- 木は、エイリアスもアンカーもマージキーも含まない(展開済み)。マップのキーは文字列で重複せず、**記述順**を保つ(第 4.5 節のマージの順を含む)。
- 木を走査する処理(段階 3 の走査、深さの数え、検査 Walk、変換器の書き出し)は、**再帰を使わず、明示のスタック**で行うことが望ましい。必須なのは、深い入力でも異常終了せず、定められた誤りで返ること(第 6.4 節)。

### 6.2 YAML の展開の手順(段階 3)

ライブラリが返した、最初の文書の木(エイリアスを参照として持つ)を、深さ優先・入力に現れる順に走査し、上の木に写す。各ノードについて、次を行う。

1. エイリアスなら、参照先を(第 4.3 節の再帰の確認のうえで)展開する。展開したノードとその子の位置は、**エイリアスのトークン `*name` の位置**に置き換える(第 13 節)。
2. 明示のタグがあれば、`syntax`(タグ)で打ち切る。
3. スカラーなら、第 4.2 節で型を決める(キーの位置のスカラーは、文字列でなければ `syntax`(第 4.4 節))。
4. マップなら、第 4.4・4.5 節のとおり、キーの確認、重複の確認、マージの展開を行う。
5. 第 6.3 節の上限を、ノードを訪れるごとに加算して確認する。

### 6.3 上限

| 上限 | 値 | 超過したときの失敗 |
|------|----|--------------------|
| 要素数 | 100,000 | `tooLarge`、理由 ``要素数が上限(100000)を超えています`` |
| 文字の大きさ | 16 MiB(16,777,216 バイト) | `tooLarge`、理由 ``文字の大きさが上限(16 MiB)を超えています`` |
| 入れ子の深さ | 32 | `syntax`、理由 ``入れ子が深すぎます(上限は 32 段)`` |

- **要素数の数え方**: 展開で訪れたノードを 1 つずつ数える。**キーのスカラーも数える**。マップ・リストも 1。根のマップも 1。エイリアスは、エイリアス自身ではなく、**展開した参照先のノード(コレクションなら、その全部)を数える**(同じアンカーを n 回参照すれば、n 回数える)。マージキー `<<` のキー自身も 1 と数え、マージで取り込まれるマップの中身も、捨てられるものを含めて数える。**100,000 ちょうどまで受理**し、100,001 個目で失敗する。JSON にも同じ上限がある(展開はないが、数え方は同じ)。例: `a: [0, 0, ...]`(0 を n 個)は、根のマップ 1 + キー 1 + リスト 1 + 要素 n で、n = 99,997 まで受理、99,998 で失敗(JSON の `{"a":[0,0,...]}` も同じ境界)。
- **文字の大きさの数え方**: 訪れたスカラーの文字のバイト数(UTF-8)を足す。キーと値の両方。文字列(引用符つき、ブロックスカラーを含む)は、**値(エスケープを解いたもの)のバイト数**。引用符なしのスカラー(数、真偽値、null を含む)と、JSON の数・真偽値・null は、**書かれた文字のバイト数**(`123` は 3、`0x1F` は 4、`null` は 4、`true` は 4。値が空の null は 0)。エイリアスの参照のたびに、参照先のスカラーの大きさを足す。マージキー `<<` は 2 バイト。**16 MiB ちょうどは受理**し、1 バイト超えると失敗する。複製・確保の**前**に確認すること(巨大な展開でメモリを使い果たさないために必要)。
- **入れ子の深さの数え方**: テーブルに当たるもの、つまりマップとリストは、それぞれ**1 段**と数える。スカラーは数えない。**根のマップそのものは数えない**。根の直下のコレクションの深さを 1 とし、その子のコレクションは 2、…と数える。**32 段まで受理**し、**33 段目を拒否する**。数えるのは、**展開後の木**(アンカーの入れ子による深さを含む)に対して。失敗の行は、33 段目になったコレクションの位置(第 13 節)。YAML のフロー形式でもブロック形式でも同じに数える。
  - 例: `a: [[[...]]]`(`[` が n 個)は n 段。32 個は受理、33 個は拒否。JSON の `{"a": [[[...]]]}` も同じ。`a: {b: {b: ... 1}}` も、`{` の数が 32 まで受理、33 で拒否。
  - 例: ブロックのリスト `- - - ... x`(`- ` が n 個)は、根がリストでなくマップの値として置くなら n 段(`a:` の次の行から置く)。
  - 例: アンカーの入れ子 `l0: &l0 [x]`、`l1: &l1 [*l0]`、… の `l(k)` は、展開後に k + 1 段になる。`l31` まで(32 段)は受理、`l32`(33 段)は拒否(これらのキーが、`unknownKey` でない場所に置かれているときの話。深さの検査は Walk より先に行うので、根のキーの種類は関係ない)。
- 上限超過の失敗は、いずれも段階 3 の 1 件の打ち切り(`tooLarge`/`syntax`)で、複数は返さない。同じ入力に複数の上限の超過があれば、入力に現れる順で最初のもの。
- どの上限にも、**30 秒以内に**(巨大な展開でも)到達して終わること(必須)。

### 6.4 深い入力と異常終了の禁止

- 数千〜数十万段の入れ子の入力(フロー形式の `[[[[...`、ブロックのリストの `- - - ...`、深いインデントの入れ子)でも、プロセスが異常終了(Go のスタックあふれは `recover` できない致命的な失敗である)せず、`syntax` の 1 件で返らなければならない(必須)。理由が ``入れ子が深すぎます(上限は 32 段)`` か ``YAML の文法に誤りがあります`` かは、実装に任せてよい。
- JSON は自前の読み取りなので、明示のスタックで読み、33 段目を開く時点で打ち切る(必須ではないが、推奨)。
- YAML は、採用ライブラリがこの入力でスタックを使い果たさないことを、実装時に試験で確かめる(未確認)。確かめられなければ、ライブラリに渡す前に、入れ子を字句の上で概算して早期に拒否する前処理を足すか、ライブラリを替える(第 7 節)。

### 6.5 変換器との違い

[09. 変換器](09-converter.md)は、この節の上限と数え方をそのまま使う。変換器だけが、範囲外の数(`bigint`、`overflow` の浮動小数)と NaN・∞ を、拒否する。定義の読み込みは、拒否しない。

### 6.6 JSON の段階 3

JSON には、タグ、アンカー、マージキーがないので、段階 3 は、第 6.3 節の上限の確認と、最上位の確認(次の 6.7)だけである。重複キーと文法の誤りは段階 2 で済んでいる。

### 6.7 最上位の確認

| 入力 | 結果 |
|------|------|
| 最上位がマップ | 次へ |
| YAML で、文書が 0 個、または最上位が null | 空のマップとして次へ(段階 4 で `versionMissing`) |
| それ以外(リスト、スカラー。JSON の `null` を含む) | `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置 |

## 7. YAML ライブラリの選定と、追加で実装すること

### 7.1 方針

YAML は Go の標準ライブラリにないので、外部ライブラリを使う。**選定の基準**は次のとおり。

| 基準 | 内容 |
|------|------|
| 位置 | エラーの行と、各ノードの行・列を取れる(ノードの木が、位置つきで得られる) |
| 木の API | ノードの種別、スタイル(引用符・ブロック・フロー)、アンカー、エイリアス、明示のタグの有無を、型に落とさずに取れる(重複キー、非文字列キー、タグ、複数文書を、自前で拒否するため) |
| 複数の文書 | 入力に文書がいくつあるかを、数えられる |
| 保守 | 保守が続いている(実装時に、直近の更新と、報告された不具合の状況を確認する) |
| 依存 | 依存が少ない |

### 7.2 候補と採用案

| 候補 | 評価(**この文書の作成時に確認できた範囲**) | 判断 |
|------|---------------------------------------------|------|
| `go.yaml.in/yaml/v3`(YAML 組織が保守している、`gopkg.in/yaml.v3` の後継) | 公開ドキュメントで、`Node` の型(`Kind`、`Style`、`Tag`、`Value`、`Anchor`、`Alias`、`Content`、`Line`、`Column`)と、スタイルのビット(`TaggedStyle`、`DoubleQuotedStyle`、`SingleQuotedStyle`、`LiteralStyle`、`FoldedStyle`、`FlowStyle`)があることを確認した。`Decoder` が値を 1 つずつ読むことも確認した(複数文書を順に読めると見込めるが、明記は確認できなかった)。元のリポジトリが「保守されていない」と表明されて、YAML 組織が引き継いだことを、確認した。ドキュメントには、より新しい主版(v4)の存在が示されていた | **採用案**。ただし、採用前に、第 7.4 節の受け入れ試験に通ることを確かめる。実装時に、最新の安定版と、v3 系を使い続けてよいか(v4 が安定版か)を確認し、版を固定する |
| `gopkg.in/yaml.v3` | 上の後継の元。保守されていない(作者が表明した、と上のドキュメントで確認) | 採用しない |
| `github.com/goccy/go-yaml` | 位置つきの構文木を持つとされる(確認していない) | 採用案が試験に通らないときの、代替候補(未確認) |
| `sigs.k8s.io/yaml` | YAML を JSON に変換して扱う作り。位置を持たない | 位置の基準を満たさないので採用しない |
| 自前の YAML 解析 | 文法が大きく、規格への適合の確認が重い | 採用しない |

- この文書は、採用案のライブラリの `Node` の木(種別、スタイル、アンカー、エイリアス、タグの有無、行、列)だけに依存して、規定を満たせるように書いてある。同じ情報を返す別のライブラリでも、実装できる。
- ライブラリの版、モジュールのパス、`go.mod` への固定の仕方は、実装時に確認して決める(未確認)。

### 7.4 受け入れ試験(採用の条件)

第 16 節の受理・拒否の例を、そのままテストにして通ること。特に次を確かめる(これらに通らないライブラリは採用しない)。

1. 第 4.1 節の「受理」の構文が、すべて受理される。
2. 明示のタグ(スカラーにも、マップ・リストにも)が、拒否される。

4. 1 MiB の `[` の連続、1 MiB の `- ` の連続が、プロセスを落とさず、`syntax` で返る(第 6.4 節)。
5. 範囲外の整数、`yes`/`no`/`on`/`off` が、第 4.2 節の型になる(自前の判定の確認)。
6. 文法の誤りの入力が、`syntax` になり、第 13.4 節の例の行が(取れる範囲で)一致する。

## 8. 書式の版(VersionCheck)

根の `format_version` を確認する。

| 状況 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `versionMissing` | なし | `` `format_version` が必要です(対応する版は 1 です) `` |
| 整数でない(文字列、浮動小数、真偽値、null、リスト、マップ。`1.0`、`1e0` を含む) | `versionUnsupported` | 値の位置の行 | `` `format_version` は整数で書きます(対応する版は 1 です) `` |

## 9. 定義の構造(Walk)

以降の「マップ」「リスト」は、木の型(第 6.1 節)である。**キーの型**は、すべて文字列(第 4.4 節で保証)。位置の取り方は第 13 節。

根のマップは、次のキーだけを持てる。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `format_version` | 整数 | 必須 | 第 8 節 |
| `pipeline` | マップ | 必須 | 第 9.1 節 |
| `job` | マップのリスト | 必須(1 つ以上) | 第 9.2 節 |

許されていないキー(上の 3 つ以外)は、`unknownKey` である。`jobs`(複数形)も未知のキーとして拒否される(``キー `jobs` は定義にありません``)。`unknownKey` の理由は、`` キー `<キー名>` は定義にありません `` の形(`<キー名>` は整形したキー名)で、キー名の整形は第 12.2 節。位置はそのキーの位置。値の型は問わない(null でも、アンカーの参照でも同じ)。

### 9.1 `pipeline`

| キー | 型 | 必須 | 既定値 | 検査 |
|------|----|------|--------|------|
| `name` | 文字列 | 必須 | なし | 空白だけ(trim して空)なら `emptyField` |
| `description` | 文字列 | 任意 | なし | 型だけ |
| `run_id_env` | 文字列 | 任意 | なし(実行時の既定は環境変数 `CONDUCTOR_RUN_ID`) | 名前の形(下記) |
| `remove_on_complete` | 真偽値 | 任意 | `false` | 型だけ |

- 許されたキー以外は `unknownKey`(例: `owner`、`remove_on_complet`)。
- `name` が無い: `typeMismatch`、行は `pipeline` のマップの位置、理由 ``必須の値 `name` がありません``。文字列でない(null を含む): `typeMismatch`、値の位置、理由 `` `name` は文字列で書きます ``。`description` が文字列でない: `typeMismatch`、値の位置、理由 `` `description` は文字列で書きます ``。`run_id_env` が文字列でない: `typeMismatch`、値の位置、理由 `` `run_id_env` は文字列で書きます ``。`remove_on_complete` が真偽値でない: `typeMismatch`、値の位置、理由 `` `remove_on_complete` は真偽値(`true` または `false`)で書きます ``。
- `name` が空白だけ: `emptyField`、`name` の値の位置、理由 `` `name` が空です ``(名前の照合はしない)。
- `run_id_env` の名前の形の誤り: `invalidEnvName`、値の位置、理由 `` `run_id_env` は、英字または `_` で始まり、英数字と `_` だけの名前で書きます ``。
- `run_id_env` の名前の形: 1 文字以上で、先頭が ASCII の英字(`A-Za-z`)または `_`、2 文字目以降が ASCII の英数字(`A-Za-z0-9`)または `_`。受理: `A`、`_`、`_a1`、`GITHUB_RUN_ID`。拒否(`invalidEnvName`): `""`、`1A`、`A-B`、`A B`、`A=B`、`é`、`A.B`、NUL を含む文字列。文字列でない値(整数など)は `typeMismatch`。誤りの文に、値は含めない。
- `remove_on_complete` は真偽値だけ(`true` / `false`、YAML では `True`、`TRUE` なども)。文字列 `"true"`、`yes`(文字列)、整数 `1`、リスト `[true]` は `typeMismatch`。型が違うときの値は、`false` として扱って続行する(誤りは報告済み)。
- `pipeline` の形:
  - 無い: `typeMismatch`、行は **1 行目**(位置 (1, 1))、理由 ``必須の値 `pipeline` がありません``。
  - リスト: `typeMismatch`、リストの位置、理由 `` `pipeline` は 1 つだけで、マップで書きます(1 ファイルに 1 パイプライン) ``。
  - その他(整数、文字列、null など): `typeMismatch`、値の位置、理由 `` `pipeline` はマップで書きます ``。
  - 上の誤りのとき、`pipeline` の中身の検査は行わない。
- 名前の照合: `expectedPipelineName` が与えられ、定義の `name` と**完全に同じでない**(大文字小文字・空白も区別。バイト列の比較)と、`pipelineNameMismatch`、行は `name` の値の位置、理由 ``指定されたパイプライン名が、定義の `name` と一致しません``。理由に両方の名前は含めない。`name` が空白だけのときは、`emptyField` だけを返し、照合はしない。`name` が文字列でない・無いときも、照合はしない。

### 9.2 `job`

`job` は、マップのリストでなければならない。

- 無い: `noJobs`、行は 1 行目(位置 (1, 1))、理由 ``ジョブ(`job`)が 1 つもありません``。
- 空のリスト(`job: []`): `noJobs`、行は `job` の値の位置。
- リストでない(マップ、整数、null など): `typeMismatch`、値の位置、理由 `` `job` はマップのリストで書きます ``。
- リストの要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `job` の要素はマップで書きます ``(その要素の検査は行わない)。

各ジョブ(マップ)のキー:

| キー | 型 | 必須 | 既定値 | 説明 |
|------|----|------|--------|------|
| `id` | 文字列 | 必須 | なし | ジョブID。第 11.1 節の検査 |
| `command` | 文字列、または文字列のリスト | 必須 | なし | 第 9.3 節 |
| `warning_exit_codes` | 整数のリスト | 任意 | 空(`[]`) | 警告にする終了コード |
| `success_exit_codes` | 整数のリスト | 任意 | 省略(意味は `[0]`) | 成功にする終了コード |
| `transitions` | マップのリスト | 任意 | 空 | 第 9.4 節 |
| `retry` | マップ | 任意 | なし | 第 9.5 節 |

許されたキー以外は `unknownKey`(例: `warn_exit_codes`)。

- `id` が無い: `typeMismatch`、行はジョブのマップの位置、理由 ``必須の値 `id` がありません``。文字列でない: `typeMismatch`、値の位置、理由 `` `id` は文字列で書きます ``。
- 終了コードのリスト(`warning_exit_codes` と `success_exit_codes`):
  - リストでない(null を含む): `typeMismatch`、値の位置、理由 `` `<キー名>` は整数のリストで書きます ``(`<キー名>` は実際のキー名)。
  - 要素が整数でない、または 32 ビット符号つき整数の範囲(-2,147,483,648〜2,147,483,647)に収まらない: 要素ごとに `typeMismatch`、その要素の位置、理由 `` `<キー名>` の要素は、整数(32 ビットの範囲)で書きます ``。1 つでも誤りがあれば、そのキー全体を「無効」として扱い、後続の重なりの検査では使わない。
  - 負の値(例: `-1`)は、その範囲なので**受理**する。重複した値も受理し、除かない(書いた順のまま保持する)。空のリストも受理する(`success_exit_codes: []` は、成功にする終了コードが無い、の意味になる)。
  - 整数は、YAML の `0x1F`、`0o17`、`+3`、`007` でもよい(値で判定する)。JSON は 10 進の整数だけ。
- `success_exit_codes` を省略すると、成功の終了コードは `[0]`。書いたら、**書いた値だけ**が成功(`0` を書かなければ 0 でも成功にならない)。
- 要素が浮動小数(`1.0`、`1e0`)や、範囲外の整数(`99999999999999999999`)のときも、要素の型の誤り(`typeMismatch`)になる。

### 9.3 `command`

| 書き方 | 受理の条件 | 保持される値 |
|--------|-----------|---------------|
| 文字列 | trim して空でない | 1 本の文字列(そのまま。trim した値ではない) |
| 文字列のリスト | 空でないリストで、全要素が文字列で、**先頭の要素が trim して空でない**。2 番目以降の要素は空文字列でもよい | 要素の並び(そのまま) |

どちらの書き方かは、取り込み後も区別して保持する(実行側の解釈が異なる。[05. 実行フロー](05-execution-flow.md)・[07. プロセスとシグナル](07-process-and-signals.md))。

誤り:

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `typeMismatch` | ジョブのマップの位置 | ``必須の値 `command` がありません`` |
| 文字列が空または空白だけ | `emptyField` | 値の位置 | `` `command` が空です `` |
| リストが空 | `emptyField` | 値の位置 | `` `command` の配列が空です `` |
| リストに文字列でない要素がある | `typeMismatch`(要素ごと) | その要素の位置 | `` `command` の配列の要素は、文字列で書きます `` |
| リストの先頭の要素が空または空白だけ(全要素が文字列のとき) | `emptyField` | 先頭の要素の位置 | `` `command` の配列の先頭の要素が空です `` |
| 文字列でもリストでもない(整数・真偽値・マップ・null) | `typeMismatch` | 値の位置 | `` `command` は文字列、または文字列の配列で書きます `` |

- リストに型の誤りの要素があるときは、先頭要素の空の検査はしない。
- 受理の例(YAML): `command: echo x`、`command: ["my prog", "a b", "$HOME", ""]`、`command: [echo, ""]`。拒否の例: `command: 5`、`command: true`、`command: {a: 1}`、`command: ["a", 5]`、`command: [[a]]`(`typeMismatch`)、`command: ""`、`command: "   "`、`command: []`、`command: [""]`、`command: ["  ", x]`(`emptyField`)、`command:`(値なしは null。`typeMismatch`)。
- 文字列の `command` の中の引用符・`$` などは、この段階では解釈しない(実行時の解釈は実行側の仕様)。YAML の引用符なしの複数行のスカラーは、折りたたまれた 1 つの文字列(改行が空白 1 個になる)になるが、書き方による値の違いは、そのまま保持する。
- 理由の文言(`の配列` という語)は、リストを指す(日本語の原文として固定する。`リスト` に言い換えない)。
- 誤りの文に、入力の値は含めない。

### 9.4 `transitions`

`transitions` は、マップのリスト(YAML のブロックの `- on: success` の繰り返し、またはフロー形式 `[{on: success, next: b}]`、JSON の配列)。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `on` | 文字列 | 必須 | `success` または `warning` |
| `next` | 文字列 | 必須 | 遷移先のジョブID、または `@end` |

- 許されたキー以外(`when` など)は `unknownKey`。
- `transitions` がリストでない(null を含む): `typeMismatch`、値の位置、理由 `` `transitions` はマップのリストで書きます ``(遷移は空として扱う)。要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `transitions` の要素はマップで書きます ``。
- `on` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `on` がありません``。文字列でない: `typeMismatch`、値の位置、`` `on` は文字列で書きます ``。
- `on` の値: `success`、`warning` を受理。`error` は `errorTransition`、値の位置、理由 ``エラー結果(`error`)には遷移先を書けません``。それ以外の文字列(`later`、大文字の `Success` など)は `typeMismatch`、値の位置、理由 `` `on` は `success` または `warning` で書きます ``。YAML のキー `on` は、YAML 1.1 の真偽値ではなく、文字列のキー(`on`)として読まれる(第 4.2 節)。
- `next` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `next` がありません``。文字列でない: `typeMismatch`、値の位置、`` `next` は文字列で書きます ``。
- 同じ `on`(`success` どうし、`warning` どうし)の遷移が 2 つ以上: 2 つ目以降の遷移に `duplicateTransition`、行は**その遷移(マップ)の位置**、理由 ``同じ結果(`on`)の遷移が 2 つ以上あります``。`success` と `warning` を 1 つずつは受理。`on` が不正(`error` や未知の値、型の誤り)の遷移は、重複判定に入れない。
- 遷移先の存在・順序の検査は、第 11 節。

### 9.5 `retry`

ジョブが決めた終了コードで終わったときに、待って実行し直す設定。書き方は、ブロックのマップでもフローのマップでも、JSON のオブジェクトでもよい。

許されたキーは次の 5 つだけ。それ以外は `unknownKey`(例: `retries`)。

| キー | 型 | 必須 | 範囲・書式 | 取り込み後 |
|------|----|------|-----------|-------------|
| `exit_codes` | 整数のリスト | 必須 | 空でない。各要素は 1 以上 255 以下の整数 | 昇順に並べ、重複をまとめる(`[75, 3, 75, 3, 12]` → `[3, 12, 75]`) |
| `max` | 整数 | 必須 | 1 以上 100 以下 | 整数(32 ビット符号なしに収まる) |
| `interval` | 文字列 | 必須 | `<整数><s\|m\|h>`、1 秒以上 24 時間以下 | 秒(64 ビット符号なし整数) |
| `multiplier` | 整数 | 任意 | 2 以上 10 以下 | 整数、または無し |
| `max_interval` | 文字列 | 任意 | `interval` と同じ書式、`interval` 以上 | 秒、または無し |

- 127 などの値も受理する(`[127, 1]` → `[1, 127]`)。
- `multiplier` と `max_interval` は、**両方を書くか、両方とも書かない**か。片方だけなら `retryBackoffIncomplete`。両方なしなら、待ち時間は毎回 `interval`。

#### 間隔の文字列の書式

- 文字列の最後の 1 文字が単位(`s`=秒、`m`=分=60 秒、`h`=時間=3600 秒。小文字だけ)。その前が、**ASCII の数字(0〜9)だけ**の 1 文字以上の列(符号・空白・小数点・`_`・全角数字・16 進(`0x`)は不可)。
- 数値は 1 以上。秒に換算した値が 1 以上 86,400(24 時間)以下。桁あふれ(64 ビット符号なし整数に収まらない、または換算の乗算があふれる)は拒否。先頭の 0 は何個並べてもよい(`0000000000000000000000000001s` は値 1 で受理)。値が 86,400 秒を超えるものは、桁数にかかわらず拒否する(巨大整数の型を使うか、あふれを検知すればよい。結果は同じ)。
- 受理: `1s`、`30s`、`5m`、`2h`、`24h`、`1440m`、`86400s`、`01s`(値 1)。拒否: `""`、`s`、`10`、`1.5s`、`-1s`、`+1s`、` 1s`、`1s `、`1 s`、`1d`、`1S`、`１s`、`1ms`、`0x10s`、`1_0s`、`0s`、`0h`、`86401s`、`25h`、`99999999999999999999999s`、`18446744073709551615h`。文字列でない値(整数・真偽値・null)も拒否。
- YAML では、`interval: 30s` のように引用符なしで書いた `30s` は文字列、`interval: 30` は整数なので拒否。`interval: 0x10s` は文字列だが、書式に合わないので拒否(`retryDurationInvalid`)。

#### 誤りと検査

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| `retry` がマップでない(整数、文字列、リスト、null) | `retryNotTable` | `retry` の値の位置(リストのときは、リストの位置) | `` `retry` はマップで書きます `` |
| 必須のキー(`exit_codes`、`max`、`interval`)が無い | `retryMissingKey`(欠けたキーごとに 1 件) | `retry` のマップの位置 | ``必須の値 `<キー名>` がありません`` |
| `exit_codes` がリストでない | `retryExitCodeInvalid` | 値の位置 | `` `exit_codes` は整数の一覧で書きます `` |
| `exit_codes` が空のリスト | `retryExitCodesEmpty` | 値の位置 | `` `exit_codes` が空です `` |
| `exit_codes` の要素が整数でない、32 ビットの範囲外、1〜255 の範囲外(0、256、-1、1.5、`"75"`、`true` など) | `retryExitCodeInvalid`(要素ごと) | その要素の位置 | `` `exit_codes` の要素は、1 以上 255 以下の整数で書きます `` |
| `max` が整数でない、または 1〜100 の範囲外(0、101、-1、1.5、`"3"`、`true`) | `retryMaxInvalid` | 値の位置 | `` `max` は、1 以上 100 以下の整数で書きます `` |
| `interval` / `max_interval` が書式・範囲に合わない | `retryDurationInvalid` | 値の位置 | `` `<キー名>` は、整数と単位(`s`、`m`、`h`)で、1 秒以上 24 時間以下に書きます(例: `30s`) ``(`<キー名>` は `interval` か `max_interval`) |
| `multiplier` が整数でない、または 2〜10 の範囲外(1、11、0、-2、`2.0`、`"2"`、`true`) | `retryMultiplierInvalid` | 値の位置 | `` `multiplier` は、2 以上 10 以下の整数で書きます `` |
| `multiplier` と `max_interval` の片方だけがある | `retryBackoffIncomplete` | `retry` のマップの位置 | `` `multiplier` と `max_interval` は、両方を書くか、両方とも書きません `` |
| `exit_codes` に、そのジョブの成功または警告の終了コードと同じ値がある | `retryExitCodesOverlap` | `exit_codes` の**キー**の位置 | `` `exit_codes` に、成功または警告の終了コードと同じ値があります `` |
| `max_interval` が `interval` より小さい(秒で比べる。等しければ受理) | `retryMaxIntervalTooSmall` | `max_interval` の値の位置 | `` `max_interval` は、`interval` 以上で書きます `` |

- 整数の判定は、整数の型の値(64 ビット符号つきに収まるもの)で行う。範囲外の整数(`bigint`)は、範囲外の誤りと同じ扱い。
- 空のマップ(`retry: {}`)は、`retryMissingKey` が 3 件(`exit_codes`、`max`、`interval` の順)返る(行はすべて同じ。マップの位置は、フロー形式では `{` の位置)。
- `exit_codes` の複数の要素が不正なら、不正な要素ごとに 1 件(例: `[0, 75, 256]` は 2 件)。
- **重なりの検査**(`retryExitCodesOverlap`)は、定義の他の値と照合する。`exit_codes` が有効(エラーなし)のときだけ行う。
  - 成功の終了コード: `success_exit_codes` を**書かなければ `[0]`**。書いて有効なら、その値。書いたが誤り(無効)のときは、成功との重なりを調べない(警告との重なりは調べる)。
  - 警告の終了コード: `warning_exit_codes` が有効なら、その値(無効なら調べない)。
  - どちらかと 1 つでも共通する値があれば、1 件(重なりの値の数にかかわらず 1 件)。
  - 例: `success_exit_codes: [0, 5]` と `exit_codes: [5, 75]` は誤り。`success_exit_codes: [3]` と `exit_codes: [3]` も誤り。`success_exit_codes: [0, 5]`、`warning_exit_codes: [4]`、`exit_codes: [75]` は受理。
- `retry` の有無は、ほかのキーの読み取りの結果に影響しない。
- 誤りの文に、入力の値は含めない。

## 10. 検査の順序とエラーの集約・並び

Walk の中の処理順(誤りは、見つかった順に集める):

1. 根のキー検査(`unknownKey`)。
2. `pipeline`: キー検査 → `name` → `description` → `run_id_env`(型の誤り、続けて名前の形の誤り) → `remove_on_complete` → `name` の空の検査 → 名前の照合。
3. `job`: 無い/空/型の誤りの処理。リストなら、各ジョブを順に、次の順で検査する: キー検査 → `id` → `command` → `warning_exit_codes` → `success_exit_codes` → `transitions`(各遷移について、キー検査 → `on` → `next` → 重複) → `retry`(キー検査 → `exit_codes` → `max` → `interval` → `multiplier` → `max_interval` → 倍率と上限の片方だけの検査)。
4. 全ジョブにまたがる検査(第 11 節): ジョブIDの検査 → 各ジョブについて、遷移先 → 終了コード(`zeroAsWarning`、`overlappingExitCodes`) → `retry` の重なり・上限と間隔の大小。
5. 誤りが 1 件もなく、`pipeline` とすべてのジョブが組み立てられるときだけ、定義を返す。

返す誤りの順序: すべての誤りを、**位置(行、同じ行なら列)の昇順**に並べて返す。同じ位置のものは、上の検査の順(集めた順)を保つ(安定な並べ替え)。位置の取り方は第 13 節。

- 型の誤りなどで検査できなくなった値は、その値に依存する後続の検査だけを省略する(他の検査は続ける)。
- 位置が (1, 1) の誤りは、行 1 として扱われる(`pipeline` が無い、`job` が無い)。

複数の誤りの例:

```yaml
format_version: 1
unknown_top: true          # 2 行目: unknownKey

pipeline:
  name: p

job:
  - id: a
    command: x
    success_exit_codes: [zero]   # 10 行目: typeMismatch

  - id: b
    command: y
    colour: red              # 14 行目: unknownKey
    transitions:
      - on: success
        next: nowhere        # 17 行目: unknownTarget
```

返る誤り: `unknownKey`(2)、`typeMismatch`(10)、`unknownKey`(14)、`unknownTarget`(17)。

## 11. ジョブ間の検査

### 11.1 ジョブID

`id` が文字列であるジョブごとに、記述順に検査する。

- trim して空、または先頭が `@` → `invalidJobId`、`id` の値の位置、理由 ``ジョブID(`id`)は、空でなく、`@` で始まらない文字列で書きます``。この ID は、遷移先の索引に入らない(後続のジョブから、遷移先として参照できない)。
- 既出の ID と完全に同じ(大文字小文字・前後の空白も区別。`" a "` と `"a"` は別) → `duplicateJobId`、2 つ目以降の `id` の値の位置、理由 ``同じジョブID(`id`)が、すでに定義されています``。
- 長さの上限、使える文字(空白・記号)の制限は、これ以外にない(定義の検査では。実行時の状態ファイル名などへの影響は、[06. ステートファイル](06-state-file.md)による)。

### 11.2 遷移先

`on` と `next` がともに有効な遷移について、`next` を検査する(`on` が不正な遷移は、検査しない)。

- `next == "@end"`: 受理(以降のジョブをスキップして終える)。
- ID の索引に無い(存在しない、または無効な ID): `unknownTarget`、`next` の値の位置、理由 ``遷移先(`next`)のジョブが、定義にありません``。
- 記述順で、自分自身または前のジョブ(位置 ≦ 自分の位置): `backwardOrSelfTarget`、`next` の値の位置、理由 ``遷移先(`next`)は、記述順で後ろのジョブまたは `@end` で書きます``。
- 後ろのジョブの ID は受理する。

### 11.3 終了コード

各ジョブについて(`warning_exit_codes` と `success_exit_codes` が有効なとき):

- `warning_exit_codes` に 0 を含む → `zeroAsWarning`、`warning_exit_codes` の**キー**の位置、理由 ``0 は警告の終了コード(`warning_exit_codes`)にできません``。(`success_exit_codes` の誤りの有無に関わらず検査する。)
- 両方を書き、有効で、共通する値がある → `overlappingExitCodes`、`warning_exit_codes` の**キー**の位置、理由 `` `warning_exit_codes` と `success_exit_codes` に、同じ値があります ``。ただし、共通の値が 0 だけで、すでに `zeroAsWarning` を報告した場合は、重ねて報告しない(例: `warning_exit_codes: [0]` と `success_exit_codes: [0]` は `zeroAsWarning` の 1 件だけ)。
- `success_exit_codes` を書かないとき、成功は `[0]` だが、`warning_exit_codes` との重なりは(書かれていない側は)調べない。警告に 0 を入れた場合は、`zeroAsWarning` で拒否される。

### 11.4 `retry` との関係

第 9.5 節(重なり、上限と間隔の大小)。

## 12. エラーの種類と表示

### 12.1 エラーの構造

型の骨格(例):

```go
type Error struct {
    File   string // 表示用のファイル名(第 2.1 節)
    Line   int    // 1 始まり。0 は「行なし」
    Column int    // 1 始まり。0 は「列なし」。順序づけにだけ使い、表示には出さない
    Kind   ErrKind // 種類(第 12.3 節。木のノードの Kind とは別の型)
    Reason string // 固定の文から組み立てた理由
}
```

| フィールド | 内容 |
|------------|------|
| `file` | 表示用のファイル名 |
| `line` | 行番号(1 始まり)。位置が決まらないときは無し |
| `column` | 列番号(1 始まり)。同じ行の中での順序づけのために保持する。**表示には出さない** |
| `kind` | 種類(第 12.3 節) |
| `reason` | 固定の文から組み立てた理由。入力の値は含めない。入力由来はキー名だけ(`unknownKey`) |

ライブラリ(読み込み処理の呼び出し側)に返す表示の書式:

```
<file>:<line>: <種類の文>: <reason>      行があるとき
<file>: <種類の文>: <reason>             行が無いとき
```

例: ``conductor.yaml:7: 定義にないキーです: キー `x` は定義にありません``。ここで `<file>` は、制御文字・書式文字(第 12.2 節と同じ対象)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは、256 文字までで切って末尾に `…` を付ける)。

`conductor` コマンドの標準エラーへの表示は、`conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason>` の 1 行(誤りごとに 1 行、位置の順)で、`reason` は日本語のまま(言語によらない)。種類の文は、メッセージの言語([08](08-output-and-i18n.md))が日本語のとき日本語(第 12.3 節の「日本語」)、それ以外は英語(「英語」)。`<file>` と `reason` は、改行・制御文字・書式文字をエスケープして表示する(`\n`、`\r`、`\t`、その他は `\u{16進小文字}`)。**ここでは文字数で切らない**。例:

```
conductor: error: bad.yaml:7: unknown key: キー `typo` は定義にありません
conductor: error: conductor.yaml: definition file does not exist: 指定の場所にファイルがありません
```

定義の誤りがあるときの終了コード(64)と、その標準出力・標準エラーの扱いは、[10. エラーと終了コード](10-errors-and-exit-codes.md)に従う。

### 12.2 キー名の表示

`unknownKey` の理由に入るキー名は、`` ` `` で囲み、次の整形をする。

- 改行を `\n`、復帰を `\r`、タブを `\t` に、その他の制御文字(U+0000〜U+001F、U+007F〜U+009F)と書式文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)を `\u{16進小文字}` にエスケープする(例: U+0001 は `\u{1}`)。
- エスケープ後の文字数が **64 文字**を超えるときは、64 文字までで切って末尾に `…` を付ける(エスケープの途中では切らない。たとえば、残りが 2 文字でエスケープが 6 文字なら、そのエスケープは入れず、そこで切る)。ちょうど 64 文字は切らない。
- この整形は、`file`(256 文字)の整形と同じ手順で、上限だけが違う。

### 12.3 種類の一覧(31 種)

「識別子」は機械が読む名前、「日本語」は日本語の種類の文、「英語」は英語の種類の文。

| 識別子 | 日本語 | 英語 |

## 13. 位置(行番号と列番号)の出し方

### 13.1 位置の単位

- 位置は、行と列の組(`Pos`)。**行は 1 始まりで、LF の数で数える**(CRLF でも、CR は直前の行に属し、LF のあとが次の行)。**列は 1 始まりで、その行の先頭からの文字数 + 1**(ライブラリが返す列の単位が、文字数かバイト数かは未確認。**列は、同じ行の中の誤りの並びを決めるためだけに使い、行が違えば比べない**。同じ行の中で、前にあるものほど小さい列を返す限り、単位はどちらでもよい)。
- 先頭の BOM は、位置には数えない(1 行目の 1 列目は、BOM の次の文字)。
- 位置が決まらない誤りは、行なし(取り込み、`versionMissing`、一部の `syntax`)。
- 位置が (1, 1)(入力の先頭)の誤りは、`pipeline` が無い、`job` が無い。

### 13.2 ノードの位置

| ノード | 位置 |
|--------|------|
| スカラー | 値の先頭の文字(引用符つきなら、開く引用符。ブロックスカラーなら、`\|` または `>` の位置)。アンカー `&name` が前置されていても、**内容の位置**(アンカーの位置ではない。ライブラリがこう返すかは未確認。違う場合は、実装が補う。差が出るのは、アンカーと内容が別の行にあるときだけ) |
| ブロックのマップ | **最初のキーの先頭**。そのキー自身が引用符つきなら、開く引用符 |
| フローのマップ | `{` の位置 |
| ブロックのリスト | **最初の `-` の位置** |
| フローのリスト | `[` の位置 |
| JSON のオブジェクト・配列 | `{` / `[` の位置 |
| マップのキー(`KeyPos`) | キーのスカラーの先頭 |
| 展開されたノード(エイリアスから) | **エイリアスのトークン `*name` の位置**(複製した子のすべても同じ位置) |
| マージで取り込まれたエントリ | そのマージキー `<<` の位置(キー、値、値の中のすべて) |

- 「値の位置」とは、そのキーの値のノードの位置。「キーの位置」とは、`KeyPos`。「マップの位置」とは、上の表のマップのノードの位置(必須キーの欠落、`retryMissingKey`、`retryBackoffIncomplete` で使う)。
- ライブラリが返す行・列が、上の表と違う場合(例: ブロックのマップの位置を、親のキーの位置にするなど)は、実装が補正する(未確認)。補正が必要かは、第 7.4 節の試験の行番号で確かめる。

### 13.3 誤りの位置の取り方(まとめ)

- 型の誤りや範囲の誤りは、**誤った値のノードの位置**。
- 未知のキーは、**キーの位置**。
- 必須のキーの欠落は、**それを含むマップの位置**。
- `pipeline` や `job` 自体が無いときは、(1, 1)。
- 終了コードの重なり(`overlappingExitCodes`、`zeroAsWarning`、`retryExitCodesOverlap`)は、対象の**キー**の位置(値ではない)。
- リストの誤りは、要素ごとに、その要素の位置。
- 取り込みの誤り、`unsupportedFormat`、`versionMissing` は、行なし。
- 段階 3 の誤りは、そのノードの位置(キーの誤り(重複、非文字列)はキーの位置、マージキーの誤りは `<<` の位置、深さの誤りは 33 段目のコレクションの位置、上限(要素数、大きさ)の誤りは、超えたノードの位置)。

### 13.4 文法の誤りの行

- **JSON**: 第 5.2 節のとおり、必須。
- **YAML**: 文法の誤りは、ライブラリが検出した位置の行。検出位置は、ライブラリの作りで変わる(原因の行より後ろになることも、前になることもある)。**必須なのは、種類(`syntax`)と理由(`YAML の文法に誤りがあります`)であり、行は、ライブラリが返すものでよい**(下の例で、採用したライブラリの結果を確認し、違うときは実装時に判断して、この文書の例を更新する)。実装時に確認する例(未確認): `format_version: 1` + `pipeline: [1, 2` のように、閉じていないフローの誤りが、後ろの行で検出される。

## 14. 取り込み後のデータモデル

検証に成功すると、次のデータを返す(型の骨格)。

```go
type Definition struct {
    Name             string  // 空白だけでない(trim していない元の値)
    Description      *string // 無いなら nil
    RunIDEnv         *string // 名前の形は検査済み。nil なら実行時に CONDUCTOR_RUN_ID
    RemoveOnComplete bool    // 省略時 false
    FormatVersion    int     // 1
    Jobs             []Job   // 記述順を保つ。1 つ以上
}

type Job struct {
    ID               string        // 空白だけでなく、@ で始まらず、定義内で一意
    Command          Command       // 文字列で書いたか、リストで書いたか
    WarningExitCodes []int32       // 省略時は空。0 を含まない。書いた順のまま
    SuccessExitCodes *[]int32      // 省略時 nil(意味は [0])
    Transitions      []Transition  // 書いた順。on ごとに高々 1 つ
    Retry            *RetryPolicy  // 書かなければ nil
}

type Command struct {
    Line string   // 文字列で書いたとき
    Argv []string // リストで書いたとき
    IsArgv bool   // どちらで書いたか
}

type Transition struct {
    On   string // "success" | "warning"
    Next string // ジョブID。End のときは IsEnd を真にする
    IsEnd bool  // "@end" のとき
}

type RetryPolicy struct {
    ExitCodes    []int32  // 昇順・重複なし・各 1〜255・空でない
    Max          uint32   // 1〜100
    IntervalSecs uint64   // 1〜86400
    Backoff      *Backoff // nil なら固定間隔。multiplier と max_interval は必ず同時に有る/無い
}

type Backoff struct {
    Multiplier      uint32 // 2〜10
    MaxIntervalSecs uint64 // IntervalSecs 以上、86400 以下
}
```

- 成功として扱う終了コード = `SuccessExitCodes` があればそれ、なければ `[0]`。
- ジョブIDから記述順の位置(0 始まり)を引く操作がある(遷移先の検査と、実行時の遷移の解決に使う)。

## 15. `run_id_env` のゆるい読み取り

`watch` と `reset` は、`--run-id` が無いとき、定義全体を検証せず、`pipeline.run_id_env` だけを取り出す。

- 書式の決定(第 2.1 節)から段階 3(第 6 節の上限を含む)までは、定義の読み込みと同じに行う。段階 4・5 は行わない。
- 拡張子が対応していない、ファイルを読めない、大きさの上限を超える、YAML・JSON として読めない(上限を含む)、最上位がマップでない、`pipeline` がマップでない、キーが無い、文字列でない、名前の形(第 9.1 節)に合わない、のどれでも「無し」(実行時は `CONDUCTOR_RUN_ID`)。
- ほかの誤り(`format_version` の誤り、未知のキーなど)は無視する。壊れた入力でも異常終了しない。
- ファイルの大きさの上限(第 3 節)は、この読み取りにも適用する(超えれば「無し」)。
- 例(YAML): `pipeline:\n  name: p\n  run_id_env: X_ID\n` → `X_ID`。`run_id_env: 5`、`"1A"`、`""` → 無し。`pipeline: 3` → 無し。空の入力 → 無し。

## 16. 受理・拒否の例

### 16.1 受理

最小の定義(YAML):

```yaml
format_version: 1

pipeline:
  name: p

job:
  - id: a
    command: c
```

同じ定義(JSON):

```json
{
  "format_version": 1,
  "pipeline": { "name": "p" },
  "job": [
    { "id": "a", "command": "c" }
  ]
}
```

全キーを使った定義(YAML):

```yaml
format_version: 1

pipeline:
  name: nightly
  description: 夜間バッチ
  run_id_env: GITHUB_RUN_ID
  remove_on_complete: true

job:
  - id: extract
    command: ["python", "scripts/extract.py", ""]
    warning_exit_codes: [4]
    success_exit_codes: [0, 5]
    retry:
      exit_codes: [75, 111]
      max: 5
      interval: 10s
      multiplier: 2
      max_interval: 60s
    transitions:
      - on: warning
        next: notify

  - id: load
    command: load
    transitions:
      - on: success
        next: "@end"

  - id: notify
    command: notify --channel ops
```

別の書き方でも同じ定義になる例(フロー形式、引用符つきのキー、コメント):

```yaml
"format_version": 1   # コメントは捨てられる
pipeline: { name: p }
job: [{ id: a, command: c, retry: { exit_codes: [75], max: 3, interval: 5s } }]
```

アンカーとエイリアス、マージキーを使った定義(受理。`b` は、`a` の `command` を取り込み、`id` は自分の値):

```yaml
format_version: 1
pipeline:
  name: p
job:
  - &base
    id: a
    command: c
    success_exit_codes: &ok [0, 2]
  - <<: *base
    id: b
    warning_exit_codes: [3]
  - id: c
    command: d
    success_exit_codes: *ok
```

(`b` は `command: c`、`success_exit_codes: [0, 2]`、`warning_exit_codes: [3]`、`id: b`。)

### 16.2 拒否(Walk の誤り)

行番号は、次の共通のヘッダの続きとしての値。ジョブは 5 行目の `- id: a`、6 行目の `command: c` から。

```yaml
format_version: 1
pipeline:
  name: p
job:
  - id: a
    command: c
```

| 入力(ヘッダの続き) | 結果 |
|------|------|
| 7 行目 `    transitions:`、8 行目 `      - on: success`、9 行目 `        next: zzz` | `unknownTarget` 9 行目 |
| 同、`on: error`、`next: "@end"` | `errorTransition` 8 行目 |
| 同、`on: success`、`next: a`(自分自身) | `backwardOrSelfTarget` 9 行目 |
| 7 行目 `    warning_exit_codes: [2, 3]`、8 行目 `    success_exit_codes: [0, 3]` | `overlappingExitCodes` 7 行目 |
| 7 行目 `    warning_exit_codes: [0]` | `zeroAsWarning` 7 行目 |
| 7 行目 `    warning_exit_codes: [x]` | `typeMismatch` 7 行目 |
| 5 行目を `  - id: 1` に | `typeMismatch` 5 行目 |
| 6 行目の `command: c` が無い | `typeMismatch` 5 行目(ジョブのマップの位置 = 最初のキー `id`) |
| 7 行目 `    warn_exit_codes: [1]` | `unknownKey` 7 行目 |
| 5 行目を `  - id: ""` に / `  - id: "@end"` に | `invalidJobId` 5 行目 |
| 同じ `id` の 2 つ目のジョブ | `duplicateJobId`(2 つ目の `id` の行) |
| 6 行目を `    command: "  "` に | `emptyField` 6 行目 |
| ヘッダのうち、`job:` 以降が無い(`format_version: 1` / `pipeline:` / `  name: p` だけ) | `noJobs` 1 行目 |
| 7 行目 `    retry: {}` | `retryMissingKey` 3 件(`exit_codes`、`max`、`interval` の順)、すべて 7 行目(`{` の位置) |
| 7 行目 `    retry:`(値なし) | `retryNotTable` 7 行目 |

`retry` の複数の誤り(同じヘッダの続き。`retry` は 7 行目から):

```yaml
format_version: 1
pipeline:
  name: p
job:
  - id: a
    command: c
    retry:
      exit_codes: [0]
```

### 16.3 拒否(段階 1〜4)

| 入力 | 種類(行) |
|------|----------|
| パス `conductor.txt` | `unsupportedFormat`(行なし) |
| パス `conductor`(拡張子なし) | `unsupportedFormat`(行なし) |
| 存在しない `x.yaml` | `fileMissing`(行なし) |
| ちょうど 1,048,576 バイトの有効な定義 | 受理(Walk へ) |
| 1,048,577 バイトのファイル | `tooLarge`(行なし) |
| UTF-8 でないバイト列(1 MiB 以下) | `unreadable`(行なし) |
| 空のファイル(YAML) | `versionMissing`(行なし) |
| 空のファイル(JSON) | `syntax` |
| `format_version: 1` だけ(YAML) | `typeMismatch`(`pipeline` が無い、1 行目)と `noJobs`(1 行目)の 2 件 |
| `format_version: 2` | `versionUnsupported`(`この版には対応していません…`、1 行目) |
| `format_version: "1"` | `versionUnsupported`(`整数で書きます…`) |
| `format_version: 1.0` | `versionUnsupported`(`整数で書きます…`) |
| `format_version: 0x01` + 有効な定義 | 受理 |
| `format_version:`(値なし) | `versionUnsupported`(`整数で書きます…`) |
| `format_version: 99999999999999999999` | `versionUnsupported`(`この版には対応していません…`) |
| `- a`(最上位がリスト) | `typeMismatch`(`最上位はマップで書きます`、1 行目) |
| `---`(最上位が null の文書) | 空のマップとして扱い、`versionMissing` |
| `format_version: 1` の後に `---` と別の文書 | `syntax`(`複数の文書は書けません…`) |
| `a: 1`、`a: 2`(重複キー) | `syntax`(`キーが重複しています`、2 つ目の行) |
| `1: x`(整数のキー) | `syntax`(`キーは文字列で書きます`、1 行目) |
| `command: !!str c`(タグ) | `syntax`(`タグは使えません`、その行) |
| `a: &r [*r]`(再帰) | `syntax`(`アンカーが自分自身を含んでいます`、1 行目) |
| `a: [1, 2`(閉じていない) | `syntax`(`YAML の文法に誤りがあります`。行はライブラリによる) |
| `<<: 5`(最上位のマージキーの値が整数) | `syntax`(`マージキーの値がマップではありません`、1 行目) |
| JSON: `{"format_version": 1,}` | `syntax`(`JSON の文法に誤りがあります`、1 行目) |
| JSON: `// c` で始まる | `syntax` |
| JSON: `{"a": 1, "a": 2}` | `syntax`(`キーが重複しています`、2 つ目の `"a"` の行) |
| JSON: `[1]`(最上位が配列) | `typeMismatch`(`最上位はマップで書きます`) |
| JSON: `"format_version": 1.0` を持つオブジェクト | `versionUnsupported`(整数でない) |
| JSON: `"format_version": 1e0` | `versionUnsupported`(整数でない) |
| 要素数が 100,001 になる入力 | `tooLarge`(`要素数が上限(100000)を超えています`) |
| 入れ子が 33 段 | `syntax`(`入れ子が深すぎます(上限は 32 段)`、33 段目の行) |
| 入れ子が 32 段 | 受理(後続の段階へ) |

JSON の例(Walk の誤り。5 行目の `1.0` が整数でない):

→ `typeMismatch` 5 行目(要素 `1.0`)。
