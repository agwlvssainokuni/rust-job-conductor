# 09. 変換器(`.psd1` と JSON の相互変換)

この文書は、`conductor convert <ファイル> --to <psd1|json>` の中身である変換器の振る舞いを定める。この文書だけで、PowerShell でゼロから、同じ受理・拒否・出力・エラーを返す変換器を実装できることを目標とする。

- 変換器は、定義ファイルの**検証をしない**。変換した結果が `conductor` の定義([03. 定義ファイルの書式と検証](03-definition-format.md))として正しいかは見ない(任意の `.psd1` のハッシュテーブル / JSON のオブジェクトを変換する)。
- 副作用はない: ファイルへの書き込み、環境変数、プロセス、ネットワークに触れない(読むのは入力ファイル 1 つだけ)。変換結果は、文字列として返す(標準出力への書き出しは、[04. CLI](04-cli.md) の側の仕事)。
- 入力の値を、エラーの文に含めない(キー名だけを、エスケープと切り詰めをして、場所として示すことがある)。
- 確認できなかった点は「未確認」と書く。公式ドキュメントや公開されたソースで確かめた点は「確認(出典: …)」と書く。この環境には PowerShell(`pwsh`)も .NET SDK も無く、実機では動かしていない。したがって「確認」は、**文書・ソースの記述の確認**であり、動作の確認ではない。実装時に最初に行う試験を第 12 節に一覧にする([03 第 16 節](03-definition-format.md)の試験も同じ)。
- 「必須」の挙動は、利用者から見える結果(受理/拒否、変換結果の文字列、エラーの種類・文言・行・場所)で、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、変換結果を読み戻した木が変わらない範囲で、実装が選んでよい。
- コマンドの引数・終了コードの全体は [04. CLI](04-cli.md) と [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方と標準出力の文字コードは [08. 出力と多言語対応](08-output-and-i18n.md) に従う。
- `.psd1` と JSON の**読み取り**(文法、許可する構文、数の字句、キーの重複、上限、木の型)は、[03](03-definition-format.md)の第 4〜6 節と**同じ**で、実装も共有する(`src/Conductor/Private/Definition/` と `Private/Json/` の木の読み取りを、`src/Conductor/Private/Convert/` が呼ぶ)。この文書は、読み取りの上の差分(取り込み、最上位、拒否する数)と、書き出しを定める。
- 変換の本体では、`ConvertTo-Json`、`ConvertFrom-Json`、`Export-Clixml`、`ConvertTo-Expression` に類するコマンドレットと、`System.Text.Json` の書き出し(`Utf8JsonWriter`、`JsonSerializer`)を**使わない**(出力の文字列を、この規定に一致させるため。[03 第 5 節](03-definition-format.md)の比較表と、本文書の第 6.1、7 節)。
- 画面への出力は行わない。戻り値は `return` で明示し、`[System.Text.StringBuilder]::Append` の戻り値(`StringBuilder` 自身)や `HashSet[string]::Add` の戻り値(`bool`)など、出力を返すメソッドの結果は、`[void]` か `$null =` で捨てる(関数の戻り値に混ざる事故を避けるため。PowerShell は、文の結果をすべて出力に流す)。

## 1. 入口と入出力

型と関数の骨格(例。`[pscustomobject]` で表す。`class` は使わない。[03 第 6.1 節](03-definition-format.md)):

```powershell
# 結果(成功)
[pscustomobject]@{ Ok = $true;  Text = [string]'…' }
# 結果(失敗)
[pscustomobject]@{ Ok = $false; Error = $convertError }   # 第 10 節

function Convert-ConductorFile {
    [CmdletBinding()]
    [OutputType([pscustomobject])]
    param(
        [Parameter(Mandatory)][string] $Path,
        [Parameter(Mandatory)][ValidateSet('psd1', 'json')][string] $To
    )
    # パスのファイルを読み、$To の形式に変換した文字列を返す
}

function Convert-ConductorText {
    [CmdletBinding()]
    [OutputType([pscustomobject])]
    param(
        [Parameter(Mandatory)][string] $Text,
        [Parameter(Mandatory)][ValidateSet('psd1', 'json')][string] $To,
        [Parameter(Mandatory)][string] $FileLabel
    )
    # ファイルに触れない。$FileLabel はエラーの表示に使う名前
}
```

| 入口 | 引数 | 戻り値 |
|------|------|--------|
| `Convert-ConductorFile` | 入力ファイルのパス、変換後の形式 | 成功: 変換結果の文字列、失敗: 変換の誤り(第 10 節) |
| `Convert-ConductorText` | 文字列(復号済み)、変換後の形式、表示用のファイル名 | 同上(ファイルに触れない) |

- 変換後の形式は `psd1` または `json`。
- **入力の形式は、変換後の形式の反対**とみなす(`--to psd1` なら入力は JSON、`--to json` なら入力は `.psd1`)。**拡張子は見ない**。`.psd1` の名前のファイルでも、`--to psd1` なら JSON として読む(`.psd1` を JSON として読めば、JSON の文法の誤りになる)。
- 変換結果は、全部作ってから 1 つの文字列として返す。失敗のときは、出力は無い。
- 誤りは、例外ではなく戻り値で返す。例外は、実装の不具合にだけ使う。
- `conductor convert` は、成功したら結果を標準出力に 1 回で書く(`Send-ConductorOutput -Text $text`。08 章 10.1 節。`Write-ConductorStream` が、`[Console]::OpenStandardOutput()` のストリームを包んだ BOM なし UTF-8 の `StreamWriter`(LF、`AutoFlush`)に 1 回の `Write` で書く。戻り値の `[bool]` の偽が書き込みの失敗)。`[Console]::Out` と `WriteLine` は使わない。**変換結果の改行は LF だけであり、書き出しで CRLF に変わってはならない**(自前の `StreamWriter` は `NewLine = "`n"` で、文字列の `\n` を変えない。Windows の実機では未確認。試験 T-C06)。標準出力の文字コード(UTF-8、BOM なし)は [08](08-output-and-i18n.md) に従う。`Write-Host`、`Write-Output`、`Out-File`、`Set-Content` は使わない。失敗したら標準出力は空で、標準エラーに原因を出し、終了コード 67 で終わる([04](04-cli.md)・[10](10-errors-and-exit-codes.md))。

## 2. 処理の流れと失敗の順序

```
Intake → 読み取り(Parse) → 展開と写し取り(Resolve) → 最上位の確認(RootCheck) → 書き出し(Write)
```

失敗は、次の順で最初に見つかったものを 1 件だけ返す(以降は実行しない)。

| 順 | 段階 | 失敗 |
|----|------|------|
| 1〜2 | Intake: 開く(存在しない → `fileMissing`、権限など → `unreadable`) | 第 3 節 |
| 3 | Intake: 通常のファイルでない → `unreadable`、大きさが 1 MiB を超える → `tooLarge` | 第 3 節 |
| 4 | Intake: 上限 + 1 バイトまでの読み取りと UTF-8 の確認 → `unreadable` | 第 3 節 |
| 5 | Parse: 文法の誤り → `syntax`。JSON は、先頭から読んで最初に見つかった文法の誤り・重複キー。`.psd1` は、前処理とパーサー(`ParseError`)で、全文を確かめ終えてからの文法の誤り | 第 4 節 |
| 6 | Resolve(入力に現れる順で、最初に見つかったもの): 許可しない構文・非文字列キー・重複キー(いずれも `syntax`)、要素数・文字の大きさの上限(`tooLarge`)、入れ子の深さの上限(`syntax`) | 第 4 節 |
| 7 | RootCheck: 最上位がマップでない → `rootNotMap` | 第 4.3 節 |
| 8 | Resolve で記録した、表せない値のうち、入力に現れる順で最初のもの → `unrepresentable` | 第 5 節 |

- 順 6 の失敗は、順 8 より優先する(先に表せない数があっても、上限超過が返る)。
- 順 7 は順 6 より後。最上位がマップでない入力に順 6 の失敗が含まれるときは、順 6 の失敗が先に返る。実装は、順 6 の走査を終えてから最上位を確認する。
- 順 3 は順 4 より先: 1 MiB を超え、かつ UTF-8 でない入力は `tooLarge`。順 3 は順 5 より先: 1 MiB を超える入力は、中身が壊れていても `tooLarge`。
- 順 5(文法)は、順 6(許可しない構文など)より先。たとえば、先頭の組が `$x` を含み(順 6 の失敗)、後ろに閉じていない `@(` がある(順 5 の失敗)入力は、後ろの文法の誤りを `syntax`(理由 ``.psd1 の文法に誤りがあります``)として返す。

## 3. 取り込み(Intake)

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルを開こうとして「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | ファイルを開けない。権限がない | `unreadable` | `読み取りの権限がありません` |
| 2' | 同、ディレクトリを開こうとした(通常のファイルでない) | `unreadable` | `通常のファイルではありません` |
| 2'' | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 3 | 開いたファイルの情報(種別・大きさ)が取れない | `unreadable` | 権限なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 3' | 通常のファイルでない(ディレクトリ、シーク不能なものなど) | `unreadable` | `通常のファイルではありません` |
| 4 | 大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `入力が上限(1 MiB)を超えています` |
| 5 | 読み取り結果が上限を超える(順 4 のあとに大きくなった場合) | `tooLarge` | 同上 |
| 6 | 読み取りの途中の失敗 | `unreadable` | 権限なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 7 | UTF-8 として読めない | `unreadable` | `UTF-8 として読めません` |

実装(PowerShell + .NET)の対応:

- 順 1〜2'': `[System.IO.FileStream]::new($path, [System.IO.FileMode]::Open, [System.IO.FileAccess]::Read, [System.IO.FileShare]::ReadWrite)` を `try` で呼ぶ。`FileNotFoundException`・`DirectoryNotFoundException` なら順 1、`UnauthorizedAccessException` なら順 2(ディレクトリを開こうとした場合、.NET が `UnauthorizedAccessException` を投げる OS があるので、ディレクトリかどうかは、先に `[System.IO.Directory]::Exists($path)` で確かめ、真なら順 2' にする)、それ以外(`IOException`、`ArgumentException`、`NotSupportedException`、`PathTooLongException`、`SecurityException`。パスに NUL を含むときを含む)は順 2''。ディレクトリの検査は、`FileStream` を開く前に行う(`Directory.Exists` は例外を投げない)。
- 順 3・3'・4: 開いた `FileStream` の `CanSeek` が偽(名前つきパイプなど)なら順 3'。`Length` が 1,048,576 を超えれば順 4。`Length` の取得の失敗は順 3。名前つきパイプ(FIFO)を `FileStream` で開くとき、書き込む側が現れるまで**ブロックして戻らない**可能性は、未確認(試験 T-C01)。ブロックする場合は、パスの種別を、開く前に調べる(例: `[System.IO.File]::GetAttributes` の結果、または .NET 7 以降の `[System.IO.File]::GetUnixFileMode`(これは権限ビットで、種別は返さない。確認していない))手段を、この仕様の変更として追加する。
- 順 5・6: `FileStream.Read(byte[], int, int)` で、**上限 + 1 バイトまで**を読む(戻り値 0 か、合計が上限 + 1 バイトに達するまで繰り返す。1 回の `Read` が、要求より少なく返すことがあるので、繰り返す)。`try`/`finally` で `Dispose()` する。**`[System.IO.File]::ReadAllBytes`、`ReadAllText`、`Get-Content` は使わない**(巨大なファイルを読み込まない。第 3 節の理由)。
- 順 7: `[System.Text.UTF8Encoding]::new($false, $true)` の `GetString`([03 第 3 節](03-definition-format.md)と同じ。厳格な復号で、`DecoderFallbackException` なら順 7。引数なしの `[System.Text.Encoding]::UTF8` は使わない)。

- 先にファイルを開き、**開いたもの**の情報で大きさを調べる(調べたあとにファイルが差し替わっても、読み取りの結果と食い違わない)。
- **ちょうど 1 MiB は受理**し、1 バイトでも超えれば `tooLarge`。
- 権限のないファイルは、大きさにかかわらず `unreadable`(開く操作が先に失敗する)。ただし、権限の確認を迂回する利用者(root など)では、この結果にならない。
- 行番号は付かない。
- 空のファイル(0 バイト)は、空の入力として次へ進む(`.psd1`・JSON とも `syntax`。[03 第 4.8、5 節](03-definition-format.md))。
- OS による権限・種別の判定の細部(Windows での `HResult` の値など)は、実装に任せてよい(未確認)。必須なのは、上の表の条件の順序と、各理由の文言である。
- 定義ファイルの取り込み([03 第 3 節](03-definition-format.md))とは、上限超過と UTF-8 の理由の文言が違う(ここは `入力が上限(1 MiB)を超えています`、`UTF-8 として読めません`)。また、定義ファイルと違い、**拡張子の確認はしない**。
- `Get-Content`、`Test-Path`、`Resolve-Path` を使わない([03 第 3 節](03-definition-format.md))。

## 4. 読み取り

### 4.1 受理する文法

- `--to psd1`(入力は JSON)のとき: JSON は、[03 第 5 節](03-definition-format.md)の形式(RFC 8259 の厳格な形式。コメント・末尾カンマ・重複キー・対にならないサロゲートの拒否を含む)で、[03 第 5.3 節](03-definition-format.md)の自前の字句・構文解析で読む。`ConvertFrom-Json` は使わない。
- `--to json`(入力は `.psd1`)のとき: `.psd1` は、[03 第 4 節](03-definition-format.md)の部分集合を、そこで定めた手順(前処理、`ParseInput`、AST のノード型の許可リスト、`Extent.Text` による数の字句、キーの重複(ASCII の大文字小文字を畳む))で読む。要点: ハッシュテーブル `@{}`、配列 `@()`・カンマ区切り・単項のカンマ、文字列(単一引用符、展開のない二重引用符、here-string)、整数(10 進・`0x`・`0b`。接尾辞なし)、浮動小数、`$true`/`$false`/`$null`、コメント(捨てる)。**拒否**: 変数、コマンド、式、演算子、スクリプトブロック、`$()`、キャスト、`[type]`、数の接尾辞(`kb` など)、複数の文、`#requires`・`using`・`param`、単独の入れ子の `@(@(...))`。
- 読み取りの誤りの種類・理由・行は、[03 第 10.3 節](03-definition-format.md)の `syntax`/`tooLarge` の理由の表と同じ(``.psd1 の文法に誤りがあります``、``.psd1 で使えない書き方です``、``JSON の文法に誤りがあります``、``キーが重複しています``、``キーは文字列で書きます``、``入れ子が深すぎます(上限は 32 段)``、``要素数が上限(100000)を超えています``、``文字の大きさが上限(16 MiB)を超えています``)。行の出し方も、[03 第 11 節](03-definition-format.md)と同じ。
- 入力の先頭の BOM(U+FEFF)は受理される(無視する)。LF・CRLF の両方を受理する(`.psd1` は、前処理で LF にそろえる)。CR だけの改行は、`.psd1` では `syntax`([03 第 4.8 節](03-definition-format.md))、JSON では空白として受理する(JSON の空白は LF・CR・スペース・タブ)。
- JSON の対にならないサロゲートのエスケープ(`"\ud800"`)は、`syntax`(``JSON の文法に誤りがあります``。[03 第 5 節](03-definition-format.md))。

### 4.2 上限(03 と同じ)

| 上限 | 値 | 超過したときの失敗 |
|------|----|--------------------|
| 入力の大きさ | 1 MiB | `tooLarge`(Intake) |
| 要素数 | 100,000 | `tooLarge` |
| 文字の大きさ | 16 MiB | `tooLarge` |
| 入れ子の深さ | **根のマップを数えず 32 段まで** | `syntax`(33 段目) |

数え方は [03 第 6.3 節](03-definition-format.md)の規定のとおり(要素数にはキーも数える、文字の大きさは値のバイト数など)。JSON の入力にも `.psd1` の入力にも、同じ上限があり、同じ境界になる(例: `{"a":[0,0,...]}` で、0 を n 個並べるとき、n = 99,997 まで受理、99,998 で失敗。`.psd1` の `@{ a = @(0, 0, ...) }` も同じ境界)。

数千〜数十万段の入れ子の入力は、いずれも、プロセスを落とさず、`syntax` で終わること(必須。[03 第 6.4 節](03-definition-format.md)。`.psd1` は、パーサーに渡す前の事前走査で守る)。

### 4.3 最上位の確認(RootCheck)

| 入力 | 結果 |
|------|------|
| 最上位がマップ(`.psd1` の `@{ a = 1 }`、JSON の `{}` を含む) | 次へ |
| 最上位が、マップでない(`.psd1` の配列・文字列・数・`$true`・`$null`、JSON の配列・数・文字列・`null`) | `rootNotMap`、理由 ``最上位がマップではありません``、行は最上位のノードの位置の行 |

- 定義ファイルと違い、**空のマップとして扱う入力はない**。`.psd1` も JSON も、空の入力(0 バイト、空白とコメントだけ)は、`rootNotMap` ではなく `syntax`(値が 1 つ必要)。
- 空のマップ(`@{}`、`{}`)は受理され、変換できる(第 7、9 節)。
- 定義の読み込み([03 第 6.7 節](03-definition-format.md))は、マップでない最上位を `typeMismatch` にする。変換器は `rootNotMap` を返す。同じ読み取りの関数(`Read-ConductorTree`)を使い、段階 3 で最上位の種別を、見分けられる形で受け取る。

### 4.4 内部表現

読み取りと展開の結果は、[03 第 6.1 節](03-definition-format.md)の木にする。

| 種類(`Kind`) | 内容 |
|--------------|------|
| `null` | 値なし |
| `bool` | `[bool]` |
| `int` | `[long]`(64 ビット符号つき整数の範囲) |
| `hugeInt` | 範囲外の整数(値は持たない。第 5 節で拒否) |
| `float` | `[double]`(IEEE 754 binary64)と、`Overflow` の印 |
| `string` | `[string]`(対にならないサロゲートを含まない) |
| `seq` | `[System.Collections.Generic.List[object]]` |
| `map` | エントリ(文字列のキー, 木)の `List[object]`。**キーは重複しない(`.psd1` は ASCII の大文字小文字を畳んで重複しない)。記述順を保つ** |

- 変換器は、`hugeInt` と、`Overflow` の印のある浮動小数を、第 5 節のとおり記録して失敗させる。
- **内部表現の等価**(往復の確認に使う): 型が違えば不等(`'1'` と 1、1 と 1.0、`$true` と `'true'`、null と `'null'`)。整数は、`[long]` の値が等しいこと。浮動小数は、ビット表現が同じなら等しい(`[System.BitConverter]::DoubleToInt64Bits($a) -eq [System.BitConverter]::DoubleToInt64Bits($b)`。NaN は木に現れない。**`0.0` と `-0.0` は異なる**。PowerShell の `-eq` は、`0.0 -eq -0.0` が真なので、使わない)。マップは、**キーの順序を無視**して比べる(キーの比較は完全一致)。リストは順序を含めて比べる。比較は、`Kind` の文字列を `-ceq` で比べてから、値を比べる(`-eq` は、型を右辺に合わせて変換するので、`1 -eq $true` などが真になりうる。使わない。[03 第 1.1 節](03-definition-format.md))。

## 5. 表せない値(`unrepresentable`)

展開の途中で見つけた「相手の形式で表せない値」のうち、**入力に現れる順で最初の 1 つ**だけを記録し、走査の終了後に返す(上限超過・非文字列キーなど、第 2 節の順 6 の失敗は、これより優先する)。

| 値 | 理由(日本語の原文) | 対象の入力 | 例 |
|----|----------------------|------------|-----|
| 範囲外の整数(64 ビット符号つき整数に収まらない。種別 `hugeInt`) | `数値が表せる範囲を超えています` | JSON、`.psd1` | `{"a": 9223372036854775808}`、`@{ a = 9223372036854775808 }` |
| 範囲を超える浮動小数(`Overflow` の印) | `数値が表せる範囲を超えています` | JSON、`.psd1` | `{"a": 1e400}`、`@{ a = 1e999 }`(後者は、パーサーが数として読む場合。読まなければ `syntax`。[03 第 4.3.1 節](03-definition-format.md)) |
| 同じオブジェクトの中に、ASCII の英字の大文字小文字だけが違うキーがある | `.psd1 では、大文字小文字だけが違うキーを同時に書けません` | JSON(`--to psd1` のときだけ) | `{"a": 1, "A": 2}` |

- `.psd1` から JSON への変換で、表せない値は、上の 2 行(範囲外の数)だけである。`.psd1` に NaN・無限大を書く構文はなく、`.psd1` のキーは重複しない(ASCII の大文字小文字を畳んで)ので、JSON のキーの重複も起きない。`$null`、真偽値、文字列(すべてのコードポイント)、リスト、マップは、すべて JSON で表せる。
- **JSON から `.psd1` への変換で、表せない値は、上の 3 行だけである**。JSON の値は、(範囲内の)整数、有限の浮動小数、文字列(対にならないサロゲートを含まない、すべての文字)、真偽値、null、リスト(空を含む。入れ子を含む。1 要素の入れ子を含む)、マップ(空を含む)で、すべて `.psd1` に書ける(第 8 節で、書き方を定める)。キーの文字も、すべて書ける(引用符つきのキー。第 8.3 節)。**キーの大文字小文字だけが違うものだけが書けない**(`.psd1` のハッシュテーブルは、キーの大文字小文字を区別しない(未確認: 公式ドキュメントを取得して確かめていない)ので、書き出した `.psd1` を、他の道具が読むと、キーが衝突するため。また、この仕様の読み取りも、重複として拒否する([03 第 4.5 節](03-definition-format.md)))。
- キーの大文字小文字の検査は、各オブジェクトで、キーを訪れる順に、これまでのキー(A〜Z を a〜z にした文字列を、`[System.Collections.Generic.HashSet[string]]`(`Ordinal`)に入れたもの)と比べ、2 つ目に現れたキーの場所で記録する。判定は ASCII の英字だけ(非 ASCII の大文字小文字は、区別して別のキーと見なす)。
- 失敗の表示: `kind` は `unrepresentable`、行なし。**場所(`key_path`)**がつく。
- **場所の書式**: キーを `.` でつなぐ。リストの要素は `[添字]`(0 始まり。直前のキーに続けて、`.` なしで書く)。リストが最上位に来ることはない(最上位はマップ)。キー名は、制御文字・書式文字をエスケープし(`\n`、`\r`、`\t`、その他は `` \u{16進小文字} ``。対象の文字と切り詰めは [03 第 10.2 節](03-definition-format.md)と同じ)、64 文字(エスケープ後の文字数。コードポイントで数える)を超えると、64 文字で切って `…` を付ける。例: `job[1].note`、`a.b`、`a[2]`。キーの大文字小文字の衝突の場所は、2 つ目のキー自身(例: `{"a":1,"A":2}` は `A`、`{"x":{"k":1,"K":2}}` は `x.K`)。
  - 実装の指針: 経路は、走査の明示のスタックから、**最初の 1 件を記録するときだけ**文字列にする(すべてのノードで作らない)。
- 範囲外の数は、変換後の形式が `.psd1` でも JSON でも拒否する(内部表現が 64 ビットのため)。
- 入力に現れる順の例: `{"a": 1, "job": [{"id": "x"}, {"id": "y", "n": 1e999}, {"z": 9223372036854775808}], "later": 1e999}`(`--to psd1`)は、最初の `job[1].n` を返す。

読み取り(Resolve)の関数は、変換器のために、記録の機能を持つ(例):

```powershell
# 表せない値(最初の 1 件)
[pscustomobject]@{ Reason = [string]'数値が表せる範囲を超えています'; KeyPath = [string]'job[1].n' }
```

[03 第 12.2 節](03-definition-format.md)の `Read-ConductorTree -ConvertTo psd1|json` が、変換器のとき(`-ConvertTo` を指定したとき)に、最初の表せない値を `FirstUnrepresentable` に入れて返す。定義の読み込みでは `-ConvertTo` を指定せず、記録しない。キーの大文字小文字の衝突の検査は、`-ConvertTo psd1` のときだけ行う。

## 6. 書き出し(共通)

- 書き出しの前に、最上位は(必ず)マップになっている(第 4.3 節)。
- **各マップのキーは、入力の記述順のまま出力する**(キーをソートしない)。リストの順序も保たれる。コメントは捨てられる。
- 変換結果の最後は改行(LF)で終わる。改行は LF だけ。
- 木の深さは、読み取りの上限により 33 以下(根を含む)だが、**書き出しも、関数の再帰を使わない明示のスタックで書く**(PowerShell の関数の呼び出しの深さの上限は、版で変わる(未確認)。深さ 33 の再帰は、通常は問題にならないと推測されるが、依存しない)。
- 出力は、`[System.Text.StringBuilder]` に溜めて、最後に `ToString()` で 1 つの文字列にする(`+=` の繰り返しは、文字列を毎回作り直すので使わない)。`Append` の戻り値は `[void]` で捨てる。数・文字の書式化は、すべて `[System.Globalization.CultureInfo]::InvariantCulture` で行う(文化に依存する `ToString()` を使わない)。
- 文字列は、`[char]` ごとに走査する。上位サロゲート(U+D800〜U+DBFF)と下位サロゲート(U+DC00〜U+DFFF)の対は、1 つのコードポイントとして、そのまま(エスケープ要の文字でない限り、エスケープせずに)書く。単独のサロゲートは木に存在しない(第 6.4 節)。

### 6.1 浮動小数の書き方(`.psd1` と JSON で共通)

内部表現の浮動小数を、**必ず浮動小数と読み戻される形**で書く。

- NaN、±∞: 木に現れない(JSON にも `.psd1` にも、これらを書く構文がなく、入力にできないため。`overflow` の印のある浮動小数は、第 5 節で先に拒否される)。万一、現れたら、実装の不具合として扱う(想定外の内部失敗)。
- それ以外は、往復で同じ値になる**最短の桁数**の 10 進で書く。確認(出典: .NET の標準の数値書式の公式ドキュメント): `Double` の `ToString()`(書式なし。"G")は、.NET Core 3.0 以降、往復できる最小の桁数の文字列を返す(「Smallest round-trippable number of digits to represent the number。.NET Framework では G15」)。"G" は、指数が -5 より大きく、桁数(精度)より小さければ固定小数点、そうでなければ指数形で書き、指数は `E+XX`(最低 2 桁)で書く。同じドキュメントは、.NET Framework と 3.0 より前の .NET Core の "R" が、往復に失敗することがある、と書く。したがって、**`$d.ToString([System.Globalization.CultureInfo]::InvariantCulture)`(書式なし)で得た文字列から、桁と指数を取り出し**、次の規則で、自前で組み立てる(出力の書式を、.NET の指数形・固定小数点の切り替えに依存させないため)。
  1. 取り出し: 文字列を、符号(先頭の `-`)、仮数部、指数部(`E` または `e` の後ろ。符号つき整数。無ければ 0)に分ける。仮数部から `.` を除いて数字の列 `D0` を得て、小数点の位置から、最初の非ゼロの数字の 10 進の指数 `e`(`1.5e-7` なら -7、`123.4` なら 2)を求める。`D0` の先頭と末尾の 0 を除いた数字の列 `D`(1 桁以上)を得る。値が 0(すべて 0)のときは、`0.0`(符号が負なら `-0.0`)で終わる。
  2. 絶対値が 1e16 以上、または 1e-4 未満(0 を除く)、つまり `e >= 16` または `e < -4` のときは**指数形**: `D` の 1 桁目、2 桁以上なら `.` と残りの桁、続けて `e` と指数 `e`(`-` は付ける。`+` は付けない。先頭の 0 は付けない)。例: `1e16`、`1e21`、`1e-5`、`1.5e-7`、`1.2345678901234568e16`、`5e-324`、`1.7976931348623157e308`。
  3. それ以外は、10 進の小数表記で、整数値でも必ず小数部を付ける。`e >= 0` のとき: 整数部は `D` の先頭 `e + 1` 桁(足りなければ 0 を補う)、小数部は残りの桁(無ければ `0`)。`e < 0` のとき: `0.` の後ろに、`-e - 1` 個の 0、続けて `D`。例: `1.0`、`100.0`、`1000000000000000.0`(1e15)、`0.0001`、`0.1`、`123.456`。
  4. 負の値は、先頭に `-` を付ける。
- 確認した例の期待値(実装時の単体テストに使う。実機では未確認): `1.0` → `1.0`、`100.0` → `100.0`、`1e15` → `1000000000000000.0`、`1e16` → `1e16`、`1e21` → `1e21`、`1e-5` → `1e-5`、`0.0001` → `0.0001`、`0.00009999` → `9.999e-5`、`0.1` → `0.1`、`-0.0` → `-0.0`、`9999999999999998.0` → `9999999999999998.0`、`0.30000000000000004` → `0.30000000000000004`、`12345678901234567.0`(入力。値は 12345678901234568)→ `1.2345678901234568e16`、`5e-324` → `5e-324`、`1.7976931348623157e308` → `1.7976931348623157e308`。
- **書き出しの規則が、.NET の返す桁の最短性に依存すること**(.NET Core 3.0 以降で最短)は、実機で確かめる(試験 T-C02: ランダムな浮動小数で、規則で書いた文字列を `[double]::Parse` で読み戻して、ビット表現が一致すること。`ToString()` の結果が、固定小数点でも指数形でも、同じ出力になること)。
- 指数形(`1e16`)は、JSON でも `.psd1` でも、読み戻すと浮動小数になる(JSON は指数部を持つ数。`.psd1` は、`Extent.Text` が指数部を持つ数の字句([03 第 4.3.1 節](03-definition-format.md)))。パーサーが、`1e16` を `double` の定数として読むこと(確認(出典: tokenizer のソース): `e`/`E` の指数部で、実数(real)として扱う)。
- 浮動小数の書き方で、PowerShell の `[double]::ToString("R")` と `"G17"` は使わない(最短でない、または公式ドキュメントが推奨する対象が異なるため。上の引用)。

### 6.2 整数・真偽値・null

- 整数: 10 進(64 ビット符号つき整数。`-9223372036854775808` を含む)。`$value.ToString([System.Globalization.CultureInfo]::InvariantCulture)`(`[long]`)で書く。桁は 19 桁以下。**PowerShell の演算で、整数が `double` に昇格しない**ように、値は `[long]` の型のまま扱う(`[long]` どうしの加減乗算は、オーバーフローで例外か `double` への昇格かが規定として確認できていない(未確認)。この文書の処理は、整数の算術を行わない)。
- 真偽値: JSON は `true` / `false`、`.psd1` は `$true` / `$false`(**ノードの種別から**選ぶ。`[bool]` の `ToString()` は `True` / `False` で、使えない)。
- null: JSON は `null`、`.psd1` は `$null`。

### 6.3 整数の精度(決定)

| 場面 | 規定 |
|------|------|
| 入力の整数の字句(`.psd1` の 10 進・`0x`・`0b`、JSON の整数) | 数字の列から `[System.Numerics.BigInteger]` を経由して値を得る([03 第 4.3.1、5.1 節](03-definition-format.md))。範囲を超えるものは、桁数で `hugeInt` にする。`[long]` への変換は、範囲を検査した後にだけ行う |
| 木 | 整数は `Kind = 'int'`(`[long]`)。浮動小数は `Kind = 'float'`(`[double]`)。**型が違えば別の値**(JSON の `1` と `1.0`、`.psd1` の `1` と `1.0` は、変換でも区別する)。真偽値は `Kind = 'bool'` |
| 出力 | 整数は第 6.2 節。浮動小数は第 6.1 節 |
| 浮動小数の書き方の整数値 | 値が整数でも、書き方に小数部か指数部があれば浮動小数。2^53 を超える値は、`[double]` の最も近い値になり、桁が変わりうる(`9007199254740993.0` → 値 9007199254740992.0 → 出力 `9007199254740992.0`。`12345678901234567.0` → `1.2345678901234568e16`)。これは浮動小数の性質であり、エラーにしない |
| 比較・検査 | 範囲の比較は、`[long]` か `[System.Numerics.BigInteger]` どうしで行う。`[double]` に変換してから比べない |

- 例: JSON `{"a": 9007199254740993}`(2^53 + 1)→ `.psd1` `a = 9007199254740993`(値が保たれる。`[double]` を経由すると 9007199254740992.0 になって誤る)。`.psd1` `a = 9223372036854775807` → JSON `"a": 9223372036854775807`。`.psd1` `a = -9223372036854775808` → JSON でも同じ。`{"a": 9223372036854775808}` と `a = 9223372036854775808` は、`unrepresentable`(範囲外の整数)。
- **`.psd1` の `-9223372036854775808` の読み取り**(最小値)は、パーサーが `-` と `9223372036854775808` を、単項のマイナスと、`double` 化された 9223372036854775808 として返す可能性がある(確認(出典: tokenizer のソース): 接尾辞なしの 10 進整数は、int、long、decimal、double の順に試す。`-` が数の一部として読まれるかは、文脈による(`AllowSignedNumbers`))。この仕様は `Extent.Text` を字句として解析するので、結果は `[long]::MinValue` で、パーサーの型の選択に依存しない。ただし、書き出した `.psd1` を、他の道具(`Import-PowerShellDataFile` など)が、`double` として読む可能性は、未確認(試験 T-C03)。

### 6.4 文字列と対にならないサロゲート(決定)

- .NET の `[string]` は、対にならないサロゲート(U+D800〜U+DFFF)を持てる(`[char]0xD800` は作れる)。**変換器の木の文字列は、対にならないサロゲートを含まない**。入力が UTF-8 のバイト列から厳格に復号されること([03 第 3 節](03-definition-format.md))、JSON の `\ud800` のエスケープと、`.psd1` の `` `u{D800} `` が拒否されること([03 第 4.4、5 節](03-definition-format.md))、前半と後半のエスケープが続けて書かれた JSON の `😀` が、2 つの `[char]`(UTF-16 の対。U+1F600)になること、によって保たれる。したがって、書き出しの文字列は、常に UTF-8 に符号化できる。
- 書き出しは、`[string]` を `[char]` ごとに走査し、上位サロゲートの直後の下位サロゲートを、対として、そのまま書く(エスケープしない。エスケープの要る文字は、第 7、8 節の表のとおり、BMP の文字と、対でないサロゲートだけ)。
- 変換結果の文字列を標準出力へ書く符号化(UTF-8)は [08](08-output-and-i18n.md) に従う。変換結果には単独のサロゲートが無いので、BOM なしの UTF-8 の符号化は失敗しない。変換の誤りの表示の `<file>` には、OS から得た文字列に不正なバイトが入りうる(未確認。[03 第 10.2 節](03-definition-format.md))ので、第 10 節のとおり、表示の前にエスケープする。

## 7. JSON の書き出し(`--to json`)

**すべて必須**(出力の文字列が一致する)。

**レイアウト**(インデントは半角スペース 2 個。タブは使わない。行末に空白を残さない):

- 空のマップ: `{}`。空のリスト: `[]`。
- 空でないマップ: `{` + 改行、各エントリを `<インデント + 2>"<キー>": <値>` で、エントリの間を `,` + 改行で区切り、最後のエントリの後に改行、`<インデント>}`。キーと値の間は `": `(コロンの後に半角スペース 1 個)。
- 空でないリスト: `[` + 改行、各要素を `<インデント + 2><値>` で、`,` + 改行で区切り、最後の後に改行、`<インデント>]`。**要素は 1 行に 1 つ**(短い配列も 1 行にまとめない)。
- 最上位の値の後ろに LF を 1 個付ける。

**文字列(値もキーも同じ)**: `"` で囲み、次のとおりエスケープする。

| 文字 | 出力 |
|------|------|
| `"` | `\"` |
| `\` | `\\` |
| U+000A | `\n` |
| U+000D | `\r` |
| U+0009 | `\t` |
| U+0008 | `\b` |
| U+000C | `\f` |
| そのほかの U+0000〜U+001F、U+007F〜U+009F、U+2028、U+2029、U+FEFF、U+FFFE、U+FFFF | `\u` + 16 進の**小文字** 4 桁(例: `\u001b`、`\u007f`、` `)。16 進は `([int]$ch).ToString('x4', [System.Globalization.CultureInfo]::InvariantCulture)` |
| それ以外(`/`、`<`、`>`、`&`、非 ASCII、絵文字(サロゲートの対)を含む) | そのまま書く(エスケープしない) |

- **`ConvertTo-Json` は使えない**(確認(出典: ConvertTo-Json の公式ドキュメント): 既定のエスケープは制御文字だけ(`-EscapeHandling Default`)で、`EscapeNonAscii` は非 ASCII をすべてエスケープし、`EscapeHtml` は `<`、`>`、`&`、`'`、`"` をエスケープする。どれも、この規定(U+007F〜U+009F、U+2028、U+2029、U+FEFF、U+FFFE、U+FFFF のエスケープ、`/` などを書いたまま)と一致する保証がない。浮動小数の書式、インデント、`-Depth` の既定が 2 であることも、規定と違う)。自前で書く(必須)。数・真偽値・null は、第 6 節のとおり。

JSON の出力例(入力 `.psd1` は `@{ a = 1.5e-7; b = @(1, @(2, @(,@())), @{}); c = "x`ty" }`):

```json
{
  "a": 1.5e-7,
  "b": [
    1,
    [
      2,
      [
        []
      ]
    ],
    {}
  ],
  "c": "x\ty"
}
```

(上の `b` は、`@(1, @(2, @(,@())), @{})` の木。`@(,@())` は、空のリストを 1 つ含むリスト `[[]]`。実装時の単体テストの期待値として使う。)

## 8. `.psd1` の書き出し(`--to psd1`)

自前の書き出し。`Export-PowerShellDataFile` に類するコマンドレット、`ConvertTo-Expression`、`[System.Management.Automation.PSSerializer]` は**使わない**(出力の文字列を、この規定に一致させるため)。**すべて必須**(出力の文字列が一致する)。

### 8.1 レイアウト

インデントは半角スペース **4 個**(タブは使わない)。行末に空白を残さない。改行は LF。

- 最上位のマップが空: `@{}` + 改行。空でなければ、次の形。
- **マップ**: `@{` + 改行、各エントリを `<インデント + 4><キー> = <値>` で 1 行に 1 つ(エントリの区切りは改行だけ。`;` を使わない)、`<インデント>}`。値がコレクションのときは、`<キー> = ` のあと、同じ行に開きの印(`@{` または `@(`)を書き、中身をインデントして、閉じの印を、`<インデント + 4>`(エントリの行と同じインデント)に書く。空のマップは `@{}`。
- **リスト**: 空のリストは `@()`。空でないリストは、`@(` + 改行、各要素を `<インデント + 4><値>` で 1 行(コレクションの要素は、開きの印を同じ行に書く)、要素の間を `,`(要素の閉じの直後、行末)で区切り、最後の要素の後に `,` を付けず、`<インデント>)`。
  - 要素がマップのとき: `@{` + 改行、エントリ、`<インデント + 4>}`。次の要素があれば、`}` の直後に `,`。
  - 要素がリストのとき: `@(` + 改行、…、`<インデント + 4>)`。次の要素があれば `)` の直後に `,`。
  - **1 要素のリストで、その要素がリスト(空のリストを含む)のとき**、その要素の行の先頭に `,` を付ける(`,@(`、空なら `,@()`)。単独の `@(@(...))` は、PowerShell の実行時の意味で 1 段平坦化され、この仕様の読み取りも拒否する([03 第 4.6 節](03-definition-format.md))ので、単項のカンマで包む。要素が複数のリストや、1 要素でも要素がマップ・スカラーのときは、単項のカンマを付けない(カンマ区切りの要素は入れ子のまま保たれる)。
- 最上位の値の後ろに LF を 1 個付ける。

### 8.2 スカラー

- 整数・浮動小数・真偽値・null: 第 6 節のとおり(`$true`、`$false`、`$null`)。
- 文字列(値もキーも同じ規則): 第 8.4 節。
- 浮動小数の `.psd1` の字句: 第 6.1 節の結果(`1.0`、`1e16`、`-0.0`)。負の数は先頭に `-`(空白なし)。

### 8.3 キー

- 次の**すべて**を満たすときだけ、**裸のキー**(引用符なし)で書く: (1) 空でない。(2) 先頭が ASCII の英字(`A-Za-z`)か `_`。(3) 2 文字目以降が ASCII の英数字(`A-Za-z0-9`)か `_`。(4) PowerShell の予約語(次の一覧。ASCII の大文字小文字を区別せず比べる)でない。
  - 予約語(安全側に倒した一覧。未確認: 公式ドキュメントとの突き合わせ。一覧に無い語を裸で書いて問題が起きるかも未確認。試験 T-C04): `begin`、`break`、`catch`、`class`、`clean`、`configuration`、`continue`、`data`、`define`、`do`、`dynamicparam`、`else`、`elseif`、`end`、`enum`、`exit`、`false`、`filter`、`finally`、`for`、`foreach`、`from`、`function`、`hidden`、`if`、`in`、`inlinescript`、`null`、`parallel`、`param`、`process`、`return`、`sequence`、`static`、`switch`、`throw`、`trap`、`true`、`try`、`until`、`using`、`var`、`while`、`workflow`。
  - 例: `format_version`、`pipeline`、`job`、`id`、`command`、`warning_exit_codes`、`on`、`next`、`_x`、`A1` は裸。`if`(予約語)、`true`、`1a`、`a-b`、`a.b`、`a b`、空文字列、非 ASCII(`é`、`夜間`)は引用符つき。
  - この判定は、自前の走査で行う(`-match` を使わない)。
- 引用符つきのキーは、第 8.4 節の文字列の規則で書く(`'a-b'`、`''`、`"é`u{a}"`)。キー `on` は、裸で書ける(`on = 'warning'`)。

### 8.4 文字列の書き方

PowerShell の単一引用符の文字列は逐語的(エスケープがない。中の `'` は `''`)、二重引用符の文字列は、`$` による展開と、バッククォートによるエスケープがある(確認(出典: about_Quoting_Rules)。[03 第 4.4 節](03-definition-format.md))。また、PowerShell は、U+2018、U+2019、U+201A、U+201B を単一引用符と、U+201C、U+201D、U+201E を二重引用符と見なす(確認(出典: CharTraits のソース、about_Quoting_Rules))。次のとおり書く。

1. 文字列の各文字について、**単一引用符の文字列で書けない文字**(次の集合 N)を含むか調べる。N: U+0000〜U+0008、U+000A〜U+001F(**U+0009(タブ)は含まない**)、U+007F〜U+009F、U+2028、U+2029、U+FEFF、U+FFFE、U+FFFF、およびスマートクォート U+2018、U+2019、U+201A、U+201B、U+201C、U+201D、U+201E。(U+201C〜U+201E は、単一引用符の文字列の中では引用符として働かないと推測されるが未確認(試験 T-C05)なので、安全側に N に含める。**決定**。)
2. N の文字を**含まない**とき: **単一引用符の文字列**で書く。`'` を `''` に置き換え、前後を `'` で囲む。そのほかの文字(`$`、`` ` ``、`"`、非 ASCII、絵文字、タブを含む)は、そのまま書く。
3. N の文字を**含む**とき: **二重引用符の文字列**で書く。前後を `"` で囲み、次の文字を、`` `u{16進} `` で書く(確認(出典: about_Special_Characters): `` `u{x} `` は、1〜6 桁の 16 進の Unicode のエスケープで、PowerShell 6 以降。最大 10FFFF): 集合 N の文字、`"`(U+0022)、`$`(U+0024)、`` ` ``(U+0060)。16 進は**小文字**、先頭の 0 なし(例: U+000A は `` `u{a} ``、U+001B は `` `u{1b} ``、U+0000 は `` `u{0} ``、U+2028 は `` `u{2028} ``)。**そのほかの文字は、そのまま書く**(非 ASCII、絵文字(サロゲートの対)、タブ、`'` を含む)。
   - `` `u{…} `` の波括弧の中は 16 進だけなので、直後の文字が 16 進の数字でも、混ざらない。
   - 二重引用符の文字列の中の `$` は、`` `u{24} `` にするので、展開(`ExpandableStringExpressionAst`)にならない。
4. 空文字列は `''`。

- 例(値 → 出力): `nightly` → `'nightly'`、`it's` → `'it''s'`、`夜間バッチ` → `'夜間バッチ'`、`transform "in dir" $HOME` → `'transform "in dir" $HOME'`、`a` + LF + `b` → `"a`u{a}b"`、タブを含む `x<TAB>y` → `'x<TAB>y'`(タブはそのまま)、`a'` + LF → `"a'`u{a}"`、`$x` → `'$x'`、`` ` `` + `n` → `` '`n' ``(単一引用符の文字列の中のバッククォートは逐語的)、`“q”`(U+201C、U+201D)→ `` "`u{201c}q`u{201d}" ``、`don’t`(U+2019)→ `` "don`u{2019}t" ``、U+1F600 → `'😀'`、U+007F → `` "`u{7f}" ``、U+FEFF → `` "`u{feff}" ``、空文字列 → `''`。
- **読み戻しの保証**: 書き出した文字列は、[03 第 4.4 節](03-definition-format.md)の規則で、元の値に読み戻される(`Value` のとおり)。二重引用符の文字列の `` `u{…} `` が、BMP 外(U+10000 以上)の文字を、サロゲートの対にして値に入れること、`` `u{0} `` が NUL 文字を作ることは、未確認(試験 T-C05)。BMP 外の文字は、二重引用符の文字列の中でも、そのまま書くので、`` `u{1f600} `` は出力に現れない(N に含まれる文字は BMP の文字だけ)。

## 9. 往復の保証

- 保証するのは、**木の等価**である(第 4.4 節。マップのキーの順序は無視、リストの順序は有意)。入力を読んだ内部表現と、変換結果を(変換後の形式として)読み戻した内部表現が、等しい。さらに、変換結果を元の形式へ戻した結果の木も、元の木と等しい。
- 保証されないもの: コメント、引用符・文字列の書き方(単一引用符と二重引用符の別、here-string の形)、数値の書式(`0xFF` → `255`、`0b101` → `5`、`1e3` → `1000.0`、JSON の `-0` → `0`、`.psd1` の `-0` → `0`)、`$TRUE` の大文字小文字(`$true` に統一される)、裸のキーと引用符つきのキーの別、リストの書き方(カンマ区切り・`@()`・改行区切りの別)。
- 往復で保たれることが期待される値(単体テストで確かめる。実機では未確認): 文字列(`yes`、`no`、`on`、`off`、`1`、`1.5`、`null`、`true`、`<<`、空文字列、前後に空白がある文字列、`a: b`、`$x`、`` `n ``、`'`、`"`、改行・タブ・引用符・バックスラッシュ・制御文字・スマートクォート・日本語・絵文字を含む文字列、長い文字列)、整数(64 ビット符号つき整数の最小値・最大値、0、2^53 + 1 などの 2^53 を超える整数)、浮動小数(`1.0`、`-0.0`、`1.5e-7`、`1e21`、`0.1`、`5e-324`、最大値)、真偽値、null、空のリスト・空のマップ、入れ子のリスト(1 要素の入れ子を含む)、リストの中のマップ、型が混在するリスト、キー `on`・`if` などの予約語と記号を含むキー。
- 試験(実装時): ランダムに作った 1 万個の木(深さ 4 まで。文字列は、`'`・`"`・`$`・`` ` ``・`#`・`:`・`,`・`@`・`{`・`(`・タブ・改行・CR・U+0085・U+2028・U+FEFF・U+FFFE・U+007F・制御文字・スマートクォート(U+2018〜U+201E)・`é`・日本語・絵文字・全角空白などの文字と、予約語からランダムに組み立てたもの。浮動小数は、ビット列からランダムに作ったものと境界の値。整数は、範囲の両端、2^53 + 1、ランダム。キーは、予約語・ASCII の大文字小文字違い(1 つのオブジェクトに入れない)・非 ASCII を含む)を、JSON と `.psd1` に書き出し、読み戻した木が、元の木と等しいこと(試験 T-C07)。
- ただし、**範囲外の数を含む入力は、どちらにも変換できない**(第 5 節)。**キーの大文字小文字だけが違うオブジェクトを含む JSON は、`.psd1` に変換できない**(第 5 節)。

## 10. エラーの構造と表示

型の骨格(例。`[pscustomobject]`):

```powershell
$script:ConductorConvertErrorKinds = @(
    'fileMissing', 'unreadable', 'tooLarge', 'syntax', 'unrepresentable', 'rootNotMap'
)   # 6 種

[pscustomobject]@{
    Kind    = [string]'unrepresentable'
    File    = [string]'in.json'                 # 入力ファイルの表示用の名前
    Line    = [Nullable[int]]$null              # 1 始まり。$null は行なし
    KeyPath = [string]'job[1].n'                # 表せない値の場所。$null は場所なし(空文字列にしない)
    Reason  = [string]'数値が表せる範囲を超えています'   # 固定の文(日本語)。入力の値・パーサーのエラー文は含まない
}
```

| フィールド | 内容 |
|------------|------|
| `File` | 入力ファイルの表示用の名前 |
| `Line` | 行番号(1 始まり)。位置が分かるときだけ |
| `KeyPath` | 表せない値の場所(キーの経路)。値そのものは含まない |
| `Kind` | 種類 |
| `Reason` | 固定の文(入力の値・パーサーのエラー文は含まない) |

種類(6 種):

| 識別子 | 日本語 | 英語(英語のメッセージのとき) |
|--------|--------|----------------------------|
| `fileMissing` | 入力ファイルが存在しません | input file does not exist |
| `unreadable` | 入力ファイルを読めません | cannot read input file |
| `tooLarge` | 入力が大きすぎます | input is too large |
| `syntax` | 文法の誤りです | syntax error |
| `unrepresentable` | 相手の形式で表せない値があります | value cannot be represented in the target format |
| `rootNotMap` | 最上位がキーと値の集まり(マップ)ではありません | top level is not a map |

ライブラリ(呼び出し側)の表示:

```
<file>:<line>: <種類の文>: <reason>(場所: <key_path>)    行も場所もあるとき
<file>: <種類の文>: <reason>                              どちらも無いとき
```

行だけ・場所だけのときは、それぞれ `<file>:<line>: <種類の文>: <reason>`、`<file>: <種類の文>: <reason>(場所: <key_path>)` となる。`(場所: …)` は、`KeyPath` があるときだけ、末尾に付く(直前に区切りの空白はない)。`<file>` は、制御文字・書式文字・サロゲート(U+D800〜U+DFFF)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは末尾に `…`。エスケープの規則は [03 第 10.2 節](03-definition-format.md))。

`conductor convert` の失敗の表示(標準エラーの 1 行、終了コード 67):

```
conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason> (<at|場所>: <key_path>)
```

`<reason>` は日本語のまま。`(at: …)` は英語のメッセージ、`(場所: …)` は日本語のメッセージ(言語の選び方は [08](08-output-and-i18n.md))。`(…)` の前に半角スペース 1 個。`KeyPath` がないときは `(…)` を付けない。`<file>`・`<reason>`・`<key_path>` は、制御文字・書式文字・サロゲートをエスケープして出す(ここでは文字数で切らない。`key_path` の中のキー名は、第 5 節の規則で 64 文字に切られている)。実行例:

```
conductor: error: n.json: value cannot be represented in the target format: 数値が表せる範囲を超えています (at: a)
conductor: error: c.json: value cannot be represented in the target format: .psd1 では、大文字小文字だけが違うキーを同時に書けません (at: x.K)
conductor: error: x.json:3: syntax error: JSON の文法に誤りがあります
conductor: error: x.psd1:2: syntax error: .psd1 で使えない書き方です
conductor: error: e.psd1:1: syntax error: .psd1 の文法に誤りがあります
conductor: error: t.json:1: top level is not a map: 最上位がマップではありません
```

(最後の例は、`--to psd1` で、最上位が配列の JSON を入力したとき。)

### 理由の一覧(日本語の原文。英語版はない)

| 理由 | 使われる種類 |
|------|--------------|
| `指定の場所にファイルがありません` | `fileMissing` |
| `読み取りの権限がありません` / `読み取りに失敗しました` / `通常のファイルではありません` / `UTF-8 として読めません` | `unreadable` |
| `入力が上限(1 MiB)を超えています` / `要素数が上限(100000)を超えています` / `文字の大きさが上限(16 MiB)を超えています` | `tooLarge` |
| `.psd1 の文法に誤りがあります` / `.psd1 で使えない書き方です` / `JSON の文法に誤りがあります` / `キーが重複しています` / `キーは文字列で書きます` / `入れ子が深すぎます(上限は 32 段)` | `syntax` |
| `数値が表せる範囲を超えています` / `.psd1 では、大文字小文字だけが違うキーを同時に書けません` | `unrepresentable` |
| `最上位がマップではありません` | `rootNotMap` |

### 11.1 `.psd1`(コメント、16 進、`$true`、`on: error` を含む)→ JSON(`--to json`)


(`on = 'error'` のような遷移は、変換器は検査しない。定義として読み込むときに `errorTransition` になる([03 第 8.4 節](03-definition-format.md))。)

## 12. 実装時に最初に確かめる試験(実機が必要なもの)

この環境では動かせなかった。[03 第 16 節](03-definition-format.md)の試験(T-01〜T-20)に加えて、変換器の実装の最初に、最小・最新の PowerShell で、3 つの OS で行い、結果に合わせてこの文書を更新する。

|------|------|--------------|

| T-C04 | 裸のキー | 予約語を含む、第 8.3 節の予約語の一覧が十分か。一覧に無い語(例: `Class`、`Enum`)の裸のキーが、`ParseInput` で `StringConstantExpressionAst`(`BareWord`)になること |
