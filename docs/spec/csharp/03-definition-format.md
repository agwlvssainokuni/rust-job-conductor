# 03. 定義ファイルの書式と検証

この文書は、`conductor` の定義ファイルの書式と、読み込み時の検証を定める。この文書だけで、C#(.NET)でゼロから、同じ受理・拒否・エラー(種類、文言、行番号)を返す読み込み処理を実装できることを目標とする。

- 定義ファイルの書式は **JSON(主)** と **YAML(副)** の 2 つ。書式は**拡張子**で決める(第 2 節)。既定のファイル名は `conductor.json`。人が書く定義にコメントが要るときは、YAML を使う(JSON はコメントを書けない)。
- 検証は、見つけた誤りを**まとめて**返す。ただし、早い段階の誤り(取り込み、文法、展開と上限、版)は 1 件だけで打ち切る(第 2 節)。
- 定義の内容は、読み込みでは実行も評価もしない。`command` の文字列は、そのまま保持する。
- 確認できなかった点は「未確認」と書く。公式ドキュメントや公開されたソースで確かめた点は「確認(出典: …)」と書く。この環境には .NET SDK が無く、実機では動かしていない。したがって「確認」は、**文書・ソースの記述の確認**であり、動作の確認ではない。実装時に、第 7.5 節の受け入れ試験(YAML)と第 4.4 節の差分試験(JSON)を、採用する版と最小・最新の LTS で、3 つの OS で行う。
- 「必須」と書いた挙動は、利用者から見える結果(受理/拒否、エラーの種類・文言・行番号、取り込み後の値)であり、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、利用者から見える結果が変わらない範囲で、実装が選んでよい。
- このツールの終了コード、エラー行の標準エラーへの出し方は [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方と標準出力・標準エラーの文字コードは [08. 出力と多言語対応](08-output-and-i18n.md) に従う。この文書は、エラーの内容(種類・位置・理由)までを定める。
- JSON と YAML の読み取り(第 4〜7 節)は、[09. 変換器](09-converter.md)と共有する。実装は、`src/Conductor.Core/` の中に「木の読み取り」の部分(名前空間 `Conductor.Json`(自前の JSON 読み書き)、`Conductor.Definition`(木の型、YAML の読み取り、上限、検査)。ファイル名は任意)を置き、名前空間 `Conductor.Convert` はその公開メソッドを使う([02. アーキテクチャ](02-architecture.md))。
- 実装は、`<Nullable>enable</Nullable>`、`<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` で書く。読み込み処理は、利用者の入力の誤りを**例外ではなく戻り値**(結果の型)で返す。例外は、実装の不具合(想定外の内部失敗)にだけ使う。ただし、ライブラリや BCL が投げる例外は、第 3、7.4 節のとおり、読み込み処理の内側で捕まえて、定められた種類の戻り値にする。
- 文化に依存する API(`ToString()`、`Parse`、`ToUpper`、`string.Compare`、`StartsWith(string)` など)は、この文書の処理では使わない。数の書式化と解析は `CultureInfo.InvariantCulture`、文字列の比較は `StringComparison.Ordinal` を使う([02. アーキテクチャ](02-architecture.md)の `InvariantGlobalization=true` の決定)。

## 1. 記法と用語

| 語 | 意味 |
|----|------|
| 文字 | Unicode のコードポイント(スカラー値。サロゲートを除く)。「N 文字」と書いたものは、この単位で数える(UTF-8 のバイト数でも、書記素でも、`string.Length`(UTF-16 のコード単位)でもない)。C# では `Rune`(`System.Text.Rune`)がコードポイント 1 つを表す。文字列を `Rune` で走査するには `string.EnumerateRunes()`、コードポイントの数は、`EnumerateRunes()` の要素数で数える(下の注)。 |
| コード単位 | `char`(UTF-16 のコード単位。サロゲートの前半・後半は別の `char`)。位置の列(第 13.1 節)と、YAML ライブラリの位置の添字は、この単位である。 |
| 空白を取り除く(trim) | 文字列の先頭と末尾から、Unicode の White_Space 属性を持つ文字(U+0009〜U+000D、U+0020、U+0085、U+00A0、U+1680、U+2000〜U+200A、U+2028、U+2029、U+202F、U+205F、U+3000)を取り除く。「空白だけ」は、取り除いた結果が空文字列になること。**`string.Trim()` と `char.IsWhiteSpace` を、この列挙と同じものとして使ってよい**(確認(出典: `Char.IsWhiteSpace` の公式ドキュメントの列挙(SpaceSeparator の U+0020、U+00A0、U+1680、U+2000〜U+200A、U+202F、U+205F、U+3000、LineSeparator の U+2028、ParagraphSeparator の U+2029、そして U+0009〜U+000D、U+0085)と、`String.Trim()` の説明(`Char.IsWhiteSpace` が真の文字を取り除く)。列挙はこの文書の列挙と一致する。U+200B と U+FEFF は含まれない))。ただし、Unicode のデータの版で `SpaceSeparator` が増える可能性は、ドキュメントからは否定できないので、全 `char`(U+0000〜U+FFFF)を `char.IsWhiteSpace` に通して、この列挙(25 個)と一致することを確かめる単体テストを置く(未確認: 実機での結果)。引数なしの `Trim()` の代わりに、`string.IsNullOrWhiteSpace` も同じ判定である。 |
| 位置 | 値や構文要素の、入力中の場所。行(1 始まり)と列(1 始まり)の組。取り方は第 13 節。 |
| 行 | 行番号。1 始まり。**LF(U+000A)の数**で数える(CRLF でも同じ)。ライブラリが報告する行(U+0085、U+2028、U+2029、CR だけの改行も改行として数える)は**使わない**(第 13.1 節)。 |
| 値の型 | 木の値は、null、真偽値(bool)、整数(int)、範囲外の整数(hugeInt)、浮動小数(float)、文字列(string)、リスト(seq)、マップ(map。キーと値の対応)の 8 種のいずれか(第 6 節)。 |
| 範囲外の整数 | 64 ビット符号つき整数(`long`)の範囲(-9,223,372,036,854,775,808〜9,223,372,036,854,775,807)に収まらない整数の書き方。木では種別 `HugeIntNode` で表し、値は持たない。エラーにはしない(使う側の検査が拒否する)。`decimal` や `BigInteger` は、この仕様では使わない(第 4.3 節の決定)。 |
| マップのリスト | 要素がすべてマップであるリスト(`job` や `transitions`)。 |
| 誤り | エラーの 1 件。種類(`kind`)、行(なしもある)、理由(`reason`)をもつ(第 12 節)。 |
| 受理 | その値や書き方を誤りなく読み込むこと。拒否はその逆。 |

- **入力から得た `string` は、対にならないサロゲート(U+D800〜U+DFFF の単独の `char`)を含まない**。UTF-8 の復号が拒否し(第 3 節)、エスケープで書かれたものも拒否する(第 4、5.5 節、第 7.4 節 #12)。したがって、`string` を `char` で走査しても、サロゲートの対が壊れる問題は、対(前半の直後に後半)をそのまま通す限り起きない。コードポイントの数は、`char` のうちサロゲートの後半(`char.IsLowSurrogate`)でないものの数と一致する(対が正しいので)。表示用のエスケープと切り詰め(第 12.2 節)は、対を 1 文字として数える。
- **`bool` と整数は別の型**: この文書の木は、真偽値(`BoolNode`)と整数(`IntNode`)を別の型で持つので、検査は型(種別)で行う。C# では `bool` は `int` に暗黙変換されないが、`object` に入れた値の型判定(`is long`)や、`JsonElement` などの汎用の木に頼ると、整数と浮動小数(`1.0`)の区別が失われる(第 4.4 節)。この文書の木だけを使う。

## 2. 書式の決定と処理の段階

### 2.1 書式の決定(拡張子)

- 定義ファイルのパスの指定(`--config`)があれば、それを使う。なければ、カレントディレクトリの `conductor.json`。
- 書式は、パスの**拡張子**で決める。拡張子は、パスの最後の要素(最後のパス区切りより後ろ。区切りは `Path.DirectorySeparatorChar` と `Path.AltDirectorySeparatorChar`。Windows では `\` も `/` も、Unix 系では `/` だけ)の、最後の `.` から末尾まで。`Path.GetExtension(string)` は、この規則(確認(出典: `Path.GetExtension` の公式ドキュメント。最後の文字から先頭へ向かって `.` を探し、区切り文字より前に見つかれば、`.` から後ろを返す。見つからなければ空)。`".yaml"` は `".yaml"` を返す(この規則から。実機の確認は未確認)。末尾が `.` のものは、空を返す(未確認。ただし、どちらの結果でも `unsupportedFormat` なので差は出ない))と同じなので、**使ってよい**。大文字小文字は区別しない(`.JSON` は `.json`)。**ASCII の拡張子のときだけ**、自前で ASCII の英大文字を小文字にして(`c is >= 'A' and <= 'Z'` なら `(char)(c + 32)`)比べる(`ToLower()` や `ToLowerInvariant()`、`StringComparison.OrdinalIgnoreCase` は使わない。非 ASCII の文字が ASCII に化ける可能性を、公式ドキュメントでは確かめていないため。例: ケルビン記号 U+212A)。非 ASCII を含む拡張子は、無条件で未対応。

| 拡張子 | 書式 |
|--------|------|
| `.json` | JSON |
| `.yaml`、`.yml` | YAML |
| それ以外(拡張子なしを含む。`.txt`、`.xml`、末尾が `.` のものなど) | 拒否: `unsupportedFormat`、行なし、理由 ``拡張子は .yaml、.yml、.json のいずれかで書きます`` |

- この判定は、ファイルに触れる前に行う(ファイルが存在しなくても、拡張子が合わなければ `unsupportedFormat` になる)。
- `.json` という名前だけのファイル(拡張子の前の名前が空)も、拡張子は `.json` で、JSON として読む。
- 表示用のファイル名は、パスを文字列にしたもの(与えられた表記のまま。正規化しない。`Path.GetFullPath` を通さない)である。

### 2.2 処理の段階と打ち切り

`Load(path, expectedPipelineName)` は次の順に処理する。前の段階で失敗したら、そこで打ち切り、**その 1 件だけ**を返す(後ろの段階は実行しない)。最後の Walk だけが、複数の誤りを返す。

| 段階 | 内容 | 失敗の種類(`kind`) | 返る誤りの数 |
|------|------|----------------------|--------------|
| 1. Intake | 書式の決定、ファイルの読み取り | `unsupportedFormat` / `fileMissing` / `unreadable` / `tooLarge` | 1 |
| 2. Parse | 文法の検査(JSON は自前の読み取り、YAML はライブラリ)と、木の組み立て | `syntax` | 1 |
| 3. Resolve | 文書の数、タグ、キー、アンカーとエイリアスの展開、マージキー、重複キー(YAML)、上限(要素数・文字の大きさ・入れ子の深さ)、最上位の確認 | `syntax` / `tooLarge` / `typeMismatch`(最上位がマップでない) | 1 |
| 4. VersionCheck | `format_version` | `versionMissing` / `versionUnsupported` | 1 |
| 5. Walk | 構造、型、遷移、終了コード、名前 | 第 12.3 節の種類のうち該当するもの | 1 件以上(位置の順) |

`Parse(text, format, fileLabel, expectedPipelineName)` は、段階 2〜5 を文字列に対して行う(ファイルに触れない)。`fileLabel` は、エラーの表示に使うファイル名である。

- `expectedPipelineName`(`pipeline` コマンドで渡されたパイプライン名)が無い(`null`)ときは、名前の照合をしない。
- 検証に成功したときだけ、定義(第 14 節)を返す。誤りが 1 件でもあれば、定義は返さない。
- 版の確認(段階 4)に通らないと、構造の検査(段階 5)は一切行わない。たとえば `format_version` が無い定義に、未知のキーや型の誤りがあっても、返るのは `versionMissing` の 1 件だけである。
- 文法の誤り(段階 2)は版の確認より先である。
- **JSON の段階 2 は、入力を 1 回、先頭から読み、最初に見つかった問題(文法の誤り、重複キー)で打ち切る。** 入れ子の深さ・要素数・文字の大きさの上限は、段階 2 では確認しない(段階 3 で確認する。第 6.3 節)。
- **YAML の段階 2 は、入力の全体(全文書)を、文法の誤りが無いか最後まで読み終えてから、段階 3 の結果を返す。** したがって、YAML では、入力の後ろにある文法の誤りが、前にある段階 3 の誤り(タグ、重複キー、上限)より先に返る。実装は、読み取り(段階 2)と展開(段階 3)を 1 回の走査で行ってよい。そのとき、段階 3 の最初の誤りを覚えておき、以降は展開を止めて、文法の誤りの検出のためだけに最後まで読み進め、読み取りの途中で文法の誤りが出たらそれを返し、出なければ覚えておいた誤りを返す(第 7.4 節 #5)。例: `a: &x 1` + `---` + `b: [1` は、2 つ目の文書の文法の誤りが返る(行は第 13.4 節の規則)。
- 段階 3 は、木を、深さ優先・入力に現れる順に走査し、最初に見つかった問題で打ち切る。

## 3. 取り込み(Intake)

書式の決定(第 2.1 節)のあと、次の順に調べる。最初に当てはまったもので失敗する。

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルの情報(種別・大きさ)の取得で「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | 同、権限がない | `unreadable` | `読み取りの権限がありません` |
| 3 | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 4 | 通常のファイルでない(ディレクトリなど) | `unreadable` | `通常のファイルではありません` |
| 5 | 取得した大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `ファイルの大きさが上限(1 MiB)を超えています` |
| 6 | ファイルを開けない(権限) | `unreadable` | `読み取りの権限がありません` |
| 6' | ファイルを開けない(その他) | `unreadable` | `読み取りに失敗しました` |
| 7 | 読み取りの途中の失敗 | `unreadable` | 権限の問題なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 8 | 読み取った結果が上限を超える(順 5 のあとに大きくなった場合) | `tooLarge` | 順 5 と同じ |
| 9 | UTF-8 として解釈できない | `unreadable` | `文字コードが UTF-8 ではありません` |

実装(C#)の対応。**条件の順序と理由の文言が必須**であり、API の選び方は、次を標準とする。

- 順 1〜5(情報の取得): `File.GetAttributes(path)` と `new FileInfo(path).Length`。
  - 例外の分類: `FileNotFoundException`、`DirectoryNotFoundException` は順 1。`UnauthorizedAccessException` は順 2。それ以外(`IOException`(`PathTooLongException` を含む)、`ArgumentException`(パスに NUL を含む場合など)、`NotSupportedException`、`System.Security.SecurityException`)は順 3。
  - **空文字列のパス**(`--config ""`)は、`ArgumentException` になるが、順 1(`fileMissing`)とする(この仕様の決定。POSIX の `stat("")` が「存在しない」を返すことに合わせる)。
  - `FileAttributes.Directory` が立っていれば順 4。順 4 は、ディレクトリ以外(名前つきパイプ、デバイスなど)にも当てはまる(下の注 1)。
  - `FileInfo.Length` が 1,048,576 を超えれば順 5。
- 順 6・7(読み取り): `new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite, bufferSize: 1, FileOptions.SequentialScan)` で開き、**上限 + 1 バイト(1,048,577 バイト)まで**を、`byte[]` に読む(`FileStream.Read(byte[], int, int)` が 0 を返すか、合計が上限 + 1 バイトに達するまで繰り返す。1 回の `Read` が、要求より少なく返すことがあるので、繰り返す)。`using` で必ず閉じる。**ファイル全体を一度に読む `File.ReadAllBytes`、`File.ReadAllText`、`File.ReadLines`、`StreamReader` は使わない**(上限を超える巨大なファイルをメモリに読み込まないため。`ReadAllText` と `StreamReader` は、さらに BOM の取り除きと復号を黙って行うので、第 4.1 節の BOM の規定を満たせない)。開くときの例外の分類は順 1〜3 と同じ(`FileNotFoundException` は、ここでは順 6' になる)。読み取り中の `UnauthorizedAccessException` は権限、他の `IOException` は失敗。
- 順 8: 読み取ったバイト数が 1,048,576 を超えていれば。
- 順 9: 先頭の 3 バイトが `EF BB BF` なら、その 3 バイトを**バイト列のまま**取り除く(第 4.1 節)。残りを、`new UTF8Encoding(encoderShouldEmitUTF8Identifier: false, throwOnInvalidBytes: true)` の `GetString(byte[], int, int)` で復号し、`DecoderFallbackException` (または、その基底の `ArgumentException`)なら順 9。**`Encoding.UTF8` と `new UTF8Encoding()`(確認(出典: `UTF8Encoding` のコンストラクターの公式ドキュメント): 引数なしのコンストラクターは、不正な符号化を検出しても例外を投げない。セキュリティのために `throwOnInvalidBytes: true` を使うことが推奨されている)、`StreamReader` の自動判定、`File.ReadAllText` は使わない**。過長な符号化(`C0 80`)、サロゲートの符号化(`ED A0 80`)、範囲外(`F4 90 80 80`)、単独の `FF` が、いずれも復号の失敗になることは、**未確認**(.NET の UTF-8 の復号が、Unicode の規定どおりの厳格な検査をすると考えられるが、確認していない)。実装時に、この 4 つの入力を単体テストで確かめる。

注 1(未確認): **名前つきパイプ(FIFO)やデバイスファイル**は、.NET の `FileAttributes` では、通常のファイルと区別できない可能性がある(未確認。`FileAttributes` にパイプを表す値は無い)。その場合、`FileStream` の `Open` が、書き込む側が現れるまで**ブロックして戻らない**ことがありうる(未確認)。これは、通常の利用では起きない(定義ファイルとしてパイプを渡す利用は想定しない)。**必須の対応**: 受け入れ試験(第 7.5 節 #13)で、FIFO を `--config` に渡して、ブロックしないことを確かめる。ブロックする場合の対処は、実装が決める(例: Unix 系で、`libc` の `open` を `O_NONBLOCK` つきで P/Invoke し、`fstat` の結果で通常のファイルかを調べる。[07. プロセスとシグナル](07-process-and-signals.md)の `libc` の P/Invoke と同じ方針)。この対処をしない実装は、「FIFO を渡すと待ち続ける」ことを、既知の制限として README に書く。

注 2(未確認): `File.GetAttributes` と `FileInfo.Length` が、シンボリックリンクのとき、リンク先の情報を返すか(この仕様は、リンクを辿ることを要求する)。返さない場合は、順 4・5 を、開いた `FileStream` の `Length` で判定してよい(その場合、権限のない 1 MiB 超のファイルが `tooLarge` でなく `unreadable` になる差が出る。通常は起きない)。実装時に、リンク(通常ファイルへ、ディレクトリへ、存在しない先へ、自分自身へ)の単体テストで確かめる。

- 上限は **1 MiB = 1,048,576 バイトちょうどまで受理**し、1 バイトでも超えると `tooLarge`。
- 空のファイル(0 バイト)は、空の文字列として読めて、次の段階へ進む。YAML では文書が 0 個の入力として扱われ、`versionMissing` になる(第 6.7 節)。JSON では文法の誤り(`syntax`)になる(第 4 節)。
- 順 5 の大きさの確認は UTF-8 の確認(順 9)より先なので、1 MiB を超えて UTF-8 でないファイルは `tooLarge` である。
- 先頭の BOM(バイト列 EF BB BF)は不正ではない(順 9 を通る)。第 4.1 節のとおり、バイト列の段階で取り除く。
- いずれも、行番号は付かない。
- OS による権限・種別の判定の細部(Windows での `IOException` の `HResult` の値など)は、実装に任せてよい(未確認)。必須なのは、上の表の条件の順序と、各理由の文言である。

## 4. JSON の受理する形式と読み取り(主書式)

JSON は、RFC 8259 の厳格な形式で読む。読み取りは**自前の字句・構文解析**で行う(第 4.4 節の決定)。

### 4.1 受理する形式

| 項目 | 規定 |
|------|------|
| 入力 | UTF-8 のバイト列。先頭の BOM(`EF BB BF`)は、バイト列の段階で取り除く(第 3 節)。位置には数えない(第 13.1 節)。取り除いたあとの、先頭の U+FEFF(BOM が 2 つ並んだ入力)は、文字として残り、空白ではないので、文法の誤りになる。 |
| 空白 | 半角スペース、タブ、LF、CR だけ。それ以外(垂直タブ、全角スペースなど)を、トークンの間に置くことは拒否。 |
| コメント(`//`、`/* */`、`#`) | **拒否**(`syntax`)。 |
| 末尾のカンマ(`[1,]`、`{"a":1,}`)、連続したカンマ、先頭のカンマ | **拒否**(`syntax`)。 |
| リテラル | `true`、`false`、`null`(小文字だけ)。`True`、`NaN`、`Infinity`、`undefined` は拒否。 |
| 文字列 | `"..."` だけ(単一引用符は拒否)。中にタブを含め、U+0000〜U+001F を直接書くことは拒否(`\t` などで書く)。U+007F 以上は直接書いてよい。エスケープは `\"`、`\\`、`\/`、`\b`、`\f`、`\n`、`\r`、`\t`、`\uXXXX`(16 進 4 桁。大文字小文字どちらでも)。それ以外のエスケープは拒否。`\u` でサロゲートの前半(U+D800〜U+DBFF)に、後半(U+DC00〜U+DFFF)の `\u` が続く対は 1 つの文字(コードポイント。UTF-16 では、その対のまま)にする。**対にならないサロゲート**(単独の前半、単独の後半)は拒否(`syntax`)。 |
| 数 | `-?(0\|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` だけ。`+1`、`01`、`.5`、`5.`、`1e`、`0x10`、`1_000` は拒否。 |
| キー | 文字列だけ。 |
| 重複したキー | **拒否**(`syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置)。判定は、エスケープを解いた後の文字列の完全一致(序数比較。`"a"` と `"a"` は重複)。 |
| 最上位 | 任意の JSON の値を、文法としては受理する。最上位がオブジェクト(マップ)でなければ、第 6.7 節のとおり `typeMismatch`。JSON の `null` もマップではないので `typeMismatch`。 |
| 空の入力、空白だけの入力 | 拒否(`syntax`)。 |
| 最上位の値の後ろ | 空白以外が続くことは拒否(`syntax`。複数の値、`{}{}`、後ろのゴミ)。 |

### 4.2 数の型と範囲(`long` への判定。決定)

- 整数: `-?(0|[1-9][0-9]*)` だけ(小数部も指数部もない書き方)。`-0` は整数 0。値は次の手順で得る(**浮動小数(`double`)や `decimal` を経由しない**)。(1) 符号を除いた数字の桁数が **19 を超える**なら、値を調べず、範囲外の整数(`HugeIntNode`)にする(`long` の最大値 9,223,372,036,854,775,807 は 19 桁なので、20 桁以上は必ず範囲外)。(2) 19 桁以下なら、`long.TryParse(字句, NumberStyles.AllowLeadingSign, CultureInfo.InvariantCulture, out long v)` で得る。失敗(`9223372036854775808` など、19 桁で範囲を超えるもの)は、範囲外の整数にする。`-9223372036854775808` は成功する(`long.MinValue`。`TryParse` の仕様。未確認: 実機での結果)。字句は、自前の読み取りが文法を確かめた後なので、`TryParse` が受け付ける他の書式(空白、全角数字など)は入らない。**例外を投げる `long.Parse`、`checked` の演算は使わない**。
- 浮動小数: 小数部または指数部を持つもの(`1.0`、`1e3`、`1E3`、`1e0`、`-0.0`)。値は `double.Parse(字句, NumberStyles.Float, CultureInfo.InvariantCulture)`(または `double.TryParse`)で得る。.NET Core 3.0 以降の `double` の解析は IEEE 754 に準拠する(確認(出典: .NET Core 3.0 の浮動小数の解析・書式化の改善についての .NET ブログ。無限大と NaN の解析、符号の扱いを含む、解析の準拠の修正)。丸めが最も近い値になることと、桁あふれのときに例外でなく無限大を返すことは、ブログの記述からは確かめきれていない: **未確認**。実装時の試験(第 7.5 節の数の試験)で確かめる)。結果が ±無限大(`1e400`)のものは、`FloatNode` に「範囲を超えた」印(`Overflow = true`)を付ける(エラーにはしない)。極小(`1e-400`)は 0.0(エラーにしない)。**指数部の桁が 10 桁以上**(先頭の 0 を除く)のときは、`double.Parse` に渡さず、仮数が 0 なら ±0.0、そうでなければ、指数の符号が正なら ±無限大(`Overflow = true`)、負なら ±0.0 とする(入力は 1 MiB 以下なので、仮数の桁数が約 105 万桁を超えず、指数の大きさ 10^9 以上を打ち消せない。したがって結果は常に同じ)。指数部が 9 桁以下の巨大な値(`1e999999999`)を `double.Parse` が例外なく処理するかは**未確認**(例外が出たら、同じ規則で、桁数でなく値で打ち切る。実装時に確かめ、必要なら閾値を 5 桁に下げる。結果は同じ)。
- **整数だけの項目**(`format_version`、`max`、`multiplier`、各種の終了コード)に、浮動小数が来たら、型の誤りとして拒否する。**`1.0`、`1e0`、`10e-1` のように値が整数になる書き方でも拒否**(YAML の `1.0` も同じ)。実装は、ノードの種別(`IntNode` か `FloatNode` か)で判定する。`double` の値が整数かどうか(`d == Math.Floor(d)`)で整数と見なさない。
- JSON の数のうち、値を使う検査の対象外の場所にある浮動小数や範囲外の整数は、エラーにならない(そのキーが `unknownKey` になるだけ)。

### 4.3 `decimal` と `BigInteger` の扱い(決定)

| 型 | 決定 | 理由 |
|----|------|------|
| `decimal` | **使わない** | 有効桁が約 28 桁・指数が限られ、`double` の全範囲(±1.8e308、5e-324)を表せない。浮動小数の字句を `decimal` に入れると、`1e400` や `1e-30` で失敗・丸めが起き、`double` に入れた場合と結果が変わる。整数は `long` で足りる(範囲外の判定は桁数と `TryParse` で行える)。 |
| `System.Numerics.BigInteger` | **使わない** | 範囲外の整数は、値を持たない種別 `HugeIntNode` で表す。値を保つ必要がない(第 5.2 節、[09. 変換器](09-converter.md)は範囲外の数を拒否する)。巨大な桁数の字句を、解析する時間を避ける(桁数による打ち切りを先に行う)。 |
| `double` | 浮動小数だけに使う | `1` と `1.0` は別の型として扱う(木の等価でも、書き出しでも)。`long` を `double` に変換して比べる、書くことは、2^53 を超える整数で桁が落ちるので、しない。 |

### 4.4 読み取りの方式の決定: `Utf8JsonReader` を土台にしない(全面自前)

`System.Text.Json` の `Utf8JsonReader` を土台にするか、全面自前にするかを検討し、**全面自前**に決めた。以下は、公式ドキュメントで確認できた範囲と、この仕様の要件との関係である。

| 要件(この仕様) | `Utf8JsonReader` について確認できたこと | 判断 |
|----------------|--------------------------------------|------|
| 厳格な RFC 8259(コメント・末尾カンマの拒否) | 既定で RFC に厳密に従う。コメントの扱いと末尾カンマの許可は `JsonReaderOptions` で変えられる(確認(出典: `Utf8JsonReader` と `JsonReaderOptions` の公式ドキュメント。`CommentHandling`、`AllowTrailingCommas`)) | 満たせる |
| BOM は無視する | **BOM を取り除いてから渡す必要がある。さもないと不正な JSON として例外**(確認(出典: 「Use Utf8JsonReader」の公式ドキュメント)) | 呼ぶ側で取り除く(第 3 節)。問題にならない |
| 入れ子の深さは、文法の誤りの後(段階 3)で判定する | `JsonReaderOptions.MaxDepth` の既定は 64(0 が既定を表す)。超えると読み取りが失敗する(確認(出典: `JsonReaderOptions` の公式ドキュメント。最大値は未確認))。深さを大きくしても、読み取りは再帰を使わないと考えられるが未確認 | 深さの失敗が、文法の誤りより先に出うる。大きな `MaxDepth` で回避できるかは未確認 |
| 重複キーを、**2 つ目のキーの位置**で拒否する | 読み取り器は、プロパティ名を 1 つずつ返すだけで、重複の検査機能は確認できなかった(`Utf8JsonReader` のドキュメントに該当する設定が無い)。呼ぶ側が、オブジェクトごとに名前の集合を持つ必要がある。名前は、エスケープを解いた文字列で比べる(`ValueIsEscaped`、`GetString`、`ValueTextEquals` を使う) | 自前の集合が必要 |
| 位置: **誤りの位置は「読み進められなくなった最初の文字」**、値・キーの位置は先頭 | `TokenStartIndex`(最後に読んだトークンの開始位置。**バイト**の添字。空白を飛ばした後。確認)。`BytesConsumed`。文法の誤りは `JsonException`(行番号とその行の中の**バイト**位置を持つ。確認(出典: `Utf8JsonReader` の説明))で、位置の規則(読み進められなくなった最初の文字か)は、ドキュメントからは確認できない: **未確認** | 位置が必須の規則(第 4.5 節)と一致する保証がない |
| 整数の字句(`01`、`1.`、`1e`、`+1` の拒否位置)、`long` の範囲 | 数の解析は、`TryGetInt64` などで、`long` に収まるかを返す。巨大な整数は、`TryGetDecimal` が失敗するなど、型ごとに範囲が違う(`GetInt64` などの名前から。範囲外の挙動は未確認)。整数と浮動小数の区別は、トークンの文字(`.`、`e`、`E` の有無)を、自分で見る必要がある | 自前の字句の判定が結局要る |
| 文字列: 対にならないサロゲートのエスケープを拒否する | `GetString()` が、不正な UTF-16 のときに例外を投げることが知られているが、**公式ドキュメントでは確認できなかった**。位置(エスケープの `\` の位置)は、読み取り器から得にくい | 未確認 |
| 不正な UTF-8 | 不正なバイトは、読み取りの失敗になると考えられる(未確認)。ファイル全体の復号は第 3 節で厳格に行うので、読み取り器に任せない | 第 3 節で済む |
| 位置の単位 | バイトの添字しか得られない。この仕様の列は、`string` の `char` の添字(第 13.1 節)で、同じ行の中の順序づけにだけ使う。バイトの添字でも順序は保たれるが、行の求め方(LF の位置の表)が、バイトと `char` で別になる | 単位をそろえる自前の読み取りのほうが単純 |
| 巨大な入れ子で落ちない | 読み取り器は、再帰でなく、ビットのスタックで入れ子を追う、と考えられるが、未確認 | 自前で、明示のスタックを使う |

結論: 位置の規則と、重複キーの時点・位置、整数の字句の位置、サロゲートの拒否位置が、すべて**必須**であり、`Utf8JsonReader` を土台にしても、これらを補う処理が大半になる。確認できた範囲では、要件の半分以上が、読み取り器の文書に書かれていない(未確認)ので、**全面自前の読み取り**を採る。`Utf8JsonReader` は、**試験の比較相手(オラクル)としてだけ**使う(開発時のテストプロジェクトで、`System.Text.Json` はテスト用の依存として使ってよい。BCL なので、外部のパッケージは増えない): 同じ入力を、自前の読み取りと `Utf8JsonReader`(コメント・末尾カンマは拒否の設定、`MaxDepth` は最大)の両方に通し、**受理と拒否の結果が一致すること**(位置は比べない)を、ランダムに作った入力と、第 4.1 節の例で確かめる(差分試験。**必須**)。差が出た入力は、どちらが正しいかを、RFC 8259 に照らして決め、この文書の規定を直す(`Utf8JsonReader` の挙動が RFC と違えば、規定を優先)。

### 4.5 JSON の誤りの位置

文法の誤りの位置は、**入力の先頭から読んでいって、読み進められなくなった最初の文字**(その前までが、有効な JSON の先頭部分になっているもの)の位置。入力が途中で終わったとき(閉じていない配列・文字列など)は、入力の末尾の位置(末尾が改行なら、その次の空の行を 1 行と数える)。例:

| 入力(`\n` は改行) | 誤りの位置 |
|------|------------|
| `{"a": 1,}` | `}` の位置(1 行目) |
| `{"a" 1}` | `1` の位置 |
| `{\n  "a": 1\n  "b": 2\n}` | `"b"` の位置(3 行目) |
| `[1, 2` + 末尾の改行 | 末尾(2 行目) |
| `{"a": "x` + 改行 + `"}` | 改行の位置(1 行目。文字列の中に改行を直接書いたため) |
| `{"a":1}{"b":2}` | 2 つ目の `{` の位置 |
| `{"a":1,"a":2}`(重複) | 2 つ目の `"a"` の位置(1 行目) |

文字列の中の誤り(不正なエスケープ、対にならないサロゲート、直接書いた制御文字)の行は、その文字列の行(文字列は改行を含められないので、どの文字でも同じ行)。

### 4.6 JSON の読み取りの規定(自前の字句・構文解析)

読み取りのメソッド: `JsonReader.Read`(第 14.2 節。成功なら木、失敗なら 1 件の誤り)。ステートの読み込みも、同じメソッドを `deferDuplicateKey: true` で呼ぶ(重複を見つけても止めず、後ろの文法の誤りを優先する。[06. ステートファイル](06-state-file.md))。**この読み取りは、定義・変換・ステートの 3 つで共用する。** 実装の詳細は任せるが、次は**必須**である。

1. **入力(復号済みの `string`)を、先頭から 1 回だけ読む**。`char` の添字を進め、位置(行、列)を、改行(LF)の数と、行の先頭の添字から求める(第 13.1 節)。`Span<char>` や `ReadOnlySpan<char>` で走査してよい。
2. **入れ子は、明示のスタック(`List<Frame>` など)で読む**(メソッドの再帰で読まない)。この段階では、入れ子の深さの上限を**適用しない**(段階 3 が適用する)。これは、深い入れ子の後ろに文法の誤りがあるとき、文法の誤りが先に返る(段階 2 が先)ことを守るためである。スタックの大きさは、入力の大きさ(1 MiB)で抑えられる。`StackOverflowException` は、`try`/`catch` で捕まえられず、プロセスが既定で終了する(確認(出典: `StackOverflowException` の公式ドキュメント。深い再帰で投げられる。捕捉できず、再帰の深さを自分で制御するよう求めている))ので、再帰を使わないことは、**異常終了を避ける唯一の方法**である。
3. **整数の字句**: 第 4.1 節の「数」の文法に従って、字句を先頭から読む(自前の文字の比較。`[0-9]` は `c is >= '0' and <= '9'` で判定し、`char.IsDigit` は使わない: 確認(出典: `Char.IsDigit` の公式ドキュメント): `char.IsDigit` は「Unicode の 10 進数字に分類される文字」を真とする。この分類は ASCII 以外の 10 進数字(全角数字 `１` など)にも当たると考えられるが、個別の文字は未確認)。読んだ字句に、小数部・指数部が無ければ整数、有れば浮動小数とする(第 4.2 節)。字句の直後の文字が、区切り(空白、`,`、`]`、`}`、入力の末尾)でなければ、その文字の位置で文法の誤り(`01` は 2 文字目の `1`、`1.` は `.` の次、`1e` は `e` の次、`+1` は `+`、`.5` は `.`、`0x10` は `x`)。
4. **リテラル**: `true`、`false`、`null` は、文字ごとに照合し(序数比較)、最初に合わない文字(または入力の末尾)の位置で文法の誤り。リテラルの直後が区切りでなければ、その文字の位置で文法の誤り。
5. **文字列**: 開きの `"` から読む。U+0000〜U+001F の文字、改行、入力の末尾は、その位置で文法の誤り。エスケープは第 4.1 節の表のとおり。`\u` の 4 桁が 16 進(`0-9a-fA-F`。自前の比較)でなければ文法の誤り。サロゲートの前半の `\uD800`〜`\uDBFF` の直後が、`\uDC00`〜`\uDFFF` の `\u` でなければ、文法の誤り(位置はそのエスケープの `\` の位置)。後半が単独で現れたときも同じ。読んだ文字列は、`StringBuilder` にエスケープを解いた `char` を足して得る(対のサロゲートは、前半、後半の順に 2 つの `char` を足せば、1 つのコードポイントになる)。エスケープのない文字列は、`string.Substring` か `new string(span)` でよい。
6. **オブジェクト**: `{` の後ろは、空白を飛ばして `}`(空のオブジェクト)か文字列(キー)。キーの文字列を読み終えた**時点で**、重複を調べる(そのオブジェクトの `HashSet<string>`(比較は `StringComparer.Ordinal`)に、エスケープを解いたキーが既にあれば、**そのキーの開きの `"` の位置で**重複のエラー。`:` 以降は読まない。この仕様の決定)。次に `:`、値、そして `,`(次のキー)か `}`。**`HashSet<string>` と `Dictionary<string, T>` は、既定の比較が序数なので使ってよいが、比較器を明示する**(`StringComparer.Ordinal`。文化依存の比較器を渡さない)。
7. **配列**: `[` の後ろは、空白を飛ばして `]`(空の配列)か値。値の後ろは `,`(次の値)か `]`。`,` の直後に `]` が来ること(末尾のカンマ)は、`]` の位置で文法の誤り。
8. **最上位**: 空白を飛ばして値を 1 つ読み、空白を飛ばして入力の末尾に達しなければ、その位置で文法の誤り。入力が空(空白だけを含む)なら、入力の末尾の位置で文法の誤り。
9. 木のノードの位置は、第 13.2 節(オブジェクトは `{`、配列は `[`、スカラーは字句の先頭、キーの位置は開きの `"`)。
10. 木は、`MapNode.Entries`(第 6.1 節。キーを `string` で持つ並び)として作る。`Dictionary` に入れて重複を落とすことをしない(重複は拒否するので、結果は同じだが、キーの順序と、重複の検出の時点を、この規定のとおりにするため)。

文法の誤りの理由は `JSON の文法に誤りがあります`、重複は `キーが重複しています`(いずれも `syntax`)。

## 5. YAML の受理する部分集合(副書式)

YAML は、YAML 1.2(改訂 1.2.2)の文法を基本として読み、スカラーの型は **コアスキーマ**(第 5.2 節)で決める。YAML 1.1 の型(`yes`/`no`/`on`/`off` の真偽値、`0777` の 8 進、日付、`<<` 以外の拡張など)は扱わない。

文法の細部(エスケープ、折りたたみ、インデントの規則など)は YAML 1.2.2 の規格に従い、読み取りライブラリがそれを実装する。ただし、採用するライブラリ(YamlDotNet。第 7 節)は、libyaml の流れをくむ読み取りで、**1.2 の文法と違う点がある**。**この文書が規格と別に決めること**は、次の 5.1 の表の「扱い」の列と、第 5.2〜5.6 節である。ライブラリがこれと違う結果を返すときは、この文書の規定が優先し、実装が補う(第 7 節)。

### 5.2 スカラーの解決(コアスキーマ)

**引用符なしのスカラー**(`Scalar` イベントの `Style` が `ScalarStyle.Plain`)の型は、スカラーの文字列**全体**に対して、次の順に判定する。ライブラリは、型を付けない(`Scalar.Value` は、書かれた文字を `string` のまま返す。確認: `Scalar` イベントは `Value`、`Style`、`IsPlainImplicit`、`IsQuotedImplicit` を持ち、値の型は持たない)ので、**実装が自前で判定する**(YamlDotNet の `Deserializer` やシリアライザーの型の解決は使わない。第 7.3 節)。

| 順 | 条件 | 結果の型 |
|----|------|----------|
| 1 | 空文字列、`~`、`null`、`Null`、`NULL` | null |
| 2 | `true`、`True`、`TRUE` / `false`、`False`、`FALSE` | 真偽値 |
| 3 | `.inf`、`.Inf`、`.INF`、`+.inf`、`+.Inf`、`+.INF` / `-.inf`、`-.Inf`、`-.INF` / `.nan`、`.NaN`、`.NAN` | 浮動小数(+∞、-∞、NaN) |
| 4 | `0x` + 1 桁以上の 16 進数字(`0-9a-fA-F`) | 整数(16 進。符号なし) |
| 5 | `0o` + 1 桁以上の 8 進数字(0〜7) | 整数(8 進。符号なし) |
| 6 | `[-+]?[0-9]+`(`007` は 7、`-0` は 0、`+7` は 7) | 整数(10 進) |
| 7 | `[-+]? ( \.[0-9]+ \| [0-9]+ (\.[0-9]*)? ) ([eE] [-+]? [0-9]+)?`(整数の書式は順 6 が先) | 浮動小数 |
| 8 | 上のどれでもない | 文字列 |

- **判定は、自前の文字の走査で行う**(文字ごとの比較。`Regex` を使うなら、`\A` と `\z` で全体に一致させ、数字は `[0-9]` と書き、`RegexOptions.CultureInvariant` を付ける)。次を使わない。(a) `\d`(確認(出典: 正規表現の文字クラスの公式ドキュメント): 既定で、Unicode の 10 進数字(Nd)に当たる。`RegexOptions.ECMAScript` を付けると、`\w` は `[a-zA-Z_0-9]` と等しくなる(`\d` が ASCII だけになるかは、このドキュメントの範囲では未確認)。全角数字 `１` に一致しうる)。(b) `$`(確認(出典: 正規表現のアンカーの公式ドキュメント): 既定で、文字列の末尾、または**末尾の `\n` の直前**に一致する。`\Z` も同じ。`\z` は、末尾だけ)。`Regex.IsMatch(s, @"^[A-Za-z_]+$")` は、`"A\n"` に一致してしまう。(c) `char.IsDigit`、`char.IsLetterOrDigit`、`char.IsLetter`(Unicode の分類に当たる)。
- **整数は `long` で値にする**(第 4.2 節と同じ手順で、桁数による打ち切りと `TryParse` を使う)。符号つきの 10 進は第 4.2 節。16 進は、先頭の 0 を除いた桁数が 16 を超えれば範囲外(`HugeIntNode`)、16 桁以下なら `ulong.TryParse(桁, NumberStyles.AllowHexSpecifier, CultureInfo.InvariantCulture, out ulong u)` で値を得て、`u <= long.MaxValue` なら `IntNode`、そうでなければ範囲外。8 進は、先頭の 0 を除いた桁数が 22 を超えれば範囲外(8 進 22 桁は 66 ビット)、22 桁以下なら自前の繰り返しで `UInt128` に溜めて(`v = v * 8 + 桁`。`UInt128` は 128 ビットで、22 桁でも桁あふれしない)、`v <= long.MaxValue` なら `IntNode`、そうでなければ範囲外。`-0` は整数 0。**`int.Parse`、`long.Parse`(例外を投げる)、`Convert.ToInt64`、`Convert.ToInt64(string, 8)`、`checked` は使わない**(字句の検査と範囲の判定を、桁数と `TryParse` で自前で行うため。第 4.2 節)。
- 浮動小数は、スカラーの文字列から、第 4.2 節の手順(正規化してから `double.Parse`。指数が 10 桁以上のときの打ち切りを含む)で値にする。**順 7 の書式に一致した文字列だけを渡すこと**。`1.`、`.5`、`+.5`、`1.e3` を、`double.Parse` が受け付けるかは**未確認**なので、次のとおり**正規化してから渡す**(必須): 整数部が空なら `0` を、小数点の後ろが空なら `0` を補い、`<符号>?<整数部>.<小数部>(e<符号>?<指数>)?` の形にする(例: `1.e3` → `1.0e3`、`.5` → `0.5`、`1.` → `1.0`、`1e3` → `1.0e3` か `1e3` のまま)。結果が ±無限大になる(`1e999`)ときは、値は ±∞ のまま、`Overflow = true` の印を付ける(エラーにはしない。変換器だけが、これを拒否する)。極小の値(`1e-400`)は、0.0 の浮動小数として受理する(エラーにしない)。
- 浮動小数の例: `1.5`、`-0.0`、`.5`、`1.`、`1e3`、`1.5E-2`。文字列になるもの: `.`、`e3`、`1e`、`1.2.3`、`-`、`+`、`.e1`、`inf`、`nan`、`NaN`、`0b11`、`1_000`、`0x`(桁なし)、`0o8`、`+0x1`、`0X1F`。
- **`yes`・`no`・`on`・`off`・`y`・`n`(大文字小文字を問わず)は文字列**。日付・時刻らしい書式(`2001-01-01`、`12:30:00`)も**文字列**。
- 引用符つき(`'...'`、`"..."`)のスカラーと、`|`・`>` のブロックスカラーは、常に文字列(`'1'` は文字列 `1`、`"null"` は文字列 `null`)。
- 空の値(`key:` の後ろに何もない、`- ` の後ろに何もない)は、引用符なしの空文字列と同じ扱いで、**null**(確認: `Parser` は、値が省略された位置に、`Style` が `Plain` で値が空文字列の `Scalar` を返す(`Parser.cs` の空のスカラーを作る箇所)。引用符つきの空文字列 `''` は、`Style` が引用符なので見分けられる)。アンカーだけで中身がない(`a: &x`)も null。フローのマップでキーだけを書いた `{a, b: 1}` と、明示のキーだけの `? a` の「値」も、空のスカラーが返ると考えられるので(未確認)、**YAML の null として扱い、位置はそのキーの位置とする**。
- 定義ファイルの検査で、null は「どの型でもない値」である。`description:`(値なし)は `description` の型の誤り、`retry:`(値なし)は `retryNotTable`、`job:`(値なし)は `job` の型の誤り、未知のキーの値が null なら `unknownKey` になる(第 9 節)。

### 5.3 アンカーとエイリアス

- `&name` で付けたアンカーを、`*name` で参照できる。`name` は、`[0-9A-Za-z_-]` の 1 文字以上(ライブラリの規則。第 5.1 節)。
- エイリアスは、参照先のノードの内容に置き換わる(コレクションは複製して展開する)。展開後の木には、アンカーもエイリアスも残らない。
- 同じ名前のアンカーを再定義してよい。エイリアスは、それより前の**最後の**定義を指す(`a: &x 1`、`b: &x 2`、`c: *x` で、`c` は 2)。**YamlDotNet の高水準の木(`YamlStream`、`YamlDocument`、`Deserializer`)は、この組み立てを自前で行うので使わない**(第 7.3 節)。**構文イベントの読み取り(`Parser`)は、アンカーを名前のまま `NodeEvent.Anchor` に持つだけである**(確認: `Parser.cs` は、アンカーの再定義を調べない。未確認: 入力ごとの実測)。
- アンカーより前にあるエイリアス(`a: *x` + `b: &x 1`)、定義のないエイリアスは、拒否: `syntax`、理由 ``YAML の文法に誤りがあります``、行はそのエイリアスの行。実装の名前の表に無いことで検出する。
- 閉じたアンカーへの参照は再帰ではない(`a: &r [1]` + `b: *r` は受理)。**自分自身を含むエイリアス**(`a: &r [*r]`)は拒否: `syntax`、理由 ``アンカーが自分自身を含んでいます``、行はそのエイリアスの行。判定は、**まだ閉じていない(終了のイベントに達していない)アンカーつきコレクションの集合**を持ち、エイリアスの参照先がその集合に含まれるかで行う。実装の指針: アンカーの名前の表(`Dictionary<string, AnchorEntry>`。比較は序数)に、スカラーと閉じたコレクションは完成した木を、閉じていないコレクションは「開いている」印を登録する。展開した木は、アンカーもエイリアスも含まないので、閉じたものを辿るだけでは再帰しない。
- エイリアスをキーにしてよい(`*k : 1`)。参照先が、文字列に解決されるスカラーのときに限る(第 5.4 節)。
- **展開の上限**: 第 6.3 節(要素数 100,000、文字の大きさ 16 MiB、深さ 32)。アンカーの入れ子による爆発的な増加(`l0: &l0 [x, x]`、`l1: &l1 [*l0, *l0]`、…)は、この上限で止まらなければならない(必須)。上限を超えたら、複製・確保の**前**に打ち切る(展開は、参照先の木を、上限を数えながら辿り、数え終わってから複製する。数えるときも、複製するときも、**明示のスタック**で辿る)。YamlDotNet のオブジェクトの組み立て(`Deserializer`、`YamlStream.Load`)は**使わない**(展開を自前で数えるため)。
- 定義の中でアンカーを置ける場所は、定義に存在するノードの中だけである(根のキーは 3 つだけなので、例えば根に `defaults:` を足すと `unknownKey` になる)。典型的な使い方は、ジョブの中のキーの値(`success_exit_codes: &ok [0, 2]` を別のジョブで `*ok`)や、ジョブのマップ全体(`- &base` を、別のジョブが `<<: *base` で取り込む)である(第 16 節の例)。

### 5.4 キー

- マップのキーは、**文字列に解決されるスカラー**でなければならない。次は `syntax`、理由 ``キーは文字列で書きます``、行はそのキーの位置: 整数・真偽値・浮動小数・null に解決されるスカラー(`1: x`、`true: x`、`1.5: x`、`~: x`)、範囲外の整数、リストやマップのキー(`? [1, 2]`、`[a]: 1`、`{a: 1}: x`)。引用符つきは常に文字列なので受理(`"1": x`)。キーが空の `: x` は、ライブラリが拒否すると考えられる(未確認。拒否されれば `syntax`、理由は ``YAML の文法に誤りがあります``。受理されて空のスカラー(null)のキーになるなら、``キーは文字列で書きます``。どちらも `syntax` で、理由だけが違う)。
- **重複したキー**は拒否: `syntax`、理由 ``キーが重複しています``、行は 2 つ目のキーの位置。判定は、解決した後の文字列の同一性(`string.Equals(a, b, StringComparison.Ordinal)`、つまり `HashSet<string>` と `StringComparer.Ordinal`。コードユニットの完全一致)で行う。**Unicode の正規化はしない**(`string.Normalize` を呼ばない。`"é"` の合成済みの 1 文字と、`e` + 結合アクセントは別のキー)。引用符の有無が違っても重複(`a: 1` と `"a": 2`)。入れ子のマップごとに別。エイリアスをキーにしたときは、参照先の文字列で判定する。マージキー `<<`(第 5.5 節)を同じマップに 2 回書くことも重複。引用符つきの `"<<"`(通常のキー)と、引用符なしの `<<`(マージキー)は、**互いに重複としない**(この文書の決定。別の集合で数える)。
  - 重複の判定は、マップごとに `HashSet<string>` を持って行う。ライブラリには重複キーの検査が無い(`Parser` は、キーを調べずに、イベントを返す。未確認: 入力ごとの実測)ので、**時間の問題は起きない**(未確認: 10 万個のキーでの実測は、第 7.5 #5)。
- キーの空文字列(`"": x`)は受理する。キーの大文字小文字・前後の空白は区別する。
- この検査は、入力に現れる順(深さ優先)に、段階 3 で行う。重複と非文字列のキーが同じ位置にあれば、どちらでも同じ `syntax` だが、理由は非文字列が先(キーの解決が先)。

### 5.5 マージキー(`<<`)

- マージキーとして扱うのは、**引用符なし・タグなし**のキー `<<` だけ(`Scalar` イベントの `Style` が `ScalarStyle.Plain` で、値が `<<`。タグは元々拒否される)。`"<<"`(引用符つき)は、文字列のキー `<<` として、通常のキーと同じに扱う。エイリアスを通して得たキー `<<` も、通常の文字列のキーとして扱う(この仕様の決定)。
- 値は、マップ、またはマップだけのリスト(`<<: [*a, *b]`)。それ以外(整数・文字列・null(`<<: ~` を含む)、マップでない要素を含むリスト)は拒否: `syntax`、理由 ``マージキーの値がマップではありません``、行はマージキーの位置。
- 優先順位: マップ自身の(`<<` でない)キーが、マージの内容より優先する(自身のキーが `<<` の前にあっても後にあっても同じ)。値がリストのときは、**先頭のマップが優先**。マージされるマップが `<<` を含むとき(入れ子のマージ)は、そのマージも同じ規則で先に展開した結果を使う。優先されずに捨てられたキーは、エラーにしない。
- **キーの順**: マージで加わるエントリは、そのマップの `<<` のエントリがあった位置に、取り込み元の順(リストなら先頭のマップから)で並ぶ。捨てられたものは並ばない。その後ろに、`<<` の後ろにある自身のエントリが続く。
- **位置**: マージで取り込まれたエントリ(キーと値と、その中のすべての子)の位置は、そのマージキー `<<` 自身の位置に置き換える(元の位置は使わない)。これは、エラーの行を決めるための規則である(第 13 節)。
- 実装の指針(任意): マップの走査では、`<<` のエントリは「場所取り」として並びに入れ、取り込み元の内容(値のノード)を覚えておく。そのマップの全エントリの走査が終わってから(自身のキーの集合が決まってから)、場所取りを、捨てられないエントリで置き換える。例: `b: &b {x: 1}` + `a:` の下に `<<: [*b, {x: 2, y: 3}]` と `y: 9` で、`a` は `{x: 1, y: 9}`(`x` は `b` の値、`<<` の位置に並ぶ)。

### 5.6 複数の文書と最上位

- 文書の数を数える(`---` で区切る。構文イベントの `DocumentStart` の数。末尾の `---` の後ろが空でも、空の文書が 1 つあるものとして数える。`a: 1\n---\n` は 2 文書)。文書が 2 つ以上ある入力は、読み取り全体(段階 2)が成功し、かつ最初の文書の走査(段階 3)で他の失敗が無かったときに限り、拒否: `syntax`、理由 ``複数の文書は書けません(1 ファイルに書ける文書は 1 つです)``、行は 2 つ目の文書の内容(根のノード)の位置の行(第 13.2 節。`a: 1\n---\n\n\nb: 2\n` で 5 行目、`a: 1\n---\n` で 3 行目になる、と他の版の規定にそろえる。YamlDotNet での実測は未確認)。
  - 最初の文書の失敗(タグなど)は、2 つ目の文書の拒否より先に返る(入力に現れる順)。2 つ目以降の文書は、走査しない(要素数・大きさの加算に含めない)。ただし、文法の誤りの検出のために、最後まで読み進める(第 2.2 節)。
- 文書が 0 個(空の入力、コメントと空行だけ)は、**空のマップ**として扱う(結果は `versionMissing`)。`DocumentStart` のイベントが 1 つも出ない、と考えられる(未確認)。
- 最初の文書の最上位が **null**(`---` だけの文書など、中身が空)も、空のマップとして扱う(空の `Scalar` イベントが内容になる。未確認)。
- 最上位が、マップでもなく null でもない(リスト、文字列、数など)なら、拒否: `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置。

## 6. 木への展開(Resolve)と上限

### 6.1 木の型

段階 3 の結果と、段階 4・5 の入力は、JSON と YAML に共通の木である。型の骨格(例。名前は実装が決めてよい。判別共用体の代わりに、**抽象クラスと、`sealed` の派生クラス**で表し、判別は `switch` 式の型パターン(`node switch { IntNode n => …, _ => … }`)で行う。名前空間 `Conductor.Json`。[02. アーキテクチャ](02-architecture.md)の置き場所の決定のとおり、木の型は、BCL だけに依存する `Conductor.Json` に置く)。

```csharp
namespace Conductor.Json;

/// <summary>入力中の位置(1 始まり)。順序づけと行の表示に使う。列は UTF-16 のコード単位。</summary>
public readonly record struct Pos(int Line, int Column) : IComparable<Pos>
{
    public int CompareTo(Pos other) =>
        Line != other.Line ? Line.CompareTo(other.Line) : Column.CompareTo(other.Column);
}

/// <summary>木のノード。record にしない(下の注)。</summary>
public abstract class TreeNode
{
    protected TreeNode(Pos pos) { Pos = pos; }
    public Pos Pos { get; }
}

public sealed class NullNode : TreeNode { public NullNode(Pos pos) : base(pos) { } }
public sealed class BoolNode : TreeNode { public BoolNode(Pos pos, bool value) : base(pos) { Value = value; } public bool Value { get; } }
/// <summary>64 ビット符号つき整数に収まる整数。</summary>
public sealed class IntNode : TreeNode { public IntNode(Pos pos, long value) : base(pos) { Value = value; } public long Value { get; } }
/// <summary>64 ビット符号つき整数の範囲を超える整数。値は持たない。</summary>
public sealed class HugeIntNode : TreeNode { public HugeIntNode(Pos pos) : base(pos) { } }
public sealed class FloatNode : TreeNode
{
    public FloatNode(Pos pos, double value, bool overflow) : base(pos) { Value = value; Overflow = overflow; }
    public double Value { get; }      // NaN、±∞ を含みうる
    public bool Overflow { get; }     // 範囲を超えた書き方(1e999 など)のとき true
}
public sealed class StringNode : TreeNode { public StringNode(Pos pos, string value) : base(pos) { Value = value; } public string Value { get; } }
public sealed class ListNode : TreeNode { public ListNode(Pos pos, IReadOnlyList<TreeNode> items) : base(pos) { Items = items; } public IReadOnlyList<TreeNode> Items { get; } }

public sealed record MapEntry(string Key, Pos KeyPos, TreeNode Value);

public sealed class MapNode : TreeNode
{
    public MapNode(Pos pos, IReadOnlyList<MapEntry> entries) : base(pos) { Entries = entries; }
    public IReadOnlyList<MapEntry> Entries { get; }  // 順序つき。キーは重複しない
}
```

- 木は、エイリアスもアンカーもマージキーも含まない(展開済み)。マップのキーは `string` で重複せず、**記述順**を保つ(第 5.5 節のマージの順を含む)。
- **木のノードを `record` にしない**(決定): `record` が自動で作る `Equals`、`GetHashCode`、`ToString`(`PrintMembers`)は、子のノードを**再帰して**呼ぶ。段階 2 の直後の木は、入れ子の深さが数十万になりうる(第 6.4 節)ので、うっかり `ToString()` を呼ぶ(例: 例外のメッセージの組み立て、デバッガーの表示、ログ)と、`StackOverflowException` でプロセスが終了する(確認: 第 4.6 節の 2 の公式ドキュメント。捕捉できない)。クラスで、`Equals` などを上書きしない(参照の等価のまま)。木の等価は、専用の非再帰の関数で比べる([09. 変換器](09-converter.md)第 4.4 節)。`MapEntry` は、値のノードを持つが、`record` が作る `ToString` は、ノードの `ToString`(参照の型名)を呼ぶだけで再帰しない(`TreeNode` が `ToString` を上書きしないため)。ただし、`MapEntry` を `Equals`/`GetHashCode` に使わない。
- マップを `Dictionary` で持たない(位置つきのエントリを順序どおりに持つため)。`Entries` の `IReadOnlyList<MapEntry>`(実体は配列または `List<MapEntry>`)で持つ。キーの検索が要る検査では、`Dictionary<string, MapEntry>`(比較器 `StringComparer.Ordinal`)を一時的に作る(`Dictionary` は、削除をしない限り、挿入順に列挙されることが多いが、**順序は保証されない**ので、順序は `Entries` から得る)。「許されたキーか」の判定には、`HashSet<string>`(または `FrozenSet<string>`。`StringComparer.Ordinal`)を使う。
- **`IntNode.Value` は `long`、`BoolNode.Value` は `bool`** で、検査は種別で行う(第 1 節)。`FloatNode.Value` の等価の判定は、NaN が自分自身と等しくない(`double.NaN == double.NaN` は偽。`double.Equals(double)` は NaN どうしを真とする)ことと、`0.0 == -0.0` が真であることに注意する([09](09-converter.md)の木の等価は、ビット表現で比べる)。
- 木を走査する処理(段階 3 の走査、深さの数え、検査 Walk、変換器の書き出し)は、**メソッドの再帰を使わず、明示のスタック**で行うことが**必須**である(`StackOverflowException` は捕捉できない。第 6.4 節)。

### 6.2 YAML の展開の手順(段階 3)

ライブラリが返した、最初の文書の構文イベントの列を、入力に現れる順に走査し、上の木に写す(明示のスタックで、木を組み立てる)。各ノードについて、次を行う(ここで「ノードの位置」は、第 13.2 節の位置)。

1. エイリアスなら、参照先を(第 5.3 節の、定義の有無と再帰の確認のうえで)展開する。展開したノードとその子の位置は、**エイリアスのトークン `*name` の位置**に置き換える(第 13 節)。
2. 明示のタグがあれば、`syntax`(タグ)で打ち切る。
3. スカラーなら、第 5.2 節で型を決める(キーの位置のスカラーは、文字列でなければ `syntax`(第 5.4 節))。
4. マップなら、第 5.4・5.5 節のとおり、キーの確認、重複の確認、マージの展開を行う。
5. 第 6.3 節の上限を、ノードを訪れるごとに加算して確認する。確認の順は、深さ、要素数、文字の大きさ(同じノードで複数が超えるとき、先のものを返す。この仕様の決定)。

複数の文書のときは、最初の文書だけを走査し、走査で失敗が無かったとき、第 5.6 節の失敗を返す。

### 6.3 上限

| 上限 | 値 | 超過したときの失敗 |
|------|----|--------------------|
| 要素数 | 100,000 | `tooLarge`、理由 ``要素数が上限(100000)を超えています`` |
| 文字の大きさ | 16 MiB(16,777,216 バイト) | `tooLarge`、理由 ``文字の大きさが上限(16 MiB)を超えています`` |
| 入れ子の深さ | 32 | `syntax`、理由 ``入れ子が深すぎます(上限は 32 段)`` |

- **要素数の数え方**: 展開で訪れたノードを 1 つずつ数える。**キーのスカラーも数える**。マップ・リストも 1。根のマップも 1。エイリアスは、エイリアス自身ではなく、**展開した参照先のノード(コレクションなら、その全部)を数える**(同じアンカーを n 回参照すれば、n 回数える)。マージキー `<<` のキー自身も 1 と数え、マージで取り込まれるマップの中身も、捨てられるものを含めて数える(マージキーの値として、通常の値と同じに走査されるため)。**100,000 ちょうどまで受理**し、100,001 個目で失敗する。JSON にも同じ上限がある(展開はないが、数え方は同じ)。例: `a: [0, 0, ...]`(0 を n 個)は、根のマップ 1 + キー 1 + リスト 1 + 要素 n で、n = 99,997 まで受理、99,998 で失敗(JSON の `{"a":[0,0,...]}` も同じ境界)。
- **文字の大きさの数え方**: 訪れたスカラーの文字のバイト数(UTF-8)を足す。キーと値の両方。文字列(引用符つき、ブロックスカラーを含む)は、**値(エスケープを解いたもの)のバイト数**(`Encoding.UTF8.GetByteCount(値)`。対のサロゲートを 4 バイトと数える。木の文字列は、対にならないサロゲートを含まないので、例外・置き換えは起きない)。引用符なしのスカラー(数、真偽値、null を含む)と、JSON の数・真偽値・null は、**書かれた文字のバイト数**(`123` は 3、`0x1F` は 4、`null` は 4、`true` は 4。値が空の null は 0)。YAML の引用符なしのスカラーの書かれた文字は、入力の文字列の、スカラーの開始(アンカーを前置していれば、その後ろ。第 13.2 節)から、構文イベントの `End.Index` までの部分文字列(`string.Substring`、または `AsSpan`)である。複数行にまたがるときは、途中の改行とインデントを含む。この点の境界は、実用上差が出る入力が 16 MiB 付近の複数行スカラーに限られる(未確認)。エイリアスの参照のたびに、参照先のスカラーの大きさを足す。マージキー `<<` は 2 バイト。**16 MiB ちょうどは受理**し、1 バイト超えると失敗する。複製・確保の**前**に確認すること(巨大な展開でメモリを使い果たさないために必要)。大きさの合計は `long`(または `ulong`)で持ち、`int` の桁あふれを起こさない(加算は、上限との比較を先に行ってから足す)。なお、ファイルの大きさの上限(1 MiB)により、展開のない入力が 16 MiB に達することはない。この上限が働くのは、アンカーとエイリアスで展開が増える場合だけである。
- **入れ子の深さの数え方**: マップとリストは、それぞれ**1 段**と数える。スカラーは数えない。**根のマップそのものは数えない**。根の直下のコレクションの深さを 1 とし、その子のコレクションは 2、…と数える。**32 段まで受理**し、**33 段目を拒否する**。数えるのは、**展開後の木**(アンカーの入れ子による深さを含む)に対して。失敗の行は、33 段目になったコレクションの位置(第 13 節)。YAML のフロー形式でもブロック形式でも同じに数える。
  - 例: `a: [[[...]]]`(`[` が n 個)は n 段。32 個は受理、33 個は拒否。JSON の `{"a": [[[...]]]}` も同じ。`a: {b: {b: ... 1}}` も、`{` の数が 32 まで受理、33 で拒否。
  - 例: ブロックのリスト `- - - ... x`(`- ` が n 個)は、根がリストでなくマップの値として置くなら n 段(`a:` の次の行から置く)。
  - 例: アンカーの入れ子 `l0: &l0 [x]`、`l1: &l1 [*l0]`、… の `l(k)` は、展開後に k + 1 段になる。`l31` まで(32 段)は受理、`l32`(33 段)は拒否(これらのキーが、`unknownKey` でない場所に置かれているときの話。深さの検査は Walk より先に行うので、根のキーの種類は関係ない)。
- 上限超過の失敗は、いずれも段階 3 の 1 件の打ち切り(`tooLarge`/`syntax`)で、複数は返さない。同じ入力に複数の上限の超過があれば、入力に現れる順で最初のもの。
- どの上限にも、**30 秒以内に**(巨大な展開でも)到達して終わること(必須)。第 7.4 の対策を含めて、実装時に、第 7.5 の敵対的な入力で測る(未確認: 実測は未実施)。

### 6.4 深い入力と異常終了の禁止

- 数千〜数十万段の入れ子の入力(フロー形式の `[[[[...`、ブロックのリストの `- - - ...`、深いインデントの入れ子)でも、プロセスが異常終了せず、`syntax` の 1 件で返らなければならない(必須)。理由が ``入れ子が深すぎます(上限は 32 段)`` か ``YAML の文法に誤りがあります`` かは、実装に任せてよい。
- **`StackOverflowException` は、`try`/`catch` で捕まえられず、プロセスが終了する**(第 4.6 の 2 の出典)。だから、木の走査、深さの数え、木の破棄以外のすべての再帰処理を、明示のスタックにする。`RuntimeHelpers.EnsureSufficientExecutionStack()` で、再帰の前に確かめる方法(`InsufficientExecutionStackException` を投げる)は、補助としてなら使ってよいが、**これだけに頼らない**(この API の仕様は、この文書の範囲では未確認)。別のスレッドを大きなスタックで立てて再帰する方法は採らない(深さは、入力の大きさだけ増える)。
- JSON は自前の読み取りなので、明示のスタックで読む(第 4.6 節)。
- YAML は、構文イベントの読み取り(`Parser`)が、メソッドの再帰を使うかは、**未確認**(`Parser.cs` は、状態の列挙とスタック(`states`)で進む、libyaml 型の状態機械と考えられる)。実装時に、1 MiB の `- ` の連続(524,288 個の入れ子)、`[` の連続、`{a: ` の連続を、第 7.5 #4 で確かめる。**確認(ソース)**: `Scanner` は、単純キーの候補をスタックで持ち、トークンを 1 つ取り出すたびに、**候補の全部を調べる**(`Scanner.cs` の古くなった単純キーを調べる箇所。`key.Index + maxKeySize < cursor.Index` の判定を含む)。フロー形式の入れ子が深いと、候補が入れ子の数だけ溜まり、**入れ子の深さに応じて極端に遅くなる**可能性がある(未確認: 実測)。そこで、**読み取りの途中の入れ子の深さ(開いているコレクションの数。構文イベントの開始で +1、終了で -1)が 1,000 を超えた時点で、読み取りを打ち切り、`syntax`(理由 ``入れ子が深すぎます(上限は 32 段)``、行は 1,001 段目のコレクションの位置の行)にする**(この文書の決定。他の言語版と同じ値)。ただし、それ以前に段階 3 の深さの失敗(33 段目)が記録されていれば、それを返す(第 2.2 節の、最初の誤りを覚えておく手順)。この打ち切りは、33〜1,000 段の入力には影響しない(それらは、最後まで読み、後ろの文法の誤りを優先する)。1,001 段以上の入力は、後ろに文法の誤りがあっても、深さの失敗を返す(この点が、JSON の規定(深さが後。第 4.6 節)と違う)。
- ライブラリの呼び出しは、`YamlException`(`SyntaxErrorException`、`SemanticErrorException` を含む基底)と、`ArgumentException`、`ArgumentOutOfRangeException`、`InvalidOperationException`、`FormatException`、`OverflowException`、`IndexOutOfRangeException`、`NullReferenceException`(ライブラリの不具合の防御)を、すべて捕まえて、`syntax`(`YAML の文法に誤りがあります`)にする(`catch (Exception ex) when (ex is not OutOfMemoryException)` の形でよい。`OutOfMemoryException` は、捕まえずに、最上位の想定外の失敗の処理([10. エラーと終了コード](10-errors-and-exit-codes.md))に任せる)。

### 6.5 変換器との違い

[09. 変換器](09-converter.md)は、この節の上限と数え方をそのまま使う。変換器だけが、範囲外の数(`HugeIntNode`、`Overflow` の浮動小数)と NaN・∞ を、拒否する。定義の読み込みは、拒否しない。

### 6.6 JSON の段階 3

JSON には、タグ、アンカー、マージキーがないので、段階 3 は、第 6.3 節の上限の確認(木を深さ優先・入力に現れる順に走査して、第 6.2 節の 5 と同じ順で確認する)と、最上位の確認(次の 6.7)だけである。重複キーと文法の誤りは段階 2 で済んでいる。

### 6.7 最上位の確認

| 入力 | 結果 |
|------|------|
| 最上位がマップ | 次へ |
| YAML で、文書が 0 個、または最上位が null | 空のマップとして次へ(段階 4 で `versionMissing`) |
| それ以外(リスト、スカラー。JSON の `null` を含む) | `typeMismatch`、理由 ``最上位はマップで書きます``、行は最上位のノードの位置 |

## 7. YAML ライブラリの選定と、追加で実装すること

### 7.1 方針

YAML は .NET の BCL にないので、外部のライブラリを使う(実行時の依存は、この YAML ライブラリ 1 つだけ。JSON は第 4.6 節の自前の読み取りで、BCL だけで済む。[02. アーキテクチャ](02-architecture.md))。**選定の基準**は次のとおり。

| 基準 | 内容 |
|------|------|
| 位置 | エラーの行と、各ノードの位置を取れる(構文イベントに、入力中の位置が付く) |
| 構文イベントの API | ノードの種別、スタイル(引用符・ブロック・フロー)、アンカー、エイリアス、明示のタグの有無を、型に落とさずに取れる(重複キー、非文字列キー、タグ、複数文書を、自前で拒否するため)。値を .NET のオブジェクトに組み立てる前の段階(構文イベントの列)を取り出せる(低水準の API) |
| 複数の文書 | 入力に文書がいくつあるかを、数えられる |
| 重複キー・非文字列キー | ライブラリが拒否しなくてよい(自前で検出できる)。ライブラリの検査を、使わずに済む |
| アンカーの展開 | 展開をライブラリに任せず、自前で上限を数えながら展開できる(アンカーとエイリアスを参照のまま取れる。アンカーの再定義を、ライブラリが拒否しない) |
| 型の解決 | ライブラリの型の解決を使わずに、自前で YAML 1.2 のコアスキーマに沿った判定ができる(スカラーを、書かれた文字列のまま取れる) |
| リフレクションとトリミング | 構文イベントの読み取りが、リフレクションに頼らない。または、トリミング・NativeAOT の警告が出ない(出ても、使う範囲が安全と確かめられる) |
| 保守 | 保守が続いている(実装時に、直近の更新と、報告された不具合の状況を確認する) |
| 依存 | 依存が少ない(実行時に、ほかのパッケージを要しない) |
| 配布 | NuGet のパッケージ。対象の .NET(最新の LTS と、1 つ前の LTS)で動く。ライセンスが、配布に差し支えない |

### 7.3 ライブラリの呼び出しと設定

読み取りは、BOM を取り除き、第 5.1 節の事前の確認(CR だけの改行、U+0085・U+2028・U+2029、制御文字)を済ませた文字列に対して、次のように呼ぶ。

| 項目 | 値 | 理由 |
|------|----|------|
| 構築 | `var scanner = new Scanner(new StringReader(text), skipComments: true, maxKeySize: 1024); var parser = new Parser(scanner);` | 構文イベントを、`parser.MoveNext()` で 1 つずつ取り出し、`parser.Current`(`ParsingEvent?`)で読む。値を .NET のオブジェクトに組み立てない。**入力の文字列(`StringReader`)を渡す**(バイト列やファイルを渡さない。符号化の判定がライブラリに移るため)。ライブラリは、取り出すまで読み進めない(未確認。`MoveNext` の遅延評価) |
| スカラーの型 | 付けない | `Scalar.Value` を、書かれた文字の `string` として受け取る。型は、実装が第 5.2 節で決める |
| 位置 | `ev.Start.Index`、`ev.End.Index` | 入力の文字列の**添字(UTF-16 のコード単位)**。`ev.Start.Line`・`ev.Start.Column` は**使わない**(NEL・LS・PS・CR だけの改行も改行として数えるため。第 13.1 節)。実装が、LF の位置の表(`int[]`)を作り、添字から行・列を二分探索で求める。`Mark.Index` は `long` なので、`int` に狭める前に、入力の長さの範囲(`text.Length` 以下)を確かめる |
| 高水準の API | 使わない(`YamlStream`、`YamlDocument`、`Deserializer`、`DeserializerBuilder`) | 値の組み立て、アンカーの再定義の扱い、制御の外の上限、リフレクション |
| 警告 | 出ない | ライブラリは、`Console` に何も書かない(未確認) |

- 構文イベントの読み取りで、文書の中身の誤りは、例外(`YamlException` の派生の `SyntaxErrorException`、`SemanticErrorException` など)として投げられる(確認: `Scanner.cs`、`Parser.cs` の `throw`)。実装は、これらと、第 6.4 節の例外を、読み取りの呼び出しの外側(`try`)で捕まえる(第 7.4 #11)。
- 例外から行を得る: `YamlException.Start`(`Mark`)の `Index` を、LF の表で行にする。**`Start` が `Mark.Empty`**(`Index` が 0、`Line` が 1、`Column` が 1。確認(出典: `Mark.cs`))のときは、位置を持たない例外(`new SyntaxErrorException(message)` と `new YamlException(message)` は、`Mark.Empty` を使う。タブのインデントの例外がこれ)なので、`scanner.CurrentPosition.Index`(例外の時点の読み取り位置。ライブラリは先読みをするので、原因の位置より後ろになりうる。未確認)を使う。どちらでも、**行は、ライブラリが返すものでよい**(第 13.4 節)。例外が行を持たない(`ArgumentException` など)場合は、行なし。
- 位置の確認は、第 13 節。例外の文(英語)は、利用者に見せない(第 7.4 #10)。

### 7.4 ライブラリだけでは足りないので、追加で実装すること

次は、いずれも**必須**である(利用者から見える結果が、この文書の規定と一致するために必要)。

| # | 追加で実装すること | 理由・確認 |
|---|--------------------|--------------------|
| 1 | 入力のすべての文書を読み、文書の数を数える(第 5.6 節) | `DocumentStart` のイベントを数える。文書が 0 個の入力(空、コメントだけ)は、そのイベントが出ない(未確認) |
| 2 | **スカラーの型の判定を自前で行う**(第 5.2 節) | ライブラリの型の解決は使わない。YAML 1.1 の型の混入を避けるため。`Scalar` イベントは、そもそも型を持たない(確認) |
| 3 | **明示のタグの検出**(第 5.1 節) | 各 `NodeEvent` の `Tag.IsEmpty` が偽なら、明示のタグがある(確認(出典: `Parser.cs`。タグのトークンがあるときだけ `tagName` を作る))。スカラー(`a: !!str 1`)、フローとブロックのマップ・リスト、キーのスカラー(`? !!str a`)、文書の根(`--- !!str` + 改行 + `foo`)、空の値(`a: !!str`)、`%TAG` で定義した名前(`!e!foo`)、`!<tag:yaml.org,2002:str>` のすべてで検出できるか: **未確認**(受け入れ試験 #2)。タグが無い要素の `Tag` は `TagName.Empty`(確認)。**`!`(非特定のタグ)単独は、`TagName` の構築が例外を投げうる**(`Parser.cs` は `new TagName(tag.Suffix)` を呼ぶ。空の接尾辞での挙動は**未確認**)。例外が出た場合は、第 6.4 節の捕捉で `syntax`(`YAML の文法に誤りがあります`)になり、理由が ``タグは使えません`` と違うだけである(許容する。この 1 入力だけの差) |
| 4 | **重複キーの検出**(第 5.4 節) | マップごとの `HashSet<string>`。構文イベントの読み取りは、重複を調べない |
| 5 | **段階 2 を優先するための、「最初の誤りを覚えて、最後まで読み進める」手順**(第 2.2 節) | 段階 3 の最初の誤りを記録し、以降の木の組み立てを止めて、読み取りだけを最後まで進める。読み取りの途中で例外が出たら、記録を捨てて、その例外の `syntax` を返す。**全文書の構文イベントを、一度にリストに溜めない**(巨大な入力でメモリを使うため) |
| 6 | **アンカーとエイリアスの展開**、未定義・前方参照の検出、再帰の検出、上限の確認(第 5.3・6.3 節) | 構文イベントの列は、エイリアスを参照のまま持つ(`AnchorAlias` は名前だけ) |
| 7 | **マージキーの展開**(第 5.5 節) | `<<` は、`Style` が `Plain` で値が `<<` の通常の `Scalar` として返ると考えられる(未確認) |
| 8 | **位置の補正**(第 13 節): アンカー(とタグ)を前置したノードの位置を、内容の位置に直す。ブロックのマップの位置(最初のキーの位置。明示のキー `? a` のときは、`?` ではなくキーの位置)。値が省略された対の値の位置(キーの位置)。`---` だけの文書の根の位置。展開したノード、マージで取り込んだエントリの位置の置き換え | ライブラリの構文イベントの位置は、アンカー・タグを前置したノードでは、アンカー・タグの先頭を指す(libyaml 型の実装の一般的な挙動。YamlDotNet では**未確認**)。第 13.2 節の補正の手順は、すでに内容を指している位置に適用しても、位置が動かないように書いてあるので、どちらの場合でも安全である |
| 9 | **ライブラリの文法の誤りを `syntax` に変換**し、行を取り出す(第 7.3 節) | 閉じていないフローの誤りなどは、原因の行より後ろ(次の行、入力の末尾)で検出される(第 13.4 節) |
| 10 | ライブラリの誤りの文(英語)は、利用者に見せない(理由は固定の ``YAML の文法に誤りがあります``) | 入力の値や、ライブラリの文面を、エラーに出さない規則のため |
| 11 | ライブラリの呼び出しで投げられた例外(第 6.4 節)を捕捉して `syntax` にする | 異常終了の禁止 |

## 8. 書式の版(VersionCheck)

根の `format_version` を確認する。

| 状況 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `versionMissing` | なし | `` `format_version` が必要です(対応する版は 1 です) `` |
| 整数でない(文字列、浮動小数、真偽値、null、リスト、マップ。`1.0`、`1e0` を含む) | `versionUnsupported` | 値の位置の行 | `` `format_version` は整数で書きます(対応する版は 1 です) `` |
| 整数だが 1 でない(0、-1、2、9、範囲外の整数) | `versionUnsupported` | 値の位置の行 | `この版には対応していません(対応する版は 1 です)` |

- 対応する版は **1 だけ**。`format_version: 1` を受理する。YAML の `0x1`、`01`、`+1` でも、値が 1 なら受理する(JSON では `1` だけ)。判定は、ノードが `IntNode` で、値が `1` であること(真偽値は `BoolNode` で整数ではないので、`format_version: true` は「整数でない」の行になる)。
- 版が 1 のとき、取り込み後の定義の `format_version` は 1 になる。

## 9. 定義の構造(Walk)

以降の「マップ」「リスト」は、木の型(第 6.1 節)である。**キーの型**は、すべて `string`(第 5.4 節・第 4.1 節で保証)。位置の取り方は第 13 節。

根のマップは、次のキーだけを持てる。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `format_version` | 整数 | 必須 | 第 8 節 |
| `pipeline` | マップ | 必須 | 第 9.1 節 |
| `job` | マップのリスト | 必須(1 つ以上) | 第 9.2 節 |

許されていないキー(上の 3 つ以外)は、`unknownKey` である。`jobs`(複数形)も未知のキーとして拒否される(``キー `jobs` は定義にありません``)。`unknownKey` の理由は、`` キー `<キー名>` は定義にありません `` の形(`<キー名>` は整形したキー名)で、キー名の整形は第 12.2 節。位置はそのキーの位置。値の型は問わない(null でも、アンカーの参照でも同じ)。

### 9.1 `pipeline`

| キー | 型 | 必須 | 既定値 | 検査 |
|------|----|------|--------|------|
| `name` | 文字列 | 必須 | なし | 空白だけ(trim して空)なら `emptyField` |
| `description` | 文字列 | 任意 | なし | 型だけ |
| `run_id_env` | 文字列 | 任意 | なし(実行時の既定は環境変数 `CONDUCTOR_RUN_ID`) | 名前の形(下記) |
| `remove_on_complete` | 真偽値 | 任意 | `false` | 型だけ |

- 許されたキー以外は `unknownKey`(例: `owner`、`remove_on_complet`)。
- `name` が無い: `typeMismatch`、行は `pipeline` のマップの位置、理由 ``必須の値 `name` がありません``。文字列でない(null を含む): `typeMismatch`、値の位置、理由 `` `name` は文字列で書きます ``。`description` が文字列でない: `typeMismatch`、値の位置、理由 `` `description` は文字列で書きます ``。`run_id_env` が文字列でない: `typeMismatch`、値の位置、理由 `` `run_id_env` は文字列で書きます ``。`remove_on_complete` が真偽値でない: `typeMismatch`、値の位置、理由 `` `remove_on_complete` は真偽値(`true` または `false`)で書きます ``。
- `name` が空白だけ: `emptyField`、`name` の値の位置、理由 `` `name` が空です ``(名前の照合はしない)。
- `run_id_env` の名前の形の誤り: `invalidEnvName`、値の位置、理由 `` `run_id_env` は、英字または `_` で始まり、英数字と `_` だけの名前で書きます ``。
- `run_id_env` の名前の形: 1 文字以上で、先頭が ASCII の英字(`A-Za-z`)または `_`、2 文字目以降が ASCII の英数字(`A-Za-z0-9`)または `_`。照合は、**自前の文字の走査**で行う(先頭は ASCII の英字か `_`、2 文字目以降は、それに ASCII の数字を足したもの。`c is (>= 'A' and <= 'Z') or (>= 'a' and <= 'z') or '_'` のように書く)。`Regex` を使うなら `\A[A-Za-z_][A-Za-z0-9_]*\z` と書く(**`^…$` は使わない**。確認(出典: 正規表現のアンカーの公式ドキュメント): `$` は末尾の `\n` の直前にも一致し、`"A\n"` が通ってしまう。`\w`、`char.IsLetterOrDigit`、`char.IsLetter` も使わない。非 ASCII を受理するため)。受理: `A`、`_`、`_a1`、`GITHUB_RUN_ID`。拒否(`invalidEnvName`): `""`、`1A`、`A-B`、`A B`、`A=B`、`é`、`A.B`、NUL を含む文字列、`A` + 改行。文字列でない値(整数など)は `typeMismatch`。誤りの文に、値は含めない。
- `remove_on_complete` は真偽値だけ(`true` / `false`、YAML では `True`、`TRUE` なども)。文字列 `"true"`、`yes`(文字列)、整数 `1`、リスト `[true]` は `typeMismatch`。判定は、ノードの種別が `BoolNode` であること(整数の `1` は `bool` ではない)。型が違うときの値は、`false` として扱って続行する(誤りは報告済み)。
- `pipeline` の形:
  - 無い: `typeMismatch`、行は **1 行目**(位置 (1, 1))、理由 ``必須の値 `pipeline` がありません``。
  - リスト: `typeMismatch`、リストの位置、理由 `` `pipeline` は 1 つだけで、マップで書きます(1 ファイルに 1 パイプライン) ``。
  - その他(整数、文字列、null など): `typeMismatch`、値の位置、理由 `` `pipeline` はマップで書きます ``。
  - 上の誤りのとき、`pipeline` の中身の検査は行わない。
- 名前の照合: `expected_pipeline_name` が与えられ、定義の `name` と**完全に同じでない**(大文字小文字・空白も区別。`string.Equals(a, b, StringComparison.Ordinal)` が偽)と、`pipelineNameMismatch`、行は `name` の値の位置、理由 ``指定されたパイプライン名が、定義の `name` と一致しません``。理由に両方の名前は含めない。`name` が空白だけのときは、`emptyField` だけを返し、照合はしない。`name` が文字列でない・無いときも、照合はしない。

### 9.2 `job`

`job` は、マップのリストでなければならない。

- 無い: `noJobs`、行は 1 行目(位置 (1, 1))、理由 ``ジョブ(`job`)が 1 つもありません``。
- 空のリスト(`job: []`): `noJobs`、行は `job` の値の位置。
- リストでない(マップ、整数、null など): `typeMismatch`、値の位置、理由 `` `job` はマップのリストで書きます ``。
- リストの要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `job` の要素はマップで書きます ``(その要素の検査は行わない)。

各ジョブ(マップ)のキー:

| キー | 型 | 必須 | 既定値 | 説明 |
|------|----|------|--------|------|
| `id` | 文字列 | 必須 | なし | ジョブID。第 11.1 節の検査 |
| `command` | 文字列、または文字列のリスト | 必須 | なし | 第 9.3 節 |
| `warning_exit_codes` | 整数のリスト | 任意 | 空(`[]`) | 警告にする終了コード |
| `success_exit_codes` | 整数のリスト | 任意 | 省略(意味は `[0]`) | 成功にする終了コード |
| `transitions` | マップのリスト | 任意 | 空 | 第 9.4 節 |
| `retry` | マップ | 任意 | なし | 第 9.5 節 |

許されたキー以外は `unknownKey`(例: `warn_exit_codes`)。

- `id` が無い: `typeMismatch`、行はジョブのマップの位置、理由 ``必須の値 `id` がありません``。文字列でない: `typeMismatch`、値の位置、理由 `` `id` は文字列で書きます ``。
- 終了コードのリスト(`warning_exit_codes` と `success_exit_codes`):
  - リストでない(null を含む): `typeMismatch`、値の位置、理由 `` `<キー名>` は整数のリストで書きます ``(`<キー名>` は実際のキー名)。
  - 要素が整数でない、または 32 ビット符号つき整数の範囲(-2,147,483,648〜2,147,483,647)に収まらない: 要素ごとに `typeMismatch`、その要素の位置、理由 `` `<キー名>` の要素は、整数(32 ビットの範囲)で書きます ``。1 つでも誤りがあれば、そのキー全体を「無効」として扱い、後続の重なりの検査では使わない。範囲の判定は、`IntNode` の値(`long`)で行う(`v >= int.MinValue && v <= int.MaxValue`)。取り込み後の値は `int` に落とす(範囲内なので、落としても値は変わらない)。
  - 負の値(例: `-1`)は、その範囲なので**受理**する。重複した値も受理し、除かない(書いた順のまま保持する)。空のリストも受理する(`success_exit_codes: []` は、成功にする終了コードが無い、の意味になる)。
  - 整数は、YAML の `0x1F`、`0o17`、`+3`、`007` でもよい(値で判定する)。JSON は 10 進の整数だけ。
- `success_exit_codes` を省略すると、成功の終了コードは `[0]`。書いたら、**書いた値だけ**が成功(`0` を書かなければ 0 でも成功にならない)。
- 要素が浮動小数(`1.0`、`1e0`)や、範囲外の整数(`99999999999999999999`、種別 `hugeInt`)、真偽値(`true`)のときも、要素の型の誤り(`typeMismatch`)になる。

### 9.3 `command`

| 書き方 | 受理の条件 | 保持される値 |
|--------|-----------|---------------|
| 文字列 | trim して空でない | 1 本の文字列(そのまま。trim した値ではない) |
| 文字列のリスト | 空でないリストで、全要素が文字列で、**先頭の要素が trim して空でない**。2 番目以降の要素は空文字列でもよい | 要素の並び(そのまま) |

どちらの書き方かは、取り込み後も区別して保持する(実行側の解釈が異なる。[05. 実行フロー](05-execution-flow.md)・[07. プロセスとシグナル](07-process-and-signals.md))。

誤り:

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| キーが無い | `typeMismatch` | ジョブのマップの位置 | ``必須の値 `command` がありません`` |
| 文字列が空または空白だけ | `emptyField` | 値の位置 | `` `command` が空です `` |
| リストが空 | `emptyField` | 値の位置 | `` `command` の配列が空です `` |
| リストに文字列でない要素がある | `typeMismatch`(要素ごと) | その要素の位置 | `` `command` の配列の要素は、文字列で書きます `` |
| リストの先頭の要素が空または空白だけ(全要素が文字列のとき) | `emptyField` | 先頭の要素の位置 | `` `command` の配列の先頭の要素が空です `` |
| 文字列でもリストでもない(整数・真偽値・マップ・null) | `typeMismatch` | 値の位置 | `` `command` は文字列、または文字列の配列で書きます `` |

- リストに型の誤りの要素があるときは、先頭要素の空の検査はしない。
- 受理の例(YAML): `command: echo x`、`command: ["my prog", "a b", "$HOME", ""]`、`command: [echo, ""]`。拒否の例: `command: 5`、`command: true`、`command: {a: 1}`、`command: ["a", 5]`、`command: [[a]]`(`typeMismatch`)、`command: ""`、`command: "   "`、`command: []`、`command: [""]`、`command: ["  ", x]`(`emptyField`)、`command:`(値なしは null。`typeMismatch`)。
- 文字列の `command` の中の引用符・`$` などは、この段階では解釈しない(実行時の解釈は実行側の仕様)。YAML の引用符なしの複数行のスカラーは、折りたたまれた 1 つの文字列(改行が空白 1 個になる)になるが、書き方による値の違いは、そのまま保持する。
- 理由の文言(`の配列` という語)は、リストを指す(日本語の原文として固定する。`リスト` に言い換えない)。
- 誤りの文に、入力の値は含めない。

### 9.4 `transitions`

`transitions` は、マップのリスト(YAML のブロックの `- on: success` の繰り返し、またはフロー形式 `[{on: success, next: b}]`、JSON の配列)。

| キー | 型 | 必須 | 説明 |
|------|----|------|------|
| `on` | 文字列 | 必須 | `success` または `warning` |
| `next` | 文字列 | 必須 | 遷移先のジョブID、または `@end` |

- 許されたキー以外(`when` など)は `unknownKey`。
- `transitions` がリストでない(null を含む): `typeMismatch`、値の位置、理由 `` `transitions` はマップのリストで書きます ``(遷移は空として扱う)。要素がマップでない: `typeMismatch`、その要素の位置、理由 `` `transitions` の要素はマップで書きます ``。
- `on` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `on` がありません``。文字列でない: `typeMismatch`、値の位置、`` `on` は文字列で書きます ``。
- `on` の値: `success`、`warning` を受理。`error` は `errorTransition`、値の位置、理由 ``エラー結果(`error`)には遷移先を書けません``。それ以外の文字列(`later`、大文字の `Success` など)は `typeMismatch`、値の位置、理由 `` `on` は `success` または `warning` で書きます ``。YAML のキー `on` は、YAML 1.1 の真偽値ではなく、文字列のキー(`on`)として読まれる(第 5.2 節)。
- `next` が無い: `typeMismatch`、遷移のマップの位置、理由 ``必須の値 `next` がありません``。文字列でない: `typeMismatch`、値の位置、`` `next` は文字列で書きます ``。
- 同じ `on`(`success` どうし、`warning` どうし)の遷移が 2 つ以上: 2 つ目以降の遷移に `duplicateTransition`、行は**その遷移(マップ)の位置**、理由 ``同じ結果(`on`)の遷移が 2 つ以上あります``。`success` と `warning` を 1 つずつは受理。`on` が不正(`error` や未知の値、型の誤り)の遷移は、重複判定に入れない。
- 遷移先の存在・順序の検査は、第 11 節。

### 9.5 `retry`

ジョブが決めた終了コードで終わったときに、待って実行し直す設定。書き方は、ブロックのマップでもフローのマップでも、JSON のオブジェクトでもよい。

許されたキーは次の 5 つだけ。それ以外は `unknownKey`(例: `retries`)。

| キー | 型 | 必須 | 範囲・書式 | 取り込み後 |
|------|----|------|-----------|-------------|
| `exit_codes` | 整数のリスト | 必須 | 空でない。各要素は 1 以上 255 以下の整数 | 昇順に並べ、重複をまとめる(`[75, 3, 75, 3, 12]` → `[3, 12, 75]`) |
| `max` | 整数 | 必須 | 1 以上 100 以下 | `int`(1〜100) |
| `interval` | 文字列 | 必須 | `<整数><s\|m\|h>`、1 秒以上 24 時間以下 | 秒(`ulong`。1〜86,400) |
| `multiplier` | 整数 | 任意 | 2 以上 10 以下 | `int`、または無し(`null`) |
| `max_interval` | 文字列 | 任意 | `interval` と同じ書式、`interval` 以上 | 秒(`ulong`)、または無し(`null`) |

- 127 などの値も受理する(`[127, 1]` → `[1, 127]`)。並べ替えは、数値の昇順(`codes.Distinct().OrderBy(c => c)`。要素は `int` なので、数値で並ぶ。文字列の比較にしない)。
- `multiplier` と `max_interval` は、**両方を書くか、両方とも書かない**か。片方だけなら `retryBackoffIncomplete`。両方なしなら、待ち時間は毎回 `interval`。
- 取り込み後の秒数は、`ulong` で、最大でも 86,400。**待ち時間の計算(倍率の累乗、上限、64 ビット符号なし整数の飽和)は、[05. 実行フロー](05-execution-flow.md)の規定に従う**(`ulong` と `Math.BigMul`(または `UInt128`)で計算し、`checked` で例外にせず、飽和させる。折り返さない)。ここ(読み込み)では、桁あふれは起きない(最大 86,400)。

#### 間隔の文字列の書式

- 文字列の最後の 1 文字が単位(`s`=秒、`m`=分=60 秒、`h`=時間=3600 秒。小文字だけ)。その前が、**ASCII の数字(0〜9)だけ**の 1 文字以上の列(符号・空白・小数点・`_`・全角数字・16 進(`0x`)は不可)。照合は、**自前の文字の走査**で行う(最後の 1 文字が `s`、`m`、`h` のどれか、その前の全文字が `c is >= '0' and <= '9'`)。`Regex` を使うなら `\A[0-9]+[smh]\z` と書く(**`\d` を使わない**: 確認(出典: 正規表現の文字クラスの公式ドキュメント)で、`\d` は Unicode の 10 進数字に当たり、全角数字 `１` に一致しうる。`^…$` も使わない。第 9.1 節と同じ)。`int.Parse`、`long.Parse` の既定の書式は、符号や空白を受け付けるので、使わない。
- 数値は 1 以上。秒に換算した値が 1 以上 86,400(24 時間)以下。桁あふれ(64 ビット符号なし整数に収まらない、または換算の乗算があふれる)は拒否。先頭の 0 は何個並べてもよい(`0000000000000000000000000001s` は値 1 で受理)。値が 86,400 秒を超えるものは、桁数にかかわらず拒否する。**判定は `long` で行う**(数字の列を、自前の繰り返しで `long` にして、単位の倍率を掛けて、1 以上 86,400 以下かを調べる)。巨大な桁数の字句で、時間を使わず、桁あふれを起こさないために、先頭の 0 を除いた数字の桁数が 5 を超えるものは、数値化せずに範囲外とする(6 桁以上の数は 100,000 以上で、単位が `s` でも 86,400 を超えるので、結果は同じ)。5 桁以下だけ数値化すればよい(`99999 * 3600` は `long` に収まる)。
- 受理: `1s`、`30s`、`5m`、`2h`、`24h`、`1440m`、`86400s`、`01s`(値 1)。拒否: `""`、`s`、`10`、`1.5s`、`-1s`、`+1s`、` 1s`、`1s `、`1 s`、`1d`、`1S`、`１s`、`1ms`、`0x10s`、`1_0s`、`0s`、`0h`、`86401s`、`25h`、`99999999999999999999999s`、`18446744073709551615h`。文字列でない値(整数・真偽値・null)も拒否。
- YAML では、`interval: 30s` のように引用符なしで書いた `30s` は文字列、`interval: 30` は整数なので拒否。`interval: 0x10s` は文字列だが、書式に合わないので拒否(`retryDurationInvalid`)。

#### 誤りと検査

| 条件 | `kind` | 行 | 理由 |
|------|--------|----|------|
| `retry` がマップでない(整数、文字列、リスト、null) | `retryNotTable` | `retry` の値の位置(リストのときは、リストの位置) | `` `retry` はマップで書きます `` |
| 必須のキー(`exit_codes`、`max`、`interval`)が無い | `retryMissingKey`(欠けたキーごとに 1 件) | `retry` のマップの位置 | ``必須の値 `<キー名>` がありません`` |
| `exit_codes` がリストでない | `retryExitCodeInvalid` | 値の位置 | `` `exit_codes` は整数の一覧で書きます `` |
| `exit_codes` が空のリスト | `retryExitCodesEmpty` | 値の位置 | `` `exit_codes` が空です `` |
| `exit_codes` の要素が整数でない、32 ビットの範囲外、1〜255 の範囲外(0、256、-1、1.5、`"75"`、`true` など) | `retryExitCodeInvalid`(要素ごと) | その要素の位置 | `` `exit_codes` の要素は、1 以上 255 以下の整数で書きます `` |
| `max` が整数でない、または 1〜100 の範囲外(0、101、-1、1.5、`"3"`、`true`) | `retryMaxInvalid` | 値の位置 | `` `max` は、1 以上 100 以下の整数で書きます `` |
| `interval` / `max_interval` が書式・範囲に合わない | `retryDurationInvalid` | 値の位置 | `` `<キー名>` は、整数と単位(`s`、`m`、`h`)で、1 秒以上 24 時間以下に書きます(例: `30s`) ``(`<キー名>` は `interval` か `max_interval`) |
| `multiplier` が整数でない、または 2〜10 の範囲外(1、11、0、-2、`2.0`、`"2"`、`true`) | `retryMultiplierInvalid` | 値の位置 | `` `multiplier` は、2 以上 10 以下の整数で書きます `` |
| `multiplier` と `max_interval` の片方だけがある | `retryBackoffIncomplete` | `retry` のマップの位置 | `` `multiplier` と `max_interval` は、両方を書くか、両方とも書きません `` |
| `exit_codes` に、そのジョブの成功または警告の終了コードと同じ値がある | `retryExitCodesOverlap` | `exit_codes` の**キー**の位置 | `` `exit_codes` に、成功または警告の終了コードと同じ値があります `` |
| `max_interval` が `interval` より小さい(秒で比べる。等しければ受理) | `retryMaxIntervalTooSmall` | `max_interval` の値の位置 | `` `max_interval` は、`interval` 以上で書きます `` |

- 整数の判定は、`IntNode`(`long` の値)で行う。範囲外の整数(`hugeInt`)と真偽値は、範囲外の誤りと同じ扱い。
- 空のマップ(`retry: {}`)は、`retryMissingKey` が 3 件(`exit_codes`、`max`、`interval` の順)返る(行はすべて同じ。マップの位置は、フロー形式では `{` の位置)。
- `exit_codes` の複数の要素が不正なら、不正な要素ごとに 1 件(例: `[0, 75, 256]` は 2 件)。
- **重なりの検査**(`retryExitCodesOverlap`)は、定義の他の値と照合する。`exit_codes` が有効(エラーなし)のときだけ行う。
  - 成功の終了コード: `success_exit_codes` を**書かなければ `[0]`**。書いて有効なら、その値。書いたが誤り(無効)のときは、成功との重なりを調べない(警告との重なりは調べる)。
  - 警告の終了コード: `warning_exit_codes` が有効なら、その値(無効なら調べない)。
  - どちらかと 1 つでも共通する値があれば、1 件(重なりの値の数にかかわらず 1 件)。
  - 例: `success_exit_codes: [0, 5]` と `exit_codes: [5, 75]` は誤り。`success_exit_codes: [3]` と `exit_codes: [3]` も誤り。`success_exit_codes: [0, 5]`、`warning_exit_codes: [4]`、`exit_codes: [75]` は受理。
- `retry` の有無は、ほかのキーの読み取りの結果に影響しない。
- 誤りの文に、入力の値は含めない。
- `retry` のマップの位置は、ブロック形式では**最初のキーの位置**(`retry:` の次の行)であり、`retry` のキーの行ではない(第 13.2 節)。JSON では、`retry` のオブジェクトの `{` の位置である。

## 10. 検査の順序とエラーの集約・並び

Walk の中の処理順(誤りは、見つかった順に集める):

1. 根のキー検査(`unknownKey`)。
2. `pipeline`: キー検査 → `name` → `description` → `run_id_env`(型の誤り、続けて名前の形の誤り) → `remove_on_complete` → `name` の空の検査 → 名前の照合。
3. `job`: 無い/空/型の誤りの処理。リストなら、各ジョブを順に、次の順で検査する: キー検査 → `id` → `command` → `warning_exit_codes` → `success_exit_codes` → `transitions`(各遷移について、キー検査 → `on` → `next` → 重複) → `retry`(キー検査 → `exit_codes` → `max` → `interval` → `multiplier` → `max_interval` → 倍率と上限の片方だけの検査)。
4. 全ジョブにまたがる検査(第 11 節): ジョブIDの検査 → 各ジョブについて、遷移先 → 終了コード(`zeroAsWarning`、`overlappingExitCodes`) → `retry` の重なり・上限と間隔の大小。
5. 誤りが 1 件もなく、`pipeline` とすべてのジョブが組み立てられるときだけ、定義を返す。

返す誤りの順序: すべての誤りを、**位置(行、同じ行なら列)の昇順**に並べて返す。同じ位置のものは、上の検査の順(集めた順)を保つ(**安定な並べ替え**。確認(出典: 公式ドキュメント): `Enumerable.OrderBy` は安定な並べ替えである。`List<T>.Sort` と `Array.Sort` は**不安定**(ドキュメントに、等しい要素の順序が保たれない可能性があると明記されている)なので、**使わない**。`errors.OrderBy(e => e.Line ?? 0).ThenBy(e => e.Column ?? 0).ToList()` とする)。位置の取り方は第 13 節。

- 型の誤りなどで検査できなくなった値は、その値に依存する後続の検査だけを省略する(他の検査は続ける)。
- 位置が (1, 1) の誤りは、行 1 として扱われる(`pipeline` が無い、`job` が無い)。

複数の誤りの例:

```yaml
format_version: 1
unknown_top: true          # 2 行目: unknownKey

pipeline:
  name: p

job:
  - id: a
    command: x
    success_exit_codes: [zero]   # 10 行目: typeMismatch

  - id: b
    command: y
    colour: red              # 14 行目: unknownKey
    transitions:
      - on: success
        next: nowhere        # 17 行目: unknownTarget
```

返る誤り: `unknownKey`(2)、`typeMismatch`(10)、`unknownKey`(14)、`unknownTarget`(17)。確認(試作): 上のとおり。

## 11. ジョブ間の検査

### 11.1 ジョブID

`id` が文字列であるジョブごとに、記述順に検査する。

- trim して空、または先頭が `@` → `invalidJobId`、`id` の値の位置、理由 ``ジョブID(`id`)は、空でなく、`@` で始まらない文字列で書きます``。この ID は、遷移先の索引に入らない(後続のジョブから、遷移先として参照できない)。
- 既出の ID と完全に同じ(大文字小文字・前後の空白も区別。`" a "` と `"a"` は別) → `duplicateJobId`、2 つ目以降の `id` の値の位置、理由 ``同じジョブID(`id`)が、すでに定義されています``。(既出の ID は `HashSet<string>`(`StringComparer.Ordinal`)で調べる。`__proto__` や `constructor` という ID も、通常の文字列として扱う。)
- 長さの上限、使える文字(空白・記号)の制限は、これ以外にない(定義の検査では。実行時の状態ファイル名などへの影響は、[06. ステートファイル](06-state-file.md)による)。

### 11.2 遷移先

`on` と `next` がともに有効な遷移について、`next` を検査する(`on` が不正な遷移は、検査しない)。

- `next == "@end"`: 受理(以降のジョブをスキップして終える)。
- ID の索引に無い(存在しない、または無効な ID): `unknownTarget`、`next` の値の位置、理由 ``遷移先(`next`)のジョブが、定義にありません``。
- 記述順で、自分自身または前のジョブ(位置 ≦ 自分の位置): `backwardOrSelfTarget`、`next` の値の位置、理由 ``遷移先(`next`)は、記述順で後ろのジョブまたは `@end` で書きます``。
- 後ろのジョブの ID は受理する。

### 11.3 終了コード

各ジョブについて(`warning_exit_codes` と `success_exit_codes` が有効なとき):

- `warning_exit_codes` に 0 を含む → `zeroAsWarning`、`warning_exit_codes` の**キー**の位置、理由 ``0 は警告の終了コード(`warning_exit_codes`)にできません``。(`success_exit_codes` の誤りの有無に関わらず検査する。)
- 両方を書き、有効で、共通する値がある → `overlappingExitCodes`、`warning_exit_codes` の**キー**の位置、理由 `` `warning_exit_codes` と `success_exit_codes` に、同じ値があります ``。ただし、共通の値が 0 だけで、すでに `zeroAsWarning` を報告した場合は、重ねて報告しない(例: `warning_exit_codes: [0]` と `success_exit_codes: [0]` は `zeroAsWarning` の 1 件だけ)。
- `success_exit_codes` を書かないとき、成功は `[0]` だが、`warning_exit_codes` との重なりは(書かれていない側は)調べない。警告に 0 を入れた場合は、`zeroAsWarning` で拒否される。

### 11.4 `retry` との関係

第 9.5 節(重なり、上限と間隔の大小)。

## 12. エラーの種類と表示

### 12.1 エラーの構造

型の骨格(例。名前空間 `Conductor.Definition`。種類は `enum ErrorKind`。判別共用体の代わりに、抽象の `record` と `sealed record` の継承階層を使う)。

```csharp
namespace Conductor.Definition;

/// <summary>エラーの種類(31 種。第 12.3 節の表と同じ順)。機械が読む識別子は、IdentifierOf で得る。</summary>
public enum ErrorKind
{
    UnsupportedFormat, FileMissing, Unreadable, TooLarge, Syntax,
    TypeMismatch, UnknownKey, VersionMissing, VersionUnsupported,
    UnknownTarget, ErrorTransition, BackwardOrSelfTarget,
    OverlappingExitCodes, ZeroAsWarning, PipelineNameMismatch,
    DuplicateJobId, InvalidJobId, NoJobs, EmptyField,
    DuplicateTransition, InvalidEnvName, RetryNotTable,
    RetryMissingKey, RetryExitCodesEmpty, RetryExitCodeInvalid,
    RetryExitCodesOverlap, RetryMaxInvalid, RetryDurationInvalid,
    RetryBackoffIncomplete, RetryMultiplierInvalid,
    RetryMaxIntervalTooSmall,
}

public sealed record DefinitionError(
    ErrorKind Kind,
    string File,        // 表示用のファイル名(第 2.1 節)
    int? Line,          // 1 始まり。null は「行なし」
    int? Column,        // 1 始まり。null は「列なし」。順序づけにだけ使い、表示には出さない
    string Reason);     // 固定の文から組み立てた理由(日本語)。入力の値は含めない

public abstract record LoadResult;
public sealed record LoadOk(Definition Definition) : LoadResult;
public sealed record LoadFailed(IReadOnlyList<DefinitionError> Errors) : LoadResult;  // 1 件以上
```

- 種類の識別子(`fileMissing` など。第 12.3 節の「識別子」)は、`enum` の名前の先頭を小文字にしたもの(`FileMissing` → `fileMissing`)である。**`ErrorKind.ToString()` に頼らず、`switch` 式で書いた対応表**(`static string IdentifierOf(ErrorKind kind)`)で得る(名前の変更で、表示がこっそり変わることを避ける。トリミングを使わないので、`ToString()` でも動くが、単体テストで、対応表の全 31 件を確かめる)。
- 種類の文(日本語、英語)も、`switch` 式の対応表(`static string JapaneseTextOf(ErrorKind)`、`EnglishTextOf(ErrorKind)`)で持つ。**単体テスト**: (a) `Enum.GetValues<ErrorKind>().Length` が 31、(b) 全要素で、識別子・日本語・英語が空でなく、識別子が互いに異なる、(c) 識別子が第 12.3 節の表の「識別子」の列と一致する(コンパイラーは、`switch` 式の網羅の警告を出す(`CS8509`)ので、`TreatWarningsAsErrors` で、要素の追加時の書き忘れを防げる)。
- `Line` と `Column` は、`int?`(null 許容の値型)。`record` の等価比較は、`Reason` などの値で行われるので、テストでそのまま比べてよい。`LoadFailed.Errors` の等価は、参照の比較になるので、テストでは、要素ごとに比べる。

| フィールド | 内容 |
|------------|------|
| `File` | 表示用のファイル名 |
| `Line` | 行番号(1 始まり)。位置が決まらないときは無し |
| `Column` | 列番号(1 始まり)。同じ行の中での順序づけのために保持する。**表示には出さない** |
| `Kind` | 種類(第 12.3 節) |
| `Reason` | 固定の文から組み立てた理由。入力の値は含めない。入力由来はキー名だけ(`unknownKey`) |

ライブラリ(読み込み処理の呼び出し側)に返す表示の書式:

```
<file>:<line>: <種類の文>: <reason>      行があるとき
<file>: <種類の文>: <reason>             行が無いとき
```

例: ``conductor.json:7: 定義にないキーです: キー `x` は定義にありません``。ここで `<file>` は、制御文字・書式文字・サロゲート(第 12.2 節と同じ対象)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは、256 文字までで切って末尾に `…` を付ける)。

`conductor` コマンドの標準エラーへの表示は、`conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason>` の 1 行(誤りごとに 1 行、位置の順)で、`reason` は日本語のまま(言語によらない)。種類の文は、メッセージの言語([08](08-output-and-i18n.md))が日本語のとき日本語(第 12.3 節の「日本語」)、それ以外は英語(「英語」)。`<file>` と `reason` は、改行・制御文字・書式文字・サロゲートをエスケープして表示する(`\n`、`\r`、`\t`、その他は `\u{16進小文字}`)。**ここでは文字数で切らない**。例:

```
conductor: error: bad.json:7: unknown key: キー `typo` は定義にありません
conductor: error: conductor.json: definition file does not exist: 指定の場所にファイルがありません
```

定義の誤りがあるときの終了コード(64)と、その標準出力・標準エラーの扱いは、[10. エラーと終了コード](10-errors-and-exit-codes.md)に従う。

### 12.2 キー名の表示

`unknownKey` の理由に入るキー名は、`` ` `` で囲み、次の整形をする。

- 改行を `\n`、復帰を `\r`、タブを `\t` に、その他の制御文字(U+0000〜U+001F、U+007F〜U+009F)と書式文字(U+200B〜U+200F、U+2028、U+2029、U+202A〜U+202E、U+2060〜U+2064、U+2066〜U+2069、U+FEFF)を `\u{16進小文字}` にエスケープする(例: U+0001 は `\u{1}`)。**対にならないサロゲート(U+D800〜U+DFFF の単独の `char`)も、同じ形でエスケープする**(例: U+DC80 は `\u{dc80}`)。.NET では、OS から得た文字列(コマンドラインの引数、環境変数、ファイル名)に、UTF-8 として不正なバイトがあるとき、どう `string` になるか(U+FFFD に置き換わるのか、単独のサロゲートが入るのか)は、**未確認**であり([08. 出力と多言語対応](08-output-and-i18n.md)で決める)、単独のサロゲートが入りうるものとして、表示の前にエスケープする(標準出力・標準エラーの UTF-8 の符号化が、置き換えか例外になるのを避ける)。定義の中のキー名には、単独のサロゲートは含まれない(第 1 節)ので、この規定が働くのは、`<file>` だけである。
- エスケープ後の文字数(コードポイントの数)が **64 文字**を超えるときは、64 文字までで切って末尾に `…` を付ける(エスケープの途中では切らない。たとえば、残りが 2 文字でエスケープが 6 文字なら、そのエスケープは入れず、そこで切る)。ちょうど 64 文字は切らない。
- この整形は、`file`(256 文字)の整形と同じ手順で、上限だけが違う。
- 文字列は、**コードポイントごと**に走査する(`string.EnumerateRunes()`。`char` ごとに走査すると、サロゲートの対を壊す。単独のサロゲートに当たると、`EnumerateRunes()` は、U+FFFD を返すと考えられるので(未確認)、サロゲートの検出は、`char.IsSurrogate` で、`char` ごとに先に行い、対(前半の直後に後半)でないものを、`\u{16進}` にする)。

## 13. 位置(行番号と列番号)の出し方

### 13.1 位置の単位

- 位置は、行と列の組(`Pos`)。**行は 1 始まりで、LF の数で数える**(CRLF でも、CR は直前の行に属し、LF のあとが次の行)。**列は 1 始まりで、その行の先頭からの `char`(UTF-16 のコード単位)の数 + 1**。JSON も YAML も、同じ単位である(入力の `string` の添字から、実装が求める)。**列は、同じ行の中の誤りの並びを決めるためだけに使い、行が違えば比べない**。同じ行の中で、前にあるものほど小さい列を返す限り、単位はどちらでもよい(他の言語版が、コードポイントで数えても、結果は変わらない)。
- **行と列は、ライブラリの `Mark.Line`・`Mark.Column` を使わず、`Mark.Index` から求める**。理由: ライブラリは、U+0085、U+2028、U+2029、CR だけの改行も改行として数える(第 5.1 節。確認(ソース))。第 5.1 節の事前の確認で、これらを拒否した後でも、拒否の位置の求め方と、受理する入力の位置を、LF の数に統一するためである。求め方: LF の添字の表(`List<int>`。`[0]` に 0 を入れ、`text[i] == '\n'` の `i` ごとに `i + 1` を足す)を作り、**添字 `index` 以下で最大の要素の位置**が行(1 始まり)、`index - 表[行 - 1] + 1` が列。二分探索は、自前で書くことを標準とする(`List<int>.BinarySearch` は、見つからないとき、次に大きい要素の添字のビット補数を返す、と一般に言われるが、この文書の作成時に公式ドキュメントで確かめていない: 未確認。使うなら、`i >= 0` なら行 = `i + 1`、そうでなければ行 = `~i` で、単体テストで確かめる)。範囲外の添字は、最後の行。
- 先頭の BOM は、位置には数えない(1 行目の 1 列目は、BOM の次の文字)。実装は、BOM を取り除いた文字列を、ライブラリと自前の読み取りに渡す(第 3 節)。
- 位置が決まらない誤りは、行なし(取り込み、`unsupportedFormat`、`versionMissing`)。
- 位置が (1, 1)(入力の先頭)の誤りは、`pipeline` が無い、`job` が無い。

### 13.2 ノードの位置

YAML のノードの位置は、構文イベントの `Start.Index`(入力の文字列の中の `char` の添字)を、第 13.1 節の求め方で行・列にしたもの。ただし、アンカーを前置したノードは、次の補正をする。

- **アンカー・タグを前置したノード**(`NodeEvent` の `Anchor` が空でない、または `Tag` が空でない、エイリアスでないもの)の `Start` は、アンカー・タグの先頭を指す可能性がある(libyaml 型の実装の一般的な挙動。YamlDotNet では未確認)。**内容の位置**に直すために、`Start.Index` から、次の手順で進める: 繰り返し、(1) 空白(半角スペース、タブ、CR、LF)を飛ばす、(2) `#` ならその行の LF まで飛ばす(コメント)、(3) `&` または `!` ならその次の空白まで飛ばす(アンカー・タグの 1 つ)、(4) それ以外の文字なら止まる。止まった添字が、内容の位置である。例: `a: &s` + 改行 + `  x` で `x` の位置(2 行目 3 列目)、`a: &s "q"` で `"` の位置、`a: &m` + 改行 + `  b: 1` で `b` の位置(2 行目 3 列目。マップは、次の「ブロックのマップ」の規定)。**すでに内容を指している位置に、この手順を適用しても、位置は動かない**(内容の先頭の文字は、`&` でも `!` でも空白でも `#` でもないため)。

| ノード | 位置 |
|--------|------|
| スカラー | 値の先頭の文字(引用符つきなら、開く引用符。ブロックスカラーなら、`\|` または `>` の位置)。アンカーやタグが前置されていても、**内容の位置**(上の補正。アンカーやタグの位置ではない) |
| ブロックのマップ | **最初のキーの位置**(最初のキーのノードの位置。そのキー自身が引用符つきなら、開く引用符。アンカーつきのキーも内容の位置)。明示のキー `? a` のときは、`?` の位置ではなくキー `a` の位置(ライブラリのマップの `Start` は `?` の位置を指す可能性があるので、補正が要る。`? a` + 改行 + `: 1` で 1 行目 3 列目)。マップがアンカーやタグを前置していても、同じ(最初のキーの位置)。実装は、マップの開始のイベントの次のイベントを 1 つ先読みして、その位置を得る(先読みのイベントが、スカラー、エイリアス、コレクションの開始のいずれでも、そのノードの位置) |
| フローのマップ | `{` の位置(アンカーやタグが前置されていても、上の補正で `{` の位置) |
| ブロックのリスト | **最初の `-` の位置**(アンカーが前置されていても、上の補正で `-` の位置。インデントなしのリストも `-` の位置) |
| フローのリスト | `[` の位置 |
| JSON のオブジェクト・配列 | `{` / `[` の位置 |
| マップのキー(`KeyPos`) | キーのスカラーの先頭(エイリアスのキーは、`*name` の位置) |
| 値が省略された対の値(`key:` の後ろに何もない、`{a, b: 1}` の `a`、`? a`、`a: &x` のようにアンカーだけ) | その対の**キーの位置**(ライブラリが返す位置は使わない) |
| リストの要素が省略された `- ` の後ろの null | ライブラリが返す位置(ダッシュの直後。同じ行) |
| `---` だけの文書(最上位が null)の根 | `---` の行の位置(`DocumentStart` の `End.Index`、または `---` の位置。行は `---` の行) |
| 展開されたノード(エイリアスから) | **エイリアスのトークン `*name` の位置**(複製した子のすべても同じ位置) |
| マージで取り込まれたエントリ | そのマージキー `<<` の位置(キー、値、値の中のすべて) |

- 「値の位置」とは、そのキーの値のノードの位置。「キーの位置」とは、`KeyPos`。「マップの位置」とは、上の表のマップのノードの位置(必須キーの欠落、`retryMissingKey`、`retryBackoffIncomplete` で使う)。**JSON では、マップの位置は `{` の位置**(`"retry": {` なら、`retry` のキーの行にある `{`。`{` が次の行にあれば、次の行)であり、YAML のブロック形式の「最初のキーの位置」とは違う。
- 複数の文書の 2 つ目の文書の位置(第 5.6 節の行)は、その文書の根のノードの位置(上の表)である。空の文書(`---` の後ろが空)は、ライブラリが返す位置(次の行の先頭など。未確認)。

### 13.3 誤りの位置の取り方(まとめ)

- 型の誤りや範囲の誤りは、**誤った値のノードの位置**。
- 未知のキーは、**キーの位置**。
- 必須のキーの欠落は、**それを含むマップの位置**(JSON は `{`、YAML のブロックは最初のキー)。
- `pipeline` や `job` 自体が無いときは、(1, 1)。
- 終了コードの重なり(`overlappingExitCodes`、`zeroAsWarning`、`retryExitCodesOverlap`)は、対象の**キー**の位置(値ではない)。
- リストの誤りは、要素ごとに、その要素の位置。
- 取り込みの誤り、`unsupportedFormat`、`versionMissing` は、行なし。
- 段階 3 の誤りは、そのノードの位置(キーの誤り(重複、非文字列)はキーの位置、マージキーの誤りは `<<` の位置、深さの誤りは 33 段目のコレクションの位置、上限(要素数、大きさ)の誤りは、超えたノードの位置。エイリアスの展開の中で超えたときは、エイリアスの位置)。

### 13.4 文法の誤りの行

- **JSON**: 第 4.5 節のとおり、必須。
- **YAML**: 文法の誤りは、ライブラリが検出した位置の行(例外の `Start.Index` から求めた行。`Mark.Empty` のときは、第 7.3 節)。検出位置は、ライブラリの作りで変わる(原因の行より後ろになることも、前になることもある)。**必須なのは、種類(`syntax`)と理由(`YAML の文法に誤りがあります`)であり、行は、ライブラリが返すものでよい**。次の表は、libyaml 型の読み取りで**期待される**行(他の言語版の読み取り実装での観測に基づく目安)であり、YamlDotNet では**未確認**である。実装時の結果が違えば、その版の結果に合わせて、この表を更新する。

| 入力(`\n` は改行) | 期待する行 |
|------|----|
| `format_version: 1\npipeline: [1, 2\n` | 3(入力の末尾の空の行) |
| `a: [1, 2\n` | 2 |
| `a: [1, 2\nb: 3\n` | 2(`b` の行) |
| `a: [1, 2`(末尾の改行なし) | 1 |
| `a: "x\n` | 2 |
| `a: 1\nb: "\q"\n` | 2 |
| `x: 1\na: b: c\n` | 2 |
| `a: 1\nb:\n\t- x\n`(タブのインデント) | 3(未確認。位置を持たない例外なので、第 7.3 節の補完) |
| `a:\n  b: 1\n c: 2\n` | 3 |
| `a: @x\n` | 1 |
| `a: 1\r\nb: [1,\r\n c: 2\r\n`(CRLF) | 4(CRLF でも、LF の数で数えた行) |
| `a: [1,\n  2\n` | 3 |
| `a: 1\nb: 2\nc: ` + U+0007 + `\n`(制御文字) | 3(事前の確認の位置) |
| `a: "\U00110000"` | 1(位置を持たなくてもよい。行なしでもよい) |

## 14. 取り込み後のデータモデルと検査の関数

### 14.1 データモデル

検証に成功すると、次のデータを返す(型の骨格。`sealed record` で、変更できない値として返す)。

```csharp
namespace Conductor.Definition;

public abstract record Command;
public sealed record LineCommand(string Line) : Command;                  // 文字列で書いた
public sealed record ArgvCommand(IReadOnlyList<string> Argv) : Command;   // 配列で書いた。1 要素以上。先頭は空白だけでない

public enum TransitionOn { Success, Warning }

public abstract record Transition(TransitionOn On);
public sealed record ToJob(TransitionOn On, string JobId) : Transition(On);
public sealed record ToEnd(TransitionOn On) : Transition(On);             // next が "@end"

public sealed record Backoff(int Multiplier, ulong MaxIntervalSecs);      // 2〜10、interval 以上 86400 以下

public sealed record RetryPolicy(
    IReadOnlyList<int> ExitCodes,   // 昇順・重複なし・各 1〜255・空でない
    int Max,                        // 1〜100
    ulong IntervalSecs,             // 1〜86400。待ち時間は 64 ビット符号なしの飽和演算で使う([05])
    Backoff? Backoff);              // null なら固定間隔。multiplier と max_interval は必ず同時に有る/無い

public sealed record Job(
    string Id,                                   // 空白だけでなく、@ で始まらず、定義内で一意
    Command Command,
    IReadOnlyList<int> WarningExitCodes,         // 省略時は空。0 を含まない。書いた順のまま。各値は 32 ビット符号つき整数
    IReadOnlyList<int>? SuccessExitCodes,        // 省略時 null(意味は [0])。書いた順のまま
    IReadOnlyList<Transition> Transitions,       // 書いた順。on ごとに高々 1 つ
    RetryPolicy? Retry);                         // 書かなければ null

public sealed record Definition(
    string Name,                    // 空白だけでない(trim していない元の値)
    string? Description,
    string? RunIdEnv,               // 名前の形は検査済み。null なら実行時に CONDUCTOR_RUN_ID
    bool RemoveOnComplete,          // 省略時 false
    int FormatVersion,              // 1
    IReadOnlyList<Job> Jobs);       // 記述順を保つ。1 つ以上
```

- 成功として扱う終了コード = `SuccessExitCodes` があればそれ、なければ `[0]`。
- ジョブIDから記述順の位置(0 始まり)を引く操作がある(遷移先の検査と、実行時の遷移の解決に使う)。`Dictionary<string, int>`(`StringComparer.Ordinal`)で持つ。
- `record` の自動の等価は、`IReadOnlyList<T>` を参照で比べる。テストや比較には、要素ごとの比較(`SequenceEqual`)を使う。`Definition` の等価に頼らない。
- 取り込み後の整数(終了コード、`max`、`multiplier`)は `int`(範囲検査の後)、秒数は `ulong` である。`checked` の演算で例外にしない(範囲は検査済み)。

## 15. `run_id_env` のゆるい読み取り

`watch` と `reset` は、`--run-id` が無いとき、定義全体を検証せず、`pipeline.run_id_env` だけを取り出す。

- 書式の決定(第 2.1 節)から段階 3(第 6 節の上限を含む)までは、定義の読み込みと同じに行う。段階 4・5 は行わない。
- 拡張子が対応していない、ファイルを読めない、大きさの上限を超える、JSON・YAML として読めない(上限を含む)、最上位がマップでない、`pipeline` がマップでない、キーが無い、文字列でない、名前の形(第 9.1 節)に合わない、のどれでも「無し」(`null`。実行時は `CONDUCTOR_RUN_ID`)。
- ほかの誤り(`format_version` の誤り、未知のキーなど)は無視する。壊れた入力でも異常終了しない(例外を投げず、`null` を返す。`Load` の内側と同様に、BCL とライブラリの例外を捕まえる)。
- ファイルの大きさの上限(第 3 節)は、この読み取りにも適用する(超えれば「無し」)。
- 例(JSON): `{"pipeline": {"name": "p", "run_id_env": "X_ID"}}` → `X_ID`。`"run_id_env": 5`、`"1A"`、`""` → 無し。`"pipeline": 3` → 無し。空の入力 → 無し。YAML: `pipeline:\n  name: p\n  run_id_env: X_ID\n` → `X_ID`。

## 17. C# 固有の落とし穴(まとめ)

この文書の規定のうち、.NET の標準の API をそのまま使うと誤るもの、または結果が文化・環境で変わりうるものを、まとめる。「確認」は、公式ドキュメント・公開ソースの記述の確認であり、動作の確認ではない。

| 落とし穴 | 確認した事実(出典) | この文書の規定 |
|----------|--------------------|----------------|
| 文化依存 | `ToString()`、`Parse`、`ToUpper`、`string.Compare`、`StartsWith(string)` の既定は、文化に依存する(この文書の作成時に、個別の公式ドキュメントでは確認していない。確認: `Double.ToString()` の出力が `NumberFormatInfo` に従うことは、標準の数値書式の公式ドキュメントの例(`en-US` と `fr-FR` で小数点が変わる)による) | 不変文化(`CultureInfo.InvariantCulture`)と序数比較(`StringComparison.Ordinal`)だけを使う(冒頭) |
| `\d` | 確認(出典: 正規表現の文字クラス): Unicode の 10 進数字(Nd)に当たる | `[0-9]` か自前の走査(第 5.2、9.5 節) |
| `$` | 確認(出典: 正規表現のアンカー): 末尾、または末尾の `\n` の直前に一致する。`\z` は末尾だけ | `\A…\z` か自前の走査(第 5.2、9.1 節) |
| `char.IsDigit`、`char.IsLetter` | 確認(出典: `Char.IsDigit`): Unicode の 10 進数字に分類される文字 | `c is >= '0' and <= '9'` で判定(第 4.6 節) |
| `string.Trim()` と White_Space | 確認(出典: `Char.IsWhiteSpace`、`String.Trim`): 一致する。ただし、Unicode のデータの版による変化は未確認 | `Trim()` を使い、全 `char` の単体テストを置く(第 1 節) |
| `int.Parse`・`long.Parse` | 既定の `NumberStyles` が、符号・前後の空白を受け付け、例外を投げる(未確認: 全角数字を受け付けるかは、確認していない) | 字句を自前で確かめてから `TryParse`(`NumberStyles` を明示、`InvariantCulture`)(第 4.2、5.2 節) |
| `double` の書式化 | 確認(出典: .NET ブログ、標準の数値書式): .NET Core 3.0 以降、`ToString()`、`"G"`、`"R"` は、往復できる最短の文字列を返す。.NET Framework と、3.0 より前の .NET Core では、`"R"` が往復に失敗することがある | 指数形・桁の組み立ては自前(桁と指数を取り出して、自分で並べる。[09. 変換器](09-converter.md)第 6.1 節) |
| `double.Parse` の桁あふれ・書式 | 確認(出典: .NET ブログ): .NET Core 3.0 以降の解析は IEEE 754 に準拠する。桁あふれの結果(例外か ∞)と、`1.`・`.5` の受理は未確認 | 字句を正規化し、指数が 10 桁以上のものは打ち切る(第 4.2、5.2 節) |
| `Path.GetExtension` | 確認(出典: 公式ドキュメント): 最後の `.` が最後の区切りより後ろにあれば、その後ろを返す | 使ってよい。大文字小文字は ASCII だけで自前で畳む(第 2.1 節) |
| テキストの復号 | 確認(出典: `UTF8Encoding`): 引数なしの構築は、不正なバイトで例外を投げない | `throwOnInvalidBytes: true` を使い、BOM はバイト列で取り除く(第 3 節) |
| `Utf8JsonReader` | 確認(出典: 公式ドキュメント): BOM を取り除いてから渡す必要がある。位置はバイトの添字 | 全面自前(第 4.4 節) |
| `StackOverflowException` | 確認(出典: 公式ドキュメント): `try`/`catch` で捕まえられず、プロセスが終了する | 再帰を使わない(第 4.6、6.1、6.4 節) |
| `record` の自動のメンバー | `Equals`、`GetHashCode`、`ToString` が、メンバーを再帰して呼ぶ(`record` の仕様。この文書の作成時に、個別には確認していない) | 木のノードは `sealed class`(第 6.1 節) |
| `List<T>.Sort` | 確認(出典: 公式ドキュメント): 不安定な並べ替え | `OrderBy` + `ThenBy`(安定。確認(出典: 公式ドキュメント))(第 10、14.2 節) |
| `Dictionary` の列挙の順 | 順序は保証されない(一般的な契約。未確認) | 順序は `Entries` の並びから得る(第 6.1 節) |
| `string.Normalize`、`StartsWith(string)` | 文化依存・正規化の可能性 | 呼ばない。`string.Equals(a, b, StringComparison.Ordinal)`、`StartsWith(char)` か `StartsWith(string, StringComparison.Ordinal)` |
| `Mark.Line`・`Mark.Column`(YamlDotNet) | 確認(ソース): NEL・LS・PS・CR だけも改行として数える | `Mark.Index` から LF の表で求める(第 13.1 節) |
| `Mark.Index` の単位 | 確認(ソース): `char` 1 個ごとに +1(UTF-16 のコード単位) | 添字として `string` にそのまま使える。コードポイントでは数えない(第 7.2 節) |
| YamlDotNet の `Scanner` の既定の単純キーの上限 | 確認(ソース): 既定 1,024。コンストラクターで変えられる | 明示して 1,024 で作る(第 5.1 節) |
| YamlDotNet が制御文字を拒否しない | 確認(ソース): `IsPrintable` は定義だけで、`Scanner` が呼ばない | 事前に自前で検査する(第 7.4 #13) |
