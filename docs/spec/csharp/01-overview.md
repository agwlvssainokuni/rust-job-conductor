# 01. 概要

この文書は、`conductor`(C# 版。挙動の版は 0.8.0)が何のためのツールか、どのような方針で作るか、何を作らないか、どのような制約の下で作るか、を述べる。詳細な規定は、02 章以降にある。

## 1. 目的

複数のコマンド(シェルスクリプトや実行ファイル)を決まった順に実行する一連の作業(バッチ処理、定期ジョブ、データの取り込みの手順など)を、次の 3 点で支える。

| 目的 | 内容 |
|------|------|
| 宣言的に書く | 実行するコマンドの並びと、終了コードごとの扱い(成功・警告・エラー、次に進むジョブ、リトライ)を、1 つの定義ファイル(JSON が主、YAML も可)に書く |
| 途中経過を残す | どのジョブがどう終わったか、次にどこから再開するかを、ステートファイル(JSON)に保存する |
| 失敗から再開する | 失敗したジョブで止まり、原因を直したあとの再実行で、終わったジョブは飛ばして、失敗したところから続ける |

`conductor` は、C#(.NET)で書くコマンドラインツールである。RID(OS とアーキテクチャ)ごとの、単一ファイル・自己完結の実行ファイルとして配り、利用者は .NET を入れずに使える(11 章 6 章)。

## 2. ユースケース

| ユースケース | コマンド | 内容 |
|--------------|----------|------|
| パイプラインを順に実行する | `conductor pipeline <名前>` | 定義の全ジョブを記述順に実行する。失敗したジョブで止まり、再度実行すると、そのジョブから再開する |
| 1 つのジョブだけ実行する | `conductor run <ジョブID>` | 外部のスケジューラが、ジョブを 1 つずつ呼ぶ。順序が守られているかをステートで確かめ、順序外なら拒否する |
| 状態を確かめる | `conductor watch` | ステートを表にして標準出力に出す(定義は検証しない) |
| ステートを捨てる | `conductor reset [--all]` | ステートを初期化する。壊れたステートからの回復にも使う |
| 定義を検査する | `conductor validate [<名前>]` | 定義とコマンドの書き方を、ジョブを起動せずに検査する(CI で定義の誤りを早く見つける) |
| 書式を変換する | `conductor convert <ファイル> --to json\|yaml` | 定義(など)を JSON と YAML のあいだで変換する(人が書く定義にコメントが要るときは YAML を使う) |
| 同じ定義を並行して使う | `--run-id <ID>` | run ID でステートを分け、別の実行単位として扱う(CI の実行番号など) |
| 警告を許す | `warning_exit_codes`、`transitions` | 一部の終了コードを「警告」として扱い、続行したり、別のジョブへ飛んだりする |
| 一時的な失敗を再試行する | `retry` | 決めた終了コードで終わったときに、待ってから実行し直す(間隔の倍率と上限を指定できる) |

## 3. 設計方針

| 方針 | 内容 |
|------|------|
| 同じ挙動 | 版 0.8.0 と、利用者から見て同じ挙動にする。サブコマンド、オプション、終了コード、メッセージの文言、`watch` の表、実行の意味論は同じ |
| 失敗を値で返す | 外部の入力(引数、環境、ファイル、シグナル、ジョブの出力)に対して異常終了しない。誤りは、種類・位置・固定の理由・終了コードで返す(各章の `abstract record` の階層。10 章 8 章)。例外は、標準出力の書き込みの失敗(`OutputException`)だけ。想定外の内部失敗だけが 70 |
| 少なくとも 1 回 | ジョブは、少なくとも 1 回は実行される。結果の記録を書けなければ、ジョブの終了コードより 65 を優先する。記録の前に落ちると、再実行されうる |
| シェルを介さない | `command` は、決まった規則で分割した引数を、`System.Diagnostics.Process`(`UseShellExecute = false`)に直接渡す。展開・パイプ・リダイレクトは解釈しない。メタ文字は、そのまま引数になる(Windows の `.cmd` / `.bat` だけは、07 章 4.8 節の安全策を通す) |
| 入力の値を表示に出さない | エラーの文に、入力の値やライブラリのエラー文を含めない(入力に由来するのは、キー名だけ。制御文字と孤立サロゲートをエスケープして切り詰める) |
| 純粋な判断とふるまいの分離 | 分類・遷移・再開・リトライの判断は、入出力に触れない純粋な関数(`Conductor.Flow`)にして、表駆動のテストで確かめる。ファイル・プロセス・シグナル・時刻・標準出力は、`Deps`(`interface` の束)の向こうに置く |
| 原子的なステート | ステートは、一時ファイルに書いて、同期してから、`File.Move(overwrite: true)` で置き換える。読み手は、直前の完全な内容か、新しい完全な内容のどちらかだけを見る |
| 同期モデル | 同期(`async`・`Task`・`Thread` を使わない)。ジョブ、出力、ステートの書き込みは、すべて直列。シグナルのコールバックは別のスレッドで動くので、旗を立てるだけで、待つ側が短い刻みで旗を見る |
| 出力を完了させてから終わる | 標準出力・標準エラーは、書くたびに `Flush()` する。終了(`Main` の戻り値)は入口の 1 か所 |
| 依存は最小 | 実行時の外部ライブラリは、YAML の読み取りの 1 つだけ(採用案は YamlDotNet)。ほかは BCL(引数の解析は自前、JSON の読み取りと書き出しも自前) |
| 文化・文字単位を明示する | `string` は UTF-16。文化に依存する API を使わず、不変文化と序数比較を使う。文字を数える単位(コードユニット、コードポイント、UTF-8 のバイト数)は、場面ごとに規定する |
| 確かめられる仕様 | すべての規定は、ビルドした `conductor` を外から実行する受け入れテスト(11 章。AC-001〜550)で確かめられる形で書く |

## 4. 非目標

次のことは、この版では行わない。

| 非目標 | 補足 |
|--------|------|
| ジョブの並列実行 | ジョブは、記述順に 1 つずつ実行する。分岐は、遷移による前方へのスキップだけ(後戻り・ループはない) |
| 常駐とスケジューリング | デーモンも、時刻による起動もない。起動は、利用者か外部のスケジューラが行う |
| 排他制御 | ファイルロックや PID ファイルを使わない。同じ定義(同じ run ID)の同時実行は、避けること(run ID で分ければ並行できる) |
| ジョブの出力の加工 | ジョブの標準入出力・標準エラーは、そのまま流れる(`Redirect*` を `false` のまま引き継ぐ)。ログの収集・保存はしない |
| シェルの機能 | 変数の展開、パイプ、リダイレクト、ワイルドカードの展開は、`conductor` は解釈しない(必要なら、ジョブがシェルを起動する) |
| 環境変数の展開 | 定義の値に環境変数を埋め込む機能はない。環境変数を読むのは、run ID、ロケール、色の判定と、実行ファイルの探索(`PATH`)・`cmd.exe` の場所(`ComSpec`)だけ |
| 定義の再利用や継承 | YAML のアンカー・マージキーによる、書式の内側での再利用だけ(展開して読む) |
| ネットワーク | 外向きの通信をしない(`System.Net` を使わない)。リモートの実行や、状態の共有もない |
| ほかの書式 | 定義は JSON と YAML だけ(拡張子が `.json`・`.yaml`・`.yml` 以外は拒否する) |
| リトライの回数の保存 | リトライの回数と待ち時間は、ステートに保存しない(再開は、最初の実行から数え直す) |
| 画面の対話 | 対話的な入力も、進捗の動的な表示もない(標準入力を読まない。ジョブに引き継ぐ) |
| ジョブの強制終了 | 中断のとき、子プロセスにシグナルを 1 回転送するだけ(UNIX 系)。止まらないジョブを強制終了しない(`Process.Kill` を使わない) |
| ジョブを新しいプロセスグループに置くこと | しない(`conductor` と同じグループ。07 章 4.7 節) |
| ライブラリとしての公開 | 公開するのは実行ファイル `conductor` だけ。NuGet には公開しない |
| トリミング・Native AOT・ReadyToRun | 採らない(02 章 1 章、11 章 6.2 節) |
| 署名・公証 | macOS の署名・公証と Windows のコード署名は行わない(11 章 6.5 節) |

## 5. 制約

| 項目 | 内容 |
|------|------|
| .NET の版 | 対象は .NET 10(`net10.0`)だけ(作成時点でサポート中の LTS は .NET 10 だけ。確認: .NET の公式のサポートポリシーのページ。.NET 8 と 9 は 2026-11-10 にサポート終了)。実装時に、次の LTS の登場とサポートの状況を確認し、最小と最新の版を分ける。`global.json` は `10.0.100` + `rollForward: latestFeature`。`Directory.Build.props` の `ConductorMinTfm`・`ConductorMaxTfm`、CI の版との一致を検査する(11 章 AC-477) |
| 言語の設定 | C#(`LangVersion` は `latest`)、`Nullable=enable`、`ImplicitUsings=disable`、`TreatWarningsAsErrors=true`。`!` の使用、`catch (Exception)`(入口以外)、`async`・`Task`・`Thread` を製品のコードで使わない |
| 対象 OS | Linux、macOS、Windows の 3 つ。OS 差は、プラットフォーム層(`PlatformDetector`、`UnixPlatform`、`WindowsPlatform`、`CmdLauncher`)と `Conductor.Native.UnixNative` の 1 か所に隔離する(OS の判定は `PlatformDetector.Detect()` だけ) |
| 配布 | RID ごとの単一ファイル・自己完結の実行ファイル(`linux-x64`、`linux-arm64`、`osx-arm64`、`win-x64`)と `SHA256SUMS`。タグ `v*` で、ドラフトのリリースに添付する |
| 依存の方針 | 実行時の依存は、YAML のライブラリ 1 つだけ(採用案は `YamlDotNet`。03 章 7 章、11 章 8 章)。選定は、位置の取得、構文要素の API、重複キー・タグ・複数文書の検出、アンカーの展開の上限、保守の継続、依存の少なさを基準にする。採否は、実装時の小さな試験で決める(12 章 4 章) |
| 開発時の依存 | xUnit、`Microsoft.NET.Test.Sdk`、`coverlet.collector`、`Microsoft.CodeAnalysis.BannedApiAnalyzers`。選定と版は、実装時に確認する |
| ほかの依存 | ネイティブの部品を必須としない(P/Invoke は `libc` の関数だけ)。ネットワークのライブラリ、`eval` 相当の動的実行、`System.CommandLine`、`System.Text.Json` の読み書きを使わない |
| 入力の大きさ | 定義・ステート・変換の入力は 1 MiB まで。YAML・JSON の展開後の要素数は 100,000、文字の大きさは 16 MiB、入れ子の深さは 32 段まで |
| 文字コード | 定義・ステート・変換の入力は UTF-8(先頭の BOM は、定義と変換では受理し、ステートでは拒否する)。引数と環境変数は、.NET の `string`(UTF-16)で受ける(不正な UTF-8 の扱いは 04 章 4.4 節。一部は未確認) |
| 言語 | メッセージは、日本語と英語(環境変数 `LC_ALL`、`LC_MESSAGES`、`LANG` で決める)。理由の文(定義・ステート・変換)は、常に日本語 |
| ライセンス | Apache License 2.0。ソースの先頭に著作権表示を置く(11 章 2.4 節) |
| 検証の限界 | 作成時には .NET SDK がなく、コードのビルドも実行もしていない。確認できた点と未確認の点は、各章と 12 章に書いた |

## 6. 利用者像

| 利用者 | 求めるもの |
|--------|------------|
| 運用担当(バッチや定期ジョブの運用者) | 失敗したところから再開できること。状態を `watch` で確かめられること。壊れたステートを `reset` で回復できること |
| 開発者(ジョブと定義を書く人) | 定義の誤りが、種類と行番号つきで分かること。`validate` を CI に入れられること。リトライと警告の扱いを宣言で書けること |
| CI の管理者 | 実行番号などで run ID を分けて並行して使えること。終了コードで結果を判断できること。3 OS で動くこと |
| この仕様書の読者(再実装する人) | 02〜11 章を読んで、同じ挙動の実装を作り、受け入れテストで確かめられること。`string` が UTF-16 であること、文化依存の API、`Process.ExitCode` とシグナル終了、閉じたパイプで書き込みが捨てられること、`PosixSignalRegistration` の保持、YAML ライブラリの扱いなどの落とし穴と、最初の試験が分かること(12 章) |

## 7. 概念の概観

### 7.1 定義ファイル

1 つのパイプラインと、ジョブの並びを書く。既定の名前は `conductor.json`。

```json
{
  "format_version": 1,
  "pipeline": {
    "name": "nightly",
    "description": "夜間バッチ"
  },
  "job": [
    {
      "id": "extract",
      "command": "extract --all --since yesterday",
      "warning_exit_codes": [3, 4],
      "transitions": [{ "on": "warning", "next": "notify" }]
    },
    {
      "id": "load",
      "command": "load",
      "retry": { "exit_codes": [75], "max": 3, "interval": "30s" }
    },
    { "id": "notify", "command": "notify --channel ops" }
  ]
}
```

- 書式は拡張子で決まる(`.json`・`.yaml`・`.yml`。ASCII の大文字小文字を区別しない)。YAML でも同じ構造を書く(`conductor convert` で相互に変換できる)。
- ジョブは記述順に実行する。`transitions` で、成功・警告のときの次のジョブ(後ろのジョブか `@end`)を指定できる。飛ばされたジョブはスキップになる。
- 読み込みは、見つけた誤りをまとめて返す(種類、行、理由)。詳細は 03 章。

### 7.2 実行と分類

ジョブを起動し、終了コードで分類する。

| 結果 | 分類 | 終了コード |
|------|------|------------|
| 成功コード(省略時は 0)で終了 | 成功 | 0 |
| 警告コードで終了 | 警告 | 0 |
| それ以外の終了コード | エラー | ジョブの終了コード(0〜255 に合わせる) |
| シグナルで終了(UNIX 系) | エラー | 128 + 番号 |
| 起動できない | エラー | 127 |
| 起動前に中断された | 分類なし | 128 + 番号 |

UNIX 系の「シグナルで終了」は、`Process.ExitCode` が 129〜159 で、そのジョブの成功・警告のコードに含まれないときだけの推定である(07 章 4.4 節)。`pipeline` は、エラーで止まり、そのジョブの終了コードで終わる。リトライの対象なら、待って実行し直す。詳細は 05 章。

### 7.3 ステートと再開

実行の途中経過を、定義ファイルと同じ場所の `<定義ファイル名>.state` に JSON で保存する(run ID があれば `<定義ファイル名>.<run ID>.state`)。再実行では、終わったジョブを飛ばし、再開位置から続ける。`run` は、順序外のジョブを拒否する(66)。スキップ対象・`@end` より後ろ・実行済みのジョブは、拒否ではなく、スキップとして 0 で終わる。全ジョブが終わると完了になり、完了のステートは、次の実行では空とみなす。詳細は 05・06 章。

### 7.4 中断

UNIX 系では SIGHUP・SIGINT・SIGQUIT・SIGTERM を `PosixSignalRegistration` で、Windows では Ctrl+C を `Console.CancelKeyPress` で受ける。コールバックは別のスレッドで動き、中断の合図(`Interrupt`)に最初の番号を残すだけである。UNIX 系では、実行中のジョブにシグナルを 1 回転送し(`libc` の `kill`)、再開位置を記録して、128 + 番号で終わる。Windows は、OS が Ctrl+C を同じコンソールのジョブにも配るので、転送しない。リトライの待機は、合図から 1 秒以内に切り上げる。詳細は 07 章。

### 7.5 出力

- `conductor` 自身は、既定では何も出力しない(ジョブの出力がそのまま流れる)。エラーのとき、または `-v` のときだけ、標準エラーに書く。
- `watch`、`--help`、`--version`、`convert` は、結果を標準出力に書く。標準出力に書けないとき(容量不足など)は、`watch` が 65、`convert` が 67 で終わる(`--help`・`--version` は、失敗を無視して 0)。UNIX 系で、読み手が先に閉じたパイプへの書き込みは、.NET の標準のストリームに捨てられ、65・67 でなく 0 で終わりうる(既知の差。08 章 1.3.1)。
- メッセージは、環境変数で日本語か英語を選ぶ。`watch` の表は、端末なら状態語に色が付く。詳細は 08 章。

### 7.6 内部の構成

```text
Program ─▶ EntryPoint ─▶ Report / Runner / State / Convert / RunIds / Flow / Definition / Json / Text
                          (Runner と State は Native を使う)
```

`Conductor.Cli` が引数を解き、各部を組み立てて終了コードを決める。`Flow` は純粋な判断、`State` はステートの入出力、`Runner` は子プロセスとシグナル(OS 差はプラットフォーム層に隔離)、`Report` は文の組み立てと書き込みの窓口、`Definition` は定義の読み込みと検査(YAML の読み取りを含む)、`Json` は自前の JSON の読み取りと書き出し(`State` と `Convert` が共用する)、`Convert` は書式の変換、`Text` はエスケープ、`Native` は P/Invoke である。`Program.Main` は薄い入口で、内部の誤りの捕捉と、出力の完了と、終了を受け持つ。プロジェクトは `Conductor.Cli` → `Conductor.Runtime` → `Conductor.Core` の向き。依存の向きと型の骨格は 02 章。
