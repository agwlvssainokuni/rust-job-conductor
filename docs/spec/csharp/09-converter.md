# 09. 変換器(JSON と YAML の相互変換)

この文書は、`conductor convert <ファイル> --to <json|yaml>` の中身である変換器の振る舞いを定める。この文書だけで、C#(.NET)でゼロから、同じ受理・拒否・出力・エラーを返す変換器を実装できることを目標とする。

- 変換器は、定義ファイルの**検証をしない**。変換した結果が `conductor` の定義([03. 定義ファイルの書式と検証](03-definition-format.md))として正しいかは見ない(任意の JSON / YAML のマップを変換する)。
- 副作用はない: ファイルへの書き込み、環境変数、プロセス、ネットワークに触れない(読むのは入力ファイル 1 つだけ)。変換結果は、文字列として返す(標準出力への書き出しは、[04. CLI](04-cli.md) の側の仕事)。
- 入力の値を、エラーの文に含めない(キー名だけを、エスケープと切り詰めをして、場所として示すことがある)。
- 確認できなかった点は「未確認」と書く。公式ドキュメントや公開されたソースで確かめた点は「確認(出典: …)」と書く。この環境には .NET SDK が無く、実機では動かしていない。「確認」は、文書・ソースの記述の確認であり、動作の確認ではない。実装時に、第 11 節の例と第 9 節の往復の試験を、そのままテストにして行う。
- 「必須」の挙動は、利用者から見える結果(受理/拒否、変換結果の文字列、エラーの種類・文言・行・場所)で、同じにしなければならない。「任意」「実装に任せてよい」と書いた点は、変換結果を読み戻した木が変わらない範囲で、実装が選んでよい。
- コマンドの引数・終了コードの全体は [04. CLI](04-cli.md) と [10. エラーと終了コード](10-errors-and-exit-codes.md)、メッセージの言語の選び方と標準出力の文字コードは [08. 出力と多言語対応](08-output-and-i18n.md) に従う。
- JSON と YAML の**読み取り**(文法、スカラーの型、アンカー、マージキー、重複キー、上限、木の型)は、[03](03-definition-format.md)の第 4〜7 節と**同じ**で、実装も共有する(`Conductor.Definition` の木の読み取り(`Conductor.Definition.TreeReader`、`Conductor.Json.JsonReader`、`Conductor.Json.Limits`)を、名前空間 `Conductor.Convert` が呼ぶ)。この文書は、読み取りの上の差分(取り込み、最上位、拒否する数)と、書き出しを定める。
- 数と文字列の型: 整数は `long`(64 ビット符号つき)、浮動小数は `double`(IEEE 754 binary64)、文字列は `string`(UTF-16)。`decimal` と `System.Numerics.BigInteger` は使わない(第 6.3 節)。標準のライブラリの JSON の書き出し(`System.Text.Json` の `JsonSerializer`、`Utf8JsonWriter`、`JsonNode.ToJsonString`)と、YAML ライブラリの書き出し(`Serializer`、`Emitter`)は、**使わない**(出力の文字列を、この規定に一致させるため。第 6.1、7、8 節)。
- 文化に依存する API(`ToString()`、`Parse` など)は使わない。数の書式化は `CultureInfo.InvariantCulture`、比較は `StringComparison.Ordinal` を使う([03](03-definition-format.md)冒頭)。

## 1. 入口と入出力

型とメソッドの骨格(例。本体は省略している。`DefinitionFormat` は [03 第 14.2 節](03-definition-format.md)と同じ。判別共用体の代わりに、抽象の `record` と `sealed record` の継承階層を使う)。

```csharp
namespace Conductor.Convert;

using Conductor.Definition;
using Conductor.Json;

public abstract record ConvertResult;
public sealed record ConvertOk(string Text) : ConvertResult;
public sealed record ConvertFailed(ConvertError Error) : ConvertResult;

public static class Converter
{
    /// <summary>パスのファイルを読み、to の形式に変換した文字列を返す。</summary>
    public static ConvertResult ConvertFile(string path, DefinitionFormat to);

    /// <summary>ファイルに触れない。text は、BOM を取り除いた、復号済みの文字列。fileLabel はエラーの表示に使う名前。</summary>
    public static ConvertResult ConvertText(string text, DefinitionFormat to, string fileLabel);
}
```

| 入口 | 引数 | 戻り値 |
|------|------|--------|
| `ConvertFile` | 入力ファイルのパス、変換後の形式 | 成功: 変換結果の文字列、失敗: 変換の誤り(第 10 節) |
| `ConvertText` | 文字列(復号済み)、変換後の形式、表示用のファイル名 | 同上(ファイルに触れない) |

- 変換後の形式は `json` または `yaml`。
- **入力の形式は、変換後の形式の反対**とみなす(`--to json` なら入力は YAML、`--to yaml` なら入力は JSON)。**拡張子は見ない**。`.json` の名前のファイルでも、`--to json` なら YAML として読む(JSON を YAML として読んでも、JSON は YAML のほぼ部分集合なので、読めることがある。ただし、この仕様の YAML の読み取りの規則(タブ、`\/` のエスケープなど)で拒否されることがある。逆に、YAML を JSON として読めば、JSON の文法の誤りになる)。
- 変換結果は、全部作ってから 1 つの文字列として返す。失敗のときは、出力は無い。
- 誤りは、例外ではなく戻り値で返す。例外は、実装の不具合にだけ使う。
- `conductor convert` は、成功したら結果を標準出力に 1 回で書く。**変換結果の改行は LF だけであり、書き出しで CRLF に変わってはならない**。.NET の `Console.Out` と `StreamWriter` が、`\n` を `\r\n` に変換するかは、公式ドキュメントでは確認していない(未確認。`TextWriter.NewLine` の既定は `Environment.NewLine` で、Windows では CRLF だが、`Write(string)` が文字列中の `\n` を変換するとは考えにくい)。したがって、**`Console.OpenStandardOutput()` で得た `Stream` に、UTF-8(BOM なし。`new UTF8Encoding(false)`)の `GetBytes` の結果を、そのまま書く**(08 章の決定に合わせる)。`Console.Out.WriteLine` は使わない(`NewLine` を付けるため)。実機での確認は、Windows で未確認。失敗したら標準出力は空で、標準エラーに原因を出し、終了コード 67 で終わる([04](04-cli.md)・[10](10-errors-and-exit-codes.md))。

## 2. 処理の流れと失敗の順序

```
Intake → 読み取り(Parse) → 展開と写し取り(Resolve) → 最上位の確認(RootCheck) → 書き出し(Write)
```

失敗は、次の順で最初に見つかったものを 1 件だけ返す(以降は実行しない)。

| 順 | 段階 | 失敗 |
|----|------|------|
| 1〜2 | Intake: 開く(存在しない → `fileMissing`、権限など → `unreadable`) | 第 3 節 |
| 3 | Intake: 通常のファイルでない → `unreadable`、大きさが 1 MiB を超える → `tooLarge` | 第 3 節 |
| 4 | Intake: 上限 + 1 バイトまでの読み取りと UTF-8 の確認 → `unreadable` | 第 3 節 |
| 5 | Parse: 文法の誤り → `syntax`。JSON は、先頭から読んで最初に見つかった文法の誤り・重複キー。YAML は、ライブラリで全文書を読み終えてからの文法の誤り | 第 4 節 |
| 6 | Resolve(入力に現れる順で、最初に見つかったもの): 複数の文書(YAML)・タグ・非文字列キー・重複キー・再帰するアンカー・マージキーの誤り(いずれも `syntax`)、要素数・文字の大きさの上限(`tooLarge`)、入れ子の深さの上限(`syntax`) | 第 4 節 |
| 7 | RootCheck: 最上位がマップでない → `rootNotMap` | 第 4.3 節 |
| 8 | Resolve で記録した、表せない値のうち、入力に現れる順で最初のもの → `unrepresentable` | 第 5 節 |

- 順 6 の失敗は、順 8 より優先する(先に表せない数があっても、上限超過が返る)。
- 順 7 は順 6 より後。最上位がマップでない入力に順 6 の失敗が含まれるときは、順 6 の失敗が先に返る(例: `- &a [*a]\n` は、`rootNotMap` ではなく、再帰の `syntax`)。実装は、順 6 の走査を終えてから最上位を確認する。
- 順 3 は順 4 より先: 1 MiB を超え、かつ UTF-8 でない入力は `tooLarge`。順 3 は順 5 より先: 1 MiB を超える入力は、中身が壊れていても `tooLarge`。
- 順 5(文法)は、順 6(複数の文書など)より先。たとえば `a: 1\n---\nb: [1\n` は、2 つ目の文書の文法の誤りを `syntax` として返す(行は [03 第 13.4 節](03-definition-format.md))。

## 3. 取り込み(Intake)

| 順 | 条件 | `kind` | 理由(日本語の原文) |
|----|------|--------|----------------------|
| 1 | ファイルを開こうとして「存在しない」 | `fileMissing` | `指定の場所にファイルがありません` |
| 2 | ファイルを開けない。権限がない | `unreadable` | `読み取りの権限がありません` |
| 2' | 同、ディレクトリだと分かるとき | `unreadable` | `通常のファイルではありません` |
| 2'' | 同、その他の失敗 | `unreadable` | `読み取りに失敗しました` |
| 3 | 開いたファイルの情報(大きさ)が取れない | `unreadable` | 権限なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 3' | 通常のファイルでない(パイプ、デバイスなど) | `unreadable` | `通常のファイルではありません` |
| 4 | 大きさが 1 MiB(1,048,576 バイト)を超える | `tooLarge` | `入力が上限(1 MiB)を超えています` |
| 5 | 読み取り結果が上限を超える(順 4 のあとに大きくなった場合) | `tooLarge` | 同上 |
| 6 | 読み取りの途中の失敗 | `unreadable` | 権限なら `読み取りの権限がありません`、他は `読み取りに失敗しました` |
| 7 | UTF-8 として読めない | `unreadable` | `UTF-8 として読めません` |

実装(C#)の対応。**条件の順序と理由の文言が必須**であり、API の選び方は、次を標準とする。

- 順 1〜2'': **先にファイルを開く**: `new FileStream(path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite, bufferSize: 1, FileOptions.SequentialScan)`。失敗したとき、`FileNotFoundException`、`DirectoryNotFoundException` なら順 1。`UnauthorizedAccessException` なら、`Directory.Exists(path)` が真のとき順 2'(.NET は、ディレクトリを開こうとすると、`UnauthorizedAccessException` を投げると考えられる(未確認)ので、この確認で、権限と区別する)、そうでなければ順 2。それ以外(`IOException`、`PathTooLongException`、`ArgumentException`(パスに NUL を含む場合)、`NotSupportedException`)は順 2''。空文字列のパスは順 1([03 第 3 節](03-definition-format.md)と同じ決定)。
- 順 3・3'・4: 開いた `FileStream` の `Length`(開いたものの大きさ。取得に失敗すれば順 3。`NotSupportedException` は、シークできないストリームのとき(パイプなど)に投げられる)。`fs.CanSeek` が偽なら順 3'(パイプ、一部のデバイス。**この判定は、公式ドキュメントでは確かめていない: 未確認**)。`Length` が 1,048,576 を超えれば順 4。
  - **FIFO(名前つきパイプ)の `Open` が、ブロックして戻らない可能性**がある(未確認)。対処は [03 第 3 節](03-definition-format.md)の注 1 と同じ(`libc` の `open` を `O_NONBLOCK` つきで呼ぶなど。実装が決める)。受け入れ試験は [03 第 7.5 節](03-definition-format.md)の #13 と共有する。
- 順 5・6: `FileStream.Read(byte[], int, int)` を繰り返し、**上限 + 1 バイトまで**を読む(1 回の `Read` が、要求より少なく返すことがあるので、0 が返るか、合計が上限 + 1 バイトに達するまで繰り返す)。**`File.ReadAllBytes`、`File.ReadAllText` は使わない**。`using` で必ず閉じる。
- 順 7: [03 第 3 節](03-definition-format.md)の順 9 と同じ(先頭の `EF BB BF` をバイト列で取り除き、`new UTF8Encoding(false, true)` で厳格に復号。`DecoderFallbackException` なら順 7)。

- 先にファイルを開き、**開いたもの**の情報で大きさを調べる。開いてから調べるので、調べたあとにファイルが差し替わっても、読み取りの結果と食い違わない。
- **ちょうど 1 MiB は受理**し、1 バイトでも超えれば `tooLarge`。
- 権限のない(モード 000 の)ファイルは、大きさにかかわらず `unreadable`(開く操作が先に失敗するので、1 MiB を超えるモード 000 のファイルも `unreadable`)。ただし、権限の確認を迂回する利用者(root など)では、この結果にならない(その場合は、通常どおり読める)。
- 行番号は付かない。
- 空のファイル(0 バイト)は、空の入力として次へ進む(YAML は `rootNotMap`(`文書が空です`)、JSON は `syntax`)。
- OS による権限・種別の判定の細部(Windows での `IOException` の `HResult` など)は、実装に任せてよい(未確認)。必須なのは、上の表の条件の順序と、各理由の文言である。
- 定義ファイルの取り込み([03 第 3 節](03-definition-format.md))とは、上限超過と UTF-8 の理由の文言が違う(ここは `入力が上限(1 MiB)を超えています`、`UTF-8 として読めません`)。また、定義ファイルと違い、**拡張子の確認はしない**。

## 4. 読み取り

### 4.1 受理する文法

- `--to yaml`(入力は JSON)のとき: JSON は、[03 第 4 節](03-definition-format.md)の形式(RFC 8259 の厳格な形式。コメント・末尾カンマ・重複キー・対にならないサロゲートの拒否を含む)で、[03 第 4.6 節](03-definition-format.md)の自前の字句・構文解析で読む。`Utf8JsonReader` は使わない(03 第 4.4 節)。
- `--to json`(入力は YAML)のとき: YAML は、[03 第 5 節](03-definition-format.md)の部分集合を、[03 第 7 節](03-definition-format.md)のライブラリの設定と補完で読む。要点: YAML 1.2 のコアスキーマ、ブロックとフローのマップ・リスト、引用符なしと引用符つきとブロックのスカラー、コメント(捨てる)、アンカーとエイリアス(展開する)、マージキー `<<`(展開する)。**拒否**: タグ(標準のタグも)、複数の文書、非文字列のキー、重複したキー、タブのインデント。さらに、[03 第 5.1 節](03-definition-format.md)の「狭い」点も同じ(U+0085・U+2028・U+2029・CR だけの改行・制御文字・ASCII 英数字と `-`、`_` 以外を含むアンカー名は、`syntax`)。
- 読み取りの誤りの種類・理由・行は、[03 第 12.3 節](03-definition-format.md)の `syntax`/`tooLarge` の理由の表と同じ(`YAML の文法に誤りがあります`、`JSON の文法に誤りがあります`、`キーが重複しています`、`キーは文字列で書きます`、`タグは使えません`、`複数の文書は書けません(1 ファイルに書ける文書は 1 つです)`、`アンカーが自分自身を含んでいます`、`マージキーの値がマップではありません`、`入れ子が深すぎます(上限は 32 段)`、`要素数が上限(100000)を超えています`、`文字の大きさが上限(16 MiB)を超えています`)。行の出し方も、[03 第 13 節](03-definition-format.md)と同じ。
- 入力の先頭の BOM(`EF BB BF`)は受理される(バイト列の段階で取り除く)。LF・CRLF の両方を受理する。
- YAML の対にならないサロゲートのエスケープ(`"\ud800"`)は、`syntax`(`YAML の文法に誤りがあります`。[03 第 7.4 節](03-definition-format.md) #12)。

### 4.2 上限(03 と同じ)

| 上限 | 値 | 超過したときの失敗 |
|------|----|--------------------|
| 入力の大きさ | 1 MiB | `tooLarge`(Intake) |
| 要素数 | 100,000 | `tooLarge` |
| 文字の大きさ | 16 MiB | `tooLarge` |
| 入れ子の深さ | **根のマップを数えず 32 段まで** | `syntax`(33 段目) |

数え方は [03 第 6.3 節](03-definition-format.md)の規定のとおり(要素数にはキーも数える、エイリアスは参照のたびに参照先を数える、文字の大きさは値のバイト数など)。ここでは、JSON の入力にも同じ上限があり、同じ境界になる(例: `{"a":[0,0,...]}` で、0 を n 個並べるとき、n = 99,997 まで受理、99,998 で失敗。YAML も同じ)。

数千〜数十万段の入れ子の入力、アンカーの入れ子による爆発的な展開、マージキーによる増幅は、いずれも、プロセスを落とさず、30 秒以内に、上の上限の失敗(または `syntax`)で終わること(必須)。木の走査・書き出しを再帰で書くと、`StackOverflowException`(捕捉できない)で落ちる([03 第 6.4 節](03-definition-format.md))ので、**明示のスタック**で書く。読み取りの途中の入れ子の上限(1,000 段。[03 第 6.4 節](03-definition-format.md))も、同じ。実測は未実施(未確認)。

### 4.3 最上位の確認(RootCheck)

| 入力 | 結果 |
|------|------|
| 最上位がマップ(YAML の `{a: 1}`、JSON の `{}` を含む) | 次へ |
| YAML で、文書が 0 個(空の入力、コメントと空行だけ) | `rootNotMap`、理由 ``文書が空です``、行なし |
| 最上位が、マップでない(YAML のリスト・スカラー・null(`---` だけの文書)、JSON の配列・数・文字列・`null`) | `rootNotMap`、理由 ``最上位がマップではありません``、行は最上位のノードの位置の行 |

- 定義ファイルと違い、**空の入力や null の文書を、空のマップとして扱わない**(変換器は、中身のない入力をマップにしない)。
- JSON で、空の入力(0 バイト、空白だけ)は、`rootNotMap` ではなく `syntax`(JSON は値が 1 つ必要)。
- 空のマップ(`{}`)は受理され、変換できる(第 8 節)。
- `---` だけの文書(最上位が null)の行は、`---` の行(1 行目。[03 第 13.2 節](03-definition-format.md))。
- 実装の注意: 定義の読み込みでは、文書が 0 個、または最上位が null のとき、空のマップにして続ける([03 第 6.7 節](03-definition-format.md))。変換器は、同じ読み取りのメソッド(`TreeReader.ReadTree`)を使い、その手前の結果(`TreeOk.Root` が `null`(文書が 0 個)、`NullNode`(最上位が null))を見分けられる形で受け取る。

### 4.4 内部表現と木の等価

読み取りと展開の結果は、[03 第 6.1 節](03-definition-format.md)の木にする。

| 種類 | 内容 |
|------|------|
| `NullNode` | 値なし |
| `BoolNode` | `bool` |
| `IntNode` | `long`(64 ビット符号つき整数の範囲) |
| `HugeIntNode` | 範囲外の整数(値は持たない。第 5 節で拒否) |
| `FloatNode` | `double`(IEEE 754 binary64)と、`Overflow` の印 |
| `StringNode` | `string`(対にならないサロゲートを含まない) |
| `ListNode` | 木の `IReadOnlyList<TreeNode>` |
| `MapNode` | `MapEntry`(文字列のキー, 木)の `IReadOnlyList<MapEntry>`。**キーは重複しない。記述順を保つ** |

- 変換器は、`HugeIntNode` と、`Overflow` の印のある浮動小数を、第 5 節のとおり記録して失敗させる。
- **内部表現の等価**(往復の確認に使う。**非再帰の関数**で、明示のスタックで比べる): 型(ノードのクラス)が違えば不等(`"1"` と 1、1 と 1.0、`true` と `"true"`、null と `"null"`)。整数は、`long` の値が等しいこと。浮動小数は、ビット表現が同じなら等しい(`BitConverter.DoubleToInt64Bits(a) == BitConverter.DoubleToInt64Bits(b)`。ただし、NaN どうしは、ビット表現が違っても等しい(`double.IsNaN` が両方で真)。**`0.0` と `-0.0` は異なる**(ビット表現が違う)。`==` は、`0.0 == -0.0` が真で、`NaN == NaN` が偽なので、使わない)。マップは、**キーの順序を無視**して比べる(`Dictionary<string, TreeNode>`(`StringComparer.Ordinal`)に入れて、キーごとに比べる)。リストは順序を含めて比べる。`record` や `object.Equals` の自動の等価は使わない([03 第 6.1 節](03-definition-format.md))。

## 5. 表せない値(`unrepresentable`)

展開の途中で見つけた「相手の形式で表せない値」のうち、**入力に現れる順で最初の 1 つ**だけを記録し、走査の終了後に返す(上限超過・マージキーの誤りなど、第 2 節の順 6 の失敗は、これより優先する)。展開の走査は、捨てられるマージのエントリも訪れるので、そこにある表せない値も、記録の対象である。

| 値 | 理由(日本語の原文) | 対象の入力 | 例 |
|----|----------------------|------------|-----|
| 範囲外の整数(64 ビット符号つき整数に収まらない。`HugeIntNode`) | `数値が表せる範囲を超えています` | JSON、YAML | `{"a": 9223372036854775808}`、`a: 0xFFFFFFFFFFFFFFFFFF` |
| 範囲を超える浮動小数(`Overflow` の印) | `数値が表せる範囲を超えています` | JSON、YAML | `{"a": 1e400}`、`a: 1e999`、`a: -1e999` |
| NaN、無限大(YAML の `.nan`、`.inf`、`-.inf`、`+.inf` など。`Overflow` の印がない、値が NaN・±∞ の浮動小数) | `NaN と無限大は JSON で表せません` | YAML(`--to json` のときだけ) | `a: .nan`、`a: [1, .inf]` |
| 長すぎるキー(1,024 文字を超える。文字数で数える) | `キーが長すぎます(上限 1024 文字)` | JSON(`--to yaml` のときだけ。YAML の単純キーの上限のため) | 1,025 文字のキー |

- 失敗の表示: `kind` は `unrepresentable`、行なし。**場所(`KeyPath`)**がつく。
- **場所の書式**: キーを `.` でつなぐ。リストの要素は `[添字]`(0 始まり。直前のキーに続けて、`.` なしで書く)。リストが最上位に来ることはない(最上位はマップ)。キー名は、制御文字・書式文字・サロゲートをエスケープし(`\n`、`\r`、`\t`、その他は `\u{16進小文字}`。対象の文字と切り詰めは [03 第 12.2 節](03-definition-format.md)と同じ)、64 文字(エスケープ後のコードポイントの数)を超えると、64 文字で切って `…` を付ける。例: `job[1].note`、`a.b`、`a[2]`。マージで取り込まれる値の中の表せない値の場所は、`<<` のキーを経由した経路(`a.<<.x`)とする(この仕様の決定)。エイリアスの中の表せない値の場所は、エイリアスを書いた場所の経路とする。
  - 実装の指針: 経路は、走査の明示のスタックから、**最初の 1 件を記録するときだけ**文字列にする(すべてのノードで作らない。`StringBuilder` を使う)。
- **長すぎるキーの検査**: 内部表現のキー(エスケープを解いた後の文字列)の**コードポイントの数**で判定する(`char` のうち、`char.IsLowSurrogate` でないものの数。`string.Length` ではない。サロゲートの対は 1 と数える)。1,024 文字ちょうどは受理。**既知の制限**: YAML の読み取りの単純キーの上限は、UTF-16 のコード単位で数える([03 第 5.1 節](03-definition-format.md))ので、非 BMP の文字を多く含む 1,024 文字以下のキーは、書き出せても、読み戻しで拒否されうる。また、引用符つきで書くキー(第 8 節。非 ASCII を含むもの、特殊な文字を含むもの)は、引用符とエスケープを含めた長さが 1,024 を超える(1,022 文字前後以上のキー)と、読み戻しで拒否されうる。これらは、他の言語版と同じ規則を保つための既知の制限であり、第 9 節の往復の保証の例外である(未確認: 実機での確認)。
- YAML の NaN・無限大は、`--to json` のときだけ拒否する。`--to yaml` の入力は JSON なので、NaN・無限大は文法として存在しない。
- 範囲外の数は、変換後の形式が YAML でも JSON でも拒否する(内部表現が 64 ビットのため)。
- 入力に現れる順の例: `a: 1\njob:\n  - id: x\n  - id: y\n    note: .nan\n  - z: .inf\nlater: .nan\n`(`--to json`)は、最初の `job[1].note` を返す。

読み取り(Resolve)のメソッドは、変換器のために、記録の機能を持つ(例):

```csharp
namespace Conductor.Definition;

public sealed record Unrepresentable(string Reason, string KeyPath);
```

[03 第 14.2 節](03-definition-format.md)の `TreeReader.ReadTree(text, format, fileLabel, convertTo)` が、変換器のとき(`convertTo` が `DefinitionFormat.Json` か `DefinitionFormat.Yaml`)に、最初の `Unrepresentable` を `TreeOk.FirstUnrepresentable` に入れて返す。定義の読み込みでは `convertTo` が `null` で、記録しない。

## 6. 書き出し(共通)

- 書き出しの前に、最上位は(必ず)マップになっている(第 4.3 節)。
- **各マップのキーは、入力の記述順のまま出力する**(キーをソートしない)。マージキーで取り込まれたエントリは、`<<` のエントリのあった位置に並ぶ([03 第 5.5 節](03-definition-format.md))。リストの順序も保たれる。コメントは捨てられる。
- 変換結果の最後は改行(LF)で終わる。改行は LF だけ。
- 木の深さは、読み取りの上限により 33 以下(根を含む)だが、**書き出しも、メソッドの再帰を使わない明示のスタックで書く**(必須: 実装が、深さの上限の変更・不具合で、`StackOverflowException`(捕捉できず、プロセスが終了する。[03 第 4.6 節](03-definition-format.md))を起こさないために。深さ 33 の再帰は、実際には、スタックに遠いが、この仕様は再帰に頼らないことを規定とする)。
- 出力は、`StringBuilder` に溜めて、最後に `ToString()` で 1 つの文字列にする(`string` の `+=` の繰り返しは避ける)。`StringBuilder.Append(char)` と `Append(string)` を使い、`AppendFormat`・補間文字列(`$"..."`)を、数の書式化に使うときは、`CultureInfo.InvariantCulture` を明示する(`string.Create(CultureInfo.InvariantCulture, $"...")`、または `ToString(CultureInfo.InvariantCulture)`)。

### 6.1 浮動小数の書き方(YAML と JSON で共通)

内部表現の浮動小数を、**必ず浮動小数と読み戻される形**で書く。

- NaN、+∞、-∞: YAML は `.nan`、`.inf`、`-.inf`。JSON は書けない(第 5 節で拒否済み)。
- 0: 正の 0 は `0.0`、負の 0 は `-0.0`。**符号は、`double.IsNegative(d)`(確認: `Double.IsNegative` が存在する。符号ビットを見る。この項目の公式ドキュメントでの確認は未実施)、または `BitConverter.DoubleToInt64Bits(d) < 0` で判定する**(`d < 0` は、`-0.0` で偽になる)。
- それ以外は、往復で同じ値になる**最短の桁数**の 10 進で書く。次の手順で組み立てる(**`double.ToString()` の出力をそのまま使わず、桁と指数を取り出して、自分で並べる**)。
  1. `string r = Math.Abs(d).ToString("R", CultureInfo.InvariantCulture)` を得る。.NET Core 3.0 以降、`double` の `ToString()`、`ToString("G")`、`ToString("R")` は、**往復できる最短の文字列**を返す(確認(出典: .NET Core 3.0 の浮動小数の書式化・解析の改善についての .NET ブログ(`ToString()`、`"G"`、`"R"` は、最短の往復できる文字列を返す、と明記)と、標準の数値書式の公式ドキュメント(`double` の既定の書式は、往復できる最小の桁数。`"R"` は、.NET Framework と 3.0 より前の .NET Core では、一部の値で往復に失敗する))。したがって、**最小の対象を .NET 8 以降とし(02 章の決定)、3.0 より前を考えない**。`r` の形は、`123.456`、`1E+16`、`1.5E-07` など(整数の桁、小数点と小数の桁、指数部 `E` + 符号 + 数字)がありうる。どの形で返るか(指数形に切り替わる閾値、指数部の桁数)は、公式ドキュメントでは確かめていない(未確認)ので、**次の 2 で、形に依存せずに桁と指数を取り出す**。
  2. `r` を、(a) `E` または `e` で、仮数部と指数部(無ければ 0)に分ける。(b) 仮数部から `.` を取り除いた数字の列を `digits`、`.` より前の桁数を `pointPos`(`.` が無ければ `digits` の長さ)とする。(c) `digits` の先頭の 0 を取り除くたびに `pointPos` を 1 減らす。(d) `digits` の末尾の 0 を取り除く(`pointPos` は変えない)。(e) 十進の指数 `x = pointPos + (指数部) - 1`(値 = `d.ddd × 10^x`、`d` は `digits[0]`)。`digits` が空になるのは 0 のとき(上で処理済み)。
  3. **指数形**にするのは、`x >= 16` または `x <= -5` のとき(絶対値が 1e16 以上、または 1e-4 未満)。書式: `digits[0]` + (桁が 2 つ以上なら `.` + 残りの桁) + `e` + `x`(10 進。**`+` を付けず、先頭の 0 を付けない**。負なら `-`)。例: `1e16`、`1e21`、`1e-5`、`1.5e-7`、`1.2345678901234568e16`、`5e-324`、`1.7976931348623157e308`。
  4. それ以外は、**10 進の小数表記**: `x >= 0` なら、整数部は `digits` の先頭 `x + 1` 桁(足りなければ 0 で埋める)、小数部は残りの桁(無ければ `0`)。`x < 0` なら `0.` + 0 を `-x - 1` 個 + `digits`。整数値でも必ず小数部を付ける(`1.0`、`100.0`)。例: `1e15` は `1000000000000000.0`、`0.0001` は `0.0001`、`0.1` は `0.1`、`9999999999999998.0` は `9999999999999998.0`。
  5. 負なら、先頭に `-` を付ける。
  - 閾値の根拠: 他の言語版の書式(指数形に切り替えるのは、1e16 以上と 1e-4 未満)と同じ出力にそろえるため。この閾値は、この仕様の決定である。
- 指数形(`1e16`)は、JSON でも YAML でも、読み戻すと浮動小数になる(JSON は指数部を持つ数、YAML は [03 第 5.2 節](03-definition-format.md)の順 7)。
- 確認した例(上の手順を、手で適用した結果。実装時に、単体テストにする): `1.0` → `1.0`、`100.0` → `100.0`、`1e15` → `1000000000000000.0`、`1e16` → `1e16`、`1e21` → `1e21`、`1e-5` → `1e-5`、`0.0001` → `0.0001`、`0.00009999` → `9.999e-5`、`0.1` → `0.1`、`-0.0` → `-0.0`、`9999999999999998.0` → `9999999999999998.0`、`0.30000000000000004` → `0.30000000000000004`、`12345678901234567.0`(入力。値は 12345678901234568)→ `1.2345678901234568e16`、`5e-324` → `5e-324`、`double.MaxValue` → `1.7976931348623157e308`。
- **実装時の必須の試験**: ビット列から作ったランダムな `double`(20 万個以上。0、`-0.0`、`double.Epsilon`、`double.MaxValue`、`1e15`、`1e16`、`1e21`、`1e-5`、`1e-4` などの境界を含む)で、(a) 書き出した文字列を、`double.Parse(s, NumberStyles.Float, CultureInfo.InvariantCulture)` で読み戻すと、ビット表現が元と同じ、(b) 文字列が、上の規則(指数形の閾値、`.0` の付与、指数部の整形)に合う。
- `System.Text.Json` の `Utf8JsonWriter.WriteNumberValue(double)` や `JsonSerializer` の浮動小数の書式は、**使えない**(指数形の閾値と、`+`・桁の書式が、この規定と一致する保証がない。公式ドキュメントでは確かめていない)。

### 6.2 整数・真偽値・null

- 整数: 10 進(64 ビット符号つき整数。`-9223372036854775808` を含む)。**`long.ToString(CultureInfo.InvariantCulture)`**(`NumberFormatInfo.NegativeSign` が、文化によって変わらないよう、不変文化を明示する)で書く。桁は 19 桁以下。
- 真偽値: `true` / `false`(`bool.ToString()` は `True`/`False` を返すので、使えない。ノードの種別から `"true"`、`"false"` を選ぶ)。
- null: `null`。

### 6.3 整数の精度、`double`、`decimal`、`BigInteger`(決定)

| 場面 | 規定 |
|------|------|
| 入力の整数の字句(YAML の 10 進・`0x`・`0o`、JSON の整数) | 桁数による打ち切りと `TryParse`、または自前の累積(`ulong`、`UInt128`)で値を得る([03 第 4.2・5.2 節](03-definition-format.md))。範囲を超えるものは、値を求めずに(桁数で)`HugeIntNode` にする |
| 木 | 整数は `IntNode`(`long`)。浮動小数は `FloatNode`(`double`)。**型が違えば別の値**(JSON の `1` と `1.0`、YAML の `1` と `1.0` は、変換でも区別する)。真偽値は `BoolNode`(整数ではない) |
| 出力 | 整数は `long.ToString(InvariantCulture)`。浮動小数は第 6.1 節 |
| 浮動小数の書き方の整数値 | 値が整数でも、書き方に小数部か指数部があれば浮動小数。2^53 を超える値は、`double` の最も近い値になり、桁が変わりうる(`9007199254740993.0` → 値 9007199254740992.0 → 出力 `9007199254740992.0`。`12345678901234567.0` → `1.2345678901234568e16`)。これは浮動小数の性質であり、エラーにしない |
| 比較・検査 | 範囲の比較は `long` どうしで行う。`double` に変換してから比べない。`(double)long` と `(long)double` のキャストを、検査に使わない(2^53 を超えると桁が落ちる。範囲外の `double` から `long` へのキャストの結果は、実装・環境で変わりうる(未確認)) |
| `decimal` | **使わない**: 有効桁が約 28 桁で、`double` の範囲(±1.8e308、5e-324)を表せない。JSON の `1e400`・`1e-400` の判定や、浮動小数の最短の書き出しに使えない。整数にも `long` で足りる |
| `System.Numerics.BigInteger` | **使わない**: 範囲外の整数は、拒否するので、値を保つ必要がない。巨大な桁数の字句の解析は、時間がかかる(桁数の打ち切りを先に行う) |

- 例: JSON `{"a": 9007199254740993}`(2^53 + 1)→ YAML `a: 9007199254740993`(値が保たれる。`double` を経由すると 9007199254740992.0 になって誤る)。YAML `a: 9223372036854775807` → JSON `"a": 9223372036854775807`。YAML `a: -9223372036854775808` → JSON でも同じ。`{"a": 9223372036854775808}` と `a: 9223372036854775808` は、`unrepresentable`(範囲外の整数)。

### 6.4 文字列とサロゲート・`Rune`(決定)

- .NET の `string` は、対にならないサロゲート(U+D800〜U+DFFF の単独の `char`)を持てる。UTF-8 への符号化は、`Encoding.UTF8`(置き換え)か `UTF8Encoding(false, true)`(例外)で結果が違う(確認(出典: `UTF8Encoding` の公式ドキュメント): 引数なしの構築は、例外を投げない)。**変換器の木の文字列は、対にならないサロゲートを含まない**。入力が UTF-8 のバイト列から厳格に復号されること([03 第 3 節](03-definition-format.md))、JSON の `\ud800` と YAML の `"\ud800"` のエスケープが拒否されること([03 第 4、7.4 節](03-definition-format.md))、前半と後半のエスケープが続けて書かれた JSON の `\ud83d\ude00` が、1 つの文字(U+1F600。UTF-16 では、前半と後半の 2 つの `char`)になること、によって保たれる。したがって、書き出しの文字列は、常に UTF-8 に符号化できる。
- 書き出しは、`string` を **`char` ごと**に走査してよい(エスケープの対象の文字は、すべて BMP の `char` 単独で判定でき、サロゲートの `char`(U+D800〜U+DFFF)は、エスケープの対象ではなく、そのまま書く。前半の直後に後半が来るので、対は、そのまま保たれる)。コードポイントで走査する(`EnumerateRunes()`)必要はない。**対にならないサロゲートを見つけたら(防御)、内部の失敗として、第 10 節ではなく、[10. エラーと終了コード](10-errors-and-exit-codes.md)の想定外の内部失敗(終了コード 70)にする**(木にはあり得ない)。
- 変換結果の文字列を標準出力へ書く符号化(UTF-8)と BOM なしの扱いは [08](08-output-and-i18n.md) に従う。変換の誤りの表示の `<file>` には、OS から得た文字列(単独のサロゲートの可能性がある。[03 第 12.2 節](03-definition-format.md))が入りうるので、第 10 節のとおり、表示の前にエスケープする。
- 書記素(結合文字など)は、考慮しない。文字列は、コードポイントの並びとして、そのまま書く(正規化しない)。

## 7. JSON の書き出し(`--to json`)

**すべて必須**(出力の文字列が一致する)。

**レイアウト**(インデントは半角スペース 2 個。タブは使わない。行末に空白を残さない):

- 空のマップ: `{}`。空のリスト: `[]`。
- 空でないマップ: `{` + 改行、各エントリを `<インデント + 2>"<キー>": <値>` で、エントリの間を `,` + 改行で区切り、最後のエントリの後に改行、`<インデント>}`。キーと値の間は `": `(コロンの後に半角スペース 1 個)。
- 空でないリスト: `[` + 改行、各要素を `<インデント + 2><値>` で、`,` + 改行で区切り、最後の後に改行、`<インデント>]`。**要素は 1 行に 1 つ**(短い配列も 1 行にまとめない)。
- 最上位の値の後ろに LF を 1 個付ける。

**文字列(値もキーも同じ)**: `"` で囲み、次のとおりエスケープする。

| 文字 | 出力 |
|------|------|
| `"` | `\"` |
| `\` | `\\` |
| U+000A | `\n` |
| U+000D | `\r` |
| U+0009 | `\t` |
| U+0008 | `\b` |
| U+000C | `\f` |
| そのほかの U+0000〜U+001F、U+007F〜U+009F、U+2028、U+2029、U+FEFF、U+FFFE、U+FFFF | `\u` + 16 進の**小文字** 4 桁(例: `\u001b`、`\u007f`、`\u2028`)。`((int)c).ToString("x4", CultureInfo.InvariantCulture)` で得る |
| それ以外(`/`、`<`、`>`、`&`、非 ASCII、絵文字(サロゲートの対)を含む) | そのまま書く(エスケープしない) |

- **`System.Text.Json` の書き出しは使えない**: `Utf8JsonWriter` と `JsonSerializer` は、既定で、`<`、`>`、`&`、`'`、`+` や非 ASCII の文字をエスケープする(`JavaScriptEncoder.Default` の既定の挙動。この文書の作成時に、公式ドキュメントで確認していない: 未確認)。`JavaScriptEncoder.UnsafeRelaxedJsonEscaping` などで挙動を変えても、U+007F〜U+009F、U+2028、U+2029、U+FEFF の扱いが、この規定と一致するかは未確認。インデントの書式(`WriteIndented`)も、この規定(配列の要素は 1 行に 1 つ、`": ` の書式、改行は LF 固定か `Environment.NewLine` か)と一致する保証がない(未確認)。**自前で書く**(必須)。数・真偽値・null は、第 6 節のとおり。

JSON の出力例(YAML の入力 `a: 1.5e-7\nb: [1, [2, []], {}]\nc: "x\ty"\n`):

```json
{
  "a": 1.5e-7,
  "b": [
    1,
    [
      2,
      []
    ],
    {}
  ],
  "c": "x\ty"
}
```

## 8. YAML の書き出し(`--to yaml`)

自前の書き出し(ブロック形式の YAML)。YamlDotNet の書き出し(`Emitter`、`Serializer`、`SerializerBuilder`、`YamlStream.Save`)は**使わない**(出力の文字列を、この規定に一致させるため。`Emitter` が、スカラーの引用符の判定を、YAML 1.1 の語、行の折り返し、既定のインデントなどで、独自に行う)。**すべて必須**(出力の文字列が一致する)。

**レイアウト**

- 最上位のマップが空: `{}` + 改行。空でなければ、各エントリを書く。
- マップのエントリ: `<キー>: <値>`。値がスカラー、空のリスト(`[]`)、空のマップ(`{}`)なら同じ行に書く。値がコレクションなら、`<キー>:` のあと改行し、子を**2 スペース深く**書く。
- リストの要素: `- <値>`。要素がスカラー・`[]`・`{}` なら同じ行。要素がマップなら、最初のエントリを `- ` と同じ行に書き、残りのエントリを、`- ` の内容の位置(ダッシュの桁 + 2)に揃える。要素がリストなら、`- - 1`(最初の要素を同じ行)の形で、残りの要素も、内容の位置に揃える。
- リストは、親のキーより 2 スペース深く書く(`job:` の次の行に `  - id: a`)。
- インデントは 2 スペース。タブは使わない。行末に空白を残さない。
- 実装は、**明示のスタック**で、ノードと「次に書く子の番号」と「インデントの桁」と「最初のエントリを同じ行に書くか」を持つ。

**スカラー**

- 整数・真偽値・null・浮動小数: 第 6 節のとおり。
- 文字列(値もキーも同じ規則): 次の条件を**すべて**満たすときだけ、引用符なし(plain)で書く。1 つでも外れたら、二重引用符で囲む。
  1. 空でない。
  2. 先頭が、ASCII の英字(`A-Za-z`)、`_`、`/` のどれか(数字・`-`・`.` などで始まるものは、数値や記号に読まれうるので引用符)。
  3. 末尾が空白でない。
  4. すべての文字が、ASCII の英数字、`_`、`-`、`.`、`/`、半角スペース のどれか。
  5. 半角スペースが 2 つ連続しない。
  6. YAML 1.1 の語(`y`、`Y`、`yes`、`Yes`、`YES`、`n`、`N`、`no`、`No`、`NO`、`on`、`On`、`ON`、`off`、`Off`、`OFF`)でない。
  7. [03 第 5.2 節](03-definition-format.md)の規則で解決して文字列になる(`true`、`false`、`null`、`Null`、`NULL`、`True` などは引用符)。この判定は、読み取りと**同じメソッド**(引用符なしのスカラーの型の判定。例: `ScalarResolver.Resolve(string)` が `StringNode` 相当を返すか)を呼んで行う。
  - 条件 1〜5 は、**自前の文字の走査**で判定する(`c is (>= 'A' and <= 'Z') or (>= 'a' and <= 'z') or '_' or '/'` など)。`Regex` を使うなら `\A[A-Za-z_/][A-Za-z0-9_./ -]*\z` で全体に一致させ、末尾が半角スペースでなく、`"  "`(半角スペース 2 つ)を含まない、と言い換えられる(**`^…$` を使わない**: `$` は末尾の `\n` の直前にも一致し、`"a\n"` が通ってしまう。`\w`・`\d`・`char.IsLetterOrDigit` も使わない。[03 第 5.2 節](03-definition-format.md))。
  - **条件 6 の方針と理由(この版の決定)**: 出力は、YAML 1.2 のコアスキーマのローダーだけでなく、**YAML 1.1 の型の解決をするローダー(YAML 1.1 の既定の型の表を使うものなど)でも、文字列が文字列のまま読み戻される**ようにする。YAML 1.1 の型の表では、`y`・`n`(`Y`・`N` を含む)・`yes`・`no`・`on`・`off` とその大文字の形が真偽値になりうる(`y`・`n` を真偽値にするローダーがあるかは未確認)ので、値でもキーでも読み誤られる。このため、条件 6 の 16 語は、1.2 では文字列でも、必ず引用符で囲む(読み誤るローダーの範囲を、確かめきれないので、安全側に倒す)。この仕様の読み取り([03 第 5.2 節](03-definition-format.md))は、これらを(引用符なしでも)文字列として読むので、条件 6 は、この仕様の読み取りとの往復には要らないが、他のツールが出力を読む場合の誤読を避けるために置く。条件 6 を外す(plain を広げる)変更は、出力の文字列が変わるので、この仕様の変更になる。条件 7 は、この仕様の読み取りと同じメソッドで判定するので、読み取りの規則を変えたとき、出力も同時に変わる(往復の保証のため)。
  - plain になる例: `hello`、`echo hello world`、`/bin/run.sh`、`a-b_c.d`、`prog build --release`、`inf`、`_x`、`a b`。引用符になる例: `yes`、`no`、`on`(キー `on` は `"on": warning`)、`off`、`y`(キー `y` は `"y": []`)、`n`(キー `n` は `"n": null`)、`true`、`null`、`~`、`1`、`-1`、`1.5`、`0x1F`、`""`(空)、` lead`、`trail `、`<<`、`a: b`、`a #b`、`.nan`、`1e3`、`Yes`、`Y`、`@end`、`-a`、`x  y`、`a `、非 ASCII を含む文字列(`"夜間バッチ"`、`"é key"`)。
- 二重引用符の中のエスケープ: `"` → `\"`、`\` → `\\`、改行 → `\n`、復帰 → `\r`、タブ → `\t`。そのほかの制御文字(U+0000〜U+001F、U+007F〜U+009F)と U+2028、U+2029、U+FEFF、U+FFFE、U+FFFF は `\uXXXX`(16 進の**大文字** 4 桁。例: `\u001B`、`\u007F`。`((int)c).ToString("X4", CultureInfo.InvariantCulture)` で得る)。その他の文字(非 ASCII、絵文字を含む)は、そのまま書く。例: `"a\u2028b \u007F é 😀"`。(JSON の書き出しは小文字の 16 進。第 7 節。U+0008 と U+000C は、JSON では `\b`・`\f`、YAML の二重引用符では `\u0008`・`\u000C`。)
- キー `<<` は、必ず引用符で囲む(マージキーとして読み戻されないように。上の plain の規則で、`<` で始まるので引用符になる)。
- 非 ASCII を含む文字列は、常に二重引用符で囲む(値もキーも)。
- **長いキー**: 1,024 文字を超えるキーは書き出せない(第 5 節で `unrepresentable` として拒否済み。YAML の単純キーの上限のため。[03 第 5.1 節](03-definition-format.md))。

例(JSON の入力を `--to yaml` で変換した出力):

```yaml
format_version: 1
pipeline:
  name: nightly
job:
  - id: extract
    command: extract --all --since yesterday
    warning_exit_codes:
      - 3
      - 4
  - warning_exit_codes:
      - 3
      - 4
    id: transform
    command: "transform \"in dir\" $HOME"
    success_exit_codes:
      - 0
```

入れ子のリストとマップの例(入力 JSON `{"a": [[1,2],[3,[4]]], "b": [{"x":1,"y":[{"z":2}]}]}`):

```yaml
a:
  - - 1
    - 2
  - - 3
    - - 4
b:
  - x: 1
    "y":
      - z: 2
```

空のマップ、空のリスト、null、浮動小数を含む入力 JSON `{"x": {}, "y": [], "n": null, "f": 1.0, "e": 1e21}` は次になる(キー `y` と `n` は YAML 1.1 の語なので、引用符つき)。

```yaml
x: {}
"y": []
"n": null
f: 1.0
e: 1e21
```

最小の入力 `{}` は、`{}` + 改行になる。

## 9. 往復の保証

- 保証するのは、**木の等価**である(第 4.4 節。マップのキーの順序は無視、リストの順序は有意)。入力を読んだ内部表現と、変換結果を(変換後の形式として)読み戻した内部表現が、等しい。さらに、変換結果を元の形式へ戻した結果の木も、元の木と等しい。
- 保証されないもの: コメント、アンカー・エイリアス・マージキー(展開される。出力に `<<`・`*`・`&` は残らない)、引用符・文字列の書き方(plain と引用符の別、ブロックスカラーの形)、数値の書式(`0x1F` → `31`、`007` → `7`、`1e3` → `1000.0`、JSON の `-0` → `0`)、`1_000` のような YAML の文字列の、他の形式での再解釈(YAML の `1_000` は文字列なので、`"1_000"` になる)。第 5 節の「既知の制限」(長いキー)。
- 往復で保たれると期待される値(実装時の試験の対象): 文字列(`yes`、`no`、`on`、`off`、`1`、`1.5`、`null`、`~`、`true`、`false`、`<<`、空文字列、前後に空白がある文字列、`a: b`、改行・タブ・引用符・バックスラッシュ・制御文字・日本語・絵文字を含む文字列、長い文字列)、整数(`long` の最小値・最大値、0、2^53 + 1 などの 2^53 を超える整数)、浮動小数(`1.0`、`-0.0`、`1.5e-7`、`1e21`、`0.1`、`5e-324`、最大値。NaN、±∞ は YAML 内だけ)、真偽値、null、空のリスト・空のマップ、入れ子のリスト、リストの中のマップ、型が混在するリスト、`on` キー。
- **実装時の必須の試験(往復)**: ランダムに作った 1 万個以上の木(深さ 4 まで。文字列は、`yes`・`~`・`<<`・`a: b`・`#`・`:`・`,`・`[`・`{`・`&`・`*`・`!`・`|`・`>`・`'`・`"`・`%`・`@`・`` ` ``・`\`・タブ・改行・CR・U+0085・U+2028・U+FEFF・U+FFFE・U+007F・制御文字・`é`・日本語・絵文字(サロゲートの対)・全角空白などの文字と、キーワードの語からランダムに組み立てたもの。浮動小数は、ビット列からランダムに作ったものと境界の値。整数は、範囲の両端、2^53 + 1、ランダム)を、JSON と YAML に書き出し、読み戻した木が、元の木と等しいこと。**サロゲートの対を含む文字列で、UTF-16 の対が保たれること**を含める。
- ただし、**NaN と無限大を含む YAML は、JSON に変換できない**(第 5 節)。また、**範囲外の数**は、どちらにも変換できない。

## 10. エラーの構造と表示

型の骨格(例。種類は `enum ConvertErrorKind`。名前空間 `Conductor.Convert`)。

```csharp
namespace Conductor.Convert;

public enum ConvertErrorKind
{
    FileMissing,
    Unreadable,
    TooLarge,
    Syntax,
    Unrepresentable,
    RootNotMap,
}

public sealed record ConvertError(
    ConvertErrorKind Kind,
    string File,        // 入力ファイルの表示用の名前
    int? Line,          // 1 始まり。null は行なし
    string? KeyPath,    // 表せない値の場所。null は場所なし(空文字列にしない)
    string Reason);     // 固定の文(日本語)。入力の値・ライブラリのエラー文は含まない
```

| フィールド | 内容 |
|------------|------|
| `File` | 入力ファイルの表示用の名前 |
| `Line` | 行番号(1 始まり)。位置が分かるときだけ |
| `KeyPath` | 表せない値の場所(キーの経路)。値そのものは含まない |
| `Kind` | 種類 |
| `Reason` | 固定の文(入力の値・ライブラリのエラー文は含まない) |

種類の識別子(下の表の「識別子」)は、[03 第 12.1 節](03-definition-format.md)と同じく、`enum` の名前の先頭を小文字にしたもので、`switch` 式の対応表で持つ。単体テストで、6 件が、識別子・日本語・英語とも、空でなく、互いに異なることを確かめる。

種類(6 種):

| 識別子 | 日本語 | 英語(英語のメッセージのとき) |
|--------|--------|----------------------------|
| `fileMissing` | 入力ファイルが存在しません | input file does not exist |
| `unreadable` | 入力ファイルを読めません | cannot read input file |
| `tooLarge` | 入力が大きすぎます | input is too large |
| `syntax` | 文法の誤りです | syntax error |
| `unrepresentable` | 相手の形式で表せない値があります | value cannot be represented in the target format |
| `rootNotMap` | 最上位がキーと値の集まり(マップ)ではありません | top level is not a map |

ライブラリ(呼び出し側)の表示:

```
<file>:<line>: <種類の文>: <reason>(場所: <key_path>)    行も場所もあるとき
<file>: <種類の文>: <reason>                              どちらも無いとき
```

行だけ・場所だけのときは、それぞれ `<file>:<line>: <種類の文>: <reason>`、`<file>: <種類の文>: <reason>(場所: <key_path>)` となる。`(場所: …)` は、`KeyPath` があるときだけ、末尾に付く(直前に区切りの空白はない)。`<file>` は、制御文字・書式文字・サロゲート(U+D800〜U+DFFF)をエスケープし、エスケープ後の文字数で 256 文字までに切る(超えるときは末尾に `…`。エスケープの規則は [03 第 12.2 節](03-definition-format.md))。

`conductor convert` の失敗の表示(標準エラーの 1 行、終了コード 67):

```
conductor: error: <file>[:<line>]: <種類の文(言語による)>: <reason> (<at|場所>: <key_path>)
```

`<reason>` は日本語のまま。`(at: …)` は英語のメッセージ、`(場所: …)` は日本語のメッセージ(言語の選び方は [08](08-output-and-i18n.md))。`(…)` の前に半角スペース 1 個。`KeyPath` がないときは `(…)` を付けない。`<file>`・`<reason>`・`<key_path>` は、制御文字・書式文字・サロゲートをエスケープして出す(ここでは文字数で切らない。`key_path` の中のキー名は、第 5 節の規則で 64 文字に切られている)。**サロゲートのエスケープが要る理由**: コマンドラインの引数のファイル名に、UTF-8 として不正なバイトがあるとき、.NET が `string` にどう入れるか(U+FFFD に置き換えるか、単独のサロゲートか)は未確認([08](08-output-and-i18n.md)で決める)。単独のサロゲートが入りうるなら、そのまま標準エラーに UTF-8 で書くと、符号化が失敗または置き換えになる。実行例:

```
conductor: error: n.yaml: value cannot be represented in the target format: NaN と無限大は JSON で表せません (at: a)
conductor: error: x.json:3: syntax error: JSON の文法に誤りがあります
conductor: error: x.yaml: top level is not a map: 文書が空です
conductor: error: m.yaml: syntax error: 複数の文書は書けません(1 ファイルに書ける文書は 1 つです)
```

### 理由の一覧(日本語の原文。英語版はない)

| 理由 | 使われる種類 |
|------|--------------|
| `指定の場所にファイルがありません` | `fileMissing` |
| `読み取りの権限がありません` / `読み取りに失敗しました` / `通常のファイルではありません` / `UTF-8 として読めません` | `unreadable` |
| `入力が上限(1 MiB)を超えています` / `要素数が上限(100000)を超えています` / `文字の大きさが上限(16 MiB)を超えています` | `tooLarge` |
| `YAML の文法に誤りがあります` / `JSON の文法に誤りがあります` / `キーが重複しています` / `キーは文字列で書きます` / `タグは使えません` / `複数の文書は書けません(1 ファイルに書ける文書は 1 つです)` / `アンカーが自分自身を含んでいます` / `マージキーの値がマップではありません` / `入れ子が深すぎます(上限は 32 段)` | `syntax` |
| `数値が表せる範囲を超えています` / `NaN と無限大は JSON で表せません` / `キーが長すぎます(上限 1024 文字)` | `unrepresentable` |
| `最上位がマップではありません` / `文書が空です` | `rootNotMap` |

### 11.2 失敗の例

| 入力(`--to json`、YAML) | 結果 |
|------|------|
| `a: 1\nb: 2\na: 3\n` | `syntax` 3 行目、`キーが重複しています` |
| `- 1\n- 2\n` | `rootNotMap` 1 行目、`最上位がマップではありません` |
| `` (空) | `rootNotMap`、行なし、`文書が空です` |
| `---\n` | `rootNotMap` 1 行目、`最上位がマップではありません` |
| `a: 1\n---\nb: 2\n` | `syntax`、`複数の文書は書けません(1 ファイルに書ける文書は 1 つです)` |
| `a:\n  <<: 5\n` | `syntax` 2 行目、`マージキーの値がマップではありません` |
| `a:\n  <<: ~\n` | 同上 |
| `a: &r [*r]\n` | `syntax` 1 行目、`アンカーが自分自身を含んでいます` |
| `a: *x\n` | `syntax` 1 行目、`YAML の文法に誤りがあります` |
| `a: .nan\n` | `unrepresentable`、`NaN と無限大は JSON で表せません`、場所 `a` |
| `a: [1, .inf]\n` | `unrepresentable`、場所 `a[1]` |
| `a: 9223372036854775808\n` | `unrepresentable`、`数値が表せる範囲を超えています`、場所 `a` |
| `1: x\n` | `syntax` 1 行目、`キーは文字列で書きます` |
| `a: !!str 1\n` | `syntax` 1 行目、`タグは使えません` |
| `a:\n  <<: {x: 1}\n  <<: {y: 2}\n` | `syntax` 3 行目、`キーが重複しています` |
| `a: 1\n---\n` | `syntax`、`複数の文書は書けません(1 ファイルに書ける文書は 1 つです)` |
| `a: "\ud800"\n` | `syntax` 1 行目、`YAML の文法に誤りがあります` |
| `a: 1\n---\nb: [1\n` | `syntax`、`YAML の文法に誤りがあります`(2 つ目の文書の文法の誤りが先。行は [03 第 13.4 節](03-definition-format.md)の規則) |

| 入力(`--to yaml`、JSON) | 結果 |
|------|------|
| `{"a":1,}` | `syntax` 1 行目、`JSON の文法に誤りがあります` |
| `{"a":1,"a":2}` | `syntax` 1 行目、`キーが重複しています` |
| `[1]` | `rootNotMap` 1 行目、`最上位がマップではありません` |
| `null` | `rootNotMap` 1 行目、`最上位がマップではありません` |
| `` (空) | `syntax`(JSON は値が 1 つ必要) |
| `{"a": 1e400}` | `unrepresentable`、`数値が表せる範囲を超えています`、場所 `a` |
| `{"a": 9223372036854775808}` | `unrepresentable`、同上 |
| `{"a": 9223372036854775807}` | 受理(`a: 9223372036854775807`) |
| キーが 1,025 文字のオブジェクト | `unrepresentable`、`キーが長すぎます(上限 1024 文字)`、場所は 64 文字で切った名前 |
| `// c\n{}` | `syntax` |

### 11.3 成功の例(`--to json`、YAML)

| 入力 | 出力(値) |
|------|------|
| `a: \|\n  x\n  y\nb: >\n  p\n  q\n\n  r\nc: \|-\n  k\n` | `a` は `"x\ny\n"`、`b` は `"p q\nr\n"`、`c` は `"k"`(出力は `{`、`  "a": "x\ny\n",`、`  "b": "p q\nr\n",`、`  "c": "k"`、`}`) |
| `a: foo\n  bar\n  baz\n` | 値 `"foo bar baz"` |
| `a: 0o17\nb: 0x1F\nc: 1e3\nd: .5\ne: 1.\nf: 007\ng: yes\nh: ~\n` | 値 15、31、1000.0、0.5、1.0、7、`"yes"`、`null` |
| `a: 2001-01-01\nb: 12:30:00\nc: 1_000\n` | 値 `"2001-01-01"`、`"12:30:00"`、`"1_000"`(すべて文字列) |
| `b: &b {x: 1}\na:\n  <<: [*b, {x: 2, y: 3}]\n  y: 9\n` | 出力のキーの順は `b`、`a`。`a` は `{"x": 1, "y": 9}`(自身のキーが優先、リストは先頭が優先。取り込まれた `x` は `<<` の位置に入る) |

| `a: "<<"\n"<<": 1\n` | キー `<<` は通常のキー(`"<<": 1`)。値 `"<<"` は文字列 |

## 12. 未確認事項

- YAML の受理する文法の細部(引用符なしのスカラー中の特殊な文字、他の版のライブラリの挙動)と、ライブラリの採否: [03 第 7・18 節](03-definition-format.md)と同じ。YAML ライブラリ(YamlDotNet)の採否は、そこに書いた受け入れ試験で決める。
- YAML の文法の誤りの行番号の厳密な規則(ライブラリの検出位置による。[03 第 13.4 節](03-definition-format.md)の表は、期待する値で、未確認)。
- 第 3 節: `UnauthorizedAccessException` が、ディレクトリを開いたときに投げられること、`FileStream.CanSeek` でパイプ・デバイスを見分けられること、FIFO の `Open` がブロックするか。Windows での標準出力の改行(CRLF への変換の有無。`OpenStandardOutput` に直接書くので、起きないと考えられるが、未確認)と、`IOException` の分類。
- 第 6.1 節: `double.ToString("R", InvariantCulture)` の出力の形(指数形への切り替えの閾値、指数部の桁数、`-0` の表記)。この規定は、桁と指数を取り出して並べ直すので、形に依存しないが、実装時に、ランダムな 20 万個以上の `double` で往復と書式を確かめる。`double.IsNegative` の公式ドキュメントでの確認。
- 第 7 節: `System.Text.Json` の書き出しの、エスケープの既定の挙動(使わないので、確認していない)。JSON の出力で、U+007F〜U+009F などを `\u` でエスケープする(この仕様で決めた。他の実装が、これらをそのまま書いても、木は同じだが、出力の文字列は一致しない)。
- 非 ASCII のキー・値の YAML 出力は、常に二重引用符で囲む(この仕様で決めた)。plain で書ける範囲を広げる変更は、この仕様の変更になる。
- マージで取り込まれる値の中の表せない値の場所(`a.<<.x`)は、この仕様の決定であり、他の規定による裏づけはない。
- `--to yaml` で、1,024 文字を超えるキーを拒否する規定は、YAML の読み取りの単純キーの上限による(YamlDotNet の `Scanner` の既定が 1,024。[03 第 5.1 節](03-definition-format.md))。フロー形式の中の長いキーに同じ制限が掛かるかは未確認だが、この変換器はブロック形式だけを書くので、使わない。第 5 節の既知の制限(非 BMP の文字、引用符つきのキーの長さ)は、実機で未確認。
- 変換の入力の大きさの上限(1 MiB)の近くの入力の、実行時間とメモリ(`StringBuilder` の大きさを含む)の測定は、実装時に行う。
